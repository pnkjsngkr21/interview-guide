Chapter 7 — I/O, NIO & Networking

7.1 The java.io Stream Model

Every classic Java I/O class is a thin decorator over four abstractions. Two axes decide which class you want: bytes or characters, and unbuffered or buffered. Getting the axes straight explains the whole hierarchy without memorising it.

  bytes              characters
  ------              ---------
  InputStream         Reader
  OutputStream        Writer

  unbuffered  InputStream / OutputStream      one syscall per call
  buffered    BufferedInputStream / BufferedOutputStream
              BufferedReader / BufferedWriter   amortises it

  the bridges
  InputStreamReader   InputStream  --decode--> Reader      charset lives here
  OutputStreamWriter  OutputStream <--encode--  Writer
  DataInputStream     byte level: readInt(), readUTF()
  BufferedReader.readLine()     the one method Reader adds

The performance consequence is the whole reason this chapter exists. An unbuffered stream does one read syscall per call, so reading a file with a 1 KB buffer and a byte-at-a-time loop makes a million syscalls for a megabyte. Wrapping in a BufferedInputStream makes it about a thousand. Files.readString and Files.newBufferedReader buffer for you, which is why reaching for FileInputStream directly is almost never the right first move — Files.newInputStream is the modern equivalent, and it also takes a Path rather than a File.

Interview trap

A stream you never explicitly close leaks a file descriptor, and the leak is invisible until the process runs out of them and every subsequent new FileInputStream throws — which, on Linux, is around 1024 open files. Two asymmetries matter. First, wrapping is what obliges you to close: closing the outermost stream closes everything it wraps, so try-with-resources only needs the outermost resource. Second, Scanner closes the underlying stream when it is itself closed, so a Scanner passed into a method that does not close it will close the caller’s stream as a side effect. Scanner is also markedly slower than BufferedReader and is not the right tool for large input.

Character encoding is decided by the bridge, not by the stream. new InputStreamReader(in) uses the platform default charset, which differs between a developer machine and a container and is a long-standing source of mojibake. Always pass the charset: new InputStreamReader(in, StandardCharsets.UTF_8), or use Files.readString(path), which is UTF-8 by definition.

// try-with-resources: the outermost resource is the only one declared
try (BufferedReader in = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line;
    while ((line = in.readLine()) != null) {          // readLine() excludes the terminator
        process(line);
    }
}

// modern equivalents that avoid the object graph entirely
String text  = Files.readString(path);                 // UTF-8
List = Files.readAllLines(path);               // whole file, UTF-8
byte[]  bytes = Files.readAllBytes(path);

7.2 Path and Files — Replacing java.io.File

Everything in java.io is built around java.io.File, which is a mutable, platform-dependent String wrapper with methods that touch the filesystem directly — delete() on a directory, exists() as an instance method. java.nio.file splits that in two: Path is an immutable reference to a location with pure navigation methods, and Files is a static utility of operations against it. Nothing about a Path requires the file to exist.

java.io.Filejava.nio.file.Path
MutabilityMutable — renameTo, delete change itImmutable — every resolve/getParent returns a new object
OperationsInstance methods on the path objectStatic methods on Files taking a Path
FilesystemOne, always the defaultPluggable — FileSystems also gives you zip and jar
Existenceexists() on the objectFiles.exists(p), or no check at all until you touch it
ErrorsReturns false for most failuresThrows IOException; use Files.deleteIfExists for the tolerant form

Two navigation pairs are constantly confused. resolve is lexical concatenation — base.resolve("a/../b") yields base/a/../b with the .. still in it. normalize is lexical and removes . and .. without touching disk. toRealPath resolves symlinks and requires the path to exist. To collapse .. safely you need base.resolve(other).normalize(), and to be safe against a symlink escaping the base directory you need toRealPath() — which is a security control, not a convenience, in any code that takes a user-supplied path.

Must remember

Files.walk and Files.list return a Stream that holds an open directory handle. Consuming it lazily and abandoning it leaks a file descriptor per call. Both must be used in try-with-resources. Files.walkFileTree is the callback form and needs no such care — and its SimpleFileVisitor returns a FileVisitResult, so you can CONTINUE, SKIP_SUBTREE or TERMINATE.

For events rather than snapshots, WatchService registers a directory and delivers ENTRY_CREATE, ENTRY_DELETE, ENTRY_MODIFY. Two behaviours make it unusable as a correctness guarantee: events can coalesce (several rapid modifications may arrive as one), and they can be missed entirely if the watcher is not re-registered promptly. Treat it as a hint to re-scan, never as the source of truth.

7.3 Buffers, Channels and Selectors

This is the part of Java I/O that is genuinely different, and the part almost nobody is asked about. A ByteBuffer is a fixed-size array plus three indices, and the indices move in a pattern that has to be right or the buffer silently produces zeros.

  +-------------------------------------------------------+
  |  | capacity                                          |
  |  +-------------+ limit                               |
  |  +------+------+                                      |
  |  | mark | position ------------>                     |
  |  +------+                                      +-----+
  +-------------------------------------------------------+

  WRITE SIDE (filling a buffer)
      position advances with each put()   limit == capacity
      flip()   -> limit = position; position = 0;   now READ side
      clear()  -> position = 0; limit = capacity;     ready for reuse
      rewind() -> position = 0;                      keeps limit as-is
      compact()-> moves unread bytes to the front, position = n

  THE CLASSIC BUG: put() without a matching flip() before get().
  position == limit, so remaining() == 0 and you read nothing —
  or worse, you read stale bytes from a previous round trip.
Interview trap

There are two ByteBuffers and they are not interchangeable. allocate(n) returns a buffer on the heap — its backing array is a byte array, and getting at it is an array copy that the JIT can usually eliminate when it can prove the array does not escape. allocateDirect(n) allocates outside the JVM heap, so the OS can write into it directly through a channel with no intermediate copy; the cost is that access goes through slower native memory. Direct buffers are what you want for socket channels and file mapping, and you do not pay off-heap accounting for them.

A Channel is the transport; a Buffer is the staging area between it and your code. The design separates the two because one channel can read into any buffer position, and one buffer can be reused across channels. FileChannel, SocketChannel and ServerSocketChannel are all selectable, which means one thread can drive many open connections.

try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    ByteBuffer buf = ByteBuffer.allocateDirect(64 * 1024);
    while (ch.read(buf) != -1) {
        buf.flip();                       // write side done -> read side
        while (buf.hasRemaining()) {
            process(buf.get());           // 64k syscalls -> one
        }
        buf.clear();                      // ready to fill again
    }
}

Selector is how a single thread handles many channels: register them, then select() returns as soon as at least one is ready, without blocking on any one of them. That is the pre-JDK-11 answer to socket-per-thread scaling, and it is still how the JDK’s own HttpClient and Netty work. AsynchronousChannel (NIO.2) goes further and completes an operation via a CompletionHandler or a Future, which is closer to an async model but has historically been less widely used than Selector.

In production

The performance story for file I/O is not the buffer size — it is whether you are copying at all. FileChannel.map(MapMode.READ_ONLY, 0, size) returns a MappedByteBuffer: the OS maps the file into your address space, so reads become memory reads with no syscall and no copy, and the OS pages them out under pressure. transferTo and transferFrom move bytes between channels inside the kernel, bypassing your buffer entirely. In a long-running process, note that a mapped file can hold the mapping until it is force-unmapped, which is one of the reasons you System.gc() in some unmapping folklore — that is a hint about the collector, not a guarantee.

7.4 Sockets and TCP

A Socket is a TCP connection, and its default behaviour is the thing that bites in production: reads block indefinitely. Three settings turn a hung peer from an outage into an error you can handle.

SettingDefaultPrevents
connect(addr, timeout)Blocks until the OS gives up (minutes)A firewall silently dropping SYNs holding a thread for 2 minutes
setSoTimeout(ms)0 = infiniteA half-open connection wedging a reader thread forever
setTcpNoDelay(true)off (Nagle enabled)Nagle’s algorithm delaying small writes by up to 40 ms — the classic “my request takes 40 ms longer on the first byte”

Nagle batches small writes to fill a segment, trading latency for throughput. It is right for bulk transfer and wrong for request/response, which is nearly every web service. HttpURLConnection sets it; raw Socket does not. And Socket is bidirectional over one connection, so a request/response protocol needs a framing discipline on the read side — read until a delimiter, or read exactly the declared length, and never assume one read() returns one message.

7.5 The JDK HTTP Client

java.net.http.HttpClient (Java 11) is the third implementation in the JDK, after HttpURLConnection and the Apache/OkHttp options people actually use. It is built on Selector, supports HTTP/2 by default over TLS with ALPN, and its async API returns a CompletableFuture — so it composes with the rest of the JDK concurrency model rather than with a callback library.

// shared client: constructing one per request is the classic HttpClient mistake,
// because each owns a selector thread and a connection pool
static final HttpClient CLIENT = HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_2)
        .connectTimeout(Duration.ofSeconds(3))
        .followRedirects(HttpClient.Redirect.NORMAL)
        .build();

HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/orders"))
        .timeout(Duration.ofSeconds(10))          // response timeout, distinct from connect
        .header("Accept", "application/json")
        .GET()
        .build();

HttpResponse res = CLIENT.send(req, HttpResponse.BodyHandlers.ofString());
System.out.println(res.statusCode() + " " + res.body());

// async, as a CompletableFuture
CLIENT.sendAsync(req, HttpResponse.BodyHandlers.ofString())
      .thenApply(HttpResponse::body)
      .thenAccept(this::handle);
Interview trap

Three things are commonly wrong. One: connectTimeout is set on the client and covers only establishing the connection; the response timeout is set per request via HttpRequest.Builder.timeout, and forgetting it means a server that accepts and then stalls hangs you indefinitely. Two: HttpClient is immutable and thread-safe, so share one instance; it became AutoCloseable in JDK 21, and on an earlier baseline each instance keeps its selector thread alive for the life of the process. Three: BodyHandlers.ofInputStream() returns a stream the response does not close for you — unlike ofString and ofFile, which consume and close it. Using it without try-with-resources leaks the connection back out of the pool.

For a plain file-over-HTTP body, BodyHandlers.ofFile(path) writes straight to disk instead of buffering the whole response in memory. For one-shot scripts this client is enough. For anything at real throughput you are usually still choosing an HTTP client on pooling, connection eviction, observability and gRPC/websocket support — but you should know that the JDK one is no longer the embarrassing choice it was in 2015.

Chapter summary

The classic model is decorators over four types, where buffering and the choice of bridge are what make it fast and what decide the charset. The modern model separates a Path (immutable, pure navigation) from Files (static operations), and separates a Buffer (your three indices, which you must flip correctly) from a Channel (the transport). Networking adds exactly one real requirement beyond blocking streams: never block indefinitely — set connect timeout, read timeout, and TCP_NODELAY, and use the JDK’s own HttpClient rather than hand-rolling request framing.
