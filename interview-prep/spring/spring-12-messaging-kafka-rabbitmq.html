About This Guide

This is a twelve-volume study guide to the Spring ecosystem, written for engineers who already know Java and are preparing for senior and staff-level backend interviews. It is not a tutorial. Nothing here explains what a class is.

This volume covers the two messaging models and the Spring APIs on top of them. It exists because KafkaTemplate, @KafkaListener and @RabbitListener were entirely absent from the first eleven volumes, while Volume 11 spent a chapter arguing that a system needs an outbox pattern without ever naming the broker that would carry it. That is now closed.

Must remember — the versions this volume is written against

spring-kafka, spring-amqp and spring-rabbit 4.1.1, with Spring Boot 4.1.1. These are the current GA lines as of this writing; 4.0.x and 3.3.x are maintenance trains. This matters more here than in other volumes because major API changes landed in the 4.0 line — error-handler classes were removed, retry classification was reworked, and a producer-side API people had learned does not exist. Anything you remember about spring-kafka from before 3.0 needs checking before you say it in an interview.

How This Guide Is Structured

Each chapter is a sequence of numbered sections, then Common Mistakes, then Interview Questions, then Further Reading. The mistakes are the ones that reach production; the questions are the ones you are actually asked. Diagrams are ASCII, and are not code — do not paste them anywhere that expects to compile.

Chapter 1 — The Two Models

Before any Spring API, one distinction has to be right, because almost every configuration decision follows from it: a queue delivers a message to one consumer; a log stores a message until every consumer has read it. RabbitMQ is the first. Kafka is the second. Everything people get wrong in interviews — why concurrency does not give ordering, why a Rabbit consumer that throws loops forever, why Kafka replays — follows from taking the wrong model into the design.

1.1 Log Versus Queue

A queue holds a message and hands it to one consumer, then it is gone. Ten consumers on one queue is work distribution: ten times the throughput, and each message handled once, by exactly one of them. A log is an ordered, append-only sequence with a per-partition offset. Each consumer keeps its own position in it and advances independently, so ten consumers on one log is fan-out: every consumer sees every message.

QUEUE (RabbitMQ) — one consumer per message

   producer ──▶ [ msg1 ][ msg2 ][ msg3 ] ──▶ consumer A gets msg1
                   ▲                        consumer B gets msg2
                   └── exactly one, then gone    consumer C gets msg3

LOG (Kafka) — every consumer sees every message

   producer ──▶ log: [0][1][2][3][4][5][6][7]
                  │                      │
                  ├──── consumer A ──────┤  reads all 8, offset = 8
                  ├──── consumer B ──────┤  reads all 8, offset = 8
                  └──── consumer C ──────┘  replays from 0 whenever it likes

   the log does not delete on read — retention (time or size) does

The operational consequence is the one to say out loud: Kafka's retention is what makes replay possible, and that is what gives you the audit log, the rebuild-the-read-model trick, and the ability to introduce a new consumer without disturbing the old ones. A queue has no such thing — once acknowledged, the message is gone, and a consumer that was down missed it. If a question asks why you would replay events rather than snapshot state, this is the whole answer.

Trade-off — the question behind every broker choice

“Can a new consumer read history?” Kafka: yes, from any retained offset, and it costs nothing because the data is already there. RabbitMQ: no — the messages were consumed and are gone; you would need a second exchange feeding a fresh queue, which means changing the producers. This single property drives most of the “why Kafka” answers: event sourcing, cache rebuilds, feeding a new downstream, and letting analytics replay without touching production.

1.2 What a Consumer Group Actually Is

A consumer group is a set of consumers that share the work of the partitions they are assigned. The guarantee is one assignment rule, and everything else follows: each partition is assigned to exactly one consumer in the group at a time. Two consumers in the same group never process the same partition in parallel. Two consumers in different groups each get all the partitions, independently.

topic: orders, 3 partitions

GROUP "billing"  ──▶ p0→C1   p1→C2   p2→C3     work split, each partition once
                     (C1 and C2 never touch p0)

GROUP "analytics" ──▶ p0→A1   p1→A2   p2→A1     independent, full copy

same group, 5 consumers, 3 partitions
                     ──▶ p0→C1  p1→C2  p2→C3  C4 idle  C5 idle
                          surplus consumers receive nothing and sit there

That last line is the answer to the most common Kafka interview question. Raising concurrency above the partition count does nothing except start idle consumers. To scale a partition-ordered stream you add partitions, and you accept that ordering is now only guaranteed within each partition. Ordering across the whole topic is gone, permanently, and no amount of consumer tuning restores it.

1.3 Ordering, Partitions and the Key

Kafka guarantees order within a partition, and nothing across partitions. So the key you produce with decides which orderings you have. Same key → same partition → ordered. Different keys → different partitions → no relationship between them.

// Same orderId always lands on the same partition, so all events
// for one order arrive in the order they were produced.
kafkaTemplate.send("orders",
        new ProducerRecord<>("orders", order.getId(), event));

// No key: the partitioner picks, effectively at random, so two events
// for the same order can arrive reversed.
kafkaTemplate.send("orders", event);

The failure this prevents is subtle and worth describing precisely, because it is not "messages arrive out of order" in the abstract. It is: an OrderCreated and a subsequent OrderCancelled for the same order are processed by the same consumer instance in creation order, so the consumer's in-memory model never sees a cancellation for an order it has not seen created. Remove the key and both events can land on different partitions, be assigned to different consumers, and the cancellation is processed first — leaving an order cancelled that the system believes does not exist, or a phantom reactivation. Keying by aggregate id is the single highest-value habit in this chapter.

Interview trap — more partitions is a semantic change, not a scaling knob

Adding a partition to increase parallelism is correct and routine, and it also lowers your ordering guarantee, because ordering was per-partition and you just made the partitions finer. The honest framing for a scaling review: partitions are the unit of parallelism and the unit of ordering, so raising them trades the second for the first. The thing that is not true is that a partition is processed in parallel — it never is, no matter how many consumers are in the group.

1.4 Delivery Semantics — the Only Three That Are Real

“Exactly once” is the phrase that causes the most damage in messaging interviews, because it is not a broker feature — it is a property of what you built, and only two are achievable without extraordinary effort.

SemanticWhat it meansHow you get it
At-most-onceMessages may be lost, never duplicatedCommit the offset before processing. Fast, and you have chosen to lose data on a crash
At-least-onceMessages are never lost, may be duplicatedThe default. Commit after processing. The only safe option without idempotency, and therefore the one you must design for
Exactly-onceNeitherNot a broker switch. Requires idempotent processing, or a transaction spanning the read and the write (§2.5)

At-least-once is the honest default, and it forces the only discipline that matters: every consumer must be idempotent, because it will receive the same message twice and that is not a bug, it is the contract. Volume 11 develops this in its saga and outbox chapters; §4.4 here is the operational form of the same rule.

Must remember — duplication is the default, so design for it first

The failure nobody plans for is a consumer that is not idempotent, because the duplicates only appear when something goes wrong — a rebalance, a timeout, a deploy — which is exactly when you are least able to investigate. The two operations that must be idempotent are the ones with an externally visible effect: charging a card, refunding an order, sending an email, incrementing a counter. A consumer that logs and moves on is fine. A consumer that sends an email is a support ticket every time it replays.

Common Mistakes

  • Treating Kafka as a queue with extra steps. If you cannot say what happens to a message after it is acknowledged, you do not yet know which model you have.
  • Raising concurrency above the partition count and reporting no improvement, then raising it again. The surplus consumers are idle by construction.
  • Producing without a key, then debugging an out-of-order bug that is really an absence of ordering.
  • Adding partitions as a pure scaling move without saying what ordering guarantee was given up.
  • “Kafka gives exactly-once.” It gives at-least-once by default; exactly-once is something you build, over a sequence rather than a single step (§2.5).
  • Designing a consumer that is not idempotent, on the assumption that duplicates are rare. They are guaranteed under rebalance.

Interview Questions — The Two Models

Q1 When would a queue be a better choice than a log? TRICKY

When you need per-message routing and priority, or when the work is genuinely “do this once” rather than “keep this state”. Concretely: a queue gives you basic.priority and per-message TTL, which a log does not; a queue message is consumed by one worker, which is the correct semantic for a command like “resize this image” where running it twice is wasteful rather than merely redundant. A log is the wrong shape when consumers need different views of the same events — a queue forces you to publish once per consumer type, which is the fan-out cost Kafka removes. The honest answer is that both are defensible and the deciding question is whether you will ever want to replay.

Q2 Your topic has 6 partitions and you set concurrency=10. What happens? STAFF

Ten consumers start, six receive a partition, and four sit idle doing nothing — because the guarantee is that each partition is assigned to exactly one consumer in the group, so a seventh consumer has nothing to consume. Throughput is capped at six consumers regardless. The fixes are to add partitions (which trades away per-partition ordering, so it is a semantic decision) or to change the partitioning so the hot key is not the bottleneck. The follow-up that shows depth: asking whether the key distribution is skewed, because six partitions with five keys means one partition is doing most of the work and adding consumers has not helped because that partition is the constraint. Idle consumers in a consumer group are a symptom, not a capacity problem.

Q3 Explain “exactly-once” in a Kafka context. TRICKY

It is not a broker feature, and that is the point of the question. The official qualifier is that exactly-once applies to a sequence: for a read → process → write cycle, the sequence completes exactly once, while the read and the process individually remain at-least-once. In practice you get there two ways — make the consumer idempotent so a replay is indistinguishable from the first delivery, or use a transaction spanning the consume and the produce (§2.5), which has its own caveat because the database commit and the Kafka commit cannot be one atomic thing. Anyone who says “Kafka gives exactly-once, so I do not need idempotency” is the answer this question is looking for.

Q4 How do you guarantee ordering for events about one aggregate? TRICKY

Key every event by the aggregate id, so all of them hash to the same partition and are read by the same consumer in order. The alternative — one topic per aggregate — is correct but operationally absurd. The honest caveat is that ordering is guaranteed within a partition and per key, so two different aggregates have no order relationship to each other, which is usually exactly what you want. The follow-up worth volunteering: rebalancing can briefly interleave, and a retry that seeks backwards replays in order but the consumer must not assume a record it has already processed will never reappear.

Q5 A team wants a new read model built from existing events without touching production. Which model makes this possible and why? STAFF

A log — Kafka. New consumer groups can start from any retained offset, so you add a consumer in a new group, let it read history, and build whatever projection you want. Production is not involved at all, because adding a group does not disturb existing groups or their offsets. With a queue this is impossible: the messages were consumed and deleted long ago, and getting them again would mean changing the producers to publish a second time. Retention is the enabler, so the real question to ask back is how long the topic retains data and whether that is longer than the rebuild you are planning.

Chapter 2 — Spring for Kafka

Everything in this chapter is verified against spring-kafka 4.1.1 source. Where the answer differs from what you will read in older tutorials, that is called out — because in this API the defaults have moved and some classes no longer exist.

2.1 @KafkaListener: id and idIsGroup

@KafkaListener has two attributes that look unrelated and are actually one decision. id is the container's unique identifier — and, unless you stop it, it is also your group.id.

@KafkaListener(id = "orders-billing", topics = "orders")
public void handle(OrderEvent event) { ... }

The precedence, from the source:

  1. An explicit groupId always wins.
  2. Otherwise, if idIsGroup is true (the default) and id is set, id becomes the group id.
  3. Otherwise the group.id from the consumer factory config is used.

So two listeners with the same id are in the same consumer group and will split the partitions between them. Two listeners with different ids are separate groups and each sees everything. That is occasionally the intent and almost always an accident.

Interview trap — idIsGroup defaults to true, and the javadoc reads as though it does not

The source is unambiguous: boolean idIsGroup() default true;. But the attribute's javadoc ends with the phrase “@return false to disable”, which reads exactly like a default of false — and that phrasing is where the folk answer comes from. The processing logic branches on kafkaListener.idIsGroup() directly, so true is what actually happens. The practical consequence: renaming a listener's id silently moves it into a different consumer group, which restarts it from the committed offset for a group that does not exist yet — the full retention window, or from the earliest available offset. That is a replay bug that presents as a slow production incident.

2.2 AckMode: Seven Values and a Default Nobody Guesses

The first thing to get right is that there are seven, not the four the older tutorials list. ContainerProperties.AckMode in 4.1.1:

ValueWhen the offset is committed
RECORDAfter each record is processed by the listener
BATCHAfter all records from the previous poll have been processed. This is the default.
TIMEAfter ackTime has elapsed
COUNTAfter ackCount records
COUNT_TIMEWhichever of ackCount / ackTime comes first
MANUALThe listener acks; commits are queued and flushed when the poll's records are all processed
MANUAL_IMMEDIATEThe listener acks; the commit happens immediately if it occurs on the consumer thread
Interview trap — the default is BATCH, not RECORD

The field is private AckMode ackMode = AckMode.BATCH;, and Spring Boot does not change it — spring.kafka.listener.ack-mode has no default in Boot's metadata and is applied only when you set it. Most people answer RECORD, and the difference is not cosmetic: under BATCH a failure part-way through a poll commits the offsets of the records already processed, and only the remaining ones are rewound (§2.4). Two runtime overrides exist and are worth knowing: a container with no consumer group id and explicit partition assignment is forced to MANUAL, and asyncReplies with a non-manual mode is also forced to MANUAL.

The practical reason to prefer RECORD over BATCH is the mirror image of the trap: it commits per record, so a crash mid-batch replays more — but replay is safe only because you made the consumer idempotent. If you have not, BATCH gives you fewer duplicates at the cost of losing the ones that were mid-flight. Neither is correct without the idempotency work.

2.3 Error Handling — Where the Defaults Bite

Two objects, and they are not alternatives. DefaultErrorHandler is the retry-and-backoff policy. DeadLetterPublishingRecoverer is what it delegates to once retries are exhausted. You nest them.

DeadLetterPublishingRecoverer recoverer =
        new DeadLetterPublishingRecoverer(kafkaTemplate,
                (record, ex) -> new TopicPartition(record.topic() + "-dlt", record.partition()));

DefaultErrorHandler errorHandler =
        new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L));

@Bean
ConcurrentKafkaListenerContainerFactory<String, Order> factory(
        ConcurrentKafkaListenerContainerFactoryConfigurer configurer,
        ConsumerFactory<String, Order> consumerFactory) {
    var f = new ConcurrentKafkaListenerContainerFactory<String, Order>();
    configurer.configure(f, consumerFactory);
    f.setCommonErrorHandler(errorHandler);   // otherwise: seek, 9 retries, no delay
    return f;
}

Three defaults that surprise people, all from the source:

  • Default failure behaviour is SEEK, not stop. The container rewinds so the message can be replayed — it does not halt the partition. Default backoff is 9 retries with no delay, which is not a retry policy anyone writes deliberately; it is a default.
  • With a transaction manager, no error handler is installed at all, so the exception rolls the transaction back instead. The docs state this explicitly.
  • Unmatched exception types are classified retryable. The classifier's default for anything it does not recognise is true. So an unexpected NullPointerException is retried nine times by default, and your poison message takes nine attempts to reach the recoverer.

The default fatal list is short and specific, and worth knowing because two entries are traps:

DeserializationException.class      // org.springframework.kafka.support.serializer
MessageConversionException.class
ConversionException.class
MethodArgumentResolutionException.class
NoSuchMethodException.class
ClassCastException.class

The first is Spring's DeserializationException, not Kafka's org.apache.kafka.common.errors.SerializationException. Getting that wrong means configuring the fatal list and finding your deserialization failures retried anyway. If you want to invert the default — treat unknown exceptions as fatal — that is a deliberate classifier configuration, and the property to reach for is adding not-retryable exceptions rather than a retryable set.

Interview trap — there is no RetriableException marker interface

People reliably describe a RetriableException marker and a setRetriableExceptions(...) method. Neither exists in modern spring-kafka. The mechanism was replaced by ExceptionClassifier plus ExceptionMatcher, and the vocabulary inverted: you configure what is not retryable via addNotRetryableExceptions. The concept — some exceptions are fatal, some are transient — is right; the API names are from an older version. SeekToCurrentErrorHandler and SeekToCurrentBatchErrorHandler are in the same category: removed in the 3.0 line, replaced by DefaultErrorHandler.

2.4 What Happens When a Listener Throws

This is the single most useful thing to understand about the Kafka container, and the official example is precise enough to quote. If a poll returns six records — two from each of partitions 0, 1, 2 — and the listener throws on the fourth:

poll() returns 6 records:  p0=[1,2]  p1=[1,2]  p2=[1,2]
listener processes 1,2,3 then throws on record 4

  ┌────────────────────────────────────────────────────────────┐
  │ 1. container COMMITS offsets for records 1,2,3             │
  │    "The container commits any pending offset commits       │
  │     before calling the error handler."                     │
  ├────────────────────────────────────────────────────────────┤
  │ 2. DefaultErrorHandler SEEKS back over the REMAINDER only   │
  │    p1 → seek to offset 1        p2 → seek to offset 0      │
  ├────────────────────────────────────────────────────────────┤
  │ 3. next poll() returns the 3 unprocessed records            │
  └────────────────────────────────────────────────────────────┘

  record 4 is retried. records 1-3 are NOT — their offsets are
  already committed, and a later crash cannot bring them back.

Two consequences to state unprompted. First, the container commits before the error handler runs, so anything processed before the failure is durably marked done. Second, this makes the effective semantics at-most-once for the records before the failure and at-least-once for the rest — a mixture nobody chooses deliberately and everybody should be able to explain. Only RuntimeException subclasses reach the error handler; an Error bypasses it entirely.

The mitigation the container itself uses for slow retries is worth knowing, because it explains why a long backoff does not always cause a rebalance: the error handler pauses the consumer and polls it before sleeping, which keeps the group alive through an extended retry sequence.

2.5 Exactly Once, and What It Does Not Cover

KafkaTransactionManager is a PlatformTransactionManager. Configured on the container, it starts a transaction before the listener is invoked; KafkaTemplate operations inside the listener join it; on success the offsets are sent to the transaction via producer.sendOffsetsToTransaction() and then it commits. On failure it rolls back and repositions the consumer so the records come round again.

Here is the qualifier that makes this a real answer rather than a slogan:

“Using transactions enables Exactly Once Semantics (EOS). This means that, for a read → process → write sequence, it is guaranteed that the sequence is completed exactly once. (The read and process have at least once semantics.)”

The parenthetical is the interview answer. Exactly-once covers the sequence, not the individual steps, and it only helps if the thing you are protecting is a Kafka write. The common real requirement — a database write — is not covered, because the database transaction and the Kafka transaction are two separate commits with a gap between them. The documentation is explicit about what happens when the second commit fails after the first has already succeeded: the exception is now thrown to the caller and “applications should take remedial action, if necessary, to compensate for the committed primary transaction.”

Must remember — for database writes, the outbox beats the transaction manager

Chained transactions across a database and a broker do not compose atomically. The pattern that does is the outbox: write the message to a table in the same transaction as the business change, then publish it asynchronously and mark it sent. You get atomicity from the database you already have, and the cost is a relay process plus a deduplication problem at the consumer. Volume 11 chapter 7 develops it; §4.4 here is the operational view. ChainedKafkaTransactionManager is the old answer — deprecated since 2.7, still present in 4.1.1, replaced by KafkaTransactionManager on the container plus @Transactional on the listener.

2.6 KafkaTemplate, and How a Send Fails

KafkaTemplate is the class; KafkaOperations is the interface it implements, and depending on the interface is the better habit. The send methods return CompletableFuture<SendResult<K,V>>.

kafkaTemplate.send("orders", orderId, event)
        .whenComplete((result, ex) -> {
            if (ex != null) {
                // the broker rejected it, or the send timed out
                log.warn("send failed for {}", orderId, ex);
            }
        });

The version boundary matters because it is a common interview and code-review disagreement: send() returned ListenableFuture through the 2.9.x line and returns CompletableFuture from 3.0 onward. If you are reading pre-3.0 code, that is why it looks different.

How a send fails is where the folklore gets active. There is no producer-side error handler — no setErrorHandler on the producer factory, and no producer DefaultErrorHandler. Verified absent from DefaultKafkaProducerFactory, ProducerFactory and KafkaTemplate in 4.1.1. The two real mechanisms are the CompletableFuture callback and a ProducerListener, and Boot wires a LoggingProducerListener by default — which logs errors and does nothing on success. Failures surface as a KafkaProducerException carrying the failed record.

Serialization has a Boot-shaped default that is worth attributing correctly: under Spring Boot, both key and value serializer default to StringSerializer. Plain spring-kafka's DefaultKafkaProducerFactory has nullable serializers and applies no such default. So “keys and values are strings by default” is true of a Boot application and not a spring-kafka guarantee — and it is the reason a Boot app that produces a POJO without configuring a serializer fails with a class-name error rather than a serialization error.

2.7 Concurrency Is Consumers, Not Parallelism

The concurrency attribute sets the maximum number of KafkaMessageListenerContainers running, each with its own consumer, all in the same consumer group. The javadoc states the constraint that matters: “Messages from within the same partition will be processed sequentially.”

So the scaling rule from §1.2 applies unchanged: concurrency above the partition count starts idle consumers. Boot's own description of the property — “number of threads to run in the listener containers” — invites the wrong mental model, because it is consumer-group membership, not a thread pool you can size freely.

The failure mode that follows from this is worth being able to name: if one partition is hot (a skewed key, or far more traffic than the others), adding consumers up to the partition count helps, and then stops helping, because the hot partition is still read by exactly one consumer. Diagnosing that is a question about the key distribution, not about the consumer count.

2.8 Schemas and Serialization

The ordering problem across producer and consumer deployments is the one that bites in practice: you cannot deploy a consumer that expects a field the producer has not started sending, and you cannot remove a field while old consumers are running. The mechanisms are a schema registry with a compatibility mode, and a versioned topic or a tolerant reader.

The Spring-side consequence is that deserialization failure lands in the error handler as a fatal exception by default (§2.3) — which is correct, because retrying a message your consumer cannot parse will never succeed. The operational consequence is that a bad deploy produces a partition that stops advancing rather than an error rate, because the container seeks and re-reads the same unparseable record. That is the shape of the failure in §4.3.

Trade-off — JSON vs Avro vsProtobuf, and where the real cost is

JSON is debuggable and loose; Avro and Protobuf are compact and schema-enforced. But the cost that actually bites is not payload size, it is who is allowed to change the schema and when both sides have to be redeployed. A compatibility mode that permits additive changes lets you deploy producer-first; one that does not forces a coordinated release, which for a shared topic across teams means a version negotiation. Pick the strictness that matches how independently your teams deploy, not the one with the nicer benchmark.

Common Mistakes

  • Answering idIsGroup as false. It is true; the javadoc's “@return false to disable” phrasing is the source of the error. Renaming a listener's id silently moves it to a new consumer group and replays from the earliest offset.
  • Saying the Kafka ack mode defaults to RECORD. It is BATCH, and Spring Boot does not change that.
  • Describing a RetriableException marker or setRetriableExceptions. Neither exists; classification is ExceptionMatcher and you configure what is not retryable.
  • Adding Kafka's SerializationException to the fatal list. The default list contains Spring's DeserializationException, which is a different class in a different package.
  • Configuring a producer-side error handler on DefaultKafkaProducerFactory. There is no such API; use the CompletableFuture callback or a ProducerListener.
  • Leaving the default 9-retry no-delay backoff on an exception you did not expect, since unmatched types are classified retryable.
  • Claiming transactions give exactly-once for a database write. The sequence is covered; the cross-system commit gap is not, and the docs say so.
  • Raising concurrency past the partition count and concluding the broker is slow.
  • Using SeekToCurrentErrorHandler, which was removed in the 3.0 line.

Interview Questions — Spring for Kafka

Q1 What does concurrency on @KafkaListener actually do? TRICKY

It sets the number of consumer containers running, each with its own consumer, all in the same consumer group — and because each partition goes to exactly one consumer, records from the same partition are always processed sequentially. So concurrency is consumer-group membership, not intra-partition parallelism, and setting it above the partition count starts idle consumers that receive nothing. To go faster you add partitions, which lowers the ordering guarantee, or you fix a skewed key so the hot partition is not the constraint. The trap in this question is answering with the Boot property description, which calls it a number of threads and invites exactly the wrong model.

Q2 A listener throws on one record. What has already been committed? STAFF

The container commits pending offsets before invoking the error handler, so every record processed before the failure is durably marked done and only the remainder is rewound. The documented example: a poll returning six records with a throw on the fourth commits the first three, then seeks p1 to offset 1 and p2 to offset 0, and the next poll returns the three unprocessed records. The consequence worth stating is that the effective semantics are mixed — at-most-once for what was already processed, at-least-once for the rest — and that a crash immediately after cannot recover the committed ones. This is also the argument for idempotency: the retry path and the crash path both assume you can safely see a record twice.

Q3 When would you use RECORD over the default BATCH? TRICKY

When you have made the consumer idempotent and want to minimise replay after a crash. BATCH commits only once the whole poll's records are processed, so a failure replays records that were already handled; RECORD commits per record, so a crash mid-batch replays less. Neither is safe without idempotency — RECORD just makes the duplicate window smaller. If the consumer is not idempotent, the safer default is BATCH, because fewer duplicates reach it, and the correct answer is that the ack mode is a knob for tuning replay volume, not a delivery guarantee.

Q4 How do you make a database write and a Kafka publish atomic? STAFF

You usually cannot, and the honest answer is the outbox rather than a transaction manager. KafkaTransactionManager gives exactly-once over a read → process → write sequence, but that covers Kafka writes; the database commit and the Kafka commit are two separate commits with a gap, and the documentation says that if the second fails after the first has committed, the application must take remedial action to compensate. The outbox avoids the gap by writing the message to a table inside the same database transaction as the business change, then relaying it asynchronously. You trade the two-phase gap for a relay process and consumer-side deduplication. Chained transaction managers are the deprecated version of the same idea.

Q5 How do you configure retries and a dead-letter topic? TRICKY

Two objects composed, not chosen between: a DefaultErrorHandler holding the retry policy, constructed with a DeadLetterPublishingRecoverer as its recoverer and a BackOff. Set it via setCommonErrorHandler on the container factory. Two defaults to correct first — the default backoff is 9 retries with no delay, and unmatched exception types are classified retryable, so a NullPointerException is retried nine times before it reaches the recoverer. And the fatal list contains Spring's DeserializationException, not Kafka's, so a parse failure is genuinely terminal while an unexpected runtime exception is not. Set the common handler explicitly rather than inheriting either default.

Q6 How does a send to Kafka fail, and how do you find out? TRICKY

There is no producer-side error handler to configure — no setErrorHandler on DefaultKafkaProducerFactory and no producer DefaultErrorHandler; verified absent in 4.1.1. Failure arrives on the CompletableFuture returned by send(), which has returned a CompletableFuture since the 3.0 line and a ListenableFuture before it, so the callback idiom changed with the major version. The second mechanism is a ProducerListener, where Boot installs a LoggingProducerListener that logs errors by default. The practical gap is that a fire-and-forget send with no callback and no producer listener can fail with only a log line — so the answer to “how would you know” is that you attached one of the two.

Chapter 3 — Spring for RabbitMQ

Everything here is verified against spring-amqp and spring-rabbit 4.1.1. RabbitMQ's model is the queue from §1.1, and the API reflects it: fewer knobs, and the defaults assume you have thought about failure.

3.1 AcknowledgeMode: Three Values, and One of Them Is Not Kafka's

SimpleMessageListenerContainer.acknowledgeMode takes exactly three values, and this list has not changed since 2.3.0:

ValueWhat it means
AUTOThe default. The container acks when the listener returns normally, and nacks when it throws
MANUALThe listener acks explicitly, via the Channel and delivery tag. Also nacks on exception unless marked
NONENo acknowledgement at all. The broker redelivers on channel or connection close
Interview trap — there is no MANUAL_IMMEDIATE in RabbitMQ

MANUAL_IMMEDIATE is a spring-kafka concept. Carrying it across is the single most common cross-contamination between the two APIs, because the names are otherwise identical and the semantics are not comparable at all. Kafka's manual modes control when the offset is committed against a log; RabbitMQ's manual mode controls whether the broker is told at all, and the commit does not exist. Three values, one default, and a mode whose counterpart on the other side has no meaning here.

The comparison worth carrying in your head, because it explains why the defaults differ:

KafkaRabbitMQ
Unit of progressPartition offsetIndividual delivery
Default onBATCH commit, SEEK on failureAUTO ack, requeue on failure
Failure actionRetry via error handler, then DLTReturn to the queue, immediately, forever
Retry controlExplicit, via BackOffImplicit — a redelivery loop

3.2 What Happens When a Listener Throws

Here is the trap the whole chapter is built around. defaultRequeueRejected defaults to true, and it is a Boot property default. A listener that throws therefore causes the message to be returned to the queue and redelivered — immediately, with no delay, no attempt limit and no backoff. If the exception is deterministic, which it usually is, you get a tight loop that hammers the broker and never makes progress.

listener throws SQLException
   │
   ▼
basic.nack(deliveryTag, requeue=true)          ← defaultRequeueRejected=true
   │
   ▼
message returns to the head of the queue
   │
   ▼
next delivery → same exception → nack → ...
   └─▶ tight loop, hot CPU, no progress, queue never drains

set default-requeue-rejected=false instead:
   │
   ▼
basic.nack(deliveryTag, requeue=false)  or  basic.reject
   │
   ├─▶ queue has a dead-letter exchange  ──▶ message routed to it
   └─▶ queue has no DLX                     ──▶ message DROPPED

the DLX is configured on the QUEUE, by the broker.
Spring's recoverer bypasses the broker entirely (§3.4).

This is why almost every production RabbitMQ service ends up with a RepublishMessageRecoverer or a RejectAndDontRequeueRecoverer and a dead-letter exchange, and why “our queue was at 100% and CPU was pinned” is a familiar incident. The two properties have to be set together, and setting only one of them fails quietly.

3.3 Concurrency and Prefetch

RabbitMQ's prefetch is the number of unacknowledged messages the broker will hand a consumer at once, and it defaults to 250 per consumer in the Spring container. Multiply it by your consumer count and that is the maximum a client can be holding — a real constraint, because a 250-message buffer means the broker has already delivered work it cannot reclaim, and a consumer restart replays all of it.

spring.rabbitmq.listener.simple.concurrency=10
spring.rabbitmq.listener.simple.max-concurrency=20
spring.rabbitmq.listener.simple.prefetch=10
spring.rabbitmq.listener.simple.default-requeue-rejected=false
spring.rabbitmq.listener.simple.acknowledge-mode=auto

The value 1 is the one that produces true round-robin fairness across queues; anything above it lets a fast consumer hoard unacked messages and a slow one starve. In practice a modest number tuned to the work is right, and the operational warning is that an unacked message is a message you cannot take back — a long-running handler behind a large prefetch is an amplifier for any restart.

3.4 The Dead-Letter Trap

Two mechanisms move a message out of circulation, and they are not the same thing. This distinction is the most valuable thing in the chapter.

  • The broker's dead-letter exchange. Configured on the queue, with an optional routing key. It fires when the broker itself rejects a message with requeue=false and the queue has a DLX. The broker performs the routing.
  • Spring's RepublishMessageRecoverer. After the retry policy is exhausted, the container publishes the message elsewhere itself and acknowledges the original.

And the consequence, which the reference documentation states plainly: with RepublishMessageRecoverer, “the message is ack'd and is not sent to the dead letter exchange by the broker.” The broker DLX does not fire. So a system that relies on a queue-level DLX for its dead-lettering is silently not dead-lettering anything — the messages are being republished by the application, and if the application's republish target is misconfigured, they are being acked and dropped.

Interview trap — the two dead-letter paths are not additive

Configuring both a queue DLX and a RepublishMessageRecoverer does not give you two layers of safety. It gives you one path, chosen by the recoverer, and the other one silently inert. Decide which mechanism owns dead-lettering, verify the dead-letter queue actually receives traffic under test, and be able to say which one it is. The version to have ready: RejectAndDontRequeueRecoverer lets the broker's DLX do the routing, so if you chose that, the queue's dead-letter configuration is the part that must be right.

3.5 Message Conversion — the Silent Java Serialization

SimpleMessageConverter — the default when you do not configure otherwise — handles String, byte[] and Serializable. That third case is the one to know about. Send a POJO that implements Serializable and it will be handled, silently, using Java serialization — with all the consequences that carries: the class name travels in the payload, the consumer needs the identical class on its classpath, serialVersionUID changes break the message, and Java deserialization of untrusted input is a well-known attack surface.

Nothing warns you. The message is published, routed, and delivered, and the problem surfaces when one side is redeployed. The fix is to configure an explicit converter — Jackson2JsonMessageConverter for JSON payloads, or JacksonAvroMessageConverter — and, where trust crosses a boundary, to use a converter with an explicit allow-list of permitted types rather than relying on the default.

Must remember — a message that works is not a message that is safe

The reason to set the converter explicitly is not compatibility, it is that the default is a silent decision. Configuring SimpleMessageConverter is a choice about a wire format; leaving it in place is a choice about Java serialization that nobody made deliberately. If a payload type implements Serializable — and most DTOs do, for caching reasons — the default will take it. Assert in a test what the payload actually looks like, because “it round-trips fine” passes in exactly the case that will break in production.

3.6 Simple Versus Direct — the Namespace Split

RabbitMQ in Spring has two listener containers with different configuration namespaces:

  • spring.rabbitmq.listener.simple.* — SimpleMessageListenerContainer. Polls with a background thread, consumer thread pool, prefetch-based. The default choice.
  • spring.rabbitmq.listener.direct.* — DirectMessageListenerContainer. Drives basicConsume on the consumer's own thread, so a slow listener blocks its consumer. Better when a message must be handled on the channel thread or when ordering per channel is more important than throughput.

Both extend the shared AmqpContainer base, so acknowledge-mode, prefetch and default-requeue-rejected exist and behave identically under either namespace. But the per-container properties — concurrency, max-concurrency, missing-queues-fatal, the task-executor settings — are on the concrete containers and do not cross-configure. Setting spring.rabbitmq.listener.simple.concurrency=10 has no effect on a direct listener, and it fails silently.

Common Mistakes

  • Saying MANUAL_IMMEDIATE is a RabbitMQ acknowledge mode. It is spring-kafka's; RabbitMQ has three values and AUTO is the default.
  • Leaving defaultRequeueRejected at its default of true and calling it retry behaviour. It is an unbounded redelivery loop with no delay and no attempt limit.
  • Configuring a queue dead-letter exchange and a RepublishMessageRecoverer and believing both are active. The recoverer's republish means the broker DLX never fires.
  • Assuming a dead-lettered message is preserved because the DLX is configured, without checking that the queue actually has one and that the routing key resolves.
  • Relying on SimpleMessageConverter with a Serializable DTO and getting Java serialization by default, with no warning at publish or consume time.
  • Leaving prefetch at 250 on a slow handler, so a restart replays a large buffer of unacknowledged work.
  • Setting spring.rabbitmq.listener.simple.concurrency and expecting it to affect a direct listener. The namespaces do not cross-configure.

Interview Questions — Spring for RabbitMQ

Q1 A RabbitMQ listener is stuck in a CPU loop and the queue depth is flat. Why? STAFF

It is almost certainly the redelivery loop. defaultRequeueRejected defaults to true, so a listener that throws a deterministic exception causes the message to be nacked with requeue, returned to the queue and immediately redelivered — no delay, no attempt limit, no backoff. The queue depth stays flat precisely because the same message is cycling rather than being consumed, and CPU is pinned because that is the loop. The fix is default-requeue-rejected=false plus a real dead-letter destination, and the diagnosis step is checking the queue's messages_ready against messages_unacknowledged and looking for a repeated delivery of the same body. The deeper point is that this is not retry behaviour, it is a bug that presents as a throughput problem.

Q2 What is the difference between a broker dead-letter exchange and RepublishMessageRecoverer? TRICKY

The broker DLX is configured on the queue and the broker performs the routing when a message is rejected with requeue=false. The recoverer is a Spring component that, after the retry policy is exhausted, publishes the message itself and acknowledges the original. The consequence is the trap: with RepublishMessageRecoverer the message is acked and is not sent to the dead letter exchange by the broker — so configuring both does not give you two layers, it gives you one. Pick which mechanism owns dead-lettering, and if it is the broker's, verify the queue's DLX and routing key are actually correct, because nothing errors if they are not.

Q3 How do you stop a POJO being serialized with Java serialization? TRICKY

Configure an explicit MessageConverter — Jackson2JsonMessageConverter or JacksonAvroMessageConverter — as a bean or on the container factory. The reason this matters is that SimpleMessageConverter, the default, handles String, byte[] and Serializable, and most DTOs implement Serializable for caching reasons. So the failure is silent at both ends: the class name travels in the payload, the consumer needs the identical class, and a serialVersionUID change breaks messages that were already in flight. Where trust crosses a boundary, use a converter with an explicit allow-list rather than relying on type headers from the message.

Q4 When would you choose the direct container over simple? TRICKY

When the listener must run on the channel's own thread — the DirectMessageListenerContainer drives basicConsume directly, so a slow handler blocks that consumer rather than being absorbed by a background polling thread. That matters when you depend on per-channel ordering or need the listener to interact with the channel itself, such as doing channel-scoped work inside the callback. The cost is throughput: a blocking listener consumes its consumer entirely. Note the operational trap too — the two containers have separate configuration namespaces, so spring.rabbitmq.listener.simple.* per-container properties silently do nothing on a direct listener, although the shared AmqpContainer settings such as acknowledge mode, prefetch and requeue behaviour are common to both.

Q5 How does RabbitMQ differ from Kafka on failure handling? STAFF

Kafka has an explicit retry policy you configure: a DefaultErrorHandler with a BackOff and a recoverer, defaulting to nine retries with no delay and a seek. RabbitMQ's is implicit and unbounded: defaultRequeueRejected=true requeues immediately with no attempt limit, which is a redelivery loop rather than a retry. The underlying reason is the model — Kafka commits offsets, so progress is a number it tracks, while RabbitMQ simply gives the message back and the broker forgets it. So on Kafka you tune retry configuration, and on RabbitMQ you first have to turn the default loop off before you have a retry story at all.

Q6 What does prefetch control, and what is the default? TRICKY

It controls how many unacknowledged messages the broker hands a single consumer, and the default is 250 per consumer. A value of 1 gives strict round-robin fairness; higher values let a fast consumer hold work it has not acknowledged, which starves slower consumers and means a consumer restart replays the whole unacked buffer. The operational reading is that an unacknowledged message is one the broker cannot reclaim, so prefetch is a memory and restart-cost knob as much as a throughput one. Tuning it is a balance between the work per message and the buffer you are willing to lose on a restart.

Chapter 4 — Choosing and Operating

Chapters 1–3 were the APIs. This one is what you are asked in a design review and what you are paged for at 2am: which broker, and what the dashboards say.

4.1 Kafka or RabbitMQ

The decision reduces to a single question from §1.1 — do consumers need history? — with a few real modifiers.

KafkaRabbitMQ
ModelPartitioned log, retainedQueue, consumed and gone
Fan-outFree — a new group is freePublish once per consumer type
Replay / new read modelAny retained offsetNot possible after consumption
RoutingKey-based partitioning onlyExchanges, routing keys, headers, per-message TTL, priority
OrderingPer partition, durablePer queue, while it exists
Scale ceilingVery high, disk-boundThousands of msg/s per queue; millions of connections
LatencyHigher; batching is the pointLower; basic.consume push

So: event streams, audit, analytics, replay, high throughput with many consumers → Kafka. Work distribution, complex routing, low latency, per-message priority or TTL, the broker doing the heavy lifting → RabbitMQ. The wrong choice in each direction is recognisable — a RabbitMQ fan-out to three consumer types that required three publishes and now has no history, or a Kafka topic where every message went to the same key and ordering was the only requirement that mattered.

4.2 The Consumer-Lag Metric That Tells the Truth

On Kafka, consumer lag is the distance between a consumer group's committed offset and the log end offset for each partition. It is the single most useful number on the platform, and it answers a different question per partition: this consumer is n records behind on this partition, and n is growing or shrinking.

The reading is easy to get wrong in two ways. A growing lag means the consumer cannot keep up — the rate is below the production rate, and it will not recover on its own. A flat but non-zero lag is not necessarily a problem: if production is currently idle, a backlog drains at the rate the consumer can work, and steady state can be a permanent offset. And lag that oscillates by a few records per partition is a poll-timing artefact, not an incident. The alarm worth writing is a sustained growth rate, not a threshold.

RabbitMQ has no equivalent single number, and this is a genuine operational difference. You have messages_ready and messages_unacknowledged per queue, and you have to derive the trend yourself; the useful derived signal is whether messages_ready is growing while consumers stays constant, which is the queue-form of a growing consumer lag.

4.3 The Rebalance Storm

A rebalance is the group re-assigning partitions. It happens when a consumer joins, leaves, dies, or exceeds the poll timeout. It is cooperative and mostly invisible, and it is also the most common cause of a self-inflicted outage in a Kafka consumer, because a handler that takes longer than max.poll.interval.ms is evicted and the entire group rebalances — and while it rebalances, nothing is consuming.

handler takes 6 min,  max.poll.interval.ms = 5 min

  t=0    poll → 500 records → handler starts
  t=5:00 consumer considered dead ──▶ evicted
        every OTHER consumer's partitions move
        ──▶ the whole group stops consuming
  t=6:00 handler finishes, acks
        ──▶ 500 records just processed by a revoked member
            are now lost, or replayed depending on timing

  FIX: 1) increase max.poll.interval.ms
       2) pause the container between polls (pauseConsumerImmediate)
       3) reduce max.poll.records so a batch fits the interval
       4) move long work OFF the listener thread

  the 4th is the right one. the others buy time.

And the amplifier: a deserialization failure is fatal by default (§2.3), so one unparseable record makes the container seek back to it and try again, on every poll, forever. The partition does not advance, lag climbs, the poll interval is exceeded, and you get a rebalance storm on top of a poison message. Diagnose it as a stuck offset, not as a slow consumer: look for a partition whose lag is growing while its neighbours are fine. That single observation separates the two failure modes, and it is the most useful operational heuristic in this chapter.

4.4 Idempotency and the Outbox

Two mechanisms, two different gaps, and confusing them is the usual mistake.

The outbox solves the publish side. You cannot atomically commit a database change and publish a message. So you write the message into a table in the same transaction as the business change, and a relay publishes it afterwards and marks it sent. Atomicity comes from the database transaction you already have. The cost is a relay process, a small publish delay, and duplicates when the relay publishes and crashes before marking — so the outbox does not give you exactly-once, it gives you at-least-once with a guarantee that the message will not be lost. Volume 11 chapter 7 covers the pattern; the Spring side here is KafkaTemplate with a future callback (§2.6) or a RabbitTemplate with publisher confirms and returns, plus a table to drain.

Idempotency solves the consume side. A deduplication key the consumer stores, a natural key with an upsert, a state machine that ignores an already-applied transition. The rule of thumb: make the effect idempotent, not the handler — logging something twice is fine, sending the email twice is not, and the fix has to be at the point where the external effect happens.

Must remember — the outbox is at-least-once, and that is the correct target

Chasing exactly-once with a broker transaction does not close the gap, because the database commit and the broker commit are two separate commits (§2.5). The outbox closes it properly by making the publish part of the database transaction, and what it buys is never lose the message — not never deliver twice. That residual duplicate is handled on the consume side by idempotency, which you needed anyway for rebalances. Two mechanisms, one gap each, and together they are the actual answer to “how do you make this atomic”.

4.5 Schema Registry and Evolution

The deploy-ordering problem: you cannot ship a consumer that expects a field the producer does not send, and you cannot remove a field while old consumers run. A schema registry with a compatibility mode turns that from coordination into a gate — the producer's new schema is rejected at registration if it breaks the configured mode, so the break happens in CI rather than in production.

Choosing a mode is a deployment-topology decision, not a data-modelling one. BACKWARD lets you deploy consumers first and is the safe default for a registry you control. FULL is strictest and forces agreement. FORWARD suits a log being read by consumers you do not control, since old readers keep working. BACKWARD_TRANSITIVE checks against all previous versions, which is what you actually want when several historical versions are still in flight — and it will fail builds for changes that only the latest version tolerated, which is the point.

The operational rule that follows: set the mode to cover your slowest reader, not your newest schema. A topic that retains a week of history has seven days of consumers in whatever shape they were when they were written, and the compatibility check is the only thing that knows that.

Common Mistakes

  • Choosing Kafka or RabbitMQ by throughput alone, ignoring the replay and fan-out properties that follow from the model.
  • Alerting on a lag threshold rather than a growth rate. A flat non-zero lag is often the steady state of an idle producer.
  • Diagnosing a rebalance storm as a slow consumer when the cause is one unparseable record holding a partition at a fixed offset.
  • Long-running work on the listener thread, exceeding max.poll.interval.ms and evicting yourself from the group.
  • Retrying by increasing max.poll.interval.ms rather than moving the long work off the listener thread, which treats the symptom and costs rebalance headroom.
  • Publishing directly in a database transaction and calling it atomic. Without an outbox there is a window where the commit succeeded and the publish did not.
  • Setting a compatibility mode that only checks against the latest schema, when the topic still holds days of older-shaped records.
  • Assuming a Serializable payload on RabbitMQ means a neutral format. It means Java serialization.

Interview Questions — Choosing and Operating

Q1 When would you pick RabbitMQ over Kafka? TRICKY

When consumers do not need history and the routing is the hard part. RabbitMQ gives you exchanges, routing keys, header-based routing, per-message TTL and basic.priority, and none of which a Kafka partition key can express. It also has lower latency, because there is no batching-to-durability step in the way. Kafka is the right answer the moment you want a new consumer group to read history, to build a new read model without touching production, or to fan out cheaply to several consumer types. Deciding by throughput alone is the common error, because throughput is the axis where they are closest and the model is the axis where they are furthest apart.

Q2 How do you debug a consumer group that has stopped consuming? STAFF

Look at per-partition lag first, and ask whether it is uniform. A partition whose lag grows while its neighbours are flat points at a stuck offset — usually one record that fails fatally, such as a deserialization error, so the container seeks back to it on every poll and the partition never advances. Uniformly growing lag across all partitions means the consumers genuinely cannot keep up, and the next question is whether it is CPU, an external dependency the handler calls, or a handler whose duration exceeds the poll interval. The third failure mode to check is the group itself: a member evicted for exceeding max.poll.interval.ms causes a rebalance that stops the whole group, which looks like slowness but is really a stall. The partition-level view is what separates these three, and that is why per-partition lag beats a group total.

Q3 A rebalance storm is happening after a deploy. What are the causes? STAFF

In rough order of likelihood: a handler whose runtime exceeds max.poll.interval.ms, so the member is evicted and the group rebalances; a new deployment where several replicas start together, so a sequence of joins and leaves cascades; max.poll.records set high enough that one batch cannot be processed inside the poll interval; and a slow or blocked external dependency inside the listener, which is the first case wearing a different hat. The real fix for the first and fourth is to move the long work off the listener thread and return control quickly, not to keep raising the interval. The deploy-shaped one is fixed with a slower rollout and a larger session.timeout relative to the poll interval, not by configuration of the handler.

Q4 Explain the outbox pattern and when you would not use it. TRICKY

You write the outgoing message into a table in the same database transaction as the business change, then a relay publishes it and marks it sent. That makes the publish atomic with the write, because both are in one transaction — which is the gap a plain “commit then publish” has, where the commit succeeds and the publish fails and nobody knows. The costs are a relay process, a small delay between commit and publish, and duplicates when the relay publishes and crashes before marking — so the outbox gives at-least-once, not exactly-once, and the consumer still has to be idempotent. You would not use it when the source of truth is not a relational database you can put a table in, or when you have accepted eventual consistency and the occasional lost or duplicated event, in which case a direct publish with a callback and monitoring is less machinery.

Q5 How do you evolve a message schema without breaking consumers? TRICKY

Use a schema registry with a compatibility mode, so the new schema is validated at registration instead of at runtime. The mode is a deployment-topology decision: backward lets you deploy consumers first, full is strictest, forward suits a log read by consumers you do not control, and backward-transitive checks against all previous versions. The rule is to set the mode for your slowest reader rather than your newest schema — a topic retaining a week of history still has readers in whatever shape they were when those records were written, and the compatibility check is the only thing that knows it. The other half is making the deserialization failure visible: a parse error is fatal by default, so a bad deploy shows up as a partition that stops advancing rather than as an error rate.

Q6 Your consumer is not idempotent. What breaks, and when? STAFF

Duplicates are the default — at-least-once is the contract, not an accident — and under BATCH ack mode a failure replays records that were already handled, a retry re-delivers, and a rebalance replays in-flight work. So a non-idempotent consumer breaks on a rebalance, a deploy, a timeout, or a poison message, which is to say it breaks under exactly the conditions where you have least capacity to investigate. The operations that must be idempotent are the ones with an externally visible effect: charging, refunding, emailing, incrementing. The fix belongs at the point of the external effect rather than in the handler, because logging twice is harmless while emailing twice is a support ticket per replay. Note also that this is a prerequisite for preferring RECORD over the default BATCH ack mode.

Scenario Bank

Three narratives. Each needs every chapter, and each is shaped like the production question it came from.

Scenario 1 — The Listener That Stops Consuming

Symptom. A billing consumer's group shows healthy CPU and an alert on consumer lag. Lag is climbing steadily. The team restarts the service; the lag resets briefly, then climbs again. Nothing is in the logs.

Diagnosis. Look at per-partition lag, not the group total. One partition is pinned while the others move — which means it is not a capacity problem, it is a stuck offset. A record on that partition fails to deserialize, deserialization is fatal by default (§2.3), the error handler seeks back, and the container re-reads the same record on every poll. The logs are empty because no error is escaping: the error handler is handling it, correctly, forever.

Fix. Get the record off the partition — skip it to the DLT after reviewing it — and prevent the next one. The structural fix is schema compatibility enforced at registration (§4.5) plus a consumer deployed before the producer so the shape is never ahead. A DefaultErrorHandler with a DeadLetterPublishingRecoverer stops the infinite loop but does not tell you which record is bad; adding the record's key and offset to the error log does.

Scenario 2 — The Queue That Fills Up

Symptom. A RabbitMQ queue climbs to 200k ready messages overnight. Consumer count is unchanged. CPU on the consumers is near zero. The application is not erroring.

Diagnosis. Check messages_unacknowledged first. If the ready count is climbing while the unacked count sits at exactly prefetch times the consumer count, the consumers are alive and blocked — most often on a downstream call that is slow, and a listener that exceeds the ack timeout. If unacked is zero and ready is climbing, the consumers are gone or the routing is wrong, and the redelivery loop from §3.2 is worth ruling out: a listener throwing a deterministic exception keeps the same message cycling, so the ready count looks flat rather than climbing — a flat queue plus a hot consumer is that bug, and it is a different symptom from this one.

Fix. Depends on the cause, and the diagnostic is what decides it. Blocked consumers mean a timeout budget on the downstream call and a circuit breaker, not more consumers. A missing route means a binding problem. And the standing improvement is a prefetch matched to the work — 250 per consumer means a restart replays a large unacknowledged buffer, so a queue that is slow to recover after a deploy is often a prefetch problem rather than a throughput one.

Scenario 3 — The Deploy That Duplicated Every Order

Symptom. After a routine deploy, downstream sees each order twice. No exceptions. The consumer group is healthy. The duplication stops after the backlog drains and never recurs.

Diagnosis. Almost always a group identity change, and the Kafka one has a specific mechanism: a listener's id is its group.id by default because idIsGroup is true (§2.1). A rename, a package move that changes a generated name, or a groupId removed in a refactor puts the listener in a brand-new group with no committed offsets — so it starts from the earliest retained offset and replays the topic's history. The signature is a burst of duplicates proportional to retention that then stops, which is why it presents as self-healing and gets dismissed.

Fix. Restore the group id. Prevention is to set groupId explicitly on every @KafkaListener so the group's identity does not depend on a name, and to keep id as a container label only. The related exposure is worth stating alongside it: even with a stable group, a rebalance replays in-flight records, so the consumer still has to be idempotent (§4.4). This scenario is the argument for idempotency more clearly than any other, because nothing failed — the group just became someone new.
