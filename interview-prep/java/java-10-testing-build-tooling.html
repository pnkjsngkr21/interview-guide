Chapter 1 — JUnit 5: The Test Lifecycle & the Extension Model

Volume 8 established that @Test is an annotation with no magic of its own: something has to read it and act on it. This chapter is that something. JUnit is not that interesting on its own — the interview-grade material is the lifecycle, because that is where the surprises live.

1.1 The Default Lifecycle Is PER_METHOD

Jupiter creates a new instance of your test class before each test method. This is the default, and it is the detail most people get wrong — the intuition from JUnit 4 and from plain Java is one instance per class, reused across methods.

class OrderTest {

    // A FRESH instance for EVERY test method — not one shared instance
    @Test void addsLineItems()   { ... }   // uses instance A
    @Test void rejectsEmptyCart() { ... }   // uses instance B

    // Non-static @BeforeEach runs before each of them, on that method's own instance
    @BeforeEach void setUp() { repository.insert(new Order()); }
}
Interview trap

The instinct is "one test object per test class, fields set up once." It is wrong, and the consequence is real rather than academic: instance fields assigned in one test method do not leak into the next, because the next method gets a new object. A test that passes only because it inherited state from a sibling is passing by accident — and it will start failing the moment someone reorders the methods, which a parallel runner will do for free.

1.2 PER_CLASS, and When It Bites

@TestInstance(Lifecycle.PER_CLASS) changes exactly one thing: the class is instantiated once per class rather than once per method. Everything else — ordering, isolation expectations — follows from that.

AspectPER_METHOD (default)PER_CLASS
Instances per classOne per test methodOne per class
@BeforeAll / @AfterAllMust be staticMay be non-static — they run on the shared instance
@BeforeAll in @NestedNeeds static, and historically also needed PER_CLASSAllowed without static
Field isolation between methodsFull — nothing carries overNone — mutations persist across methods
CostMore allocationsFewer; mutable state is your problem
Must remember

The reason PER_CLASS is more than a micro-optimisation: with one shared instance, @BeforeAll and @AfterAll can be instance methods and can therefore touch the instance's own state. Under PER_METHOD they must be static because there is no instance yet to run them on.

Interview trap

Two details get conflated. First, PER_CLASS is what makes a non-static @BeforeAll possible — but non-static @BeforeAll in a @Nested class also needs PER_CLASS. Second, this is version-sensitive in a way that has already changed: before Java 16 a static @BeforeAll inside @Nested was not permitted at all, so PER_CLASS was the only route. From Java 16 onward a static @BeforeAll in a @Nested class works under either lifecycle. Saying "PER_CLASS is required for @BeforeAll in nested classes" is right on the mechanism and wrong on the necessity.

1.3 The Three Registration Mechanisms

An extension is registered through exactly three mechanisms. There is no fourth.

MechanismPlaced onUse when
@ExtendWithThe test class, a nested class, a test method, a field, or a parameter (fields and parameters since Jupiter 5.8)The extension is global to that class or method — the common case
@RegisterExtensionA non-static (instance) or static fieldThe extension needs runtime configuration, or you want to assert on its captured state afterwards
ServiceLoader auto-discoveryA file on the classpath, not codeA tool supplies extensions for code you do not own
Interview trap

ServiceLoader auto-discovery is off by default. It is enabled by setting the system property junit.jupiter.extensions.autodetection.enabled=true. An extension author who adds the service file and then reports "my extension never loads" has hit the default, not a bug — and the failure is silent, because nothing is registered and nothing complains.

In production

This is why SpringExtension is not discovered automatically. You have to write @ExtendWith(SpringExtension.class) on your test class, and that is deliberate: a test that silently spins up a Spring context because a jar on the classpath registered an extension is a test whose runtime and behaviour you do not control. Explicit registration is the difference between a test suite you can reason about and one you have to observe.

1.4 The Eight Extension Callbacks, in Order

One extension may implement several callback interfaces, and the framework runs them in a fixed order. Knowing the order is how you answer "where does my code actually run relative to @BeforeEach?"

Must remember

The distinction that gets asked: BeforeTestExecutionCallback and AfterTestExecutionCallback fire immediately before and after the test method itself — inside @BeforeEach/@AfterEach. That is the right hook for timing and tracing, because it measures the test body and nothing else. To wrap @BeforeEach and @AfterEach as well, implement BeforeEachCallback and AfterEachCallback instead. Both are correct; they measure different spans.

Note that one extension implementing several of these — SpringExtension is the canonical example — is normal, not unusual. The callbacks nest, so a single extension can contribute behaviour at every level of one test.

Common Mistakes

  • Assuming one test-class instance is shared across methods. It is not, unless PER_CLASS.
  • Writing @BeforeAll as an instance method under the default PER_METHOD lifecycle — it will not compile as intended.
  • Adding a META-INF/services entry and expecting auto-discovery without the system property.
  • Implementing BeforeTestExecutionCallback to time setup, when @BeforeEach runs outside it.
Chapter summary

JUnit 5's interview-grade content is its lifecycle, not its assertions. PER_METHOD by default means no state carries between tests; PER_CLASS trades that isolation for non-static @BeforeAll and cheaper setup. Extensions register through exactly three mechanisms, one of which is silent by default. The eight callbacks nest in a fixed order, and the TestExecution pair sits inside the Each pair.

Interview Questions — JUnit 5

Q1 Does JUnit create one instance of a test class, or one per test method?

One per test method — PER_METHOD is the default. @TestInstance(PER_CLASS) changes it to one per class.

Q2 Why can @BeforeAll be a non-static method under PER_CLASS but not PER_METHOD? TRICKY

Under PER_METHOD there is no instance yet when @BeforeAll runs, so it must be static. Under PER_CLASS the single instance exists, so an instance method can run against it.

Q3 How many ways are there to register an extension?

Three: @ExtendWith, @RegisterExtension, and ServiceLoader auto-discovery — the last being opt-in via junit.jupiter.extensions.autodetection.enabled=true.

Q4 Your extension's setup ran but your timing assertion measured nothing. What is wrong?

You implemented BeforeTestExecutionCallback, which fires immediately around the test method and inside @BeforeEach. To include setup, implement BeforeEachCallback.

Q5 A test passes alone but fails under a parallel runner. What is the most likely cause? ADVANCED

It depends on state left by another test method — an assumption that the default PER_METHOD lifecycle was already supposed to prevent, made real by shared external resources the lifecycle does not isolate.

Chapter 2 — Mockito: Where to Mock, and Where Not To

Mockito's own documentation is blunt that a mocking framework's value is not in how much you can mock. The API is small enough to learn in a paragraph; the judgment about what should be mocked at all is what a senior interviewer is probing.

2.1 The Core Surface

The whole framework is four operations: create a double, stub its answers, exercise the code under test, verify what happened.

NeedAPINotes
Create a doublemock(SomeType.class) / @Mock@Mock needs Mockito's JUnit extension to be initialised
Define return valueswhen(mock.call()).thenReturn(x)Must happen before the call under test is exercised
Match argumentsany(), eq(x), anyString()A matcher's presence switches the whole verification into matcher mode
Assert interactionsverify(mock).call(), verifyNoInteractions(mock)Checks that happened, not what it returned
Capture an argument@Captor / ArgumentCaptorFor asserting on something you could not know in advance
BDD styleBDDMockito.given(...).willReturn(...)Readability only; see the trap below

2.2 Stubbing & Verification

List<String> mockedList = mock(List.class);

when(mockedList.get(0)).thenReturn("first");   // stub
when(mockedList.size()).thenReturn(1);          // a second stub

verify(mockedList).get(0);                      // called exactly once
verify(mockedList, never()).clear();            // never called
verifyNoInteractions(spy);                      // nothing at all
Interview trap

BDDMockito.given() does not pair with thenReturn(). It returns a different stubbing type whose method is willReturn(), so given(x).thenReturn(y) does not compile. Writing given(...).thenReturn(...) is the single most common way to fumble this in a live interview — it is a compile error, so it is better than a silent bug, but it still costs you the point.

Must remember

Use exactly one style across a test suite. Mixing when/then in some tests and given/willReturn in others reads as two authors, and the reader pays the translation on every method.

2.3 The Three Rules: Where NOT to Mock

Mockito's own site states three boundaries. They are worth more than the entire API surface above, because the API is what you look up and these are what you have to defend.

RuleWhyWhat to do instead
Do not mock types you don't ownYour test then asserts your assumption about a third party's behaviour, not your own logicStub at your own boundary — an interface you defined, or an HTTP layer
Do not mock value objectsA mocked Money or Email has no behaviour left to verify; you are asserting on the mock frameworkConstruct real ones — they are cheap and they carry real equals/hashCode (Volume 3)
Do not mock everythingA test where every collaborator is a mock verifies your own wiring and nothing about the codeUse a real implementation for pure logic; mock only at I/O, time, or network edges
Interview trap

The third rule is the one that separates a mid-level answer from a senior one. "Mock the repository" is a reflex; the judgment is knowing that a repository with one method returning a List is not worth mocking at all — an in-memory implementation tests more, and a mock only records that you called it. Over-mocking produces the characteristic failure where a test passes, the suite is green, and no assertion has ever touched real behaviour.

In production

Mocking static methods and constructors needs the inline mock maker, which changes the bytecode of the class under test. That is a real cost in build time and in debugging — the stack trace in a failing test no longer maps cleanly onto the source you wrote. It is a legitimate tool for genuinely unavoidable static coupling, and a smell when it becomes the default answer to "this is hard to test".

Common Mistakes

  • Stubbing after the call under test has already run, then asserting the new stub applied.
  • Mixing a raw value and a matcher in one verification — one forces matcher mode for all of them.
  • Mocking a value object and then asserting on its equals, which a mock does not implement meaningfully.
  • Pairing given() with thenReturn().
Chapter summary

Mockito is create, stub, exercise, verify — four operations. The defensible knowledge is the three negative rules: do not mock what you do not own, do not mock value objects, do not mock everything. A candidate who can say why a repository mock may be the wrong choice is more employable than one who has memorised every matcher.

Interview Questions — Mockito

Q1 Name the four core operations in a Mockito test.

Create a double, stub its answers, exercise the code under test, verify the interactions.

Q2 Why does given(...).thenReturn(...) not compile? TRICKY

BDDMockito.given() returns a stubbing type that declares willReturn(), not thenReturn().

Q3 When should you not mock a type at all?

When you do not own it, when it is a value object, and when a real implementation would exercise more than a mock would. The value is in the boundary, not in coverage.

Q4 What does mocking a value object like Money actually verify? ADVANCED

Almost nothing. The mock has no real equals or arithmetic, so the assertion is about the framework rather than about behaviour.

Q5 A whole test class is mocks. What is the smell?

It verifies wiring rather than logic. Mock at I/O, time and network edges; use real objects for pure logic and value types.

Chapter 3 — Maven: Lifecycles, Phases & Goals

Most people can run mvn package and cannot explain why install exists. The whole build model is three ideas — lifecycle, phase, goal — and separating them is the entire chapter.

3.1 Three Lifecycles

There are exactly three built-in lifecycles: default, clean, and site. Each is a fixed, ordered list of phases.

3.2 The Default Lifecycle, in Order

The default lifecycle has 23 phases. The ones an interviewer expects you to know by heart are validate, compile, test, package, verify, install, deploy — but the shape matters more than the list, because it explains why the next section is true.

You typeProducesRuns before it, always
mvn compileCompiled classesvalidate
mvn testTest reports, no artifactcompile and everything before it
mvn packageJAR/WARtest — tests run before you get an artifact
mvn verifyVerified artifact, not yet in a repositorypackage
mvn installArtifact in your local ~/.m2verify
mvn deployArtifact pushed to a remote repositoryinstall

3.3 Phases Are Cumulative

Invoking a phase runs every phase before it in that lifecycle, in order. mvn verify therefore runs validate, compile, test, package first, and only then verify.

Must remember

This is why verify exists separately from install. install means "put it in my local repository" — which is a side effect on your machine, not a statement about the artifact's quality. A CI pipeline runs verify, not install, because the thing it wants to assert is "this artifact passed its checks," and publishing to a local repository is not part of that claim.

3.4 Goals Bind to Phases

A goal is a task a plugin performs. A goal may be bound to zero or more phases. If a phase has no goals bound to it, that phase does nothing and execution moves on — which is why the 23-phase list above contains phases your build never uses.

TermIs it a noun you type?What it is
LifecycleIndirectlyAn ordered list of phases — default, clean, site
PhaseYes — mvn packageA named step in a lifecycle; always runs its predecessors
GoalYes — mvn clean:cleanA plugin task, bound to a phase or invoked directly
Interview trap

The plugin prefix colon form — mvn dependency:tree, mvn clean:clean — invokes a goal directly and bypasses the lifecycle entirely. That is the difference from mvn clean, which invokes the clean phase and runs pre-clean and post-clean too. Saying "they are the same" is the classic beginner answer and it is wrong in a way that matters when a plugin relies on its pre-phase.

In production

When several goals bind to one phase, those from the packaging run first, followed by those configured in the POM. So a plugin you add to an existing lifecycle is additive and runs after the built-in work — it cannot be relied upon to influence it, which is exactly why plugins that must run before the standard binding are bound to the earlier phase instead.

Common Mistakes

  • Describing mvn package as producing an artifact without running tests. It runs every earlier phase, test included.
  • Treating install as a quality gate. It is a repository side effect; verify is the gate.
  • Conflating mvn clean (a phase) with mvn clean:clean (a goal).
  • Expecting all 23 default phases to do something. Unbound phases are deliberately no-ops.
Chapter summary

Three lifecycles, a fixed ordered set of phases per lifecycle, phases that run cumulatively, and goals that bind to phases. Every confusion in this chapter reduces to collapsing one of those three levels into another — most often by reading plugin:goal as a phase.

Interview Questions — Maven

Q1 How many built-in Maven lifecycles are there and what are they?

Three: default, clean, and site.

Q2 What else runs when you type mvn verify? TRICKY

Every earlier default phase in order — validate, compile, test, package, and so on. Phases are cumulative.

Q3 Does mvn package run your tests?

Yes. test precedes package, and the phase runs everything before it.

Q4 Difference between mvn clean and mvn clean:clean? ADVANCED

clean is a phase, so pre-clean and post-clean run too. clean:clean invokes one goal directly and skips the lifecycle.

Q5 What happens when a phase has no goals bound to it?

Nothing — it is a no-op and the build moves to the next phase. That is why some of the 23 default phases never appear in a given build.

Chapter 4 — How the Tooling Fits the Rest of the Series

Tooling questions in interviews are rarely about the tool. They are about a mechanism the series has already taught, arriving through a build or test framework.

4.1 The Three Mechanisms Reappearing

MechanismOwned byWhere it surfaces in tooling
ReflectionVolume 8, Ch. 1How JUnit discovers @Test methods and invokes them; how Maven's Surefire finds and runs a test class
Annotations as metadataVolume 8, Ch. 2@Test, @BeforeEach, @ExtendWith are all inert markers — the framework is what reads them
Class loading and isolationVolume 7, Ch. 2Surefire forks a JVM per module; JUnit's extension model is a different question — how it is wired, not how it is loaded
Must remember

An annotation does nothing on its own. @Test is metadata; Jupiter is the thing that reads it. This is the same point Volume 8 makes about Spring and Jackson, and it is the answer to "how does any of this work without me writing the wiring?" — annotations plus something reading them reflectively.

4.2 Where Tooling Questions Actually Go

Three places, in descending order of how often they appear:

  • Reflection questions — asked as Java questions, and answered with Volume 8.
  • Build and CI questions — "why did the build fail", "what does this flag do", "why is the artifact not in the repository". Chapter 3 answers these.
  • Testability questions — "this class is hard to test, why?" The answer is nearly always coupling to something that is not pure logic: a clock, a network call, a static singleton, or a type you do not own. That is Chapter 2's three rules restated as a diagnosis.
Chapter summary

Tooling is where the series' mechanisms show up wearing a different hat. Reflection discovers the tests, annotations mark them, and the Maven model explains what a build actually did. The judgment question — what should be mocked at all — is the one worth practising.

Interview Questions — Tooling

Q1 How does JUnit know which methods to run without manual registration?

It reflects over the class for methods annotated @Test and invokes them — the same mechanism Spring and Jackson use for their own annotations.

Q2 A class is genuinely hard to unit test. What are the usual causes?

Coupling to non-pure concerns: a clock, network, filesystem, static state, or a third-party type you do not own. Each names a seam to introduce rather than a reason to mock harder.

Q3 CI runs mvn deploy on every commit. What is wrong with that? ADVANCED

It publishes an artifact per commit and treats publishing as the gate. CI wants verify as the assertion, with deploy reserved for tagged, release-worthy builds.

Chapter 5 (Bonus) — Scenario Questions

Interview Questions — Scenarios

S1 A test passes alone and fails in CI. CI runs the suite in parallel. What is the most likely cause?

Shared mutable state across test methods — a static field, a singleton, or a shared database row. The default PER_METHOD lifecycle isolates instance fields, but nothing isolates statics or external resources.

S2 A developer adds a JUnit extension via a service file and reports it never loads.

ServiceLoader auto-detection is off by default. It requires junit.jupiter.extensions.autodetection.enabled=true. The failure is silent because nothing is registered.

S3 A timing assertion in an extension reports zero for a slow test.

The extension implements BeforeTestExecutionCallback/AfterTestExecutionCallback, which wrap the test method only — not @BeforeEach. Use the Each callbacks to include setup.

S4 A test class holds an expensive fixture and rebuilds it for every one of 40 methods. Reviewer asks for a fix.

@TestInstance(Lifecycle.PER_CLASS) — one instance per class. The trade-off is losing field isolation, so the fixture must be reset deliberately in @BeforeEach rather than rebuilt.

S5 @BeforeAll in a @Nested class is non-static and fails on Java 11.

Expected: under the default PER_METHOD lifecycle it must be static, and PER_CLASS is the alternative. From Java 16 a static @BeforeAll in @Nested works under either lifecycle.

S6 A service has 400 unit tests, each mocking the repository, the client, and the clock. A reviewer objects. What is the objection?

Over-mocking. A mocked repository records that a method was called; it does not exercise retrieval. Mock at I/O and time edges, use real objects for pure logic and value types.

S7 A developer mocks BigDecimal to control rounding, and the test passes while production rounds differently.

A mocked value object has no arithmetic and no meaningful equals. The test asserted on the mock, not on rounding. Construct real instances — Volume 1 covers BigDecimal's scale semantics.

S8 A candidate writes given(orderRepo.findById(id)).thenReturn(order) in a live interview. What is wrong?

BDDMockito's given() pairs with willReturn(), not thenReturn(). when(...).thenReturn(...) is the Mockito form.

S9 mvn package produced a JAR but the test report shows the tests never ran.

Almost always a naming or binding problem: tests not matching Surefire's include patterns, or the test phase having no goal bound. package runs test first — it does not skip it.

S10 A build needs to delete target/ before compiling. Should it run clean or clean:clean?

mvn clean — it invokes the phase, so pre-clean and post-clean also run. clean:clean calls one goal directly and bypasses the lifecycle.

S11 A plugin must run before the compiler. Where is it bound?

To a phase earlier than compile — generate-sources or process-sources. Goals added to an existing phase run after that phase's packaging-provided goals.

S12 Why does a CI pipeline run verify rather than install?

install publishes to the local ~/.m2 repository — a machine side effect, not a statement about quality. verify is the assertion that the artifact passed its checks.

S13 An interviewer asks how Spring's @Autowired resolves a bean. Which chapters of this series are the answer?

Annotations as metadata and reflection — Volume 8, Chapters 1 and 2. The annotation marks the intent; reflection reads it and constructs the object.

S14 A test needs a deterministic clock. The developer mocks Instant.now(). What are the two costs? ADVANCED

Static mocking requires the inline mock maker, which rewrites the bytecode of the class under test, slowing builds and muddying stack traces. Injecting a Clock instead is the better seam.

S15 Why is @ExtendWith(SpringExtension.class) explicit rather than auto-registered?

Because silently starting a Spring context because a jar on the classpath registered an extension produces tests whose runtime and behaviour you do not control.
