Volume 8 — Spring Security

Which filter decides, in what order — and the four ways a stateless API passes every test you have and still ships a cross-service privilege escalation.

  • 9 sections
← Prev Next →

If you only remember five things

  1. It is a servlet Filter, not a HandlerInterceptor. Boot registers exactly one filter, springSecurityFilterChain, ahead of the DispatcherServlet — so it protects requests that never reach a controller, and authorization written as an interceptor is bypassed by requesting a path with no handler.
  2. URL rules are an ordered list of if statements, first match wins. A broad rule above a narrow one does not merge with it — it makes it dead code, silently, and /admin/** is world-writable.
  3. SecurityContextHolder is a ThreadLocal and does not cross a thread boundary. Propagate explicitly with DelegatingSecurityContextAsyncTaskExecutor; setting MODE_INHERITABLETHREADLOCAL copies at thread creation and permanently poisons every pooled thread.
  4. A JWT is a signed assertion, not a revocation mechanism. JwtValidators.createDefaultWithIssuer checks iss, exp and nbf and never aud — a valid signature means someone you trust signed it, not that they signed it for you.
  5. Disable CSRF only when no browser-held credential can be attached automatically. An HttpOnly refresh-token cookie is ambient, so "we're stateless" is not the condition — it is a server property, not a browser one.

No section matches that filter.

01

Filter chain & SecurityContext

The container registers one filter. Everything you configure becomes an entry inside that filter's ordered list, which is why "add a filter at position N" is a real and frequently necessary activity. Know the order: when a request is rejected and the reason is not obvious, the answer is nearly always a filter you forgot is in the list.

Interview trap — filter, not interceptor

"Spring Security uses HandlerInterceptors" is wrong in a way that matters. Interceptors run inside DispatcherServlet dispatching, after handler resolution — so they cannot secure a request for a handler that does not exist, which is exactly the request an attacker sends. Spring Security is a Filter registered as springSecurityFilterChain, a DelegatingFilterProxy over the FilterChainProxy bean, and it runs for /health, /error, static resources and 404s alike.

What the container sees, and where the filters live
LayerHoldsConsequence
Container filtersForwardedHeaderFilter, RequestContextFilter Run before security; trust their input
springSecurityFilterChainOne Filter holding the ordered list above A plain FilterRegistrationBean sits outside or inside it depending on its @Order, which changes what it can see
DispatcherServletHandler resolution, binding, rendering Everything security does applies to the whole application, not to controller methods
Multiple chains — the rules, and how they are usually misread
MechanismWhat it actually does
securityMatcherRestricts which requests this chain handles. The first chain whose matcher matches is used, exclusively
@Order on the beanDecides which chain is consulted first — highest priority first. Not declaration order, and not alphabetical
No matcher at allMatches every request not already claimed. If it is not last, it swallows the rest of the application
Matching timingEvaluated once, at chain-selection time, before a single filter runs
Typical shapeTwo is almost always right: a machine-facing /api/** chain at @Order(1), a browser catch-all at @Order(2)
 
@Bean
@Order(1)                                     // highest priority, evaluated first
SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")           // first match wins, exclusively
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(csrf -> csrf.disable())
        .oauth2ResourceServer(o -> o.jwt(withDefaults()))
        .exceptionHandling(e -> e.authenticationEntryPoint(
            new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)))   // 401, not a 302
        .build();
}

@Bean
@Order(2)                                     // the browser fallback
SecurityFilterChain browserChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(withDefaults())
        .build();
}
Must remember — the filter that loads but never saves

Through Spring Security 5.6 the filter around the chain was SecurityContextPersistenceFilter, which loaded the context and saved it back in a finally. From 5.7 it is SecurityContextHolderFilter, which does not save. If you set an Authentication during a request and nothing else persists it, that authentication lives only for the rest of that request — the bug that presents as "works until the session expires". A stateless chain therefore wants NullSecurityContextRepository as well as SessionCreationPolicy.STATELESS: the first stops the session being created, the second stops the context being written.

How the holder stores the context — and where each strategy breaks
StrategyBehaviourVerdict
ThreadLocalSecurityContextHolderStrategyA plain ThreadLocal The default. Correct while one request occupies one thread for its whole life
MODE_INHERITABLETHREADLOCALInheritableThreadLocal — children inherit at thread creation Dangerous. A pool created during a request inherits that request's identity permanently
MODE_GLOBALOne static valueStandalone and CLI tools only
Reactive strategyContext in the Reactor Context WebFlux. A ThreadLocal is meaningless on an event loop — see Volume 10
Interview trap — the identity that changes hands

SecurityContextHolder does not cross a thread boundary. An @Async method, a scheduled job, or a manually created pool that reads it gets null — the thread is the problem, not the user. The tempting "fix" is MODE_INHERITABLETHREADLOCAL, which is worse than the bug: it copies at thread creation, so one request's Authentication is baked permanently into every pooled thread created during it, and user A sees user B's data. It reproduces only under concurrency, which is why it survives staging. The correct mechanism is explicit delegation, which captures the context per task submission.

@Bean
TaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor pool = new ThreadPoolTaskExecutor();
    pool.setCorePoolSize(10);
    pool.setMaxPoolSize(50);
    pool.setQueueCapacity(500);
    // The wrapper is the point: it captures and re-installs the calling
    // context around each task, then clears it. The raw pool does neither.
    return new DelegatingSecurityContextAsyncTaskExecutor(pool);
}

For the servlet async case, WebAsyncManagerIntegrationFilter at position 2 registers the interceptors that carry the context across a startAsync() boundary, so a controller returning a Callable or a CompletableFuture still sees the right principal. Every request pays for the whole chain whether it is secured or not — a dozen filters doing small work is not where a request's time goes, and the cost that actually bites is I/O inside a filter, which adds a round trip to every anonymous 401 and every health check. Profiling a chain with two filters in it is a way of avoiding the question.

02

Authentication

Authentication is five objects with distinct jobs. The most common interview error is naming UserDetailsService as the mechanism — it loads; the provider decides.

The five collaborators, and the confusion each invites
CollaboratorJobCommon confusion
AuthenticationCredential carrier on the way in, principal plus authorities on the way out Believed to be two types. It is one interface; the same token class, authenticated and not
AuthenticationManagerOrchestrates: iterate providers, return the first success, throw if none Believed to do the checking. It delegates
AuthenticationProviderPerforms the actual check for one token type Returning null for "failed" instead of throwing
UserDetailsServiceloadUserByUsername — a lookup and nothing more Believed to validate. It does not
PasswordEncoderencode and matches matches(raw, encoded) argument order, easy to reverse
What a provider's return value means to ProviderManager
ReturnMeansWhen it bites
An AuthenticationAuthenticated Returned immediately — first match wins, so provider order is significance
null"I do not handle this token type" Next provider is tried; if none handle it and there is no parent, ProviderNotFoundException
Throws BadCredentialsException"I handle it, and the answer is no" Propagates immediately; the remaining providers are not consulted
Interview trap — null is not "no"

Returning null and throwing are semantically different, and confusing them produces the bug that presents as "my second provider is never called". Return null for a token type you do not support; throw BadCredentialsException for a token you do support and the answer to which is no. Return null on a wrong password and ProviderManager moves on, then throws ProviderNotFoundException — which surfaces as a 500 or an opaque error rather than a 401.

DaoAuthenticationProvider is the default for username and password, and it runs four account-state checks before it touches the password: isEnabled, isAccountNonExpired, isCredentialsNonExpired, isAccountNonLocked. Checking them first means a disabled account cannot be probed for a valid password at all.

The UserDetails stub that disables lockout

All four flags default to true in User.UserBuilder. A custom UserDetails implemented as a stub — every method returns true — makes the disabled and locked branches unreachable code. The account-state mechanism is present, reads correctly in review, and does nothing, so your lockout does not lock out. The deeper habit: return an identical 401 for BadCredentialsException, UsernameNotFoundException, DisabledException and LockedException, because distinguishing them tells an attacker which usernames exist.

Password encoders, and what each one costs
EncoderProperties
BCryptPasswordEncoder Default strength 10, ~100ms per hash. Salt is embedded, so the hash is self-contained. Truncates at 72 bytes — two passwords sharing a 72-byte prefix are the same password to it
Argon2PasswordEncoder Memory-hard, tunable, parameters carried in the encoded string. Requires Bouncy Castle
SCryptPasswordEncoder Memory-hard; must be supplied explicitly to DelegatingPasswordEncoder
Pbkdf2PasswordEncoder The delegating encoder's default when nothing else is registered; random salt, 185,000 iterations in recent versions
NoOpPasswordEncoder {noop} — compares plaintext. A demo tool and a production vulnerability
Must remember — the only hash-migration mechanism that works

DelegatingPasswordEncoder prefixes every stored hash with {id} — {bcrypt}$2a$10$…, {argon2}$argon2id$… — so the application can hold hashes made by different algorithms at the same time and know which produced each. Register the new algorithm as the encoding default and the old one as the matching fallback: DaoAuthenticationProvider then calls upgradeEncoding(stored) after a successful match and re-hashes through updatePassword. It is the only mechanism that works because you cannot re-hash offline — the plaintext does not exist in your database, and login is the only moment you have it. Two costs to plan for: an extra write on essentially every login, and an implementation that silently discards the update, in which case the migration never progresses and nothing tells you.

@Bean
PasswordEncoder passwordEncoder() {
    Map<String, PasswordEncoder> encoders = new HashMap<>();
    encoders.put("argon2", Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8());
    encoders.put("bcrypt", new BCryptPasswordEncoder(12));
    encoders.put("noop", NoOpPasswordEncoder.getInstance());   // legacy matches only

    // First argument is the DEFAULT FOR ENCODING; the rest stay for matching.
    return new DelegatingPasswordEncoder("argon2", encoders);
}

One consequence is worth stating because it surprises teams mid-migration: going from BCrypt 10 to BCrypt 12 roughly quadruples comparison time. If your failed-login lockout counts attempts on that slow path, a security upgrade has silently changed your effective rate limit by 4×. Capacity-plan the login path and review the rate limiter in the same change.

03

Authorization & method security

The matcher DSL, and the one rule that has to be last
MethodMatches
requestMatchers(String…)Path patterns — Ant style in 5.x, PathPattern in 6.x
requestMatchers(HttpMethod, String…)Method and path
requestMatchers(RequestMatcher…)Arbitrary predicates — headers, content type, parameters
anyRequest()Everything remaining. Must be last, as a statement of intent
hasRole / hasAuthorityRequires ROLE_X / exactly X
access(…)Raw SpEL, or a bean reference

hasRole("ADMIN") and hasAuthority("ROLE_ADMIN") are exactly equivalent — hasRole prepends the literal ROLE_ if absent, and that is the entire difference. The bug is therefore never in the DSL; it is always a mismatch between what the grant produced and what the expression asks for.

Interview trap — the prefix nobody expected

A JWT resource server maps the scope claim to authorities prefixed SCOPE_, so orders.read becomes SCOPE_orders.read and hasRole("orders.read") looks for ROLE_orders.read and matches neither. Half the time a missing prefix is the whole story; the other half the claim is named scp rather than scope, or it is a space-delimited string where a list was expected. The diagnostic is to log the authorities on the Authentication at the point of rejection — not the token, which puts a live credential in your logs.

Must remember — the migration that enforces nothing

@EnableGlobalMethodSecurity was deprecated in Spring Security 5.6 and removed in 6.0. Its replacement, @EnableMethodSecurity, defaults prePostEnabled, securedEnabled and jsr250Enabled all to false — whereas the annotation it replaced defaulted prePostEnabled to true. So swapping the annotation and nothing else compiles, starts, and enforces nothing: every @PreAuthorize is silently a comment. The correct form is @EnableMethodSecurity(prePostEnabled = true). There is no warning and no failing test, because the failure is a protected method that is simply public.

The method-security annotations
AnnotationRunsUse it for
@PreAuthorizeBefore the method, SpELThe default choice — the check happens before any side effect, including logging and notifications
@PostAuthorizeAfter, with returnObjectAuthorizing on what the method produced. Skipped entirely if the method throws
@PreFilterBefore, on a collection argumentKeeping unauthorized rows out of the method at all — the most underused of the four
@PostFilterAfter, on the return valueRead paths. The method has already run, so side effects happened for rows you then removed
@SecuredJSR-250 role namesPrefix required: @Secured("ROLE_ADMIN")
@RolesAllowedJSR-250 role namesPrefix not added
Interview trap — two annotations are AND, not OR

Multiple @PreAuthorize annotations on one method are AND-ed; each registers its own interceptor and all must pass. There is no built-in OR, and the resulting AccessDeniedException is indistinguishable from the user having neither role — which is why "the user has the role and still gets a 403" is such a common report. Use hasAnyRole('ADMIN','AUDITOR') or an explicit SpEL or.

// Enable with explicit flags — the no-attribute form enables nothing.
@EnableMethodSecurity(prePostEnabled = true, securedEnabled = true)

// Authority naming decides which check matches. These three do not agree:
User.withUsername("u").roles("ADMIN")        // grants ROLE_ADMIN       -> hasRole("ADMIN")
User.withUsername("u").authorities("ADMIN")   // grants ADMIN            -> hasAuthority("ADMIN")
Jwt  withClaim("scope", "orders.read")        // grants SCOPE_orders.read -> hasAuthority("SCOPE_orders.read")

@PreAuthorize("hasAuthority('SCOPE_orders.write')")
@PostAuthorize("returnObject.ownerId == authentication.name or hasRole('ADMIN')")
@PreFilter("filterObject.ownerId == authentication.name")
public List<Order> findVisible(List<Order> orders) { ... }

Method security is proxy-based, which is where its blind spot lives. The general self-invocation mechanics belong to Volume 3; the security-specific version is that a private or final method, a final class, or a call from inside the same class means the annotation is never evaluated. The structural fix is to put the check on the public entry points, so the set of protected methods and the set of publicly reachable methods are the same set — a discipline problem becomes a structural one. The scalable version of that is an ArchUnit rule failing the build when a public method on a @RestController or @Service in a protected package is unannotated.

AuthorizationManager — what replaced the decision point

Since Spring Security 6, the authorization decision is made by an AuthorizationManager, which generalised away the old AccessDecisionManager. hasRole, hasAuthority and the rest are AuthorizationManagers, composed into a RequestMatcherDelegatingAuthorizationManager — so “which class decides?” and “which annotation expresses it?” are the same question at two levels. Signature, both extension points, and the reactive variant are in vol08 §3.6.

The decision surface in 6.x
QuestionAnswer
What is the decision type? AuthorizationManager<T>, with check(Supplier<T> authentication, T object)
Why a Supplier? So the decision can be deferred — a JWT validated asynchronously must be able to resolve before authorization checks it
Is AccessDecisionManager still around? No. Replaced. Anything you remember about AbstractAccessDecisionManager and RoleVoter is 5.x-era
Custom domain permission? Two hooks: a SpEL bean method (@accountPermission.canEdit(...)) or a PermissionEvaluator for hasPermission(...)
Reactive? The reactive variant returns Mono<AuthorizationDecision> — the two variants are not interchangeable
Interview trap — authorization annotations are enforced by a proxy, so the method must be reachable through it

The same self-invocation trap that breaks @Transactional breaks @PreAuthorize, for the same reason: both are applied by a proxy around the bean. An internal call never passes through it, so the check silently does not run. This is why the fix is to protect public entry points rather than the method you happen to be worried about — and it is why an ArchUnit rule that fails the build on an unannotated public method in a protected package scales better than review.

04

JWT & stateless APIs

The reason JWTs are everywhere is not that they are good. A server-side session store does not scale the way a stateless service does, and teams reach for tokens long before they need federation. Every problem below is a consequence of one decision — making the token self-contained — and that decision buys exactly one thing: eliminating a lookup. A Redis GET is well under a millisecond, so if it is not your bottleneck you have taken on all of this to remove it.

What a claim you do not check actually enables
ClaimWhat skipping it permits
issA token from any other tenant of the same IdP is accepted — in a multi-tenant IdP, a full cross-tenant breach
audCross-service privilege escalation. Service A accepts service B's token
expA token works forever. Nimbus enforces this; a hand-rolled check often forgets it
nbfA leaked token from the future is accepted early
scope / scpThe missing scope check: a read-only token calls a write endpoint, returns 200, and nothing records the distinction
Must remember — a token is an assertion, not a capability

There is no server-side state saying "this token was cancelled", so logout cannot invalidate it. Three responses, and choosing between them is the real design decision: short expiry (5–15 minutes, at the cost of a refresh path and clock correctness), refresh tokens (a store again — a smaller one), or a jti denylist checked per request. Production systems run all three. Treat the access-token lifetime as a revocation budget: the maximum window you are willing to accept between compromise and containment. A 12-hour token is a stated policy decision, and the reason an account disabled in the morning kept trading until the evening.

Interview trap — alg: none and algorithm confusion

Two attacks, one mitigation. A token with {"alg":"none"} and an empty signature is accepted by any verifier that dispatches on the header. Algorithm confusion is subtler: the server holds an RSA public key and trusts RS256; the attacker signs an HS256 token using that public key as the HMAC secret — and the public key is a known string, so it verifies. The mitigation is identical: never derive the verification algorithm from the token. Configure the decoder with the algorithm you chose. Nimbus refuses both by default, provided you have not configured around it.

@Bean
JwtDecoder jwtDecoder(String issuer, String audience) {
    // FIXED algorithm — never read from the token header.
    NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation(issuer).build();

    OAuth2TokenValidator<Jwt> audienceCheck = jwt ->
            jwt.getAudience() != null && jwt.getAudience().contains(audience)
                ? OAuth2TokenValidatorResult.success()
                : OAuth2TokenValidatorResult.failure(
                    new OAuth2Error("invalid_token",
                        "This token was not issued for " + audience, null));

    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(issuer),   // iss, exp, nbf — NOT aud
        audienceCheck));                                // aud — yours to write
    return decoder;
}
The two numbers that decide whether key management works

A denylist has a natural bound: an entry only needs to outlive the token it revokes, and only tokens with exp more than about 15 minutes ahead can matter. Size it by issued_per_second × token_lifetime_seconds — 50 tokens/second with 15-minute tokens needs at most 45,000 entries, which fits a local Caffeine cache with a 15-minute TTL and needs no Redis at all. Storing every jti forever is a memory leak with an operational alarm attached. The second number is the rotation overlap: publish the new key, start signing with it, and keep the old one published for longer than the access-token lifetime — 24 hours for a 15-minute token. Getting it wrong is a total logout at the moment of rotation, which is exactly what 30% of requests returning 401 after a rotation looks like.

Clock skew is the fourth failure mode and the least discussed. exp and nbf are compared against the verifying node's clock, so without tolerance the same token is accepted on one node and rejected on another — intermittent, and shaped like a load-balancer problem. Thirty seconds of tolerance is comfortable and sixty starts to show up in an incident review; the right number is your worst observed drift, and the real fix is NTP.

05

OAuth2 & OIDC

OAuth2 says nothing about who the user is — it is a delegation protocol, and knowing which grant a system uses is the first question to ask, because the grant tells you whether there is a person in the token at all.

The grants, and what the principal is
GrantPrincipalUse it for
Authorization code + PKCEThe userBrowsers and mobile acting for a person. The only browser grant still recommended
Client credentialsThe serviceMachine to machine. No user, no browser, no refresh token — a username/password exchange where the password is the client secret
ImplicitThe userDeprecated. Token in the URL fragment, no PKCE — the reason PKCE was invented
Resource owner passwordThe userDeprecated. Your app sees the user's password; legacy IdPs only
Device codeThe userTVs, CLIs — anything with no browser and no keyboard. The honest answer for a desktop CLI
Must remember — client credentials has no user

The token's subject is the calling service, and sub is meaningless as a person. You cannot act on behalf of anyone, there is no refresh token because there is no session to refresh, and a scope in a client-credentials token describes the service's permissions. The characteristic mistake is bolting client credentials onto a user-facing flow, and the symptom is an audit log that names a service where a person should be.

Interview trap — why implicit died, and what PKCE buys

Implicit returned the access token in the URL fragment, which put a credential in the address bar, in history, in the Referer header of every outbound request, and in any script on the page — and it had no client secret to protect the exchange, so an interceptor had the token outright. PKCE (RFC 7636) fixes it without a secret: the client generates a 43–128 character code_verifier, sends only its SHA-256 code_challenge in /authorize, and reveals the verifier in the back-channel /token call. An interceptor of the redirect has the code and not the verifier, so the code is useless. That is why implicit is deprecated at the OAuth 2.1 draft level and removed from 2.1.

Access token or ID token — reading the wrong one is a design error
Access tokenID token
AudienceYour APIYour client application
Containsscope, aud, sub — permissionssub, name, email — identity
Your API reads it?YesNo
Spring type@AuthenticationPrincipal Jwt@AuthenticationPrincipal OidcUser

Note the split in what Spring Security 6 actually contains: oauth2Login, oauth2Client and oauth2ResourceServer — the consumer side. Authorization-server and OIDC-provider functionality moved out to the separate spring-authorization-server project for 6.x. If you are building the issuer, the cost is four things you now own: client-secret storage, signing-key rotation with an overlap, refresh-token storage and revocation, and being a high-value target whose compromise hits every client at once.

Service to service: propagation or client credentials
Question the call is answeringMechanismCost
"Who is the end user doing this?"Token propagation — pass the caller's token through Downstream can act as the user but cannot be re-attributed to the calling service. A compromise of any one service is a compromise of the user's full permission set everywhere
"Is this service allowed to do this?"Client credentials, or token exchange (RFC 8693) Blast radius confined to that service's scopes, and the calling service is a known principal — but user identity has to be passed as validated data, which is engineering work
Trade-off — the identity model, chosen once org-wide

The choice is whether the model is end-user-centric (propagation) or service-centric (client credentials). Flips on: whether a downstream genuinely acts for a person — "list this customer's orders across all services" is a straightforward query under propagation and awkward work under client credentials; "service A may read service B's data" is the reverse. The pattern that holds up is client credentials by default with propagation as a deliberate, reviewed exception, so the exception is visible in review and the default blast radius is one service's scopes. Either way the whole model rests on section 4's check: a downstream that cannot tell a token meant for it from a token meant for someone else has no model at all.

Spring Security does not contain an authorization server

The single most-repeated mistake in OAuth2 interview answers is treating Spring Security as though it can be an issuer. It cannot. The authorization-server and OIDC-provider functionality moved out to a separate project, spring-authorization-server. What Spring Security 6.x gives you is the consumer side — oauth2Login(), oauth2Client(), oauth2ResourceServer().jwt() and client credentials.

Consumer versus issuer — different projects, different blast radius
SideWhat it isOwns
Consumer
(Spring Security 6.x)		 oauth2Login(), oauth2Client(), oauth2ResourceServer().jwt() Verifying a token, mapping claims to authorities, your own session after login
Issuer
(separate project)		 spring-authorization-server — /authorize, /token, /userinfo, /jwks Client secrets, refresh tokens, signing-key rotation, consent, token storage
Interview trap — the two sides have opposite security postures

A resource server verifies; an authorization server stores secrets and signs tokens. That makes the issuer a high-value target whose compromise affects every client at once, and it is why operating one correctly is a specialty rather than a Spring feature. The defensible default for most teams is a hosted provider (Auth0, Okta, Cognito, Keycloak) for the issuer and being a resource server in Spring. The full argument is in vol08 §5.4.

06

CSRF, CORS & sessions

Must remember — the condition, stated precisely

Disabling CSRF is correct when no browser-held credential can be attached to a cross-site request automatically: no session cookie, no browser-cached Basic credentials, no client certificate in the browser's store, no refresh token in a cookie. An Authorization: Bearer header does qualify — a cross-origin script cannot set one on a form POST, so there is nothing for an attacker to have the browser supply. The condition is a property of the credentials, not of the deployment, and "the service is stateless" is the shortcut that eventually gets applied to a refresh-token-in-a-cookie chain and produces the incident.

Where csrf.disable() is right, and where it ships a vulnerability
SituationCSRFWhy
Bearer-token API, no cookies at allDisable is correctNo browser-held credential to forge
JWT plus a refresh token in an HttpOnly cookieKeep CSRFThe refresh cookie is ambient. This is the mistake — "we're stateless" while holding a cookie
Form login with JSESSIONIDKeep, alwaysThe canonical case
Server-rendered Thymeleaf formsKeepth:name="${_csrf.parameterName}" is free
SPA with a cookie-backed sessionKeepUse CookieCsrfTokenRepository
HTTP Basic called from a browserKeepBrowsers cache and resend Basic credentials — it is ambient

CsrfFilter checks only unsafe methods; GET, HEAD, TRACE and OPTIONS are exempt, because a state change is defined as a non-idempotent one. A GET endpoint that mutates is therefore a CSRF-adjacent design error of its own — the one place a browser will cross-site-send a credential with no token check at all. The synchroniser token itself is a SecureRandom 32-byte value stored in the session and rendered into the form, compared in constant time on every unsafe method.

@Bean
SecurityFilterChain spaChain(HttpSecurity http) throws Exception {
    // XOR handler: masks the token with a one-time pad so a reflected value
    // cannot serve as a BREACH compression oracle.
    CsrfTokenRequestAttributeHandler handler = new XorCsrfTokenRequestAttributeHandler();
    handler.setCsrfRequestAttributeName(null);   // SPA reads ONE token, not two

    return http
        .csrf(csrf -> csrf
            // httpOnly: false is DELIBERATE — the SPA must read it and
            // echo it in the X-XSRF-TOKEN header. With true, every write 403s.
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            .csrfTokenRequestHandler(handler))
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .build();
}
Interview trap — CORS and CSRF are not substitutes

CORS decides whether a script on another origin may read a response; CSRF decides whether a request was intended. A CSRF form POST succeeds under perfect CORS, because the attacker never needed the response — the money still moves. Conversely CORS is what stops evil.com reading your API's response via fetch with credentials, and it is a browser-only control that curl ignores entirely, so it is never server-side authorization. Teams that disable CSRF "because we configured CORS" have removed the half that matters and kept the half that does not.

Trade-off — cookie CSRF repository is not safe alone

A bare double-submit comparison is vulnerable to cookie injection: an attacker who can set a cookie on your domain — a subdomain takeover, a header-injection bug, a related-domain XSS — plants a known token and sends a matching header, and the server sees a valid pair. Flips on: whether the token cookie is Secure (so it cannot be planted over plaintext), host-only rather than Domain-widened to siblings, and paired with SameSite on the session cookie — which stops the browser sending the session cross-site at all, making the double-submit check the second line rather than the only one. Never wildcard Access-Control-Allow-Origin with credentials; browsers reject the combination, and they differ in when they reject it, which is why it reproduces as a Safari-only bug.

Testing & hardening

An authorization assertion is only real if the assertion went through the chain. A test that builds a SecurityFilterChain and asserts on its filter list tells you about the configuration and nothing about the behaviour — and it still passes after someone inserts a permissive rule.

The suite that passes over an open endpoint

@AutoConfigureMockMvc(addFilters = false) removes the filter chain and with it every authorization rule the application has. A test that posts to /api/accounts and expects 201 passes whether the rule is authenticated(), permitAll(), or absent entirely. It is a legitimate speed tool for controller-behaviour tests — binding, serialisation, exception handling — and a coverage hole the moment it is the only kind of test. The staff-level position is two layers: handler tests without filters, plus real requests through the real chain asserting 401 for anonymous and 403 for insufficient scope. The decision to use it should be visible in the test name.

HeaderWriterFilter writes several headers by default — X-Content-Type-Options: nosniff, X-Frame-Options: DENY, X-XSS-Protection: 0, and Cache-Control on responses that set credentials; HSTS only when requiresChannel is HTTPS. The attack surface outside the filter chain

Almost every Spring security question is about the filter chain, and almost every real vulnerability is not. The chain decides who you are; it does not stop a @ModelAttribute from binding role, a Resource from serving ../../etc/passwd, or a redirect: URL from sending a user off-site. Volume 8 keeps the full table at §6.7; these are the ones that recur in review.

Sessions: fixation, concurrency, timeout

Stateless JWT APIs removed most of this from the critical path, but any browser-held session brings it back. The three properties, and what each defends:

  • Fixation defence. Spring Security changes the session ID on authentication by default (sessionFixation().changeSessionId()). An attacker who planted a known ID pre-login must not still hold a valid session afterwards. This is why “regenerate the session on privilege change” is the rule to remember — login is a privilege change.
  • Concurrency control. maximumSessions bounds how many sessions one principal may hold; the second login can be told to expire the first. It is a policy decision, not a security control, and it is enforced by SessionManagementFilter — which is also why it disappears entirely in a stateless setup.
  • Timeout. Inactivity timeout bounds an abandoned session; absolute timeout bounds its total lifetime. Both are attributes on the servlet HttpSession, configured through Boot's server.servlet.session.*.
Interview trap — “we’re stateless, so CSRF and sessions don’t apply”

Half right, and the half that is wrong causes real incidents. Dropping the session removes fixation, concurrency and timeout — but a cookie still authenticates you if one is present, and that is precisely the CSRF condition. Statelessness is what makes SameSite and CSRF-tolerance decisions possible; it does not make them automatic. See vol08 §6.6 and §4 of this sheet for the token-side equivalent.

Must remember — the three capabilities a 3am runbook needs

Security features are specified by what they prevent and rarely by what they enable afterwards. Three questions a design has to answer, and most do not: kill one user's access immediately (a SessionRegistry or a jti denylist); enumerate who is currently authenticated (a session store — stateless removes the capability entirely, because there is no list when there is no state); and determine what an account touched in a window (audit logging at the data-access layer, not the login layer). A stateless architecture removes the second one by design; the honest test is whether anyone made that choice deliberately rather than as a side effect.

The login path is a capacity model, not just a security control

BCrypt at strength 10 costs roughly 100ms of CPU per comparison, on the login path, by design — and a failed attempt costs the same as a successful one. A service with 200 concurrent login attempts in flight is therefore spending about 20 CPU-seconds per second of wall time, so it needs headroom proportional to your peak login rate rather than your average request rate. Two scaling consequences: a per-instance rate limiter is multiplied by the instance count the moment you scale out, so it must be distributed; and a distributed limiter puts a dependency on exactly the path an attacker wants to exhaust. Moving to strength 12 quadruples all of it — which is why the strength change and the rate-limiter review belong in the same change.

The pattern across all of it: a security control that only works during business hours is not a control. A rate limiter that lives in memory, a denylist only the author understands, a lockout counter that resets on deploy, a signing key nobody can rotate under pressure — each is a feature that fails in the one situation it was built for. The concrete test is the runbook: can a person who did not build the system, at 3am, with a leaked credential, execute the containment steps? If not, the gap is in capability — enumeration, revocation, key rotation, audit — and not in the configuration.
