Volume 12 — Messaging, Kafka & RabbitMQ

Two models, two sets of defaults, and almost every messaging outage traces back to picking the wrong one or inheriting a default nobody chose. Written against spring-kafka / spring-amqp 4.1.1 and Boot 4.1.1.

  • 6 sections
← Prev All cheatsheets →

If you only remember five things

  1. A queue gives a message to one consumer; a log keeps it for every consumer. Retention is what makes replay possible, and it is the single property that drives most broker choices. One deletion happened at ack time — Kafka does not delete on read.
  2. @KafkaListener's id is the group id by default. idIsGroup defaults to true even though the javadoc's "@return false to disable" reads as though it does not. Rename an id and the listener joins a new group, replaying from the earliest offset.
  3. Kafka's default ack mode is BATCH, not RECORD, and Spring Boot does not change it. RabbitMQ's is AUTO, and on failure it requeues — an unbounded loop, not a retry.
  4. Kafka's default backoff is 9 retries with no delay, and exception types the classifier does not recognise are classified retryable. Your NullPointerException is getting nine attempts.
  5. Exactly-once covers the sequence, not the steps. The official wording is that the read and process still have at-least-once semantics, and a database commit plus a broker commit cannot be one atomic thing. That gap is what the outbox closes — see Volume 11 §7, not here.

Interview trap — what does Kafka do with a message after a consumer reads it?

Nothing. The log does not delete on read; retention does, by time or size. That is why replay, a new read model from history, and feeding a brand-new consumer group are all free. On a queue the message is gone at ack time, and a consumer that was down missed it. If you cannot say which of these your system has, everything downstream is guesswork.

Trade-off — retention is a capacity decision, not a footnote

The same property that buys replay costs storage, and the two are on one dial: raise retention and you can rebuild any read model you will ever want, at 7 days × daily throughput × average record size. The number worth having in an interview is that order of magnitude — 100k msg/s at 1KB retained for a week is roughly 60 TB before replication. That is why retention is usually set per topic by purpose, and why “we might need it back someday” is not an argument for a week on a high-volume topic.

02

Consumer groups and ordering

One rule generates everything else: each partition is assigned to exactly one consumer in a group at a time. Different groups each get all the partitions, independently.

What each grouping change actually does
ChangeEffect
Same group, more consumersSplit partitions — capped at the partition count
New groupA full independent copy of everything from its committed offset
More partitionsMore parallelism, and a weaker ordering guarantee forever
Concurrency above partitionsIdle consumers. Nothing. This is the most common Kafka misconfiguration
Produce with a keySame key → same partition → ordered
Produce with no keyPartitioner chooses — two events for one order can arrive reversed
 
// Key by aggregate id: every event for one order lands on one partition,
// so the consumer never sees a cancel for an order it has not seen created.
kafkaTemplate.send("orders",
        new ProducerRecord<>("orders", order.getId(), event));

// No key: the partitioner picks, so ordering across the pair is lost.
Interview trap — is a partition processed in parallel?

No. Not with any number of consumers. The javadoc says it outright: "Messages from within the same partition will be processed sequentially." concurrency is consumer-group membership, not a thread pool. And a partition is never the thing that is parallel — which is why adding partitions to raise throughput is a semantic decision, not a scaling knob.

03

Spring for Kafka — the defaults

Version-tagged: spring-kafka 4.1.1, Boot 4.1.1. Major changes landed in the 4.0 line, so anything remembered from before 3.0 needs checking before you say it.

Defaults and precedence people answer from memory, and the truth
ThingMost people sayActually
idIsGroupfalsetrue — the javadoc's "@return false to disable" misleads. id becomes the group id
Ack modeRECORDBATCH. Boot does not change it — no default in its metadata
On failureStop the partitionSEEK — rewind and replay, do not halt
BackoffA sensible exponential one9 retries, no delay
Unknown exception typeFatalRetryable — the classifier defaults to true
Producer error handlersetErrorHandler on the factoryDoes not exist. Use the future callback or a ProducerListener

Group-id precedence, from the source: an explicit groupId wins; otherwise id becomes the group when idIsGroup is true; otherwise the consumer factory's group.id is used.

How a send fails — there is no producer-side error handler to configure, verified absent from DefaultKafkaProducerFactory, ProducerFactory and KafkaTemplate in 4.1.1. Failure arrives on the CompletableFuture as a KafkaProducerException carrying the failed record, or through a ProducerListener — and Boot installs a LoggingProducerListener by default, which logs errors and does nothing on success. A fire-and-forget send with neither can fail with only a log line.

Interview trap — which DeserializationException?

Spring's — org.springframework.kafka.support.serializer — not Kafka's SerializationException. It is in the default fatal list along with MessageConversionException, ConversionException, MethodArgumentResolutionException, NoSuchMethodException and ClassCastException. Adding the wrong class to your fatal list configures nothing and your parse failures get nine retries.

04

Error handling & exactly-once

Two objects, composed, not chosen between: DefaultErrorHandler holds the retry policy; DeadLetterPublishingRecoverer is what it delegates to once retries are exhausted.

DeadLetterPublishingRecoverer recoverer =
        new DeadLetterPublishingRecoverer(kafkaTemplate,
                (r, ex) -> new TopicPartition(r.topic() + "-dlt", r.partition()));

DefaultErrorHandler errorHandler =
        new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L));

f.setCommonErrorHandler(errorHandler);   // otherwise: seek, 9 retries, no delay

What the container does when a listener throws — the documented six-record example, three partitions, two records each, throw on the fourth:

  1. It commits pending offsets before calling the error handler — records 1–3 are durably marked done.
  2. SEEK rewinds only the remainder: p1 to offset 1, p2 to offset 0.
  3. The next poll returns the three unprocessed records.

So the effective semantics are mixed — at-most-once for what was already processed, at-least-once for the rest. A crash immediately after cannot recover the committed ones. Only RuntimeException reaches the error handler; an Error bypasses it.

What transactions actually cover, against the usual interview answer
CoveredNot covered
KafkaTransactionManagerA read → process → write sequence completing exactly onceThe read and the process individually — those stay at-least-once
Kafka write in the sequenceOffsets sent and committed in the same transactionNothing
Database writeNothingThe whole problem. Two separate commits with a gap; the docs require "remedial action" if the second fails
The actual answerOutbox — message row in the same DB transaction, relayed asyncAt-least-once, not exactly-once; consumer idempotency still required

Note the long-retry mechanism: the error handler pauses the consumer and polls it before sleeping, which keeps the group alive through an extended backoff instead of triggering a rebalance.

Interview trap — a transaction manager removes the error handler entirely

With a transactionManager on the container, no error handler is installed — the exception rolls the transaction back instead. That is documented behaviour, not a misconfiguration. It also means your retry and DLT policy silently stops applying the moment you add a transaction manager.

Spring for RabbitMQ

Version-tagged: spring-amqp / spring-rabbit 4.1.1. Three acknowledge modes, unchanged since 2.3.0.

spring.rabbitmq.listener.simple.concurrency=10
spring.rabbitmq.listener.simple.max-concurrency=20
spring.rabbitmq.listener.simple.prefetch=10
spring.rabbitmq.listener.simple.default-requeue-rejected=false
spring.rabbitmq.listener.simple.acknowledge-mode=auto

defaultRequeueRejected defaults to true. A listener that throws a deterministic exception nacks with requeue, the message returns to the head of the queue, and the next delivery fails identically — a tight loop, hot CPU, no progress, and a flat queue depth. That flat depth is what makes it confusing: the queue looks fine and the consumer looks busy.

With requeue=false: the broker routes to the queue's dead-letter exchange if it has one, and drops the message if it does not. So the DLX is a queue-level broker setting, and if you never configured one, rejecting is deletion.

Two dead-letter paths — pick one, they are not additive
MechanismWho routesState it clearly
Queue dead-letter exchangeThe broker, on requeue=falseRequires the queue to have a DLX and a resolvable routing key, or messages are dropped
RepublishMessageRecovererSpring, after retries are exhausted"the message is ack'd and is not sent to the dead letter exchange by the broker"
RejectAndDontRequeueRecovererNobody — it just rejectsLets the broker's DLX do the routing, so the queue config becomes the critical part
Configuring both DLX and a republish recovererThe recoverer winsThe broker DLX is silently inert. This is the trap

The silent Java-serialization case. SimpleMessageConverter — the default — handles String, byte[] and Serializable. Most DTOs implement Serializable for caching reasons, so they get Java serialization with no warning at either end: the class name travels in the payload, the consumer needs the identical class, and a serialVersionUID change breaks messages already in flight. Fix it with an explicit Jackson2JsonMessageConverter, and an allow-list where trust crosses a boundary.

simple vs direct. spring.rabbitmq.listener.simple.* is SimpleMessageListenerContainer (background poll thread, thread pool, prefetch-based); .direct.* is DirectMessageListenerContainer (drives basicConsume on the channel thread, so a slow listener blocks its consumer). Both extend the shared AmqpContainer base, so acknowledge-mode, prefetch and default-requeue-rejected work identically under either — but concurrency, max-concurrency and the executor settings are on the concrete containers and do not cross-configure. Setting .simple.concurrency for a direct listener fails silently.

Interview trap — what does a requeued message actually cost?

Everything downstream of the queue, and it never converges. defaultRequeueRejected=true is a redelivery loop, not a retry: no attempt limit, no backoff, no dead letter, and it re-uses a delivery slot each time. If the exception is deterministic — a bad payload, a missing row, a constraint violation — the queue depth stays flat while a CPU burns. Diagnose it as messages_ready flat plus a hot consumer, not as throughput.

06

Choosing and operating

The three production questions, and the single observation that answers each
SymptomLook atMeans
Lag climbing on one partition, neighbours flatPer-partition lagStuck offset, not slowness. One record fails fatally — a deserialization error is fatal by default — so the container seeks back forever and nothing is logged
Lag climbing on every partitionConsumer rate vs produce rateGenuinely cannot keep up: CPU, a slow downstream call, or a handler exceeding max.poll.interval.ms
Whole group stops, in burstsRebalance log, poll interval vs handler durationA member was evicted for exceeding the poll interval, and the rebalance stops everything while it runs

Every order duplicated after a deploy, then stopsThe consumer group idThe listener joined a new group — renamed id, with no committed offsets, replaying from the earliest retained offset
Idempotency and the outbox — two mechanisms, two different gaps
MechanismClosesDoes not close
Outbox — message row in the same DB transaction, relayed asyncThe publish gap: commit succeeds and publish failsDuplicate delivery, because relay-then-crash-before-mark re-publishes. It is at-least-once, not exactly-once
Idempotency — dedup key, upsert, state machineDuplicate processing, which is the defaultNothing on the publish side
Where it has to liveAt the point of the external effect — charge, email, incrementLogging twice is harmless; emailing twice is a ticket per replay
Not using itSource of truth is not a relational DB you can put a table in…or you have accepted eventual consistency and occasional loss

Schema evolution. A registry with a compatibility mode turns a runtime break into a CI failure. The mode is a deployment-topology decision: BACKWARD lets you deploy consumers first; FULL is strictest; FORWARD suits a log read by consumers you do not control; BACKWARD_TRANSITIVE checks every historical version. Set it for your slowest reader — a topic retaining a week of history still has readers in whatever shape those records were written in.

Must remember — alert on a lag growth rate, never a threshold

A growing lag never recovers on its own; a flat, non-zero lag is often the steady state of an idle producer, and a few records of oscillation between partitions is poll-timing noise. RabbitMQ has no equivalent single number at all — you derive the trend from messages_ready against a constant consumer count, which is the queue-form of the same signal. And whichever broker it is, per-partition granularity is what separates "one bad record" from "not enough capacity", because a group total cannot distinguish them.

1partition is the unit of both parallelism and ordering — raising it trades the second for the first
Scaling reality check — the uncommitted buffer is the blast radius of a restart

RabbitMQ: prefetch × consumers is the maximum a client can be holding unacknowledged, so 250 × 20 consumers is 5,000 messages that a restart replays. Kafka: partitions caps consumer throughput, and total capacity is partitions × per-partition throughput, disk-bound. Both mean the same thing operationally — the uncommitted buffer is the blast radius of a restart, and it is set by configuration, not by how fast the code is.
