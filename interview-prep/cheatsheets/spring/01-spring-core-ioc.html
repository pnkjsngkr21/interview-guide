Spring — The Spring Complete Deep-Dive

Volume 1 — Spring Core & the IoC Container

How a bean travels from a BeanDefinition to a wired object, which of the four stereotypes actually changes behaviour, and why publishEvent is not fire-and-forget.

  • 9 sections
Next →

If you only remember five things

  1. Beans are BeanDefinition metadata, not objects. The class name is held as a String until resolution, which is what makes the container lazy-capable and re-configurable at all.
  2. refresh() runs in three phases, and the order is the answer to most "why did my bean do X at startup" questions. Definitions edited (BeanFactoryPostProcessor), then processors registered (BeanPostProcessor), then every non-lazy singleton created — which is where your @PostConstruct runs, before your migrations.
  3. @Autowired is a four-step resolution, not reflection. Candidates by type with generics resolved, filtered by @Qualifier, then @Primary → @Priority → field-name match, else NoUniqueBeanDefinitionException. Collection injection points skip the disambiguation step entirely.
  4. The stereotypes are three behaviours and one comment. @Repository adds exception translation, @Controller adds MVC handler registration, and @Service adds nothing at all.
  5. The event bus is synchronous and in-process. publishEvent returns only after every listener has returned, a @TransactionalEventListener with no active transaction does nothing at all without an error, and the effect dies with the JVM.

No section matches that filter.

01

Architecture & modules

Spring is three things stacked: a container that constructs objects, wires them, manages their lifecycle and intercepts cross-cutting calls; an integration layer of transactions, persistence and HTTP built on it; and an annotation-based programming model. Spring is not a persistence or web framework — JPA, Hibernate, Tomcat and Jackson are separate projects it adapts, which is why most "Spring is slow" arguments are really arguments about Hibernate or the connection pool.

Interview trap — two answers that score zero

"Spring is an IoC container." Correct, and nearly content-free. The senior answer continues: it is a container that owns construction, wiring, lifecycle and cross-cutting interception — and the interception is exactly why @Transactional and @PreAuthorize fail silently when the proxy is not in the call path (Volume 3, Volume 4).

"IoC and DI are the same thing." No. IoC is the principle: the container controls construction and lifecycle. DI is one technique for achieving it. Template Method, Strategy and event listeners are all IoC without any DI anywhere.

Interview trap — why not just extend BeanFactory and stop?

Because BeanFactory is deliberately minimal, and a narrow surface is what makes it cheap to implement — which is what keeps it appropriate for embedded, lazy, or library contexts. ApplicationContext is the façade that bundles the enterprise services so applications get them by default. Adding them to BeanFactory would make it unimplementable in practice.

02

Injection styles

There are three, and the difference is not style — it is when the failure surfaces and whether the class is constructible without a container. Field injection fails last and quietly, which is the whole argument.

Constructor, setter, field — and the cost of each
ConstructorSetterField
Object immutableYesNoNo
Required vs optionalNaturally requiredNaturally optionalAmbiguous — always
Circular referenceImpossibleResolvesResolves
Fails atConstruction — fail-fastFirst useFirst use
Unit test without Springnew and gonew and goReflection or @InjectMocks
Spring's positionDefaultOptional dependencies onlyDiscouraged; cycles rejected by default since Boot 2.6
 
@Service
class OrderService {

    private final PaymentClient payment;      // 1. CONSTRUCTOR — required, immutable

    public OrderService(PaymentClient payment) {
        this.payment = payment;
    }

    private NotificationClient notification;   // 2. SETTER — genuinely optional

    @Autowired
    public void setNotification(NotificationClient n) {
        this.notification = n;
    }

    @Autowired
    private AuditClient audit;                 // 3. FIELD — do not do this
}
Must remember — why constructor injection is the default

Three concrete reasons, none of them taste. One: a final field is safe under safe publication, so injected state does not depend on the container's internal synchronisation. Two: a required dependency cannot be accidentally absent. Three: the class is constructible outside Spring, which is what makes unit testing free — a 4,000-bean context takes seconds to start, and field injection forces that cost into every test.

Flips on: a dependency that is genuinely optional, or that must resolve lazily. That is the whole legitimate use of setter or field injection — and it is narrower each release, because Boot 2.6+ rejects circular references by default precisely so that field injection cannot keep hiding them. The full circular-reference mechanism belongs to Volume 2.

Interview trap — "why is my injected field null?"

The reflexive answer is that @Autowired did not run. The real answer is that the bean was constructed through a path that bypassed injection: a new in a lambda or a test, a static factory, a @Configuration method that called new instead of returning the bean, or a self-invocation of a proxied method. Field injection makes all of those compile happily, so the failure is deferred to runtime. The second consequence nobody says out loud: with field injection, anything in the constructor sees null.

03

Resolving @Autowired

"It uses reflection" is the answer that scores zero. There is a four-step candidate resolution with a fixed precedence, and every ambiguity question in a Spring interview comes down to knowing which step you are standing in.

Split the interface— None of the above read naturally. Four implementations of one contract is a modelling problem

class CheckoutService {

    @Autowired
    @Qualifier("stripeClient")
    private PaymentClient preferred;        // explicit — @Primary cannot reach it

    @Autowired
    private PaymentClient defaultClient;    // LegacyPaymentClient, via @Primary

    @Autowired
    private List<PaymentClient> allClients;  // all three, in registration order
}

indexers.orderedStream();   // respects @Order, closed with the context
Interview trap — generics are erased, and proxies widen the type

Generic matching works because a @Bean definition records the resolved return type of its method — which is why List<ShippingClient> contains only the FedEx bean and not every bean on the classpath. It has a raw-type edge: with a bare List, Spring matches on List itself, collects nothing, and injects an empty list without an error. And it has a proxy edge: generics are erased at runtime, so a JDK-proxied bean can resolve to the interface rather than the concrete class — and a generic point expecting the concrete type then matches nothing, again silently.

Scaling reality check — type lookup is not free

getBeansOfType() walks the whole definition registry and, for unresolvable types, loads classes to read their hierarchies. It is O(bean count) per call, so calling it once per request on a 4,000-bean application is a real throughput bug rather than a style nit. Fix: inject List<T> or hold an ObjectProvider<T> and let the container resolve it once at startup.

04

BeanDefinitions & refresh

Beans in the container are not objects. They are BeanDefinition records saying how to make one — which is precisely what lets the container answer "what beans exist?" before instantiating anything, stay lazy, and reconfigure itself.

What a BeanDefinition actually records
FieldWhy it is on the record
beanClassName as a String The class need not be loaded to register or instantiate a bean — this is what keeps startup from eagerly loading the whole classpath
scope, lazy Singleton or prototype; lazy defers creation past phase 3
constructorArgumentValues, propertyValues What the factory method needs to build the object
autowireMode, autowireCandidate byType, byName, constructor, or no
dependsOn Explicit ordering, because source order is not a mechanism
initMethodName, destroyMethodName Destruction callbacks — Volume 2 owns these
role ROLE_APPLICATION vs ROLE_INFRASTRUCTURE — the filter behind every bean listing you have ever used
Must remember — the three phases, and the one that bites

Phase 1, BeanFactoryPostProcessor, edits the definitions before any bean exists. Phase 2, BeanPostProcessor is registered early — a processor not registered by then never sees a single bean. Phase 3 is instantiation, where @PostConstruct and InitializingBean actually run; Volume 2 owns the full callback sequence.

The production surprise falls straight out of it: a @PostConstruct or an eager @Bean method that queries the database runs in phase 3, during refresh, before your own migrations. If the table does not exist, startup dies with a BeanCreationException whose cause is three frames deep. A startup gate should not be a bean constructor.

Interview trap — the constructor that breaks on Friday

A single-argument constructor is auto-selected with no @Autowired annotation at all — but only while exactly one candidate for that type exists. Add a second Clock bean three packages away and the container can no longer disambiguate, so the bean fails to create in a file nobody edited. Mark such constructors @Autowired explicitly, even where it is not strictly required.

The reflexive bad answer to the wider question is "Spring injects by constructor if there is one, otherwise by setter". Setter injection is a fallback for properties, never for constructor dependencies, and it only happens at all on a bean that has an instantiable no-arg constructor.

Must remember — the class name is a string

Holding beanClassName as a String is not laziness for its own sake: it is what lets a bean be registered, listed, and described without the class ever being loaded. It is also why getBean(MyService.class) usually works on a JDK-proxied bean — the container records the resolvable target class when it builds the proxy — and why the erased-generics case in section 3 is a real failure rather than a theoretical one.

To answer "what beans exist?", read getBeanDefinitionNames() then filter on getRole(). On a 4,000-bean application roughly 3,900 are Spring's own, and that filter is the difference between a useful listing and an unusable one.

05

Scanning & stereotypes

All four stereotypes are meta-annotated with @Component and are found by the same scan. They are not four names for one thing, and the popular "they're all just semantic" answer is wrong for two of the four.

What each stereotype changes, and what it does not
AnnotationChanges at runtimeDoes not change
@ComponentDiscovery by the scan; meta-annotated @Indexed Nothing else — it is the baseline
@ServiceNothing Bean name, scope, proxying, exception translation
@RepositoryRegisters PersistentExceptionTranslationPostProcessor, proxying the bean so vendor exceptions become DataAccessException How the bean is named or scoped
@ControllerRequestMappingHandlerMapping registers it as a handler Any dependency-injection behaviour
 
@Configuration                        // full mode: CGLIB-enhanced
class AppConfig {

    @Bean DataSource dataSource() { return new HikariDataSource(cfg); }

    @Bean OrderRepository orderRepository(DataSource ds) {
        return new JdbcOrderRepository(ds);   // calls the METHOD, not new DataSource()
    }
}

@Configuration(proxyBeanMethods = false)   // lite mode: that call builds a SECOND DataSource
class FastConfig { }
Interview trap — "@Configuration classes are proxied" hides the qualifier

Full-mode CGLIB enhancement happens only when proxyBeanMethods is true (the default) and the class is not final and the methods are not final or private. Change any one of those and you are in lite mode silently — and in lite mode, calling your own @Bean method from another one constructs a second, unmanaged instance. Two connection pools where one was expected, or a repository that does not share the transaction. Passing the bean as a method parameter is safe in both modes and is the better habit even where the direct call happens to work.

proxyBeanMethods is not a free optimisation
true — full (default)false — lite
Class enhanced by CGLIBYesNo
Intra-@Bean call returnsThe container singletonA new, unmanaged instance
Bean-definition processingFullLite
A cycle between two @Bean methodsSometimes deferred and resolvesFails at startup
Reach for it whenYou call your own @Bean methods directlyYou do not — the sane default
Interview trap — a @Qualifier in the wrong place

@Qualifier on a @Bean method's parameter selects the dependency to inject. The same annotation at method level puts a qualifier on the produced bean and does nothing to disambiguate the parameter — and it is silently ignored rather than rejected. A qualifier that looks like it is working and is not is the worst version of this bug.

Scaling reality check — basePackages = "com"

Scanning uses ASM metadata reading, not class loading, so a broad scan is faster than it looks — but it is still an ASM pass over every class on the classpath. In a 500-developer monorepo where every team owns a com.acme.* package, that produces a build of around 90 seconds and an application context registering beans from libraries you never meant to include. Narrowing the scan to the module's own package is the difference between a 5-second and a 60-second startup, and it is a one-line fix teams routinely ship without making. lazyInit on the scan is a diagnostic, never a fix.

06

The context family

ApplicationContext is the enterprise façade, and the hierarchy below it is mostly a question of which web stack you are on. Environment is the format-agnostic abstraction over configuration sources, which is what lets the same code read from a file, system properties, the command line, or a remote source unchanged.

How Boot picks, and what that choice costs
Servlet (MVC)Reactive (WebFlux)

Default serverTomcatReactor Netty
Request handlingThread per request, blockingEvent loop, non-blocking
Chosen whenspring-boot-starter-web presentspring-boot-starter-webflux present and web absent

Interview trap — classpath: vs classpath*:

classpath: resolves the first match and stops. classpath*: aggregates all matches across every jar. For a single well-known resource the difference is invisible; for anything that several jars might contribute — templates, locale bundles, auto-configuration metadata — you need classpath*:, and the failure mode is silent: you get one jar's copy and no warning, so an override in the application jar is simply ignored. This one mechanism explains a whole family of "my override is not being picked up" bugs in layered jars.

Scaling reality check — classpath*: is O(n)

The resolver has to open and read directory entries for every candidate it matches. A classpath*: over templates in an application shipping 40,000 resources is a measurable startup cost — and it is typically hidden inside a starter rather than written by the team that suffers it. When startup is inexplicably slow, classpath*: is a top-three suspect alongside scan breadth and eager I/O.

Must remember — the i18n setting people find in production

setFallbackToSystemLocale(false). Left at its default of true, a user whose OS locale is en_GB can take the system-locale path and land on the base bundle, while a user requesting en gets the translation — producing the classic "works for some users" pattern, where message keys resolve correctly on the developer's machine and not on the user's.

Trade-off — injecting Environment

Reaching into Environment from a service is a service locator: it makes the class's configuration surface invisible, and env.getProperty(...) scattered through a service is a coupling no test can see. Flips on: a genuinely dynamic value that is not part of the class's contract — a feature flag, a tenant-selected setting, a secret resolved at request time. The staff-level test is whether you can name the cases. If you cannot, you wanted a typed properties group instead, and Volume 7 covers that end to end.

07

Events

The publisher, the multicaster, the listeners — that part is easy. Almost every question turns on three facts the API does not show you: the multicaster is synchronous, a transactional listener silently does nothing without a transaction, and the whole thing dies with the JVM.

@TransactionalEventListener phases, and the one that does nothing
PhaseRunsThe catch
AFTER_COMMIT (default)Only if the transaction commits No transaction is active on that thread any more
BEFORE_COMMITJust before the commit, still inside the transaction Can still veto, but sees uncommitted state
AFTER_COMPLETIONAfter commit or rollback Cleanup only — the outcome is already fixed
No active transactionNothing runs. No error, no warning, no log. fallbackExecution = true opts in when the publisher is not always transactional
 
@Bean
ApplicationEventMulticaster multicaster() {
    SimpleApplicationEventMulticaster m = new SimpleApplicationEventMulticaster();
    m.setTaskExecutor(new ThreadPoolTaskExecutor());  // bounded — the default is a thread per task
    return m;
}

@Component
class OrderAuditListener {

    @EventListener @Order(10)                          // lower runs first
    public void afterCacheEviction(OrderCreatedEvent e) { ... }
}
Must remember — the p99 that jumped 20×

Problem: order-creation p99 went from 120 ms to 2.4 s, CPU flat, database fine. Investigation: a thread dump showed request threads parked in an HTTP client called from an @EventListener. Root cause: the synchronous multicaster — the publisher's thread was running the listener inline, and the listener made a slow blocking call. Solution: a SimpleApplicationEventMulticaster with a bounded executor. Prevention: publish a small immutable payload and never do I/O inline unless you have explicitly budgeted for it.

Three silent event failures, one root cause

No transaction, no listener. A @TransactionalEventListener binds to a transaction phase; with none active the event is discarded with nothing logged. This is the single most common "my listener never fires" cause.

AFTER_COMMIT means after, not during. The transaction is over: an exception in the listener cannot roll anything back, and a @Transactional call from it starts a new transaction. It is the right default for "notify the world" and the wrong choice for "make sure two writes agree".

Async failures vanish. The multicaster has no executor configured, so it is synchronous and listener latency is the publisher's latency. The trap is the fix: a SimpleAsyncTaskExecutor creates a new thread per task, so adding asynchrony without configuring an executor converts a latency problem into unbounded thread creation. And an exception in an @Async listener goes to the AsyncUncaughtExceptionHandler, which by default logs and swallows — the request succeeds and the effect silently does not happen.

Trade-off — in-process event, or outbox and broker?

An in-process event moves the coupling rather than removing it: the listener still runs on the publisher's thread, still fails the request when it throws, and is now invisible to anyone reading the publisher. It has no durability and does not cross a process boundary — two instances have two buses. Flips on one question: if this process dies between the commit and the listener running, what is lost? "The confirmation email, fine" — events are right. "The ledger entry" — you need a transactional outbox plus a broker. Volume 11 owns the distributed half.

Properties & profiles

Property resolution is a strict precedence ladder, and the rule behind it is one sentence: more specific and more external wins. The working shorthand is command line, then system properties, then environment variables, then the config file, then @PropertySource.

Interview trap — "environment variables override everything"

Wrong, and wrong in the direction that costs you. Environment variables sit at position 8, below command line arguments at 3 and below Java system properties at 7 — which is exactly why java -jar app.jar --server.port=9000 beats SERVER_PORT=9000 java -jar app.jar. The practical consequence is a CI system's convenience flag being silently overridden by whatever the deployment puts on the command line.

Interview trap — relaxed binding does not apply to @Value

Relaxed binding is a @ConfigurationProperties feature. @Value("${...}") does an exact-key lookup against the Environment. So a key that binds fine through a properties class can fail through @Value with Could not resolve placeholder — use the kebab-case key in both places. Relaxed binding exists at all because an environment variable cannot contain . or -: Duration takes 10s, 500ms or ISO PT10S; DataSize takes 10MB; an Enum accepts UPPER_SNAKE, camelCase or kebab-case.

Must remember — @Profile, and the committed-profile hazard

@Profile is shorthand for @Conditional(ProfileCondition.class), evaluated against the active profiles; expressions like "prod & !eu" and {"staging", "qa"} work, and "!dev" excludes a profile. The production hazard is a committed spring.profiles.active: dev, which silently overrides whatever the environment intends — the usual symptom is an app in production connecting to a developer's database. Set the active profile from the environment in every deployment, and spring.profiles.default: prod as a fail-safe so a missing setting fails toward production behaviour. The general @Conditional family is Volume 7's.

One decision belongs to this volume: @Value is for a single value, a @ConfigurationProperties class for a group — typed, JSR-380 validated at startup, relaxed-bound, and enumerable in one place. The scattered version has no validation, no enumeration, and no answer to "what can an SRE change at runtime?" beyond a grep. Volume 7 owns the binding mechanics; Volume 11 owns a distributed config server.
