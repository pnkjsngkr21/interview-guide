Volume 10 — WebFlux & Project Reactor

The demand signal that makes a slow consumer survivable, the one rule about threads that a reactive application lives or dies by, and the handful of operators whose defaults decide whether you hold memory or lose data.

← Prev Next →

If you only remember five things

  1. Reactive is demand, not async. The subscriber calls request(n) and the publisher may never emit more — and request(n) is a hint, so a publisher is free to emit fewer.
  2. Backpressure is automatic only for sources that can be slowed. Kafka, a hot Flux, an already-materialised list cannot honour demand, so you must insert an onBackpressureX — and the no-argument onBackpressureBuffer() is unbounded heap waiting for a slow consumer.
  3. A blocking call on an event-loop thread stalls every other request on that loop. Reactor catches block() and throws IllegalStateException; an undeclared blocking library is worse, because it shows up as a throughput plateau rather than an error.
  4. Laziness is per subscription, not per assembly. A cold Flux re-runs its whole pipeline — the database query included — for every subscriber, and a discarded subscribe() in a controller is a latent double-execution bug.
  5. flatMap runs 256 inner publishers concurrently by default. That number is a real bound on in-flight work and is very often exactly the number that trips a downstream rate limit.

01

The reactive model: demand and backpressure

Reactive is not "async with nicer syntax". It inverts control of the data flow. An imperative producer decides when to produce and blocks if the consumer is slow; a reactive producer hands a Publisher to a framework and waits to be asked. That request is demand, and demand-based flow control is the entire point of the Reactive Streams specification.

public interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}

public interface Subscriber<T> {
    void onSubscribe(Subscription s);   // 1. first, exactly once — the only route to a Subscription
    void onNext(T t);                  // 2. only after request(n) with n > 0
    void onError(Throwable t);         // 3. terminal, at most once
    void onComplete();                 // 4. terminal, at most once
}

public interface Subscription {
    void request(long n);              // the demand signal — a HINT, not a counter
    void cancel();                     // "no more, ever"
}

Must remember — request(n) is a hint

A publisher is permitted to emit fewer items than requested — request(10) on a source with three items left emits three and completes. What it may never do is emit more. This is why Flux.generate and Flux.push take request accounting seriously, and it is the single most common source of "my backpressure settings aren't being respected" confusion.

Interview trap — "what if the consumer can't keep up?"

The reflexive answer is "backpressure kicks in and the producer slows down". That is true only for sources that can honour demand. For a source that cannot — a Kafka consumer, a hot publisher, a JDBC-style buffered source — backpressure has to be inserted with an onBackpressureX operator, and the choice is therefore a data decision you are making under load. The senior answer names which operator and what it costs, because each of the five in the table above gives up something different. "It just buffers" is the answer that produces a production OOM.

Scaling reality check — the no-argument buffer

onBackpressureBuffer() with no size is unbounded. When the consumer degrades — a GC pause, a slow downstream, a cache-miss storm — the buffer grows until the heap dies, and the process takes the healthy event loops down with it. The bounded form surfaces a visible, bounded, diagnosable failure instead. The second question is always why is the consumer slow, because the buffer is usually a symptom of a degradation that should have been found first.

02

Project Reactor core: Mono, Flux, cold, hot

Mono<T>Flux<T>
Cardinality0 or 10 to N
Completes withA value, or emptyA value, a completion, or neither
subscribe() returnsMono<Void>Flux<Void>
Typical useA single DB row, an HTTP responseA stream of records, a collection
Interview trap — lazy per subscription, not per assembly

"Reactive operators are lazy" is right, and the useful follow-up is the trap: a cold Flux re-executes its whole pipeline, including the database query, for every subscriber. Two subscribers to a cold pipeline means two queries — the most common WebFlux N+1, and invisible in tests, which subscribe once.

The related bug is a discarded subscription: hotFlux.subscribe(this::handle) inside a method throws the Disposable away, so the Flux keeps running with nobody listening and can never be cancelled. The fix for "my controller method is being called twice" is almost always to find the second subscription.

Mono.just(fetchExpensiveThing()) is the eager twin of the same mistake: the argument is evaluated at assembly, so Mono.defer is what defers the computation. And caching a cold Mono field does not merely cost less, it changes semantics — every subscriber gets one result, including ones that wanted fresh data, and a Mono field still looks lazy.

Flux.just(m1, m2, m3)
    .flatMap(this::unwrap)            // concurrent, UNORDERED; default concurrency 256
    .concatMap(this::unwrap)          // sequential, ordered — one at a time, no head-of-line surprise
    .flatMapSequential(this::unwrap)  // concurrent AND emits in source order
    .flatMap(this::call, 8);          // explicit concurrency bound, overriding 256
Must remember — 256 is an operational number

flatMap's default concurrency is 256 (Queues.SMALL_BUFFER_SIZE). A flatMap over a 10,000-element stream will therefore have 256 calls in flight, not 10,000 — and if each one hits a downstream with a rate limit, 256 concurrent is the number that trips it. Choosing between flatMap, concatMap and flatMapSequential is often the whole performance story of a pipeline.

The related shape worth catching: Mono.zip(a, b).then(c) is not a short circuit. a and b are subscribed concurrently, both must complete, their values are discarded, and then c runs — all three execute. Reading .then() as "skip the earlier work" produces load, not savings.

Trade-off — which Sinks sink you pick

Sinks.many().multicast().onBackpressureBuffer() buffers for slow subscribers, and with no bound specified that buffer grows until the heap dies. Sinks.many().multicast().directBestEffort() drops for the slowest subscriber instead. Flips on: whether the stream carries facts or state. Use the buffered sink when every element is a fact and losing one is unacceptable, and you are willing to spend memory to keep it. Use directBestEffort for a live dashboard or a current-value stream where only the latest value is meaningful. Using it for a data stream silently loses events; using the unbounded buffer for a fast producer is an OOM. This is a data-modelling decision, not an operator preference.

03

Errors, retries & timeouts

An error is a terminal signal travelling down the chain, not an exception thrown across a thread boundary — the subscriber receives onError. Because it is terminal, a stream that errors delivers nothing further to the subscriber: every element that would have followed is lost, not queued.

The fallback vocabulary, and what each one hides
OperatorBehaviourRead as
onErrorReturn(v)Emits a fixed value and completesCheapest; also the easiest way to make an outage invisible to alerting
onErrorResume(f)Calls f with the exception, continues with whatever Publisher it returnsUse it when the fallback depends on error type or must be asynchronous
onErrorResume(Class, f)Type-selectiveOne exception is expected, another is not — OrderNotFound → empty, everything else propagates
onErrorMapTranslates the exception, stays fatalDomain errors at the edge; usually for tests and for error contracts
onErrorComplete()Swallows the error and completesAlmost always a bug — the failure never reaches anyone
onErrorContinueDrops the failed element, carries onDocumented as best avoided; see the trap below
Interview trap — onErrorContinue

onErrorContinue lets an errored element be dropped and the stream carry on. It is documented as best avoided, and the reason is worth knowing: the operator must attempt to resubscribe to recover the next element, and recovering the position of a failed element inside a source that is not restartable produces duplicate or skipped data. If you need "skip the bad rows", do it in filter/flatMap with an explicit per-element result type rather than with onErrorContinue.

Retry variants, and the one you ship
FormBehaviourHow it bites
retry()InfiniteDo not ship — an outage becomes a permanent hot loop against the dependency
retry(3)Three immediate retriesOne user request becomes four, arriving in a burst exactly when the dependency can least serve them
retryWhen(Retry.max(n))Max attemptsStill immediate unless backoff is added
retryWhen(Retry.backoff(..)Full control: backoff, max backoff, jitter, filter, exhaustion handlerThe only form with a retry budget; filter transient errors and exclude a 400 or a 401
 
// retry(3) — no delay, no backoff, no jitter: the version that causes incidents
Mono.just(callApi()).retry(3);

Mono.just(callApi())
    .retryWhen(Retry.backoff(3, Duration.ofMillis(100))
                      .maxBackoff(Duration.ofSeconds(2))
                      .jitter(0.5)                  // ±50% randomisation
                      .filter(this::isTransient));  // a 400 is not worth retrying
Scaling reality check — jitter is not a nicety

Un-jittered retry is worse than no retry in a fleet. If every instance retries at 100ms, 200ms, 400ms after a shared dependency fails, the retries are synchronised across the fleet and produce periodic load spikes that keep the dependency from recovering. Jitter is what breaks the synchronisation.

The multiplication is also multiplicative, not additive, and the two figures quoted for it mean different things. Amplification is attempts per layer, raised to the number of layers: three layers making one attempt plus one retry is 2³ = 8 requests per user request, while three layers making two retries each is 3³ = 27. Which of those you are looking at follows from the retry policy you configured, not from the layer count alone — and either way it compounds again with the number of concurrent callers. Observed in production: an upstream reporting a 4× traffic spike that matched our request count while it returned 503s. Retrying a non-idempotent operation is the sharper version of the same mistake — a 504 after the work actually succeeded becomes a duplicate write. And a circuit breaker belongs alongside retry, not instead of it: retry handles transient blips, the breaker fails fast when the failure is sustained (see Volume 11).

Timeout forms, and what each one actually measures
FormScopeWatch out
timeout(Duration)The whole subscriptionNo fallback — errors with TimeoutException
timeout(Duration, fallback)Source and fallbackThe fallback does not get its own budget; it consumes the running one
timeout(Duration) on a FluxPer item — the timer resets on each elementIt is an idle timeout, not a total one
timeout(d, Mono.empty()).onErrorResume(ex -> fb)Source onlyThe composition that gives the fallback an independent budget
Must remember — the fallback shares the clock

Concretely: the composition that gives the fallback an independent budget is source.timeout(Duration.ofSeconds(2), Mono.empty()).onErrorResume(ex -> fallbackMono), and the two-argument form is what you should not reach for when the fallback is itself an I/O call. Understanding the difference explains both "my timeout fallback never fires" and "my timeout fires even though the fallback is instant" bug reports, and is worth being able to describe precisely rather than approximately.

WebFlux vs MVC: the threading model

Not "which is better" — which constraint is binding
QuestionAnswerWhen it bites
Reactive or blocking?Reactive wins when the bottleneck is waiting: I/O-bound, high concurrency, low CPU, many connections few of them active, fan-out to many services, streaming, gatewaying, WebSocketBlocking wins when the bottleneck is CPU — image processing, encryption, compression — because reactive adds scheduling overhead and does not add cores. It is slower
What is the win, exactly?A different resource profile, not speed: a few event loops hold thousands of mostly-idle connectionsIt disappears the moment a blocking call sneaks in. For CPU-bound work and for teams whose code is full of blocking calls, MVC is at least as fast and simpler
Is 100× the concurrency free?No. It is traded for thread dumps that are near-unreadable, lost ThreadLocal state, and a persistence story that means leaving HibernateA CRUD service at 200-300 requests/second, where the thread model was never the constraint, buys complexity and nothing else

Must remember — the exact block() failure

Reactor deliberately detects the obvious case and throws:

java.lang.IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-3

Recognising that message — the thread name reactor-http-nio-N is the giveaway that you are on an event loop — is how you tell the declared failure from the dangerous one. The more insidious variant is block() on a boundedElastic thread, because an earlier operator scheduled there: it succeeds, works in testing, and consumes a thread per call under load.

Trade-off — the real cost of a reactive migration

The cost is not the library, it is the people. block(), a ThreadLocal MDC lookup, a blocking JDBC driver, and a debugger showing an event-loop thread with a 40-frame stack all quietly stop working. Before recommending reactive the question is: do we have a measured concurrency requirement that threads cannot meet, and is the team prepared for the operational consequences? "It's more scalable" is not an answer. "We need 50,000 concurrent connections and Tomcat needs 50,000 threads at 1MB of stack each, which is 50GB" is an answer.

Symmetrically, boundedElastic is a legitimate bridge and a poor destination. Flips on: use it as the right interim measure during a migration — put a date and an owner on replacing the blocking dependency — and treat it as the wrong steady state, because the thread is still consumed and you have added a hop and a context switch.

Scaling reality check — finding the undeclared block

BlockHound instruments Thread.sleep, synchronized blocks and Thread.join to throw when the calling thread is a non-blocking thread. It is the tool for the blocking call Reactor cannot detect — the one that shows up as a mysterious throughput plateau far below the hardware's capability. Run it in a load test, because a unit test never exercises the concurrency that causes the stall.

The general executor and thread-pool failure modes — bounded queues, rejection policies, sizing by Little's Law — are owned by the Java concurrency track. The servlet DispatcherServlet path this contrasts with is Volume 5.

public Mono<Order> get(@PathVariable UUID id) { return service.findById(id); }

@GetMapping
public Flux<Order> list() { return service.findAll(); }   // 0 to N — serialises as an array

public Mono<Void> delete(@PathVariable UUID id) { return service.delete(id).then(); }

@PostMapping

    return req.flatMap(service::create)
               .map(o -> ResponseEntity.status(HttpStatus.CREATED).body(o));
}

Request bodies bind reactively too: @RequestBody Mono<T> exposes the body as a publisher, plain @RequestBody T still works through Jackson, and reactive types nest inside ordinary objects. The filter-test and slice-test families are Volume 9 material.

Interview trap — 256KB, and the limit that is not protecting you

WebFlux's spring.codec.max-in-memory-size defaults to 256KB and applies to aggregated bodies — anything not handled as a stream. Exceed it and you get a DataBufferLimitException surfaced as a 500. The production surprise is that people configure spring.servlet.multipart.max-file-size, a completely separate property on a separate stack that does not apply to WebFlux, and conclude they are covered. A team that configured multipart limits and then moved to WebFlux is unprotected and finds out from production.

Must remember — limitRate is the cheap insurance

limitRate(n) caps the demand a downstream operator requests upstream instead of Long.MAX_VALUE. Without it, one greedy consumer downstream — a collectList(), a block(), anything that asks for everything — removes backpressure for the whole upstream chain, including a database cursor, and the resulting memory growth shows up nowhere near the cause. It is a small operator protecting a large system.

Its sibling bufferTimeout(100, Duration.ofSeconds(1)) emits a list when either a hundred elements have arrived or a second has elapsed — the batching primitive for write throughput, one bulk insert instead of a hundred. The dual trigger matters: a count-only buffer stalls on a low-volume stream, a time-only buffer emits enormous batches under load.

Scaling reality check — SSE holds a socket per client

A service pushing to 20,000 idle clients is holding 20,000 sockets, and every hop in the path — load balancer, ingress, proxy — needs a raised idle timeout. Without it, connections are reaped and every client reconnects in a synchronised wave, which is a self-inflicted thundering herd. The fix is a heart-beat on a shorter period than the proxy's idle timeout (an SSE comment, or a Flux.interval of 20 seconds merged into the event stream), a matching idle-timeout configuration on every hop, and jittered client-side reconnect.

Reactive persistence & remote calls

JDBC and R2DBC, and what leaving JDBC actually costs
JDBC / JPAR2DBC
BlockingYesNo
Driver supportUniversalSubset — PostgreSQL, MySQL, MSSQL, H2, Oracle, DB2
ORMJPA / HibernateNone — JPA has no reactive equivalent
Transactions@TransactionalYes, via TransactionalOperator
PaginationOffset-basedOffset-based, or keyset (better)
MaturityDecadesYoung — fewer edge cases, more gaps

The client counterpart is WebClient, the non-blocking HTTP client, paired with DatabaseClient for R2DBC in place of JdbcTemplate. retrieve() is the default and the right first choice: 4xx and 5xx arrive as onError via WebClientResponseException, 2xx gives you the body. exchangeToMono() is what you reach for when the status has to drive logic rather than fail the chain; exchangeToFlux() is for a streaming or chunked response body. Service-to-service resilience — breakers, rate limiters, bulkheads — is Volume 11.

Trade-off — is leaving JPA worth it?

R2DBC's real cost is not the driver; it is that JPA and Hibernate have no reactive equivalent, so choosing R2DBC means leaving the ORM. That is a large decision: no entity mapping, no dirty checking, no persistence context, no derived queries, no Specification, no @EntityGraph — and years of accumulated tuning knowledge. Those ORM concepts are covered in Volume 6. The migration cost is re-implementing the object model by hand, which is a data-modelling project wearing a persistence change's clothes, and it needs a stated rollback.

Flips on: a measured concurrency requirement that threads cannot meet, a query surface simple enough not to need an ORM, and a team prepared to own the persistence layer. Absent those, MVC + JPA + a correctly sized pool is the better trade, and saying so is a stronger answer than listing R2DBC's advantages.

Must remember — no @Transactional in reactive code

@Transactional works by intercepting a method call, binding a connection to the calling thread, and committing when the method returns. A reactive pipeline returns immediately and does work later, on a different thread, so there is no thread to bind a connection to and no "return" to commit on. TransactionalOperator.transactional(manager, callback) replaces it.

The subtlety worth being able to explain: the callback runs on subscription, and the connection is acquired at that moment, not when transactional() is called. So a Mono assembled outside the callback and returned from inside it does not join the transaction — any eager operator ran at assembly time. Mono.defer, or a chain built inside the callback, is the fix. The symptom is a write that commits outside the boundary while the code reads as though it does not.

@Service
class OrderService {
    private final TransactionalOperator tx;   // not @Transactional
    private final R2dbcTransactionManager tm;
    private final OrderRepository orders;

    Mono<Order> create(CreateOrderCommand cmd) {
        return tx.transactional(tm, s -> orders.insert(toOrder(cmd))
                .then(Mono.defer(() -> orders.findById(idOf(cmd)))));
    }
}
Scaling reality check — WebClient is a connection pool

WebClient must be injected as a bean, never built per request. It carries a connection pool, so constructing one inside a controller creates a pool per request — a connection storm against both services, and file descriptor exhaustion on the client side, which is the wrong place to look.

The pool size is also shared across every user of the bean, so under 1,000 concurrent requests a default pool of roughly 100 (Netty's HttpResources defaults) becomes a queue that manifests as latency rather than as an obvious error. Build the bean once with connect timeout, response timeout and maxInMemorySize configured at construction — an HTTP client with no connect timeout and no response timeout is a latency bug waiting for a slow dependency.

07

Context propagation

Reactor's whole point is that work moves between threads — the HTTP event loop schedules onto parallel for a map, onto boundedElastic for a blocking call, back to the event loop for the response. Every per-thread mechanism loses that journey, and the symptom is almost never an error: it is log lines without trace IDs.

What breaks, and what replaces it
MechanismIn WebFluxReplacement
MDC trace correlationSilently absent on any line emitted after a scheduler hopReactor Context via contextWrite, bridged to MDC by Micrometer
SecurityContextHolderReliable only with Context Propagation enabled — see Volume 8 for the reactive security chainThe same Micrometer bridge, registered for the security key
RequestContextHolderThreadLocal-based and therefore unreliablePass the context explicitly as a parameter
InheritableThreadLocalDoes not help at allNothing — it copies at thread creation, and scheduler pools are pre-warmed
Request-scoped beansNot bound to a threadReactor Context for anything new
Must remember — ThreadLocal is wrong by default here

The correct store is Reactor's Context: a per-subscription immutable map that flows downward with the signal, so it follows the work across scheduler hops automatically and concurrent subscriptions cannot see each other's values. A ThreadLocal is scoped to a thread, which is the wrong axis in a reactive pipeline.

Reading it from ordinary code is awkward, which is what Micrometer's Context Propagation is for. Once enabled, Reactor copies the Context into the relevant ThreadLocal around each operator invocation, and existing MDC.get(...) keeps working. State the bridge's purpose precisely: it exists to preserve existing ThreadLocal-based code, not to license new ThreadLocal usage — new code should take the context as a parameter.

// Read and write the Reactor Context, not a ThreadLocal
Mono.just(1)
    .contextWrite(ctx -> ctx.put("traceId", traceId));

// Bridge it back to ThreadLocals so existing MDC code keeps working
ContextRegistry.getInstance()
    .registerThreadLocalAccessor(
        MDC.class.getName(),
        () -> MDC.get("traceId"),
        value -> MDC.put("traceId", (String) value),
        () -> MDC.remove("traceId"));

Hooks.enableAutomaticContextPropagation();
Scaling reality check — Context is not free

Reactor's Context stores values in an immutable linked structure, one node per contextWrite, and every signal walks that chain. A pipeline with dozens of contextWrite calls pays that cost per element — and the usual culprit is a contextWrite inside a flatMap, which then multiplies across thousands of concurrent inner subscriptions. The mitigation is to write context once at the entry point, never per element.

Interview trap — the global registration

Automatic Context Propagation is global mutable state keyed by class name, so two teams each registering an accessor for the same key is a silent conflict where one quietly wins. Own the registration in one bootstrap configuration the whole application imports, rather than letting each library or starter register its own.

And InheritableThreadLocal is the wrong answer to a question people ask constantly: it copies at thread creation, not at task submission. Every Reactor scheduler is a pre-created pool, so the child thread was created long before the value was set and the inherited copy is whatever was there at pool warm-up. The half-and-half log pattern is the diagnostic tell: lines emitted from the event-loop thread carry the trace ID, lines emitted after a hop do not.

08

Testing & the production reality

@Test
void retriesThenSucceeds() {
    StepVerifier.create(callingApiTwiceThenOk())
        .expectNext("first-failure", "second-ok")
        .expectComplete()
        .verify(Duration.ofSeconds(5));   // ALWAYS a duration, or a hung pipeline hangs CI
}

@Test
void emitsEverySecond() {
    StepVerifier.withVirtualTime(() -> Flux.interval(Duration.ofSeconds(1)).take(5))
        .expectSubscription()
        .thenAwait(Duration.ofMinutes(10))   // instant, and deterministic
        .expectNext(0L, 1L, 2L, 3L, 4L)
        .verifyComplete();
}
Must remember — verify() always takes a duration

verify() blocks until the sequence terminates. If the pipeline never completes — which is exactly what a missing onErrorResume or a flatMap that swallows the terminal signal produces — the test thread hangs until the build's global timeout fires, and the report says nothing useful. Passing a duration makes it a fast, legible failure with the expected-versus-actual difference instead.

A hang is worse than a false failure, because it consumes the whole pipeline budget and reports nothing: the team learns to ignore it and the real signal is lost. A test that can hang is a test whose failure mode has not been designed, and reactive pipelines make that easy to overlook because nothing blocks visibly. Virtual time buys more than speed — it buys determinism, which matters more: a Thread.sleep test of a retry schedule is both slow and flaky under CI load. And reach for block() in tests with care: it occupies a thread, so it tests a different code path from production.

What operating the two stacks actually costs

Test the error, retry and timeout-fallback paths, not just the happy path — that is where the value is. When a reactive endpoint is fast in tests and plateaus in production, the three most likely causes are a blocking call on an event loop, an unbounded onBackpressureBuffer or Sinks buffer, and unsized WebClient connection pools. The first two are found with BlockHound in a load test and a heap dump; the third shows up as latency with no error anywhere.

Trade-off — instrument first, decide second

Adopting reactive means adopting a different operational toolset, and that has a real staffing cost, so it should be argued for explicitly before adoption rather than discovered during the first incident. Flips on: whether the binding constraint is connections held open — which reactive genuinely solves — or requests per second, which it usually does not. For a service that has measured neither, the answer is very often MVC with a properly sized Tomcat pool and a tuned connection pool: boring, debuggable, and it ships. If a service is already in production and nobody can find a slow endpoint from a thread dump, the answer is JFR (event-loop threads are sampled rather than blocked, so a parking or CPU profile finds what a thread dump cannot) plus BlockHound in a load test.
