Volume 4 — Transaction Management

The annotation is a label on a door and the proxy is the doorframe — a call that bypasses the doorframe never sees it, and almost every transaction bug is a call that took a shortcut.

  • 9 sections
← Prev Next →

If you only remember five things

  1. Only RuntimeException and Error roll back by default. A checked exception commits everything the method wrote before the throw — the single most common source of silent partial commits. Use rollbackFor = Exception.class.
  2. @Transactional does nothing without a proxy. private, final, static, self-invocation, or a new-ed instance: the code runs, the annotation is inert, and nothing warns.
  3. REQUIRES_NEW suspends the outer transaction, it does not clean it. The first connection stays checked out holding its row locks, and the inner work needs a second — so pool demand is concurrency × nesting depth.
  4. No standard isolation level prevents a lost update. It is a read-modify-write race; the fix is @Version or SELECT ... FOR UPDATE, and SERIALIZABLE on PostgreSQL just converts corruption into 40001 aborts you must retry.
  5. A green test suite proves nothing about commit. @Transactional on a test class rolls back, so the commit path — deferred constraints, readOnly flush discards, two-manager partial commits — is never exercised.

01

The transaction abstraction

Spring's answer to a repeated setAutoCommit(false) block is not clever. It is three interfaces, and the whole volume is a consequence of which of them you are looking at when a transaction misbehaves.

@Bean
public JpaTransactionManager transactionManager(
        EntityManagerFactory emf,
        @Qualifier("dataSource") DataSource dataSource) {
    JpaTransactionManager tm = new JpaTransactionManager(emf);
    tm.setDataSource(dataSource);   // JPA and JdbcTemplate share ONE connection
    return tm;
}
Interview trap — "Spring handles transactions with AOP"

True and nearly useless. The senior version splits the two layers: @Transactional is metadata read by a TransactionAttributeSource into a TransactionAttribute, applied by a TransactionInterceptor running inside the proxy chain, which then calls PlatformTransactionManager. The AOP is how the advice gets invoked; the manager is what actually starts and ends anything. Knowing which of those two failed is most of the debugging. The general proxy mechanics — JDK versus CGLIB selection, why a private or final method cannot be advised — belong to Volume 3; here they are only transaction consequences.

Must remember — the timeout is in seconds

getTransactionTimeout() is seconds, inherited from EJB 2.1 and never changed. timeout = 5000 meaning five seconds is an 83-minute transaction that holds locks and defeats every timeout the operations team set. TIMEOUT_DEFAULT is -1, and on JDBC the value becomes a query timeout — it does not bound how long a SELECT ... FOR UPDATE waits for a lock unless the database has lock_timeout set.

Scaling reality check — a transaction is a thread-local fact

The manager binds the resource in a ThreadLocal owned by TransactionSynchronizationManager / DataSourceUtils, so a transaction's identity is the thread's identity. In an app with 200 Tomcat worker threads a leaked transaction context is 200 separate leaks. The consequence interviewers ask about: a task handed to an executor does not inherit the transaction — the new thread has an empty holder, borrows its own connection, and commits independently, so the async write is neither committed with nor rolled back with the request that scheduled it. ThreadLocal context propagation is the reactive answer (Volume 10); for MVC the honest answer is a separate unit of work with its own @Transactional method.

@Transactional

The rollback rule, stated exactly
Thrown out of the methodDefault outcomeHow to change it
RuntimeException — NPE, IllegalArgumentException, DataIntegrityViolation Rollback—
Error — OutOfMemoryError, StackOverflowError Rollback—
Checked exception — IOException, SQLException, your own extends Exception Commit. Everything written before the throw is durable rollbackFor = Exception.class, or make the exception extend RuntimeException — the better fix, because it also lets Spring's exception translation produce DataAccessException subtypes

The rule is inherited from EJB 2.0 CMMT: a checked exception means the application has declared it can handle the failure, so the container must not roll back. Spring kept it for compatibility, which is why a method that declares throws SomethingChecked and silently commits partial work is the framework's most common production surprise.

@Service
public class OrderService {

    @Transactional private void recalculate(Order o) { ... }   // CGLIB cannot override it
    @Transactional public final void settle(Order o) { ... }   // final: same
    @Transactional public static void archive(Order o) { ... } // not an instance method

    @Transactional
    public void place(OrderRequest req) {
        validate(req);        // this.validate(req) — the proxy never sees this call
        repo.save(toOrder(req));
    }

    @Transactional
    public void validate(OrderRequest req) { ... }   // annotation is inert on this path
}
Interview trap — self-invocation is a design constraint, not bad manners

The reflexive answer is "don't call methods on this" — which is advice, not an explanation. A proxy can only intercept calls that arrive through the proxy reference; this.validate(req) is a virtual call on the raw target, so the target's own body runs directly and the advice never fires. So keep @Transactional on the outermost method, and treat the inner call as a different unit of work. The senior answer names the constraint the constraint implies: any unit of work that must run in its own transaction must be reachable as a separate bean, because "separate bean" is the only condition under which Spring can guarantee a proxy exists. That is why the correct refactor is a design change, and why annotating the inner method "so it is definitely covered" looks correct and does nothing. Ranked fixes: move it to another bean; inject self with @Lazy; TransactionTemplate inside the class; AopContext.currentProxy() (deprecated, needs exposeProxy = true).

Interview trap — readOnly = true is a hint, not a guard

Two different mechanisms, two different databases. The JDBC layer calls Connection.setReadOnly(true): PostgreSQL throws on any write to such a connection, MySQL and H2 treat it as a driver hint and do not enforce it — so the same annotation is a hard guarantee on one database and no guarantee at all on another, and code that relies on it works in one environment and corrupts in another. Under JpaTransactionManager it is worse in the other direction: readOnly = true sets Hibernate's FlushMode.MANUAL, so mutating a managed entity is silently discarded with no exception, because the write was simply never issued. Still set it — it enables replica routing and lets Hibernate skip dirty checking — but describe it to a reviewer as "a hint and an optimisation", never as a safety mechanism.

Interview trap — "I can tell because the annotation is there"

That answer scores zero, and it is the most common one. The annotation is always there — it is in the compiled bytecode, and reading the source tells you nothing about whether a proxy was created or whether the call reached it. The senior answer names the runtime check, the reason it is necessary, and the one case where it lies: isActualTransactionActive() is true for a SUPPORTS method that joined a transaction, which is not the same as "this method started one" — for that you need TransactionStatus.isNewTransaction() from the programmatic API. And the boolean still cannot see the two-manager case, which is why the connection identity is the higher-value diagnostic.

// level 1 — one line, catches "no transaction at all"
assertThat(TransactionSynchronizationManager.isActualTransactionActive())
      .as("must run in a transaction — check self-invocation or a new instance")
      .isTrue();

// level 2 — the connection identity catches what the boolean cannot
var conn = DataSourceUtils.getConnection(dataSource);
log.info("tx={} conn={} thread={}",
         TransactionSynchronizationManager.getCurrentTransactionName(),
         System.identityHashCode(conn),
         Thread.currentThread().getName());
Must remember — attributes do not merge

A method-level @Transactional(readOnly = true) does not inherit propagation = REQUIRES_NEW or timeout from the class annotation. Resolution order, highest first: method on the concrete class, method on an interface, class-level on the concrete class, class-level on an interface. The method annotation is the complete attribute set, and everything else resets to its default. This is the most common "why did my propagation change" bug in layered services, and it is why adding a method annotation "just to be explicit" to a carefully-configured class is a code review comment, not a style choice.

03

Propagation

Propagation is not a style preference. It is a statement about whether this unit of work belongs to the caller's. The decision is made inside AbstractPlatformTransactionManager.getTransaction by inspecting TransactionSynchronizationManager for an existing transaction.

All seven, from the enum REQUIRED(0) … NESTED(6)
PropagationNo existing transactionExisting transaction Second connection?Rollback semantics
REQUIRED (default)Create one Join itNo Inner rollback marks the whole thing rollback-only
SUPPORTSRun non-transactionallyJoin itNo None of its own — it has no boundary to roll back
MANDATORYThrows IllegalTransactionStateException Join itNoSame as REQUIRED
REQUIRES_NEWCreate one Suspend the outer, start a new one, resume the outer after YesFully independent — survives an outer rollback
NOT_SUPPORTEDRun non-transactionally Suspend the outer for the durationNo None; inner data access runs on its own
NEVERRun non-transactionally Throws IllegalTransactionStateExceptionNo None
NESTEDBehaves like REQUIRED — no savepoint Create a savepoint on the same connection; roll back to it on failure No Inner failure undoes only that portion; a checked exception still rolls back everything
Interview trap — MANDATORY and NEVER are assertions

The two nobody uses are the two an interviewer reaches for, because they test whether you understand propagation as assertion rather than strategy. MANDATORY asserts "this method only makes sense inside someone else's transaction" and fails fast at the offending call site, in the test, rather than writing an audit row that rolls back two transactions later. NEVER asserts the inverse and is how you guard a long read-only computation that must not inherit — and therefore not hold — the caller's write locks. Both are cheaper and more durable than a comment saying "must be called from a transaction", because the framework enforces them and the comment verifies nothing.

Scaling reality check — the pool is sized for nesting, not requests

A HikariCP pool of maximumPoolSize = 10 with 10 concurrent request threads each doing one REQUIRES_NEW means every thread holds two connections. The 11th waits the full connectionTimeout and the log says HikariPool-1 - Connection is not available, request timed out after 30000ms — while the database sits at 8% CPU and the on-call pages the DBA. It looks like a database outage and it is a code problem. Sizing the pool as peak concurrency × max depth is legitimate, but it converts a code bug into a permanent capacity tax; the honest staff position is to size for the depth you actually have and treat any depth greater than 1 as a design-review item.

Trade-off — NESTED vs REQUIRES_NEW for "undo just this part"

NESTED reuses one connection, keeps the outer transaction's atomicity, and rolls back only to the savepoint — but the savepoint is not free (the engine issues statements, and some flush before establishing one) and it is not universally supported. REQUIRES_NEW is universally supported and gives a truly independent outcome, but costs a second connection, breaks first-level-cache coherence, and means the inner commit survives an outer rollback. Flips on: if the inner operation must be visible outside even when the caller fails, you need REQUIRES_NEW; if it must vanish with the caller, you need NESTED.

Must remember — NESTED fails silently

Three conditions must hold and none is visible at the call site: the manager must support savepoints, the driver and database must implement them, and there must already be a transaction to nest inside — with no outer one, NESTED silently behaves as REQUIRED and there is no partial rollback at all. The worst case is under JpaTransactionManager: where HibernateJpaDialect cannot obtain a savepoint, Spring falls back to a fresh transaction — not an error — so a method that appears to roll back only its own writes may in fact be committing them independently of the outer, with no log line either way. If you use it, verify TransactionStatus.hasSavepoint() before trusting the semantics you designed around.

The exception nobody caught: UnexpectedRollbackException

Transaction rolled back because it has been marked as rollback-only means an inner participating method threw, someone caught it up the stack, and the outer method returned normally. The inner interceptor called setRollbackOnly() on the shared TransactionStatus as the exception propagated; catching the exception removed the exception, not the mark. The outer code then tries to commit a transaction that is already doomed. The "catch and continue" is running on work that will not commit — and the same mechanism is why retrying a deadlock inside the same transaction can never work: the retry has to wrap a call to a separate @Transactional method so each attempt is a genuinely new transaction with a fresh lock acquisition, and the backoff must be jittered, or every thread retries in lockstep and deadlocks again.

public <T> T withDeadlockRetry(Supplier<T> op) {
    for (int attempt = 1; ; attempt++) {
        try {
            return op.get();     // MUST be a separate @Transactional method
        } catch (CannotAcquireLockException ex) {
            if (attempt >= 3) throw ex;
            Thread.sleep(20L * attempt + ThreadLocalRandom.current().nextLong(20));
        }
    }
}
04

Isolation & concurrency

Four SQL levels, and what each actually buys
LevelDirty readNon-repeatablePhantomMechanism and cost
READ UNCOMMITTEDPossiblePossiblePossible No locks at all. Rarely correct; a reporting replica at best
READ COMMITTEDPreventedPossiblePossible Statement-level snapshot. The PostgreSQL and MySQL/InnoDB default — so this is what most Spring applications actually run
REPEATABLE READPreventedPrevented Possible on PostgreSQL, prevented on InnoDB Transaction-level snapshot (Postgres) or gap locks (InnoDB). A long transaction pins an old snapshot and inflates bloat
SERIALIZABLEPreventedPreventedPrevented Predicate locks / SSI (Postgres) or next-key locks (InnoDB). Aborts — a normal expected outcome you must retry

The table is the Spring-facing view: which level you get from @Transactional(isolation = ...) and what it costs you in the framework. The isolation model itself — every anomaly by name, how each level is implemented under MVCC versus locking, lost updates, and write skew — belongs to Database Volume 5 and is not restated here.

Must remember — DEFAULT means the engine's own level

Isolation.DEFAULT does not mean READ COMMITTED. It means Spring sets nothing and you get the database's configured default, which is READ COMMITTED on PostgreSQL and MySQL/InnoDB and something else elsewhere. And the guarantee you get is per statement, not per transaction, which is the whole explanation for "the same query inside one transaction returned two different counts" — and it means any read-decide-write logic spanning two statements is unprotected. That is not a missing isolation setting; it is the designed behaviour of the default.

Optimistic or pessimistic — the two decisions and their costs
@Version (optimistic)SELECT ... FOR UPDATE (pessimistic)
MechanismVersion column in UPDATE ... WHERE id = ? AND version = ?; 0 rows affected throws ObjectOptimisticLockingFailureException @Lock(PESSIMISTIC_WRITE); the second transaction blocks
CostOne extra column, a bounded jittered retry loop, and a policy for an exhausted budget A wait rather than a fast failure; lock-wait timeouts; deadlocks as a normal occurrence; the lock is held for the whole transaction
Use whenDefault. Single-entity writes, no waiting, cheap to retry High conflict rate, a multi-row or multi-table invariant, or genuine "check this precondition still holds" semantics
 
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;
    @Version private Long version;   // emitted in every UPDATE's WHERE clause
}

// Hibernate emits:
// UPDATE account SET balance = ?, version = ? WHERE id = ? AND version = ?;
// 0 rows affected -> ObjectOptimisticLockingFailureException, caller retries
Interview trap — "SERIALIZABLE prevents every concurrency problem"

It prevents the three anomalies, which is not the same as preventing the corruption that actually happens. Two corrections a senior answer makes: under SERIALIZABLE on PostgreSQL, concurrent transactions do not queue — they abort with ERROR: could not serialize access due to concurrent update (SQLState 40001), so any code running at SERIALIZABLE without a retry loop is a latent outage; on MySQL/InnoDB the second transaction waits on a next-key lock and its write then happens to be correct — a side effect of locking, not of the level being safer. And the lost update is not on the anomaly list at all.

Trade-off — READ COMMITTED + @Version vs SERIALIZABLE + retry

The first is fast, waits for nothing, and turns a lost update into a 40001-shaped application exception you retry — which is the shape every high-traffic system converges on, because retrying a cheap operation beats waiting for a lock. The second is correct without any application code, at the cost of aborted transactions you still have to retry and throughput you lose. Flips on: when the conflict rate is high enough that most optimistic attempts fail — at that point you are doing N failed attempts where one wait would have done. And the general position: isolation is a per-operation decision made on the method that needs it; a global setting is a way of not having to make that decision, paid on every read-only path.

Deadlocks are the inevitable price of pessimistic locking, and the database detects them itself — InnoDB and PostgreSQL abort one side immediately rather than waiting. So the practical response is not prevention but a bounded, jittered retry. Prevention, in order of effectiveness: keep transactions short; sort the identifiers before locking a set of rows, which makes the lock graph a total order and removes the cycle structurally; keep one statement per lock; and use one consistent lock order across code paths.

05

Declarative vs programmatic

TransactionTemplate is not a different mechanism. It calls the same three PlatformTransactionManager methods with the boundary expressed in a lambda — which means every annotation limitation is a TransactionInterceptor limitation, and every template capability is something the annotation simply cannot express.

What the template buys, and when it is the right tool
Capability@TransactionalTransactionTemplate
Conditional boundaryAwkward — needs a no-op wrapper or a self-invocation hackNatural — the if stays outside execute
A transaction per loop iterationImpossible without a method call per iterationNatural — tx.execute inside the loop
Vary propagation or isolation per call siteFixed at compile timeA fresh DefaultTransactionDefinition per call
The TransactionStatus in handOnly via the programmatic APIYes — status.setRollbackOnly() from a side path
Applies to code you do not ownNo — you cannot add an annotationYes — a TransactionInterceptor with your own pointcut
Trade-off — declarative by default, template on purpose

Declarative is readable, greppable, impossible to accidentally wrap, and what a reviewer expects — it should be what 90% of a codebase looks like. Programmatic buys conditional boundaries, per-iteration transactions, code you do not own, and the status object. Flips on: the moment the boundary depends on a runtime value, loops, or needs to influence the transaction's outcome rather than just its extent. The anti-pattern to name is migrating a whole service to templates for style reasons: it loses greppability and gets reverted within a release. One concrete trap — TransactionTemplate is not safe for concurrent reconfiguration, so a shared template whose propagation is mutated per call will have one thread run with another's propagation, which for REQUIRES_NEW means an unexpected second connection and a second commit.

@Transactional
public void placeOrder(OrderRequest req) {
    Order order = repo.save(toOrder(req));

    TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override public void afterCommit() {
                    notificationGateway.send(order.id());   // already durable
                }
                @Override public void afterCompletion(int status) {
                    if (status == STATUS_ROLLED_BACK) dlq.publish(order.id());
                }
            });
}
The four lifecycle callbacks, and what each cannot do
CallbackFiresUse forTrap
beforeCommit(readOnly)Just before the commit Flushing a pending change that must be inside the transaction Throwing here rolls the transaction back
afterCommit()After the commit succeeded Notify, invalidate a cache, "tell the cache" Throwing here does NOT roll back. The data is already durable, so the failure is "written but not published"
afterCompletion(status)After commit or rollback Cleanup on both outcomes, DLQ, metrics, timing You do not know which happened unless you read status; STATUS_UNKNOWN means a heuristic outcome or a connection that died mid-commit
beforeCompletion()Before commit or rollback Releasing a resource that must not be held during commit—
Must remember — afterCommit cannot undo anything

An exception thrown in afterCommit does not roll back: the transaction is over. And it compounds — if the listener is also @Async, the exception is swallowed by the default AsyncUncaughtExceptionHandler and is not even logged. afterCommit is right for "tell the cache" and wrong for "charge the card". If the side effect is one the business depends on, the answer is not a better hook: it is a transactional outbox row written inside the transaction, relayed with a retry and a deduplication key. That is the difference between an event and a promise. The same applies to registerSynchronization — it throws IllegalStateException when no transaction is active, which is the better of the two failure modes, because a listener that quietly does nothing is worse.

06

Failure modes

Every entry in this chapter shares one property: none of them throws. Self-invocation, a readOnly flush discard, a non-transactional caller, a test that never commits, and a read-modify-write race all produce a green build and corrupt data.

Symptom, mechanism, diagnostic
SymptomMechanismThe diagnostic that settles it
Writes occasionally half-applied; a transactional method "doesn't roll back" Self-invocation — this.inner() never reaches the proxy Log System.identityHashCode(DataSourceUtils.getConnection(ds)) across two calls; one identity means one transaction
A method throws, an alert fires, the data is still written A checked exception, so the default rule commits Grep for throws on methods carrying @Transactional — two minutes, finds most of a team's latent half-commits
An update silently did nothing on one database, wrote fine on another readOnly = true → FlushMode.MANUAL discards; or a setReadOnly hint the driver ignores Assert isCurrentTransactionReadOnly() in a test; then assert the method does not call a mutator
500s on roughly half the write endpoints, database healthy A second DataSource made Boot's auto-configuration back off; two managers, so every unnamed @Transactional is ambiguous NoUniqueBeanDefinitionException at the first call, not at startup; a startup assertion that counts the manager beans catches it
Data written outside any transaction; a batch that stops partway with no record of where The caller is not transactional, so each inner call starts and commits its own Put the boundary on the caller; a loop inside no boundary is 1,000 commits

Rank the causes of "Connection is not available, request timed out after 30000ms"
  1. Connection demand exceeds pool size because of REQUIRES_NEW or deep nesting. Every request holds two. Check the request path for nesting first — by far the most common and least obvious cause, because the code looks ordinary.
  2. A leaked connection from code doing dataSource.getConnection() outside Spring. Outside Spring nothing returns it.
  3. Long transactions — effective capacity is pool size / average transaction duration × request rate. A 30-second transaction in a 10-connection pool is 0.33 transactions per second.
  4. The pool really is too small — the answer people jump to, and the one to check last, because raising it to paper over a nesting bug moves the failure from the pool to the database, where it is harder to diagnose and affects other tenants of the same instance.
What @Transactional on a test class hides
What the test doesWhat it hides
Sees uncommitted data through the same persistence context A write no other connection or request would ever see
Never observes a real COMMIT A deferred constraint violation, a commit() that throws, an optimistic-lock failure that only surfaces when the UPDATE reaches the database
Rolls back unconditionally A method whose rollback behaviour is wrong — including the checked-exception rule
Holds one connection for the whole test Nothing — but that cost is invisible locally and is exactly what starves a small pool in CI
Must remember — the one line that turns a silent bug red

Assert TransactionSynchronizationManager.isActualTransactionActive() at the top of every write-path test. It converts the most common class of silent transaction bug from "discovered in production" to "red in CI", for one line. Its known limit is the point to state alongside it: the boolean cannot distinguish no transaction by design (SUPPORTS, NEVER, NOT_SUPPORTED) from no transaction by accident (self-invocation, new, a non-bean class), so it has to be paired with knowing which propagation the method uses. Its complement is a small real-commit test slice with no rollback transaction, against a real database — a rollback-wrapped test cannot detect a readOnly flush discard, a two-manager partial commit, or a replication-lag bug.

The diagnostic principle behind the whole chapter: a transaction is a thread-bound, connection-bound fact, so every question about transactions is a question about which connection this thread holds and for how long. Log the connection identity, the thread name, the label, and the elapsed time in an afterCompletion hook, and most of these failures become visible before they become incidents.

07

Beyond one database

ACID gives you four guarantees about one resource under one coordinator. Distributed needs all four across several resources and several processes, and the reason it is hard is not the algorithms — it is that a participant that has prepared cannot abort without risking an inconsistent commit, which is why 2PC blocks and why XA costs a coordinator, a replicated decision log, and a human in the recovery path.

What 2PC/XA actually buys and what it costs
2PC / XAOutboxSaga
GuaranteesAll-or-nothing across resources, with no compensating logic to write The state change and the intent to publish are one atomic commit Eventual, not immediate, consistency across a multi-step flow
Failure mode it introducesIn-doubt. Prepared resources block holding locks; if the coordinator's log is lost, a human resolves a heuristic outcome Relay lag of a poll interval, and a row that is never published if the relay dies Compensations are new business logic that can fail, cost money, and be seen by users
Operational costA stateful coordinator — a single point of failure — plus XA-capable pools everywhere One table to prune, one relay to monitor, alert on published_at IS NULL A new stateful service with its own durability and retry story
Use whenThe data genuinely must be atomic and latency is acceptable — a low-throughput, high-value ledger posting A single service's state change must notify the world The flow itself spans services and can fail halfway with meaningful intermediate state
Must remember — compensation is not a rollback

A rollback restores the previous state and is guaranteed by the storage engine. A compensating action is new business logic that happens to move the system to a similar state: it can fail, it can be rate-limited by a third party, it is visible to users, and it costs money. Charging a card and refunding it is not equivalent to not charging — the customer sees both entries, the provider takes a fee, and fraud systems can flag the pair. So the Saga design question is not "how do I undo this" but "what is the compensating business action, what happens if it fails, and is it idempotent". Two properties the word "Saga" hides: there is no isolation — between steps a UI can show an order with no stock, so every Saga has to answer "what does the user see mid-flight"; and the compensation is only as good as the last step, so a Saga ending in a sent email has a hole in it.

Trade-off — and the question nobody asks in time

2PC is correct, which is the whole argument for it: no compensating logic, no in-doubt states your application must reason about, and the data model stays a single database. Flips on: use it when the data genuinely must be atomic and the latency budget tolerates it — a ledger posting between institutions, not a checkout path. The real argument against is asymmetry: adopting XA is easy, and removing it later means writing compensating logic for code that was never designed to have any. Relatedly, exactly-once is not achievable across a broker and a consumer that cannot join the same transaction; what you can achieve is effectively-once processing, which means at-least-once plus idempotency. So the useful question is not "how do we get exactly once" but "what is our dedup key, and is it committed atomically with the effect" — a claim the guard and the effect share a transaction, or a message that has its own RECEIVED → PROCESSING → DONE state machine.

Beneath all of it is idempotency, because every one of these mechanisms can deliver twice. The primitive is a client-generated UUID per logical operation, sent in a header and stored under a UNIQUE constraint in the same transaction as the effect, with the result stored rather than a "seen" flag, and a retention window longer than the client's retry window. Choosing 2PC to satisfy request-level idempotency is a category error — a client that timed out was never in the transaction.

08

Design decisions

These are the questions that separate a senior answer from a staff one: not what the API does, but where the boundary belongs, what it costs, and how expensive it is to undo.

Positions worth holding, and the evidence behind each
QuestionThe positionBecause
Where do transaction boundaries live? One per use case, at the service layer, and nowhere else Start from the use case, not the layer: if this write succeeded and that one failed, does the system have a coherent state? Annotating repositories "for safety" gives every repository call its own transaction and turns a three-repository use case into three commits
One transaction manager per data source — enforce or document? Enforce first, document as the fallback A thread has one bound resource per manager type, so two active transactions on one thread means the first is suspended or lost. That is a mechanism, so it earns a startup assertion counting the manager beans, not a wiki page
Is class-level @Transactional a reasonable default? Defensible as a default, a trap as a habit It silently applies REQUIRED to methods that should be read-only, so the readOnly optimisation is never available; and any method-level annotation replaces it wholesale, resetting propagation and timeout
Adopt @Version across a codebase? On the entities where the invariant is real, with a written retry owner A blanket @Version with no retry policy converts silent corruption into visible 500s — technically an improvement, operationally a fire. Also check the column is non-null and defaulted, or an existing table defeats the mechanism silently
Size the pool to fix a nesting bug? No — fix the holding, then size the pool for what remains Pool size is a throughput knob. Raising it to hide a nesting bug moves the failure to the database's own connection limit, where it affects other tenants of the same instance
How do you raise the bar in the first two weeks? Instrument, then defend mechanically, then refactor Set label, time transactions in afterCompletion, alert on idle in transaction — you want to know which existing problems are real before reorganising. Then the assertions, the real-commit test slice, and an ArchUnit rule confining @Transactional to services. It is an observability project before it is a refactoring project
Must remember — the distributed question is a product question

It is almost never "which algorithm should we use." It is "which inconsistency can this business tolerate, and for how long", and that is a product decision engineering executes rather than makes. Run it in a design review by putting the specific window on the table with a number on it — "an order can exist for up to five seconds with no inventory reserved, and the UI shows it as processing" — and get an explicit answer. If the answer is "zero, ever," the options are XA or a single database boundary, and you should say what each costs. If it is "a few seconds," you need an outbox and a consumer. If it is "a few minutes and a human reconciles," you need a saga and a repair UI. Do not let the architecture be decided by whichever engineer is most comfortable with the mechanism.

The same discipline answers the audit question, which comes up in nearly every transaction design review: before implementing "write an audit row that survives a rollback," establish what the row is asserting — that an attempt happened, or that an outcome occurred. An independent commit for an outcome creates the worse problem, because the audit then records a success the business data contradicts. For an outcome, write it in the same transaction; for an attempt, write it before the work. A REQUIRES_NEW audit write with no reconciliation produces records that lie, and it costs a second connection on every request that touches the path.
