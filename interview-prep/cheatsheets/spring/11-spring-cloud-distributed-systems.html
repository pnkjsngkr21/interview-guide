Spring — The Spring Complete Deep-Dive

Volume 11 — Spring Cloud & Distributed Systems

Every call leaves the process, and the machinery that made the in-process world safe — a transaction, a thread pool, a lock — stops working at the network boundary. What replaces each one, and what it costs.

If you only remember five things

  1. minimumNumberOfCalls gates the failure threshold. Below it the rate is unmeasured, not low — so a window smaller than the minimum means the breaker never opens, silently, and an entire resilience mechanism is doing nothing.
  2. The breaker goes outermost, the retry inside. Reversed, each retry is a separate call the breaker sees, so three attempts count as three failures for one user request and the breaker opens three times too fast.
  3. The registry health check must be liveness, not composite. Point it at /actuator/health and a slow database deregisters an otherwise-healthy service, turning a partial dependency failure into a zero-traffic outage.
  4. A compensation is a new forward business action, not a rollback. You issue a refund; you do not un-charge the card. It can itself fail, it is not instantaneous, and it needs its own retry and its own idempotency key.
  5. Resilience4j's rate limiter is per-instance and in-memory. The configured number is not the number the fleet enforces — 10 rps on five instances is 50 rps, and 500 rps the day you scale to fifty.

Service discovery

Where the load-balancing logic lives decides where the failure lives

The registry is a source of truth the client pulls from, not a proxy it calls through. On Kubernetes the "server side" is already the kube-proxy / service-mesh data plane, which is why client-side libraries went quiet there — you are handed the server-side behaviour for free.

public class StaleRegistryCacheFilter implements GlobalFilter {

    @Override
    public Mono<Void> filter(ServerWebExchange ex, GatewayFilterChain chain) {
        // 1. on failure, serve the LAST GOOD snapshot from local cache
        // 2. once the snapshot ages past the window (30-60s),
        //    drop instances entirely
        // 3. so the client fails fast rather than routing to a dead host
        return chain.filter(ex);
    }
}
Interview trap

"Spring Cloud uses Eureka, which is client-side with Spring Cloud LoadBalancer" is half right, and the wrong half is the interesting one. Ribbon is removed — IClient, ServerList and @RibbonClient are 2018. The current namespace is spring.cloud.loadbalancer.*; naming a service for injection is @Bean @LoadBalanced plus a @Qualifier, not a @RibbonClient(name = ...).

Must remember

A discovery health check must be liveness (/actuator/health/liveness), never the composite /actuator/health. The composite includes the database, so a slow database marks every instance down, the registry removes them all from rotation, and a service that could still have served most of its traffic receives none. Full readiness gating is a deliberate policy with a real cost, not a default.

Trade-off — what a registry partition does

Eureka is AP: both halves of a partition keep serving with incomplete views, each routing to instances the other half believes are dead — a discovery partition becomes a mass misrouting event. Zookeeper is CP: the minority side stops serving, trading availability for one truth, and failing loudly. Consul is configurable per service. Flips on: whether you would rather lose availability visibly or lose it silently — because only one of the two fails loudly, and a team that does not know which model it runs cannot answer "what happens on a partition" during one.

Scaling reality check — the cache that sizes itself wrong

spring.cloud.loadbalancer.cache.capacity defaults to 256 and is per entry. Past a few hundred services, entries are evicted and re-fetched — the symptom is periodic latency spikes on calls to infrequently-used services, which reads as "the registry is slow" and is actually a cache-sizing problem.

Its sibling, retry.retry-next-service, defaults to false and is worth justifying: if a retry moves to a different instance, a genuine application-level failure — a validation error counted as a 5xx by a sloppy handler — gets retried against every instance, multiplying load exactly when you can least serve it.

Production scenario — the 09:14 checkout outage

Problem: the registry became unreachable from one availability zone; within minutes, checkout across three services returned 503 with NoInstanceAvailable on normal CPU. Investigation: the client cache filter was configured with a 0-second staleness window — a legitimate "fail fast" setting — so the instant the fetch failed, the local snapshot was discarded. Root cause: a discovery outage converted into an application outage by a setting that is correct in a different failure model. Solution: a bounded 30–60s window, plus alerting on eureka.client.refresh failures separately from 5xx rates so the two problems are distinguishable. Prevention: the window is now a per-environment platform setting with the reasoning written next to it.

02

The gateway

A route is an id, a uri, a list of predicates and a list of filters. It matches if every predicate matches. The pairing that everyone gets wrong once is Path=/api/orders/** with StripPrefix=2, which turns /api/orders/123 into /123 at the service — a missing StripPrefix sends the public path straight through and nothing matches.

Predicates, and the one that earns its keep
PredicateMatches onTypical use
PathURI patternThe workhorse: /api/orders/**
MethodHTTP verbSplitting reads from writes
HeaderPresence or regexCanary on X-Canary, tenant selection
CookieCookie valueSession affinity to a legacy tier
QueryQuery parameterVersioning, feature selection
WeightGroup name + integerBlue/green and percentage canaries — weights in a group sum to 100
RemoteAddrClient IPAllowlists
Interview trap — the canary that is not sticky

Weight splits traffic randomly per request, not per user, so a user in the 5% canary cohort sees the canary on some requests and stable on others. That is correct for a statistical comparison and wrong for a user trying to report a bug about "the new version". Sticky canaries need a deterministic key — the Cookie predicate on a session id, or a header set by whatever already identifies the user — chosen before the canary, not after the first confused report.

Interview trap — CORS, where Swagger lies to you

Three failures in order of frequency: no OPTIONS in allowedMethods, so the preflight fails and the browser never sends the real request; a global CorsGatewayFilter on routes that are not browser-facing, advertising permissive headers on an internal route; and allowedOrigins: "*" with allowCredentials: true, which the CORS spec forbids — allowedOriginPatterns exists so you can say "any subdomain" without the wildcard. Swagger UI is same-origin and issues no preflight, so a team that has only ever tested through the API explorer has never tested CORS. The symptom — a network error with no server-side log line for the real endpoint — belongs in a runbook.

Scaling reality check — the token bucket that lies

RequestRateLimiter is a token bucket: replenishRate 100/s, burstCapacity 200, requestedTokens 1. Two decisions decide everything. Where the bucket lives decides whether the limit is global or per-instance — an in-memory limiter on a 20-instance fleet enforces 20× what you configured, which is why the Redis implementation is the default recommendation. burstCapacity is the number that causes the incident: 200/100 lets 200 requests through instantaneously on an empty bucket, which is precisely the shape of a retry storm. If the intent is to smooth traffic, keep burst close to the refill rate.

Must remember — the healthy gateway is small

Routing, auth termination, rate limiting, observability. Nothing else. A gateway is one component every request in the product passes through, so its availability is the product's availability, its p99 is the product's p99 and its connection pool is the product's connection pool. Business logic placed there is logic that cannot be deployed independently, cannot be tested against its domain, and takes down every other team's traffic when it breaks — it is also the most natural place in the architecture to accidentally rebuild the monolith you split up.

Trade-off — gateway rate limiting, for what?

Right for a global or per-tenant limit on inbound traffic: the bucket is global by construction and there is one place to change it. Wrong for protecting a downstream dependency — a gateway limiter limits requests to the gateway, not the load on the thing you are shielding. Flips on: whether the thing being protected is the edge or a service behind it; for a dependency, the right tools are a bulkhead and a client-side limiter with an external bucket, colocated with the client that makes the call.

Circuit breakers

The configuration, and how each setting fails silently
SettingRuleWhen it bites
sliding-window-typeCOUNT_BASED or TIME_BASED Count-based reacts to volume, so it is blind during a genuine traffic trough; time-based reacts to wall-clock, so it reacts to a low rate sooner
sliding-window-sizeHow many recent calls the decision rests on Smaller than the minimum → the threshold can never be met and the breaker is permanently closed while looking configured
minimum-number-of-callsGate before the rate is evaluated at all Below it there is no measurement, not a low rate. How many calls, and how long at your p50 rate?
failure-rate-thresholdBelongs at 75–90%, not 50 50 opens on a degraded dependency and turns a partial failure into a total one
wait-duration-in-open-stateLong enough for a recovering dependency to prove itself Too short and you re-probe into the same outage, repeatedly
permitted-number-of-calls-in-half-open-stateThe probe budget Too large and the probe itself is a load spike on something barely alive
slow-call-rate-threshold + slow-call-duration-threshold Lets the breaker act on latency, not only on errors This is the answer to a slow dependency, where no error exists yet to trip an error threshold
Scaling reality check — the breaker that amplifies the outage

A dependency is degrading: 30% of requests return 500 and the other 70% take two seconds. That is degraded, not down. Without a breaker the path succeeds 70% of the time and recovers.

With a breaker tuned at 50% that opens after 20 calls, every call then fails instantly — including the 70% that would have succeeded. Path success goes from 70% to 0% in seconds. And because the failures are fast, the breakers in the callers trip too: one slow dependency becomes a fleet-wide error whose traces show every service failing in under 5ms. Tune for 75–90% with a meaningful minimum, and treat slowness with timeouts and slowCallDurationThreshold.

Must remember — a fallback can hide the outage

A fallbackMethod that returns a success-shaped response removes the evidence from every dashboard you have: the breaker is open, every call is served from cache, the error rate is 0%, and the business is quietly returning stale answers to users while nothing pages anyone. Invisible outages last longer because the pressure to fix them never arrives. The degradation is a product decision and the visibility is an engineering one, and they have to be made together — a first-class fallback.invoked counter with an alert on its rate.

04

Retry & isolation

// RIGHT ORDER — breaker outermost. It sees ONE logical call,
// retries happen inside it, and the amplification is contained.
@CircuitBreaker(name = "payment", fallbackMethod = "cachedCard")
@Retry(name = "payment")
public Receipt charge(Card card, long amount) { ... }

// WRONG ORDER — 3 attempts = 3 failures per user request.
@Retry(name = "payment")
@CircuitBreaker(name = "payment", fallbackMethod = "cachedCard")
public Receipt charge(Card card, long amount) { ... }
Scaling reality check — how a retry storm is born

A retry multiplies load on a dependency that is already struggling. Three retries at three layers of a call chain means one user request generates 27 downstream calls — and the multiplication lands on the failing component, which is the one with no spare capacity. Retries without backoff, without jitter and without a breaker turn a 2× slowdown into a 27× load increase on exactly the wrong dependency.

Backoff without jitter is a stampede, not a fix: every client that failed at t=0 retries at t=200ms and arrives together. The fix is a central retry budget of 10–20% of total traffic that the client sheds under load, plus exponential backoff with jitter, plus a breaker outside the retry.

Interview trap — what you are allowed to retry

The ignore-exceptions list is the part usually missing. Retrying a business rejection — a declined card, a validation failure, a 404 — multiplies load for a response that will never change. Retries belong to transport failures, and the exception taxonomy has to be written down or the framework will retry everything that is an Exception.

Composition rules, outermost first
CombinationRuleWhy
@Bulkhead outermostCorrect Concurrency is capped before any work is admitted
@CircuitBreaker outside @RetryCorrect One logical call; amplification contained
@TimeLimiter outside @CircuitBreakerCorrect The deadline covers the whole protected call, retries included
@Retry outside @CircuitBreakerWrong Amplification counted as failure; the breaker opens 3× too fast
@RateLimiter + @RetryFine, with care The limiter is per-instance, and the retry still multiplies downstream load

The rule that generalises: the breaker goes outermost, because its job is to protect the dependency from everything happening inside it. Anything that makes more than one call — a retry, a loop over shards, a flatMap fan-out — belongs inside it.

Bulkhead: thread pool versus semaphore — not a stylistic choice
Thread-pool isolationSemaphore isolation
Limit is onThreads, a bounded ExecutorServicePermits, a Semaphore
A hung callBlocks a dedicated thread; other calls unaffectedHolds a permit and blocks a shared caller thread
ConsequenceContains the damage — the other bulkhead's pool is separatePermits are held until timeout, so the bulkhead fills and rejects — every rejected call already paid a call's worth of delay
Thread costOne thread per concurrent call — 1MB stack each at Tomcat defaultsNone
Use whenThe call can genuinely hang and you need hard isolationCalls are short and latency-bound; it is really a concurrency cap
Trade-off — isolation, and what it costs

Thread-pool isolation contains a hung dependency and semaphore isolation does not: the pool's threads are dedicated to that dependency, so a hang blocks only those. The cost is a thread per concurrent call — 50 concurrent calls is ~50MB of stack — plus a hard ceiling on throughput, so maxThreadPoolSize set too low converts a throughput problem into self-inflicted queueing and you have built your own outage. Flips on: whether the dependency can hang rather than merely be slow. Either way, neither type is safe without a timeout — a bulkhead without one is a queue with no drain.

Must remember — a time limiter is not a timeout

@TimeLimiter does not speed anything up. It imposes a deadline on the caller: the caller's future completes exceptionally while the underlying work keeps running. A @TimeLimiter with no bulkhead means N concurrent callers all start work and then N callers time out while the work continues — full production load and a failure report, the worst of both worlds. The three mechanisms limit different things: the time limiter how long the caller waits, the bulkhead how many run concurrently, the client timeout how long the socket waits.

05

Distributed configuration

A config server externalises configuration into a git repository, a Vault or a JDBC backend. The thing to understand is not the syntax but the mechanism: bootstrap.yml requires a separate bootstrap application context whose only job is fetching config, so resolution happens before the main context exists — including before @ConfigurationProperties validation runs — and it needs spring-cloud-starter-bootstrap. spring.config.import brings the remote config in as a ConfigData source in the normal ordered resolution process, which is why it composes with profiles and the environment. Same concept, modern mechanism; the legacy path is not the one to reach for in a new project.

// A value that /actuator/refresh can re-read at runtime.
@Component
@RefreshScope
public class PaymentLimits {

    @Value("${payment.timeout-ms:2000}")
    private long timeoutMs;   // refresh re-binds this without a restart
}
Must remember — config is a deploy that skips the build

It changes behaviour without changing code, and it changes behaviour in every instance that re-reads it — a different blast radius from a code deploy. Three consequences. Rolling compatibility: old and new code are both live during a rollout, so remove or rename nothing that new code expects — properties are additive and get deprecated with a removal date, never renamed in the same change. Testing: a YAML file gets no review that can tell you whether a timeout is sane, so run the candidate config through the same integration suite as a candidate build. Rollback: git revert plus a refresh, which only exists if the values were never hand-edited — see the trap below.

Trade-off — is a config server a SPOF you do not need?

Right when you want configuration versioned, reviewed and rolled back with the same machinery as code. Wrong for the reason most teams adopt one: "so we can change values without a deploy" — the values still need a deploy-equivalent event, and the config server only relocates it. Flips on: whether config changes are currently going through change control. If they are not, the problem is the process and the server will only give you an unreviewed path to production values.

Scaling reality check — fail-fast is a startup decision

spring.cloud.config.fail-fast: true makes the application refuse to start when the config server is unreachable. That is correct for a stateless service that would otherwise start with wrong values, and genuinely dangerous for one that could start from a last-known-good cache. Whichever you choose, it is a decision about whether "no config" means "don't serve" or "serve stale" — and unlike most resilience settings, this one is made once, at startup, and appears in no per-request metric.

Interview trap — the config system that cannot roll back

Editing production values by hand in a Consul KV store or a cloud console removes the rollback story and the audit trail in one move. The first incident is always "who changed this and how do we undo it?" Config belongs in git, next to the application, reviewed and reverted like code. And note what Config Server's encryption actually buys: it protects the values at rest in the repository — not in transit, and not once they are in the running application's memory. A secret with a real rotation story belongs in a secret manager a property references, not encrypted into a config repo.

06

Saga & compensation

A saga replaces the distributed transaction with a sequence of local transactions and compensating actions. It is the honest answer once each service owns its tables, because XA/2PC is not a real alternative at that point: it requires participants to share a transaction manager and hold resources locked for the duration — the coupling the boundary was created to remove. A saga buys availability by giving up isolation, and everything below exists to manage what that costs.

Compensation is not the inverse of the forward action
Forward actionCompensating actionWhat it costs
INSERT an order rowRollback — the row is goneNothing; this is the easy case
UPDATE stock = stock - 1Rollback — an arithmetic factNothing, as long as no other reader observed the intermediate value
Send a confirmation emailNo rollback exists — send a correctionA correction may be worse than silence for a customer who read the first one
Charge a card £49.99No rollback — issue a refundA separate transaction, days to appear, and it can time out having succeeded
Invoice the customerNo rollback — issue a credit noteAccounting period may have closed
Send a dispatchNo rollback — cancel itIt may already be in a van
Notify a partner systemNo rollback — send a correction eventThe partner may have already acted on the first
Must remember

Compensation is a forward action with its own semantics, and it is allowed to fail. Three consequences teams plan for only after their first incident: it can fail, so it needs its own retry and its own idempotency — a timed-out refund may or may not have gone through, and retrying without a key can double-refund; it is not instantaneous, so the ledger stays inconsistent for a window and reconciliation that assumes atomic closure alerts falsely; and it is a differently-shaped, rarely-exercised code path running when things are already broken — a compensation that has never been exercised is an assumption, not a mechanism.

Choreography versus orchestration
ChoreographyOrchestration
CoordinationNone — eventsA saga coordinator
Where the flow livesThe event graph, implicitlyOne state machine, explicitly
DebuggingYou reconstruct it from event typesYou read one class
CouplingGrows per event; consumers know each other's eventsOnly the coordinator knows the participants
New participantPublish/subscribe, no coordinator changeThe coordinator must change
Availability costNothing extra to keep aliveThe coordinator is now a component that must itself be available
Failure handlingEvery consumer implements its own compensationCentralised and consistent
Trade-off — choreography or orchestration

With three participants and a straight line, choreography is genuinely better: no coordinator to deploy, none to keep available, and each service owns its own reaction. Its cost is not infrastructure, it is legibility — the flow lives in the event graph, is invisible in any single component, and coupling grows one event at a time until services react to each other's internal events. Flips on: branching or a failure path. Once step 2's outcome changes step 3, or there is conditional compensation, orchestration wins — and the cost you accept is that the coordinator needs durable state, a lease or leader election so two do not drive the same saga, and an operator-facing view of in-flight sagas.

Interview trap — two orchestrators, one saga

Deploy the orchestrator as two replicas without leader election and both can observe and drive the same in-flight saga: the compensation is issued twice, the forward step re-issued after it completed, and the outcome depends entirely on whether the steps are idempotent — which they usually are not. Two refunds is the visible damage, and it is the same idempotency discipline that outbox consumers require.

07

Outbox, idempotency, reads

@Transactional
public Order place(PlaceOrder cmd) {
    Order order = orders.save(new Order(cmd));
    // Same transaction, same database — this is what makes it safe.
    outbox.save(OutboxMessage.of("ORDER_PLACED", order.id(), payload));
    return order;
}

@Transactional
public void on(OrderPlacedEvent event) {
    if (inbox.alreadyProcessed(event.messageId())) {
        return;                        // duplicate is a no-op, not an error
    }
    inventory.reserve(event.orderId(), event.lines());
    inbox.record(event.messageId());   // same tx: a crash rolls back the record too
}
Must remember

The inbox record must be written in the same local transaction as the business change. Record-then-work loses the work on a crash between them; work-then-record repeats it. And the side effect needs its own idempotency key — a real carrier will not dedup for you — plus a reconciliation path, because the system authoritative about shipments is not the one that consumed the message.

Interview trap — CDC is not free

Change Data Capture reads the database's own log, so the producing service needs no outbox table and no relay — genuinely the pragmatic answer for a legacy service that cannot be modified. The costs: schema changes flow through the same stream, so a DROP COLUMN becomes an event consumers cannot deserialise, and a schema change becomes a genuinely distributed change needing expand/contract discipline. Consumers now depend on the physical table structure rather than a published contract, so a well-meant column rename breaks consumers nobody knew existed.

Read-after-write, and the cost of each fix
FixCatchesWhat it costs
Session stickiness to the primary for a short windowThe immediate read-after-write casePrimary capacity, including for users not reading anything
Bounded lag check (now() - replication_timestamp < threshold)Also user A wrote, user B readNeeds a lag signal you can trust — a heartbeat table on the primary
Explicit read-your-own-writesExactly the caller's own writesPrecise, and it pushes the guarantee onto every read call site
Route a hot aggregate to the primary permanentlyOne aggregate, foreverThe wrong default — it is choosing which users pay
Scaling reality check — the staleness threshold that fails in the incident

Replication lag is not a constant. A replica behind by 800ms under normal load can be behind by 30 seconds during a failover, a long-running analytical query that pins the replication thread, or a storage event on the replica. A threshold set to 5 seconds holds in the steady state and fails in the incident — and the incident is exactly when read-after-write failures cluster. This is the most common "how did this happen" report in any system with read replicas.

Giving each service its own database is a data-migration project, not a configuration change: cross-service joins become denormalisation, referential integrity moves into code or nowhere, and the business operation spanning two of them needs the saga above. The boundaries and the decomposition that decide who owns which table belong to the Microservices volumes; the only part owned here is that once a call leaves the process, none of the in-process guarantees come with it.

CQRS and event sourcing are pattern-matched decisions, not performance switches. CQRS pays when the read model is genuinely complex or you need several projections; adopting it to fix one slow screen inherits a projection pipeline. Event sourcing pays where a regulatory audit trail is a requirement or a temporal query is the product — its real costs are event schema evolution (an event written two years ago must stay readable, so "just add a nullable field" is unavailable) and having no current-state query without a projection you build anyway.

08

Tracing & observability

Metrics cannot answer "why is this one request slow across six services", because they are pre-aggregated across every dimension you chose not to label. A trace is a tree of spans sharing a trace id, each recording its start, duration and parent — exactly the shape of the question. The context travels in a header: traceparent: version-trace-id(16 bytes)-parent-span-id(8 bytes)-flags, with the low bit of the flags byte carrying the sampling decision so it propagates without a round trip.

Must remember — the header that is easy to forget

Trace context must travel in message headers, and a consumer that does not read it starts a new trace. The visual result is a trace that stops dead at the broker — the async half of your system is invisible, and this is worse than having no traces, because a coherent-looking trace that simply ends reads as an explanation. The test is cheap: publish an event that triggers a slow downstream call and check whether the trace continues through the consumer. A hand-rolled propagator that handles only one of B3's two header forms breaks traces at exactly the boundary you forgot.

Must remember — an Observation is not automatically a span

Micrometer's Observation is a vendor-neutral description of what happened; it becomes a metric always and a trace span only when a tracer bridge is configured — micrometer-tracing-bridge-otel (or -bridge-brave) plus an OpenTelemetry / Tracer bean. Without it you get excellent metrics and no traces at all, with no error and no warning. The symptom — a full ObservationRegistry and an empty trace backend — is baffling unless you know to look for the missing dependency. Relatedly, the propagator must be uniform across the estate: three services on W3C and four on B3 breaks traces intermittently at the boundaries between them.

Head versus tail sampling
Head samplingTail sampling
Decision pointAt the root span, before any workAfter the trace completes
CostCheap, no bufferingA collector holding spans in memory, a memory budget, export latency, and a policy somebody owns
Can expressProbability only — keep if rand() < 0.1Content: keep if any span errored, keep if total > 1s
Net effect1% of traffic, including 1% of your errors100% of errors and all slow requests
Scaling reality check — 100% sampling is a bill, not a setting

Head sampling at 100% does not scale: 1,000 rps × 16 spans × 60s retained is roughly a million spans a minute — an ingest and storage cost that arrives on a bill before anyone decided to pay it. Fine briefly, as a way of discovering what you did not instrument; wrong as a steady state.

Must remember — cardinality is the metrics failure mode

Cardinality is bounded by the number of distinct values that ever occur, not the number occurring at once. A backend holds one time series per unique tag combination and retains rather than deletes, so a userId tag is a permanent series per user forever — a memory leak in the backend you cannot see from the service's own dashboards. The practical limit is a few hundred label values per metric. High-cardinality identifiers belong in span attributes and logs, where they are searchable within one trace, and never in metric tags.

Interview trap — baggage crosses trust boundaries

Baggage is propagated to every service the request touches and, if the instrumented library follows the spec, on every outbound request to third parties. So PII in baggage is a security problem, not a tidiness one: an email address is copied into every log line, every trace store and every downstream header, multiplying one disclosure into dozens of systems with different retention and access controls. High-cardinality values do not belong there either — every distinct value becomes a distinct trace and the header grows with your traffic. And because baggage crosses trust boundaries, a public-facing service must allow-list or strip inbound baggage, or an attacker populates your telemetry.

Worth being able to say what a trace does not tell you: why a decision was made (a 180ms span says the dependency was slow, not whether it was a lock wait or a bad plan), whether the business outcome was correct (a beautiful trace of a request that double-charged a customer), or the typical case — your sample is biased towards errors and slow requests, so percentiles computed from kept traces will not match metric percentiles and should not be compared.

09

Should you split at all?

The question that precedes every other one in this sheet. Splitting a monolith is a reversible mistake only in the code; the data migration behind it is not, which is why the decision inputs are mostly organisational rather than technical.

The five inputs that actually decide it — only the second and third are technical
SignalWhat it argues for
Fewer than 5 independent teamsMonolith. Conway's law has no work to do. Splitting buys coordination, not autonomy
"We can't ship on Fridays"Fix the release process first. This is the single most misdiagnosed symptom in the set
The candidate cannot own its tables without a cross-service join in the request pathDon't split. You are building a distributed monolith — see below
Path already has 4 hops at 20ms and a 5th is proposed for organisational reasonsNeeds a justification to the SRE, not a design doc
The boundary has churned ("orders" was a module, then a service, then three) Wait. Boundaries drawn under a moving domain are expensive to relocate
Must remember — extraction is a data migration first and a code move second

Teams that plan it the other way round underestimate by roughly an order of magnitude, because the code is the easy part. Moving the class is two days; replacing the direct call with a client is a week and turns it into a network call; adding a timeout is an hour. The data move is the project: who owns this table now (an organisational negotiation), what happens to the join in the request path, the foreign key from order_line to orders becoming a cross-service consistency problem, then backfill, dual-write, cutover, verification — and the rollback story if the cutover is wrong. Full argument in Volume 11 §1.4.

Interview trap — the modular monolith is a real answer, not a retreat

A single deployable whose code is organised into modules with enforced boundaries — Spring Modulith at compile time, ArchUnit at test time — gives you service boundaries before the runtime does. The modules are genuinely independent in reasoning, in testing and in team ownership, and they cannot be extracted later without a rewrite. A candidate who argues convincingly for not splitting is demonstrating judgement, not hedging. Spring Modulith is a real project worth naming here; the enforcement is the point, because convention does not survive a deadline.

Service-to-service security

Distinct from the user-facing security in Volume 8: this is authenticating workloads calling each other, and the interesting question is what each mechanism does not establish.

mTLS authenticates the workload and encrypts the hop — it says nothing about what the caller may do
MechanismEstablishesDoes not establish
mTLSThe caller's identity, from a client certificate issued by a CA the server trustsAuthorisation. Any workload with a valid certificate can call any endpoint. It is authentication, not access control
Token propagationThe original user's identity, carried downstream unchangedA narrower audience. A token minted for service A is routinely accepted by service B, which is how privilege leaks sideways
Token exchange (RFC 8693)A new, narrower token minted for the downstream audienceAnything, if not paired with authorisation — and it is a real complexity cost in a synchronous call path
Workload identityA short-lived credential with no long-lived secret to rotate or leakAuthorisation. Identity is the precondition for it, not a substitute
Scaling reality check — what the mesh actually buys you, and what it does not

A sidecar gives you mTLS, retries and telemetry without touching application code, and that consistency is genuinely valuable — especially for languages where retrofitting it is painful. What it does not give you is authorisation, which still has to live in the application because only the application knows what the caller is trying to do. The honest framing is that the mesh moves transport-level guarantees out of your codebase and leaves policy-level guarantees in it. Adopting a mesh to solve an authorisation problem solves nothing.

Interview trap — "we have mTLS so our services are secure"

mTLS answers who is calling, never what they may do. Every workload holding a trusted certificate can call every other, so a compromised or merely over-permissioned service reaches everything. Zero trust applied honestly means every call is authenticated and authorised, continuously — and it means assuming the network position is not a trust boundary, which is a different design from "we encrypted the internal network". Full treatment in Volume 11 §7.5.

The antipatterns, and the org causes

Worth learning as a list with causes rather than symptoms. Each of these looks like a coding error from the inside and is usually an organisational one from the outside.

The symptom, and what is actually generating it
AntipatternWhat you seeThe cause underneath
Synchronous call chainsLatency multiplies down the chain; one slow hop times out every callerAvailability coupled by dependency. Retry and timeout budgets are section 4 above
The distributed monolithServices that cannot be deployed independently — the thing you split to avoidSplit by noun instead of by business capability, then share the database to compensate
Shared databaseA schema change requires coordinating every serviceThe candidate service cannot own its tables. You have a network boundary with no data boundary behind it
Retries without budgets3³ amplification — 27 requests per user requestNo one owns the retry policy as a budget; each layer retries independently because each looks locally reasonable
No timeouts, or timeouts above the caller'sThreads held long after the caller gave up; pool exhaustionTimeouts chosen per-client rather than derived from the remaining budget — the chain-budget rule in Volume 5 §7.5
Chatty interfaces40ms to assemble one screen; N+1 over the network instead of over SQLThe interface was designed around tables rather than around what the caller needs
Cache as an unowned layerStale reads nobody can explain, and no answer to "who invalidates this?"No named owner and no invalidation contract. Also the most common source of cross-layer confusion — see Volume 6 §4.6 for why the Spring Cache, the persistence context and the Hibernate L2 cache are three different layers
Must remember — release process is an antipattern too

Deploying on Fridays is not superstition, it is a signal that the release process cannot be made safe, so the team has substituted a schedule for engineering. The fix is automated rollback and progressive delivery, not a better calendar. The predictive question worth being able to ask is in Volume 11 §8.9 — it is a better interview question than any single technology on this sheet.
