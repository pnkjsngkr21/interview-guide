Volume 7 — Spring Boot & Auto-Configuration

Which of Boot’s silent decisions is wrong for your workload, what each one costs at the boundary, and how you would know before production does.

  • 9 sections
← Prev Next →

If you only remember five things

  1. @EnableAutoConfiguration imports, it does not scan. It reads AutoConfiguration.imports from classpath*: across every jar and registers each class as a @Configuration bean definition; one failing condition skips the whole class, not the method.
  2. @ConditionalOnMissingBean is a question about now. It asks the bean factory what is registered at that instant, so it only backs off if you are processed after the class you defer to — declare @AutoConfiguration(after = …), and never rely on it on your own @Configuration.
  3. Enabled is not exposed. enabled-by-default is true, the default exposure list is health alone, and shutdown is the one endpoint not even enabled — so /actuator/conditions returning 404 is the allow-list working.
  4. Config precedence follows search-list order, not specificity. classpath:/, classpath:/config/, file:./, file:./config/, file:./config/*/ — so a stray file in the working directory beats the one your runbook calls authoritative.
  5. java -jar works and java -cp cannot because of the class loader. The manifest points at Boot’s LaunchedClassLoader, which understands BOOT-INF/; the standard AppClassLoader looks for top-level entries and never opens the nested dependencies.

01

Boot’s thesis: five decisions and the defaults review

Boot is a layer above Spring Framework, not a replacement for it. It makes five decisions — a dependency BOM, a starter naming convention, a conditional auto-configuration layer, an executable-jar format, and an embedded server plus an actuator surface — and every one of them is overridable. Auto-configuration is the least interesting of the five, because it is the only one that is fully reversible.

@SpringBootApplication decomposed — three constituents, three blast radii
ConstituentWhat it doesWhat it does not doFailure mode if misconfigured
@SpringBootConfiguration Marks the application root; itself a @Configuration — A second one on the classpath produces Found multiple @SpringBootConfiguration — in tests, not at runtime
@EnableAutoConfiguration Imports every auto-configuration in AutoConfiguration.imports that passes its conditions Does not scan your packages Remove it and the app starts with no DataSource and no DispatcherServlet
@ComponentScan Scans the package of the annotated class and everything below it Does not scan parent packages The scan root is decided by where the file sits — see the trap below
Interview trap — the scan root is a file-location decision

The highest-frequency Boot mistake in a large codebase, and it is a mechanism, not a warning. A monorepo where every team names its root package com.acme.<team> and someone drops the main class in com.acme “because that’s the application root” makes every module in the organisation a candidate. The cost is not seconds of startup — it is that the context now holds beans nobody asked for, from modules with their own @Bean definitions, their own @Transactional boundaries and their own auto-configuration entries. Two teams can be auto-configured into each other’s contexts, and the resulting NoUniqueBeanDefinitionException points at a file neither team touched. The rule: put the @SpringBootApplication class in the narrowest package that contains all of this service’s own beans, and in no broader one.

Must remember — the mechanism behind open-in-view

“It keeps the session open” is half the story. OpenEntityManagerInViewInterceptor binds an EntityManager to the request thread for the entire request including serialisation. On a read-heavy service with lazy associations, one request can hold a connection for its whole response — so the connection pool, not the JVM, becomes the ceiling. The signature: pool active connections pinned at maximum-pool-size with low transaction throughput, request threads WAITING on HikariPool.getConnection, and thread dumps showing the frames inside Jackson serialisation rather than inside a transaction. It is invisible at low traffic and appears as a p99 cliff under concurrency — a p50 of 90ms and a p99 of 4.1s.

The flip side, and the honest part: setting it to false is a behaviour change for a service that returns entities. Every lazy association Jackson resolved on demand then throws LazyInitializationException, and you find them in production rather than in a test using a different serialisation path. Leave it on and you are keeping an unmeasured capacity ceiling; set it and run the full endpoint suite — expect three or four findings.

Trade-off — convention over configuration

It trades control for time-to-first-request. Flips on: workload specificity — the moment your service is not a CRUD app with one database and modest concurrency, the defaults stop being free and start being decisions you are making by accident. The tell is that they are tuned for a demo: a 10-connection pool and 200 server threads are a small-deployment decision, not a neutral one. The condition does not flip back for a small team shipping a small service — there the defaults are genuinely correct and overriding them is the mistake.

02

Auto-configuration: the mechanism end to end

Exactly what changed, and in which version
VersionWhat happened
Boot ≤ 2.6Auto-configurations listed under the key EnableAutoConfiguration in META-INF/spring.factories — a generic key-value file that also carried initializers, listeners, application runners and failure analysers
Boot 2.7META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports introduced as the preferred location; the spring.factories key is deprecated. During 2.7 both are read, and using both is an error
Boot 3.0Auto-configuration via the spring.factories EnableAutoConfiguration key is removed. Other spring.factories keys — listeners, initializers, loaders, ApplicationRunners — are unaffected

The why is worth being able to give, because “it’s cleaner” is not the answer: one flat namespace overloaded across five extension mechanisms meant loading one list required parsing a file describing four others; .imports holds only fully-qualified class names in a file whose location is the semantics, so a refactoring tool can rewrite it; and @AutoConfiguration (new in 2.7) carries before/after on the class itself, next to the bean methods.

Must remember — every auto-configuration is in lite mode

@AutoConfiguration is itself meta-annotated with @Configuration(proxyBeanMethods = false). There is therefore no CGLIB subclass, and calling one @Bean method from another inside the same class constructs a new instance rather than returning the singleton. The symptoms are subtle and load-bearing: two connection objects, a mapper that does not share a transaction, an identity mismatch. It is easy to write precisely because application code in full mode does it harmlessly. Take the dependency as a method parameter instead.

@AutoConfiguration(after = DataSourceAutoConfiguration.class)
@ConditionalOnClass({ JdbcTemplate.class, DataSource.class })
@ConditionalOnProperty(prefix = "acme.reporting", name = "enabled",
                        havingValue = "true", matchIfMissing = false)
@EnableConfigurationProperties(AcmeReportingProperties.class)
public class AcmeReportingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                    // the single most important line
    public ReportingService reportingService(DataSource dataSource,
                                             AcmeReportingProperties properties) {
        JdbcTemplate jdbc = new JdbcTemplate(dataSource);
        jdbc.setQueryTimeout(properties.getQueryTimeoutSeconds());
        return new JdbcReportingService(jdbc, properties.getDefaultPageSize());
    }
}

Listed in src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, one class per line, no comments in Boot 3 — a malformed file is rejected outright.

The @Conditional family, and the trap in each
AnnotationMatches whenNotes and traps
@ConditionalOnClass(Foo.class)Foo is on the classpath Does not load the class — reads the class metadata with ASM, so it is safe on a type that only exists conditionally. The most-used condition in the ecosystem, and the one with the most common mistake (below)
@ConditionalOnMissingClass(Foo.class)Foo is not on the classpath The negative form; use it to supply a fallback bean
@ConditionalOnBean(Foo.class)A bean of type Foo is already registered Order-sensitive, and evaluated against bean definitions in the parse phase — a user’s @Bean method that has not been invoked yet does not count. Reliable only on auto-configuration, never on a scanned @Configuration
@ConditionalOnMissingBean(Foo.class)No bean of type Foo is registered The back-off mechanism and the foundation of every overrideable starter. With no type argument it means “no bean of the return type” — nearly always right, and occasionally exactly wrong when your method returns a concrete class but the application defines the interface
@ConditionalOnProperty(name, havingValue)The property is present, and equal if havingValue is set The workhorse. matchIfMissing defaults to false, so a property nobody set means off — the right default for a library, because a user who adds your starter without knowing the flag should not silently acquire the behaviour
@ConditionalOnWebApplication(type = SERVLET)The context is a servlet web app Set type explicitly — bare, it also matches a reactive app, which is not what “web application” usually means
@ConditionalOnExpression("…")The SpEL expression evaluates to true Evaluated once, at configuration-parsing time, so it cannot see a property that changes later, and it throws on an undefined property unless you give it a default. Prefer AllNestedConditions over a long unreadable SpEL string
@ConditionalOnSingleCandidate(Foo.class)Exactly one bean of the type Differs from @ConditionalOnBean in that multiple candidates still match if one is @Primary
@ConditionalOnResource, @ConditionalOnWarDeploymentA resource exists / deployed as a war The war-deployment one is the escape hatch for the “works in a container, breaks as a war” class of bug
@ConditionalOnThreading(VIRTUAL)The app is running on virtual threads Boot 3.2+; lets a starter behave differently under spring.threads.virtual.enabled. Matches only if the property and Java 21+ are both true
Interview trap — @ConditionalOnClass on the class that needs the class

The condition protects the @Bean method, not the class loading of the configuration class itself. Put the vendor type in the auto-configuration’s own signature or as a field type and you get a NoClassDefFoundError at a much more confusing moment — the condition never got a chance to run, because the class holding the condition could not be loaded to read the condition.

@AutoConfiguration
@ConditionalOnClass(AcmeVendorClient.class)   // safe: read from metadata, never loaded
public class AcmeVendorAutoConfiguration {

    private final AcmeVendorClient client;     // NoClassDefFoundError on a classpath
}                                               // without the SDK, before the condition runs
Must remember — the @ConditionalOnMissingBean ordering rule

The condition asks the bean factory what it knows at this instant, so its answer depends entirely on configuration-class processing order. Processed before the class you defer to, the answer is “no such bean”, you register a duplicate, and the application silently overrides a library. The rule, precisely: @ConditionalOnBean and @ConditionalOnMissingBean are reliable only on auto-configuration classes, never on your own @Configuration, and only when the relationship is declared with @AutoConfiguration(after = …) or before = …. User config found by @ComponentScan is processed in an order nobody controls, so a condition there is a coin flip that flips when a library joins the classpath.

Two consequences worth having ready. First, the duplicate is invisible until it is not: with @Primary the app starts, tests pass, and every injection point resolves — then the bug appears in the one place that does a getBeansOfType() or injects a List<T> and gets two entries. Adding @Primary is therefore not a fix. Second, these ordering bugs are intermittent by nature — they reproduce in the module that has the library and vanish in the module that doesn’t, which is why the first diagnostic is the report rather than the code.

Must remember — how to answer “why isn’t my bean being created?”

Three routes to the same ConditionEvaluationReport: --debug on the command line (or debug=true in application.properties) while developing; /actuator/conditions on a running instance, after you have added it to the exposure allow-list; and ApplicationContextRunner in your own starter’s test suite. Nearly nobody runs the third. /actuator/conditions is exposed no more than it is enabled — endpoints are enabled by default but only health is exposed, so the 404 means the allow-list is doing its job, not that Boot is broken.

class AcmeReportingAutoConfigurationTest {

    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(AcmeReportingAutoConfiguration.class));

    @Test
    void backsOffWhenTheApplicationDefinesItsOwn() {
        runner.withUserConfiguration(MyOwnMapper.class)
              .run(ctx -> assertThat(ctx).doesNotHaveBean(AcmeMapper.class));
    }

    @Test
    void skipsWhenTheVendorSdkIsAbsent() {
        runner.withClassLoader(new FilteredClassLoader(AcmeVendorSdk.class))
              .run(ctx -> assertThat(ctx).doesNotHaveBean(AcmeMapper.class));
    }
}

That second test catches the one bug you cannot otherwise find: an auto-configuration that references a vendor type in a @Bean method signature passes on every classpath you happen to have, and fails with NoClassDefFoundError only in a consumer’s.

03

Starters & the BOM

A starter is a POM with dependencies and no code — that is the whole definition, and the senior observation is that this makes it a transitive dependency set: you did not choose Tomcat, Jackson or SnakeYAML, someone chose them and a version, and that version is in your classpath whether you asked for it or not.

What the common starters drag in, and the one thing that bites
StarterBringsThe one that bites
spring-boot-starter-web spring-web, spring-webmvc, starter-json (Jackson + jackson-datatype-jsr310), starter-tomcat, starter (logging, snakeyaml) Tomcat is embedded — the app binds a port in-process, so two instances cannot share a host without changing server.port, and “deploy to the app server” is no longer a deployment model
spring-boot-starter-data-jpa starter-aop, starter-jdbc (HikariCP), jakarta.persistence-api, hibernate-core, spring-data-jpa, spring-aspects HikariCP arrives with a 10-connection pool, and spring-aspects brings @Async/@Scheduled support whether you use it or not
spring-boot-starter-security spring-security-config, -web, -core Adding it to a service that already has its own auth flips on the default filter chain: every endpoint becomes password-protected and a generated password appears in the logs (Volume 8)
spring-boot-starter-validation Hibernate Validator, Jakarta EL Not pulled in by starter-web since Boot 2.3 — the single most common cause of “my @Valid does nothing”
spring-boot-starter-test JUnit 5, Mockito, AssertJ, JSONassert, JsonPath, XmlUnit, spring-test Scope is test in a well-formed POM; teams that widen it “for convenience” drag test libraries into the production jar and its Docker dependency layer
spring-boot-starter-actuator + micrometer-registry-prometheus Actuator autoconfigure, Micrometer core and observation, Prometheus client Micrometer arrives with the observation API — hand-rolled instrumentation predating it becomes a refactor later. The registry choice is a monitoring-stack decision, cheap to add and expensive to change
Interview trap — “the BOM pins versions so nothing can conflict”

Wrong in the way that matters operationally. The BOM pins versions for dependencies that omit a <version> — which is everything a starter pulls. The moment you declare a version, yours wins under Maven’s nearest-wins, and the highest wins under Gradle’s platform constraints — and the two builds can produce genuinely different classpaths from identical declarations. You now own a version you must reconcile with Boot’s BOM at every upgrade. The BOM manages your classpath; it does not protect you from your own overrides. The CI answer is a dependency:tree diff — the point is not to inspect the tree but to fail a build when the classpath changes with no diff in the repository, because that is the change nobody reviews.

Parent POM or imported BOM
spring-boot-starter-parentspring-boot-dependencies (imported)

The staff-level point about the parent is that a parent POM is inheritance, and inheritance leaks — it sets the compiler source, resource-filtering delimiters and plugin versions for every module beneath it, which is convenient in a 20-module monorepo until one module needs a different release or a different Surefire configuration.

Must remember — the two rules a well-behaved starter follows

Rule 1: @ConditionalOnMissingBean on every single bean you contribute, so the application can override silently and by type. A starter that unconditionally defines an ObjectMapper, a RestTemplate, a DataSource or any client type is a bug, and it is reported as “your library broke our app” the first time two of them share a classpath.

Rule 2 is broader: never define a bean of a type the application might reasonably own. If the type is yours, contribute it with a back-off. If it is a general-purpose infrastructure type — a pool, a mapper, a template, a scheduler, a Clock — contribute a factory and let the application own the instance. Boot follows this itself: DataSourceAutoConfiguration contributes a DataSourceBuilder and JacksonAutoConfiguration a Jackson2ObjectMapperBuilder, not the objects.

The corollary people miss: the -autoconfigure module must never depend on another starter. A dependency on starter-web or starter-data-jpa there drags that starter’s entire auto-configurations into every consumer’s context, whether they use your feature or not — it works in your demo and pulls a whole web or persistence stack into an unrelated batch job. Depend on the narrow API (jakarta.persistence-api, spring-jdbc) and activate with @ConditionalOnClass.

Scaling reality check — the classpath you did not choose

An application that started with three starters routinely ends with 60+ jars. Three things scale with that number, and only one of them is startup: image size and cold-pull time (a dependency layer of 80–150MB re-pushed on every dependency bump), and blast radius — every jar is code that can throw, and every version moves on someone else’s upgrade. The diagnostic that finds it is dependency:tree: a tree that grew from 40 artifacts to 90 over a year with nobody adding a dependency is nearly always a starter pulled in for a single class. The tell that it matters most is the service that autoscales from zero — then every new replica is paying that registry transfer at the exact moment the system is under stress.

The two-module layout

The rules above are the contract; this is the shape. A starter is always two Maven modules, and the split is an architectural rule rather than ceremony — see vol07 §3.5 for the worked tree and the full POM.

What lives in which module
ModuleContains
-spring-boot-autoconfigure All the code. The @AutoConfiguration class, the @ConfigurationProperties class, any SPI factory. Depends on spring-boot-autoconfigure + your core library, and on no other starter. Holds the registration file.
-spring-boot-starter A POM and nothing else. One dependency, on the autoconfigure module. No code, so there is no second copy of anything and no second set of conditions to reason about.

Two placement facts that are easy to get wrong:

  • The registration file lives in the autoconfigure module, at META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports — one fully-qualified class name per line. It is not the old spring.factories key, and since Boot 3 it is the only supported mechanism.
  • Add spring-boot-configuration-processor as optional. It generates the IDE metadata that turns your properties into autocomplete with descriptions; being optional keeps it out of your consumers’ runtime classpath.
Interview trap — one module “for speed” breaks consumers, not you

A single-module starter is a real anti-pattern, and it fails asymmetrically: it works in your demo, and breaks in someone else’s application. Collapsing the two means the dependency on spring-boot-autoconfigure becomes a compile-scope dependency of every consumer, so they inherit your conditions and your classes whether they use your feature or not. Worse, it makes it possible for your starter to depend on another starter, which is the mistake in the trap above — and the two-module split exists precisely to make that mistake hard to commit.

04

Externalized configuration

Boot 2.4 replaced the old one-file-plus-variants model with the ConfigData API. The design conclusion underneath it is the one to carry: your configuration is an API, and it should be reviewed like one — which is a different standard from the one that produced a file nobody reads.

The default search locations — first match wins, and all are optional:
#LocationWhy it is there
1classpath:/Inside the jar — the sensible defaults
2classpath:/config/Conventional override directory, still inside the jar
3file:./The working directory — how a ConfigMap mount or a stray file beats the jar
4file:./config/The conventional external override dir
5file:./config/*/One subdirectory per profile — the legacy and multi-tenant shape, selected with spring.profiles.active
Interview trap — config/ does not beat the working directory

“The config/ directory has higher precedence because it is more specific” is the common wrong answer, and it is wrong in the direction that costs an afternoon. Precedence follows the order of the search list, not specificity: file:./ is position 3 and file:./config/ is position 4, so a stray application.yml in the working directory silently shadows the one your runbook calls authoritative. The intuition that “more specific wins” is true within a location — a profile-specific file beats the profile-less one — and false across locations. Because this is a file-being-ignored problem, the debugging instinct is to look at ./config/, which is exactly the file not winning. Use /actuator/env for the origin.

The related one: spring.config.location replaces the default list, so the in-jar application.yml silently stops being read unless you list it explicitly — usually discovered as “my default timeout is now null”. spring.config.additional-location adds and is consulted before the defaults, and is almost always the right choice.

spring:
  config:
    import:
      - "optional:configserver:http://config.internal:8888"   # most authoritative
      - "optional:vault:uri:https://vault.internal:8200"
      - "file:/etc/acme/shared.yml"
      - "classpath:defaults.yml"                            # packaged, lowest
Trade-off — hard import versus optional:

Flips on: which failure you would rather have. A hard import means the application cannot start when the config server is unavailable, which converts one service’s dependency into a fleet-wide deploy-time problem — a config-server restart during a release window takes down every service restarting at that moment. optional: fixes that and introduces the opposite failure: silent degradation to packaged defaults, and a packaged default for a database URL is a connection to the wrong database. Most teams want optional: plus a cached last-known-good and alerting on the fallback, which is the half teams forget. The staff answer is that the choice is the deliverable, written down: hard-fail where a stale config is worse than a down service, optional: plus alerting everywhere else.

        @NotNull @DefaultValue("30s") Duration queryTimeout,   // 30s, 500ms, PT30S
        @Min(1) @Max(1000) @DefaultValue("100") int pageSize,

    public record Delivery(

Must remember — validation only bites if something registers the class

@ConfigurationProperties validation runs at startup and fails the context — that is the whole point of @Validated, and it is why a missing mandatory property is a deployment failure rather than a NullPointerException at 3am. The corollary is the trap: @Validated on a class you forgot to register does nothing at all, because validation is wired by @EnableConfigurationProperties or @ConfigurationPropertiesScan, not by the @ConfigurationProperties annotation alone. Register nothing and you have a typed class that is never bound and never checked.

Two things worth raising unprompted in a review. @ConfigurationProperties on a @Bean method is the standard answer to “how do I configure a library I don’t own” — declare the bean, annotate the method, and every settable property on a third-party object becomes a typed, validated, enumerable surface. And the constraints themselves are the design conversation: a retries count with no upper bound and a connectTimeout with no lower bound are two properties whose relationship is load-bearing and currently unenforced — the constraint is where you discover that.

Interview trap — the committed default, and what sanitization really does

password: ${DB_PASSWORD:devpassword} — “just a dev default” — is a silent production secret everywhere the environment variable is missing, and it is in git history forever, where git rm and rotation both fail to remove it. The fix is no default at all: a @NotBlank String password with no : fallback, so a missing secret fails at startup and is caught in CI.

The second half is the one candidates overstate. configprops.show-values and env.show-values both default to never, which is a defence — but sanitization is a name-based filter matching patterns like password, secret, key, token, credentials. So it both over-sanitizes (acme.credentials-file is a path and gets masked) and under-sanitizes: a secret held under an unremarkable name is printed in full. The correct posture is show-values=when-authorized with the management surface on its own port — not reliance on the name filter.

And the follow-on: a @ConfigurationProperties value is bound once, at startup. Refreshing the property source does not rebind a constructed bean, so rotating a properties-bound credential is a restart — zero-downtime rotation requires reading through something that re-reads.

05

The executable JAR

Interview trap — Boot 3.2 changed the nested-jar story

For most of Boot’s life a nested jar was reachable as a jar:nested:/path/to/lib.jar!/ URL through a custom URLStreamHandler. Boot 3.2 deprecated that, and the reason is worth more than the fact: a custom jar: handler is a process-global JVM extension — registering one changes URL parsing for code you do not control, and it interacts badly with the module path and with classloaders that expect a standard handler. The failure therefore appears in someone else’s dependency. The supported operations are now explicit and out-of-band: -Djarmode=tools extract for a plain explode, -Djarmode=layertools extract for the layered layout, and -Djarmode=tools -Dloader.main=… to run a different entry point. The jar:nested: form still appears in old runbooks, which is exactly why it is worth getting right.

Layered jars — the payoff, and the condition that removes it
Unlayered fat jarLayered
Bytes pushed per code deploy~150MB~2MB
Cold pull after a code changeFull transferCached dependency layer plus a small delta
Layer invalidation triggerAny change at allOnly a dependency version change
Worse whenWhen the build regenerates dependencies/ with different ordering or timestamps, so the layer hash changes every run — all the complexity and none of the benefit. classpath.idx exists to pin the order. Check empirically: deploy twice with no dependency change and confirm the second is a cache hit
Scaling reality check — why layering is operational, not cosmetic

The scenario it changes is scale from zero. A service that autoscales on a traffic spike has to pull its image during the spike; with an unlayered 150MB image every new replica pays a registry transfer at the exact moment the system is under stress, so the scale-up meant to fix the incident is itself gated on network transfer. With layers it becomes a metadata request plus a few megabytes. This is the one most concrete argument for layering, and it only shows up in the incident where you most needed the replicas.

ENTRYPOINT ["java", \
  "-XX:MaxRAMPercentage=75.0", \      # heap from the cgroup limit, not a baked -Xmx

  "-jar", "/app.jar"]
Must remember — the JVM flags a platform team reads first

-XX:MaxRAMPercentage=75.0 so the heap derives from the cgroup limit; a -Xmx baked at build time breaks the moment the limit changes and the pod is kernel-OOM-killed. -XX:+ExitOnOutOfMemoryError so an OOM terminates with a non-zero exit code instead of leaving a Running pod serving 500s from an undefined JVM. -XX:+HeapDumpOnOutOfMemoryError with a persistent HeapDumpPath, because a dump written to the container’s writable layer is deleted by the restart it was meant to explain. And -Xlog:gc* with rotation, because GC pause data is the only legitimate input to a heap-sizing decision. The pairing to insist on is the first two: MaxRAMPercentage without ExitOnOutOfMemoryError gives you a correctly sized and silently broken container — which is the worst combination, and the one most base images ship.

Trade-off — packaging format is the deployment model

An executable jar in a container is an excellent answer for a batch job, a CLI and a simple service. Flips on: how often you ship. For a service updated 50 times a day across 40 instances, an app server or a shared runtime wins on update speed — swap a jar, restart a pool, one artefact per team — while the JVM image wins on reproducibility, dependency isolation and per-service configuration. Note that choosing “fat jar in a container” also commits you to image promotion, layer caching, config as a separate artefact and sidecar injection; agreeing to that is the part teams skip. The question that surfaces it is not “should we use containers” but “how do we ship a change to 40 instances in the next ten minutes”.

06

AOT & native image

AOT processing exists to answer a structural problem: Spring does two things at runtime that require inspecting code rather than executing it — reflection (annotation reading, name-based instantiation, generic resolution) and runtime proxy generation (CGLIB subclasses and JDK proxies). Both are unbounded, because Spring cannot know in advance which of your classes it will reflect over or proxy. AOT runs the context at build time in a mode where those operations are recorded rather than performed, and emits generated sources plus a resource index.

Must remember — AOT and native image are two claims

AOT produces a normal JVM jar. It removes runtime reflection, which speeds up startup and reduces memory, and it is largely free because it happens inside a build you already run — it is even on by default for some scenarios in Boot 3. Native image is whole-program compilation to a standalone binary with GraalVM: it removes the JVM as well, and that is what buys the dramatic startup and footprint numbers — at the cost of minutes of build time and constrained reflection. “Boot does AOT” is true and it is not the same claim as “Boot is native”.

Native image on three axes — the honest decomposition
AxisNative imageWhy
StartupBetter — tens of milliseconds where a JVM service takes 8–15sNothing is parsed, verified or JIT-compiled at startup; the binary is already machine code
MemoryBetter — typically 10–50MB RSS for a trivial service against 60–100MB+ for a bare JVMNo metaspace, code cache or JIT structures. This is the number that changes density economics
Peak throughput on hot CPU codeWorseThe AOT compiler optimises for startup and image size, with no profile-guided optimisation and no re-JIT. On a database-round-trip-dominated service — nearly every Spring service — this axis is noise
Build time2–10 minutes, growing with the dependency graphFull compilation of the whole reachable program, per architecture
Binary size50–90MB — larger than expected, and it does not shrinkStatically linked, with no shared deduplication
DebuggabilityWorse — no jstack, no heap dumpYou depend on the native agent ecosystem instead
Interview trap — “native image makes it faster”

State the three axes separately or you lose the point. Startup better, memory better, peak throughput on genuinely CPU-bound hot code worse. The reason is mechanical: the JVM’s advantage is precisely that it watches which methods are hot and recompiles them with that knowledge, and deoptimises when a profile turns out wrong — none of which a build-time compiler can do. So for the service whose cost is dominated by database and network I/O the throughput axis is noise and the wins are real, and for a service with a genuine hot loop the warmed-up JVM wins. Anyone who benchmarked startup and assumed throughput followed will be surprised in production.

Scaling reality check — the price is paid in CI, not in the jar

A 2–10 minute build is not a build problem, it is a CI capacity and feedback-loop problem, and it is multiplied by architectures, by running on every commit rather than nightly, and by cache hit rate. One real adoption: startup fell from 9s to 60ms and median memory from 340MB to 90MB exactly as advertised — and then CI went from 4 minutes to 38 and a CPU-heavy PDF endpoint regressed on p99. Native compilation routinely needs 4–8GB of RAM per build, and the cache is keyed on the full dependency graph, so the most painful moments — a big upgrade, a release, a dependency bump — are exactly when everyone waits ten minutes.

Flips on workload shape: spiky, bursty or scale-to-zero workloads gain decisively; a steady-state service running a handful of instances per node gains almost nothing, because the node’s fixed costs dominate and you experience the startup improvement approximately zero times. The staff move is an admission test per service — measure p99 both ways and count build-minutes as a first-class cost — not an estate-wide mandate.

Interview trap — whose problem is the unreachable element?

Structurally the library’s, even though it surfaces in your pipeline — and that asymmetry is the argument. A library reflects on classes AOT cannot infer are reachable from a constructor, a @Bean method or a scanned component, and ships no RuntimeHintsRegistrar. Your options are to register the hints in your own build, which you should not want to maintain forever, or to file it upstream. GraalVM ships a community reachability-metadata repository covering popular third-party libraries, which is exactly why your own dynamic code is the residue that matters. At runtime these accesses are not degraded, they are absent — a hard error at first use, not a warning at build.

Actuator, health & metrics

Actuator is not a debugging tool. It is a management API running in the same JVM as the code it reports on, and every endpoint on it assumes a trusted caller. Its defaults are a defence, and the defaults are exactly where the interview marks are.

The endpoints that matter, and what each one gives away
EndpointExposesWhy it is sensitive

/actuator/envEvery property, and with show-values, every valueA credential-disclosure endpoint — connection strings, internal hostnames, tokens

/actuator/heapdumpA full GC-rooted heap dumpEvery secret ever loaded, every byte[] in flight, every cached object. A complete data-exfiltration primitive that needs no credential

Interview trap — three claims about the defaults that cost marks

(1) “Actuator exposes health and info by default” — management.endpoints.web.exposure.include is health alone; info is enabled and must be added. (2) “/actuator/heapdump is on by default” — it is enabled but not exposed, and shutdown is the one endpoint that is not even enabled. (3) “Actuator is safe because it only exposes health” — true of the default and irrelevant the moment someone sets include=* in a profile that later reaches production.

Underneath all three is one distinction: enabled is not exposed. management.endpoints.enabled-by-default is true, so every endpoint is enabled while one is exposed over HTTP. That is precisely why /actuator/conditions 404s on a stock application — and why show-details, configprops.show-values and env.show-values all defaulting to never is a second, independent defence.

Must remember — exposure is a trust-boundary decision, not a property value

The staff answer is a separately-authenticated, internal-network-only management surface: management.server.port on a different port from the application, management.server.address bound to an internal interface, a real authentication mechanism, and a narrow allow-list rather than a wildcard.

The include=* incident has a specific shape, because the wildcard was never the problem on the day it was written. One of three things happens: a missing profile setting plus spring.profiles.default: prod runs a developer in prod mode; a Helm chart sets SPRING_PROFILES_ACTIVE=dev for a debug rollout; or a profile group — spring.profiles.group.prod=dev,prod, added during a migration — inherits the wildcard nobody removed. A platform team should own the transport in a base image or chart so no service can get it wrong, and each service should own the content. If the need is real debugging, the answer is a loopback binding plus a tunnel — not a wider bind.

Liveness, readiness, and the health contract

Actuator’s health model is four statuses and two probe groups, and the whole distinction rests on one question: is this process broken, or should it just stop being given new work? Marking a degraded dependency DOWN conflates those, and the cost is paid in capacity exactly when capacity is short.

Liveness versus readiness — two different questions, two different actions
ConceptRuleWhen it bites
Liveness/actuator/health/liveness asks “is this process irrecoverably broken?” Failure action: kill and restart the container A liveness probe that checks the database kills every pod when the database blips — a brief dependency problem becomes a restart storm, and the pods cannot start again because the database is still down. Check your liveness output for a database check and remove it
Readiness/actuator/health/readiness asks “can this instance serve traffic right now?” Failure action: remove from the load balancer, leave it running Failing readiness because an optional dependency is degraded removes capacity precisely when you are short of it. An instance that can serve 95% of traffic can serve
Health statusOUT_OF_SERVICE for a degraded dependency you can still partly serve; DOWN for genuinely broken A HealthIndicator returning DOWN for a slow gateway takes the whole instance out of rotation over the one endpoint that needed the gateway
Every checkNeeds a timeout An indicator that blocks 30 seconds against a hung downstream turns the health endpoint itself into an availability problem — and for liveness, whose failure action is a kill, that is a self-inflicted outage
Custom indicatorsCheap and local by default A contributor making a network call on every probe, every 5 seconds, across 40 pods, is 8 calls per second to a system that may itself be the problem
 
@Component
class PaymentGatewayHealthIndicator implements HealthIndicator {

    private final PaymentClient client;

    @Override
    public Health health() {
        try {
            client.ping();                     // cheap, and it must time out
            return Health.up().build();
        } catch (Exception e) {
            return Health.outOfService()       // not DOWN: degraded, not broken
                    .withDetail("error", e.getClass().getSimpleName())
                    .withDetail("gateway", "acme-pay")
                    .build();
        }
    }
}

The two probe settings that matter, and the asymmetry between them: liveness at initialDelaySeconds: 30, periodSeconds: 10, failureThreshold: 3 — 30 seconds of failure before a restart. Readiness at initialDelaySeconds: 5, periodSeconds: 5, failureThreshold: 1 — out of rotation almost immediately. Readiness is deliberately the twitchier of the two, because being removed from rotation is cheap and being killed is not.

Metrics and the cardinality trap

Micrometer is on the classpath whenever spring-boot-starter-actuator is, whether or not you write a line of instrumentation. The failure it makes possible is not a Boot bug and Micrometer will not stop you: a metric name plus a tag set is a distinct time series, held in memory for the retention period, with backend work proportional to the number of combinations.

Must remember — an unbounded tag value is a memory leak in someone else’s cluster

Ten million user IDs on one counter is ten million time series in RAM, ten million series files on disk, and a label lookup that slows with every new one. The application-side symptom, with a Micrometer in-memory or Atlas-style backend under a TTL, is unbounded heap growth that looks exactly like an application leak and is not. The rule of thumb worth carrying: every tag value must come from a set whose size is bounded by something you control — the number of endpoints, HTTP methods, regions, plan tiers — and never from a set that grows with traffic. The prevention is a cardinality budget enforced in the registry: Micrometer supports a MeterFilter that refuses or truncates a tag value over a threshold, and putting one in is cheap insurance.

Scaling reality check — the trigger is a good day

A feature adds a user.id tag; nothing happens for weeks, because the series count is small. Then a marketing push, a backfill job or a traffic spike multiplies the distinct values and the metrics backend runs out of memory — while the application is perfectly healthy, so the incident looks unrelated to the deploy that caused it. The diagnostic is the ratio, distinct series per metric name, tracked over time rather than inspected once. The two related shapes: a Counter registered with a changing tag is a bug in your code, because a counter that goes down breaks every rate calculation built on it; and a Gauge whose lambda holds a strong reference to a large object graph is a genuine leak, because the registry holds it for the process lifetime.

Failure modes: the ones that reach production

Boot’s own machinery is not where production incidents come from. They come from three places: an ordering assumption that holds in tests and not in a cluster, a default that was tuned for a demo, and a contract between the application and the platform where both halves assume the other is doing its part. The shutdown race is the clearest of the third, because the fix lives in a manifest and the bug lives in your code.

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=30s   # default 30s; in-flight requests
                                              # get this long to finish
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 1

The in-Spring mechanism is an ApplicationListener<ContextClosedEvent> that publishes ReadinessState.REFUSING_TRAFFIC — which is what management.endpoint.health.probes.enabled wires into the readiness probe — sleeps for the propagation window, and only then lets the graceful shutdown proceed. The cleaner place for the same delay is a preStop hook, because it happens before the JVM is signalled at all and does not require the application to know the number.

Where a Boot service listens — three addresses, three blast radii
PropertyWhat it doesWhy it is a decision
server.portThe port the embedded server binds in-processBecause the server is embedded, two instances cannot share a host without changing it — and “deploy to the app server” is no longer a deployment model. 0 for an ephemeral port is the test-and-metrics answer
management.server.portA different port for the management surfaceThe single highest-value actuator setting: it makes the management API unreachable from whatever can already reach the application port
management.server.addressBinds the management surface to one interfaceAn internal interface for a cluster, or loopback plus a VPN or SSH tunnel for debugging. Loopback is the answer to “we need real debugging” — never a wider bind

Logging is auto-configured rather than configured, and that is the point to make in an interview: spring-boot-starter-logging arrives inside spring-boot-starter, so nobody chose the backend and nobody reviewed the level — which is why the level being writable at runtime is the only logging question worth an answer.

Interview trap — your ApplicationRunner runs after the port is open

ApplicationRunner and CommandLineRunner beans are collected into one list and sorted together by AnnotationAwareOrderComparator — so ordering between the two interface types is not fixed by type, and ties break by registration order. They run at step 5 of SpringApplication.run: after the context has refreshed and after the web server is listening, but before ApplicationReadyEvent. Two consequences follow, and both are incidents. A runner that takes 40 seconds to warm a cache does not delay the readiness probe — the instance takes traffic with a cold cache unless you gate readiness on the warm-up, which you should. And a runner that throws aborts startup after the port was opened, so the instance is briefly reachable and then dies. The fix for both is the same: an ApplicationAvailability check reporting ReadinessState.REFUSING_TRAFFIC until a flag is set.

Interview trap — a deploy that fails and reports exit code 0

SpringApplication maps an exception to an exit code through an ExitCodeGenerator bean or an ExitCodeExceptionMapper — but that mapping only runs if the exception propagates out of run. A main that catches its own exception and returns normally lets the JVM terminate with exit 0, which every orchestrator reads as success: the pod terminates cleanly, the platform logs a normal shutdown, the deploy is green, and the service is simply missing from the pool with nothing in the logs saying why. If your startup can fail, let it fail.

Interview trap — spring.main.lazy-initialization as a startup fix

The review comment is that this trades a startup cost for a first-request cost and a failure-mode change, so it needs a reason. It converts failures caught in CI into failures caught by users: a bean with a bad dependency now fails when someone hits that path, not at boot. It also means every endpoint pays a first-request penalty, so during a scale-up event every new replica serves its worst latency exactly when the system is under stress. The acceptable version is diagnostic — turn it on to find out whether the cost is in eager initialisation at all — followed by making the specific expensive bean lazy, so the trade is scoped rather than global. The same reasoning orders the other startup levers: scan breadth first (is the main class in a package broader than the service?), then eager I/O in @PostConstruct or a @Bean method, then classpath breadth, because type resolution loads classes.

Must remember — match your review effort to the cost of reversing the decision

Asked which of Boot’s decisions is most expensive to reverse, the useful answer separates them by blast radius rather than picking one. A default is one line of config — cheap, and cheap precisely because the convention is that everything is overridable. A starter is a dependency swap plus whatever the replacement auto-configures differently: bounded, not trivial. A packaging format is expensive, because the deploy pipeline, the base image, the runbooks and every engineer’s muscle memory all encode it. An actuator exposure decision is cheap to change and catastrophic to get wrong — the worst combination available: low cost, high consequence, and no signal until someone probes it. The lesson is that the cheapest-to-reverse thing gets reviewed least, precisely because everyone assumes it is low-stakes, and that is where the include: "*" in a shared application.yml came from.
