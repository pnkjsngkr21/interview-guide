Spring — The Spring Complete Deep-Dive

Volume 5 — Spring MVC & the Web Layer

The ordered path a request actually travels, and the three places — the filter chain, the argument resolver chain, and the moment the response is committed — where almost every “why did this happen” question in the web layer is really decided.

  • 9 sections
← Prev Next →

If you only remember five things

  1. Filter or interceptor is decided by what must see an unmatched request. A filter wraps the whole DispatcherServlet and runs on every dispatch including static resources, 404s and /error; an interceptor only exists for a matched handler. CORS, authentication, MDC, rate limiting and body caching all belong in a filter.
  2. preHandle returning false is a veto, and a veto means afterCompletion never runs — for the vetoing interceptor. Anything opened in preHandle and closed in afterCompletion leaks on exactly the requests you reject.
  3. @Valid is a report generator, not a gate. Add a BindingResult parameter and Spring populates it, throws nothing, and invokes your method anyway — forget hasErrors() and invalid input returns 200 with a corrupt record persisted, silently.
  4. @ModelAttribute on a JPA entity is a mass-assignment vulnerability (CWE-915). It calls a setter for every request parameter, and JPA requires setters for role and balance, so POST /account?role=ADMIN is a privilege escalation. Bind a command record with @Valid @RequestBody.
  5. A filter's exception never reaches @ControllerAdvice; an interceptor's does, because the resolver chain runs inside doDispatch. That, not the status code, is what decides which of two error shapes the client gets.

No section matches that filter.

01

From Servlet to DispatcherServlet

Spring MVC does not replace the servlet specification; it implements it. The container accepts the socket and picks a worker thread before Spring is consulted at all, which is why “explain Spring MVC” answered as a DispatcherServlet diagram is half an answer. DispatcherServlet itself is thin: three pluggable strategies (HandlerMapping, HandlerAdapter, HandlerExceptionResolver) over a handler whose shape the framework does not care about.

The two objects people confuse under pressure

Interview trap — “the ApplicationContext is a singleton”

Incomplete in a way that matters here. The root context is a singleton, and DispatcherServlet creates a second singleton WebApplicationContext whose parent is the root. Visibility is one-directional: the child sees the parent's beans (that is how controllers get services injected), the parent cannot see the child's — so a Filter in the root context cannot inject a @ControllerAdvice from the servlet context. Boot collapses the two into one ServletWebServerApplicationContext unless you configure the servlet programmatically, which is why the split is invisible until a legacy XML config makes it real.

Threading is where the container, not Spring, sets the ceiling. The three connector settings are routinely confused, and the difference between them is the difference between “queue the work” and “refuse the connection”.

Scaling reality check — 200 threads × 50ms is 4,000 req/s

The arithmetic is unforgiving. If each request spends 50ms in the application, 200 threads is a ceiling of 4,000 requests per second, and no configuration change beats that without changing where the time goes. Raising maxThreads is the reflex fix and it is usually wrong: each extra thread costs ~1MB of stack and can independently take a connection from the pool. If the real bottleneck is a 20ms query against a 50-connection pool, going to 800 threads queues 800 threads on 50 connections — you have moved the queue out of Tomcat, where a thread dump shows it, into HikariCP, where it is invisible.

Boot property names, and what HTTP/2 changes

HTTP/2 changes what the limit means: with multiplexing, concurrent streams are bounded by maxConcurrentStreams (default 100) rather than maxThreads, head-of-line blocking disappears per stream, and the browser needs one connection per origin instead of six — so a maxThreads wall now shows up as stream-level queuing inside the connector rather than refused sockets.

02

HandlerMapping & HandlerAdapter

RequestMappingHandlerMapping does its work once, at context refresh. It scans every @Controller bean and stores a RequestMappingInfo (pattern, method, params, headers, consumes, produces) plus a HandlerMethod in a lookup structure that is read-only from then on. Nothing is scanned per request. The HandlerMethod holds the bean name, not an instance — it calls beanFactory.getBean(beanName) at invocation time, which is the only reason a prototype-scoped controller works at all.

Per-request cost, honestly

Must remember — when an endpoint is slow, it is never the mapping

Redirecting that conversation is the valuable half of the answer. Mapping is a read-only registry and a tree walk. The two things worth looking at are argument resolution (many parameters; an Object-typed unannotated parameter falls all the way through the chain into @ModelAttribute) and the work inside the handler — which very often means a database call hiding in an annotation, such as a @PreAuthorize that loads permissions or a @ModelAttribute method that queries. Volume 9 covers how to establish this with a profile.

Interview trap — a String return is a view name

“A String return value is written to the response body” is wrong unless the handler is @ResponseBody (or the controller is @RestController). In a plain @Controller, ViewNameMethodReturnValueHandler puts the string into the model as viewName and DispatcherServlet hands it to a ViewResolver. That is correct, long-standing behaviour for server-rendered views, and it is the mechanism behind “my REST endpoint echoed the literal text back and then failed to find a template”.

Interview trap — the AOP proxy and AnnotatedElement

If a controller is AOP-advised — @Transactional, @PreAuthorize, @Async, @Cacheable — the bean in the container is a proxy, so HandlerMethod.getBeanType() returns the proxy class. A JDK dynamic proxy implements only the interface and does not carry method annotations, so Spring unwraps with ClassUtils.getUserClass before reading @RequestMapping. Consequences: class-level @Transactional on a controller effectively forces CGLIB proxying or the annotation is lost; and any custom code reflecting over getBeanType().getMethod(...) gets the proxy's view, not yours. spring.aop.proxy-target-class=true is the Boot default and hides most of this. The general proxy mechanics are Volume 3; the getUserClass habit is the part that travels.

Trade-off — functional routing

RouterFunction is genuinely less machinery and the better answer for a small, stateless, self-contained API: no classpath scanning, no proxy subtlety, and tests without a context. Flips on: the moment you need HandlerInterceptor, @ControllerAdvice, argument resolution, or a method-level security annotation on the service — because a router function has no interceptors at all. In a codebase where global exception advice is already load-bearing, functional routing forces you to restructure error handling per router, and that cost, not the per-request saving, is what goes in front of a decision-maker.

@Bean
RouterFunction<ServerResponse> routes(OrderService orders) {
    return RouterFunctions.route()
        .GET("/orders/{id}", req -> orders.find(req.pathVariable("id"))
                .map(ResponseEntity::ok)
                .orElseGet(() -> ResponseEntity.notFound().build()))
        .build();
}
03

Mapping & data binding

Every @RequestMapping attribute is a RequestCondition, and at request time all of them must match — they are ANDed, so params and headers are just two more conjuncts, not either/or. @GetMapping and friends are composed annotations, which is why custom framework code scanning for the literal @RequestMapping routinely misses half the handlers in a codebase.

Path patterns — what matches, and what it costs you
PatternMatchesDoes not matchUse for
{id}/orders/12, /orders/abc/orders/12/itemsAny single segment
{id:[0-9]+}/orders/12/orders/abcRouting discrimination — yields 404, not 400
*/orders/12/orders/12/itemsExactly one segment
{*path}/files/a/b/c.txtNothing — it is greedy to the end, and only at the end of a patternCatch-all proxies, file trees
The binding annotations and how each one silently misbehaves

@PathVariableRequired — MissingPathVariableException → 500The name defaults to the parameter name from bytecode, which needs -parameters

Must remember — -parameters

@PathVariable Long id with no explicit name reads the parameter name from the bytecode. Without -parameters the name is arg0 and resolution fails with a MissingPathVariableException that surfaces as a 500 with no message. Spring Boot's Maven and Gradle plugins add the flag by default, so the failure shows up in the module you built by hand, the Android build, or the legacy javac script — which is why it presents as “works locally, 500s in the Docker build”. Always name @PathVariable and @RequestParam explicitly in a public API. Three characters, and it removes an entire class of environment-dependent failure.

Interview trap — @ModelAttribute is a mass-assignment surface

Spring instantiates the target with its no-arg constructor and calls a setter for every request parameter whose name matches a writable property. If the target is a JPA entity, that includes every field JPA requires a setter for — role, balance, tenantId, enabled. With no @Valid and no allowlist, POST /account?role=ADMIN binds the role and the attached-entity save flushes it: a privilege escalation, and CWE-915. Unknown parameters are silently ignored because WebDataBinder.ignoreUnknownFields defaults to true, so the attack leaves no error either. The durable fix is a build rule, not a review comment: an ArchUnit test banning any @Entity-annotated type in a controller signature.

// The right one: the type IS the allowlist
public record UpdateAccountCommand(@NotBlank @Email String email,
                                   @Size(max = 80) String displayName) { }

@PostMapping("/account")
public AccountDto update(@Valid @RequestBody UpdateAccountCommand cmd) { ... }

@InitBinder                                        // only if you must keep forms
void initBinder(WebDataBinder binder) {
    binder.setAllowedFields("email", "displayName"); // everything else rejected
}
Trade-off — a regex path variable is routing, not validation

{id:[0-9]+} looks like free input validation and is not. It gives you a 404 for a malformed id, not a 400 — the wrong status for a client mistake, which makes the API's error contract inconsistent — and it buries a parsing assumption in the URL space, where changing it later is a routing change rather than a validation change. Flips on: the traffic profile. It earns its place only when traffic is genuinely dominated by misses against a very large table, where rejecting in the router avoids a lookup. The default is {id}, parse it, and return a ProblemDetail 400.

Must remember — produces is a filter, not a cast

An incompatible Accept against produces yields 406 Not Acceptable — the handler simply did not match. Omit produces and Accept is effectively ignored, so you may return JSON to a client that asked for XML, and the failure appears in the client. A wrong Content-Type against consumes is checked before the method runs and gives 415.

Extension-based negotiation (/orders.json versus /orders.xml) was removed as the default in Spring 6; re-enable it explicitly through ContentNegotiationConfigurer or spring.mvc.contentnegotiation.favor-parameter. And the _method override — a hidden form field tunnelling DELETE through a POST — is a request-smuggling surface: the verb your WAF, your ingress controller and your audit log recorded is not the verb the application will execute, so anything authorising on the request line is bypassable and the audit trail lies. Scope it to browser-form endpoints and make sure the ingress layer applies the same override.

When a request 404s unexpectedly the debug log prints every condition and the mapping it tried. In likelihood order: a trailing slash (/orders/ does not match /orders unless setUseTrailingSlashMatch(true)), a produces the client's Accept cannot satisfy (but that is a 406, not a 404), or a greedy path variable.

04

Filters, interceptors & CORS

Three callbacks with genuinely different powers
CallbackCan veto?Sees the response?Runs on failure?Use for
preHandleYes — return falseNot yet writtenYes; nothing downstream runsAuth, tenant resolution, rate limiting, feature flags
postHandleNoOnly if not committedNoLegacy, pre-@ResponseBody. Use ResponseBodyAdvice instead
afterCompletionNoYes, and the statusYes, with the exceptionMetrics, MDC cleanup, auditing, always-run teardown

Interceptors run in ascending order for preHandle and descending for postHandle and afterCompletion. One registered without an order defaults to Ordered.LOWEST_PRECEDENCE, so it runs last among explicitly ordered interceptors — rarely what the author of a logging interceptor expects.

Interview trap — a preHandle veto means afterCompletion never runs

Returning false unwinds the chain; it does not complete it. No later preHandle runs, and afterCompletion runs only for the interceptors whose preHandle had already returned true — the vetoing interceptor's own afterCompletion does not run. An interceptor that opens a span or a resource in preHandle and closes it in afterCompletion therefore leaks it on every rejected request: a leak proportional to your rejection rate.

Interview trap — postHandle is nearly dead code in a JSON API

For a @ResponseBody handler the bytes are written inside the handler invocation, so by postHandle the response is committed and setStatus() or getWriter() throws IllegalStateException. That is why a reviewer's answer to “res.setStatus(401) in postHandle” is it cannot work. To alter a committed-soon response you need preHandle, the handler itself, or a ResponseBodyAdvice — the only component positioned before the bytes go out.

Scaling reality check — code after chain.doFilter is cleanup, and it needs a finally

The lines after chain.doFilter(...) run only on the way out, and only on the normal path. An MDC.remove() written there without a finally leaks the trace ID into whatever the container thread serves next; the symptom is a log line with two trace IDs and no way to tell which is which. Clearing at the top of the filter instead leaks the value into the previous request on the same thread.

public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)
        throws IOException, ServletException {

    String traceId = UUID.randomUUID().toString();
    MDC.put("traceId", traceId);
    ((HttpServletResponse) resp).setHeader("X-Trace-Id", traceId);
    try {
        chain.doFilter(req, resp);   // everything downstream
    } finally {
        MDC.remove("traceId");      // MUST be here, not after the call
    }
}
OncePerRequestFilter — the two hooks people forget
HookDefaultWhat it controls
shouldNotFilterErrorDispatch()trueWhether the filter runs on the ERROR dispatch — i.e. whether your trace ID and MDC exist on the error response
shouldNotFilterAsyncDispatch()trueWhether the filter runs again when the async cycle completes and the container re-dispatches
shouldNotFilter()falseWhole-URL opt-out, e.g. /actuator/health
Interview trap — “the filter runs once per request” is wrong twice

The container re-dispatches the same request to the same filter on the ERROR path and again on the ASYNC path, so a hand-written filter that counts requests, opens a span, or writes a header does so twice. OncePerRequestFilter exists for exactly this, using a request attribute as a latch. Its own trap is that both hooks default to true: leave shouldNotFilterErrorDispatch() alone and your error pages render with no trace ID; flip it to false and your counters double-count. Request attributes survive the async cycle even when the filter does not re-run, which is why request-attribute-based state is the safe thing to carry across.

Which layer for which concern
ConcernLayerWhy it bites elsewhere
CORSFilter (or addCorsMappings)A preflight OPTIONS is unauthenticated by definition, so anything that authorises first answers 401 and the browser reports a CORS error

Must remember — CORS is browser-enforced, and curl cannot test it

The server answers the preflight and the actual request; the browser decides whether to hand the response to JavaScript. “It works in Postman” therefore tells you nothing, and a browser console CORS error looks like a network failure with no message. The debugging path is always curl -X OPTIONS -H "Origin: https://app.acme.com" -H "Access-Control-Request-Method: GET" and reading the response headers. In likelihood order: the preflight is being rejected by the security filter chain before CORS runs; the origin is not in the allowlist; or allowCredentials(true) is combined with a wildcard origin, which the specification forbids — the browser then drops Access-Control-Allow-Origin entirely, and Spring 5.3+ throws at startup rather than failing silently. The correct form is allowedOriginPatterns("https://*.acme.com") or an explicit origin list.

Trade-off — three CORS mechanisms, pick one

@CrossOrigin is per-handler and easy to forget on a new endpoint, which is a silent failure rather than a loud one. addCorsMappings is global and easy to over-broaden. CorsFilter works below Spring MVC entirely and makes the ordering requirement explicit. Flips on: whether the ordering against the security chain is the thing that keeps biting you. The durable answer is a single CorsConfigurationSource bean referenced by both MVC and Spring Security — http.cors(withDefaults()) delegates — plus a build check that fails on any @CrossOrigin. Mixing mechanisms is what produces “works on /api/users but not /api/orders”.

@Configuration
class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/public/**", "/actuator/**")
                .order(1);      // lower runs first in preHandle, last on the way out
    }
}
05

Exception resolution

Exception handling in Spring MVC is a three-stage fallback, and knowing which stage fires tells you what shape the client sees. The resolver chain runs inside doDispatch — that single fact explains most of the surprises in this section.

The HandlerExceptionResolver chain, in order

ExceptionHandlerExceptionResolver@ExceptionHandler in the controller, then @ControllerAdviceYes — this is where your ProblemDetail comes from
ResponseStatusExceptionResolver@ResponseStatus on the class or method; ResponseStatusExceptionNo — status only, then sendError() → the container's /error
DefaultHandlerExceptionResolverSpring's own exceptions (see below)No — sendError(status), body rendered by /error

HttpMediaTypeNotSupportedException415No
HttpMediaTypeNotAcceptableException406No

MissingServletRequestPartException400No

Interview trap — one endpoint, two error shapes

A domain exception comes back as a clean RFC 7807 ProblemDetail; a malformed request comes back as {"timestamp":…,"status":400,"error":"Bad Request","path":…}. The reason is that the malformed request never reached the controller, so no @ExceptionHandler fired, and DefaultHandlerExceptionResolver only maps a status and calls sendError() — the body is then rendered by Boot's BasicErrorController at /error. Fix either way: handle ErrorResponseException and MethodArgumentNotValidException in a global advice, or replace BasicErrorController wholesale with your own ErrorController returning ProblemDetail for everything.

Must remember — the precedence rule, stated exactly

Controller-local @ExceptionHandler methods win over everything. Then @ControllerAdvice beans, most specific first — by exception-type depth, then by advice-bean @Order, lower first. Then the framework resolvers. The consequence that catches people: a catch-all @ExceptionHandler(Exception.class) in a controller silently disables every global advice handler for that controller. The correct place for a catch-all is the global advice, where it is one deliberate decision rather than one per controller quietly re-shadowing the last one someone wrote.

Must remember — the stack trace is a reconnaissance payload

Since Boot 2.3 the defaults are server.error.include-stacktrace: never, include-message: never and include-binding-errors: never. Teams turn them on for local debugging, leave them in an application-dev.yml, and that profile gets selected by a staging or canary pipeline — which is how internal class names, package structure, library versions and sometimes connection strings reach a pentest. include-binding-errors: always is the worse variant: it serialises every rejected field value from the BindingResult back to the client, which for a login form echoes the submitted password into the response body. The safe replacement for the debugging need is a correlation ID in a response header and in the logs, plus a config-lint rule that fails the build on any non-never value outside a strictly local profile.

@RestControllerAdvice
class ApiExceptionAdvice {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND,
                "No order with id " + e.getId());
        pd.setType(URI.create("https://api.acme.com/problems/order-not-found"));
        pd.setProperty("orderId", e.getId());   // stable machine-readable, not prose
        return pd;
    }
}

The three ProblemDetail properties worth fixing before the first client exist are a stable machine-readable type URI, a status that agrees with the HTTP status, and a detail safe to put in a log. The error body is a contract: every client parsing {"message": …} is a client to migrate, and teams that retrofit end up supporting both shapes forever, with the undocumented one being the one nobody maintains.

06

Validation

@Valid is a report generator, not a gate, and the method signature decides whether the report becomes a rejection. The rule stated exactly: the MethodArgumentNotValidException is thrown only when there is no BindingResult or Errors parameter immediately following the @Valid parameter. With one, Spring puts the errors there and calls your method.

// No BindingResult — the method NEVER runs on invalid input
public OrderDto create(@Valid @RequestBody CreateOrder cmd) { ... }

// BindingResult present — the method RUNS, errors are populated,
public OrderDto create(@Valid @RequestBody CreateOrder cmd, BindingResult errors) {
    if (errors.hasErrors()) {                   // and this check is not optional
        return ResponseEntity.badRequest().body(toProblem(errors));
    }
    return ResponseEntity.ok(orders.place(cmd));
}
Interview trap — the 200 on invalid input

This survives code review because the code looks validated. With a BindingResult parameter present, the invalid CreateOrder is fully bound and passed to your method anyway — the BindingResult is populated and then ignored, the service receives an object with a null email and a negative quantity, and the request returns 200 with a persisted bad record. Nothing throws, nothing is logged. A PR that adds BindingResult to “return nicer errors” has converted a 400 into a 200 unless the body checks hasErrors(). The process fix is structural: a shared helper that both checks and serialises, so the correct behaviour is the path of least resistance.

Two exception types, two sources, two defaults
MethodArgumentNotValidExceptionConstraintViolationException
Raised when@Valid on a @RequestBody parameter@Validated on the class, for method-level constraints
Comes fromArgument resolution → Bean Validation on the objectA CGLIB proxy around the bean
Default status400500 unless you map it
Where the errors areex.getBindingResult() — field errors, rejected values, nested pathsex.getConstraintViolations() — method-level only, no field-error structure
Needs a class-level annotationNoYes, @Validated — without it the constraint silently does not fire
Interview trap — a validation failure returning 500

Almost certainly ConstraintViolationException. Method-level parameter constraints — @Size(min = 3) on a @RequestParam — are enforced by a CGLIB proxy created by class-level @Validated, not by argument resolution, and ConstraintViolationException has no default status mapping. The input is plainly bad and the response is plainly wrong. Fix it with an @ExceptionHandler(ConstraintViolationException.class) returning a 400 ProblemDetail built from ex.getConstraintViolations(), and verify @Validated is on the class at all.

Trade-off — validation groups or one DTO per operation

Groups buy “one DTO, several operation profiles” without a proliferation of classes. The cost is that the constraint is no longer visible at the field: a reader of @NotBlank(groups = OnCreate.class) has to know which group the endpoint passes, and a group that is not passed silently does not run — no error tells you. Flips on: past roughly half the fields differing between operations, or whenever a constraint's applicability is non-obvious. Then separate request types are the better trade, and the deciding factor is the failure mode rather than the class count.

Must remember — the domain owns the invariant, the edge owns the shape

Duplicate the cheap shape checks — presence, format, range, parseability — at the edge, because they save a round trip and produce a good client error. Enforce every business rule in the domain, because a @Valid constraint in a controller is reached only by HTTP: a message consumer, a scheduled job, a data-fix script, a JPA callback, a test — none of them go through the controller, so none of them get the check, and “an order cannot ship before it is paid” is a statement about orders, not about HTTP. The inverse mistake is just as real: business rules only in the domain returning a ConstraintViolationException with HTTP-flavoured messages leaves a service untestable without a servlet, and clients get 400s for what are 409s.

07

Async, streaming & upload

Async is a thread-economics decision, not a syntax choice. Every async return type hands control back to the container and releases the request thread; they differ in who computes the result and when.

The async return types by thread cost
Return typeWho computes itThreads held while waitingUse for
Callable<V>A thread from a TaskExecutor, immediatelyOne, for the whole computationWork you can start right now — a report
WebAsyncTask<V>A thread from a specified executorOne, with an explicit timeoutThe same, when you need to control executor and timeout
DeferredResult<V>Any thread, at any timeZero — one only at setResult()A result produced elsewhere: JMS, a websocket, a poll
SseEmitterA thread, continuouslyOne container thread per connection, for its lifeServer-sent events
StreamingResponseBodyA thread writing to the output streamOne while writingLarge downloads, CSV export
Trade-off — Callable vs DeferredResult

Callable consumes an executor thread for the whole computation: 500 concurrent slow reports against a 100-thread executor means 400 of them queue, and the client-side wait is the same either way. DeferredResult consumes no thread while waiting and needs one only at the moment setResult() is called. Flips on: whether the work can start now. Choose Callable for work that is CPU- or blocking-bound and available immediately; DeferredResult for anything triggered externally, any wait that may be long, and any result that may never arrive. Returning a Callable for a JMS-delivered result is how an async executor gets exhausted and AsyncRequestTimeoutExceptions appear at 30 seconds.

Must remember — what returning an async type destroys

When the handler returns, the container thread goes back to the pool. Lost: the MDC and trace ID, RequestContextHolder and the LocaleContext, SecurityContextHolder under the default ThreadLocal strategy, and the transaction — which commits or rolls back at method return, so a database write attempted afterwards throws LazyInitializationException with no session to bind to. Kept: HttpServletRequest and HttpServletResponse attributes, and anything you explicitly propagated (TaskDecorator, Reactor context).

The discipline that follows: treat the return as the end of your access to thread-bound state, and capture the principal, tenant and trace ID into ordinary local variables or a DTO before that line. An audit log that loses the tenant on exactly the slowest endpoints is a genuinely painful incident to debug.

Interview trap — “why did it hang for exactly 30 seconds”

The async timeout is a separate timer that starts when the handler returns — not the servlet read timeout, which is a different 20s on a different clock. When it expires the container fires AsyncRequestTimeoutException, which DefaultHandlerExceptionResolver maps to 503 — but only if your @ExceptionHandler does not intercept it first, and only if the response is not already committed, in which case the client gets a truncated body instead of a clean error.

Scaling reality check — every SseEmitter is a container thread

At Tomcat's 200 default threads, 200 concurrent SSE clients consume the entire request pool and every unrelated endpoint starts timing out. The threshold that matters is concurrent connections, not total subscribers, which is why this works in a demo with three and appears six months later in production. Mitigations in order: set the emitter timeout to 0 so the container's async timeout does not reap connections, verify the connector is configured for it, and accept that the real fix at scale is a dedicated connector with its own executor, a dedicated thread, or moving the connections to a gateway. A ResponseBodyEmitter returned alongside a DeferredResult is the alternative that does not pin a thread for the wait.

Must remember — upload limits and the 500 that should be a 413

MaxUploadSizeExceededException defaults to 500 for what is plainly client input being too large. It needs an explicit @ExceptionHandler mapping it to 413 — and in some container configurations the limit is enforced at the connector and the exception never reaches the resolver chain at all, so the limit has to be raised there too.

On spring.servlet.multipart.file-size-threshold: Boot's default is 0, which writes every part to a temp file on disk and never holds user-uploaded bytes in heap; Tomcat's own default of 256KB keeps parts under 256KB in memory. A 0-byte or 4KB upload still gets a temp file created, deleted, and marked for deletion on JVM exit — the known mechanism behind temp-file accumulation across deploys in long-running containers. Do not “optimise” the threshold upward: that is precisely the change that puts user bytes in heap.

Must remember — outbound timeouts are a chain budget

A request arrives with a 5-second deadline. Authentication takes 100ms, local processing 50ms, and one downstream client configured with connectTimeout(2s) plus readTimeout(5s) can consume 7 seconds on that one call. The worst case is ~12 seconds against a 5-second deadline: the caller has already gone, and you held a thread for 7 extra seconds — a slow dependency converted into a throughput problem. Derive each hop from the remaining budget: a connect timeout around a tenth of the caller's deadline, a read timeout equal to what is left after the time already spent, and the deadline propagated as a header so downstream hops do the same arithmetic. Never let readTimeout exceed what the caller is willing to wait.

Production decisions

Take a thread dump before deciding anything

Running out of threads is a symptom with three distinct causes, and only one of them is fixed by going reactive. Threads parked in SocketInputStream: one downstream has degraded and is consuming the pool — a per-hop timeout plus a circuit breaker (Volume 11) makes the failure fast rather than cumulative. Threads in a pool queue: the pool is starved, not hot. One thread genuinely working: no concurrency bug, just slow work. The absence of a log line for refused requests, with p99 exploding at exactly 200 concurrent, is a maxThreads wall.

Trade-off — is WebClient worth introducing in a thread-per-request app?

Generally no, and the reason is precise: the container is still giving you one thread per request, so .block() on a reactive client inside a servlet controller is blocking throughput with reactive complexity and none of the benefits. Flips on three situations — the application is already reactive (Volume 10), one endpoint's latency is dominated by a sequential chain of downstream calls that should be a fan-out, or a large fan-out is genuinely I/O-bound. The organisational cost is real: WebClient's error model and interceptor contract differ enough that a mixed codebase ends up with two error-handling conventions. Note the paired difference: RestTemplate throws on 4xx and 5xx, while WebClient signals an error as a value on the stream.

Interview trap — RestClient is not reactive, and not "non-throwing"

Three clients, not two. RestClient is @since 6.1 and is the modern synchronous API — its own javadoc says "a fluent, synchronous API", and it has no Mono or CompletableFuture surface at all in 6.2.x. RestTemplate's javadoc points async callers at WebClient, not at RestClient.

It also throws on 4xx/5xx by default, exactly like RestTemplate. What differs is granularity: RestTemplate has one global ResponseErrorHandler on the instance, RestClient has a per-request retrieve().onStatus(...) chain, user handlers inserted before the defaults, first match wins. The one place it genuinely does not throw is exchange(), which bypasses status handling by design because your lambda gets the raw response.

And RestTemplate is not @Deprecated in 6.2 — "maintenance mode" is not in the source. It says only that RestClient "is the focus for new higher-level features". Supersession, not deprecation. RestClientAdapter is also not a RestTemplate bridge (RestClient does not implement RestOperations); use RestClient.create(RestTemplate) to carry config across. Boot 3.2+ auto-configures a prototype-scoped RestClient.Builder. Full treatment in Volume 5 §7.5.

Trade-off — should the two contexts be collapsed?

Usually yes, and not for performance. Two contexts mean two component scans, two @ControllerAdvice searches, a whole class of “why can't I inject this” bugs that have nothing to do with injection, and a parent/child visibility rule every new joiner has to learn. Flips on: genuine multi-servlet or multi-dispatcher setups, where a separate child context is how you give one servlet a different set of view resolvers or message converters. The decision should be written down deliberately, not inherited from a legacy XML config nobody has deleted.

One diagnostic worth memorising: method security is a proxy, and its cost is whatever the AuthorizationManager does — a PermissionEvaluator loading permissions from the database on each call, or a @PostAuthorize dereferencing a lazy association. An endpoint going from 40ms to 900ms after @PreAuthorize is added to a controller class, with no database or network change, is almost always that — and because it sits outside the method body it never appears in the endpoint's own profiling.
