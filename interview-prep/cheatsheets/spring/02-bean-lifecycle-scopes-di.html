Volume 2 — Bean Lifecycle, Scopes & Advanced DI

At what exact moment does this code run, what created it, and what happens if it runs at the wrong moment? Almost every failure in this volume is a phase error or a provenance error.

If you only remember five things

  1. @PostConstruct runs BEFORE afterPropertiesSet(), and @PreDestroy runs BEFORE destroy(). Destruction is not the reverse of creation. Both annotation hooks are fired by CommonAnnotationBeanPostProcessor from a post-processor pass, not by the container — one inside postProcessBeforeInitialization, one inside the DestructionAwareBeanPostProcessor pre-pass.
  2. singleton is the only scope the container manages past construction. A prototype is built, handed out, and forgotten: no reference, no DisposableBeanAdapter, no destruction callback, ever. And a prototype injected into a singleton gives you exactly one instance, because the singleton's constructor ran once.
  3. BeanFactoryPostProcessor sees definitions; BeanPostProcessor sees instances. That is the whole distinction. Scope, lazyInit and qualifiers live on the BeanDefinition, so a post-processor that tries to change them has already lost.
  4. Constructor injection cannot participate in cycle resolution. this is not assigned until the constructor body completes, so there is no instance to hand out. Setter and field can, through the three-level cache — and a working field-injected cycle is a design error running, not a solved problem.
  5. Prefer ObjectProvider<T> to a scoped proxy. The provider is explicit, allocates nothing, and says "resolved late" in the code; the proxy is indistinguishable from a singleton at the injection point and pays a ThreadLocal plus map lookup on every method call.

No section matches that filter.

01

The full bean lifecycle

Every singleton is built by AbstractAutowireCapableBeanFactory.doCreateBean(), which is roughly 300 lines of callback dispatch. The order below is fixed, all of it runs in phase 3 of refresh(), and none of it runs in the order your eye reads the file in. Step 7 is where the AOP proxy is born — so nothing before it can be intercepted by your own aspects. Volume 3 takes that one hook and follows it; here it is an ordering fact and nothing more.

@Component
public class OrderService implements InitializingBean {

    @PostConstruct
    void postConstruct() {
        // STEP 4 — fired from inside CommonAnnotationBeanPostProcessor,
        // so it runs BEFORE afterPropertiesSet(), and before the proxy exists
    }

    @Override
    public void afterPropertiesSet() {
        // STEP 5 — dispatched by the container
    }

Interview trap — the two orderings nobody remembers

@PostConstruct runs before afterPropertiesSet(), and @PreDestroy runs before destroy(). The reason is structural rather than conventional, and naming it is the answer: @PostConstruct is not a callback the container calls, it is invoked from inside CommonAnnotationBeanPostProcessor.postProcessBeforeInitialization() — a BeanPostProcessor firing an annotation, one dispatch layer below invokeInitMethods(). The mirror is DestructionAwareBeanPostProcessor.postProcessBeforeDestruction(), which AbstractAutowireCapableBeanFactory runs before it ever reaches the DisposableBeanAdapter. A candidate who says "reverse order" has memorised a symmetry the implementation does not have.

// DisposableBeanAdapter.destroy(), simplified
if (bean instanceof DisposableBean) {
    ((DisposableBean) bean).destroy();          // 1 — and ONLY this
} else if (bean instanceof AutoCloseable) {
    ((AutoCloseable) bean).close();             // 2 — the branches are exclusive
}
if (customDestroyMethodName != null) {
    invokeCustomDestroyMethod();                 // 3 — outside the if / else if
}
Must remember — three rules inside the adapter

The else if is exclusive; the custom method is not. A bean implementing DisposableBean does not get close() from the adapter — only the custom destroy-method, if you declared one. A bean implementing only AutoCloseable gets close() and nothing else.

@Bean(destroyMethod = "") disables the inference. By default Spring infers a close() or shutDown() method on a @Bean return type and registers it — so a @Bean method returning a type with a public close() gets a shutdown callback you never wrote. Set it to "" when the framework, not Spring, owns that lifecycle.

The container's shutdown has no default timeout. A destroy() that blocks on a 60-second HTTP call makes every pod take 60 seconds to terminate, and most orchestrators SIGKILL you first. Bound your own wait.

Trade-off — @PostConstruct or afterPropertiesSet?

In your own code, use @PostConstruct. It is the JSR-250 standard, refactoring tools understand it, it does not make your class implement a Spring interface, and it composes with containers other than Spring's. Flips on: you are implementing a framework contract that declares InitializingBean — Spring uses it internally on FactoryBean support and AOP infrastructure, and there you have no choice. Know that in that case your method runs after every @PostConstruct in the same class.

Interview trap — @PostConstruct calling a @Transactional method

It does not run in a transaction, and nothing fails. The proxy is created in postProcessAfterInitialization, the last step of all — two steps after @PostConstruct has already run, so this is not even a self-invocation question. The correct answers are a TransactionTemplate used explicitly, or a call into another bean whose method is transactional. The same applies to @PreAuthorize and to any custom metric aspect: you cannot rely on your own aspects intercepting your own initialisation callbacks. Volume 3 owns the full list of proxy bypasses.

02

Post-processors: definitions vs instances

Two extension points, one distinction, and almost every post-processor that "does nothing" has misread which one it is. The sentence that settles nearly all of it: a BeanFactoryPostProcessor runs before beans exist and therefore cannot see one; a BeanPostProcessor runs once per bean and therefore cannot see the whole graph.

The decision, framed as what each one can see
ConceptBeanFactoryPostProcessorBeanPostProcessor
SeesBeanDefinitionsLive bean instances
RunsOnce, at refresh step 4Once per bean, as it is created
Mutate scope / lazy / qualifiersYesNo — too late by definition
Register new definitionsOnly via the registry subclassNo, ever
Return a substitute objectNoYes — postProcessAfterInitialization
Typical userRare — you almost never write oneCommon, and dangerous

The same phase split decides something subtler. ConfigurationClassPostProcessor is itself a BeanDefinitionRegistryPostProcessor — it runs in phase 1 and its output is bean definitions, which is why turning @Configuration into definitions is a registry post-processor's job. Whether the class is then full or lite is recorded as a flag on the ConfigurationClass in that same phase, while the CGLIB subclass is installed by ConfigurationClassEnhancer in phase 2 and applied in phase 3. Three phases, one behaviour, and the observable difference is a second instance that no log line mentions.

What puts a @Configuration class into lite mode
ConditionResultHow it bites
proxyBeanMethods = falseLite — no CGLIB, no self-call interception A @Bean method calling its own method directly constructs a second, unmanaged instance. No warning, no log line
The class is finalLite, automatically Silently the same trap — the flag you never wrote
A @Bean method is private or finalLite Same, and it reads as a compiler error you thought you'd avoided
No intra-config calls at allLite Harmless — this is the case lite mode exists for
Interview trap — "set proxyBeanMethods = false, it is faster"

It is faster, and it is correct, and it is also the single most common cause of "this works in integration tests and behaves differently in production for no reason anyone can find" — because the two instances differ only in identity, so a transaction annotation, a lock or an identity-map lookup quietly applies to one of them and not the other. The safe idiom is to take collaborators as parameters rather than calling your own methods, which is correct in both modes. The related trap in the same phase: a @Bean method may only be non-static if the config class is not itself used by another @Configuration class; two config classes calling each other's @Bean methods is the case that produces "Bean method 'x' is non-static and returns an object of type 'y'".

@Configuration
public class MetricsConfig {

    @Bean                                    // static is MANDATORY
    public static MetricsBeanPostProcessor metricsPostProcessor() {
        return new MetricsBeanPostProcessor();
    }
}
Must remember — why static is mandatory

To register post-processors the container calls getBean() on the @Bean method during registerBeanPostProcessors(). A non-static method needs an instance of the configuration class, and creating that instance means running it through a BeanPostProcessor chain that is not yet assembled. The result is a BeanCurrentlyInCreationException or a BeanPostProcessorChecker warning: "Bean 'xxx' is not eligible for getting processed by all BeanPostProcessors." The checker exists precisely because this is the single most common authoring mistake for the extension point.

Interview trap — "what order do post-processors run in?"

There is no guaranteed order, and asserting one costs the point. The rules that do hold: PriorityOrdered first, then Ordered, then registration order within each group — and registration order is getBeanNamesForType over the registry, not your source file order. postProcessBeforeInitialization runs in registration order; postProcessAfterInitialization runs in reverse, so a later-registered wrapper ends up outermost. If your behaviour depends on it, implement PriorityOrdered and say so.

The related failure: a library's PriorityOrdered processor displacing CommonAnnotationBeanPostProcessor takes @PostConstruct application-wide. That, or a processor throwing in postProcessBeforeInitialization for a bean it does not understand, which aborts the entire refresh rather than one bean. Diagnose with --debug plus DEBUG on org.springframework.beans.factory.support.

Two smaller traps with the same root cause. Returning null from postProcessAfterInitialization is not a no-op — it registers a NullBean, and injection fails with NullBeanException or a misleading "expected single matching bean but found 0". And factory.addBeanPostProcessor(...) on a live factory only sees beans created after the call; register it first or the call does nothing.

03

Bean scopes

There are five scopes and one rule that generates most of the confusion: singleton is the only scope the container manages past construction. Everything else is the container handing you an object and then forgetting about it. That single fact explains the prototype-into-singleton trap, the absence of prototype destruction, and the request-scope exception on background threads.

Must remember — prototypes are never destroyed

There is no configuration flag to enable one, and the reason is structural rather than an omission: for a singleton the container holds singletonObjects plus a DisposableBeanAdapter, and iterates both at close(). For a prototype it holds nothing — no list, no adapter, no name. The phrase "the container manages the prototype's lifecycle" is wrong. What it manages is only the act of construction.

The follow-up that separates candidates: "so what is a prototype's difference from just calling new?" The honest answer is almost none, except that a prototype still gets injection, post-processing and proxying. In order of preference: don't hold resources in a prototype (make it a singleton with a real lifecycle); use request scope for genuinely per-request resources; or implement AutoCloseable and use try-with-resources at the call site, which requires an ObjectProvider rather than a direct injection.

Interview trap — a scoped proxy is not free

"It's just a proxy, so it costs nothing" is the wrong answer. The cost is a target lookup per method invocation, and for request scope that is a ThreadLocal dereference plus a map access. A service with 20 methods called 50 times per request pays 1,000 lookups a singleton would not. Worse, the proxy masks the substitution completely: the injected object is a CartService subclass, so instanceof checks and method resolution all still work and the swap is invisible in code review. It also simply fails for types CGLIB cannot subclass — a final class, a class with final methods, anything that gets serialised.

Trade-off — when request scope is the wrong tool

request scope buys a hidden dependency: the class no longer names the collaborator, no constructor mentions it, and no unit test can construct the class without a RequestContextHolder setup. It is right when the object's identity is request-bound — the security context, the current locale, a per-request idempotency token. Flips on: the moment the value could legitimately change mid-request. A request-scoped bean is frozen at first resolution for the remainder of the request, so if the answer is yes, pass it as a parameter. The test: "if you could pass this as an argument, would you?"

Two more traps that share a cause. Resolving a request-scoped bean from a @Scheduled method, an ApplicationRunner or an @Async task throws IllegalStateException: No thread-bound request found — the application being a web application is irrelevant; the thread has no RequestAttributes. And capturing a request-scoped bean in a singleton field produces no exception at all, just one user's data served to another; the proxy exists precisely because it re-resolves per invocation. Any object from a web scope must be used on the thread it came from — passing it to CompletableFuture.supplyAsync or a message listener is a correctness bug even when it does not throw.

Jakarta Validation is a specification; Hibernate Validator is the reference implementation and the one Boot pulls in. The annotations people misuse most are below, and the BindingResult one is the single most consequential bean-validation bug in Spring MVC — because it is exactly backwards from the intuition.

// No BindingResult — MVC throws MethodArgumentNotValidException, so you get 400
@PostMapping("/orders")
public Order create(@Valid @RequestBody CreateOrderRequest request) { ... }

// With BindingResult — the exception is SUPPRESSED; you own the check
@PostMapping("/orders")
public String create(@Valid CreateOrderRequest request, BindingResult errors) {
    if (errors.hasErrors()) { return "orders/new"; }   // nothing else will
    service.create(request);
    return "redirect:/orders";
}
Interview trap — the parameter that turns off the 400

ModelAttributeMethodProcessor only throws MethodArgumentNotValidException when the handler has no immediately-following BindingResult or Errors parameter. Add one and the exception is suppressed entirely: the violations are collected into the BindingResult and the method body runs with invalid input. A find-and-replace that adds the parameter for form repopulation is enough to turn POST /orders into an endpoint that persists a null customer and returns 201. The prevention is four lines: an ArchUnit rule forbidding BindingResult on @RestController methods.

Two more — blank strings, and constraints that do I/O

Any string arriving from outside your process that identifies something is @NotBlank, not @NotNull. The diff looks equivalent, the review passes, and the failure is a database row with a blank customer ID three weeks later. And @NotEmpty List<@NotNull String> is what means "at least one element, and no element is null" — container element validation is type-use syntax, supported since Jakarta Validation 2.0.

A constraint that hits the database turns a 400 into an outage vector. Constraints are expected to be pure, synchronous and fast. A rule requiring a lookup — does this SKU exist, is this IBAN valid — belongs in the service layer in the same transaction as the write, returning a domain exception. Keep bean validation about shape, keep referential integrity in the domain. The other half of the custom-validator contract that experienced reviewers check: isValid returns true for null so nullability stays with @NotNull, and disableDefaultConstraintViolation() is called before adding a custom template, or every violation arrives with two messages.

The deeper argument is about entry points, not elegance. A rule expressed only on an inbound DTO protects exactly the paths that go through MVC argument resolution — a batch import, a message consumer, a scheduled reconciliation job, a data migration and a test calling the service directly all bypass it. The review question is never "is the annotation right"; it is "how many entry points exist, and which of them enforce this?" The exception is configuration, where failing at startup is unambiguously right: @Validated on a @ConfigurationProperties class turns a wrong value into a BindValidationException during refresh that an operator sees immediately, rather than a production crash when the reading code path first runs.

05

Dynamic registration & FactoryBean

@Import comes in three forms with genuinely different powers, and the one distinction that matters in review is that an ImportSelector cannot register a bean definition — it returns strings that are then processed as configuration classes. For a definition, you need ImportBeanDefinitionRegistrar. This is also the mechanism every starter uses: Boot's AutoConfigurationImportSelector is Form 2 exactly, which is why a starter's beans arrive without you importing anything.

Three forms of @Import

A configuration classA classAs a configuration classOrdinary modular config — the default

public class SqlClientFactoryBean implements FactoryBean<SqlClient> {

    @Override public SqlClient getObject() { return new SqlClient(dataSource); }

    // The PRODUCT type, not the factory class — or type injection fails
    @Override public Class<?> getObjectType() { return SqlClient.class; }

    @Override public boolean isSingleton() { return true; }   // default
}
Interview trap — FactoryBean is not "for complex objects"

The common answer misses the point: a FactoryBean and a @Bean method are the same mechanism — the container wraps a @Bean method in one. The only reason to write the class form is that you are writing a library whose configuration is described by name rather than by code, so the indirection has to be a type. In application code it is a @Bean method written the long way, plus a getObjectType() contract you must get right.

Three more facts about that contract. Type matching uses getObjectType(), so returning the factory class makes the bean invisible to type injection — the failure is NoSuchBeanDefinitionException for a bean that is plainly registered and visible in getBeanDefinitionNames(). getBean("&sqlClient") returns the factory; the unprefixed name returns the product, and that & convention is obscure enough to be worth being able to explain rather than merely recognise. And isSingleton() is a claim, not a guarantee — returning false calls getObject() on every lookup, which is a FactoryBean re-expressing prototype scope and inheriting every problem, including no destruction. Finally, getObjectType() may be called before the factory is fully initialised, so touching its own @Autowired field there is a BeanCurrentlyInCreationException.

The programmatic levels differ in one way that causes silent failures. registerBean(Class, Consumer<BeanDefinition>) goes through the container; registerSingleton(name, instance) takes an already-constructed object and therefore bypasses the entire BeanPostProcessor chain — no @PostConstruct, no afterPropertiesSet, no init method, no AOP proxy, no exception translation — and never appears as a BeanDefinition, so it is invisible to tooling that inspects definitions. Correct for infrastructure you built yourself, a trap for anything carrying Spring annotations.

Trade-off — and the number at which it stops working

Registration buys real things: per-tenant configuration bound at startup, and startup-time validation that a failure is at deploy rather than at the first request from a customer you cannot reach. The cost is linear and the constant is not small, because each tenant's beans are a graph — 100 tenants is 200 beans and +2–5s of refresh; 1,000 is 2,000 beans and +20–50s; 10,000 is 20,000 beans and +3–8 minutes with OOM risk, around 2 GB. Flips on: whether the tenant's object graph genuinely differs, or only the implementation of one interface — and the second is overwhelmingly the more common case. The tell that you have misdiagnosed it is a registrar whose registered beans are all the same type. The failure mode to raise unprompted is the third option teams drift into: per-tenant beans and a runtime override, which gives startup validation for some tenants and none for others with no way for a reader to tell which is which.

06

Resources & the environment

Volume 1 owns the Resource abstraction and the context hierarchy, and @Value SpEL syntax. What is left here is what costs real money, and all three items below produce the same symptom: works locally, wrong in production, no stack trace pointing anywhere useful.

classpath: vs classpath*:
PrefixResolutionUse whenHow it bites
classpath:First match, then stopA single well-known resource you own Silent — a dependency shipping the same path wins and your copy is never read
classpath*:Every match across every jar, via getResources() Migrations, locale bundles, auto-config metadata — where several artifacts may legitimately contribute O(resources), re-walked on every resolution unless you cache it. Ordering is classloader order, not alphabetical
 
@Bean
MessageSource messageSource() {
    var ms = new ReloadableResourceBundleMessageSource();
    ms.setBasename("classpath:messages/messages");
    ms.setDefaultEncoding("UTF-8");
    ms.setFallbackToSystemLocale(false);   // THE setting people miss
    return ms;
}
Scaling reality check — where slow startup actually lives

classpath*: resolution is a top-three suspect for unexplained startup cost, alongside component-scan breadth and eager I/O in @PostConstruct — and the expensive scan is almost never in the team's code. It is in a starter, contributed by a transitive dependency. The canonical case: startup went from 8 seconds to 55 after a routine upgrade, with 41 of those seconds inside ConfigurationClassPostProcessor and template resolution, hitting 14,000 classes — because the new library added a scan that did not exist in the previous version. The prevention is not a faster container but a startup-time baseline in CI that alerts on a regression ratio, not an absolute number: a 40-second startup at 4× baseline is a real signal; the same 40 seconds at 1.05× is not.

Two traps, one symptom

Properties.load(InputStream) decodes as ISO-8859-1 — by specification, since Java 1.0, and it has never changed. A UTF-8 file with a € sign or an accented character comes out mangled, and the keys containing non-ASCII stop matching too. The fix is PropertiesLoaderUtils.loadProperties(resource, "UTF-8"), or an InputStreamReader with an explicit charset. The reason some files work and others do not: \uXXXX escapes are immune to encoding entirely.

setFallbackToSystemLocale at its default of true falls back to Locale.getDefault() — the JVM's locale. In Docker LANG is frequently unset, so that is en_US for every request, and a request for de missing a key silently resolves against English instead of failing. The third candidate cause of the same symptom is classpath: resolving a dependency's copy of the bundle. All three are invisible without reproducing the container's locale and classpath.

One more thing worth knowing about SpEL: the senior question is not the syntax, which Volume 1 covers, but the reach. It is evaluated in @Value, in @PreAuthorize, in @Profile and in @Conditional, and in every one of them the security property is identical: the expression stays a constant in the annotation and the data is bound to a parameter. Concatenating an untrusted value into an expression is code-execution class — Volume 8 owns the authorisation mechanics.

Circular dependencies

Which injection styles can participate in a cycle
StyleCycle resolvable?Why
Field @AutowiredYesThe instance exists before population — it can be handed over mid-population

// FIX A — extract the third object both sides actually share
@Service
class OrderService {
    private final PricingRules rules;             // both sides need THIS
    public OrderService(PricingRules rules) { this.rules = rules; }
}

// FIX B — @Lazy injects a PROXY; the failure moves to first use
@Service
class RuleEngine {
    public RuleEngine(@Lazy OrderService orders) { this.orders = orders; }
}
Must remember — field injection hides cycles, it does not solve them

The three-level cache makes a setter/field cycle work, and that is exactly the problem: a working cycle is invisible. Nobody gets an exception, so nobody investigates. The class is genuinely un-constructible in isolation, new A(b) and new B(a) are mutually impossible, and the only reason the application runs is that the container will hand out half-built objects. Every test that constructs these with a mock gets a different object graph than production. In review the finding is not "add @Lazy" — it is "this class cannot be constructed without a container, and that is a design problem hiding behind a runtime mechanism."

Trade-off — is @Lazy the right fix?

Sometimes, and it is better than the alternatives when the cycle is real. But it does not remove the cycle: the injection point receives a proxy, so the BeanCurrentlyInCreationException moves to the first call rather than going away, a proxy is allocated at every injection point, and every call becomes a virtual dispatch. ObjectProvider<T> is better where you can use it, because it allocates nothing and is explicit about the timing. Flips on: whether the cycle is genuine. If two classes need each other, they usually both need the same third thing, and naming it is the refactor. The genuine exception is a bidirectional JPA association — there the cycle lives in the entities, is resolved by the persistence context rather than the container, and the right move is to keep it out of the bean graph entirely.

Interview trap — why Boot 2.6 turned cycles off

Because they were working, and working cycles are worse than broken ones. The concrete failures: a bean obtained as an early reference may never have had its @PostConstruct run and may never have been proxied, so a @Transactional bean in a cycle is silently non-transactional for exactly the callers inside the cycle — intermittent, correlated with the call path rather than with load, and indistinguishable from a connection-pool problem. And the cycle itself survives refactors until someone converts field injection to constructor injection, which is what happened to thousands of teams on 2.6. spring.main.allow-circular-references=false is now the default.

Do not "fix" it with spring.main.lazy-initialization=true. Nothing is created during refresh, so no cycle is hit and startup passes — and the cycle is now deferred to the first request that touches it. Startup no longer validates the object graph, a cold instance in a scale-up serves its worst latency exactly when the system is stressed, and a BeanCurrentlyInCreationException surfaces as a 500 in production instead of a failure in CI. It is a diagnostic — turn it on, see whether startup improves, learn whether the cost is in eager initialisation — never the fix.

One debugging note that catches people: the exception names where the loop closes, not where it started. A cycle that was resolvable via field injection becomes a hard failure the moment either side is converted to constructor injection, so look at recent injection-style changes — and at recent proxyBeanMethods = false changes, which have the same effect on intra-config cycles. A bean that has not changed in two years is not evidence that it is not the problem.

08

Failure modes

The scenario bank for this volume has one theme running through it. Almost every failure is a phase error or a provenance error: code ran at the wrong point in the lifecycle, a bean was Spring's when you thought it was yours or the reverse, a value was captured at construction when you assumed it resolved at use, or a proxy was assumed to be in the call path when it was not. The candidates who stand out ask "which phase is this in?" before answering, and can say why the container behaves as it does rather than only that it does.

Scaling reality check — a 25-second refresh

With 3,000 beans and a 25-second refresh, audit the @PostConstruct methods and non-lazy @Bean methods doing I/O first: they all run in finishBeanFactoryInitialization() and they run serially on the refresh thread, so a @PostConstruct making three HTTP calls at 200 ms each is 600 ms per bean. Then the SmartInitializingSingleton implementations, which are a single serial batch by definition, and only then classpath resolution. The probe timing separates the two causes before you open a profiler: a slow startup delays readiness measurably, while a slow first request delays nothing until traffic arrives. Do not reach for spring.main.lazy-initialization as the fix — it moves a startup failure into a first-request failure, which is the same trade as section 7's, for the whole application.
