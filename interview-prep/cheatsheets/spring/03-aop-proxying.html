Spring — The Spring Complete Deep-Dive

Volume 3 — AOP & Proxying

Why @Transactional, @PreAuthorize and @Async quietly do nothing: a proxy, a pointcut that is a string, and an advice chain that has to be in the call path.

  • 8 sections
← Prev Next →

If you only remember five things

  1. Spring AOP proxies; it does not weave. It can only intercept a call that arrives through a proxy, on a Spring-managed bean, through a method that is not private, static or final. Every limitation in this volume is that one fact seen from a different angle.
  2. JDK proxy if the target implements an interface, CGLIB otherwise — DefaultAopProxyFactory decides, and proxyTargetClass overrides both. Since Boot 2.0 spring.aop.proxy-target-class defaults to true, which bought concrete-type injection and cost you final as a real constraint.
  3. Self-invocation never reaches the proxy. Inside a method this is the target, so this.advised() silently skips @Transactional, @PreAuthorize, @Async and @Cacheable. Fix it by extracting the advised work into its own bean, not by self-injection.
  4. A pointcut is a string, not a symbol. Rename an advised method and the behaviour disappears with no compile error, no warning and no failing test — and if the pointcut carried @PreAuthorize, the endpoint is now open to anyone.
  5. Lower @Order value means higher precedence, outermost, first in and last out. @Transactional defaults to LOWEST_PRECEDENCE, so it is innermost — and anything recording a durable outcome must sit outside it.

No section matches that filter.

01

Vocabulary & the one fact

The interview asks for all seven terms, and the trap is that most candidates can define them and almost none can say which of them Spring AOP actually supports. The senior answer is the third column, not the second.

No build step is why AOP works in a plain main(), a JUnit test and a GraalVM native image, where an agent is a serious problem. The costs are the price: pointcuts are strings, so a rename is a silent behaviour change, and the proxy is a different object, so identity and stack traces change too.

Interview trap — "Spring AOP uses AspectJ"

It is the answer that loses points, and it is wrong in the direction that matters. Spring borrows AspectJ's language — the @Aspect model and execution(...) — on top of a Spring-implemented proxying mechanism. The precise version: it inherits AspectJ's expressiveness at the pointcut level and none of its power at the interception level.

The follow-up is the real question: when would you use AspectJ? When you must advise something Spring AOP cannot reach — a new-ed object, a self-invocation, a static method, or a third-party jar — and you can accept the agent. That is a real answer in a legacy codebase of static helpers; it is rarely right in a greenfield app, where extracting an interface is cheaper than an agent.

Must remember — the whole volume in one sentence

Spring AOP can only intercept a method call on a Spring-managed bean, arriving through a proxy, on a method that is not private, static or final. If any one of those fails, the advice does not run and nothing tells you.

When AOP is the wrong tool, and what to do instead
TargetWhy Spring AOP cannotDo instead
An object you new yourselfNothing creates a proxy for itMake it a bean; inject it
A static methodInstance proxies cannot intercept staticsMake it an instance method on a bean
A private methodThe proxy is a different classWiden, or move the caller out of the class

Trade-off — aspect or decorator

A decorator costs a constructor parameter, a class, and a line at every call site; the aspect costs nothing at the call site and gives a behaviour no reader of the target class can see. Flips on: use the decorator when there are few call sites and the wrapping is part of that call's semantics — use the aspect when the concern is genuinely uniform across dozens of sites and nobody could reasonably want it applied differently to one of them. A team reaching for @Aspect to avoid writing a constructor is trading a compile-time cost for a runtime one.

02

The proxy mechanism

// DefaultAopProxyFactory.createAopProxy() — the whole decision
public AopProxy createAopProxy(AdvisedSupport config) {
    if (config.isOptimize() || config.isProxyTargetClass()
            || hasNoUserSuppliedProxyInterfaces(config)) {
        Class<?> targetClass = config.getTargetClass();
        if (targetClass.isInterface() || Proxy.isProxyClass(targetClass)) {
            return new JdkDynamicAopProxy(config);   // must fall back: cannot subclass
        }
        return new ObjenesisCglibAopProxy(config);
    }
    return new JdkDynamicAopProxy(config);
}

The fallback is the part candidates miss: if the configured target is itself an interface or another proxy, CGLIB is requested and refused, so the factory falls back to the JDK proxy. The rule is one line; the surprises are all downstream of it.

Interview trap — the ClassCastException that starts an outage

A facade injects OrderServiceImpl by its concrete type. That works with no AOP at all. The moment someone adds @Transactional, an aspect or @PreAuthorize to it, the container wraps it in com.sun.proxy.$Proxy42 implementing only OrderService — and startup fails with $Proxy42 cannot be cast to OrderServiceImpl.

What makes it nasty: the code that broke did not change. A teammate annotated a class in a different module, and the stack trace points at the consumer, not at the class that was annotated. Program to interfaces — that is not a style preference here, it is the difference between a bean that can be proxied and one that cannot.

Must remember — Boot 2.0 changed the default

Since Spring Boot 2.0, spring.aop.proxy-target-class defaults to true, forcing CGLIB even when interfaces exist. It bought concrete-type injection keeping working, effectively killed that ClassCastException class of failure, and preserved generic resolution. It cost you: final classes, methods and private methods became load-bearing constraints rather than style nits — the set of things that break got wider — and CGLIB proxies are not serializable even when the target is.

The follow-through is to treat final as a prohibited annotation on Spring beans and enforce it with ArchUnit, because the failure mode is a silently un-advised method, not a compile error.

Return values travel back up the chain, so the outermost interceptor's post-processing runs last. That single fact is the whole of the ordering chapter, and it is also why the terminal dispatch being reflective is the performance floor: a ReflectiveMethodInvocation is allocated per call, plus any argument array.

Scaling reality check — what an advised call costs

Reflective dispatch is roughly 20–50ns per hop on a warm JIT against a direct call at ~1–2ns, so three aspects is roughly 3–5× the dispatch cost of an unadvised call. That is irrelevant for a method that touches a database and decisive for one doing real work in memory.

The threshold: above roughly 50,000 calls/second and below roughly 50 microseconds of body, the proxy overhead is measurable — a hand-rolled permission check, a hot-path cache lookup, a serializer at 200,000 calls/second. The fix is to move the hot path behind an explicitly constructed collaborator, not to strip the aspects, because the aspects are usually there for correctness.

TargetSource — the proxy is a stable handle onto a changing object

SingletonTargetSourceThe same target every callThe normal case
PrototypeTargetSourceA new target per callPrototype scope
ThreadLocalTargetSourceA target bound per threadHow request-scoped state works

This indirection is what makes scoped proxies possible at all. It also explains the constructor constraint in the table above: the proxy mechanism needs a proxyable type — a non-final class with a reachable constructor, or an interface. The factory instantiates CGLIB proxies through Objenesis, so a class with only package-private constructors cannot be advised, and resolution visibly slows on deep hierarchies because method lookup walks them.

Must remember — is this bean proxied, and how do I tell?

AopUtils.isAopProxy(bean) is the reflexive answer and it is incomplete — it says a proxy exists, not what it is. The senior answer continues: check ((Advised) bean).getProxiedInterfaces() for the class-versus-interface question in runtime form, and AopProxyUtils.ultimateTargetClass(bean) to get past nested proxies.

The operationally useful form is the stack trace. A frame reading com.sun.proxy.$Proxy42.create(..) means the advice did run; a frame reading OrderServiceImpl.create(..) with the proxy class above it means it did not run for that call — the self-invocation signature. And mutating advisors through Advised in production code makes behaviour depend on bean initialisation order and leaves no trace in the source; inspection is a debugging and test tool, not application logic.

03

Declaring aspects

@EnableAspectJAutoProxy registers an AnnotationAwareAspectJAutoProxyCreator — a BeanPostProcessor that runs during context refresh, before ordinary beans are created. For every candidate it asks the Advisor registry whether any advisor applies, and if so wraps it. That is the entire mechanism, and it explains three things at once: only beans the post-processor sees are candidates; an already-proxied bean is not re-proxied but its advisor list is extended; and @Transactional, @PreAuthorize and @Async each bring their own auto-proxy creator, so @EnableAspectJAutoProxy is additive rather than a prerequisite.

Two traps the table hides

@After is a finally, not cleanup-on-success. It runs on the failure path too, so anything in it executes while an exception is propagating — and if it throws, it replaces the original exception.

@AfterReturning does not run on failure. An author who puts "invalidate the cache" there gets exactly that: it is skipped on the error path, which is the one where a stale entry matters most.

Interview trap — the subclass that silently stops being advised

Given class SpecialOrderService extends OrderService, this does not advise SpecialOrderService.create(..):

@Before("execution(* com.acme.order.OrderService.create(..))")

The CGLIB proxy for the subclass reports the method as declared in the subclass during matching, so a pattern naming the parent's declaring type does not hit. The fix is to widen the type pattern (com.acme.order.*Service) or switch to within on the concrete type. A subclass gets a new behaviour, the parent's aspect silently stops applying, and the diff shows nothing.

Trade-off — @Component or @Bean

A scanned @Aspect @Component is trivial but takes constructor injection only, must live inside a scanned package, and needs a container to test. A @Bean method takes any dependency, works with no @ComponentScan at all, and is a plain constructor call in a test. Flips on: a library, starter or auto-configuration is a @Bean method — and an aspect needing conditional assembly is too, because only that path can use @ConditionalOnMissingBean.

Declare an aspect exactly once. Doing both registers two advisor instances: advice runs twice per call, the metrics counter is exactly 2×, and Micrometer may reject the duplicate meter name at scrape time. Nothing errors.

@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(MeterRegistry.class)
@ConditionalOnMissingBean(MetricsAspect.class)   // belt and braces vs double registration
public class MetricsAutoConfiguration {

    @Bean
    @Order(Ordered.HIGHEST_PRECEDENCE + 100)      // participates in the advisor sort
    public MetricsAspect metricsAspect(MeterRegistry registry) {
        return new MetricsAspect(registry);
    }
}
Should this concern be an aspect?
AspectExplicit code in the service
Visibility at the call siteInvisibleVisible
Unit testingNeeds a context to prove it appliesFree
UniformityGuaranteed if the pointcut holdsDepends on every author remembering
RemovalChange the pointcut, restartDelete the lines

Extract when the behaviour is identical everywhere, is mechanical (timing, tracing, metrics, authorisation, retry) rather than business logic, and the team will own the pointcut as a reviewed artefact. Do not when the behaviour varies by call site — an aspect is a uniform policy, and a non-uniform policy is a lie.

Staff-level — the objection to AOP is ownership, not performance

An aspect silently changes the behaviour of code its author never reads, and no reviewer of the changed file can see that it did. A PR adding a validation call to OrderService.create looks completely self-contained; there is no hint in the diff that a pointcut now intercepts it.

Three mitigations that actually work, and they are organisational: own the aspects in a named module with a named owner, so "who decided this applies to com.acme.order?" has an answer; write a test that asserts the pointcut, so a refactor that narrows the blast radius fails CI; and cap the width — a package pattern is reviewable, within(@Service *) is a global policy decision nobody signed off on. A codebase with forty aspects and no inventory has accreted local workarounds; expect roughly a third to survive it.

Two of these are worth naming as Spring's own: bean() has no AspectJ equivalent because AspectJ has no container and therefore no bean names, and it is the slowest of the nine because it must resolve against the bean factory on every match attempt. The rest that are resolved per invocation are not merely slower — @args() buys robustness with it.

Interview trap — "which designator is fastest?"

The reflexive answer is execution, because it is the most specific. The correct answer separates match time from frequency: the four static designators are resolved once at proxy creation and the decision is cached in the advisor, so a broad runtime pointcut across a hot path is measurably worse than the equivalent static one — which is an argument for within over execution(..*..*) when both express the same intent.

Pattern separators — where the invisible bugs live

..*Any number of package segments, including none—

Must remember — a pointcut is a string, not a symbol

A method call site is a compile-time reference: rename the method and the compiler points at every caller. A pointcut is a string the compiler has never seen and will never check. Rename OrderService.create to place and the advice stops running — no error, no warning, no failing test. The metric stops being recorded; the authorisation check stops happening, and that is a security failure, not a metrics gap. The failure is the absence of a behaviour, which is the hardest class of defect to detect because the system keeps working perfectly for everyone not affected.

Why Spring does not fix it: its parser must resolve bean names, and bean names are themselves runtime strings. Spring's pointcuts are closer to a query language than to a type, and should be reviewed as one.

Trade-off — args() vs @args()

args(String, long) matches the runtime types; @args(com.acme.Sensitive) matches annotations on the arguments. Flips on: @args() is the robust choice when the thing you care about is the data — a call passing a @Sensitive argument is audited whatever the method is called, and it keeps working through a rename and covers methods the pointcut author did not know existed. Use args() when the signature itself is the contract you are matching on.

// A pointcut is just a bean, so it can be shared, named and tested.
public final class MetricsPointcuts {

    public static final Pointcut TRACKED = Pointcut.matches(
        "execution(* com.acme.order..*Service.*(..))"
      + " and !@annotation(com.acme.NoMetrics)");

    public static final Pointcut STUB = Pointcut.matches("true");  // matches nothing
}

// In a test — this is what converts a silent behaviour loss into a red build:
assertTrue(MetricsPointcuts.TRACKED.matches(method, OrderService.class));

Composing is where bean() earns its keep: bean(*Service) and !bean(healthService) expresses "everything except these" in a way no type pattern can. The escape hatch in the snippet above is legitimate and underused — a STUB pointcut lets you disable an aspect by rebinding a bean rather than deleting a @Component. The cost: an aspect that is "disabled" is still consulted on every call unless the pointcut is a constant false, so it cuts an expensive body, not a chain hop.

Two designator traps

within(@Service *) looks safe and is not. It matches every @Service bean in the application — including the forty modules that did not ask for it — and it is evaluated against the proxy class, so an unrelated proxy can change how the match behaves. A broad pointcut is a global decision with a blast radius; the right width for a logging aspect is a package pattern.

execution() matches constructors and Spring cannot advise them. The expression is satisfied, the proxy is created, and it does nothing, because a proxy cannot intercept the construction of the object it wraps. Also watch the parentheses around !, or the precedence surprises you.

05

@Around & the proceed() contract

@Around is the only advice that controls whether the target runs, and that makes its contract the most dangerous in the framework. Nothing about a mistake here produces an exception.

Five obligations, in order of how often they are violated
ObligationViolationSymptom
Call proceed() exactly onceNeverThe method silently does nothing, returns null. The worst bug in AOP
Call proceed() exactly onceTwiceThe method runs twice — double charge, double insert, and no way to know
Rethrow unless swallowing on purposeCaught and droppedFailures become silent successes. The write is gone and nobody knows
Measure around proceed(), not around setupTimer stopped earlyMetrics that do not measure the method
Return type must matchDiscarding the resultNPE in the caller, several frames away

Why the assignment is required: proceed() has a return value. Call it and discard the result and the target's value is thrown away — with no return statement, the caller gets null. Exception propagation is automatic as long as you declare throws Throwable and do not catch; the moment you add a catch block you have taken responsibility for the failure and the framework will never see it.

@Around("execution(public * com.acme..*Service.*(..))")
public Object time(ProceedingJoinPoint pjp) throws Throwable {
    String key = pjp.getSignature().getDeclaringType().getSimpleName()
               + "." + pjp.getSignature().getName();
    Timer timer = timers.computeIfAbsent(key, this::build);

    long start = System.nanoTime();        // start HERE, immediately before proceed
    try {
        return pjp.proceed();              // ONCE, and the result is returned
    } finally {                            // or exceptions are never recorded
        timer.record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
    }
}
Scaling reality check — @Around holds the request thread

@Around is a synchronous interceptor on the caller's thread, running around everything else in the chain. With Tomcat's default 200 threads, an advice that calls a 500ms downstream service on a path hit at 300 requests/second saturates the pool in under a second. The arithmetic is the ceiling: 200 threads ÷ 0.5s = 400 calls/second, and everything above that queues forever.

So: an @Around making a network call is a latency decision, and belongs on a small number of methods rather than *Service.*(..). One that takes a lock or a semaphore converts a local delay into a system-wide one, and lock ordering between two aspects that both take locks is a deadlock waiting for the day the call graph changes.

Interview trap — "why not just use @Timed?"

Micrometer's @Timed is the right answer for the body of your own method and not equivalent to an @Around timing aspect, for three reasons. It annotates the method, so covering a package means touching every class. It does not compose with ordering — you cannot make it outermost, so it times only the work inside the transaction and security chain, a systematically lower number than the caller experienced. And it gives you no hook to attach a trace id or a tenant tag dynamically.

Two deviations from "exactly once" are legitimate, and only because they are visible as deliberate. A bounded retry loop — a loop, a capped count, a whitelist of retryable exceptions, a backoff, and a rethrow on the final attempt. And a cache, whose single skipped proceed() is a decision to not run the target. The whole problem is that a forgotten proceed() in a logging aspect and a deliberate one in a cache look identical in the source.

@Around("@annotation(com.acme.Retryable)")
public Object retry(ProceedingJoinPoint pjp) throws Throwable {
    int attempts = pjp.getMethod().getAnnotation(Retryable.class).attempts();

    for (int i = 1; ; i++) {
        try {
            return pjp.proceed();          // a retry is a DELIBERATE second call
        } catch (Exception ex) {
            if (i >= attempts || !isRetryable(ex)) {
                throw ex;                  // rethrow on the last attempt, never swallow
            }
            backoff(i);
        }
    }
}

A retry around a non-idempotent POST turns double-charging from theoretical into probable. Whitelist the retryable exceptions: a broad catch retries the 4xx that will never succeed, converting a fast failure into three slow ones.

The ThreadLocal trap in every tracing aspect

MDC is a ThreadLocal and Tomcat's threads are pooled. If the advice sets the value and does not clear it in a finally, whichever request next lands on that thread inherits the stale id and every log line it produces is mislabelled. The pool size and the error rate — not the code path — determine how many requests are affected, which is exactly why it looks intermittent and why it is found by a support ticket rather than a stack trace.

Fix: clear unconditionally in the finally, restoring the inbound value if there was one. The ThreadLocal also does not survive a thread hop — across @Async, a CompletableFuture, a parallel stream or a scheduled task the trace id is gone, and the fix is a TaskDecorator or context propagation, not a better aspect.

06

Aspect ordering

The convention is the same as the rest of Spring and inverted from intuition. Ordered.HIGHEST_PRECEDENCE is Integer.MIN_VALUE, not 1; unannotated aspects sort at LOWEST_PRECEDENCE. The subtlety is that precedence describes entry order, and the highest-precedence aspect is built to be outermost — entered first, exited last.

The classic bug — logging a commit that rolls back

@Transactional defaults to LOWEST_PRECEDENCE, so the transaction interceptor is innermost — inside every aspect you write. An audit aspect at @Order(10) therefore writes "ORDER SUCCEEDED" and only then does the transaction attempt its commit. Under a database failover the commit fails, the transaction rolls back, and the audit log is left holding a durable, timestamped false record of a payment that never happened. It is discovered by finance, not by an engineer.

The fix is one annotation: @EnableTransactionManagement(order = Ordered.HIGHEST_PRECEDENCE), which makes the transaction outermost so nothing outside it can observe an outcome that has not happened. The general rule: anything that makes a durable record of an outcome belongs outside the transaction interceptor — audit rows, metrics, webhook enqueues, cache invalidation, "order created" events.

What Spring guarantees, and what it does not
GuaranteedNot guaranteed
A total order over aspects declaring distinct @Order values The relative order of two aspects with the same @Order — do not design around it
The highest-precedence aspect is outermost, so its exit logic runs last The order of a framework advisor relative to yours unless you set it explicitly
Unannotated aspects sit at LOWEST_PRECEDENCE The order of advisors on the same aspect
Once built, a singleton advisor's order is fixed That an aspect applies at all — that is the pointcut question
  Anything across proxies: a bean proxied for two reasons is proxied once, with a combined advisor list built once

@Async and @Cacheable also default to LOWEST_PRECEDENCE, so they are inner to any aspect you wrote. A timing aspect on a class with @Async therefore measures the submission of the task, not its completion — a microsecond number that looks suspiciously good and that a team trusts for three months. The same reasoning diagnoses a tripled p99: the chain cost is tens of nanoseconds and cannot move a p99, so the cause is I/O in the advice body, not the proxy.

Must remember — ordering is a document, not an intuition

Ordering is invisible until the day it matters, and the failure is production-only and low-frequency — a commit failing under a failover, a lock timeout, a deferred constraint. The team's model of their own system is wrong and the code has never told them. Three things fix it: a short document listing the aspects in chain order with their values and what each is outermost to; a review convention that a new aspect must state its position in that list; and a test asserting the durable-effect behaviours run outside the transaction. A test is the better mechanism but the wrong first step — you cannot assert a chain until you have decided what it should be, and that decision is the design conversation.

07

Pitfalls & diagnosis

Every item below is one fact — the proxy must be in the call path, and it only is if the caller holds the proxy rather than the target — seen from eight angles. Learn the mechanism and the eight symptoms stop being eight things to memorise.

The two fixes, compared honestly
Fix 1: inject self via @LazyFix 2: extract into its own bean
Code changeOne field, one annotationA new class; the caller changes
UnderstandabilityPoor — a class injecting itself confuses every readerClear — the dependency is real and visible
Unit test with a plain newNPE on selfBoth classes test directly
Works for a private methodNo — the proxy still cannot see itn/a
When it is rightContained fix when callers cannot changeThe default answer

Recommend extraction, and not for tidiness: a self-injected reference makes the class appear to depend on nothing while the container does something non-obvious to make it work, whereas extraction names the transaction boundary as an object you can inject, mock and point at in a design review. If you can name the class that should own the behaviour, name it — a self-injection is a signal that nobody has yet.

The trap that arrives two years late — record and Kotlin data class

CGLIB works by generating a subclass, so every record is final, and every Kotlin data class is final unless declared open (Kotlin classes are final by default). The failure is a startup ReflectiveOperationException: Cannot subclass final class — and it arrives at the moment someone adds the annotation, naming a class written long before. The language feature that makes records attractive, immutability by construction, is exactly the property that makes them un-proxyable.

Interview trap — "make it public"

The reflex is right more often than not, but the answer that earns the question names the mechanism. A private method cannot be advised because the proxy is a different class. Widening to protected or package-private fixes the CGLIB case provided the package matches; public fixes it unconditionally but exposes it as part of the bean's API. The genuinely good answer for a private @Transactional helper is move it to another bean — a private method that needs a transaction is doing something a collaborator should do, and the fact that it is private is the design telling you so.

Trade-off — serializing a bean into a session

A proxy is a distinct object carrying a reference back to the target, the TargetSource and the advisor chain. If the target is serializable and the proxy is not, the write succeeds and the read fails. In preference order: store an identifier, not the object — which also removes a class of stale-state bugs; or make the target Serializable and use a JDK proxy, which is serializable when its target is. Flips on: a Spring-managed object with a lifecycle does not belong in a session at all, so the second option exists for a genuine boundary crossing, not as a default.

Must remember — the one governance rule worth ten lines of code

An ArchUnit rule that fails the build when a method carrying @Transactional, @PreAuthorize, @Async or @Cacheable is private, static or final, when its class is final, or when such a method is invoked via this. — the call, not the declaration, which is the part no IDE rule catches alone. It converts an entire chapter of silent-failure bugs into a build failure, and it is the highest-leverage AOP governance an organisation can adopt.

What it cannot catch: structural self-invocation through a helper, a service instantiated with new outside the container, and a proxy created by a configuration the rule does not model. Rules find the syntax; tests find the structure. You need both — and with 400 @Transactional methods in a codebase, the real risk is that nobody can answer the question at all, and the exposure grows with the method count while the detection ability stays flat.

Finally, the cost nobody budgets for: every advised call now runs through the proxy entry point, DynamicAdvisedInterceptor.intercept, ReflectiveMethodInvocation.proceed and each interceptor body — at least three framework frames, with $Proxy42 at the top. Engineers learn to read past them, and then the frames are exactly what they needed. The production answer is to stop treating the stack trace as the narrative: log the method name explicitly, and use AopUtils.isAopProxy for the proxy question. The deeper argument is that fewer aspects would fix this more effectively than any logging change.
