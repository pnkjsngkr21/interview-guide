Why the ORM's default behaviour is more dangerous than most frameworks': the defaults are silently correct-looking, and JPA's usual failure mode is a right answer that came from somewhere other than where you thought.

If you only remember five things

  1. The persistence context is a mandated identity map, scoped to one transaction. Same row, same Java object; mutating a managed entity is a write at flush; and the rule that follows is share the EntityManagerFactory and never an EntityManager.
  2. merge returns a different object. It copies state onto a managed copy and hands that back, so mutating what you passed in writes nothing. The fix is "always use merge's return value"; the durable one is a DTO at every boundary.
  3. An N+1 costs round trips, not query time. Every statement is indexed and fast, which is why it hides from database monitoring. The only reliable detector is a query-count assertion in CI, and the fix that is usually right is a DTO projection.
  4. Bulk @Modifying operations bypass the persistence context and leave it holding stale entities, which dirty checking then writes back over the bulk result. clearAutomatically = true is close to mandatory, and this is the one bug on the page that corrupts data rather than returning wrong numbers.
  5. ddl-auto defaults to none for a real database and create-drop for an embedded one, and no value of it is a migration tool. Production is Flyway or Liquibase plus validate.

No section matches that filter.

01

JPA & Hibernate fundamentals

JPA is a specification and Hibernate is one implementation of it. Knowing the seam is what separates a portable data layer from one that only runs on one database — and Hibernate's additions are where the behaviour nobody can derive from the annotations actually lives.

The seam, and why it decides your failure modes
JPA specifiesHibernate adds
IdentityThe persistence context as a mandated identity map The dirty-tracking snapshot array behind it — not in the spec
WritesExplicit persist, merge, remove Dirty checking: an UPDATE at flush with no save() call anywhere
Query languageJPQL, over entity and attribute names HQL superset, a transformable SQL AST, statement inspectors
FetchingFetchType, JPQL join fetch @BatchSize, @Fetch, @FetchProfile, bytecode proxies
CachingNothingSecond-level cache and query cache, with pluggable consistency strategies
Interview trap — "JPQL means it's database-independent"

The accepted answer is half-wrong in the direction that costs the point. JPQL is portable only inside the spec's subset: a function the provider doesn't know fails to translate, and the moment you use left join fetch semantics, a @SqlResultSetMapping, a queryHint name, or a Criteria node the spec doesn't have, you've left it. The sharp version is that JPQL operates on entity and attribute names, never table and column names — which is the entire argument for the query language existing, and the entire reason a native query needs an explicit result mapping.

The honest flip: portability is worth exactly zero if you never run on two databases, which is true of most teams and is a legitimate reason to use vendor features freely.

The identity map, and where its edge is

Which object you may share, and what happens if you get it wrong
EntityManagerFactoryEntityManager
HoldsParsed mapping model, connection provider, query plan cache, L2 cache One persistence context — identity map, snapshots, pending actions
Cost to createExpensive: parse every mapping, build metadata, open the pool Cheap: allocate a session, bind a JDBC connection
Thread safetyThread-safe — the intended singleton Not thread-safe — one per thread at a time
LifetimeOne per application, one per persistence unit One per transaction — or one per request under OSIV
Failure modeMissing bean: the context will not start Shared across threads: IllegalStateException or silent corruption
Must remember — what Spring actually injects

Spring never injects a real EntityManager. It injects a SharedEntityManagerCreator proxy that resolves the transaction-bound session per call, which is exactly why injecting one into a singleton is safe. The subtlety: outside a transaction the proxy opens a temporary context, does the work, and closes it at method exit. So em.find() in a non-transactional method succeeds, returns managed entities, and silently detaches them — the mechanism behind "the lazy load worked in the service but not in the controller".

How the proxy binds to the thread, and what JpaTransactionManager does with it, is Volume 4's material — this page owns what happens inside the context.

persist vs merge, and save()

The most-asked question in a JPA interview

persist needs a new object, makes that same instance managed, and throws EntityExistsException on a detached one. merge copies state onto a managed instance and returns that — a different object from the one you passed in. So em.merge(x) followed by a mutation of x writes nothing, silently, because the context never saw the later mutation. After a merge, em.contains(x) is false, and the managed copy carries the database's field values — which is why merge will happily overwrite a field your detached object left populated with the row's null.

Always use the return value. And never let a detached entity reach code that mutates it: anything crossing a serialisation, queue, cache or thread boundary is exactly where this bug is born.

Entity copied from a DTO with @Version already non-nullnot newmergeSame class of surprise

Mapping defaults that hurt

Trade-off — IDENTITY against SEQUENCE

IDENTITY wins when inserts are rare and you want gap-free, monotonic, human-readable IDs that sort in insertion order, on a table with one writer anyway. SEQUENCE wins the moment insert throughput is the problem, because the ID is known before the statement and the batch goes out as one round trip. Hibernate 6's default sequence allocation size is 50 — a reasonable compromise, and raising it to 1,000 in a high-churn service just moves the ID waste around.

Interview trap — the default @Enumerated

Leaving it off means ORDINAL, which persists the enum constant's position in the declaration. Insert a constant in the middle and every existing row silently changes meaning — status = 1 was PENDING and is now SHIPPED — and it is unrecoverable without a manual UPDATE, because the database was never told what the numbers meant. EnumType.STRING costs a few bytes and makes the data self-describing. ORDINAL is defensible only for a closed, never-changing, strictly internal enum.

Lombok @Data on an entity

Two of the generated methods are actively harmful and one is a runtime bomb. equals/hashCode over mutable fields means an entity in a HashSet becomes unfindable the moment dirty checking updates one of them. toString over associations gives StackOverflowError on any bidirectional mapping, from a log line. And @Data suppresses the no-args constructor that Hibernate needs, so the next person to add @Builder gets a runtime HibernateException: Unable to invoke no-args constructor rather than a compile error. The fix is an ArchUnit rule banning @Data on @Entity — enforceable in seconds, and the incident is not.

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Product other)) return false;
    return id != null && id.equals(other.id);   // null guard: two transient products are not equal
}

@Override
public int hashCode() {
    return getClass().hashCode();      // CONSTANT — the ID doesn't exist until persist
}
Must remember — @Version is the only thing that makes staleness loud

Without a @Version field, Hibernate's update is UPDATE ... WHERE id = ? with no version predicate, so last-writer-wins is silent — data loss, discovered by a customer. With one it becomes WHERE id = ? AND version = ? and a zero-row result raises OptimisticLockingFailureException, which is retryable and therefore the right failure mode. The cost is one BIGINT column and one predicate; the exception worth naming is genuine last-write-wins data (a view counter, a heartbeat), where a version column is pure cost. That is a convention to document, not a library setting.

02

Spring Data repositories

The interface hierarchy, and what each level actually buys
InterfaceAddsUse it when
RepositoryNothing — a marker You want to declare the dependency without exposing persistence operations
CrudRepositorysave, findById, existsById, findAll, count, deleteById Whole-aggregate operations only
PagingAndSortingRepositoryfindAll(Sort), findAll(Pageable) A list endpoint you never write to
ListCrudRepository / ListPagingAndSortingRepository List-returning variants, findAllBy(Sort) Spring Data 3.0+ (Boot 3). The pre-2.x non-Iterable API
JpaRepository flush, saveAndFlush, deleteAllInBatch, getReferenceById, @Lock, JpaSpecificationExecutor Almost always — and the cost is that your service layer now names JPA types
"Use CrudRepository to stay persistence-agnostic"

Scores about zero, because the abstraction is a lie at the level that matters. CrudRepository.save returns void and hands you no ID back for a new entity with a non-IDENTITY generator — the most common complaint about it. The moment you need getReferenceById to avoid a query, @Lock, or a Specification, you are on JpaRepository anyway. The honest framing: the repository abstraction is genuinely good at CRUD on a single aggregate and is the wrong tool for everything else, and the interface you pick is a smaller decision than the queries you write.

Spring Data 3.0 deprecated getOne() and getById() in favour of getReferenceById(). getOne() returned a proxy that threw EntityNotFoundException on dereference — a behaviour that produced a lot of 404s that were 500s.

Derived query methods

public interface ProductRepository extends JpaRepository<Product, Long> {

    // [subject][Distinct][Top N][By][conditions][OrderBy ...][Asc|Desc]
    Optional<Product> findBySku(String sku);                        // subject: find|read|get|query|count|exists|delete
    List<Product>     findByNameContainingIgnoreCase(String f);    // LIKE %f% on lower(name)
    List<Product>     findByPriceBetween(BigDecimal lo, BigDecimal hi);  // BETWEEN, inclusive
    List<Product>     findByCategoryParentName(String n);          // "." means an implicit JOIN
    List<Product>     findTop5ByStatus(ProductStatus s);            // limiting
    Page<Product>     findByStatus(ProductStatus s, Pageable p);

    // A derived name CANNOT express a fetch join — it compiles, it parses,
    // and the N+1 you were trying to fix is still there.
    @Query("select distinct o from Order o join fetch o.lines where o.id = :id")
    Optional<Order> findWithLines(@Param("id") Long id);
}
Two traps in the grammar

The parse happens at context startup, not at compile time. A broken method name takes the application down at boot, and CI only catches it if the test slice actually boots a context. The error is good, though: it names the unparsed fragment, so diagnosis is mechanical — the parser stopped at the first token it could not resolve to a property, a keyword, or an And boundary.

A null argument becomes IS NULL, silently. findByStatusAndDateGreaterThan(s, null) is not an error and not a no-op; it is an IS NULL comparison that returns a plausible set of wrong rows and looks like a data problem when it is an argument problem. This is the strongest argument for @Query in anything with an optional filter.

Trade-off — derived names against @Query

Derived methods are compile-time invisible, IDE-unindexable, and reviewable only by someone who knows the grammar. @Query is greppable, refactor-safe, and validated at startup on property names — a real safety net no amount of "derived is more readable" dismisses — and it is the only option for anything the grammar can't express. It also binds by name only with @Param or a -parameters build; without one you get Name for parameter binding must not be null at startup. The rule that holds up: derived for single-property lookups, @Query from the second association traversal onward — the point where a reader has to hold the whole name in their head is where the abstraction starts costing you.

Must remember — countQuery is not optional when a count is shown

Spring Data derives the count by cloning the main query and replacing the select clause. That is right for most JPQL and wrong for any query with a join fetch of a collection — it counts joined rows, so an order with 5 line items counts 5 times — and wrong for a distinct it cannot translate. Both give a total that is too high and a UI showing "1,247 results" for 340 real ones. The page content is right and only the total is inflated, which is why it looks plausible rather than obviously broken. The same trap has a name in Specification: joining a to-many without query.distinct(true) makes getTotalElements() disagree with getNumberOfElements().

Bulk operations: fast, and dangerous

@Transactional
@Modifying(clearAutomatically = true,   // detaches everything AFTER — the fix for the stale write-back
           flushAutomatically = true)   // flushes BEFORE, so the query sees this transaction's own inserts
@Query("update Product p set p.status = :to where p.status = :from")
int bulkRetire(@Param("from") ProductStatus from, @Param("to") ProductStatus to);

You need both flags for different reasons and only one of them prevents the corruption. flushAutomatically is for when the bulk statement's target rows include rows this transaction just inserted and has not flushed. clearAutomatically is the one that stops the write-back — and its own cost is that every entity in the context is detached afterwards, so a caller iterating managed entities gets detached ones. @Modifying methods are transactional and throw TransactionRequiredException outside one, which a broad catch (Exception) will turn into a silent zero-row nightly job.

Must remember — Specification is not plan-cached

A JPQL string is parsed once into a query plan keyed by the string and looked up thereafter. A Specification builds a new criteria tree on every invocation, so the key is effectively unique, the Hibernate plan cache never hits and grows unboundedly, and the database's plan cache misses too because the SQL shape varies. Ten thousand invocations is roughly ten thousand cache entries. At a few calls per request this is irrelevant and you will not measure a difference; it is real for a search endpoint at thousands of calls per second with a different filter each time. The mitigation is not "ban Specification" — it is naming the top few filter combinations as @Query and keeping the specification for the long tail.

The real cost of the repository pattern is observability

Not verbosity — observability. A DBA asked "which queries touch products in the last hour" cannot answer it from Java. A log analyser cannot aggregate them. An APM tool cannot build a per-endpoint latency histogram because the SQL is a runtime-generated string it has never seen. The database's own pg_stat_statements can, and it will show you queries your repository interfaces do not know exist.

The rule that decides the design point: the abstraction traded a shared, queryable language for per-query encapsulation, and the trade is only good while the queries are simple. Single-aggregate CRUD through Spring Data; anything with a fetch join, a projection or a report shape through a named query layer with a hand-written mapping.

03

Relationships & fetch strategies

A bidirectional association is two fields, and one is fake

The owning side holds the @JoinColumn (or the @JoinTable, or the plain FK field) and is the only side Hibernate writes. The inverse side carries mappedBy and is never written. Setting only the inverse side is not a partial write — it is a complete no-op: the collection looks correct in memory, the transaction succeeds, the row lands with a null foreign key, and nothing throws. That is why the addChild helper pattern exists. It is an enforcement mechanism, not a convenience — it makes the two-sided update the only way to express the operation, so the failure becomes a review comment rather than a silent data bug.

@Entity
public class Customer {

    @OneToOne(fetch = FetchType.LAZY)          // spec default is EAGER — override it deliberately
    @JoinColumn(name = "passport_id", unique = true)   // unique, or it is a ManyToOne with extra steps
    private Passport passport;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();   // inverse: Hibernate never writes this

    public void addOrder(Order order) {
        orders.add(order);
        order.setCustomer(this);     // the owning side — without this the FK inserts as null
    }
}
Interview trap — cascade = REMOVE is not orphanRemoval

cascade = REMOVE means "when the parent is deleted, delete the children" — all or nothing. orphanRemoval means "when a child leaves the collection, delete the row" — one at a time. Many real mappings need both and they are not alternatives. cascade = ALL alone does not delete an orphaned child: removing it from the collection is a no-op and the row stays with a dangling FK, which is the "deleted rows come back" bug. orphanRemoval is only valid on the owning side, and only for @OneToOne and @OneToMany — a @ManyToMany cannot use it, because a row missing from the join table isn't orphaned, it's just absent.

The spec's fetch-type defaults, and what each costs in practice
AssociationSpec defaultWhat it actually doesMake it
@ManyToOneEAGER Every find on the owner issues an extra SELECT for the target, whether or not the caller touches it LAZY — it is the most common association in a typical model, so the default is the expensive one
@OneToOneEAGER Same, plus a unique-constraint requirement people trip over. Without the constraint it is a ManyToOne with extra steps — and Hibernate's eager SELECT then finds two rows and throws NonUniqueResultException LAZY, and add the unique constraint in a migration
@OneToManyLAZY A PersistentBag proxy; one SELECT on first touch LAZY is already right
@ManyToManyLAZY A proxy over the join table LAZY is already right
Trade-off — is EAGER ever the right answer?

Yes, for a small, immutable reference that is genuinely part of the owner's identity and needed on every read — a Currency, a CountryCode, a fixed FeeSchedule — and it stops being defensible the moment the association is nullable, large, or itself an aggregate root, because the eager load then cascades. Flips on scale: below roughly ten thousand requests a second an extra indexed join is cheap and eager is simpler; above it the multiplication is real.

The argument that settles most discussions is neither: a fetch strategy is a default for the mapping while the need is a property of the caller, so every value of the annotation is a compromise. The mature position is all-LAZY mappings, deliberate fetching at each call site, and a query-count assertion to stop "deliberate" decaying back into "whatever the defaults did".

Interview trap — LAZY on a to-one still issues a query

The folk memory is "associations are lazy by default" and it is wrong in the expensive direction: @ManyToOne is EAGER, so a single find() on an entity with three to-one associations issues four queries before the caller has touched anything. The three real costs of a lazy proxy: it throws LazyInitializationException when touched outside a session; a lazy load inside a loop is an N+1 wearing a disguise, with no fetch join anywhere for a reviewer to spot; and it is not "eventually cheaper" but deferred to a worse place — which is precisely what Open Session in View does.

Fetching, and the three ways it fails

How to say "fetch it now", and what each costs
MechanismWins whenWhen it bites
join fetch in JPQL / HQL One query, and you need the association for every row Pagination, two List bags, and — on a nullable to-one — it is an inner join, so rows silently disappear. left join fetch keeps them
@EntityGraph(attributePaths = ...) The same association set is needed by several queries: name it once, override per call. Subgraphs ("lines.product.category") are the only way to express a multi-level fetch Same three hazards, plus a dynamic named graph for one chosen at runtime
@BatchSize(size = n) "I need this on some rows" — a list with a child count or a child name No fetch-join hazards, at the cost of 1 + ceil(N/n) queries and an IN list of n owner IDs
@Fetch(FetchMode.SUBSELECT) You always need this association for this entity, across the whole session Two queries total regardless of N — but one query for a collection half the callers don't need, returning rows for entities you don't care about
Interview trap — MultipleBagFetchException says "bags" on purpose

A bag is a List field with no @OrderColumn. A result set has no column identifying which collection a repeated row belongs to, so Hibernate can carry one List per query and no more. Set collections don't have the problem, because rows de-duplicate by primary key — so the widely-repeated advice "one collection per query" is wrong: two Sets fetch fine.

The consequence of the workaround is ordering, and it is the thing to name: a Set is unordered unless you add @OrderColumn (a synthetic index column Hibernate maintains on every write) or @OrderBy (a read-time ORDER BY, free on write). @OrderBy is nearly always the right one.

Must remember — all-LAZY is a discipline, not an annotation

With OSIV on (the Boot default) lazy loading in the view always works, so your integration tests — @SpringBootTest + MockMvc included — pass on code containing an N+1. Setting open-in-view: false is therefore a detector, not just a policy: it surfaces every place an entity crosses a boundary, and each of those is a place where the response shape and the persistence model are coupled. The durable control is readOnly = true on read services plus a DTO returned from inside the transaction — test-slice mechanics and transactional test rollback are Volume 9's material.

04

The N+1 problem

An N+1 is not a Hibernate bug. It is what happens when a query returns N rows and the code then does something per row that needs more information — and the ORM's laziness makes it trivial to write, because the code reads like good service code.

Interview trap — "the queries are fast, so it isn't an N+1"

It absolutely is, and the second trap is "it's fine because there's an index": an index makes each of the 180 queries fast, and 180 fast queries are still 180 queries. The signature that tells you in pg_stat_statements is many calls, tiny mean — one query shape, a high calls count, a high total_exec_time, and a tiny mean_exec_time. In an APM it is N identical short child spans; in a pool dashboard it is checkout wait time spiking while query duration stays flat, which is the diagnostic that separates "the database is slow" from "we made too many trips to the database".

Detecting it

SessionFactory sf = emf.unwrap(SessionFactory.class);
HibernateStatistics stats = sf.getStatistics();
stats.setStatisticsEnabled(true);
stats.clear();

List<OrderDto> rows = new OrderService(orderRepo).listByStatus(ACTIVE);   // the measured block

// an UPPER BOUND, never an exact number — an exact one fails on every mapping change
assertThat(stats.getPrepareStatementCount()).isLessThanOrEqualTo(3);
assertThat(stats.getCollectionFetchCount()).isLessThanOrEqualTo(3);   // the more sensitive signal
Must remember — the only detector that is a control

An N+1 is a property of the combination of a query and the code that consumes it, so a unit test of either half cannot see it. The query-count assertion runs the real query through the real mapping and counts the statements — and it is the only detector that is a control rather than a diagnostic, because it fails a build instead of explaining a graph. A diagnostic you run during an incident is a diagnostic that never runs.

Two details decide whether it survives. Assert an upper bound with a comment explaining the budget; an exact number fails on every unrelated mapping change and gets deleted within a month. And check getCollectionFetchCount() alongside the statement count — one query with 400 collections hydrated is an N+1 with a clean-looking query log, and a query count of 1 with 400 loaded entities is a memory problem, not a round-trip problem, with completely different fixes.

The fixes, and the condition that picks between them

Query count for N rows, and what each fix costs you

Scaling reality check — ceil(N/n) + 1 decides this

For 20 orders at @BatchSize(50) that is 2 queries, not 21. At @BatchSize(10) it is 3. For 5,000 orders at @BatchSize(50) it is 101 — which is the point at which batching stops being a fix and becomes a slower N+1, because it is a constant-factor improvement, not an asymptotic one. The answer there is pagination, a projection with a GROUP BY, or a denormalised column — not a bigger n. The failure nobody plans for is a team that raises batch_size to 100 to make a growing report faster, which works until the IN clause hits a driver parameter limit and the query starts failing rather than slowing down.

@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
@BatchSize(size = 50)          // 20 orders -> 1 + ceil(20/50) = 2 queries
private List<OrderLine> lines;

// the fix that removes the REASON the N+1 existed: you never needed the entities
@Query("""
       select new com.acme.dto.OrderRow(
           o.id, c.name,
           (select count(l) from OrderLine l where l.order = o))
       from Order o join o.customer c
       where o.status = :status
       """)
List<OrderRow> findRows(@Param("status") ProductStatus status, Pageable p);
The fix that is usually right, and the reason isn't performance

You were rendering 20 orders. You needed four scalar columns and one count. Every other fix is about loading entities you had no intention of using in fewer round trips — a bet that the extra columns and hydration cost are cheaper than the queries saved. A projection makes no such bet: it asks the database for exactly what the response needs. The tell that you have reached it is noticing that the N+1 exists at all — the loop only ran because you were mapping entities to fill in a table. The test to apply: if the method returns an entity and the caller immediately converts it to a DTO, the projection should have been the query.

Two cache answers, both wrong

The query cache makes an N+1 worse. It is keyed on the full bind-parameter set, so 180 queries with 180 different IDs are 180 distinct cache entries — all misses, evicting each other.

The second-level cache doesn't fix it either. It makes each of the N queries cheaper, not fewer, the first cold one still hits the database, and it is per-process by default, so ten instances mean ten caches and ten independently-stale copies. It is genuinely right for a small, hot, read-mostly reference set — a few hundred Category rows read on every request — but that is a different decision, and the one that decides it is the consistency contract: a write in another process cannot invalidate a local cache, so the staleness window is unbounded in the worst case. Push caching up the stack, to HTTP or a service layer, where the TTL is explicit and a bad invalidation costs one response rather than every reader in the process. Enabling it needs hibernate.cache.use_second_level_cache plus a region factory, and the per-class CacheConcurrencyStrategy.READ_WRITE is the safe one — READ_ONLY is faster and has an unbounded stale-read window.

Would you ban join fetch in review to stop N+1s?

No — it is the wrong lever for the right instinct, and it fails the requirement. A ban removes a tool without replacing it, so teams compensate with a global default_batch_fetch_size that changes every query in the application, including the ones that work. The assertion catches every N+1, including the ones nobody wrote a fetch join for: the ones inside loops, the ones from equals touching a lazy association, the ones inherited from a mapping someone else wrote. Then the review comment on a specific join fetch is about this method's constraints — does it paginate, is more than one List involved, is the association provably non-null. That is a review that can be done; "no fetch joins" is a rule that can't.

The three cache layers, and which one a question means

The layer is decided by who can invalidate it, not by what it stores

Interview trap — the Spring Cache is not a cache, and the default one leaks

It is an AOP layer, not storage. It decides whether to call your method; a CacheManager supplies the place. Add @EnableCaching and nothing else and Boot hands you ConcurrentMapCacheManager — a ConcurrentHashMap per name, with no TTL and no size bound. Boot's own words: "The simple provider is not really recommended for production usage." Entries live until evicted or the JVM restarts, so a key built from request input is a heap ceiling, and at ten instances it is ten of them. spring.cache.type takes caffeine, redis, hazelcast … or none, which is how you A/B a cache change with the annotations still in place.

Four errors to be able to name cold. (1) An unnamed @Cacheable gets no generated name — it throws IllegalStateException: No cache could be resolved; the name must come from value/cacheNames or class-level @CacheConfig. (2) A name the manager doesn't know gives IllegalArgumentException: Cannot find cache named '...' — a typo, not a missing name. (3) The default SimpleKeyGenerator gives the argument itself as the key for one non-array argument, so an array or several arguments fall to SimpleKey and never match — write key explicitly. (4) sync = true rejects unless, rejects more than one cache name, and cannot be combined with another cache operation.

Never cache the entity — cache the DTO. A cached entity is detached from any persistence context, so its lazy associations throw LazyInitializationException on first touch, and it carries no version check. And @CacheEvict on a @Transactional method has no guaranteed order against the commit: both advisors default to LOWEST_PRECEDENCE, so eviction can run first and a reader can repopulate from pre-commit data. Wrap the manager in TransactionAwareCacheManagerProxy.

Must remember — which cache to reach for, in one line each

Same request, same entity? That's the persistence context, and it is already there — do not cache it. Small, hot, read-mostly reference rows everyone reads? @Cacheable on the service. An expensive aggregate only a few users request? A projection. Something a whole cluster must agree on? Redis, with a TTL, and accept the staleness you have chosen. Full treatment in Volume 6 §4.6; the stampede itself belongs to Database Volume 9.

05

The persistence context in practice

Section 1 drew the identity map. This section is about the four things that surprise people once they have one: what triggers a write, when the in-memory state stops matching the database, what it costs in memory, and what Spring does to it without telling you.

Flush and commit are not the same event

Commit is the transaction boundary. Flush is Hibernate synchronising the persistence context with the database, and it happens at four moments:

  • before any JPQL or HQL query whose query space overlaps a pending change;
  • before any native SQL statement, unconditionally;
  • at commit;
  • explicitly, via flush().

Native SQL is the one that bites, because the auto-flush rule only understands JPQL's query spaces. A JPQL query that does not touch the table you modified will not trigger a flush, and neither will a native statement — so a bulk UPDATE run through the JDBC template can write a value that the transaction then overwrites from a stale in-memory copy at commit.

Interview trap — "the UPDATE ran, why is the old value back?"

The write was reverted by the persistence context, not lost by the database. The in-memory entity was dirty, the flush at commit issued an UPDATE with the old value, and the bulk statement's row count was correct the whole time. The signature is a row that reverts on a path where the same code passes in a test — because in the test the bulk statement was the last thing to touch the transaction, so there was nothing left to overwrite it.

What dirty checking does that save() does not

Must remember — the asymmetry is the whole API

save() is required on the way in and optional on the way out. Transient to managed needs an explicit call, because nothing else can see the object. Managed to dirty needs nothing, because the context is already watching. Every confusion about Spring Data's save() comes from applying the first rule to the second case — and the failure is invisible, because a redundant save() on a managed entity does a SELECT and returns a different object, so the code keeps mutating an instance the context is not watching.

Scaling reality check — 3× to 5× per entity, then OOM

A managed entity is not the object you wrote: it is the object, plus a deep copy of every loaded field for dirty checking, plus a key and an entry in the context's identity map — three to five times the size of the POJO. A StatelessSession reads a 100 MB object graph where the managed path does not fit in the heap. Around 100,000 entities in a single context, the answer stops being "clear more often" and becomes a stateless session or a pagination loop — and the shape that produces it is the batch job that loads everything because it was convenient to write.

Must remember — the proxy is bound to the transaction, not the thread

What Spring injects is a shared proxy that opens a new EntityManager bound to the current transaction and closes it at the end. Inside a transaction every repository call joins that one context, which is why dirty checking works across repository boundaries. Outside one, each call gets a fresh context that closes immediately, so an entity returned from a non-transactional method is detached and its lazy associations cannot be touched — the visible symptom is a LazyInitializationException far from the method that caused it, usually inside a serialiser. Self-invocation and transaction propagation are Volume 3's and Volume 4's material; the persistence-context half of that story is the single sentence that the context follows a transaction, not a thread, and never survives it.

Open Session in View, and read-only transactions

With OSIV on, the context stays open through the test's view rendering exactly as in production, so lazy loading always succeeds and the query count is never asserted. The test suite's silence is produced by the same mechanism that produces the production problem. The order that works: turn OSIV off first, let the LazyInitializationExceptions appear, fix them by fetching what the response needs — and what remains is the N+1s, with the query-count assertion from section 4 as the control. It is a one-line change that converts a class of silent defects into a class of loud ones.

Scaling reality check — readOnly = true needs both switches

Marking a transaction readOnly = true skips dirty checking: Hibernate sets FlushMode.MANUAL, so no snapshot diffing and no accidental dirty writes. That is most of the win. The part that is easy to miss is that the database must be told too, or you have only optimised the ORM and left the driver in read-write-transactions mode — pair it with hibernate.connection.provider_disables_autocommit to put the connection into read-only mode, which is also what lets read replicas and read-only routing work. The flip condition: read-only is a performance hint with a correctness consequence. A genuine write through a read-only context throws at flush, which is the behaviour you want — but it is a behaviour change, not a free speed-up.

Querying & pagination

Three query languages, three levels of what the database will catch for you, and one pagination decision that gets more expensive the deeper the user goes.

JPQL, HQL and native SQL

PortabilityYesYes, but it is a Hibernate extensionNone — and you will find out on the migration
Use forAnything you want to keep portableLock modes, fetch hints, entity functionsThe three queries a hand-tuned index wins
Interview trap — "the native query is wrong, but it compiled"

Native SQL is a string. It is parsed by the database, not by the provider, and it is parsed when it is executed — so a renamed column, a dropped index, or a keyword that means something in one dialect and nothing in another all pass every build that does not run the code path. The honest framing for an interview: native queries buy you access to features the ORM cannot express (window functions, CTEs, INSERT ... ON CONFLICT) and cost you the guarantee that a schema change breaks the build. Keep them few, name them after the database feature they use, and cover each with one integration test against the real engine.

Section 2 covered derived queries and Specification. The choice between them and @Query is a question about who owns the query plan: a derived name is parsed and cached against the entity, a Specification is built into criteria and misses that plan cache because the criteria tree is a new object each call, and a @Query is a string the provider parses once at startup — which is why a typo in a @Query fails the context at boot and a typo in a method name fails it too, while a typo in a native query waits for production.

Projections

Three ways to get something other than an entity

Interview trap — the projection that returns null and nobody notices

With an interface projection, the alias in the select is matched against the accessor names by convention. Miss one — select o.customerName against a getter called getCustomer() — and Hibernate does not throw: it proxies the interface, finds no matching property, and returns null for that accessor while every other field is populated. It fails at the consumer, usually as a blank cell in a table or a zero in a total, long after the query. A constructor expression into a record cannot do this: the argument list is checked by the compiler and the type carries the names. That asymmetry is the whole reason to prefer it.

The other half of the cost is that offset pagination is linear in the page number, because the database must produce and discard every skipped row. Page 500 of 20 asks for 10,000 rows and returns 20. And it is inconsistent as well as slow: two requests for page 500 while a row is inserted see different data, and a row that shifts position can be shown twice or skipped entirely.

// seek pagination: no OFFSET, so page 500 costs the same as page 1
@Query("""
       select o from Order o
       where o.createdAt < :t
          or (o.createdAt = :t and o.id < :id)     // the unique tiebreaker
       order by o.createdAt desc, o.id desc
       """)
List<Order> findPageBefore(@Param("t") Instant t, @Param("id") Long id, Pageable p);
Must remember — every paginated query needs a unique tiebreaker

The cursor is a tuple, and the tiebreaker is not optional. Order by a non-unique column alone and rows with equal values are skipped or repeated, because the database has no defined order among them and the next page starts "after" a value that several rows share. Order by (created_at, id) and the pair is unique because the id is, so the boundary is exact. The comparison must be the same lexicographic form the ordering uses — hence the createdAt < :t or (createdAt = :t and id < :id) shape, not two independent predicates. Two portability notes: row-value comparison (a, b) < (:t, :id) is cleaner and is supported by PostgreSQL and MySQL but not by SQL Server or Oracle, so write the OR form; and the sort columns must be indexed together, in the same order, or the seek is no cheaper than the offset.

Schema, batching & pool sizing

Three areas where the defaults are chosen for a single-user development machine, and where the production failure is a lock, an outage, or a schema nobody can reproduce.

Who creates the schema

spring.jpa.hibernate.ddl-auto

Must remember — Boot does not set it, and no value is a migration

Spring Boot never sets ddl-auto. It reads whatever is configured, and if nothing is configured it asks the HibernateDefaultDdlAutoProvider, which returns create-drop for an embedded database and none for anything else — and forces none when Flyway or Liquibase is on the classpath. So "I set update in the test profile and nothing happened in production" describes a profile only the test profile read. The stronger point for an interview: no value of ddl-auto is a schema migration tool. update will not rename a column, will not drop one, will not backfill, and will not tell you what it did. The schema is a versioned artefact, changed by ordered, reviewed, checksummed scripts.

Interview trap — the checksum mismatch that gets "fixed" with repair

Flyway stores a checksum per applied migration and refuses to start when a file that has already run has changed — which is the feature working. Someone in a hurry runs flyway repair, the application comes up, and the environment now claims a schema state that was never deployed; the next developer reasoning about that database is reasoning from a fiction. The correct response is to find out who edited an applied migration, restore it, and write a new migration for the intended change. Applied migrations are immutable, and a checksum mismatch is tamper-evidence rather than a nuisance.

Changing a schema that is already serving traffic

JDBC batching

spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50              # statements per JDBC batch
          order_inserts: true         # group same-entity inserts, so the sequence is hit in id order
          order_updates: true
        generate_statistics: true     # off in production; the counters are not free
Scaling reality check — 50 round trips become 1, unless the ID strategy stops it

With batch_size set, 50 inserts are one or two round trips instead of 50. But with IDENTITY generation the batching is inert — the database assigns the id from the insert, so Hibernate must know each id before the next statement, which forces a round trip per row and makes batch_size a no-op. A SEQUENCE lets Hibernate fetch a block of ids up front (allocation size 50 in Hibernate 6) and batch freely, at the price of gaps after a rollback. TABLE also batches, but serialises every writer in the whole application on one row.

Two further things decide whether batching reaches the driver. First, the driver has its own rewrite setting — rewriteBatchedStatements on PostgreSQL, reWriteBatchedInserts on MariaDB, useBulkCopyForBatchInsert on SQL Server — and without it you have a batch that is still N statements, merely handed over at once. Second, on MySQL the rewrite conflicts with useServerPrepStmts: enabling batching makes Hibernate emit the rewrite, which is mutually exclusive with server-side prepared statements. Check the driver's own documentation for that pair before assuming a batch is one round trip.

Locking

@Version
private long version;          // UPDATE ... WHERE id = ? AND version = ?

@Lock(LockModeType.PESSIMISTIC_WRITE)   // SELECT ... FOR UPDATE
@Query("select p from Product p where p.id = :id")
Optional<Product> lockById(@Param("id") Long id,
        @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-1")));
Must remember — a pessimistic timeout of 0 waits forever

The values are the ones people get wrong, because they are the JPA ones and they run counter to intuition: 0 means wait indefinitely, and -1 means fail immediately, that is NOWAIT. A handler that assumes 0 means "no wait" does not fail fast — it parks a request thread and a database connection for as long as the lock is held, which converts a contention problem into an outage. The default is whatever the database does, so set it explicitly.

The choice between the two is not preference. @Version is optimistic: no lock is held, the losing writer gets an OptimisticLockingFailureException at flush, and the application decides whether to retry — which is why it is the right default for user-facing edits. Pessimistic locking is correct when the read-modify-write is not idempotent — taking a seat, decrementing stock, claiming a job — and it is a throughput ceiling wherever every writer must hold the row, because the lock serialises the critical section and turns a hot row into a queue. Isolation-level semantics and the anomaly table belong to the Database track; what JPA adds here is only the lock mode and these two timeout values.

Interview trap — "the pool is the bottleneck" is what you say before measuring

Both failure modes are visible in metrics and they look nothing alike. Pool too small: high acquisition wait, a flat active count well below the maximum, and a database at a fraction of its capacity — the requests are queuing in your JVM, not in the database. Pool too large: active pinned at the maximum, database CPU and context switches at their ceiling, and total throughput flat as the pool grows — every extra connection makes each one slower and nothing arrives sooner, because the database was already saturated. A useful starting point is one database instance's cores plus its spindles, divided across the instances that share it; but the first time active sits at the maximum, the answer is the database, not the pool. And the thing to run before changing either is the Database track's EXPLAIN (ANALYZE, BUFFERS) on the statement that dominates the profile, because no pool size fixes a sequential scan.

Must remember — when to leave the ORM

The honest answer is that you leave it when the first workaround appears, not when the tenth does. A custom repository fragment with a JPQL query is the first step. Hand-written native SQL is the second. A JdbcTemplate for a reporting query is the third. By then you have given up the persistence context for that path, the mapping, the first-level cache and portable SQL — so the cost of continuing inside the ORM is no longer obviously lower, and the benefit of staying (one dialect, identical semantics) is gone.

The symptom of having decided too late is a report that is correct, takes forty seconds, has three hand-tuned indexes and a bespoke chunking loop, and no test. The decision to leave is cheap when the requirement arrives and expensive when the workaround is already load-bearing. Volume 9 covers where to put the microbenchmark that settles the argument with a number instead of an opinion.
