Volume 9 — Testing & Production Troubleshooting

Which tier can catch which bug, what each test slice actually wires, and the two-minute diagnostic that separates a deadlocked thread from a starved connection pool.

  • 8 sections
← Prev Next →

If you only remember five things

  1. A unit test structurally cannot see the container. It builds the object graph itself, so a missing bean, an unbound property, a failed @Conditional and a @Transactional self-invocation all ship behind a green suite. That — not "more confidence" — is the argument for integration tests.
  2. @MockBean is deprecated as of Spring Boot 3.4. The replacement is the Framework's @MockitoBean, and it is not a rename: it cannot go on a @Configuration class, so migrating one means restructuring the configuration.
  3. Mock at the process boundary, run against the data boundary. H2 in PostgreSQL-compatibility mode emulates syntax, not semantics — a SELECT FOR UPDATE test passes there and double-processes in production because the row lock was never real.
  4. The heap is not the process. 200 Tomcat threads reserve roughly 200 MB of stack before any business code runs, which is why MaxRAMPercentage sits at 70–75% and why an -Xmx equal to the container limit guarantees a silent OOMKill — exit 137, no heap dump, no OutOfMemoryError.
  5. Three jcmd <pid> Thread.print -l dumps, ten seconds apart. One dump cannot tell a thread that is working from one that is stuck. What never changes across all three is the bug.

No section matches that filter.

01

The test pyramid

The pyramid is not three counts. It is a map of which tier is the only one capable of catching a given class of bug — and in Spring the mapping is unusually sharp, because only the high-level tiers execute the container.

Four tiers, and the last column is the one that decides the budget
TierWhat it is in SpringRuns inStructurally CANNOT catch
UnitPlain JUnit, no Spring. new OrderService(repo, clock) Milliseconds, hundreds of themWiring. Anything the container does
SliceOne auto-configuration, real context. @WebMvcTest, @DataJpaTest ~1–3s, tensCross-slice wiring. Anything the slice's filter excludes
IntegrationFull context, real or containerised infrastructure. @SpringBootTest 3–15s per distinct context, tensCross-service. Anything outside the JVM
E2EThe deployed system, real HTTP, real dependencies Minutes, a handfulThe internals. Anything behind a mock
Must remember — why the expensive tier exists at all

Component scanning, conditional beans, @ConfigurationProperties binding, JSR-380 validation, auto-configuration ordering, the BeanPostProcessor chain and proxy creation all happen at context refresh. A unit suite cannot observe any of it — not because nobody wrote the test, but because the technique has no container in it. The mirror image is the reason teams over-invest: a @SpringBootTest that mocks the repository is a slow test that proves the context loaded and that Mockito works.

So rank the backlog by evidence rather than by a tool. Pull the last three production incidents, write down the test that fails before each fix, and queue those. Three winners recur: a transaction-boundary test that asserts a rollback really happens (V4), a query-shape test that fails when a query becomes N+1 (V6), and a configuration-binding test that fails when a required property is absent. A "happy path for every service method" backlog feels productive and is almost never what the incidents needed.

Trade-off — coverage as an outlier signal, not a threshold

Coverage has exactly one genuinely useful property: it finds code nobody thought about. A class at 0% in a two-year-old service is alarming, because nobody is sure what happens there. Flips on: it works as an outlier detector ("this file is 4%, why?") and fails as a threshold ("we must be above 90%"). Once 90% is a target, the cheapest lines to cover are getters, constructors and toString — and that work displaces the rollback test which would have caught a real incident. The staff-level version: a 90% suite with no rollback assertion is more dangerous than a 40% suite with one, because the number suppresses the discussion.

Four sources of nondeterminism, and the replacement for each

Must remember — the test of a suite

Not "how many tests pass" but "does the suite ever fail for a reason unrelated to a change?" Order-dependent tests are worse than no tests, because they are unreliable — and an unreliable suite trains the team to re-run failures rather than read them, which makes a real failure look like a flake. The re-run becomes the workflow and the flake budget quietly becomes "whatever we can tolerate".

02

Test slices & the context cache

Each slice is one auto-configuration applied to a minimal context, plus a type filter that decides what survives. The design rests on a single rule you must learn per slice: what it includes and what it excludes. The figure below is that rule, drawn — because a slice's blind spot is invisible until you see the whole context with one column missing.

Every slice, what it wires, and what it cannot see
AnnotationLoads for realExcludesFails when
@WebMvcTest @Controller, @ControllerAdvice, WebMvcConfigurer, filters, Jackson, message converters @Service, @Repository, @Component generally You need a service — which is exactly when you reach for @MockitoBean, and the slice stops being one
@DataJpaTest @Entity, JPA repositories, JpaRepository query methods, an in-memory or replaced DataSource Everything that is not persistence You need a service or a controller
@JsonTest Jackson auto-configuration, ObjectMapper Everything else You need Spring at all, arguably
@RestClientTest The HTTP client under test, Jackson, a mock ClientHttpRequestFactory The server side entirely You want to test what the server returns — this slice fakes the request, not the response
@JdbcTest JdbcTemplate, an embedded or replaced DataSource, SQL initialisation JPA, services, controllers You are using JPA
Must remember — a slice that needs mocks is testing too much

That is the design rule the slice annotations exist to enforce. @WebMvcTest plus three mocked services is not a slice — it is a slow @SpringBootTest with extra steps, and worse, because the mocks hide exactly the wiring the slice was supposed to check. The correct move is to move the assertion down a level: test the controller's collaboration contract as a plain unit test with a mocked service and no Spring at all, and let @WebMvcTest cover only what is slice-specific — message converters, validation, status codes, @ControllerAdvice handling.

@WebMvcTest(OrderController.class)          // NOT a @Configuration class
class OrderControllerTest {

    @MockitoBean OrderService orders;       // Framework 6.2 / Boot 3.4+
    @Autowired MockMvcTester mvc;           // the fluent successor to MockMvc

    @Test
    void rejectsMissingSku() {
        mvc.post().uri("/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                         {"qty": 2}
                         """)
                .assertThat()
                .hasStatus(HttpStatus.BAD_REQUEST)
                .bodyJson().extractingPath("$.errors[0].field").isEqualTo("sku");
    }
}
@DataJpaTest
class OrderRepositoryTest {

    @Autowired TestEntityManager em;        // flush() forces the SQL to happen NOW

    @Test
    void rejectsNegativeQuantity() {
        em.persist(new Order(-1));          // pending — nothing has reached the database
        assertThatThrownBy(em::flush)       // the constraint fires HERE, not at teardown
                .isInstanceOf(DataIntegrityViolationException.class);
    }

    @Test
    @Transactional(propagation = Propagation.NOT_SUPPORTED)   // the slice's default only
    void rollsBackOnFailure() { /* ... */ }                  // means "roll back after me"
}

The default @Transactional on @DataJpaTest is a convenience — it means "roll back after each test", not "you are testing transactions". A test asserting on a row that only exists inside the test transaction proves less than it looks, so the moment the subject is the boundary you switch it off with NOT_SUPPORTED and own the transaction yourself. What propagation and rollback actually do is owned by Volume 4; what belongs here is the fact that the slice's default hides the thing you came to test.

Interview trap — @MockBean is not a Boot annotation anymore

As of Spring Boot 3.4, org.springframework.boot.test.mock.mockito.MockBean and @SpyBean are deprecated in favour of the Spring Framework's org.springframework.test.context.bean.override.mockito.MockitoBean and @MockitoSpyBean. The senior answer adds the why: the capability moved into the framework so bean overriding works in any test context, not just Boot's, and the move was a deprecation rather than a removal because it is a migration, not a rename — @MockitoBean is not supported on @Configuration classes, so a configuration that declared @MockBean on itself must be restructured to declare it on test-class fields.

Interview trap — @MockitoBean creates the mock when no bean exists

enforceOverride defaults to false (BeanOverrideStrategy.REPLACE_OR_CREATE). Source wording: "a mock will be created if a corresponding bean does not exist". So a typo'd field name, a bean you never registered, or a condition that did not fire all give you a passing test asserting against a mock nobody wired — where @MockBean failed loudly. The replacement is quieter, not stricter. Use enforceOverride = true for fail-fast. Two more from the same javadoc: only singleton beans can be mocked, and under @ContextHierarchy every @MockitoBean applies to all levels unless contextName pins one.

webEnvironment — the attribute that decides whether a real server exists
ValueWhat happensUse forCost / trap

MockMvc runs in-thread, so it cannot catch a timeout, a real serialisation difference, a container-level filter, a character-encoding default or an error-page dispatch
RANDOM_PORT A real server on an ephemeral port; @LocalServerPort is injected Tests through TestRestTemplate or WebTestClient that need real HTTP Real Tomcat, real socket, real serialisation — and TestRestTemplate does not throw on 4xx or 5xx, which surprises people in shared helpers

MOCK does not mean "the web layer is untested" — it means the servlet container is not under test. TestRestTemplate, WebTestClient and MockRestServiceServer all bind to it, so a controller test that "needs the socket" is usually testing the wrong layer. The flip is narrow and worth naming: a handful of RANDOM_PORT tests covering an agreed list — filters, security, error handling — is the right proportion; a suite of them is not.

Scaling reality check — the context cache is why a container-backed suite takes 25 minutes

SpringExtension keeps a static cache of ApplicationContext instances keyed on the MergedContextConfiguration — classes, locations, active profiles, property sources, context customisers, parent. So suite cost is linear in distinct configurations, not tests. Thirty classes sharing one configuration refresh once; thirty classes each adding a @TestPropertySource entry or a @MockitoBean refresh thirty times at 3–15s each. The default cache size is 32 and raising it via spring.test.context.cache.maxSize only helps when you have more than 32 genuinely reused contexts.

The bill has a second column: each cached context holds live singletons, and a HikariDataSource in one can hold up to 10 real connections. 32 cached contexts is up to 320 idle connections against whatever the test profile points at — and if that is shared staging, the suite is a resource leak with a build pipeline attached. And note the correctness side: a shared context means a shared singleton, so a bean mutated by one class is still mutated when the next class reuses it.

Test-profile divergences that hide production bugs — the rule is where it points, never how it behaves

Pointing a test at a container instead of a developer's laptop is correct. Halving a pool size or dropping a timeout is a behavioural change that removes exactly the code path you need to test — and a test profile is the one place someone gets to make the application easier to work with, so every such relaxation is invisible unless somebody deliberately goes looking.

03

Testcontainers

A container makes the data boundary real: the SQL, the dialect, the locking and the constraints are the production ones. The value is not convenience — it is the specific class of bug that a six-month-green service then ships on its first production migration.

@Testcontainers
@SpringBootTest
abstract class PostgresITBase {                    // ONE container for the whole JVM

    @Container
    @ServiceConnection                               // Boot 3.1+ — no @DynamicPropertySource
    static final PostgreSQLContainer<?> POSTGRES =
            new PostgreSQLContainer<?>("postgres:16-alpine")
                    .withDatabaseName("test")
                    .withInitScript("db/migration.sql");
    // .withReuse(true)  — local inner loop only. NEVER in CI.

    @DynamicPropertySource                            // per-CLASS schema: the container is
    static void perClassSchema(DynamicPropertyRegistry r) {   // shared, the schema is not
        r.add("spring.datasource.hikari.schema", () -> SCHEMA);
    }
}

@ServiceConnection matters beyond line count. With @DynamicPropertySource you hand-write the property names, and a typo there produces a context that quietly starts against whatever else was on the classpath, with no error. @ServiceConnection reads the container's own metadata, so the mapping cannot be wrong — and adding Postgres plus Kafka plus Redis does not multiply the boilerplate. It can coexist with a @DynamicPropertySource: the base class supplies the connection statically, the subclass adds its per-class schema.

Must remember — the rule for where to mock

Mock at your process boundary; run against your data boundary. Outbound HTTP, message brokers, clocks and randomness get faked; databases get containers. The reason is not ideology. An HTTP client's contract is a small documented set of responses, and the interesting behaviour is in your handling of them — serialisation, error mapping, timeout, retry — which a mocked interface skips entirely. A database's contract is the actual behaviour of your SQL against your schema under your concurrency, which is exactly what cannot be faked: a mocked repository proves the service calls findById and branches on the result, and passes identically on a schema where the column was renamed.

Fakes rather than mocks where the dependency has behaviour worth exercising — an in-memory PaymentClient that stores idempotency keys makes "never charged twice" a real test; a mock makes it verify(payment).charge(anyTimes()), which proves nothing about the key.

Trade-off — withReuse(true): right locally, catastrophic in CI

Reuse exists for a real reason: a developer pays container start-up on every mvn test, and reuse removes it entirely — the difference between a 3-second and a 40-second inner loop. Flips on the environment: it is a local developer-loop optimisation and belongs in zero CI configurations, because the whole value of a green build is that it means something.

The failure it causes is local-only and baffling: the data directory survives between runs, so a schema from a migration you have since reverted is still there (tests pass locally), a Flyway baseline created on first run means migrations are now skipped, and you are debugging against data you did not create. Reuse also requires an explicit opt-in on the consuming side, so behaviour differs between "I ran it once" and "someone else ran it".

Container start-up dominates: 1–3 seconds for Postgres to become ready, 30–60 seconds to pull the image the first time. One container per test class turns a 60-second suite into a 25-minute one, so the fix is a singleton container inherited from a base class, a unique schema per class so classes can run in parallel, and a rollback transaction per test so cleanup costs no DELETE. In CI, pre-pull the image in the build image and share one container per JVM; if the suite is still too slow, shard it across runners — do not go back to H2, because the alternative is a suite that is fast and wrong.

04

Mocking & test design

The Mockito mechanics matter less than the design rule they serve. What a senior interviewer is testing is whether you know where the boundary is — and the boundary is the process, not the class.

@ExtendWith(MockitoExtension.class)        // STRICT_STUBS is the default — leave it
class CheckoutTest {

    @Mock PaymentClient payment;
    @Mock PaymentClient fraudCheck;        // same type: @InjectMocks would GUESS

    // Construct the subject explicitly. It fails to compile the moment a
    // dependency is added, added wrong, or added in the wrong order.
    private final Checkout checkout = new Checkout(payment, fraudCheck);

    @Test
    void chargesOnceOnDecline() {
        given(fraudCheck.passes(any())).willReturn(true);
        checkout.settle(Cart.of("A-1"));

        verify(payment).charge(argThat(r -> r.amount().signum() > 0));
    }
}
Must remember — @InjectMocks hides the thing you want checked

For constructor injection, Mockito picks the constructor with the largest number of arguments and assigns the mocks positionally, by type. With two PaymentClient fields the assignment is arbitrary, declaration order is not guaranteed, and the swap is silent. For setter or field injection it matches by type first and then by field name — less dangerous, still implicit. An explicit new Checkout(payment, fraudCheck) fails to compile when a dependency is added, makes the test's own wiring visible, and by construction shows you how many collaborators the class really has. Rule: @InjectMocks for a one-dependency class, explicit construction for everything else.

Four stubbing mistakes that cost real debugging hours
PitfallWhat you seeThe fix
Stubbing with an argument the code never passes A silent null, then an NPE pointing nowhere near the cause STRICT_STUBS raises PotentialStubbingProblem at the real call site
Mixing raw values with matchers InvalidUseOfMatchersException at the next interaction, not at the line that caused it Once you use any(), eq() or argThat(), every argument must be a matcher
thenReturn(a, b, c) for changing values The same Order for all three calls Chain .thenReturn(a).thenReturn(b), or thenAnswer for a cursor or a value derived from the argument
any() matching null Since Mockito 2, any() matches null and any(Class) does not — a null-related failure instead of a stubbing one Choose the matcher deliberately for the null case
when(spy.method()) Stubbing calls the real method — fatal if the spy's constructor touches the database doReturn(x).when(spy).method()
Interview trap — why teams keep turning STRICT_STUBS off

Both exceptions it raises point at a real defect in the test. UnnecessaryStubbingException means the test carries state nothing exercises — usually copy-paste from a neighbour, and usually a sign it asserts less than its author thinks. PotentialStubbingProblem is the silent-null failure above, caught at the call site instead of twenty lines later. Teams disable the mode because the noise is unwelcome, not because the diagnosis is wrong; the alternative is a suite that quietly returns null and false from unstubbed calls. The related trap is verifyNoMoreInteractions, which fails on calls the code makes for reasons unrelated to the assertion — a toString() inside a log statement, a hashCode() when the mock enters a set.

Must remember — over-mocking re-implements the system

A test that mocks every collaborator asserts only that the class calls its collaborators. It fails on every refactoring — rename a field, reorder two calls, extract a private method — and it does not fail when the business logic is inverted. Charge the customer twice and notify once, and it passes, because it was written against the shape of the old code. The cost is review throughput: every PR needs two or three "fix the mock" commits, so teams stop refactoring, which is a far worse outcome than a weak suite. The useful diagnostic is one line: if your mock has no I/O in it, you probably should not have mocked it. Everything in-process with real logic is a candidate for a fake or a real object.

Test data is a compiler-error decision. Positional constructor literals break at every call site when a field is added — and they break in test files, so the error message points at a test. A builder turns that into one compile error, and new OrderBuilder().customer("cus-9").status(PAID) declares its own preconditions where a nine-argument call makes the reader count. Build defaults for every field: a builder whose point is naming only the relevant fields has to make the irrelevant ones safe. An object mother is right for a small, genuinely business-wide set of scenarios and becomes a builder with a shared, stale API past about ten.

05

Pools, memory & triage

This is the chapter that is worth memorising: a number, a command, and a failure mode. JVM heap sizing, GC internals and the jmap/jstat mechanics are owned by the Java track — what belongs here is the arithmetic that decides whether a Spring service survives a container, a connection pool and a slow dependency.

Scaling reality check — the container that OOM-kills the JVM

A pod requests 512Mi; a JVM that cannot see the cgroup filesystem reads the host's 64 GiB and sizes a 16 GiB heap; the kernel kills the process at 512 MiB. Result: exit 137, no stack trace, no OutOfMemoryError, no heap dump — because the kernel acted before the JVM could throw. The log line that gives it away is the reported max heap at startup. Flips on: the flag is only correct if the JVM can see the limit — JDK 10+ is cgroup-aware by default, but a different base image, -XX:+IgnoreUnrecognizedVMOptions swallowing the flag, or a launcher overriding JAVA_TOOL_OPTIONS all defeat it. Verification is never the flag's presence, it is the number in the log.

The fix is one flag — -XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=30, leaving roughly 150 MiB of a 512 MiB limit for metaspace, code cache, thread stacks and direct buffers. The heap is not the process: 200 Tomcat threads at about 1 MB of stack each is ~200 MB committed before a line of business code runs, so -Xmx equal to the container limit guarantees an OOMKill on the first request that touches all of it.

HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl(url);
cfg.setMaximumPoolSize(10);        // DEFAULT — sized as if every app were a monolith
cfg.setMinimumIdle(2);             // default TIES TO MAX: 20 instances = 200 idle connections
cfg.setConnectionTimeout(2_500);   // DEFAULT 30_000 — half a minute holding a Tomcat thread
cfg.setMaxLifetime(1_800_000);     // DEFAULT 30m — must be BELOW any proxy's idle timeout
cfg.setLeakDetectionThreshold(0);  // DEFAULT off — set 5000 while debugging, then off again

Interview trap — "make the connection pool bigger"

The correction is the interesting part. Past the knee of the cores + disks curve, more connections mean less throughput — more lock contention, worse buffer-pool locality, a longer tail. And a small pool is a containment mechanism: it bounds how much concurrency this service can push at the database, which is exactly what stops a traffic spike cascading into a database outage. The sentence most candidates get wrong is the cost of a too-small pool: it is queueing latency, not lost throughput. If a query holds a connection for 1 ms and the database does 8,000 queries a second, eight connections already sustain 8,000/sec — ten is past the knee, and if the service is not achieving that the bottleneck is the network call, not the pool. The signal to look for is threads visibly parked in HikariPool.getConnection, which looks exactly like a slow database in every latency metric.

The last row is the one that catches people, because the instinct is to raise the thread limit. The seven signatures are not seven severities — they are seven different owners of the fix, and in four of them the fix is somewhere other than the JVM. Read the row as "who do I go and talk to": the database team, the dependency's team, the author of the class holding the lock, the author of whatever is creating pools.

Must remember — the two-minute diagnostic, in order
  1. jcmd <pid> Thread.print -l three times, ten seconds apart. Costs nothing, needs no restart and no APM licence, and it separates the four failure modes that look identical from outside. What never changes is the bug.
  2. jcmd <pid> JFR.start name=diag settings=profile duration=60s when the dumps say waiting without saying on what. JFR shows allocation, locking, GC, socket and exception data a dump cannot, and it shows the inlined stack that makes teams wrongly conclude "it's all in the framework".
  3. The GC log, because a latency spike with flat CPU is very often a full GC — and that one needs no process access at all.

JFR profiles: default is ~1–2% overhead and is what you leave on permanently with a rotating buffer (maxsize=500m,maxage=2h); profile is ~5–10% with 10 ms sampling plus every exception, lock and socket operation, and is for a bounded capture or a load test. Leaving profile on continuously is the common mistake, and the resulting 3% latency rise gets attributed to something else. The reason to record continuously is retrospective: a recording started at the beginning of an incident has already missed the interesting part. The same argument applies to GC logging, which costs well under 1% of throughput — and which must be rotated (filecount=5,filesize=50M), because an unrotated GC log fills the disk and takes the pod down.

Virtual threads

spring.threads.virtual.enabled=true, Boot 3.2+, and it also needs Java 21+. Scale, not speed. A virtual thread's stack lives in the heap, so creating one is cheap — but it runs code no faster than a platform thread. A CPU-bound workload gains nothing. Full treatment in vol09 §5.8.

Scheduling Moves to SimpleAsyncTaskScheduler, which ignores all pooling properties.
Connection pool Unchanged, and now the binding constraint. Every parked continuation still wants a connection.

Pinning, by JDK version — the single most-repeated virtual-thread claim, and it is version-conditional:

Scheduling knobs: jdk.virtualThreadScheduler.parallelism (default: core count, a small work-stealing ForkJoinPool in FIFO — not the LIFO common pool) and jdk.virtualThreadScheduler.maxPoolSize (default 256). Blocking that is not pinning may temporarily expand the pool; pinning does not — that asymmetry is what makes pinning starve the scheduler. Use the jdk.VirtualThreadPinned JFR event (on by default, 20 ms threshold) rather than the removed system property.

Interview trap — jstack cannot see virtual threads

jstack and jcmd Thread.print show none of them, so a virtual-thread service looks deceptively quiet. The command is jcmd <pid> Thread.dump_to_file -format=json vt.json. It carries no object addresses, locks or heap statistics, it does not pause the application, and carrier frames do not appear in the virtual thread's stack.

Interview trap — declaring any Executor bean silently disables the whole thing

The auto-configured executor is @ConditionalOnMissingBean(Executor.class). Declare any java.util.concurrent.Executor — a scheduling pool, a one-component executor, a test double — and it stands down, so @Async runs on yours. The flag is not broken; nothing tells you it stopped applying.

Interview trap — do not pool virtual threads to limit concurrency

JEP 444 is explicit: "do not be tempted to pool virtual threads in order to limit concurrency. Instead use constructs specifically designed for that purpose, such as semaphores." Pooling was idiomatic only because platform threads were expensive. The sizing discipline survives the migration — it just moves from a thread pool to a semaphore.

06

Distributed failure modes

Every mechanism in this chapter is the same defensive move: a bound on how much a dependency can take from you. A service with none of them has no answer when a collaborator misbehaves, and availability becomes a function of its dependencies' patience rather than of its own design.

Four bounds. Read the "does NOT bound" column — that is the whole distinction
MechanismBoundsDoes NOT boundFails by
TimeoutHow long you wait for one call How many concurrent calls you make — 200 threads × 30 s is still an outage Returning an error after the deadline
BulkheadHow many concurrent calls you make How long each takes — 20 permits against a 30 s hang still parks 20 of your threads Rejecting immediately when the bulkhead is full
Circuit breakerHow many calls you attempt at all, over time What a single in-flight call consumes Opening the circuit and failing fast
Load limiterThe arrival rate Whether the work already in flight can finish Shedding deliberately, with Retry-After

The most often missing is the simplest: a timeout set to your end-to-end request budget, not to the dependency's characteristic latency. At its 30-second default a failing dependency consumes the whole thread pool before it fails, which is how an incident becomes the outage. If your SLA is two seconds, no downstream call gets thirty — and a dependency that needs thirty seconds to answer is one that should not be on the request path. Shedding follows the same discipline: reject before the resource is exhausted, not after, so a limiter that starts refusing at 80% of thread capacity still leaves room for accepted work to finish. Note also that load shedding is a product decision disguised as a technical one — some requests are refused on purpose, and somebody has to decide which, and tell the users.

@Bean
ThreadPoolTaskExecutor paymentBulkhead() {                   // BULKHEAD: its own threads
    var pool = new ThreadPoolTaskExecutor();
    pool.setCorePoolSize(20);                                // from the pool arithmetic
    pool.setMaxPoolSize(20);
    pool.setQueueCapacity(0);                                // reject, never queue
    pool.setThreadNamePrefix("payment-");
    pool.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
    return pool;
}

@Bean
CircuitBreaker paymentBreaker(CircuitBreakerRegistry registry) {
    return registry.circuitBreaker("payment", cfg -> cfg
            .failureRateThreshold(50)                        // % failures that open it
            .minimumNumberOfCalls(20)                        // never open on 3am noise
            .slidingWindowSize(100)                          // window of the last 100
            .waitDurationInOpenState(Duration.ofSeconds(30)) // how long OPEN stays open
            .permittedNumberOfCallsInHalfOpenState(5)       // trial calls
            .build());
}

The timeout is the third bound and the one with no bean: it belongs on the HTTP client itself, set to your end-to-end request budget. It is also the one most often left at its default.

Must remember — thread starvation is a containment failure, not a capacity failure

Two hundred threads, 190 blocked waiting for a connection, 8 in flight each holding one for four seconds, 2 serving trivial endpoints: 99% of the service cannot serve any request — including /health, and including the endpoint that would have told you what was wrong. That is the line between an incident and an outage. A user asking for a status page is refused exactly as hard as a user asking for their order. The fix that addresses the class rather than the instance is a hard statement timeout on every connection — statement_timeout in Postgres, a queryTimeout on the DataSource — so a pathological query cannot hold a connection indefinitely regardless of what the application code does. Raise maximumPoolSize and you have made the collapse faster.

Must remember — a bad circuit breaker kills more traffic than the outage

A breaker that opens on one failure rejects 100% of traffic for the duration of its open state, when the underlying error rate might have been 2%. That is strictly worse than having no breaker — you converted a partial failure into a total one. Three settings make it safe: a real minimumNumberOfCalls so the rate is measured on a sample rather than on one 3 am call; a slowCallDurationThreshold so slowness counts as failure, because a breaker that only counts exceptions will never open for the slow-but-returning-200s dependency that causes the actual cascade; and a fallback that is degraded rather than absent — a stale value, a cached decision, a default. A breaker that only rejects is a breaker that converts your dependency's problem into yours.

And a degraded answer must be distinguishable in the data: a metric, a log line, and a flag in the payload. A fallback returning a plausible value with no marker is worse than an error, because the business acts on it believing it is real — an empty recommendation list is indistinguishable from "there are none".

Must remember — exactly one layer owns the retry budget

Three attempts with no backoff, on a service called three times per request, across three hops, is 27× at the bottom of the chain — 3 × 3 × 3, not 3×. Then the degradation makes it worse: each retry takes longer, so each request holds connections and threads longer, so throughput drops, so the retry rate rises. Positive feedback. The rules that hold: exponential backoff with jitter (a hundred instances retrying at 100/200/400 ms arrive as a wall, and turn a smooth recovery into a second outage); cap the total time, not the attempt count; retry idempotent operations only, and never a 4xx, which will be wrong again; and retry at one level of a call chain only. That last rule removes the compounding factor entirely and is the cheapest resilience improvement available — though it is an organisational decision about who retries, not a technical one.

Bulkheads — the second row is the whole argument for thread pools
 Semaphore bulkheadThread-pool bulkhead
Bounds concurrent callsYesYes
Bounds the time a hung call takes from you No — it still parks the caller's thread for the full timeout Yes — it only parks a pool thread
Thread costFree20 threads (~20 MB) per bulkhead
Context propagation across the hopNone needed Must carry SecurityContext, RequestContextHolder and MDC

Read the second row as the decision. Twenty semaphore permits against a thirty-second timeout still parks twenty of your Tomcat threads for thirty seconds — the semaphore bounded the count and none of the consequence. A thread-pool bulkhead puts the work on its own threads, so a hang exhausts that pool and the rejection is immediate and cheap. The fourth row is where thread-pool bulkheads lose in a Spring application, and it is a ThreadLocal problem: @Async runs on a different thread, so a ThreadLocal-backed SecurityContextHolder or MDC is empty there unless the executor is configured with the TaskDecorator that copies them. Production practice

Production practice is mostly about making the system's state legible to someone who was not in the room when it was decided.

Configuration: the environment decides, the repository does not
Never committedAlways committed
spring.profiles.activeSensible, conservative defaults
Credentials, API keys, connection stringsThe shape of configuration — the @ConfigurationProperties class
Per-environment hostnames and pool sizesHealth, metric and log configuration
A prod profile file with real valuesValidation constraints on what must be present
Must remember — a committed prod profile makes the repository lie

The failure mode is not a security breach, it is a silent divergence: the file in the repository says pool size 50, the environment says 10, the environment wins — and someone reading the repository at 3am believes the service runs with 50. Set spring.profiles.default: prod so a missing profile setting fails toward production behaviour rather than toward a developer's laptop, and put @Validated plus JSR-380 on the properties class so a missing value is a startup failure rather than a null in a request path. The precedence ladder itself is Volume 1; binding is Volume 7 — note that @TestPropertySource sits at position 2, above command-line arguments and environment variables, so a test cannot be made to fail by setting the same property in the environment.

Feature flags are cheap when they are build-time and expensive when they are dynamic. @ConditionalOnProperty is evaluated once at startup, costs nothing per call, and can never put two code paths in production at once — its rollback is a deploy. A dynamic flag is a runtime branch, permanent until someone removes it, and two paths do run simultaneously. The real risk is arithmetic: ten flags is 1,024 combinations, and the useful question is not "can I enumerate them" — nobody can — but "can I explain, for any given user, why they saw this". That answer has to come from an audit trail (flag, value, subject, correlation ID) and a removal ticket with an owner, created in the same PR as the flag. Deploy mechanics — readiness probes, canary analysis, blue/green — are in Volume 7 and Volume 11.

RED and saturation — four signals, one of which is leading
SignalWhat it isWhy it is on the list
RateRequests per second, per endpointThe demand. Without it every other metric is uninterpretable
ErrorsFailures per second and the non-2xx rate — a count, never a booleanThe outcome. A boolean loses the magnitude
Durationp50 / p95 / p99 — never an averageAn average is a number nobody can alert on; p99 is what users experience
SaturationHikariCP active/idle/pending, Tomcat busyThreads, client pool utilisation, queue depth, GC pauseThe only leading indicator. Rate and errors are lagging; saturation is how you get warning. Published by Micrometer, almost never alerted on
Must remember — alert on symptoms, measure with causes

Rate, errors and duration are what the user experiences, so they are what pages a human. Saturation, pool depths and queue lengths are what explain an alert, so they are what you open once you have been paged. Every alert has to answer three questions: is this affecting users right now; what changed and when; what do I do first. An alert that cannot answer all three should not page anyone — and an alert named service_error_rate_high answers none of them, sending a 3am responder on three round trips to find the threshold, the dashboard and the runbook link. Alerting on every metric that crosses a threshold is alerting on nothing: the pager becomes noise, responders learn to triage by volume, and the real page is dismissed as the twenty-first one this hour.

Readiness is the other probe people get wrong, and the distinction is asymmetric on purpose. Readiness means "this instance can serve this traffic correctly" — can it get a connection from its own pool right now, are this version's migrations applied. It does not mean "the process started", and it must not fail when a downstream is degraded: if every instance fails readiness at once, a dependency's blip removes the entire fleet from rotation. That is how one wobble becomes a total outage, and it is why the readiness probe and the canary have to be designed together — a probe too eager sends traffic to an instance that cannot serve it.
