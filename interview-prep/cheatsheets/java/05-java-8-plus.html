What a lambda actually compiles to, why a stream pipeline touches each element exactly once, and the six behaviours that fail silently rather than loudly.

  • 8 sections
← Prev Next →

If you only remember five things

  1. A lambda is not an anonymous inner class. It compiles to an invokedynamic call site, and LambdaMetafactory generates the implementing class at first invocation — deferred, and cheaper per call than the hand-written form.
  2. Nothing in a pipeline runs until the terminal operation, and it runs element-at-a-time. Each element goes through the whole chain before the next one starts, which is the only reason short-circuiting and infinite streams are possible.
  3. sorted() and distinct() are stateful, so they break short-circuiting. infiniteStream.sorted().findFirst() hangs forever; the same pipeline with filter returns immediately.
  4. Collectors fail loudly where loops fail quietly. toMap throws IllegalStateException on a duplicate key unless you supply a merge function, and reduce silently returns a wrong answer if the identity is not a true identity.
  5. orElse(x) always evaluates x. orElseGet(Supplier) evaluates it only when empty — which is the difference between one database call and one per call.

No section matches that filter.

01

Lambdas & functional interfaces

A lambda implements a functional interface — exactly one abstract method. Its parameters and body supply that method; the rest is inferred from context.

Three questions that come up in every lambda interview
QuestionAnswerWhat it costs to get it wrong
What makes an interface functional? Exactly one abstract method. Default and static methods do not count A lambda stops compiling — and if the interface is on a public API, so does every caller
What does a lambda compile to? An invokedynamic call site, with LambdaMetafactory generating the class at runtime, on first invocation You argue for anonymous classes on performance grounds that stopped existing in Java 8
Can a lambda change a captured local? No. Only effectively final locals are captured, and the JVM copies the value rather than sharing the variable The accumulator that mysteriously stays at zero inside a forEach
Interview trap — the one everybody gets wrong

A lambda does not compile to an anonymous inner class. The compiler emits an invokedynamic instruction; at first call the JVM uses LambdaMetafactory to generate the implementing class, then caches and inlines it. The deferral is the point: generation happens only if the call site is reached, and the shape allows far more aggressive JIT optimisation.

Interview trap — @FunctionalInterface does nothing

It grants no capability: any interface with one abstract method is already a valid lambda target. Its only job is compile-time enforcement of the single-abstract-method rule, so a second abstract method added later breaks at the method, not at every call site that targets it.

@FunctionalInterface
interface Calculator {
    int calculate(int a, int b);                   // the ONE abstract method
    default void printInfo() { }                   // defaults never count
    static Calculator addition() { return (a, b) -> a + b; }
}

int factor = 10;                                   // effectively final
Function<Integer, Integer> timesTen = x -> x * factor;   // captures a COPY
// factor++;                                      // reassignment -> compile error

// inside a lambda, `this` is the ENCLOSING instance — lambdas have no own `this`
Must remember — the two capture details

Effectively final, and copied. A reassignment anywhere in the method, even in a branch that never executes, makes the lambda a compile error: it may run long after the enclosing frame is gone, possibly on another thread, and the JVM captures the value, not the variable. To accumulate, use an AtomicInteger, a one-element array, or reduce()/sum().

this is lexical. Inside a lambda it is the enclosing instance; inside an anonymous class, the anonymous one. Porting between the two changes meaning silently, and capturing this leaks the whole enclosing object graph.

Two things candidates assume wrongly. A stateless, non-capturing lambda is not required to allocate — the JVM reuses one cached instance. And this-free stateless lambdas are the safe default in a parallelStream(); a capturing one shares its context across threads (see Volume 6).

The function toolkit

java.util.function — seven interfaces cover almost everything
InterfaceTakesReturnsReach for it when
Predicate<T>TbooleanFiltering, validation rules
Function<T,R>TRChanging the type or the value
Consumer<T>TvoidA side effect — printing, saving, sending
Supplier<T>nothingTLazy production: a factory, a constant
BiFunction<T,U,R>T, URTwo inputs, one output
UnaryOperator<T>TTSame type in and out. Extends Function<T,T> — the only gain is the name
BinaryOperator<T>T, TTCombining two of the same type. Extends BiFunction<T,T,T>; this is reduce()'s type

All but the two operators compose through default methods: and, or, negate on Predicate; andThen, compose on Function; andThen on Consumer. Composed predicates short-circuit exactly like &&, so order the cheap, commonly-failing check first.

Method references — shorthand for a lambda that only calls a method
KindSyntaxReads as
StaticInteger::parseInts -> Integer.parseInt(s)
Bound instancemyList::addx -> myList.add(x) — the target is fixed now
Unbound instanceString::toUpperCases -> s.toUpperCase() — the target arrives as the argument
ConstructorArrayList::new() -> new ArrayList<>()
Interview trap — String::toUpperCase takes no arguments

It looks like the static form, because toUpperCase() declares no parameters. The functional interface's first parameter becomes the implicit receiver: as a Function<String,String> it runs fn.apply(s) against s.toUpperCase(). The receiver is supplied at call time, not at reference-creation time, so one reference serves any instance — and subclass overrides dispatch normally.

Function<Integer, Integer> plusOne  = x -> x + 1;
Function<Integer, Integer> timesTwo = x -> x * 2;

plusOne.andThen(timesTwo).apply(5);   // 12 — (5 + 1) * 2
plusOne.compose(timesTwo).apply(5);   // 11 — (5 * 2) + 1

Predicate<String> longName = s -> s.length() > 4;
Predicate<String> noSpaces = s -> !s.contains(" ");
longName.and(noSpaces).test("hello world");   // true

A named custom interface beats a generic BiFunction<X,Y,Z> when the operation is used often and domain-specific: the type parameters carry no meaning and the name does the communicating. If the behaviour is never passed around and never varies at runtime, a plain method is simpler than a field.

03

Stream fundamentals

A Stream is not a data structure. It holds no elements of its own; it is a one-time-use, lazily-evaluated pipeline over a source, composed of zero or more intermediate operations and exactly one terminal operation.

IntermediateTerminal
ReturnsAnother stream, so chaining worksA value, a collection, or void
ExecutionLazy — does nothing on its ownEager — runs the entire pipeline
CountZero or moreExactly one
Examplesfilter, map, flatMap, distinct, sorted, limit, skip, peek collect, reduce, forEach, count, anyMatch, findFirst
 
Stream.of(1, 2, 3, 4, 5)
    .filter(n -> { System.out.println("filter " + n); return n % 2 == 0; })
    .map(n -> { System.out.println("map " + n); return n * n; })
    .findFirst();
// filter 1
// filter 2
// map 2      <- map runs before filter 3 is ever called
// stops here — findFirst() is short-circuiting
Must remember — lazy, and single-use

list.stream().filter(...).map(...); with no terminal operation does absolutely nothing. No exception, no work, no output. And once a terminal operation runs, that stream instance is consumed: a second forEach on the same variable throws IllegalStateException. Re-iterating means calling .stream() again — a stream is a one-shot computation, not a container.

Sources are list.stream(), Arrays.stream(array), Stream.of(...), and the infinite generators Stream.iterate(seed, f) and Stream.generate(supplier) — the infinite ones only behind a short-circuiting terminal.

Trade-off — Stream<Integer> vs IntStream

Primitive specialisations (IntStream, LongStream, DoubleStream) skip autoboxing entirely and add numeric terminals sum(), average(), max(). Flips on: scale. For a handful of elements processed once the boxing cost is noise and the extra API is pure cost; inside a hot loop or over millions of elements, per-element Integer allocation is real GC pressure (IntStream.rangeClosed(1, 100).sum() boxes nothing at all). Converting back is asymmetric: mapToInt(Integer::intValue) cannot represent the null a boxed stream could hold, so it throws on one.

04

Stream operations

OperatorRuleWhat it bites
mapStrictly one-to-one; element count is preserved On a nested collection it produces Stream<List<T>> — a Stream<T> is what you actually wanted
flatMapOne-to-many, then flattened into one stream Removes exactly one level per call, so three levels of nesting need two calls
distinctequals/hashCode, exactly like a HashSet A type without both overridden deduplicates nothing, and it is not free — every seen element is retained
sortedStateful. Consumes the entire source before emitting anything Defeats short-circuiting entirely, and throws NullPointerException on a null element unless a null-handling comparator is supplied
limit/skipStateful, but short-circuiting skip(N) still walks the skipped elements, so deep offset pagination belongs in the database
peekDebugging only — the runtime may skip it entirely Business logic placed here silently does not run; count() can be answered without traversing at all
 
List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3, 4));

nested.stream().map(List::stream)      // Stream<List<Integer>> — still nested
         .collect(Collectors.toList());  // [[1, 2], [3, 4]]

nested.stream().flatMap(List::stream)  // Stream<Integer> — one level removed
         .collect(Collectors.toList());  // [1, 2, 3, 4]

// three levels of nesting need flatMap twice — each call removes exactly one
Interview trap — peek() for side effects

The runtime may skip calling peek() whenever it can prove the result is not needed. stream.peek(System.out::println).count() shows it: the count is often answerable from the size without traversing, so nothing prints. Put anything you depend on in forEach or map.

Two ordering facts. Elements within a groupingBy group's list keep encounter order even though the map is not ordered — pass LinkedHashMap::new or TreeMap::new when a downstream consumer needs deterministic group keys. And forEach does not itself guarantee encounter order; forEachOrdered is the explicit choice.

05

Reduction & collectors

reduce() folds elements into one immutable result; collect() is a general mutable reduction. A Collector bundles a supplier (create the container), an accumulator (add one element), and a combiner (merge two containers — invoked only under parallel execution, and so the part a custom collector is least likely to have been tested). For a plain single-value sum, reduce is more direct than reaching for a collector.

The collectors worth memorising, and the behaviour they guarantee
CollectorProducesThe specific that gets tested
toMap(k, v)A map Throws IllegalStateException on a duplicate key. Supply toMap(k, v, mergeFn) to overwrite or combine. A null value from v throws NullPointerException too
groupingBy(cls)Map<K, List<T>> Creates a key only for groups that have at least one member. Default map is unordered
partitioningBy(pred)Map<Boolean, List<T>> Always exactly two keys, true and false, even when one side is empty
mapping(fn, downstream)Transformed elements Transforms before the downstream collector runs — the only way to project a field inside a grouping
joining(d, p, s)One string Empty input yields prefix + suffix, not an error
toUnmodifiableList()An immutable list Java 10+. Disallows null elements. toList() (16+) is the same guarantee, more tersely
Interview trap — a wrong reduce identity is silent

The identity passed to reduce(identity, accumulator) must be a true identity — combining it with any value must leave that value unchanged. Zero for addition, one for multiplication, BigDecimal.ZERO for money. Use the wrong one and nothing is thrown: reduce(1, (a, b) -> a + b) returns every sum one too large, forever. The one-argument form has no identity to get wrong, which is why it returns an Optional.

Trade-off — is toMap's strictness good or bad design?

Debatable, and worth arguing either way. Failing fast catches a duplicate key where it becomes visible, which a silent map.put() in a loop would not. The cost: when overwriting really is the intent, the third argument is mandatory ceremony. Flips on: whether duplicates in your data are a bug or a rule. Do not reach for the merge function to silence a duplicate you have not explained.

record Employee(String name, String dept, double salary) {}

// count per department, one pass, no intermediate list
Map<String, Long> headcount = employees.stream()
    .collect(Collectors.groupingBy(Employee::dept, Collectors.counting()));

// true / false split, names only — mapping() transforms before the downstream
Map<Boolean, List<String>> earners = employees.stream()
    .collect(Collectors.partitioningBy(e -> e.salary() > 75000,
            Collectors.mapping(Employee::name, Collectors.toList())));

// "first seen" order needs the map factory, not just the classifier
Map<Character, Long> firstSeen = word.chars()
    .mapToObj(c -> (char) c)
    .collect(Collectors.groupingBy(c -> c, LinkedHashMap::new,
            Collectors.counting()));

Elsewhere, build the shape the business needs: toSet rather than toList then convert, summarizingDouble rather than four passes, and Collectors.teeing() (12+) rather than two traversals for two aggregates.

06

Optional

Optional<T> holds a value or is empty, and exists to make absence explicit in a return type, so a caller cannot forget there might be nothing. of asserts non-null and throws NullPointerException immediately if given one; ofNullable is the general-purpose factory.

Interview trap — orElse runs unconditionally

orElse(x) takes a plain argument, and Java evaluates arguments before the call, so the fallback is computed every time, present case included — a database round trip on a hot path where the value was already there. orElseGet(Supplier) defers it to the empty case only. The rule: orElse for a constant or trivial expression, orElseGet for anything with a cost.

Where Optional belongs, and where it does not
PositionVerdictReason
Method return typeYes Exactly the designed use. Name it findX — a getX that returns an Optional promises something the type contradicts
FieldNo Not Serializable, adds an allocation and a layer of indirection, and collides with the JavaBean convention. An immutable record is a defensible exception; a JPA entity is not
Method parameterNo Forces every caller to wrap. Overloading or a builder states optionality once, at the signature
CollectionNo An empty List already means "no results". Optional<List<T>> makes callers unwrap something that needed no wrapping
 
Optional<User> find(String id) {
    return Optional.ofNullable(db.lookup(id));
}

find("123").map(User::getAddress)
         .map(Address::getCity)
         .orElse("Unknown");

// eager: db.lookup("default") runs on EVERY call, present or not
String a = find("123").orElse(db.lookup("default"));
// deferred: only when empty
String b = find("123").orElseGet(() -> db.lookup("default"));
Interview trap — isPresent() + get()

It is the old null-check pattern wearing a new hat: identical semantics, none of the composability. Use map, filter, ifPresent, ifPresentOrElse, and the orElse family — map short-circuits to empty on a null step, so a chain needs no null checks. And get() on an empty Optional throws NoSuchElementException, not NullPointerException.

Optional reduces unchecked-null risk; it does not eliminate it. Unchecked get() still throws, and a method returning null instead of Optional.empty() violates a contract nothing enforces. Its explicitness is also only worth anything if the codebase adopts it consistently — half the API returning Optional and half returning nullable leaves callers unable to rely on either.

07

Default methods & hard problems

Must remember — why default methods exist

Java 8 needed to add forEach, removeIf, stream, spliterator and sort to Collection and List. Abstract methods would have stopped every implementation in the ecosystem working. Default methods are interface evolution without breaking binary or source compatibility.

interface Shape {
    double area();

    // a fallback body every implementation inherits, unchanged
    default String describe() { return "area=" + area(); }
}

The hard Stream problems are not built from exotic operators but from four primitives, and the difficulty is in knowing which one goes first.

Four problems, four compositions
ProblemPipelineThe decision in it
Duplicates in a list groupingBy(n -> n, counting()) → filter value > 1 → keys Not a distinct() problem at all — distinct throws the duplicates away
Second highest distinct() → sorted(reverseOrder()) → skip(1) → findFirst() distinct() first. Without it a repeated max occupies both first and second. Ask whether duplicates count as separate ranks
Flatten three levels flatMap(List::stream) twice One call removes one level, no more. Confirm each intermediate is Stream<List<T>> and not Stream<List<List<T>>>
First non-repeated character groupingBy(c -> c, LinkedHashMap::new, counting()) → filter == 1 → findFirst The map factory is what makes "first" mean anything; the default gives no ordering guarantee
 
List<Integer> nums = List.of(5, 1, 9, 9, 3, 7);

Optional<Integer> secondHighest = nums.stream()
    .distinct()                              // 9 counts once — without this,
    .sorted(Comparator.reverseOrder())       // 9 would be both first and second
    .skip(1)
    .findFirst();
// 7
Trade-off — when not to reach for a Stream

Streams pay for themselves on multi-step transformations. On a one-line sum they add per-element overhead — boxing on a reference stream, plus lambda dispatch — and on a five-element list the machinery costs more than the work. Flips on: step count. One operation is a loop; a chain is a stream. The same reasoning cuts the other way: past roughly five chained operations, or with multi-line lambdas inline, a stream stops being more readable than the loop it replaced, and a named intermediate step or an extracted method is the fix. Chain length is a weak proxy for complexity anyway — one dense predicate can be worse than six trivial ones.

Scaling reality check — the operations that stop being free
  • distinct() retains every element it has seen. It is a HashSet wearing a stream costume, and the memory scales with the input.
  • sorted().limit(10) over ten million elements sorts all ten million. A bounded priority queue answers the same question without the full ordering.
  • skip(offset).limit(page) still walks the skipped elements for most sources. Deep pagination belongs in the database's OFFSET or a cursor.
  • parallelStream() runs on the common ForkJoinPool, built for CPU-bound work. Blocking I/O inside it starves the pool rather than scaling. See Volume 6 for the threading model and Volume 9 for virtual threads — the tool for I/O-bound concurrency is not a parallel stream.
