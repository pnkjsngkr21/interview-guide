If you only remember five things

  1. Virtual threads scale I/O-bound concurrency, not CPU. For CPU-bound work you are still capped by core count, and a correctly-sized platform thread pool remains the right tool. "Virtual threads make everything faster" is the wrong answer.
  2. synchronized around a blocking call can pin a virtual thread to its carrier, in some JDK versions, defeating the unmount that the whole model depends on — and it hurts every other virtual thread, because the whole carrier is tied up. ReentrantLock does not pin.
  3. scope.join() does not propagate failure. throwIfFailed() is the line that surfaces it, and ShutdownOnFailure cancels siblings that are still running while leaving already-completed results alone.
  4. The OOM variant decides the fix. OutOfMemoryError: unable to create new native thread is the OS refusing a thread, not a full heap — raising -Xmx does nothing for it.
  5. Get an artefact before you guess. Bigger pool, more CPU, bigger heap: each of them buys time and raises the eventual bill. The dump, the GC log, the profile, or two heap dumps tell you which one is actually wrong.

01

Java 17 & 21: the features worth knowing cold

Records, sealed classes, and instanceof pattern matching belong to Volume 8. What remains is the rest of the modern surface that shows up in backend code.

The LTS releases, and what each one is actually remembered for
ReleaseHeadline for backend work
Java 8Lambdas, Streams, Optional — Volume 5
Java 11Standalone JRE removed, var in lambda params, HTTP Client API
Java 17Sealed classes, pattern matching for instanceof, records, text blocks
Java 21Virtual threads, pattern matching for switch plus record patterns, sequenced collections; structured concurrency still preview
Interview trap — the finalization version

Features are preview for a release or two before final, and citing the wrong one is the tell that a candidate read about Java years ago. Records were preview in 14/15, final in 16. Virtual threads preview in 19/20, final in 21. Sealed classes and instanceof pattern matching landed final in 17. Structured concurrency is still preview in 21 and needs an explicit --enable-preview.

int numLetters = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> 6;
    case WEDNESDAY                -> 9;
};   // exhaustive over the enum's values — no default needed

// A block body cannot fall off the end; yield supplies the value.
int result = switch (x) {
    case 1 -> 100;
    default -> {
        int computed = x * 2;
        yield computed + 1;
    }
};

Arrow form removes the fall-through footgun, and over a sealed type the exhaustiveness check is a compile-time guarantee re-evaluated on every build — add a permitted subtype in another file and a stale switch stops compiling. It does not give you a safety net in reflection-based code inspecting the hierarchy, and guard clauses (case Integer i when i > 0) run in case order, so their side effects become semantically load-bearing.

Interview trap — List.of() is not an unmodifiable wrapper

List.of(...) throws NullPointerException at construction if any argument is null. Collections.unmodifiableList(new ArrayList<>(...)) would have carried an existing null — it only blocked further mutation. Swapping one for the other in review is a behaviour change, not a cleanup. List.copyOf(existing) shares the same guarantee; only the shape of input differs.

Trade-off — text blocks, and the line that is not a security feature

Text blocks remove escaping and concatenation from static multi-line literals (SQL, JSON templates). The whitespace rules are stricter than most people expect: incidental indentation is stripped relative to the least-indented line including the closing """ delimiter, so moving the delimiter moves the output, and a delimiter on its own line implies a trailing newline. At the bytecode level a text block is an ordinary String constant. Flips on: a string built by many conditional branches is clearer as StringBuilder than forced into a rigid literal — and a text block is never a defence against injection: concatenating a parameter into a text-block query is the same vulnerability as before.

Java 21's sequenced collections give getFirst(), getLast(), and reversed() across List, LinkedHashSet, and LinkedHashMap — replacing index arithmetic and the iterator dance. reversed() is a live view, not a copy, so edits to the source show through it.

Migration reality

Phasing 8 → 11 → 17 → 21 beats one jump: each LTS step has had time to accumulate library and ecosystem compatibility, so you are not discovering three unrelated breaking changes in a single deploy. Records convert incrementally — the blast radius is the getX() to x() rename and serialization differences at real consumers, not the immutability.

02

Virtual threads

The whole trick — and the whole scaling claim — is that a virtual thread is unmounted from its carrier on a blocking operation and remounted later, possibly on a different carrier.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> doBlockingIOWork());   // one fresh thread per task
    }
}   // close() waits for every task — no shutdown() call needed
Platform thread vs virtual thread — the differences that change your design
Platform threadVirtual thread
Managed byOSJVM
Stack~1MB, fixed at creationOn the heap, grows and shrinks as needed
Creation costExpensive, OS-levelCheap enough to make millions
Best forCPU-bound workI/O-bound, mostly-blocked workloads
PoolingEssential; sizing is the hard part — Volume 6Do not. One thread per task, created fresh
ThreadLocalFine, with known leaks in pooled threadsDiscouraged at scale — a modest cost becomes millions of copies
Interview trap — three claims that are all wrong

"They make CPU-bound work faster." No: still capped by core count. "Pool them like platform threads." No: the whole point is that they are cheap, and the per-task executor is not size-bounded. "Pinning is just a virtual thread's own problem." No: it removes a carrier from a shared pool, degrading everyone.

The bottleneck moves — it does not disappear

Virtual threads remove the thread-count ceiling and relocate the constraint to whatever actually saturates. Database connections are set by the database, not by your threading model, and a pool that was accidentally protected by a 20-thread executor is now asked for thousands of concurrent connections. Rate-limited third-party APIs need a Semaphore regardless of how cheap the threads are. Plan for the new bottleneck explicitly, and point the capacity model at it.

Two migration facts that catch teams out. Pinning frequently comes from third-party library internals, not your own code, so review the whole call stack. And thread identity assumptions break: virtual threads are created and discarded constantly, so anything keyed on Thread.currentThread().getId() needs auditing. Instrument the migration with JFR pinning events — thread-count metrics will not surface pinning — and name your threads, since they have empty names by default.

03

Structured concurrency

Unstructured fan-out through ExecutorService gives every subtask a lifetime independent of the code that spawned it: nothing forces a parent to wait, nothing forces it to cancel, and a failure leaves siblings running for a result nobody will use. Structured concurrency closes that off at the type level — a subtask cannot outlive its scope.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user   = scope.fork(() -> fetchUser(id));      // a virtual thread
    var orders = scope.fork(() -> fetchOrders(id));    // fork() does not block

    scope.join();           // waits for both — but does NOT propagate failure
    scope.throwIfFailed();  // the line that actually surfaces it
    return new Profile(user.get(), orders.get());
}   // close() cancels anything still running
Interview trap — join without throwIfFailed

join() only waits. A scope that joins and returns can silently ship a null result for a subtask that failed three lines earlier. The ShutdownOnFailure policy is the defining part: one failure cancels the running siblings rather than leaving them to finish a result nobody wants. ShutdownOnSuccess is the mirror — first success wins.

Trade-off — what structured concurrency is not for

It is not a universal replacement for ExecutorService. Flips on two things: a fire-and-forget write that is meant to outlive the request fits a detached mechanism, not a scope; and a caller depending on graceful partial success gets all-or-nothing cancellation instead, a customer-visible behaviour change. Two more edges: the guarantee covers only what went through fork() — a raw thread or unmanaged executor created inside a subtask bypasses it — and ThreadLocal tracing context does not flow into the fork automatically, so a migration can quietly break request-trace continuity.

Adoption reality

Still preview in Java 21: it needs --enable-preview to compile and run, and the API can still change. Take real experience with it on internal tooling first, and treat the migration off the preview API as scheduled work rather than a surprise.

Production scenarios: performance & memory

Scenarios 1 to 4. The recurring shape: name the symptom precisely before choosing a fix. "Slow" and "out of memory" are both too coarse to act on.

Scenarios 1–4 — what it really is, and the trap
SymptomWhat it really isThe trap
API suddenly slow Time spent in the app, the network, GC, or a downstream — undecided until traced "The database is slow" is a hypothesis, not a finding. Check the GC log first: a Full GC pause is indistinguishable from a slow downstream from the outside, and ruling it out is cheap
HashMap-backed cache degrades O(1) assumes a well-distributed hashCode(). A poor one — or a key whose hash-relevant field is mutated after insertion — degrades toward O(n) Treeification bounds the worst case to O(log n); it does not restore O(1), and a mutated key stays invisible until that exact key is looked up again. Validate a fix against production keys, not uniform synthetic ones
Memory only ever climbs In a garbage-collected language, a leak means something is unintentionally still reachable Two heap dumps, diff instance counts by class, walk the GC root path to the retaining reference. Alert on the trend, not a fixed threshold — and review weekly, because a slow leak can sit under the threshold for months
OutOfMemoryError Which variant it is decides the entire fix unable to create new native thread is the OS refusing a thread, not a full heap. -Xmx does nothing for it. Hand-rolled HashMap caches are a disproportionate share of leaks — use a real caching library
Must remember — enable heap-dump-on-OOM fleet-wide

Turning it on per-incident means the one time you forget is the incident that mattered. As blanket policy it also standardises tooling across the fleet. The same argument applies to capturing a thread dump before restarting: in a real crisis nobody remembers, so automate it.

GC behaviour and heap layout belong to Volume 7; HashMap internals to Volume 4. What is new here is the diagnostic stance, not the mechanisms.

05

Production scenarios: threads & CPU

Scenarios 5 to 8. The common shape: the obvious fix delays the incident at higher cost — a bigger pool, more CPU, a bigger heap. Collect the artefact instead.

Scenarios 5–8 — what it really is, and the trap
SymptomWhat it really isThe trap
Thread pool exhausted Threads held too long by a slow downstream — not too few threads. Even a correctly-sized pool looks exhausted if tasks stop completing Growing the pool delays the same failure at higher resource cost. Timeouts and a circuit breaker address the cause. First ask whether load rose or tasks got slower at the same load
Deadlock in production A structural lock-ordering violation, and the JVM's own detector reports it directly — Found one Java-level deadlock, naming the threads and locks Adding threads cannot break circular wait; it just creates more deadlocked threads. Enforce the global lock order with static analysis or a lint rule — a wiki page relies on everyone remembering
CPU at 100% Genuine load, a hot loop, a busy-wait or livelock, or GC itself consuming cycles One aggregate number cannot separate them. Time spread across request handling is load; time flat in one method across samples is a bug. Correlate with traffic and recent deploys
GC pauses increasing A symptom with three causes: allocation rate, premature promotion, or a genuine leak Minor vs Full and the promotion rate point at different fixes. Cutting allocation rate is the highest-leverage lever; flag tuning is second. Note -XX:MaxGCPauseMillis is a G1-only knob
Interview trap — bounded everything, still broken

A bounded pool with a bounded queue and a DiscardPolicy never shows the classic OOM symptom — it silently drops work instead, which is arguably worse and will not look like "exhaustion" on a dashboard. Ask what the rejection policy does to the caller before you ask anything else about the pool.

Deadlock, starvation, and livelock as failure modes, and the dump patterns that tell them apart, belong to Volume 6. Two additions: a two-thread deadlock can be catastrophic if those two threads hold resources many others depend on, so severity does not track thread count; and separating deadlock from livelock needs multiple dumps, not one — a livelock shows threads changing state without net progress.

06

Production scenarios: concurrency bugs & scale

Scenarios 9 to 12. The shape here is precision again: the fix that looks obvious — synchronize more, make fields volatile, add servers — is almost never precise enough.

Scenarios 9–12 — what it really is, and the trap
SymptomWhat it really isThe trap
ConcurrentModificationException A fail-fast check on an internal modCount — overwhelmingly a single-threaded mutation during a for-each loop It is not a concurrency detector. Because the throw is often caught and logged generically, it gets filed as a "mysterious" concurrency bug and investigated as one. removeIf predicates must be side-effect-free
Race condition, wrong data Compound read-modify-write on shared state with no synchronization It is found by code review, not by reproduction. 100% line coverage tests no interleavings, and a race can coincidentally produce the correct result — which is why it survives testing
Multi-field inconsistency Two individually-safe field writes are not one safe pair; a reader can observe the object between them Making every field volatile changes nothing about this. Lock the combined update, or swap the whole object atomically
Slow after a traffic increase One specific resource saturating — queueing, not generalized slowness A database or HTTP connection pool is a bottleneck exactly as much as a thread pool is. Check them all in parallel rather than guessing which, and update the capacity model to point at the newly-found one 
// Two safe field writes are not one safe pair.
void apply(Order o) {
    profile.updateAndGet(p -> new Profile(p.user(), o.id()));   // one indivisible swap
}

// Or lock the combined update when the invariant spans a live object.
synchronized (this) { status = PAID; paidAt = clock.instant(); }
Must remember — non-linear means saturated, not bad

Latency that grows faster than traffic is queueing at a constrained resource, and it is a property of the mathematics rather than a verdict on your design — good systems provision before the threshold, they do not exempt themselves from it. Usually one resource is the primary constraint and the rest follow as cascading effects, so finding the first to saturate is the whole task. A normal p50 alongside a broken p99 is the classic fingerprint of intermittent saturation or a long GC pause.

Triage trap — two causes, one symptom

A race condition and a memory leak are observationally identical in the first minutes: "the service is getting slower under load". A thread dump and a heap dump separate them, not more staring at the symptom description. For the same reason, a mutual deadlock and a livelock both present as an unresponsive service — the mechanism, not the report, is the diagnosis.

07

The playbook

Each of the twelve scenarios is written in one shape, and the shape is the transferable part: Problem → Investigation → Root Cause → Solution → Prevention → Interview Answer. Prevention is a required field — a fix that resolves the symptom without closing the loop just moves the incident to a later date.

The reflex fix, and why it is the wrong one
ReflexWhat it actually does
Grow the poolDelays the same failure at higher cost, and hides a slow downstream behind a bigger symptom
Raise -XmxBuys time before a leak hits the same wall, and does nothing at all for the native-thread variant
Synchronize moreMakes a non-atomic operation safe, or just serialises the contention. Neither is what was wrong
Add serversScales the request arrival onto a bottleneck that was already saturated
Must remember — fix the first link, not the last symptom

A slow leak drives GC pressure, which drives pool exhaustion, which is what pages you. Tuning the pool leaves the leak in place and only changes when the next incident arrives. Root-cause ordering determines whether a fix holds, and complex incidents usually have several contributing causes — a latent bug, an unusual traffic shape, a monitoring gap that delayed detection — each a separate prevention action.

Interview trap — the failure mode is over-fitting

Knowing twelve scenarios well creates a real risk of forcing a novel incident into one of twelve round holes. Real incidents arrive as novel combinations of individually-understood causes. The honest answer to "are these twelve exhaustive" is no — they are a representative sample, and the framework is what transfers. The sentence that lands well in a scenario round is "I don't know, but here's how I'd investigate": real incidents involve situations nobody memorised an answer for, so a sound process beats a confident guess.

Keep the playbook alive — and re-check it after a migration

A fixed runbook goes stale exactly where it matters. Validate the twelve against your own incident history before investing training time, add a thirteenth when a new mode appears, and give each scenario a named owner so someone holds current depth. Two sections need rewriting the moment a service adopts virtual threads: pool-exhaustion diagnosis, largely obsolete for virtual-thread code paths, and thread-dump interpretation, where the dumps look different and can be far more numerous. Pinning is the obvious thirteenth entry.
