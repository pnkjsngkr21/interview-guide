Volume 4 — Collections Framework

What actually happens inside a HashMap on a collision, which list or map is wrong for the access pattern, and the three ways a collection silently lies to you.

  • 7 sections
← Prev Next →

If you only remember five things

  1. ConcurrentModificationException is a fail-fast check, not thread safety. It fires on a single thread the moment you mutate a collection through the collection instead of through its iterator, because the iterator compares a captured modCount on every step.
  2. ArrayList usually beats LinkedList, even for insert-heavy work. Growing an array is a bulk, cache-friendly copy; traversing nodes is pointer chasing. LinkedList genuinely wins only when you already hold the Node and need no traversal to reach it.
  3. A bucket treeifies on two conditions, not one. Eight or more collisions and a table of at least 64 buckets. Below 64, HashMap resizes instead — a small table with heavy collisions is assumed under-sized, not pathological.
  4. Mutating a field used in hashCode() after insertion makes the entry unreachable. The object stays in the bucket matching its original hash, so contains() and remove() look in the wrong bucket and report false. Make key fields final.
  5. ConcurrentHashMap is not just a synchronized HashMap. It locks per bucket, and it rejects null because get() == null is ambiguous between "absent" and "present with a null value" — and the containsKey() follow-up is itself racy.

Interview trap — why Map is not a Collection

Map holds key-value pairs, not single elements, so the Collection contract — add(E), iteration over single elements — does not fit its shape, which is why "why doesn't X extend Y" is asked. It is also why a Map cannot be passed where a Collection is expected, and why a for-each over a map does not compile: you iterate keySet(), values(), or entrySet().

Interview trap — not every Set is unordered

Only HashSet makes no ordering guarantee. LinkedHashSet preserves insertion order, TreeSet maintains sorted order. Iteration order of a HashSet or HashMap is unspecified and can change across a resize, a JVM version, or a run — a "sometimes the JSON array order changes between restarts" bug is almost always this.

list.removeIf(s -> s.isExpired());   // one call, modCount stays consistent

// WRONG - throws CME even on a single thread:
for (String s : list) {
    if (s.isEmpty()) list.remove(s);   // structural change behind the iterator
}
Must remember — fail-fast is a feature

ConcurrentModificationException is unchecked, and it surfaces a genuine bug immediately rather than returning a silently inconsistent result. A fail-safe iterator would not throw — it would hand you wrong answers you discover later. The exception is also a best-effort detector, not a guarantee: it does not fire on every possible misuse, and removing the second-to-last element can slip through on the hasNext()/modCount timing. Treat the code that did not throw as still broken.

Parameters and returns point in opposite directions
PositionRuleWhy
ParameterAs general as the code needs — Iterable if it only iterates, List if it indexesA narrow parameter type needlessly rejects callers
Return typeAs specific as the guarantees allow — List not CollectionTells callers what ordering and uniqueness they can rely on

Iterating entrySet() rather than keySet() and calling get() is not style: keySet() plus get() performs a second hash lookup per key and doubles the work. Updating values in place with entry.setValue() during entrySet() iteration is explicitly supported and does not trip the fail-fast check — only structural additions and removals do.

Trade-off — "LinkedList is faster for inserts"

The rule of thumb is outdated without qualification. ArrayList usually wins even for insert-heavy work, because growing and shifting an array is a bulk, vectorisable, cache-friendly memory operation while a LinkedList pays pointer chasing to find the insertion point before it gets its O(1) splice. Flips on: you already hold a reference to the Node — from a ListIterator, or during a traversal — and need no traversal to reach the insertion point.

// WRONG - O(n) per removal, O(n^2) overall
while (!list.isEmpty()) { handle(list.remove(0)); }

// RIGHT — O(1) per removal
Deque<Order> queue = new ArrayDeque<>();
queue.addLast(order);
Order next = queue.pollFirst();
Two easy-to-miss O(n²) patterns

get(i) inside a loop over a LinkedList. Each access is a fresh traversal, so a loop that looks linear is quadratic.

Front-insert or remove(0) on an ArrayList. Every removal shifts the whole tail. A real queue pattern wants the ArrayDeque above, which is also the JDK's own recommendation over Stack and LinkedList for stack and queue use.

Must remember — Vector and Stack are legacy

Both synchronize every method unconditionally, so you pay lock cost in single-threaded code where it buys nothing. Vector also doubles capacity on resize where ArrayList grows by 1.5×, and Stack extends Vector rather than composing it, inheriting a List API it should never have exposed. Modern answer: ArrayList and ArrayDeque, with concurrency chosen deliberately where it is needed — see Volume 6.

03

Set implementations

Every Set in the framework is a Map in disguise: HashSet and LinkedHashSet wrap a HashMap, TreeSet wraps a TreeMap. That is why section 5's HashMap internals explain Set behaviour you did not expect, and why mutating a hash-relevant field is a Set bug, not just a Map one.

private static final Object PRESENT = new Object();   // shared dummy value

// HashSet.add(e) is exactly this:
return map.put(e, PRESENT) == null;

// a genuinely new key -> true; an equal key already present -> false

Set.add() returning a boolean lets you detect a duplicate explicitly rather than assuming one, which is what makes a "register once" pattern expressible.

Interview trap — the entry that goes missing

Mutate a field that participates in hashCode() after the object is in the set. The object is still sitting in the bucket matching its original hash, but every subsequent lookup computes a different hash and searches a different bucket — so contains() and remove() report false and the element is, for every practical purpose, lost. Nothing throws. A dedup set then admits the duplicate it was built to reject. Make hash-relevant fields final, set once at construction; the mutability of the type is not the problem, the mutation event is.

Production scenario — the dedup set that leaks

Problem: a Set<Order> used for deduplication in a batch job intermittently lets duplicates through. Investigation: the Order's id field — the field its hashCode() reads — is mutated later in the pipeline, after insertion. Root cause: the bucket moved without the entry. Solution: an immutable key, or a separate identity-based dedup structure. Prevention: hash-relevant fields are final — cheap to enforce by policy, expensive to diagnose later.

Interview trap — TreeSet fails at runtime, not compile time

Add an element whose class does not implement Comparable to a TreeSet built without a Comparator, and you get a ClassCastException the first time the tree needs to compare it — not a compile error, because generics only enforce Comparable when the type parameter is explicitly bounded. The related pitfall: a Comparator that disagrees with equals() makes entries "duplicates" that equals() says are distinct, so elements vanish from contains().

The same trap reaches into your business keys: a Set<BigDecimal> for numeric dedup treats 2.0 and 2.00 as distinct, because BigDecimal.equals() treats scale as significant while compareTo() does not. Numeric dedup wants a TreeSet on compareTo() ordering, or explicit normalisation.

Trade-off — TreeSet vs LinkedHashSet

Ask whether the set needs sorted iteration or only deterministic iteration. TreeSet costs O(log n) per operation to stay sorted; LinkedHashSet gives deterministic insertion order at O(1) average. Flips on: you need range queries (headSet, floor, ceiling) or genuinely sorted output — then the log factor is the price of a capability, not waste.

final class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LRUCache(int capacity) {
        super(16, 0.75f, true);   // true = ACCESS ORDER
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;   // evict the least recently used
    }
}

Access order iterates least-recently-used first, so overriding removeEldestEntry() is all an LRU cache needs — five lines instead of a hand-rolled linked list plus hash map. There is no built-in size cap: the default implementation does nothing, so the override is mandatory.

Interview trap — Hashtable is not just a synchronized HashMap

Two differences, and the second is the one people miss. Nulls: Hashtable rejects null keys and values outright with a NullPointerException; HashMap allows one null key and any number of null values. Locking: Hashtable puts one coarse lock over the whole table, which is why ConcurrentHashMap — not Hashtable — is the modern answer for concurrent access. Reaching for Hashtable "for thread safety" is strictly worse than leaving a HashMap alone and choosing deliberately.

Interview trap — a HashMap read while another thread writes

Not safe, and not a narrow edge case: HashMap gives no thread-safety guarantee at all, so concurrent modification is undefined behaviour — corruption, or a hang from a cyclic chain in a pre-Java-8 resize. It will not reliably reproduce in testing, which is what makes it survive review. The choice is ConcurrentHashMap or external synchronisation; see section 6 and Volume 6.

Must remember — why TreeMap is worth its log factor

TreeMap buys sorted order and range queries: floorKey() and ceilingKey() answer "what was the configuration effective as of this timestamp", and headMap/tailMap/subMap scan a range at O(log n) to find the boundary plus O(k) to walk k results. A HashMap cannot do either without sorting the whole map yourself. The cost: do not pay O(log n) when you never need sorted order or a range — and note the null-key difference, since TreeMap throws where HashMap allows one.

When a map grows without bound — a dedup ledger, a cache keyed on mutable data — the fix is structural, not a bigger map: bound it by size or time (LinkedHashMap eviction, a WeakHashMap whose entries die with their keys, a periodic clear()), or model the domain with a class. clear() reuses the backing array, where map = new HashMap<>() throws the old one away for the collector — the cheaper choice under GC pressure.

05

HashMap internals

A HashMap is an array of buckets. Each holds zero, one, or several Nodes, caching their own hash and linking onward through next. Lookup is two steps: hash to pick the bucket, then equals() to pick the entry inside it. Every failure mode here comes from one of those two steps.

static final int hash(Object key) {
    int h;
    return (key == null) ? 0
            : (h = key.hashCode()) ^ (h >> 16);
}

// index = (table.length - 1) & hash;   -- only correct for power-of-2 capacity
Interview trap — why the XOR, and why power of two

The bucket index is hash & (capacity - 1), and that mask only ever looks at the low bits of the hash. Many hashCode() implementations vary mostly in their high bits, so masking alone would pile them all into a few buckets. XOR-folding the upper 16 bits down moves that entropy where it actually affects bucket selection.

And capacity is always a power of two precisely so that & (capacity - 1) is a valid, cheap substitute for % capacity — bitwise AND is far cheaper than modulo. Pass a non-power-of-two initial capacity and it is silently rounded up to the next power of two, not honoured as given.

Trade-off — why 0.75, and why you can change it

Load factor is a space-for-collisions trade. Lower (0.4) means more empty buckets and fewer collisions — faster lookups, wasted memory. Higher (0.95) means a denser table and more collisions — slower lookups, smaller footprint. 0.75 is the JDK's empirically chosen balance, and it is tunable through the constructor. Flips on: a map built once and held for the process lifetime may be worth a higher load factor; a hot lookup path is not.

"Amortized O(1)" describes the long-run average, not any individual call — the one put that triggers a resize is genuinely O(n), which matters for tail latency rather than throughput. And a resize holds both the old and the new table at once, so capacity planning for a map of millions of entries must account for the peak, not the steady state.

Interview trap — treeification needs two conditions

Eight collisions in a bucket is not sufficient. The table must also have at least 64 buckets; below that, HashMap resizes instead of treeifying, on the reasoning that a small table with heavy collisions is far more likely to be simply under-sized than genuinely pathological — treeification is the fallback for cases resizing does not fix. And once a bucket is a tree, dropping back to six or fewer entries turns it into a list again, so you can oscillate.

Scaling reality check — treeification is a security control

Pre-Java-8 a collision was O(n) with no ceiling, which made a public API keyed on user-controlled strings a denial-of-service lever: an attacker submits keys that all hash to one bucket and every request degrades to a linear scan. Treeification bounds the worst case per bucket at O(log n), limiting the damage without eliminating it. A hashCode() that returns a constant has the same effect by accident — a cache whose lookups quietly slow down over weeks is a constant hashCode(), and Objects.hash(...) over the identity fields is the fix.

The equals()/hashCode() contract itself belongs to Volume 3. What is new here is the consequence: because get() hashes first and compares second, a class that overrides equals() without hashCode() never gets its equals() logic consulted at all. That is the reason behind the interview answer "it needs a matching hashCode()".

Interview trap — iterating a PriorityQueue is not ordered

A PriorityQueue is a binary heap, not a sorted structure. Only the root is guaranteed to be the smallest element. Only repeated poll() calls yield priority order — printing the collection is the classic version of this bug. It is min-heap by default, with Comparator.reverseOrder() for a max-heap, and it heapifies an unsorted collection passed at construction.

One production consequence: a queue-based work distributor built on PriorityQueue can starve low-priority work indefinitely while higher priorities keep arriving. If starvation is unacceptable, the priority needs an ageing or fairness mechanism, not just a smaller number.

Must remember — ArrayDeque is the default stack and queue

A resizable circular array supporting O(1) amortized work at both ends. The JDK's Javadoc states it is likely faster than Stack used as a stack and faster than LinkedList used as a queue. Two limits: it does not implement List, so get(index) does not exist, and it does not permit null elements.

Interview trap — why ConcurrentHashMap forbids null

The rationale is the answer; the rule alone is trivia. In a concurrent map, get(key) == null is ambiguous — "the key is absent" and "the key is present and mapped to null" are indistinguishable from the return value alone. A single-threaded HashMap lets you follow up with containsKey(), but here another thread can change the map between the two calls, so the disambiguation is itself racy. Banning null removes the ambiguity at the source.

Interview trap — its iterator will not throw

Iterating a ConcurrentHashMap while another thread inserts does not throw ConcurrentModificationException, exactly as with a plain HashMap. The iterator is weakly consistent: it reflects some concurrent updates and not others, and never crashes. That is the deliberate trade for lock-free reads — the result is not a consistent snapshot, and code that relied on the fail-fast safety net no longer has it.

IdentityHashMap compares keys with == rather than equals(), which is the correct semantics for tracking visited object instances during a graph walk but a bug everywhere else.
