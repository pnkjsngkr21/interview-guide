Volume 8 — Advanced Java

The code that inspects, generates and serialises itself — where the Spring proxy actually sits, which annotation the compiler throws away, and which four habits stop being optional.

  • 8 sections
← Prev Next →

If you only remember five things

  1. An annotation does nothing until something reads it. The behaviour lives in reflection, an annotation processor, or the compiler. Forget @Retention(RUNTIME) and getAnnotation() returns null even though the annotation is in the bytecode.
  2. Never deserialize untrusted bytes with native Java serialization. readObject() sets fields directly, bypassing constructors and validation, and a chain of ordinary getters can be made to run arbitrary code. Use JSON or protobuf.
  3. An enum is the JVM's own singleton. Each constant is one public static final instance built at class initialization behind an implicitly private constructor — which is why a single-element enum is the recommended Singleton.
  4. Sealing is what buys you an exhaustive switch. The compiler proves coverage from the permits list, so a new subtype breaks every switch over that type at build time instead of at runtime.
  5. Immutability needs two defensive copies, not final. final locks the reference, not the object. Copy in the constructor and copy out of the getter, or an "immutable" class has a live back door.

01

Reflection

Reflection inspects and invokes classes, fields, methods and constructors at runtime, including ones with no compile-time existence. The entry point is the Class object — obj.getClass() or Foo.class, which needs no instance.

getDeclaredX vs getX — a different answer, not a synonym
CallReturnsReach for it when
getDeclaredFields()All access levels, declared on this class only You own the class. Inherited fields need a separate walk up the hierarchy
getFields()Public only, including inherited You are a consumer with no business reaching past the public surface
Every "magic" framework behaviour is these two mechanisms
BehaviourWhat is actually happening
Spring's @AutowiredScan for the annotated field, then reflectively set it with a resolved bean
JUnit finding @Test methodsScan for annotated methods, Method.invoke() each one
Jackson mapping a POJO to JSONReflectively read and write accessors to move state into a JSON tree
Hibernate building an entity from a rowReflectively construct from the no-arg constructor, then set fields from the ResultSet
 
class Person {
    private String name = "Asha";
    private void greet(String who) { System.out.println(who + ", " + name); }
}

Class<?> clazz = Person.class;            // entry point; no instance needed
Person person = new Person();

Field f = clazz.getDeclaredField("name");   // private, declared here
f.setAccessible(true);
f.set(person, "Ravi");                       // writes a private field

Method m = clazz.getDeclaredMethod("greet", String.class);
m.setAccessible(true);
try {
    m.invoke(person, "Hello");
} catch (InvocationTargetException e) {
    throw new IllegalStateException(e.getCause());   // unwrap, or leak the wrapper
}
Must remember — how the framework does it

"How does Spring wire this without me writing anything?" has one answer every time: annotations provide the metadata, reflection acts on it. That pairing explains Spring's DI, JUnit's discovery, Jackson's binding and Hibernate's mapping.

Interview trap — setAccessible is not unconditional

Since Java 9 a module can refuse to be opened, and setAccessible(true) then throws InaccessibleObjectException for a class you are entitled to use. The fix is an opens directive. Code that works on the classpath can fail once the module system is enabled.

Interview trap — invoke() wraps, it does not throw through

Whatever the invoked method throws arrives inside InvocationTargetException; getCause() holds the original. The same applies to the three checked exceptions reflection forces on you: NoSuchMethodException, IllegalAccessException, InvocationTargetException.

Trade-off — how slow is reflection, really?

Reflective calls bypass JIT optimisations, but modern JVMs have narrowed the gap considerably for repeated use. Flips on: whether the lookup is hoisted out of the loop. A cached accessor is close enough to free; re-resolving getDeclaredMethod() every iteration is not.

02

Annotations & custom annotations

An annotation is metadata attached to a declaration. By itself it does nothing — its entire value comes from the compiler, a build-time processor, or reflective code deciding to read it. An annotation nobody reads is a comment with an @.

The four meta-annotations
Meta-annotationControlsFailure when omitted
@RetentionSOURCE — compiler only, discarded after the build; CLASS — kept in the bytecode, invisible at runtime, the default; RUNTIME — loaded and readable via reflection Silently invisible to any framework reading it at runtime
@TargetWhich declaration kinds it may be applied to — TYPE, METHOD, FIELD, PARAMETER Too broad a @Target lets it be applied where the processor does nothing
@InheritedWhether a class-level annotation is picked up on subclasses Silent absence on the subclass — and note the narrowness: class annotations only, through extension only, never through interfaces
@DocumentedWhether the annotation appears in generated Javadoc Cosmetic only
 
@Retention(RetentionPolicy.RUNTIME)              // without this, getAnnotation returns null
@Target(ElementType.METHOD)
public @interface Loggable {
    String value() default "INFO";               // elements look like methods, act as config
    boolean includeArgs() default false;
}

Method m = OrderService.class.getMethod("placeOrder", String.class);
Loggable a = m.getAnnotation(Loggable.class);
if (a != null) {                                // absent is null, never an exception
    System.out.println(a.value() + " " + a.includeArgs());
}
Interview trap — default retention is CLASS

Omit @Retention and the annotation compiles, applies, appears in the .class file, and is invisible to getAnnotation(). Nothing fails loudly. And retention is not inheritance — that is a separate @Inherited, for class-level annotations only.

Interview trap — Lombok does not use reflection

A good trick question. The answer is no: Lombok is a compile-time annotation processor that hooks javac and rewrites bytecode during the build, so it costs nothing at runtime. Spring's @Autowired is the opposite — runtime reflection.

Trade-off — compile-time or runtime processing

Compile-time processing (Lombok, Dagger, javax.annotation.processing) catches misuse before the build finishes and leaves no runtime metadata. Flips on: genuinely runtime-configurable behaviour, which cannot be resolved at build time at all. The trade buys the caller's convenience, not the author's simplicity.

03

Serialization & deserialization

Serialization turns an object's state into a byte stream; deserialization reconstructs an equivalent object from it. A class opts in with the empty marker interface Serializable — which is why it is a trap: the interface declares an implicit contract it enforces none of.

Must remember — the deserialization vulnerability

readObject() reconstructs an object by setting fields straight from the stream, bypassing the constructor and every validation in it. Feed it attacker-controlled bytes and a chain of ordinary getters inside your own dependencies can be driven into remote code execution — the "gadget chain". A real, currently-exploited vulnerability class. The answer to "when would you use Java serialization?" is: rarely, and never on untrusted input. JSON and protobuf deserialize into plain data and never invoke arbitrary methods.

class User implements Serializable {
    private static final long serialVersionUID = 1L;   // declare it; never inherit the generated one
    private String name;
    private transient String password;                // skipped, restored as null
    private transient Thread worker;                  // a live runtime resource, not data
}

Mark a field transient for three reasons: it is sensitive and must not be persisted or transmitted (a forgotten transient puts passwords in caches, logs and backups); it is a live runtime resource with no portable form; or it is cheap to recompute. A transient field is not preserved with a default — it is not preserved at all, returning as 0, null or false, so anything the object needs must be re-established after deserialization.

Interview trap — NotSerializableException is a runtime failure

A Serializable class holding a non-serializable, non-transient field compiles cleanly and throws NotSerializableException the first time writeObject() actually runs. The compiler cannot check transitive serializability of field types, so only a round-trip test — serialize, deserialize, assert equals — will catch it.

Interview trap — the generated serialVersionUID

Omitted, the JVM derives one from the class's structure, so recompiling with a behaviourally irrelevant edit can change it and make previously-written bytes fail with InvalidClassException. Declare it explicitly. The production version: a rolling deploy leaves old and new versions side by side, and the old payloads must stay loadable.

Serializable vs Externalizable
SerializableExternalizable
ControlDefault field-by-field, optionally customised by private writeObject/readObject Total — you implement writeExternal/readExternal yourself
CostReflection-based by default Can be faster and smaller — no reflection, exactly what you write
Public no-arg constructorNot required Required — deserialization calls it before readExternal
Justify it whenAlmost always There is a measured cost on a genuinely hot path — and the manual code needs the same security review as the format it replaces
Scaling reality check — where native serialization stops working

It couples two services to the JVM and to matching class versions, so it works inside one process and stops the moment a payload crosses a service boundary or survives a deploy. That compatibility budget — versions, retention of old payloads, per-message formats — is the real cost, not the CPU.

04

Enum internals & records

An enum is not a JVM construct. It is sugar for a final class extending java.lang.Enum, where each constant is a public static final instance created once at class initialization, behind an implicitly private constructor. Constants can carry fields and methods, including an abstract method each constant implements in its own body — which compiles each one to an anonymous subclass.

Must remember — why a one-element enum is the best Singleton

Three properties fall out of the compilation model for free: thread-safe lazy initialization (class initialization is JVM-guarded), correct serialization (the stream reconstructs the same constant, not a new instance), and resistance to reflective instantiation. The classic private-constructor-plus-static-field singleton gets none of them automatically.

Interview trap — never persist ordinal()

ordinal() is declaration order, nothing more. Persist it and the stored value silently re-points at a different constant the moment someone inserts or reorders one — a reordering made purely for readability. Persist a name, or an explicit stable identifier. The same trap lives in compareTo(), so a TreeSet keyed on an enum inherits a dependency on declaration order.

A record is the language's own answer to the boilerplate Lombok solves: declare the components once and the constructor, accessors, equals, hashCode and toString are generated — natively, with no external dependency and no annotation processor.

record Range(int min, int max) {
    Range {                                          // compact constructor: validate before assign
        if (min > max) {
            throw new IllegalArgumentException("min > max");
        }
        // no this.min = min; — the assignments happen after this block
    }
}

Range r = new Range(1, 10);
r.min();                                            // accessor is min(), NOT getMin()
Data-carrier options
Traditional classLombok @DataRecord
BoilerplateAll hand-writtenGenerated at compile timeGenerated by the language
MutabilityYour choiceUsually mutable — settersAlways immutable; fields private final
Extra instance fieldsYesYesNo — state is exactly the components
DependencyNoneLombokNone, in the JDK since Java 16
Pick it whenIt needs behaviour, inheritance, or identity semanticsThe team is standardised on LombokIt is a value object with no no-arg constructor requirement
Interview trap — three record details that fail to compile

The accessor is x(), not getX() — records deliberately break the JavaBean convention. You cannot add extra instance state beyond the declared components; methods and a compact constructor are fine, fields are not. And there is no mutability to add later, so anything needing a no-arg constructor is not a record. A DTO-to-record migration is not a pure type swap.

Scaling reality check — records as JPA entities

Records are a poor fit for ORM entities, structurally. Entities need a no-arg constructor for the ORM to instantiate reflectively, plus a mutable field to populate; records are final and immutable. They are also value objects, while JPA wants identity semantics — a backed entity's equals should follow its ID, a record's compares every component. ORMs and serializers that predate records assume mutable fields and a no-arg constructor, so check the library version rather than assuming support.

05

Sealed classes & pattern matching

A sealed class or interface names its complete set of permitted subtypes — a closed world the compiler knows the contents of, sitting deliberately between final and an open class.

Every direct subclass must pick exactly one — there is no implicit option
ModifierMeansCost to exhaustiveness
finalThis branch is closed; nobody may extend itNone
sealedSealing continues here under its own permits listNone, if you also cover its subtypes
non-sealedExplicitly reopened — anyone may extend it againThe hierarchy is no longer closed here, so a default is generally needed
 
sealed interface Result<T> permits Success, Failure { }

record Success<T>(T value)      implements Result<T> { }
record Failure<T>(String error) implements Result<T> { }

String handle(Result<Integer> r) {
    return switch (r) {                             // no default: coverage is proven
        case Success<Integer>(var v) -> "ok: " + v;    // record pattern, Java 21
        case Failure<Integer>(var e) -> "err: " + e;
        case null -> "nothing";
    };
}
Must remember — what sealing is for

Records give an immutable carrier, sealed types a closed set of carriers, pattern matching the destructuring. Together they model a result as Success(value) or Failure(error) with no nullable field, so invalid combinations — "success carrying an error" — are unrepresentable rather than validated.

Interview trap — a default branch quietly disarms the safety

A default satisfies the compiler's exhaustiveness requirement, so a switch that forgets a case still compiles and you are back to a runtime gap with the appearance of a checked switch. The safety is strongest with no default. Two further edges: a non-sealed branch reopens that part of the hierarchy, so exhaustiveness does not apply automatically; and case null is matched before type patterns.

Interview trap — switch on null used to throw

Before pattern matching, switching on a null reference threw NullPointerException immediately, which is why every switch sat behind a separate null check. Pattern-matching switch can match null with case null, and because null is matched before any type pattern, that branch is not optional. Expecting an NPE from a null argument is now a bug in your own code.

Trade-off — sealed types, enums, or a flag field

Enum when the variants are pure named constants carrying no data of their own. Sealed interfaces plus records when each variant carries a genuinely different payload — the case an enum cannot express. A single class with a field when the variants differ only in data and not in behaviour. Flips on: whether the world is genuinely closed — if third parties must extend it, sealing forecloses something legitimate.

Sealed types plus a switch reach the same exhaustive-handling goal as the Visitor pattern with far less boilerplate, and they compose with generics — where exhaustiveness concerns the hierarchy's variants rather than the type argument in use.

06

Immutability, copying & functional concepts

Immutability needs four deliberate steps together: make the class final so a mutable subclass cannot break the contract, make fields private final, expose no mutating methods, and defensively copy every mutable-typed field both in and out. The fourth is the one that gets missed.

public final class ImmutablePerson {
    private final String name;
    private final List<String> hobbies;

    public ImmutablePerson(String name, List<String> hobbies) {
        this.name = name;
        this.hobbies = new ArrayList<>(hobbies);       // copy IN — the caller's list is not ours
    }

    public List<String> getHobbies() {
        return List.copyOf(hobbies);                      // copy OUT — or hand out a live reference
    }
}
Interview trap — final does not make anything immutable

final prevents reassigning the reference, not mutating the object it points at. Each missing copy opens a distinct hole: with no constructor-side copy the caller mutates their original list after construction; with no getter-side copy any caller mutates your internal list directly. Both are required; either alone is insufficient. The same applies to records — a mutable-typed component with no copy in the compact constructor is only shallowly immutable.

Shallow vs deep copy
ShallowDeep
Primitives, StringsCopied by valueIdentical — nothing to recurse into
Reference fieldsOnly the reference is copied; both objects point at the same nested objectThe nested object is recursively copied too
Mutation riskMutating a nested field on the copy changes the originalFully independent
CostConstant, relative to the graphTraverses the whole graph — and a naive recursion infinite-loops on a cyclic one
Interview trap — clone() is shallow, and Cloneable is worse

The default Object.clone() copies references, so copy and original share every nested mutable object; mutate one and the other changes. That is the whole Object class story, and why a copy constructor is preferred over Cloneable. A hand-written deep copy is only as correct as the last field someone added without updating it.

Trade-off — copy or unmodifiable view?

An unmodifiable wrapper costs nothing per access and signals intent, but it is a live view: if anything else holds a reference to the underlying collection, its mutations show through your supposedly immutable object. Flips on: whether the wrapped collection is genuinely never mutated elsewhere — and immutability pays twice, since it also lets you cache toString() and use the object as a map key.

The principle beyond immutability is defensive copying at a trust boundary: whenever mutable data crosses between code you control and code you do not, copy it. A service storing a caller's List<Order> reference directly has its own state corrupted later by an unrelated code path, with no stack trace pointing at the cause. The one limit is publication — see concurrency.

Choosing between them

Each buys a capability by giving something up — name the trade
If you needUseWhat you gave up
To act on types you do not have at compile timeReflectionCompile-time type safety, encapsulation, some JIT-friendliness
A declarative marker read at runtime@Retention(RUNTIME)Inert by default — it does nothing without a reader
Generated code with zero runtime costA compile-time annotation processorAnything decided at runtime; processor testing is its own infrastructure
To persist or transmit objectsJSON or protobufZero-schema convenience, in exchange for removing the gadget-chain class
A closed set of variants that each carry dataSealed interface + recordsExtensibility by third parties — not free to reverse later
A value objectA recordMutability, extra fields, no-arg construction, Bean-convention accessors
Objects safe to share and reason aboutImmutability with both defensive copiesAn allocation per update — measure only in a proven hot path
Must remember — the question behind every advanced feature

Reflection trades type safety for runtime flexibility; annotations trade explicitness for declarative convenience; serialization trades encapsulation for persistence; immutability trades update convenience for reasoning simplicity. The senior answer is never the feature name — it is the trade. The last question on this material is rarely "do you know sealed types?" It is "why not the simpler thing?"

Interview trap — false confidence from exhaustiveness

Exhaustiveness proves you handle every variant that exists. It does not prove the variant set correctly models the domain — a hierarchy missing a case the business actually has compiles happily. Nor is it a wire contract: it is a compile-time fact in your compilation, so an API modelled with sealed interfaces still needs defensive handling of unknown values by separately-compiled clients.
