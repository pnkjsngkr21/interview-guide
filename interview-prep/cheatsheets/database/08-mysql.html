Volume 8 — MySQL & the InnoDB Engine

Where the row actually lives, what a gap lock is protecting, and which two settings quietly define your RPO.

  • 9 sections
← Prev Next →

If you only remember five things

  1. There is no heap in InnoDB. The clustered index is the table, so physical row order is primary key order and a point lookup reads the whole row.
  2. A secondary index entry carries the full primary key, so following a lookup back to the row — the 回表 — is a second, separate random B+ tree descent. A covering index is the only thing that removes it.
  3. Next-key locking is why the default isolation level is REPEATABLE READ. Gaps in the index are sealed, not just rows, so a concurrent insert of a key that does not yet exist blocks.
  4. A read view is created on the first consistent read, not at BEGIN. One old read view pins purge for the whole instance, and the fix is always the same: find the oldest transaction and make it end.
  5. innodb_flush_log_at_trx_commit and sync_binlog are the durability settings. Neither is a performance knob; each one is an RPO decision nobody wrote down.

01

Architecture & the engine

"MySQL" is a server and a pluggable engine, and most confusion is the two halves talking past each other. The binlog belongs to the server; undo and redo belong to InnoDB; the handler interface between them is why changing engines does not lose your replication.

Four structures, four jobs, no substitutes

Interview trap — the third log

Undo is not the transaction log. Undo holds before-images and exists to serve readers; redo holds after-images in page format and exists to serve recovery. They are written in the same statement, live in different tablespaces, and recycle on completely different criteria — redo when a checkpoint passes the LSN, undo when purge has processed the record. Someone who says "MySQL keeps a transaction log so it can roll back" has described the wrong one, and every tuning conversation after that goes wrong too.

Scaling reality check — the change buffer is a bet

It pays enormously on a monotonically increasing secondary key in an append-heavy table being bulk loaded, where the index is larger than memory. It is worthless on a random-UUID work queue, and it loses whenever the page is likely to be read soon for an unrelated reason: you paid a sequential write, then a read, then a merge write, and the merge was pointless. The bet is that the page will not be read soon — that is what flips the answer.

Scaling reality check — the 128 MB default

128 MB is a development placeholder, not a recommendation. The number to get right is 70–80% of RAM on a dedicated host — and the trap is that the remaining 20% was never sized against anything: per-connection sort_buffer, join_buffer, tmp_table_size, the redo and undo logs, the adaptive hash index and 500 connection threads. Sizing the pool at 80% with default per-connection buffers will OOM the host under a burst of large sorts. Size it from performance_schema hit-rate and page-read counters, not from a rule of thumb.

Must remember — the RPO is a decision, not a default

Durability settings survive because there is no test that fails when you change them and no alert that fires when they are wrong. The fix is organisational: put innodb_flush_log_at_trx_commit and sync_binlog in version-controlled infrastructure with a comment stating the RPO you are accepting, so "what is our RPO" has an answer that is not "whatever the default was on the box someone provisioned".

Held next to PostgreSQL (Volume 7), the two differences that generate nearly every "why is MySQL like that" question are these: InnoDB locks gaps to prevent phantoms rather than relying on the snapshot alone (section 4), and a single long transaction starves purge in exactly the way it starves autovacuum in PostgreSQL (section 3). If you can say the second one in a single sentence you have demonstrated that you understand a protocol rather than a product.

02

The clustered index is the table

There is no heap. Rows live in the leaf pages of a B+ tree keyed on the primary key, so physical row order is key order and a point lookup reads the whole record. A secondary index entry is (secondary_key, DB_TRX_ID, DB_ROLL_PTR, primary_key) — the trailing primary key is why secondary indexes are fat, why an int key is materially cheaper than a bigint one, and why the phrase for following it back is worth being able to say unprompted. B+ tree mechanics, column order and EXPLAIN itself belong to Volume 4.

Choosing the clustered key
KeyPage-split behaviourSecondary-entry costWhen it bites
BIGINT AUTO_INCREMENTEvery append lands in the rightmost leaf; ~63 splits per 1M rows 8-byte suffixThe correct default. Say it first
BINARY(16) time-ordered UUIDMonotonic, same as above 16-byte suffixCorrect when a public identifier is required — UUIDv7, a ULID, or UUID_TO_BIN(uuid(), 1)
char(36) random UUID~62,500 splits per 1M rows — 1000× the rate 36-byte suffixInserts fine in batches, terrible one row at a time; 2–3× space on the clustered index; ANALYZE TABLE still reports good statistics
UUID_TO_BIN(uuid(), 0)Random — the swap flag is the whole point 16-byte suffixFixes the width and leaves the split rate exactly as bad
No primary keyHidden 6-byte GEN_CLUST_INDEX; delete-then-insert puts the new row at the end of the tree 6 bytes in every secondary entryEvery insert after a delete is a random-ish split, and replication and foreign keys have nothing to point at
Interview trap — there is no heap, and no HOT update

The wrong answer is "the row is in a heap and the clustered index points at it". There is no heap. The harder consequence to volunteer: PostgreSQL has a HOT update — if no indexed column changed and the page has room, the new version is written to the same page and no index is touched. InnoDB has none. Every UPDATE writes a new record version and rewrites every affected secondary index entry, even one that only touches an unindexed column. That is the real cost of "the index is the table".

Interview trap — the table that will not shrink

DELETE is a delete-mark, not a removal, and InnoDB never shrinks a file in place — DATA_LENGTH unchanged after deleting 45 of 50 million rows is expected, not a bug. Space only becomes reusable for inserts that fit in the holes, and only once purge can advance past the oldest live read view. Do not reach for OPTIMIZE TABLE as a habit: on a 50-million-row table that is a full copy under an exclusive metadata lock. Find the oldest transaction first.

03

Undo, read views & purge

Every clustered record carries a 6-byte DB_TRX_ID and a 7-byte DB_ROLL_PTR; the second points into the undo log. Visibility is a function of one number — the row's DB_TRX_ID — against three numbers and a set in the read view. Two of the four cases are decided by arithmetic and never touch the undo log at all.

The four visibility cases, plus the two that break the framing
CaseTest against the read viewVerdictCost
1X < m_up_limit_idVisibleNo undo walk — the fast path, and the overwhelming majority of rows
2X >= m_low_limit_idNot visibleNo undo walk; the row may not exist for you at all
3X is in m_ids[]Not visibleThe only case that walks the chain
4up <= X < low, not in m_ids[]VisibleOne hop back along roll_ptr
Own trx_idNot in the array at allAlways visible — including your own delete-marks, which hide the row from you immediatelyNone
Delete-marked, not yours—InvisibleThe undo pre-image is what a concurrent reader still sees
Must remember — purge is the reclaimer, the oldest read view is its brake

The read view is created on the first consistent read, not at BEGIN — so an idle BEGIN pins nothing, and a BEGIN followed by one SELECT pins everything. The production version of that is a job that opens a connection at 02:14, runs one SELECT to "warm" the session, then queues behind a slow HTTP call for five hours. (Do not design around SELECT 1 being constant-folded; SELECT 1 FROM t LIMIT 1 definitely creates a view.) Three things follow from a read view that is four hours old: every row modified since then has to be resolved by walking undo, long scans walk delete-marked records that are logically gone, and the undo space fills toward a threshold where writes block entirely. The distinction that decides the fix: a large history list is a throughput problem that more purge workers can drain; a history list that is not advancing is a blocking problem, and no amount of purge throughput fixes it. Find the oldest transaction and end it — information_schema.INNODB_TRX ordered by trx_started.

Interview trap — purge is the cost of deletes, not inserts

Of the three undo types, insert undo is the only one that can be discarded immediately rather than by purge: if the inserting transaction committed, no other transaction can ever need to see the absence of that row. Delete undo is the largest and the most underestimated — besides the row pre-image it carries the primary key of the row in every secondary index the delete has to remove, so a five-index table produces a delete-undo record containing five primary keys. That is why "we deleted 50 million rows and the disk filled up" has a specific answer.

04

Record, gap & next-key locks

Row locks in InnoDB are locks on index records, at four granularities, and the last three row-level modes are the entire reason REPEATABLE READ works. Lock intention locks at table level (IS, IX, SIX) only declare intent, so thousands of transactions can hold them at once while a genuine table-level X lock waits.

The row-level modes: what each locks, and what it stops
ModeLocksDoes it prevent a phantom?What it does not stop
Record (S / X)An existing row only — "locks rec but not gap" No. The gap beside it is still open for inserts of other keys Any insert into either adjacent gap
GapThe interval between two index records. Neither bordering record is locked Yes, for inserts into that intervalUpdates or deletes of the rows on either side
Next-keyThe record and the gap immediately before it, as one unit. The default for a locking read at RR Yes — and because the gaps tile without overlap, next-key locks over a range seal it completely Anything outside the range; that is correct, not a gap in the guarantee
Insert intentionThe gap the new row would occupy. Compatible with other insert intentions Nothing by itselfIt conflicts only with an existing gap or next-key lock — which is precisely how it gets blocked
Pure next-key (supremum)The pseudo-record at the very end of the index Yes, at the end of the rangeNothing — and this is why a locking read that selects nothing still blocks inserts
When a gap lock is not taken — the answer changes with the statement
StatementAt REPEATABLE READAt READ COMMITTEDWhat it means for you
Plain SELECTNo row locks; served from the read viewSame Never blocks a writer. If a plain SELECT appears to block writes, the blocker is a locking read inside a transaction that spans application code — the ORM-transaction-scoped-in-a-request pattern
Locking read (FOR UPDATE, FOR SHARE)Next-key over the whole scanned rangeRecord locks on matching rows only The single switch that changes every blocking symptom in this section
INSERTInsert intention on the target gapSame Conflicts with an existing gap or next-key lock — this is the blocked writer in the figure
Foreign-key constraint checkGap lock retainedGap lock retained A documented exception to the RC gap-lock removal, because a concurrent insert would otherwise violate the constraint
Duplicate-key checkGap lock retainedGap lock retained Otherwise two concurrent inserts of the same unique key could both believe they succeeded

Trade-off — switching to READ COMMITTED

It changes exactly two things: the read view is created per statement, and gap locks are disabled for locking reads apart from the two documented exceptions above. The condition that flips the answer is whether your application re-reads the same rows inside a transaction and assumes the answer cannot change — a read-modify-write, a check-then-insert uniqueness test, a balance check, an inventory decrement. If it does, READ COMMITTED is wrong unless you take the lock explicitly. If your transactions are single-statement, which with a connection pool and a sane ORM is most of them, it is strictly better.

SELECT id, payload
FROM   job_queue
WHERE  status = 'PENDING'
ORDER  BY priority DESC, id
LIMIT  10
FOR UPDATE SKIP LOCKED;

That one statement is the whole architecture of a MySQL work queue. NOWAIT is the opposite: it takes one row and fails immediately with error 3572, which is the right choice when contention is a signal rather than a queue. Row-based replication is effectively mandatory here — a statement that skips rows non-deterministically produces a different result set on a statement-based replica.

Scaling reality check — what actually caps a queue

Under REPEATABLE READ a WHERE status = 'PENDING' predicate takes next-key locks over every gap in the value range, so SKIP LOCKED workers contend with each other and throughput flattens well before CPU does. Two fixes, and you need both: lead the composite index with status so the next-key range is tight, and run the workers at READ COMMITTED. Add locked_until and attempts columns — a worker that dies mid-job releases its locks when the connection closes, and the row must come back on a timeout rather than be lost. The ceiling is the primary's insert rate minus the vacuum of completed rows, a few thousand to a few tens of thousands of jobs per second depending on row width, and it is reached long before the CPU is.

05

Deadlocks & the diagnostics

A deadlock is a cycle in the wait-for graph: T1 waits for what T2 holds, T2 waits for what T1 holds. InnoDB detects it rather than waiting for a timeout, and rolls back a victim with error 1213. The victim heuristic is, in order: fewer rows modified, smaller undo log, least work done, and ultimately the most recently started — so never build a correctness argument on which transaction was rolled back.

The error numbers that tell you which problem you have
ErrorNameMeaningWhat to do
1213ER_LOCK_DEADLOCKA cycle was detected; this transaction was rolled backFix the lock ordering. Retrying is a mitigation, not a fix
1205ER_LOCK_WAIT_TIMEOUTNo cycle — just a long wait. innodb_lock_wait_timeout (default 50s) expiredThe blocker is long. Find it; it is usually a long transaction spanning application code
3572ER_LOCK_NOWAITNOWAIT found the row locked and gave up immediatelyCorrect when contention is a signal, not a queue
1846ER_ALTER_OPERATION_NOT_SUPPORTEDThe ALGORITHM= you named is not supported for this ALTERThe best possible outcome — you asked for it, so it failed in one second instead of taking an outage
 
SELECT r.trx_id                AS waiting_trx,
       w.trx_id                AS blocking_trx,
       LEFT(rt.trx_query, 60)  AS waiting_query,
       LEFT(bt.trx_query, 60)  AS blocking_query,
       TIMESTAMPDIFF(SECOND, rt.trx_wait_started, NOW()) AS waited_seconds
FROM   performance_schema.data_lock_waits w
JOIN   information_schema.INNODB_TRX  rt ON rt.trx_id = w.REQUESTING_ENGINE_TRANSACTION_ID
JOIN   information_schema.INNODB_TRX  bt ON bt.trx_id = w.BLOCKING_ENGINE_TRANSACTION_ID
ORDER  BY rt.trx_wait_started;

The same information for the most recent deadlock is the LATEST DETECTED DEADLOCK section of SHOW ENGINE INNODB STATUS — a wait-for graph with each transaction's HOLDS THE LOCK(S) and WAITING FOR blocks. Setting innodb_print_all_deadlocks = ON is the difference between "we had one deadlock" and "we had four hundred and we can see the pattern". Read the lock mode, not just the tables: lock_mode X, locks rec but not gap on existing unique keys is a pure lock-ordering bug, while a lock showing NEXT-KEY — or one on the supremum record — is a range scan, and the problem is the shape of the predicate rather than the order of the statements. Concluding from the first *** (n) TRANSACTION block alone that the other side is at fault is the most common misreading of a deadlock report.

@Transactional
public void transfer(long fromAccount, long toAccount, Money amount) {
    retryWithBackoff(() -> {
        // Rule: every path locks in the same order. Sort by the primary key
        // BEFORE the first lock is taken, not inside the retry.
        long first  = Math.min(fromAccount, toAccount);
        long second = Math.max(fromAccount, toAccount);
        long aBalance = accountRepo.lockBalance(first);    // SELECT ... FOR UPDATE
        long bBalance = accountRepo.lockBalance(second);   // SELECT ... FOR UPDATE
        if (aBalance < 0 || bBalance < 0) {
            throw new InsufficientFundsException(fromAccount, toAccount);
        }
        accountRepo.setBalance(first,  aBalance - amount.cents());
        accountRepo.setBalance(second, bBalance + amount.cents());
    }, maxAttempts = 5, baseDelayMs = 20, jitter = true);
}

Retry the whole transaction, never the statement — the partial work has already been rolled back. The jitter is not decoration: without it both sides of the next deadlock retry simultaneously and collide again. Retry is the last of the three answers, and leading with it is what gets a candidate held at mid-level. Before it, shrink the transaction — no network calls, no RPC, no broker publish, no Thread.sleep inside one, because a 1213 is a designed-for outcome rather than a bug and a global ordering rule is not always achievable.

Interview trap — ordering by primary key is not enough

Two services can both claim to order by primary key and still deadlock, because InnoDB locks index records, and the record it locks for WHERE email = ? is not the record it locks for WHERE id = ?. "Primary key order" means different physical positions when the two services use different indexes. The other two failure shapes: one side takes a gap lock from a range predicate the other does not, or one side locks a row the other only reads, so the ordering is over a set the other transaction does not have. The convention that works is expressed in terms of index entries, not primary keys, and enforced in both codebases.

06

Isolation levels as two switches

The single most useful fact for predicting MySQL behaviour: the isolation level is two independent switches — when the read view is created, and whether gap locks are taken. Everything else follows. The anomaly matrix itself belongs to Volume 5; what is InnoDB's own contribution is the mechanism behind each cell.

The two switches, level by level
LevelRead view lifetimeGap locksWhat it costs, and what it buys
READ UNCOMMITTEDPer statementYes Buys nothing — InnoDB will not perform the dirty reads it promises. Never use it
READ COMMITTEDPer statement No, on locking reads only. Retained for foreign-key and duplicate-key checks Far less blocking and deadlock, short undo chains, healthy purge, a history list near zero. The right default for single-statement services
REPEATABLE READPer transaction, on the first consistent read Yes Correct for read-modify-write and check-then-insert without explicit locks; resists write skew. Pays by locking far more than it should
SERIALIZABLEPer transaction Yes, and on nonlocking reads too Every plain SELECT becomes LOCK IN SHARE MODE. A report scanning eight tables holds next-key locks on all eight for its whole duration
Interview trap — three separate wrong answers

"MySQL's REPEATABLE READ is serialisable." Refuse it: a locking read is a current read — it reads the latest committed version and ignores the read view entirely — so a single RR transaction can observe a state that did not exist when it started. That is snapshot skew, and it is the honest limit of the level. "READ COMMITTED prevents phantoms." It does not: the read view is recreated per statement, so a row committed between two identical statements is visible to the second. "SERIALIZABLE uses serialisable snapshot isolation." It does not — there is no SSI and no dangerous-structure detection in MySQL. The mechanisms in the research papers describe PostgreSQL.

Scaling reality check — what SERIALIZABLE costs

A mixed read/write workload sustaining roughly 3,000 statements per second under REPEATABLE READ typically falls to well under 500 under SERIALIZABLE on the same hardware. The drop is not a slope — it is a collapse driven by lock-wait queue depth, so the failure mode is a latency cliff. If a team says "we need SERIALIZABLE because our reports must be exact", ask what exact means: if it means "the total did not change under me", a consistent read at REPEATABLE READ already gives that for every table, for free.

Interview trap — write skew, and how InnoDB stops it

Two doctors on call, at least one must remain: both read the on-duty count, see 2, and each inserts themselves. Under PostgreSQL RR this succeeds and you have zero doctors. Under InnoDB the second insert needs a next-key lock in a range the first transaction already sealed, so it blocks. InnoDB prevents write skew by locking far too much, not by detecting it — a correct answer to a correctness question and a very expensive one to the rest of the workload.

Must remember — the level is a per-unit-of-work property

It is a session setting, which is a feature and a hazard. A session that runs SET SESSION TRANSACTION ISOLATION LEVEL … while debugging leaves every subsequent transaction on that pooled connection at that level until the connection is recycled — on a schedule you do not control. Set it explicitly in the connection-pool initialisation SQL, alert on any session whose transaction_isolation differs from the intended default, and prefer START TRANSACTION ISOLATION LEVEL … so the setting's scope matches the unit of work. Percona, Vitess and several large operators recommend READ COMMITTED as the default for web workloads.

07

Statistics, DDL & retention

Every bad plan traces back to a wrong number. InnoDB's statistics are sampled, so they drift silently when a data distribution changes and no test fails. The other half of this section is the rule that ALGORITHM=INPLACE describes whether the table is copied, not whether it is free. Partitioning as a design technique belongs to Volume 6; what InnoDB adds is the retention consequence.

EXPLAIN ANALYZE SELECT id, total_cents FROM orders
 WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01';
-- prints estimated against actual, and EXECUTES the statement

ANALYZE TABLE orders;
ALTER TABLE orders STATS_SAMPLE_PAGES = 64;   -- before ANALYZE

SET SESSION optimizer_trace = 'enabled=on';
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G
SET SESSION optimizer_trace = 'enabled=off';

Persistent statistics — the default — are sampled from innodb_stats_persistent_sample_pages, 20 leaf pages per index, written to the data dictionary, and auto-recalculated only once the table has changed by more than 10% of its rows. Transient statistics sample 8 pages, are recomputed on every restart, and are never stored. Per-column histograms (8.0+) cover unindexed columns and do not replace index statistics. Run ANALYZE TABLE after every bulk load and every schema change, and check whether the column's cardinality changed rather than assuming the statistics are merely old: a four-valued status that now has forty thousand values is a data-shape change, and a sample of 20 pages will not have caught it. A 100× divergence between the plan's estimate and EXPLAIN ANALYZE is a statistics incident, not a SQL problem. Reading EXPLAIN itself is Volume 4's material.

Changing a table's shape without an outage
ApproachMechanismTakes a write lock?When it bites
ALGORITHM=INSTANTMetadata only — add a column at the end, expand a VARCHAR, change a default NoThe cheapest thing available; name it explicitly
ALGORITHM=INPLACE, LOCK=NONERebuilds or modifies indexes without copying the table Brief exclusive lock at start and end; LOCK=NONE allows concurrent DML throughout Still reads and rewrites the whole table. A 400 GB rebuild generates tens of gigabytes of redo, thrashes the buffer pool for every other query, and produces a replication burst that takes hours to drain — with no error raised. Above roughly 50–100 GB, no rebuilding ALTER runs inline
ALGORITHM=COPYCopies the whole table to a new file, then swaps Exclusive for the entire copy — reads and writes both block A two-hour outage, discovered at run time. Naming INPLACE turns it into error 1846 in one second
pt-online-schema-changeChunked copy plus AFTER triggers on the original, throttled on load Atomic rename at cutover Needs a PRIMARY KEY or UNIQUE NOT NULL index for the chunk cursor, and no existing triggers. Foreign keys require SET FOREIGN_KEY_CHECKS=0 for the whole copy

Interview trap — "we partitioned it to make it faster"

Partitioning makes a query faster only if the optimiser can prune on the partitioning expression. If it cannot, the optimiser opens every partition and the plan is a union of the same per-partition plans you would have got anyway, plus the overhead of resolving which to open — usually a small regression, not a catastrophe. The honest summary: partitioning buys retention and manageability, and buys speed only in the narrow pruning case. The two costs to name are that every unique key must include the partitioning column, so PRIMARY KEY (id) becomes PRIMARY KEY (id, created_at) — a schema change, not a knob — and that InnoDB does not support foreign keys on partitioned tables at all, so referential integrity moves entirely into application code.

08

Replication & the operational surface

Replication is asynchronous, so the primary commits and returns before any replica has the transaction. Everything in this section follows from that one fact, including the most common user-visible bug in a MySQL system. Sharding belongs to Volume 6.

Read-after-write: four mechanisms and what each costs
MechanismLatency costCorrectnessWhen to use it
Route the session to the primary for a window after any writeOne added round trip, only for the session that wroteExact, per session The default. Simple, stateless in the database, and what most systems actually do. Size the window from the measured p99 lag, not a constant
Read from the primary for the whole request that performed a writePrimary loadExact, per requestWhen the write and the read are one user action
WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)The current lag, blockingExact, bounded by a timeout When you need linearizability against one specific write and the lag is small and measured
Accept it and let the UI retryA visible errorEventual Only with a real client retry, and never for money or inventory
Interview trap — semi-synchronous is not read-your-writes

A user creates an order and the next page load says it does not exist, with replica lag at 0.2 seconds. That is the read-after-write case, and it is architectural rather than a capacity problem — 0.2 s of lag is already excellent, and adding replica hardware does not touch the write path. Semi-synchronous replication narrows the window but does not close it, because it waits for the replica to receive the transaction, not to apply it. And do not alert on Seconds_Behind_Source: it is deprecated, and during a stall it measures nothing useful. Monitor data currency with a heartbeat row instead.

Scaling reality check — lag is a step, not a slope

Parallel apply cannot split a transaction, so a single DELETE of 200 million rows is one event and produces a step in lag, while a sustained table copy produces a plateau. Diagnose in that order: correlate with what the primary was doing at the time — a copy-based ALTER or a bulk delete is the usual culprit; establish whether the shape is a step or a plateau; check the applier configuration, because replica_parallel_type=DATABASE on a single-schema workload serialises everything and makes the worker count irrelevant; and check whether the replica is under its own load, because a long analytical query there holds a read view, starves purge, and competes with the applier for the buffer pool — the same failure as section 3, on a different instance.

Trade-off — failover is a rehearsal outcome

"Survive the loss of an availability zone" has three separable parts, and the cheapest is usually the honest baseline: plain asynchronous replication plus binlog shipping to object storage gives you a recoverable-in-an-RPO story for very little money and is worth doing regardless. Zero data loss needs semi-synchronous replication with at least one replica in another zone, which gives you acknowledged-but-not-applied, or a synchronously-replicated pair, which costs commit latency on every write. Fast failover needs automatic promotion — GTID, CHANGE REPLICATION SOURCE TO with no coordinates, automatic replica selection. The thing to say unprompted: a failover plan that has not been exercised quarterly is a plan, and the exercise is what finds the split-brain.

Must remember — four tools, all point-in-time

SHOW FULL PROCESSLIST for the fastest triage — State tells you the kind of wait and Time tells you how long, and it is the only place you will see the shape of a transaction that is idle but open. performance_schema for what PROCESSLIST cannot show, and it is on by default; the digest table's examined_per_sent ratio is the statistics-health metric applied to live traffic and is the most valuable single query in MySQL operations. The slow query log with min_examined_row_limit set, not long_query_time=0. And mysqlbinlog for the replication and point-in-time questions. A team that knows one of these has solved one incident; a team with the digest ratio and a lag alert keyed on business-visible staleness has made the class of failure visible before it becomes one.
