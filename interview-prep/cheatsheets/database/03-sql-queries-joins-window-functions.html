Volume 3 — SQL: Queries, Joins, CTEs & Window Functions

Every non-trivial SQL bug is a consequence of one fact: SQL is declarative and does not evaluate in the order you type it. Learn to name the step of the pipeline a clause is asking to run at, and the traps stop being traps.

  • 9 sections
← Prev Next →

If you only remember five things

  1. Name the pipeline step, not the syntax error. WHERE is step 2 and sees rows; GROUP BY is step 3; HAVING is step 4 and sees groups; the SELECT list is step 5 and is where aliases are minted; ORDER BY is step 6 and sees everything. A SELECT alias is illegal in WHERE and legal in ORDER BY because of exactly this, and a window function cannot be filtered in either.
  2. Any WHERE predicate on the null-extended side of a LEFT JOIN turns it into an inner join. NULL = 'SHIPPED' is UNKNOWN and WHERE admits only TRUE. The fix is structural — move the predicate into ON, which runs before the null-extension. OR col IS NULL is a fragile compensation, not a fix.
  3. One NULL anywhere in a NOT IN sub-select makes the entire result empty — every outer row, permanently, with no error. NOT IN is a negated chain of comparisons, so a single UNKNOWN term makes the conjunction never TRUE. NOT EXISTS is a quantifier over a row set, lives in two-valued logic, and is immune.
  4. A join is a filter on pairs; sum a measure only at its own grain. Summing orders.total_amount after joining to order_items counts it once per line, so a customer's true 51.00 is reported as 82.00. The fix is to pre-aggregate the finer table to the measure's grain before joining, and the diagnosis is COUNT(*) versus COUNT(DISTINCT o.id).
  5. The default window frame is RANGE, not ROWS. It is peer-aware, so two orders sharing a date both see the same running total. And ROW_NUMBER, RANK and DENSE_RANK differ only in tie handling: 1/2/3, 1/1/3 and 1/1/2 on the same three tied rows.

No section matches that filter.

01

Evaluation order & the logical pipeline

You type clauses top to bottom. The engine builds a pipeline, and the pipeline runs bottom to top. The order is fixed by the standard, identical on every engine, and it is the only explanation of almost every "SQL is strange" behaviour anyone reports.

The eight steps, and what each one can see
StepClauseCan seeCannot see
1FROMBase tables, joins, subqueries, set operationsAny alias
2WHEREIndividual rowsAggregates, SELECT aliases, window functions
3GROUP BYRows, to collapse them into groupsAggregates
4HAVINGGroups and aggregates over a groupA column neither grouped nor aggregated
5SELECTEverything above — and mints every alias—
6ORDER BYEverything, including aliases and a manufactured NULL column—
7LIMIT / OFFSETThe finished, ordered rows—
Interview trap — “why can't I use a SELECT alias in WHERE?”

The reflexive answer is “because SQL isn't a programming language”. True, and it explains nothing. The real reason is the pipeline: aliases are minted at step 5, and WHERE is step 2, so the name would be a name for a value the engine has not computed. Three rewrites, in increasing usefulness — repeat the expression; wrap the query so the inner SELECT mints the alias and the outer WHERE filters the finished rows; or move the expression into a generated column or expression index. The counter-intuitive half, worth saying out loud: the identical alias is perfectly legal in ORDER BY, because ORDER BY is step 6. The asymmetry is not a wart; it is the language telling you when each value comes into being.

Interview trap — DISTINCT is a requirement on the whole row

SELECT DISTINCT sku, category FROM products returns 7 rows; SELECT DISTINCT category, unit_price returns 5, because DESK and CHAIR both at 220.00 collapse into one FURNITURE row. So “how many price points does each category have?” is answered by COUNT(DISTINCT unit_price) grouped by category, not by SELECT DISTINCT. The same whole-row rule means another team's migration adding a column can make SELECT DISTINCT * return more rows than last month — which makes SELECT * a correctness dependency, not a style preference.

Scaling reality check — 12,000 rows where 1,200 were expected

A factor of ten is almost always one of three things, and none of them is visible in the SELECT list. Work them in order. 1. Fan-out from a join to a lower-granularity table: group by the suspected key and look at the distribution of group sizes — mostly one row, a few hundred, is fan-out. 2. A predicate that belongs in ON written in WHERE, which changes the count in the other direction. 3. An aggregate over a nullable column where SUM returned NULL for some groups and you expected 0. That is why “obviously correct” and “wrong by 10×” coexist so comfortably.

Trade-off — logical order is not physical order

Logical order is normative and testable; physical order is the optimiser's choice from millions of legal reorderings, and you must EXPLAIN it. So “the optimiser reordered my joins” is a description, not a cause — the cause is always a mis-estimate. Flips on: the two orders can only diverge when the SQL is ambiguous. A well-formed query produces the same rows under every legal plan; a query whose intent was undefined — a LEFT JOIN with a WHERE on the nullable side, a NOT IN over a nullable column — produces rows the optimiser is entirely within its rights to produce and nobody wanted.

Interview trap — LIMIT without ORDER BY

It is legal, because “any ten rows” is a well-formed question. But PostgreSQL is more helpful than it has to be: it will stream in physical order and will use an index if one helps, so the output looks deterministic — which is exactly why the bug survives review and then returns different rows after a Sunday bulk load. And a tie-breaker is not optional when paginating: if placed_at is not unique, LIMIT can split a tie group across pages, and the reader sees one row twice and another not at all.

02

Joins, ON vs WHERE, and fan-out

A join is a function from two bags to one bag. Saying it that way is what makes the four types fall out as four different functions rather than four syntaxes, and it is why the row count of a join result is the sum of the match counts, not the count of either input.

Five customers, nine orders, and what each join returns
JoinKeepsRows hereThe thing to notice
INNERPairs where a match exists9Elin has no orders and disappears entirely
LEFT A→BAll of A, B null-extended10Elin appears once, not nine times — one null-extended row per unmatched left row
RIGHT A→BAll of B9Same as inner here, because the foreign key is total. A RIGHT JOIN that never adds a row is a schema smell
FULLAll of A and all of B10Same count as the LEFT — the row count alone tells you nothing; you must know which side could have produced the null-extension
CROSS / commaThe bag product45The comma binds before a LEFT JOIN in the same FROM, so a, b LEFT JOIN c preserves all of a × b
Must remember — the one sentence that closes most tickets

ON filters which rows are allowed to match. WHERE filters the joined result. Any WHERE predicate on the null-extended side of an outer join silently reduces it to an inner join. The reverse trap is the one less discussed and more expensive in production: a predicate in ON that should have been in WHERE. Both are correct SQL. The difference between “show me all customers” and “show me all customers who have an order over 100” must be a decision, not an accident discovered in a bug report.

Interview trap — OR o.status IS NULL is not the fix

The reflexive answer to “how do I keep the unmatched rows?” is WHERE o.status = 'SHIPPED' OR o.status IS NULL. It does preserve Elin on this data, and it is fragile in exactly the case that matters: a customer whose only order was PENDING still vanishes, and a matched row whose filtered column is genuinely NULL slips through whether it matched or not. If you find yourself adding OR col IS NULL, you are compensating for having put the predicate in the wrong clause.

Diagnosing fan-out — the three queries, and what each one proves
TestAda's resultReading
COUNT(*) after joining to lines4The joined row is one per line, so this is not the customer count
COUNT(DISTINCT o.id)3The true order count — the ratio 4/3 is the average lines per order, and it is the multiplication factor
SUM(DISTINCT o.total_amount)51.00 — rightA coincidence, not a fix. It de-duplicates equal values, not repeated rows. Two legitimate orders at 12.50 would collapse to 12.50

-- BROKEN: 82.00. The correct revenue is 51.00.
SELECT c.name, SUM(o.total_amount) AS revenue
FROM   customers c
JOIN   orders o      ON o.customer_id = c.id
JOIN   order_items i ON i.order_id    = o.id   -- multiplies the order measure
GROUP  BY c.name;

-- CORRECT: pre-aggregate the finer table to the measure's grain first.
WITH per_order AS (
  SELECT order_id, SUM(qty * price) AS total
  FROM   order_items
  GROUP  BY order_id
)
SELECT c.name, SUM(p.total) AS revenue
FROM   per_order p
JOIN   orders o    ON o.id = p.order_id
JOIN   customers c ON c.id = o.customer_id
GROUP  BY c.name;
Interview trap — NATURAL JOIN makes correctness depend on the schema

NATURAL JOIN derives the join condition from shared column names, and the schema changes. Add updated_at to both customers and orders and the join condition now requires both to be equal. The query keeps parsing, keeps running, and starts returning a different number of rows — no error, no warning, and no test that asserts on current data will catch it. A JOIN whose condition you cannot see is a JOIN whose condition you cannot fix. USING is the opposite mistake in miniature: it merges the joined column, and after USING (id) the right side's o.id is a reference error, so in a three-table join of tables that all have an id you get a single merged id meaning three different things.

Trade-off — should you reorder the joins?

No, for a semantically well-formed inner join: the planner has histograms, distinct-value estimates and cross-table correlation statistics you do not have, and it is minimising intermediate row counts, which is what actually determines cost. Flips on: when the optimiser is wrong — a stale statistic, a correlated predicate it does not model, a function wrapping an indexed column. Then the first move is ANALYZE, not a hand-ordered join list. What you should review in a join is the thing a planner cannot fix for you: whether the row counts coming out are the row counts you intended.

03

Anti-joins, EXISTS, and the NOT IN trap

Half the interesting questions in a relational system are of the form “give me the rows for which there is no corresponding row somewhere else”. SQL offers three spellings of that question. On well-formed data all three agree, which is exactly what makes the third dangerous.

Three spellings of “rows with no match”
SpellingResult hereFails whenCost
NOT EXISTSElin, 1 rowNever on NULL — it tests whether a match exists, not whether a value is nullNative anti-join; hash or merge anti-join, uses the child's FK index
LEFT JOIN … IS NULLElin, 1 rowWhen the column tested for NULL is itself nullable in the child — a matched row with a real null satisfies the testMaterialises one null-extended row per unmatched left row, then discards it
NOT IN (subquery)Elin — until one NULL landsOne NULL anywhere in the sub-select: zero rows, always, for every outer rowMust materialise and de-duplicate the sub-select's value list, then semi-join against it
NOT IN on a constant listAs writtenNever — no subquery, no NULL possibleThe one case where NOT IN beats NOT EXISTS
 
-- One guest order, e.g. an import whose customer record was purged.
INSERT INTO orders (id, customer_id, placed_at, status, total_amount)
VALUES (110, NULL, '2024-07-20', 'PENDING', 5.00);

SELECT c.name FROM customers c
WHERE  c.id NOT IN (SELECT o.customer_id FROM orders o);
-- 0 rows. It was 1 row before the INSERT. No error, no warning.

SELECT c.name FROM customers c
WHERE  NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
-- 1 row: Elin. Unchanged, as it should be.
Interview trap — “why is NOT EXISTS better than NOT IN?”

Because IN is not set membership; it is a chain of = comparisons, and NULL poisons the negation of that chain. 5 NOT IN (1,2,NULL) expands to 5 <> 1 AND 5 <> 2 AND 5 <> NULL, the last term is UNKNOWN, so the conjunction is never TRUE and WHERE drops the row. EXISTS is a quantifier — “does this sub-select produce at least one row?” — and quantifiers live in two-valued logic. The NULL row simply fails to qualify, which is exactly right. The follow-up that shows depth: the two also differ on plan, so the rule is correctness first, plan shape second. The one case where NOT IN is genuinely better is a constant list — WHERE status NOT IN ('PENDING','CANCELLED') is faster than a correlated subquery and cannot contain a NULL you failed to notice.

Scaling reality check — anti-joins degrade differently from joins

An indexed INNER join on a foreign key is a nested loop of one index probe per parent row, proportional to the data. An anti-join with no usable index on the child has the same shape with a negative test, and the planner will frequently prefer a full scan of the child with a hash build — fine at 10 rows, catastrophic at 200 million. An anti-join whose subquery scans the child without an index is a query that will be fine in staging and fall over in the first week of real traffic. Check that orders.customer_id is indexed before assuming the anti-join is safe.

Must remember — “maximum” is an anti-join

The anti-join's most valuable use is not finding missing rows; it is expressing “the maximum” as a set difference. NOT EXISTS (SELECT 1 FROM orders o2 WHERE o2.customer_id = o.customer_id AND o2.placed_at > o.placed_at) literally says this row has no superior row in its group — which is the definition of a maximum, and it generalises to median approximations and to “keep the row with the lowest source-system id”. Note the tie behaviour it gives for free: when two orders share the maximum date, WHERE placed_at = (SELECT MAX(…)) and this form both return both rows, which is the honest answer to “each customer's most recent order” when there is a tie. Adding a tie-breaker changes the question to “most recent, first one wins”.

Anti-joins are not only a read construct. The highest-value production use is a DELETE of exactly the rows with no children, and NOT EXISTS is the form to reach for — not because of NULL but because it cannot multiply the rows being deleted: a DELETE written as a join against a child table with duplicates will target the same parent row repeatedly, and engines differ on whether that is an error or a no-op.

04

Subqueries, quantifiers & LATERAL

“Subquery” is not one thing. There are four structurally different constructs, with different cardinality rules and different plans, and the most common misconception is that a subquery is a loop. It is a relation, and the planner is free to turn it into a join, a semi-join, an anti-join or a hash table — unless doing so would change the answer.

The four shapes, and what each may return
ShapeCardinality ruleUn-correlates?Reach for it when
ScalarExactly one row, or an error. An aggregate is safe on an empty set because it still returns one rowYes, if it is a single aggregate with equality predicates on the outer referenceComparing to one value — WHERE total > (SELECT AVG(…))
IN / NOT INA value set; three-valued logic, so one NULL empties a NOT INYes — it is a semi-joinA constant list, or a nullable-column list you have audited
EXISTS / NOT EXISTSA boolean over the row set; two values onlyYes — semi-join or anti-joinMembership and absence, and almost always over IN
Derived tableA full table, joined like any otherIt is the joinPre-aggregating to kill fan-out, or naming a stage
Interview trap — “why didn't the engine just pick a row?”

Because “which of these two rows” is a business question and the database does not know your answer. SELECT * FROM orders WHERE placed_at = (SELECT MIN(placed_at) FROM orders WHERE customer_id = 1) is legal and returns both tied orders — the sub-select's value is well-defined even though two rows hold it. But nest a second scalar comparison one level deeper and you get “more than one row returned by a subquery used as an expression”. That error is the engine correctly refusing to pick arbitrarily, and the reaction should be “the data has a tie I did not model”, not “let me add LIMIT 1” — a silent LIMIT 1 makes the answer depend on physical row order. Make the tie-breaker explicit: (SELECT id FROM orders ORDER BY placed_at, id LIMIT 1).

Interview trap — >= ALL, silently poisoned by a different row

SELECT o1.id FROM orders o1 WHERE o1.total_amount >= ALL (SELECT o2.total_amount FROM orders o2 WHERE o2.customer_id = o1.customer_id) returns 101, 103 and 106 — not 104. Chidi's orders are {37.50, NULL}, so order 104's conjunction is (37.50 >= 37.50) = TRUE AND (37.50 >= NULL) = UNKNOWN, which is UNKNOWN, which WHERE rejects. ALL is a conjunction and one UNKNOWN term poisons it — the NOT IN mechanism arriving through a different operator, and the most under-reported SQL bug there is, because the query looks obviously correct and the missing row is exactly the row you wanted. Rewrites, in order of preference: add AND o2.total_amount IS NOT NULL inside the sub-select (4 rows); use the NOT EXISTS anti-join form, which ignores the NULL row naturally; or use a window function, which is null-safe by construction.

Scaling reality check — a correlated subquery in the SELECT list is the ORM N+1

It arrives constantly because it is the shortest way to write “and also show me a count”. Five customers means five executions, which is fine. Fifty thousand customers — a filtered list, a paginated page, a report over a growing table — means 50,000 executions, and the latency grows linearly with a number the developer thinks of as “just the rows on this page”. A correlated scalar subquery in a SELECT list cannot be turned into a join, because each outer row needs its own value at the moment it is projected. The fix for a simple aggregate is COUNT(o.id) OVER (PARTITION BY customer_id), which computes every partition in one pass. The rule for review: any correlated subquery in a SELECT list needs a comment naming the maximum outer row count it will be evaluated at.

Trade-off — LATERAL or window for top-N-per-group

They return the same rows and do different amounts of work. The window function is a set operation: read every child row, sort or hash the partition, number every row, then discard most of them. That is O(total children) plus a sort. LATERAL is a nested loop: one index probe per parent row, read N rows back, stop. That is O(groups × N) with no sort. On ten line items the difference is invisible; on 20 million lines and 3 million orders the window version sorts 20 million rows and the lateral version does 3 million index probes. Flips on: child-table size, and it also flips on the tie question — FETCH FIRST n ROWS ONLY breaks ties arbitrarily like LIMIT, while WITH TIES is RANK() <= n and is not the same thing as ROW_NUMBER() <= n. And INNER LATERAL silently drops every parent with no children; LEFT JOIN LATERAL … ON TRUE keeps them with nulls, which is a different report from the one the stakeholder usually wants.

Must remember — the optimisation fence

A derived table behaves like a table, which is a blessing for readability and a curse for optimisation. SELECT * FROM (SELECT customer_id, COUNT(*) n FROM orders GROUP BY 1) t WHERE n > 1 forces the engine to fully materialise the aggregate before it can apply the predicate, because n does not exist until the grouping is done. The correct form pushes the filter to the level where the aggregate exists — HAVING COUNT(*) > 1 inside. The fence becomes a real cost whenever the subquery contains something the engine cannot flatten: a DISTINCT, a LIMIT, a set operation, a window function, a grouping aggregate, or a volatile function. Name the boundary with a WITH clause so it is explicit and reviewable rather than an anonymous nest a future optimiser flag could quietly change.

A self-join is the same machinery viewed along a hierarchy, and UPDATE t SET x = (SELECT … FROM t) is an implicit self-join, which is why a correlated update needs an explicit alias to say which copy it means.

05

CTEs & recursive queries

A non-recursive CTE is a name for a result set, scoped to one statement. That is the whole feature, and it is worth more than it looks, because the thing it fixes is not SQL — it is the reader. Six levels of parentheses and three aliases t1/t2/t3 become three named steps, each independently testable, and the names become the vocabulary the review is written in.

Interview trap — the recursive CTE with one root and no guard

Three failure modes, and they are the ones that reach production. (1) The anchor. WHERE manager_id IS NULL traverses exactly one root. If the data has a second root — a deleted manager row, a genuine forest — that root and its entire subtree are missing, silently. (2) No cycle guard. A mis-mutated manager_id iterates until the engine's limit. (3) An accumulator seeded inconsistently. The anchor produces 0 for subtree_total while the recursive term accumulates, so the root's own contribution is missing from its own subtree total — a bug that shows up on the root and nowhere else, which is why it survives testing on a hierarchy with more than one level of data. The fix for (3) is to seed the anchor with the same expression the recursive term accumulates onto.

WITH RECURSIVE tree (id, name, path, depth) AS (
  SELECT id, name, ARRAY[id], 0
  FROM   employees WHERE manager_id IS NULL   -- anchor: one root only
  UNION ALL
  SELECT e.id, e.name, t.path || e.id, t.depth + 1
  FROM   employees e JOIN tree t ON e.manager_id = t.id
  WHERE  NOT e.id = ANY (t.path)            -- the cycle guard
)
SELECT * FROM tree ORDER BY path;

Trade-off — materialise, or inline?

PostgreSQL's default since v12 is to inline a single-reference CTE and materialise a multi-reference one; MATERIALIZED and NOT MATERIALIZED override that. Materialise when the CTE is expensive, referenced more than once, and the alternative re-derives the same work — a filtered subset reused by two aggregates, a date spine joined to several fact tables. Do not materialise when it is cheap and referenced once, because you have added a full build-and-scan plus a memory grant for nothing. Flips on: row count growth. A CTE that was 4,000 rows when the query was written may be 40 million now, and materialisation decisions age badly in a way plain query decisions do not, because the plan is checked at write time and the data is not.

Must remember — a depth limit is not a correctness check

A limit stops a runaway cycle; it does not tell you a cycle happened. Those are different failures, and only the CYCLE clause or a path-array guard distinguishes “we stopped because we hit a wall” from “we stopped because we were done”. That difference decides which defence you deploy. A WHERE NOT id = ANY (path) guard truncates the branch — correct, silent, and you get a tree missing a person. CYCLE id SET is_cycle emits a row you can page somebody about, which is why it is the version that ships on data where a cycle is possible but rare, such as an org chart written by three different HR integrations. Add the depth limit as a backstop, and state it deliberately, so hitting it is a signal rather than a surprise on a specific Tuesday.

The flip condition for recursion over a self-join per level is depth. A three-level org chart is three optimisable passes and the self-join wins outright; a nine-level hierarchy of 200,000 people and an unbounded graph are the cases where only recursion is even expressible. And a hierarchy that can change over time — who did this person report to in March — is a temporal modelling problem, not a recursion problem; a self-referencing manager_id cannot say “as of when”.

06

Window functions, frames & ranking

A window function looks and feels like an aggregate and is not one. An aggregate collapses many rows into one; a window function computes a value for every row from a defined slice of its peers. That slice — the frame — is the whole of the semantics, and most window bugs are frame bugs wearing a function's clothes.

ROW_NUMBER, RANK, DENSE_RANK on the same eight products

BOOKSBOOK12.50111

The one-sentence version that lands: ROW_NUMBER says “you are the third row”; RANK says “three rows are strictly better than you”; DENSE_RANK says “two distinct values are better than you”. So WHERE rn <= 3 always returns exactly three per group; WHERE rnk <= 2 returns three rows from FURNITURE (both 220s and the 45), which is correct for “top 2 including ties” and wrong for “top 2”; and WHERE drnk = 2 asks for the second distinct value, a genuinely different question from “second row”.

SELECT sku, category, unit_price,
       ROW_NUMBER() OVER w AS rn,      -- 1, 2, 3   no gaps, no ties
       RANK()       OVER w AS rnk,     -- 1, 1, 3   ties share, then skip
       DENSE_RANK() OVER w AS drnk     -- 1, 1, 2   ties share, no skip
FROM   products
WINDOW w AS (PARTITION BY category ORDER BY unit_price DESC);

SUM(o.total_amount) OVER (PARTITION BY o.customer_id ORDER BY o.placed_at) AS running
-- RANGE default, peer-aware:  31.00, 51.00, 51.00

SUM(o.total_amount) OVER (PARTITION BY o.customer_id ORDER BY o.placed_at
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
-- positional:               31.00, 43.50, 51.00

last_value(o.id) OVER (PARTITION BY o.customer_id ORDER BY o.placed_at)
-- WRONG: order 102 reports 109, a different order's id

last_value(o.id) OVER (PARTITION BY o.customer_id ORDER BY o.placed_at
                       ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)
Interview trap — what does last_value(x) OVER (ORDER BY y) return?

The current row's own x, not the last row's. The default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, and last_value returns the last row of the frame — so with a frame ending at the current row, the last row is the current row. On Ada's rows the effect is doubled: 102 and 109 share placed_at, so under RANGE each is a peer of the other and 102 reports 109, a value from a different order. Two things make this durable: the wrong answer is a real value from the right customer, so it passes a spot check and fails an audit; and the two bugs compound, which is why the number looks plausible. first_value works by accident — a frame that starts at the partition's beginning already contains the first row. The rule: any function whose name implies “look elsewhere in the partition” needs an explicit frame, and it should be ROWS unless you specifically want peer semantics.

Two more traps that only fire once the data grows

ROW_NUMBER() over a non-unique key. It is valid SQL and a meaningless answer: it still returns 1, 2, 3…, but which row gets which number is unspecified and can change between runs, between plans, and after a VACUUM. A paginated report built on it shows users different rows on different days with no code change. The fix is one word in the OVER clause: a tie-breaker. LAG/LEAD without an explicit frame. The default frame is RANGE UNBOUNDED PRECEDING … CURRENT ROW, so LAG sees every prior row; the portable form states ROWS BETWEEN 1 PRECEDING AND 1 PRECEDING. With no ties the two agree, which is why the bug is invisible until two rows share an ORDER BY key — and then the comparison numbers quietly change with no deploy.

Must remember — top-N-per-group, and NULLS LAST

A window function operates on the rows it is given and never manufactures a row, so Elin is simply absent from a top-2-orders report. If the report needs “every customer, with their top 2 orders or a blank”, the LEFT JOIN has to be there and the ranking must happen before the join, not after. And the NULLS LAST in the OVER clause is doing real work: PostgreSQL's default for DESC is NULLS FIRST, so order 108's NULL total would rank above Chidi's real order and, with a third order, displace one of them. Windows have their own NULLS syntax precisely because the window's ordering is independent of the outer query's.

WITH ranked AS (
  SELECT o.customer_id, o.id, o.total_amount,
         ROW_NUMBER() OVER (PARTITION BY o.customer_id
                            ORDER BY o.total_amount DESC NULLS LAST, o.id) AS rn
  FROM   orders o
)
SELECT * FROM ranked WHERE rn <= 2;   -- the filter has to be a level above
Trade-off — windows or GROUP BY?

Argue for the window when the row you return is not the row you aggregated — each order's total and the customer's total, the current value and the running value, the top row per group with its neighbours intact. GROUP BY gives you a new, smaller relation you must join back, which costs a join and loses the columns you did not group by. Argue for GROUP BY when the answer is genuinely one row per group: it is smaller, it supports HAVING, and it can feed a materialised view. Flips on: the grain of the answer versus the grain of the input — the window wins when they are equal and loses when the answer is coarser, because then it is producing rows nobody asked for. Two concrete cases where the window is wrong: when the frame would be the whole partition anyway (COUNT(*) OVER (PARTITION BY x) is GROUP BY x with extra steps and cannot use HAVING), and when the outer set is huge but the answer is ten rows, because an ORDER BY … LIMIT 10 does not stop a window that must compute over all 50,000 rows first. Narrow first, then window.

07

Set operations & subtotals

UNION is set union and therefore removes duplicates, which requires a sort or a hash of the whole result. UNION ALL is bag concatenation and does nothing. The review question is not “is UNION bad” but “can these two branches produce the same row?”

Interview trap — a trailing ORDER BY sorts the combined result

Not each branch. A set operation is a single relational expression and the trailing ORDER BY is applied to its output, after the branches have been combined. A column named there must come from the first branch's column list. An ORDER BY written inside a branch is a hint the optimiser is entitled to discard, because the set operation's output has no order until you say so. This matters for pagination: … UNION ALL … ORDER BY placed_at LIMIT 10 is ten rows from the combined result, not ten from each arm; and to get ten from each you need two parenthesised subqueries with their own LIMIT, which some engines parse and some do not. Only the top-level ORDER BY is a guarantee.

Interview trap — UNION masks a predicate mistake

SELECT customer_id, total_amount FROM orders WHERE placed_at < '2024-07-01' UNION SELECT … WHERE placed_at >= '2024-06-15' is a correct query that is quietly deleting rows: the branches overlap on 2024-06-15 to 2024-06-30, and June revenue is understated by 282.00. UNION ALL fixes the symptom. But the predicate looks like an off-by-fifteen-days bug, and it probably is one — in which case the fix is to correct the boundary, not the keyword. Switching to UNION ALL to make the symptom disappear ships the symptom's opposite, so the review comment should name the overlap rather than the operator.

Must remember — GROUPING(), because a subtotal's null is not a data null

A subtotal row produced by a grouping set has NULL in every column the set omitted, and that is indistinguishable in the data from a genuine NULL in a detail row. GROUPING(col) returns 1 when the column is NULL because the set omitted it and 0 when the data was null — the only reliable discriminator, and without it the report cannot label its totals, which means finance will not accept it. The row counts also differ by variant, which is worth memorising: four grouping sets give four sets; ROLLUP(a,b) gives (a,b), (a), () — a strict hierarchy of three; CUBE(a,b,c) gives all eight. ROLLUP and CUBE coincide for two dimensions and never again.

Scaling reality check — CUBE is exponential, and the alternative has its own bug

CUBE over six dimensions is 64 grouping sets and 64 aggregate computations per query; over three it is eight. The fix is to choose the rollup path you actually want rather than the full cube. The alternative — a UNION ALL of separate aggregate queries — re-scans the table once per level, and worse, carries a separate copy of the WHERE clause in each branch, so a filter tightened in one branch and not the others produces a grand total that is not the sum of the details, with no error. One grouping-sets query applies one filter and one set of aggregates to every level, so the total is correct by construction. The cost is dialect dependence: PostgreSQL, Oracle, SQL Server and MySQL 8 have them; SQLite and several serverless engines do not. The boundary that flips the answer is dynamism — if the set of levels is decided at runtime, GROUPING SETS cannot help, because it needs its set list at parse time. Generate the branches instead.

08

Grouping, aggregation & HAVING

GROUP BY partitions the bag into groups of equal key values and collapses each group to one row. Three rules follow, and they generate the questions. It does not manufacture groups — a key that appears in no row produces no output row, so “show every customer and their order count” is an outer-join problem, not a GROUP BY problem. Every selected expression is either in the GROUP BY or wrapped in an aggregate — there is no third option, and a column that is neither is a coin flip: most engines reject it, and the ones that do not are picking a value from an arbitrary row in the group. PostgreSQL's functional dependency extension relaxes this in exactly one case: group by a table's primary key and every other column of that table may be selected bare.

Interview trap — what does SUM return for an empty set?

NULL. Not 0, and this trips up engineers arriving from a language where summing an empty list gives zero. The reason is that SQL's NULL means “not known”, and the sum of nothing is genuinely not known rather than known-to-be-nothing. COUNT is the exception, because counting nothing is a number. The consequences are worse than the value itself, because NULL propagates: SUM(x) + 0 is NULL, SUM(x) / 100 is NULL, and SUM(x) > 0 is NULL — which is not TRUE, so a HAVING SUM(x) > 0 silently drops the group rather than erroring. The fix is COALESCE(SUM(x), 0), and the decision behind it is a business one: “a customer with no orders has zero revenue” and “has unknown revenue” are different claims, and for a financial report the second is usually right, because rendering NULL as £0.00 asserts a fact you do not have.

Interview trap — the (null) bucket is a group

GROUP BY treats NULL as a single ordinary value, so every nullable dimension grows a bucket that is a real row in the result — Elin, the one customer with no country recorded. The generalisation is worth stating because it applies to every nullable dimension you will ever group by: NULL is a value to GROUP BY and a non-value to a comparison. It groups, it never equals, and it is never equal to itself. The mistake is letting that row reach a stacked bar chart, where it becomes a fifth category labelled “null” alongside DE, GB and NG. Three handles: label it with COALESCE(country, 'UNKNOWN') for display; WHERE country IS NOT NULL when the dimension must be populated; and a standing SELECT COUNT(*) … WHERE country IS NULL metric, so the question “how many of these are real?” is answerable without a SQL query.

Must remember — HAVING is WHERE one level up

WHERE is step 2 and filters rows; HAVING is step 4 and filters groups. The test for which one a predicate belongs in is exact: could this be true or false for an individual row, or does it only mean something about the set? WHERE total > 100 filters nine rows down to three before the aggregate ever runs; HAVING SUM(…) > 100 aggregates all nine and then discards three of four groups. But HAVING COUNT(*) >= 3 has no row-level equivalent, so HAVING is the only place it can live — which is why the rule is not “always use WHERE”. And the choice is not always answer-preserving: HAVING SUM(x) > 100 and WHERE x > 100 are different questions. FILTER is the clean answer when you want a conditional aggregate instead of a second GROUP BY — but it is PostgreSQL and standard SQL, supported by DuckDB, Redshift and Snowflake, and not by MySQL or SQL Server, so the portable form remains SUM(CASE WHEN … END). A conditional aggregate is still an aggregate, and inherits every empty-set behaviour of the unconditioned one: Elin's shipped revenue is NULL, not 0.

The discipline that makes all of this reviewable: write the grain of the result as a sentence before you write the GROUP BY. It is the cheapest review comment you can write, and it is the one question — “does this query fan out?” — that catches both the multiplied measure and the nullified outer join.
