If you only remember five things

  1. S3 is strongly consistent for PUT, DELETE and LIST in every Region, and has been since December 2020. "Eventually consistent for overwrite and delete" is the pre-2020 answer and it is now wrong. What remains eventually consistent is bucket configuration, which is why AWS recommends a 15-minute wait after you first enable versioning.
  2. S3 has no folders and no query. "Folders" are a client-side group-by on / in the console; there is one flat, byte-ordered key space. Prefix listing works only because a shared prefix is one contiguous range, and a LIST returns at most 1,000 keys and is billed per 1,000 returned.
  3. A presigned URL is a bearer token, not an access-control configuration. The signature binds one method and one key, and the URL dies at the earlier of its own expiry and the expiry of the credentials that signed it — so a 24-hour link signed by a role session quietly stops working in six.
  4. The analysis chain runs twice — at index time and at query time — and a mismatch is silent. You get fewer results, not an error, and the only safe fix is a reindex with an alias swap, because the mapping is not retroactive.
  5. Shard count in Elasticsearch is close to irreversible. Target 10–50 GB per shard, choose it from a forecast, and remember that changing it later means rebuilding the index.

01

S3: the object model and its guarantees

S3 is a flat map from a string to a byte array, and every hard limit in it follows from that. There is a bucket, and a bucket is globally unique, lives in one Region, and is the unit of policy, billing and lifecycle. Inside it, a key is an opaque UTF-8 string of at most 1,024 bytes — prefixes included — and a value is 0 bytes to 5 TB. Nothing else exists. The console's folder tree is a group-by on / rendered in your browser.

What S3 gives you, and the primitive you build when it does not

Must remember

S3 is bad at exactly two things — enumeration and mutation — and both are consequences of the same design that makes it good at everything else. Any design needing "find all of X" or "change this only if it is still Y" is paying to build, in application code, a primitive the service will not give it.

Prefix listing works, and it costs

Keys sort by UTF-8 byte value, so everything sharing a prefix is one contiguous range and a prefix listing is a seek rather than a scan. What it is not is cheap: ListObjectsV2 returns at most 1,000 keys plus a continuation token, so enumerating a ten-million-object prefix is about 10,000 sequential round trips, and LIST is billed per 1,000 keys returned.

Durability, availability and consistency are three different claims

Conflating them is the most common S3 answer that sounds right and is wrong. Durability is a storage-design number — 99.999999999% (eleven nines, designed for) for the multi-AZ classes, meaning if you store ten billion objects you should expect to lose one. Availability is a monthly uptime figure — 99.99% for STANDARD, 99.9% for STANDARD_IA, 99.5% for ONEZONE_IA, 99.95% for EXPRESS_ONEZONE. Consistency is strong read-after-write for PUT, DELETE and LIST, plus HEAD and metadata reads, in all Regions since December 2020: any GET or LIST started after a successful PUT returns that data or its replacement.

Interview trap

"S3 is eventually consistent for overwrite and delete" was the state before December 2020 and is now wrong for object operations. What is still eventually consistent is bucket configuration — a delete-then-list-buckets can still show the bucket, and the first time you enable versioning the change propagates, so AWS explicitly recommends waiting 15 minutes before issuing writes.

Trade-off

The strong-consistency change removes the classic reason for caching a LIST result — you can PUT then LIST and trust it — but it does not make your cache fresh. The condition that flips it: a TTL on a cached listing is now a business decision about how stale a directory view is allowed to be, not a workaround for the storage engine. Say that out loud; it is the sentence that shows the difference between a consistency model and a cache policy.

What strong consistency does not give you is concurrency control. Two simultaneous PUTs to one key resolve by latest-timestamp-wins: no compare-and-swap, no read-modify-write, no "fail if it changed" — and updates are key-based, never multi-key. Conditional writes (If-None-Match: *) give you create-if-absent and nothing else, which is not a lease. Where two multipart uploads race on one key, the survivor is the one initiated most recently, not the one completed; and a DELETE between your initiate and your complete reports success for an object you can no longer see.

Versioning, ETag and the metadata caps

With versioning on, a DELETE writes a zero-byte delete marker carrying x-amz-delete-marker: true; a subsequent GET returns 404 and the data is retained. Versioning is the only recovery S3 offers — there is no trash and no undelete — which is why the cost argument against enabling it is storage, not risk. User metadata (x-amz-meta-*) is immutable: changing it means CopyObject onto the same key, and Last-Modified on a multipart object is the initiation date, not the completion date.

The ETag is not the MD5, and verifying integrity with it is a mistake

The metadata caps are small enough to be asked and easy to get wrong: a PUT carries a 8 kB header cap in total, user metadata is capped at 2 kB and system metadata at 2 kB, and an object takes at most 10 tags at 2 kB. A full-object checksum also requires consecutive part numbers from 1; a non-consecutive CompleteMultipartUpload is rejected with HTTP 500.

02

S3: storage classes and the four billable axes

The class list is long enough that candidates recite it and learn nothing. The useful version sorts every class on two axes that decide everything else: what it costs to store, and what it costs to read back. Minimum duration and the 128 KB floor then follow mechanically.

The storage classes, on the two axes that matter

STANDARD_IA99.9%≥ 330 days128 KBmillisecond, per-GB retrieval fee

Every multi-AZ class carries the same eleven-nines durability; the single-AZ ones trade a Region's worth of failure domain for the storage price and nothing else.

Scaling reality check

128 KB minimum billable size. STANDARD_IA, ONEZONE_IA and GLACIER_IR all bill 128 KB even for a 3 kB object. A million 4 kB thumbnails is 4 GB of real data billed as 128 GB, and lifecycle transitions into those classes are not applied below 128 KB at all. The IA classes are actively wrong for small-object workloads — use STANDARD or INTELLIGENT_TIERING.

Interview trap

Delete, overwrite or transition an IA object before its minimum and you pay the normal storage charge plus a pro-rated charge for the remainder — 30 days for the IA classes, 90 for GLACIER_IR and GLACIER, 180 for DEEP_ARCHIVE. You pay for the whole minimum whether or not the bytes were there. A nightly export that transitions at 2 TB and expires the next morning is billed 30 days of storage, every night.

The four billable axes

Storage per GB-month is the axis people plan against and, for small objects, usually the axis that matters least. The other three are where the money is: requests priced per 1,000, data transfer out (transfer in is free), and retrieval per GB for the classes that charge one.

Which axis dominates, decided by object size and read pattern
WorkloadDominant axisWhy
Ten million 4 kB objects, read rarelyRequestsEvery GET and every LIST page is a unit of 1,000; cost scales with object count, not bytes
130 kB objects at 300 millionRequests, then egressJust over the 128 KB floor, so billed at 128 KB; and a 300-million-object prefix costs 300,000 LIST requests to enumerate
Write-and-read-back in the same RegionStorageEvery transition to an archive class adds a per-GB retrieval charge on the read-back, and possibly an early-delete charge, to end up where it started
Cross-Region read of 500 GB a nightEgressDominates a month of storage-class differences by a wide margin — so reframe as "do not move the data", not "which class"

INTELLIGENT_TIERING sits where its name suggests: no retrieval fee, tiers at 30, 90 and 180 days, no minimum duration — but objects under 128 KB are not monitored at all, so a small-object workload gains nothing from it either.

Lifecycle rules, and where they bite

Two mechanics produce most of the surprises. Expiry is measured from the object's creation time, not from its last transition, so a rule that says "expire after 90 days" means 90 days after the write no matter how many times the object moved. And transitions are asynchronous — an object can be read from the old class after the rule should have moved it, which is why a benchmark written against "IA reads are millisecond" is wrong for the first few hours after a transition.

Trade-off

Lifecycle rules are the right tool for genuinely archival data and the wrong tool for a pipeline. The condition that flips it: if the data is written and read back on a schedule, transitions cost you a retrieval fee per GB and put you inside the early-deletion window for no storage saving that survives the month. If it is written once, read once, and the source is then dropped, write straight to the archive class and never read it back — cheap classes are cheap because you do not read from them.

For bulk work the service is S3 Batch Operations — a single API request performing Copy, Lambda-invoke or Restore across millions of objects, which is the answer to "per-object small writes: N requests, N round trips, partial failure".

03

S3: access control, presigned URLs and multipart

Policy evaluation is the part candidates get backwards most reliably, because the same-account case and the cross-account case are different operations.

How the two policies combine — the rule changes with the account
SituationRuleConsequence
Same accountIntersection — logical ANDAllow only if both the identity policy and the bucket policy allow
Cross-accountUnion for Allow — logical ORThe only way a bucket owner grants a principal its own account policies would refuse
EitherAn explicit Deny always winsNo Allow anywhere overrides it
Block Public AccessA bucket-level veto over the whole evaluationOn by default at the bucket level today

Three mechanics matter more than the table. A bucket policy is capped at 20 KB, so a policy enumerating thousands of ARNs is a sign you want IAM groups or access points. Resource wildcards are byte-greedy — arn:aws:s3:::bucket/* matches every key under every prefix. And conditions are where real authorisation lives: s3:signatureAge to bound presigned-URL age, aws:SecureTransport to require TLS, aws:SourceVpc to require a VPC endpoint, and s3:ExistingObjectTag to make access depend on a tag the writer set.

What a presigned URL actually signs

A presigned URL is a bearer token: a SigV4 signature over a specific set of request parameters that grants whatever its creator's credentials could grant, to anyone holding the string. Treat it like a password.

# One object, one verb, minutes not days. X-Amz-Expires is seconds.
aws s3api presign \
  's3://acme-media/reports/customer-42/q1.pdf' \
  --expires-in 300 --region us-east-1

# Scoped to the DAY and the REGION: the same URL fails tomorrow
# or from another region, with SignatureDoesNotMatch.
# X-Amz-Credential = AKIA.../20260927/us-east-1/s3/aws4_request

The signature covers X-Amz-Algorithm, X-Amz-Credential (scoped to day, Region and service), X-Amz-Date, X-Amz-Expires, X-Amz-SignedHeaders and X-Amz-Signature. It does not cover the request body, the client's identity (there is none), or anything the holder does with the bytes afterwards.

Interview trap

"We presign the prefix and let the client pick the file." The signature binds a method and a key. A sign function that interpolates a filename from the request into the key is a bucket-write primitive reachable by anyone who can call your sign endpoint — and because S3 has no atomic multi-key update and no object lock, a bucket-write primitive in a prefix you did not fully control is a data-destruction primitive. Resolve the identifier to a key from your own authoritative data, fix the verb, and make the expiry minutes.

Interview trap

Presigning with role credentials to get a 24-hour link issues a link that dies when the role session ends — an EC2 instance-profile role typically rotates every few hours, so it quietly stops working in six. Presigning with an IAM user to reach the 7-day maximum means long-lived credentials exist, which is a worse problem than the one you solved. The maximum is 7 days either way, and a URL expires at the earlier of its own expiry and its credential's. The honest answer is to shorten the expiry, not extend the credential.

Multipart

Parts run from 5 MB (any part except the last) to 5 GB, numbered 1 to 10,000, which is how the 5 TB object ceiling is reachable. Part numbers need not be consecutive — except when you are using checksums, where they must run consecutively from 1 and a non-consecutive complete is rejected with HTTP 500. Metadata is fixed at create time; you cannot add user metadata at complete. Re-uploading a part number overwrites the previous part silently.

Scaling reality check

In-progress multipart uploads never expire. A client starts a 500 GB upload, the Lambda times out, nobody calls AbortMultipartUpload, and the uploaded parts are billed indefinitely at the class each part was uploaded with. The object does not exist, nobody can see it, and it appears in no normal listing — only in ListMultipartUploads. The fix is a lifecycle rule, not discipline: AbortIncompleteMultipartUpload with DaysAfterInitiation (commonly 7), plus a periodic ListMultipartUploads alarm, because the rule is what cleans up and the alarm is what tells you the rule stopped working.

The volume gives no single-PUT size threshold at which multipart becomes worth it — the only numbers it states are the part bounds above, and a part count in the ETag is a usable operational signal on its own (an object with 500 parts was uploaded by someone who did not think about it, and small parts cost requests or, under 5 MB, are rejected outright).

04

Elasticsearch: the inverted index

Every capability Elasticsearch has follows from one structural decision: it does not store documents in a shape you can scan. It stores a terms dictionary and, for every term in it, a postings list of the documents containing it, sorted. A query is then a set of dictionary probes plus intersections over sorted lists — and a document is never read to answer it.

Analysis: text becomes the keys of the dictionary

Analysis is a three-stage chain — char filters (strip HTML, map é→e), a tokenizer (standard, whitespace, keyword, ngram, edge_ngram, pattern), then token filters (lowercase, asciifolding, stop, stemmer, synonym_graph, ngram). The tokens it emits are the dictionary keys.

Interview trap

The same chain runs at index time and at query time, and the index-time chain is what populated the dictionary. If the index stemmed and the query did not — or worse, a synonym set applied on only one side — the query returns fewer results rather than raising an error. The asymmetry is silent, and the only safe fix is a reindex with an alias swap, because the analysis chain is part of the schema, not a runtime setting, and is not retroactive.

Where a field's data actually lives

Three places, with different costs, and conflating them is the source of most "Elasticsearch is using too much heap" incidents.

Three structures, three cost profiles — and what each cannot do
StructureShapePowersCannot
_sourceThe original JSON, compressed, on disk — usually the largest single componentReturning the document; reindexing from itCannot be queried
PostingsTerm → document ids, per segment, on diskText search, matching, scoringCannot sort or aggregate
doc_valuesColumnar, on disk, off-heapSorting, aggregations, script accessNot text-searchable — it is unanalyzed; drops array order, duplicates and nulls; disableable per field
Scaling reality check

A text field with a .keyword sub-field costs three structures for one logical value — text postings, keyword postings, keyword doc_values. Usually worth it, and worth declaring explicitly rather than inheriting from the dynamic default. The heap rule that governs all of this: keep the node heap at or below roughly 31 GB (the compressed-oops limit), target 10–50 GB per shard, and keep shards under about 200 million documents.

Elasticsearch: mapping, analysis and relevance

Getting it wrong costsA match on a 500-char description finds one term; the fix is a reindexA term with the wrong case returns 0 hits and you debug the query for a day

Dynamic mapping turns a string into text plus a .keyword sub-field, which is usually right and is worth declaring on purpose so the intent lives in the mapping rather than in a guess about what the default will do. Dynamic mapping also produces the failure that fills incident reports: a new JSON key in one document creates a new field — its own dictionary segment, postings, doc_values column, norms and mapping entry, tracked per shard — and deleting its documents never removes it.

Interview trap

"Elasticsearch silently ignores a field I know is in the document." It is silent by design: a query against an unmapped field returns no matches and raises nothing, while GET index/_doc/1 shows the field in _source. It happens for a dynamic: false sub-object, a case-differing field name, a field added to the mapping after documents were indexed (not retroactive), or a field under a dynamic path typed incompatibly. Diagnose with GET index/_mapping/field_name and a match_all; prevent with dynamic: strict at the root where you control the shape, flattened for arbitrary key-value data, and dynamic templates for the middle.

Scoring: BM25, per shard

Relevance is BM25 with k1 = 1.2 (how fast term frequency saturates) and b = 0.75 (how much field length is normalised, stored as one byte of norms per document), combined with IDF. The part that bites in production is not the formula: BM25 is computed per shard, so IDF and averages are local to each shard's segment set, and scores are not comparable across shards. The default query_then_fetch collects and re-sorts at the coordinating node; dfs_query_then_fetch makes the statistics global at the cost of an extra round trip.

must and should score; filter and must_not do not — and the cache is the point
ClauseScoredFilter cacheUse for
mustYesNoTerms that should affect relevance

What you give up against a database is the other half of the trade: no joins, no cross-document transactions, no referential integrity, and a durability setting that is request versus async rather than a transaction log. The correct architecture for almost every system with search is both — a relational source of truth and a derived Elasticsearch index with a chosen staleness bound written down, not assumed.

06

Elasticsearch: shards, refresh and deep paging

Health colours, and what each one actually means
ColourMeaningMost common cause
GreenEvery primary and every replica assigned—
YellowEvery primary assigned; some replicas are not. No data loss, reduced read redundancyMore replicas than there are nodes to place them on
RedAt least one primary unassigned — that data is currently unavailableFull disk, an unrecovered node, or allocation rules that cannot place a shard

Yellow on a small cluster is arithmetic, not failure: 3 nodes, 5 primaries and 1 replica each need 15 shard copies and only 10 exist, so the topology is impossible rather than broken. The lesson generalises — shard count must be a multiple of the node count when you want full redundancy, and 5 is the number someone produced by rounding a size estimate.

Interview trap

cluster_block: read only-allow-delete reads like a permissions problem and is not one. It is the disk watermark: about 85% stops new shards being allocated to a node, about 90% sets read-only-allow-delete on that node's indices, and about 95% forces the index read-only across the cluster. The watermark check is a disk-space check, not a disk-health check, and nine times out of ten the answer is "the disk is full".

Refresh, flush and merge: three different things

index() writes into an in-memory buffer. Every refresh_interval — default 1 second — opens a new immutable segment, and that is the searchability boundary. Separately, every translog flush fsyncs, and that is the durability boundary. Merge is what reclaims space from deleted documents: a delete leaves a tombstone, and the bytes come back only when a merge completes — which is why the answer to reclaiming space is dropping a daily index, not delete by query.

{
  "refresh": "-1",
  "index": { "action": "index", "_index": "orders-2026.09",
             "_id": "doc-88213" }
}
{ "order": { "customer": "4821", "status": "SHIPPED", "total": 250.00 } }

{"index": {"_index": "orders-2026.09", "_id": "doc-88214"}}
{ "order": { "customer": "4822", "status": "NEW", "total": 75.00 }}

POST /orders-2026.09/_refresh

{ "size": 20, "sort": [{"created_at": "asc"}, {"_id": "asc"}],
  "search_after": ["2026-01-15T10:00:00Z", "doc-88213"] }

One refresh at the end of a bulk load, not refresh=wait_for per document — which would serialise the whole load on the refresh interval. The second sort key is the tiebreaker that makes the cursor deterministic.

Must remember

refresh=wait_for is the right tool and the wrong default. It is exactly what a read-your-writes test needs and exactly what you must not put on a million-document ingest. refresh_interval: -1 is correct for a load job and dangerous for a live index.

Deep paging is a memory problem, not a latency problem. from=100000&size=20 means "compute the top 100,020 matches and give me the last 20" — every skipped hit is fetched, scored and thrown away, and the coordinating node holds from + size hits in heap, which is why index.max_result_window defaults to 10,000. Use scroll for a full export and search_after for interactive paging; the latter needs a deterministic sort with a unique tiebreaker (_id) last, an exact round-trip of the previous page's sort values, and a PIT.

Scaling reality check

Shard count costs more than shard size: every shard consumes heap on every node, adds segments and file handles, and adds cluster-state and cluster-health overhead, so rebalancing never settles under churn. It is the least reversible decision in Elasticsearch, because changing it means reindexing — which is why it belongs in design review, chosen from a forecast, rather than in a default. The first thing to change on a slow index is usually refresh_interval (5 or 30 seconds), a pure latency-for-throughput trade.

07

Choosing a store

The deciding question is never "which is fastest". It is what are the four operations, and which reads, if stale, would a user call a bug? That list is usually short and identifiable — your balance, your order status, your permission check, your write confirmation — and everything else can be eventually consistent, with the cost paid by the UI rather than the database.

The all-eight table, on the columns that actually differ
StoreFits whenFails whenReversibility
PostgreSQLTransactions, joins, ad-hoc queries; human-scale writesWrites far beyond one node, or multi-region writes with local latencyHigh before sharding, low after
MySQLThe same, where the team already knows InnoDBYou need the richer types or the better plannerHigh before sharding
RedisCache, session, rate limiter, queue, lock; access by keyIt is the source of truth for anything you cannot rebuildVery high
CassandraEnormous write volume, known and narrow access patternsAd-hoc queries, secondary indexes, cross-partition strong consistencyLow — the schema is the query set

MongoDBGenuinely document-shaped data, read whole, flexibility wantedJoins across entity types, strong cross-document transactions at scaleLow once aggregations depend on the shape
S3Large, immutable, write-once objects fetched by key or prefixFind by an attribute, update part of one, join twoVery high for the bytes, zero for the semantics

Must remember

Only two of the eight do joins — PostgreSQL and MySQL. Everything else makes you denormalise, which is a consistency mechanism you now own. And the best single predictor of how hard a store is to leave is whether the access pattern is encoded in the schema: the key structure, the partition key, or the mapping. The most reversible stores are the least authoritative.

Adding a store to a system that already has one

The order of operations, cheapest reversible thing first
StepActionTrigger
1Do nothing you cannot justify with a query that is currently slowA named slow query, not a scale projection
2Add the cheapest reversible thing: Redis for expensive reads, S3 for payloadsNeither changes the system of record
3Only then add a store that encodes the access pattern — build the search index, define the staleness bound, rehearse a full reindex under loadA named access pattern the database cannot serve
4Move ownership last, if at allOnly when the access pattern is genuinely different, not because the data is "big"

Every one of these additions has the same failure mode: two systems that can disagree and no named owner for the disagreement. The highest-value artefact you can produce is a one-page derived-store contract — derived from what, how stale is allowed, what happens when it is behind, and who is paged — because that document turns "we have two sources of truth" from an incident into a known property of the system. Prefer CDC (Debezium) over a dual-write, and rehearse the rebuild before you need it: a search index you have never rebuilt is an outage with a scheduled start time.

S3 and Elasticsearch

Question, then the answer in two or three sentences
QuestionAnswer
D27. 2 billion searchable product documents. What do you check, and what do you make them promise? Four inputs: document count and doc_values footprint (heap is driven by field cardinality, so all shards' data must sit comfortably below roughly half of heap per node); the query patterns (sort and aggregate fields need doc_values, searched fields need postings — not the same set); write rate and indexing strategy; and a staleness contract with a reindex path. In exchange: a shard count from a forecast at 10–50 GB per shard, deliberate routing, an explicit dynamic: strict mapping, separate indexes per data type, an agreed retention, and — the one that decides the project — a source of truth elsewhere. If "how do we rebuild this" has no answer, push back.
D28. 500 GB written to S3 nightly, most of it read back next day from another region. Storage-class and egress reasoning? Lifecycle rules are the wrong mechanism: every transition to an archive class incurs a per-GB retrieval charge on read-back, plus an early-deletion charge inside the minimum duration. Write once, read once, source then dropped is archival, so write straight to the archive class and never read it back. The axis that dominates is cross-region egress — at 500 GB a night it dwarfs a month of storage-class differences, so the whole answer is not moving 500 GB across a region boundary: replicate after processing, process where the data is produced, or export a derived aggregate of about 1% of the volume.
T100. 40 TB bucket, 300 million files averaging 130 KB. Break down the bill. Storage (40 TB) is the easy axis. Requests dominate — 300 million objects means every GET is priced per 1,000, and any automation listing a 300-million-object prefix pays 300,000 LIST requests just to enumerate at 1,000 keys per page. Two surprises: at 130 KB the objects sit just over the 128 KB minimum billable size for IA and archive classes, so 4 KB files cost the same as 128 KB ones; and retrieving an archive read repeatedly can cost more than the storage it saved. At small object sizes, requests and egress dominate — choosing a storage class without counting reads chooses the axis that matters least.
T101. A rule moves objects to GLACIER after 30 days. What happens on read-back, and what should the rule have said? Per object: a billed Restore request, then a per-GB retrieval charge, and minutes to hours rather than the 3–5 hours of DEEP_ARCHIVE. For a few files that is trivial; at 100,000 files it can exceed the storage it saved. The rule should have transitioned at a genuinely archival age (30 days is inside the early-deletion window, so it promises permanence the data does not keep), added a DEEP_ARCHIVE tier for the cold tail, restricted transitions to objects above 128 KB, and added an expiration rule — an archive with no expiry is where data goes and is never deleted.
T102. 3 nodes, 5 shards, 1 replica, yellow. What is wrong? Arithmetic, not failure: 5 primaries with 1 replica each need 15 shard copies and only 10 exist, so the topology is impossible rather than broken. Fix it by adding a node, reducing the primary count to 3 or 2 (a reindex, not a config change), or setting number_of_replicas: 0 — which is not redundancy for free, because a node failure then loses data. Shard count must be a multiple of node count for full redundancy, and 5 is a size estimate someone rounded.
T103. Searching "running shoes" returns nothing for a document reading "Great for running and walking". Why? It is analysed correctly and still misses: "shoes" is not in the document, and the default operator effectively demands the distinctive term. Query for a single distinctive term, set operator: "or" on the bool, or apply a synonym set — at index time as well as query time, which is the most common reason a synonym "fix" does nothing. Check second for the silent unmapped field: a field name that differs from the mapping returns zero results and raises nothing. ?explain=true identifies which of these in one call, and that is the correct first step rather than guessing.
T104. 900 GB index, 40 shards, 1 replica, 8 data nodes. Rebalancing never settles, ingest p99 is 8 seconds. Three interacting problems. 900 GB over 40 shards is ~22 GB each, at the small end of the 10–50 GB target, and shard count is what costs — 80 shard copies over 8 nodes is 10 per node, so any membership change triggers reallocation that competes with ingest. The 1-second refresh opens a segment per primary, and the resulting merge pressure and I/O is the 8-second p99. Change, in order: raise index.refresh_interval to 5 or 30 seconds (the single largest ingest win, a pure latency-for-throughput trade); raise index.translog.sync_interval; reindex into a better-shaped index and cut over, which is the only irreversible-ish step; separate ingest from search with a replica tier.
T105. A search index is 20× the source data on disk. Where is the space? Five places, and the two biggest are not the expected ones. Postings and the terms dictionary — a UUID or order id analysed as text gets one dictionary entry and a posting list per sub-token, and the standard tokenizer splits a UUID into many; that field should be a keyword. _source — the original JSON, per document, forever, commonly several times the size of the postings and the first thing to attack. Then doc_values (a full columnar copy per sorted, aggregated or scripted field), deleted documents (tombstones reclaim only at merge), and a mapping explosion creating a field and a doc_values column per unexpected property. Best-ratio fixes: map unconstrained payloads as flattened, and turn _source off where the document can be re-fetched from the source of truth.
T106. A multipart ETag does not match the MD5. Is something wrong? No. For a single-part, unencrypted, SSE-S3 upload the ETag is the object MD5; for multipart it is the MD5 of the concatenated part digests plus a dash and the part count — -17 means 17 parts — so md5sum will never match. SSE-KMS and SSE-C ETags are computed over ciphertext, and since late 2024 S3 applies a default CRC-64NVME checksum, so verify ChecksumAlgorithm rather than the ETag. The part count is itself a signal: 500 parts means a part size nobody thought about, and parts under 5 MB are rejected outright.
T107. A presigned URL stopped working. What are the four things that invalidate it? All four are consequences of SigV4. (1) The signing credential's expiry — X-Amz-Expires caps validity at 7 days but cannot extend the key's life, and rotating an EC2 instance-profile role's temporary credentials breaks every link in flight. (2) Clock skew producing SignatureDoesNotMatch that looks like a code bug. (3) The credential's permissions changing — authorisation is evaluated at request time, so revoking the grant revokes every URL already issued. (4) The expiry itself, and a bucket policy with a tighter s3:signatureAge. Presign for the shortest useful life, from a role rather than a long-lived IAM user, and never presign a prefix or wildcard.

The design round — the follow-up, not the opening question

Every design question in the bank, answered in one to three sentences
QuestionAnswer
D29. Your team wants to shard orders. What would convince you, and what makes sharding reversible? Ask first: current size and growth rate, the read pattern, the write rate — and whether this is a scaling problem at all, or a missing index, a long transaction, or a table that should be partitioned by time. Application-level sharding with the shard-key function in one place is reversible — re-sharding is a scheduled data-movement job. Physical sharding by range, or a key hard-coded into every query, is not. Choose the key by "which key is every query already grouping by", never by what balances; the test is whether every query is scoped to one shard or you are accepting a fan-out as a permanent cost. See Volume 6.
D30. 400 million rows, 90-second p99 on one report. In what order, and which step is hard to undo? Measure with EXPLAIN (ANALYZE, BUFFERS) on the real query and parameters; index the implied access pattern; fix statistics if the estimate-versus-actual gap is large; make the access index-only; materialise it with a stated staleness bound; move it to a read replica; and only then partition. Partitioning — specifically the partition key — is the step that is hard to undo: it lands under load, changes the physical layout and the unique-constraint rules, and locks in a query shape. Everything before it drops in a second. Under a one-window-a-month constraint, skip the partition.
D31. A team wants DynamoDB because it scales. What do you ask — and what if the answers are good? Enumerate every access pattern with its keys; name which reads must be transactional; state the data model; say what a data change costs (a pipeline, not a transaction); and price it now and at ten times the volume. "We will figure it out" is itself the answer — a GSI is a whole second copy, its own throughput cost, and always eventually consistent. If the answers are good, support it: a candidate who cannot be talked out of a well-reasoned decision is as wrong as one who blocks it on instinct.
D32. A replica is 30 seconds behind, the primary is at 40% CPU, and replica reads are getting slower. Explain. Feedback loop: the replica serves reads and applies the WAL, so read load starves apply, and a lagging replica holds MVCC snapshots that block purge on the primary — so the primary bloats and slows too. Breaks it with a circuit breaker or a deliberate fraction of reads to the primary; then find the long query or large transaction on the replica holding the snapshot, which is the single most common cause. See Volume 7.
D33. A team proposes a cache in front of every query. Your response, and the rule? That is not a caching strategy, it is a second database with weaker guarantees and a distributed invalidation problem. For every candidate cache, ask what invalidates it and what happens if the invalidation is lost — that question is the entire review. Cache reads, not writes; cache expensive reads (a query that is 40% of your traffic should be fixed with an index, since a cache in front of a hot query just moves the load); cache repeatable ones; and prefer a materialised projection when the read shape is non-trivial. The rule: a read you can afford to be stale on, that is expensive, that repeats, and for which you can name an invalidation trigger — miss any of the four and it is a memory leak with a hit-rate dashboard.
D34. Reviewing a schema change that renames a column and adds a foreign key. What beyond "does it work"? Four categories. Locking — does the ALTER TABLE take ACCESS EXCLUSIVE, and is the foreign key added NOT VALID rather than validating 400 million rows under a lock? Reversibility — is there a deploy where old code meets the new schema, and is the old column dropped only once the new code is everywhere? Write amplification — the index the key creates costs WAL on every later write. Semantic equivalence — does the rename mean the same thing in every view and dashboard, and can a CHECK fail on rows already present?
D35. On call. p99 tripled 20 minutes ago, the deploy was 40 minutes ago. First ten minutes? Do not roll back without evidence. Correlate onset with the deploy and check whether p99 rose stepwise or gradually — a gradual rise is usually coincidental and rolling back destroys the evidence. Then establish latency versus throughput: a p99 that tripled at unchanged throughput is a regression; one that tripled because throughput tripled is capacity, and rollback will not fix it. Then the query fingerprint, the plan for the new query, and locks and waits. Roll back last, with evidence.
D36. Someone proposes Elasticsearch as the system of record for a document product. What do you ask? How do you read by id? How do you enforce uniqueness on a business key, given that search-then-write is a race? How do you do a multi-document transaction, or roll one back? What are the update semantics — _update is a full read-modify-write, so concurrent updates are last-writer-wins, not a merge? If 1 to 3 are "we have not thought about that", the answer is a search index over a source of truth. The question is not "is Elasticsearch reliable" but "what guarantee are you giving up that the database gave you for free".
D37. 40,000 reads/s, 200 writes/s, 40 ms p99. Design the data tier. The 200:1 asymmetry is the design: the write path is not the interesting problem. A relational source of truth sized for 200 writes, a cache in front of the read path where 40,000 reads at 40 ms is actually met (40 ms leaves no room for the query that occasionally takes 200 ms during a checkpoint), a replica for the miss path, and staleness as an explicit contract — a TTL per data type, a "changed at" the UI can render, a read-your-writes path. Ask back: working-set size (simple or clustered), key or query (a by-query cache hits far less), and the fallback when the cache is down, which decides graceful versus cascade.
D38. 40 services, 6 databases, 2 caches. Reduce this to "one data store". The premise is a category error, and the honest diagnosis is almost never "too many stores" but "stores whose role was never defined". Inventory every store and who writes and reads it; classify each as source of truth, projection, cache or archive; ask for each projection whether it can be rebuilt — a projection with no rebuild path and no owner is the thing to delete; consolidate the unowned ones, not the load-bearing ones. Never consolidate the source of truth with anything. The data map is worth more than the count reduction, because it is what stops the next three services adding three more stores.
D39. A product decision was made on a store three of four architects think is wrong. Do not relitigate it. Make the risk legible — not "wrong tool" but "these three things become ours: uniqueness on a business key is not enforceable, we cannot update two items atomically, a schema change becomes a reindex pipeline" — because a consequence can be accepted or mitigated, and a preference cannot. Then convert the objection into a cost the team has explicitly accepted and get the mitigations written down. Then ask the staff question: what is the reversibility, and if it is low, spend two extra weeks making it reversible.
D40. You leave in two years and the company has one database. What do you build? Four things, all cheap while everything works. A data map naming for every store what it is for, with the rebuild path for every projection. A restore procedure that has been run — a backup never restored is a hypothesis, and the first attempt routinely reveals wrong credentials or an eleven-hour dump. A named owner and a staleness contract per store, so "who do I ask why this is nine minutes old" has an answer. And the irreversible decisions recorded with their reason and their date — shard keys, partition keys, the _id scheme, storage classes with their minimum durations, the mapping — because the reason is what lets someone tell whether it still holds.
D41. Move 2 TB between engines over a weekend. Plan, and what would make you refuse? Plan: establish it is necessary (a legacy constraint is a reason, "the new engine is nicer" is a preference); define the mapping explicitly including nullability, collation, time zones and sequences; backfill in batches with a keyset cursor, not OFFSET, verifying continuously; switch reads while the old store is still writable so the switch is a config change reversible in seconds; then stop writing, then decommission after a full business cycle. Refuse if there is no reconciliation, a single cutover with no dual-write period, no rehearsed rollback, a schema difference that is silently coercible rather than rejected, or a window that must be business-critical. The weekend is not the risk — the cutover is.
D42. p99 is 400 ms and the team blames the database. How do you find out whether they are right? Do not start with the database. First establish whether the 400 ms is in the database or waiting for it — the APM trace shows queueing, pool acquisition and serialised downstream calls, and an N+1 in an ORM masquerading as a slow database is the commonest version. Then split the fingerprint into three populations: a few slow queries, a few slow plans, and fast queries that are slow on locks. Check the four impostors: lock waits, a plan changed by a statistics update or a new release, a replica or storage latency change, and resource exhaustion. And ask whether it was always 400 ms — a constant p99 for a year is an unexamined design decision, not a regression.
D43. Everything is fine until it is not. What do you want in place before the bad day? Four things, and none of them is a bigger cluster. A restore you have actually performed on production-shaped data, by someone who did not set it up. Your RPO and RTO, and honesty about which is which — a replica is a fast failover with a small loss, a nightly dump is a slow recovery with a day's loss, and teams that say "we have replication" describe the first while assuming the second. The irreversibles written down with reasons. And the failure inventory: the five ways this system plausibly breaks, what each looks like, and the first diagnostic for each — so at 3am someone reads a list rather than improvises. Alert on what users feel, error rate and latency, not disk space; make the runbook's first step reversible.
