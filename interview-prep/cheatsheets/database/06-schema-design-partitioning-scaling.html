The choices you only get to make once: which key, which side the foreign key goes on, and which door you cannot walk back through.

  • 9 sections
Prev05 — Transactions, Isolation & Concurrency Next07 — PostgreSQL

If you only remember five things

  1. The key is a promise. A BIGINT sequence inserts at the right-hand edge of the index, where a B+ tree splits cheaply; a random UUID lands in the middle of the page, and a split rewrites about 40 rows to make room — which is why a random-key table tops out around 2,000 inserts/second per node while a sequential one keeps going. If you need unguessable identifiers, use UUIDv7, not v4: the 48-bit millisecond prefix buys back insert locality, and the timestamp leak is usually a smaller problem than a table that will not scale.
  2. The partition key and the leading index column should agree. When they do, a 24-hour query prunes 10 partitions to 2 and the index is usable. When they disagree, you get Case B — pruning to 1 and an index that cannot be used. When you get it badly wrong (Case C) you prune 12 to 12: every query is slower, and the only thing you bought is the ability to DROP a region.
  3. Retention is DROP, not DELETE. A 90-day sweep on a 1.4-billion-row, 900 GB table means 300 million row deletes, ~42 GB of heap churn, at least 27 GB of WAL, and 100 minutes of table locks in one transaction. The same 90 days costs one metadata operation and a file unlink — 10 to 500 milliseconds, 180 ms measured.
  4. Stability is the one shard-key property you cannot fix later. Cardinality, evenness, and query alignment you can all adjust by adding nodes or adding a second index. Change the value the shard key is derived from and you have a reshard — every row, in a fleet-wide coordinated migration. So a shard key is never a status, a region, a category, a plan, or a timestamp.
  5. Concurrency is Little's Law, and you must size from the tail. Required connections = arrival rate × time in the system: 2,000 qps at 20 ms is 40; the same 2,000 qps at 200 ms is 400. A pool set to the wrong side of that number amplifies load instead of bounding it, and the failure looks like a healthy green server — idle, and refusing to serve.

Nothing on this page matches that filter.

01

Keys, types & relationships

A key is not a label on a column. It is a promise about where new rows land in the index, whether two nodes can generate the same value, and what happens to the rows that point at it.

Surrogate key candidates, and what each costs you
KeyInsert localityIndex sizeSafe to mergeUnguessable
BIGINT sequenceBest — rightmost edge, cheapest split8 BNo — collides across shardsNo
UUID v4Worst — random page writes16 BYesYes
UUID v7Good — 48-bit ms prefix sorts by time16 BYesYes
Natural keyVaries; usually the business stringWhatever the string isOnly if truly uniqueUsually

The mechanism is a page split. An 8 kB page holds about 40 rows; appending at the right edge of a B+ tree splits it and leaves the halves 60–70% full, so the next split is cheap. A random insert splits with nothing to give away, fills the page 100%, and splits again immediately. At 2,000 rows/second with a third of writes landing on a split, that is roughly 27,000 row-writes per second of pure overhead.

Interview trap

"Use UUID so we never need a coordination service." True — and the cost is that nextval-free inserts land randomly in the index. The second trap on the same topic is MAX(id)+1 as a hand-rolled sequence: it is a full scan to the rightmost leaf, and under concurrency two readers see the same maximum and insert the same value. The UUID you were avoiding is cheaper than either.

UUIDv7 is the compromise: the leading 48 bits are the Unix milliseconds, so values sort by creation time and write to the same page. Three properties to know. It is still 16 bytes, so your index does not shrink. It leaks creation time. And it is only monotonic within one millisecond on one node — two nodes generating in the same millisecond interleave, and under load some inserts still land mid-page.

CREATE SEQUENCE order_id_seq CACHE 50;

-- 200 concurrent sessions can each hold up to 50 sequence values
-- assigned but not yet committed: up to 10,000 values burned by
-- a single burst of rolled-back transactions. This is why
-- nextval is NOT gapless -- there is no way to make it so.
Scaling reality check

A single node tops out around 20,000–50,000 small writes per second on a sequential key, and around 2,000 on a random one. That difference is the whole reason to choose keys deliberately, and it is also the difference between needing to shard and not needing to shard. Note the direction of the argument: the number that forces a sharding decision is the write rate of the key you picked, not the row count.

Naming is a decision about what a future migration has to parse. The rules: snake_case; singular table names, plural for join tables; name a foreign key after the table it points at, so a constraint violation names the relationship rather than an opaque index; never rename a primary key, because it is already embedded in every foreign key and replication stream; encode the unit in the name; prefix booleans is_, has_, or can_.

Where the relationship lives

Relationship shapes and where the constraint belongs

Must remember

A foreign key in PostgreSQL does not create an index on the referencing column. Without one, a DELETE on the parent scans the child table, and a cascade does that scan for every deleted row. The index on the many-side FK is yours to write.

Interview trap

"target_type and target_id" — the polymorphic pair that looks like it removes the join table until you need a foreign key. There is no such table, so nothing stops target_id = 999 pointing at a deleted row, and no ON DELETE rule can ever run. A nullable triple with a CHECK exactly-one constraint and partial indexes per type keeps the integrity that the pair throws away. The loose pair is legitimate only when the set is genuinely open-ended and dangling references are harmless.

CREATE TABLE activity (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind          text NOT NULL,        -- 'order' or 'invoice'
  kind_id       bigint,
  customer_id   bigint REFERENCES customer (id),
  -- Exactly one of the two, enforced by the database
  CHECK ((kind = 'order'   AND kind_id IS NOT NULL)
      OR (kind = 'invoice' AND kind_id IS NOT NULL))
);

-- Two partial indexes, each covering only its own kind.
-- A non-order row occupies no space in the invoice index.
CREATE INDEX activity_order_idx   ON activity (customer_id, created_at)
  WHERE kind = 'order';
CREATE INDEX activity_invoice_idx ON activity (customer_id, created_at)
  WHERE kind = 'invoice';

Hierarchies are where shape costs more than it looks. An adjacency list (parent_id) is one index lookup per level: twelve levels is twelve round trips, and on a 1.2-million-row table at 0.4 ms per lookup, a 0.4 ms query becomes 4.8 ms. The practical limit is about four levels on a latency-sensitive path; deeper trees want a closure table, a materialised path, or a nested set, each trading write cost for read depth.

02

Temporal & historical data

"Keep the old value" is a schema decision, and the four answers cost wildly different amounts. Before any of them: intervals are half-open, [from, to), so consecutive rows never both claim a boundary instant, and valid_to IS NULL means infinity rather than now(). Use TIMESTAMPTZ and nothing else — a timestamp without a zone is a bug that survives until the first DST boundary or the first server move.

Slowly changing dimensions: what each type can answer
TypeWhat it storesCan answerCost
Type 1 — overwriteCurrent value only"What is it now?"Free — and cannot answer a single question about the past
Type 2 — version rowA new row per change, old row closed"What was it on date D?"Growth is the change rate; the natural key is no longer unique
Type 3 — shadow columnspostcode_current, postcode_previous, postcode_previous_2"What was it before last change?"Almost never right alone — it answers exactly one question, and the column count is fixed at design time
BitemporalFour timestamps: valid-from/to, recorded-from/to"What did we believe on date D, as of date E?"A closed knowledge interval on every correction — a report already generated becomes wrong and cannot be repaired

Type 2 is the workhorse, and the operation is the thing to be able to write from memory: close the open row and open the new one in a single statement. Two statements leaves a window — milliseconds wide, guaranteed to be hit — where the customer has zero current rows or two.

WITH closed AS (
  UPDATE customer_address
     SET valid_to = now()
   WHERE customer_id = 42
     AND valid_to IS NULL
  RETURNING customer_id, valid_from
)
INSERT INTO customer_address (customer_id, address, valid_from, valid_to)
SELECT 42, 'new address', now(), NULL FROM closed;
Interview trap

"We log all the updates, so we have history." You have history only if the log is written whole-row-before-write, is durable and queryable, and is immutable. An application log written after the UPDATE commits, or written on a different connection, has a window in which it is missing the row entirely — and a dual write outside the transaction means the log and the table can disagree permanently. The trap is not that logging is wrong; it is that logging is a different mechanism with different durability.

Must remember

If your database has no EXCLUDE constraint, a Type 2 table has no database-level guarantee that two versions do not overlap. You are relying on application code. PostgreSQL can do it properly: a tstzrange column with a gist exclusion constraint enforces it, and it needs btree_gist installed for the equality part.

ALTER TABLE customer_address ADD COLUMN span tstzrange;

ALTER TABLE customer_address ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    customer_id WITH =,
    span WITH &&
  );

CREATE INDEX ON customer_address
  USING gist (customer_id, tstzrange(valid_from,
                                     COALESCE(valid_to, 'infinity'), '[)'));

Bitemporal buys one thing Type 2 cannot: answering "what did we believe on 1 March, about a fact valid in January?" That is four timestamps and a primary key of (customer_id, valid_from, recorded_from).

-- "As we knew it on 1 March, about a fact valid in January"
SELECT address
  FROM customer_address_history
 WHERE customer_id = 42
   AND valid_from < '2026-01-31'
   AND (valid_to IS NULL OR valid_to > '2026-01-31')
   -- recorded_* is the knowledge axis: what we believed in March
   AND recorded_from < '2026-03-01'
   AND (recorded_to IS NULL OR recorded_to >= '2026-03-01');
Trade-off

Bitemporal over Type 2 flips on whether you will ever be asked to restate a historical report. If a regulator, an auditor, or a customer dispute can ask "what did you show us in February?", the knowledge interval is the only thing that answers it. If the answer can only ever be "the correct value, whenever you ask", you are paying for a dimension of history no query will read — and adding it later is a one-way door, because backfilling recorded_from for rows written before the migration is a guess.

Engine support is uneven, which is the practical constraint on the whole section: SQL Server has SYSTEM_TIME and temporal tables; Oracle has Flashback; PostgreSQL gives you tstzrange and btree_gist and expects you to assemble the rest; MySQL has nothing, and you build it yourself. On MySQL the Type 2 pattern is the answer, and the exclusion constraint has to become an application transaction.

03

Index & partition co-design

One rule governs the whole section: the partition key and the leading column of the index should be the same column. Partitioning prunes; an index locates. When the two agree you get both. When they disagree you have traded one for the other, and which one you lost is the thing to check.

Pruning and index usability, by agreement
CaseSetup24-hour query doesVerdict
APartition key created_at, index leads on created_atPrunes 10 partitions to 2, index is usable inside themBoth wins, no compromise
BPartition key created_at, index leads on customer_idPrunes to 1, then scans the whole partition — index unusable across itPruning bought, locality lost
CPartition key on a column no query constrains; index unrelatedPrunes 12 to 12Disaster — every query slower, and the only thing bought is the ability to DROP a region

Case A is worth doing the arithmetic for, because "pruning" sounds free and is not. On a 1.4-billion-row table at ~140 B/row, a last-24-hours query is about 40,000 rows — roughly 10 MB, ~15 ms. A per-customer 24-hour slice is 60 rows, ~1 ms. The same per-customer query over all time is 8,900 rows, ~1.1 GB, ~4 s. Partitioning only fixes that third query if the partition key is customer_id — a time partition gives you nothing there.

Trade-off

Partitioning converts unbounded maintenance into bounded maintenance, but it does not make maintenance free, and it adds a per-partition planning cost. The condition that flips the answer is how many partitions the planner has to consider: a few hundred per table is where planning time becomes visible, and beyond that the partition count is your new row count.

Interview trap

Generic plans. After five executions PostgreSQL may stop re-planning and reuse a generic plan, and plan_cache_mode controls that. Equality on a partition key prunes under a generic plan; a range does not. So WHERE created_at = $1 keeps working after the switch and WHERE created_at BETWEEN $1 AND $2 silently loses its pruning — which is exactly the shape of a time-window query, and exactly the shape nobody notices until the table is busy. The fix is not to disable generic plans globally; it is to know which of your predicates are the load-bearing ones.

Must remember

In PostgreSQL the primary key must contain the partition key — PRIMARY KEY (created_at, id), not PRIMARY KEY (id). And a UNIQUE constraint is only global if it contains the partition key too; a UNIQUE that omits it is unique per partition, which is a uniqueness constraint that stops being one at exactly the scale you added partitioning for.

The decision order follows reversibility, not importance: query patterns first, because they are given and do not bend; the partition key next, because it is the one-way door; then clustering and index order, which are cheap to revisit. See Making the call.

Scaling reality check

When NOT to partition: under about 100 million rows (unless the goal is retention or a maintenance bound), when your hot queries do not constrain the partition key, or when the migration cost exceeds about two years of benefit. A B+ tree lookup by primary key is already O(log n) — at 10 million rows you have 4 levels, and a partition buys you nothing on a lookup that touches 4 pages. The volume's separate thresholds: partitioning is worth it around 10 million rows for maintenance and in the low hundreds of millions for query latency.

There are exactly two legitimate cases where the partition key and the index deliberately disagree, and both are maintenance rather than query: a partition whose only purpose is retention and that is never queried directly, and a hot partition concentrated enough that the index wants a different leading column. Both are exceptions you should be able to name out loud; if you cannot, you are in Case C.

CREATE TABLE events (
  created_at  timestamptz NOT NULL,
  id          bigint      GENERATED ALWAYS AS IDENTITY,
  customer_id bigint      NOT NULL REFERENCES customer (id),
  kind        text        NOT NULL,
  payload     jsonb,
  PRIMARY KEY (created_at, id)   -- partition key must be in the PK
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE INDEX ON events (customer_id, created_at DESC);
04

Partitioning

Before choosing a strategy, name the thing you are choosing between, because "partitioning" and "sharding" are different decisions with different costs and people routinely use the words interchangeably in interviews.

Partitioning and sharding are not the same decision
DimensionPartitioningSharding
ServersOne server, one buffer pool, one max_connections, one WALMany servers, many WALs, each node fails alone
Pruning a queryFree — no cross-partition cost, the engine does itA network round trip, and routing is your code
Unit of scalingThe partition: cheap, reversibleThe shard: expensive, near-irreversible
Failure blast radiusAll of it — the server holds every partition1/N of requests when a node dies
Typical triggerRetention, or bounded maintenanceOne node physically cannot hold the rows or the connections

Within partitioning, three strategies and they are not interchangeable. RANGE is the default because it pairs with time and therefore with retention. LIST is for a small closed set of business values. HASH is the one that gives up both things partitioning is for.

Partition strategies against the four questions that decide them
StrategyLocalityRebalancing costSkew behaviourQuery routing
RANGE (created_at)Excellent — pruning is exact and localCheap: attach/detach a partition; splitting a range copies only that rangeFollows the data: a quiet month is a small partition, a launch month is a large one — which is correct, not a faultEngine-local, no application involvement
LIST (region)Good for the listed values onlyCheap, same mechanism as rangeOne very popular value is one very hot partition; a value not in the list has no partition and the INSERT fails loudlyEngine-local; a DEFAULT partition catches everything else but is unprunable and unbounded
HASH (customer_id)Poor — a range predicate touches every partitionThe whole table must be rewritten to add a partitionEven by construction, and that is the argument for itEngine-local, but you cannot answer "all of last month" cheaply
Trade-off

HASH buys evenness and pays for it twice: no range pruning, and no retention by dropping a partition. The condition that flips the answer is whether you have a retention policy. Retention is the reason to partition in most systems, and hash partitioning makes it a full-table operation, so hash is right when your distribution is genuinely uneven by time (each key's rows are spread across all of history) and wrong the moment "delete everything older than 90 days" becomes a requirement.

Sub-partitioning multiplies what you already have, and every pruning factor multiplies: four is fine, forty is painful. The pain arrives as planning time and as an INSERT path that walks a two-level tree. The volume's worked example is events_2026_08_eu at ~35 million rows and ~4.9 GB against events_2026_08_us at ~62 million and ~8.6 GB — the spread between sub-partitions is itself the argument for a third level, and the third level multiplies again.

What you get beyond pruning is that every unbounded maintenance operation becomes a bounded one — per-partition VACUUM and ANALYZE, and partition-wise append and aggregate.

Scaling reality check

The number that ends the "is partitioning worth it" argument: on a 1.4-billion-row, ~900 GB table with ~100 million rows per monthly partition, a 90-day sweep is 3 partitions, 300 million rows. As DELETE that is ~42 GB of heap rewritten, 300 million dead tuples, at least 27 GB of WAL, and ~6,000 s at 50,000 rows/second — 100 minutes in one transaction, holding every dead tuple's xmax so VACUUM can reclaim none of them and the table physically doubles. Crash at minute 90 and you roll back 90 minutes of work and replay 27 GB of WAL. As DROP TABLE the same three partitions are a metadata operation and some file unlinks: 10 to 500 ms, 180 ms measured, ~0 WAL, nothing to replay.

Retention: three ways to remove 300 million rows, and what each really costs
ApproachWall clockWALFailure mode
One DELETE transaction~6,000 s (100 min) at 50k rows/s~27 GB minimum, ~42 GB of heap churnNo dead-tuple reclaim for the whole run; a crash discards 100 minutes and replays the WAL
Batched DELETE in 10,000-row chunksComparable, but each batch commits and freesStill ~300M row operations and ~27 GBLong-running — and a DELETE that is interrupted halfway leaves the table exactly as it was, not smaller
DROP TABLE the partitions10–500 ms, ~180 ms measured~0None worth naming — but the data is gone, so this is only a retention tool, never a migration tool
Must remember

Dropping a partition is a data-destroying operation with no undo. Before you DROP, detach the partition first (ALTER TABLE ... DETACH PARTITION ...), which turns the drop into a reversible file-level event you can re-attach while you still have the disk. Dropping straight through is how a retention job becomes an incident.

Converting an existing table to a partitioned one is its own project, and the ordering is where these go wrong: create the 12 target partitions ahead of time, copy a slice at a time, take a short write freeze for the final delta, rename, ANALYZE each new partition, then delete the old job rather than disabling it. Have two numbers ready: the parallel copy needs about 1.1 TB of free disk for a 900 GB table, and 12 partitions with 6 indexes each is 72 index builds.

05

Sharding

Work through the triage in order, because most "we need to shard" conclusions are wrong at step one. Is it an index problem? A working-set problem — data that does not fit in RAM, so every query is a disk seek? Write throughput? Only when a single node is physically unable to hold the data or the connections do you get to "now shard".

Two shapes. A vertical split moves columns out — the volume separates a 3.7 kB blob from a 4.1 kB orders row into its own table, taking rows per page from 18 to 24, for blobs that are 3% of queries and 88% of the bytes. But that is a schema change and a denormalisation decision, not a scaling technique. A horizontal split cuts rows, and that is sharding.

Trade-off

Shard by tenant or by customer flips on whether multi-tenancy is a product feature or a storage detail. If a tenant is a thing you sell, onboard, bill, and support — it has a dashboard, a plan, a contract, and a name in a support ticket — then tenant_id is the right key: it concentrates every query a tenant makes onto one node, and per-tenant isolation becomes a permission check. If "tenant" is just a column you added for row-level security, customer_id spreads the load more evenly and gives you a smaller blast radius when one customer is unusually heavy. Choosing the feature-flavoured key when the product does not have features is how you end up with one tenant owning a shard.

The shard key is the whole decision: four properties, and only one of them is unrepairable.

Shard-key candidates against the four properties a key must have
CandidateCardinalityEvennessStabilityQuery alignment
is_active2 values → 2 shardsTerribleNever — a status change is a reshardTwo buckets, so "active users" is a full fan-out
country_code250 values30% of users in one countryNever — a user movesRegional reports are one shard

Interview trap

"We hash on customer_id, so it is perfectly balanced." Only if your customers are. In a B2B product, 12 customers generate 40% of queries — and a uniform hash does not help if those 12 customers land on 4 shards. Hashing removes systematic bias; it does not remove the bias your data already has. The mitigation is a routing table you can override, not a better hash function.

Must remember

Imbalance is a normal steady-state condition, not an incident. The design requirement is therefore not "distribute evenly" — you cannot, given the data — it is "choose a key whose imbalance you can remediate without resharding." That is a property of the routing layer, and it is why routing has to be a datum.

What fan-out costs

One query, one shard: ~8 ms. All shards: you pay for the slowest, not the average — 512 ms serial, or the max of 64 draws in parallel, roughly 150–250 ms of end-to-end p99. A dashboard is 64 queries; 50 open dashboards is 3,200.

Five mitigations, in the order worth trying: cache the aggregate; pre-compute it; push the filter down hard enough that each shard returns little; partition the fan-out (route by region, so a regional query touches 4 shards, not 64); accept it and paginate. Making the shards faster does not work — that moves the slowest draw, and the slowest draw is the whole latency.

Must remember

Start with twice the shards you need, so growth is a split of a known range rather than a rehash of every row. And routing must be an explicit stored map, not a modulus buried in application code — a hard-coded Math.abs(customerId) % 16 makes a reshard impossible without a fleet-wide deploy, and it has no rollback. Also note the Java signature bug that shape invites: Math.abs((int) customerId) % 16 returns a negative shard number for a negative id, and shard--8 is a routing bug that only appears in production traffic.

-- Routing is a row, not an expression.
-- A reshard is then an UPDATE, with a rollback, and an audit trail.
CREATE TABLE shard_routing (
  key_hash   bigint  NOT NULL,
  shard_id   int     NOT NULL,
  assigned_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (key_hash)
);

-- Growth: split shard 7 into 7a and 7b by re-pointing a range.
-- No deploy, no code change, reversible by updating the row back.
UPDATE shard_routing SET shard_id = 73
 WHERE key_hash BETWEEN 4200000 AND 8399999;

Resharding is five phases, and the order is the safety argument: dual write, verify the two agree, flip reads, stop writing the old copy, decommission. Skipping the verification phase is how you ship a reshard that loses a day of writes to a bug nobody catches until a customer reports missing orders.

Topology follows from one fact: a row lives in exactly one place, which is why no relational store gives you write-any-row-any-node. One-writer-N-replicas means writes are single-shard, so transactions and referential integrity are too. Split a key's value space into sub-ranges and you get multiple writers per key, at the cost of every transaction spanning both halves becoming a distributed one. More shards with the same key is more capacity at the same write rate; splitting a key's value space is more writers. Different purchases, routinely conflated.

06

Replication & read scaling

Replication is the cheapest read scale-out there is, and it is also the easiest way to introduce a correctness bug you will not find in testing. Every read-routing decision is a decision about staleness, and the default that is safest is also the one people change first: primary by default, staleness as an explicit, per-call-site opt-in.

Start with the right classification, because a query is not "safe on a replica" — it is safe under one of five conditions, and only the last two are really the same choice.

Read routing by staleness tolerance
The requestRoute toBecauseFailure if you get it wrong
The user just wrote this row and is reading it backPrimaryNothing else can see it yetBlank screen, or a "not found" on a record that exists
Read-after-write within the lag windowPrimary, or a replica known to be past the write's LSNLag is real but bounded and measurableThe ghost record: the update vanishes from the UI and reappears on refresh
Explicitly stale-tolerant (cache, dashboard, report)ReplicaThe product does not promise freshnessUsually nothing — which is why this is the one to state out loud
Everything elsePrimary by defaultUnknown is not the same as tolerantAn in-page monotonicity violation: older data on a later page than newer data

The four routing mechanisms, in order. Session or sticky routing — the same user keeps hitting the same node for a window. Sticky-by-LSN — route to a replica known to be past the write's position, so read-your-writes is a guarantee rather than a hope. Monotonic reads — once you have read from the primary, never regress; this needs session state. And explicit read-your-writes in the client. "Eventually consistent" is a product statement to a customer, not a fix to a query.

Scaling reality check

Lag figures to quote: 10–200 ms when the system is quiet; seconds during a checkpoint, a bulk load, a VACUUM, a network interruption, or when the replica is CPU-starved; and unbounded during a replica restart. The volume's production case is the one to remember: average lag sat at a healthy 40 ms for a month while the p99 was 3–8 s, and the cause was a retention job re-activating a deleted account — a write pattern, not a capacity problem.

Must remember

The average is the one statistic that cannot detect a tail. A five-minute average of 35 ms is perfectly compatible with a p99 of 30 seconds. If your lag dashboard shows one number, it is measuring the thing that cannot be wrong. Alert on the percentile, and have a panel per percentile.

Synchronous replication costs availability, not latency. With synchronous_commit = on and synchronous_standby_names set, a write waits for acknowledgements — and a dead synchronous replica is a write outage, not a degraded mode. The quorum arithmetic: N replicas requiring M acknowledgements survives the loss of N − M + 1. ANY 1 (2 of 3) tolerates one failure and is fast; FIRST 2 tolerates the same one and is slower. Pair it with synchronous_commit_timeout (3 s) so a lost replica degrades to asynchronous instead of blocking every write.

Trade-off

Synchronous replication flips on whether a lost acknowledged write is worse than an unavailable write. For a ledger, a payment, or a booking, it is: you would rather refuse the write than tell a customer it succeeded. For a read-mostly catalogue, it is not: you would rather be up and occasionally stale. "It is safer" is not an answer — both options lose data or availability under some failure, and the choice is which one your business can survive.

One more shape to name: cascading replicas. A replica of a replica removes load from the primary at the cost of adding a hop to replication lag, and it means a lag spike on tier 1 is twice as visible on tier 2. It is a reasonable topology and a common source of "why is the dashboard slow" — the dashboard is not slow, it is reading from a replica of a replica.

07

Pooling & client-side limits

Connection pooling is arithmetic, and the arithmetic is Little's Law: L = λ × W — the number of connections you need is the arrival rate times how long each request holds a connection. It is not a capacity number and it is not a preference.

Little's Law applied to one service
Arrival rateTime in systemConnections requiredWhat this tells you
2,000 qps20 ms2,000 × 0.020 = 40The healthy design. A pool of 40 is correct and comfortable.
2,000 qps200 ms2,000 × 0.200 = 400A ten-fold latency regression — from cache misses, a slow downstream, or a lock — needs ten times the pool
2,000 qps200 ms, with a pool fixed at 500400 required, 500 suppliedJust enough. The failure mode is not too-small a pool; it is too-large a one.
Must remember

A pool that is larger than the requirement converges; a pool that is smaller amplifies. Too many connections means more concurrent work inside the database, which makes every query slower, which makes the queue longer — and you arrive at 500 connections all waiting, on a server that shows 0% CPU because nothing is computing. Size from p95/p99, never the average, and carry a 1.5–2× safety factor.

Why oversizing is expensive, concretely. Every connection is a backend process holding its own work_mem (4 MB by default) whether or not it is working, so 500 connections can sit on 8 GB of shared pool while idle. Past a few hundred backends you are contending on the lock manager's 256 partitions, and raising max_connections past what memory supports converts a queueing problem into an OOM kill.

Across a fleet the multiplication is the number people forget — 20,000 backends would need roughly 2 TB of RAM. So the budget rules: the sum of all pools ≤ max_connections × 0.8, PgBouncer's own pool 2–4× max_connections, and re-check whenever the query mix changes.

Scaling reality check

The hard ceiling, and the one to quote: a 64 GB instance with a 32 GB shared pool supports about 1,200 backends, and no more — roughly 20 MB per backend plus the shared pool. Any pool sizing conversation that does not end at that number is not finished.

A connection pooler in front (PgBouncer) is what makes a large logical connection count safe, and the mode matters more than the product. Transaction pooling — 100 client sessions over 60 real server connections is a normal, healthy configuration. Session pooling is barely better than no pooler at all, because it still holds one server connection per client for the whole session, which is the thing you were trying to fix.

Interview trap

Transaction pooling is not compatible with session state, and the incompatibility is silent. A bare SET instead of SET LOCAL returns to a different backend next time. LISTEN/NOTIFY, advisory locks, WITH HOLD cursors, and temp tables all assume the session is yours. Each of these returns a wrong answer or an error far from its cause, and under a pooler only under load.

-- Timeouts belong on the role, not in application config that
-- can be forgotten, and not only in the connection string.
ALTER ROLE app_rw SET statement_timeout = '5s';
ALTER ROLE app_rw SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE app_rw SET lock_timeout = '2s';

-- These three are the ones that bound damage. The pooling
-- incompatibility is a different problem entirely.

Pool exhaustion has a signature worth recognising instantly: the database is idle and green at 40 of 500 connections while the application times out. The connections exist, they are not working, and something holds them — an uncommitted transaction, a lock wait, a client that is not returning them. The alert that finds this is not "connection count high" but "zero idle in transaction sessions older than 60 seconds".

08

Making the call

Every decision above is reversible or it is not, and that classification is the most useful thing to carry out of this volume — more useful than any individual rule, because it tells you where to spend your remaining caution.

Reversibility: what a change costs to undo
ChangeCost to makeCost to undoVerdict
Add or drop an indexMinutesMinutes, and no data lossFree — do it in the same release as the code that needs it
Add a partitionMinutesATTACH/DETACH — minutesFree — this is why partitioning is cheaper than sharding
Widen a column, add a nullable columnMetadata on most modern enginesMetadataFree
Add NOT NULL to a live columnFive ordered steps, not one ALTERDrop the constraintCheap if you sequence it, a rewrite if you do not
Change the partition keyRewrites the entire tableRewrites it againOne-way door — decide it once
Change the shard keyReshard: dual write, verify, flip, decommissionThere is no undo during the migrationOne-way door — the whole design turns on it
Freeze the shard countOne constant, in code, foreverFleet-wide deployOne-way door, and the code review one
Must remember

NOT NULL is a conclusion, not a constraint you can simply declare. The sequence: add the column as nullable, backfill, validate the constraint, NOT VALID first so the check does not take a long lock, then VALIDATE CONSTRAINT, and only then set the column NOT NULL. One ALTER TABLE ... SET NOT NULL on a large table scans the whole table under a lock, which is the outage.

Interview trap

The runbook check that does not check: SELECT count(*) FROM pg_indexes WHERE indexname = '...' passes on an invalid index. CREATE INDEX CONCURRENTLY that failed leaves a row in the catalog, so your verification passes and you have no index. Verify pg_index.indisvalid, not the catalog's existence — and remember CONCURRENTLY cannot run inside a transaction block, which is a real constraint on the migration tooling you pick.

The 1.2-billion-row migration has a shape that generalises, and the shape is worth more than the instance. Dual write to both schemas. Verify with row counts, then checksums, then a byte-identical spot check on ~1,000 keys. Flip reads with an atomic rename, so there is no window where both are live. Only then stop writing the old copy.

Interview trap

Two partitioning reviews that are both wrong for the same reason — the key was chosen without reference to the queries. PARTITION BY RANGE (id) on a sequence: id is monotonic but not time-proportional, so a range predicate on a real timestamp prunes nothing, and the partitions are arbitrary slices of the id space you can never drop. And a shard count frozen as a constant: the moment you want to add a node, the modulus changes and every row moves. Neither is a tuning mistake — both are a key chosen before the query patterns were known.

The discipline underneath all of it: spend your one irreversible decision last. Teams routinely do this in reverse — pick the key, then find queries that fit it — and discover at the migration that the key was wrong.
