Volume 5 — Transactions, Isolation & Concurrency

Two of the four letters in ACID are not guarantees at all: consistency is only what your constraints reach, and durability is a configuration switch. The other two are mechanisms you can point at. This page is those four mechanisms, the four anomalies each level actually prevents, and the failure mode of every way of buying them.

If you only remember five things

  1. No standard isolation level fixes a lost update. UPDATE accounts SET balance = balance - 100 is safe because the engine re-evaluates the expression under the row lock it has just taken — not because it is one statement. The safety disappears the moment the value is computed anywhere else: in Java, in a detached entity, in a cache.
  2. Write skew is invisible at every level below SERIALIZABLE, and REPEATABLE READ makes it more deterministic. The levels below SERIALIZABLE constrain what each transaction may see; write skew is a violation that is invisible in any individual transaction's view. Two doctors read the same roster, each concludes the other is covering, both write — and the constraint is broken by two individually valid transactions.
  3. PostgreSQL's SERIALIZABLE is SSI: it lets the bad interleaving happen and aborts one transaction at COMMIT with SQLSTATE 40001. That is a correct outcome, not a failure, so the application must retry with a bounded, jittered loop. Strict SERIALIZABLE and SSI deliver the same guarantee by opposite mechanisms — one pays in contention, the other in rollbacks.
  4. Durability is a configuration switch, not a property of committing. innodb_flush_log_at_trx_commit = 2 loses roughly the last second of commits on power loss; 0 can corrupt InnoDB rather than merely lose data. A single fsync is 0.5–10 ms, so commit throughput is bounded by how many transactions are in flight per flush — not by the disk.
  5. A deadlock is a cycle in a wait-for graph, and no timeout can break one. Lowering the lock timeout does not resolve a deadlock; the engine must abort a victim. The fix is a global total lock order — sort the ids, lock them ascending — which eliminates the class of bug. A bounded jittered retry is the seatbelt; the ordering is the fix.

01

ACID, precisely

The standard answer — ACID stands for Atomicity, Consistency, Isolation, Durability, and the database guarantees all four — restates the acronym and skips the four details that generate incidents. Each letter resolves into a mechanism, and three of the four have a knob you can turn.

Each letter, the mechanism behind it, and what it costs
LetterThe mechanismThe knob that changes itWhat it costs
A Write-ahead log plus rollback records. The uncommitted transaction is in the log, durably; recovery discards it by the absence of a commit record Log file settings, group commit One fsync per commit
C Nothing. Your job plus the constraints the engine can evaluate CHECK, UNIQUE, FOREIGN KEY A check per write
I MVCC snapshots or locks — a menu of levels, not one behaviour Isolation level A longer snapshot, or more contention
D fsync of the log at commit synchronous_commit, innodb_flush_log_at_trx_commit A device flush per commit

Atomicity is a log property

The intuition is that the engine holds changes until commit and applies them at once. What actually happens is that every modification is recorded in the write-ahead log as it happens. The data pages are modified in the buffer pool, possibly visible to nobody, and the log record is what makes those modifications real.

Must remember

A transaction is not a unit of durability unless it commits. Its intermediate states are in the log — on disk, surviving a crash, and recovery deliberately throwing them away. Durable-in-the-log and committed are two different properties, and conflating them is what produces the question about a rolled-back transaction being visible after a restart.

Interview trap — “what happens if the database crashes mid-transaction?”

“The transaction is rolled back” is correct but invites the follow-up: how does it know, and why is that safe? The strong answer: the log contains a BEGIN record and a set of update records but no COMMIT record, because COMMIT is a separate, later, durable write. Recovery replays the log to rebuild the page state, finds the transaction with no commit marker, and discards its effects. The absence of a record is what carries the information.

This is also why rollback is cheap. The engine does not “unapply” anything — it stops treating the transaction as one that happened, and the version it would have created becomes garbage that vacuum or purge reclaims later.

Durability is a flush, and the flush is configurable

At commit the engine writes the log record to the OS buffer, calls fsync, and only then acknowledges the client. Every step after the fsync that anyone tuned away is a step the client was told about but the disk never received.

SET synchronous_commit = on;            -- default. fsync WAL at every commit.
SET synchronous_commit = off;           -- hand WAL to the OS and ACK immediately.
SET synchronous_commit = remote_write;  -- wait for a standby to RECEIVE the record.
SET synchronous_commit = remote_apply;  -- wait for a standby to make it durable.

-- MySQL / InnoDB, the same decision in a different dialect:
innodb_flush_log_at_trx_commit = 1   -- default. fsync the redo log every commit.
innodb_flush_log_at_trx_commit = 2   -- write to OS cache at commit, fsync once a second.
innodb_flush_log_at_trx_commit = 0   -- write AND fsync to OS cache, fsync once a second.
Interview trap — the incident that turns a flush setting into a data-loss postmortem

Setting innodb_flush_log_at_trx_commit = 2 on an orders table is an entirely normal-looking throughput tuning, and it is invisible in every test. The failure appears on a power loss, not in a query: roughly the last second of commits is gone, and because those clients received COMMIT acknowledgements, nothing in the application noticed. 0 is worse than loss — it can corrupt InnoDB rather than merely lose rows. And wal_level = minimal combined with synchronous_commit = off means a crash can lose committed transactions outright.

Scaling reality check

A single fsync is roughly 0.5–10 ms depending on the device. Committed in one at a time, that is a ceiling of about 100–2,000 commits per second, which is why a connection pool of three cannot saturate a modern NVMe drive no matter how fast it is. The number that matters is not “how fast can we fsync” but “how many transactions are in flight when the fsync returns” — which is what group commit exploits.

Consistency is not a guarantee

The engine enforces the constraints you declared and nothing else. On a double-entry transfer the engine's contribution is that a crash leaves both updates durable or neither, and a concurrent transaction never sees money leave account 1 before it reaches account 2. “The total is conserved” was never checked by anything — it held because two statements were written symmetrically by a careful human.

Interview trap — what does the “C” actually guarantee?

The trap answer is “the data is always in a consistent state”, which asserts a guarantee the engine does not make. The honest answer: the engine does not guarantee application-level consistency at all; it guarantees the constraints you declared are never violated. If an invariant is not a single-row predicate, a unique index, or a foreign key, then nothing at the database layer is enforcing it — and SERIALIZABLE will not change that.

Must remember

A transaction protects atomicity, isolation and durability mechanically. It protects consistency only as far as your constraints reach. An invariant that is not a CHECK, a UNIQUE index, or a FOREIGN KEY is a comment in a design doc and a throw in Java.

02

Anomalies & write skew

Isolation levels are named after what they prevent, so the fastest way to be useful in an interview is to know the four anomalies by name and know why each one survives a level. “Dirty read” is the one everybody has. Write skew is the one that separates a senior answer from a staff answer, because it needs the observation that isolation levels describe what a transaction sees, not what a set of transactions may collectively decide.

The four anomalies, what each reader observes, and the level that removes it
AnomalyWhat the reader seesWhy it survives below the fixRemoved at
Lost update Two read-modify-writes of the same row; one write is silently overwritten Nothing about visibility — each transaction saw a valid state and wrote a valid value No standard level. Fix the SQL: one atomic statement, a version column, or FOR UPDATE
Dirty read Another transaction's uncommitted data, which may yet be rolled back Only READ UNCOMMITTED has no visibility filter at all READ COMMITTED and above
Non-repeatable read The same row read twice in one transaction returns two values Under READ COMMITTED each statement takes a fresh snapshot REPEATABLE READ and above
Phantom read A second SELECT returns new rows matching a predicate the first one evaluated Snapshot stability pins rows, not ranges. Row locks cannot lock a row that does not exist yet Range or predicate locking, or SERIALIZABLE
Write skew Nothing. Each transaction's own view is stable and correct; the combination is invalid Each transaction writes a different row, so there is no write-write conflict to detect SERIALIZABLE — or restructure so the invariant is single-row
Interview trap — “is UPDATE accounts SET balance = balance - 100 atomic?”

The trap is answering “yes, because it is one statement”. The load-bearing word is not statement — it is under the row lock. The engine locates the row, takes a write lock, waits if another transaction holds one, then evaluates balance - 100 against the version it just locked, not the version that existed when the statement was sent. That re-evaluation is the entire mechanism. It stops being safe the moment the value is computed anywhere else — in Java, in a detached entity, behind a cache.

Write skew, worked through

The business rule is “every (day, shift) must have at least two doctors on call”. It is an aggregate over a set, so it is not a CHECK on a doctors table; it is enforced today by a service-layer assertion, which is exactly the situation write skew exists to expose. The shift starts with one doctor, Dr Chen — already short, so two people are cancelling.

Interview trap — “at what isolation level does write skew go away?”

The trap answer is REPEATABLE READ, and it ends the interview early, because it confuses repeatable reads with repeatable decisions. REPEATABLE READ guarantees a transaction sees the same version of every row it reads, twice. It says nothing about T2 — and here it makes the bug more deterministic, because pinning both transactions to one snapshot guarantees both see “1 doctor” and both conclude they are safe.

The correct answer has a second half that is usually missing: the better answer is often not an isolation level at all. A counter row with CHECK (doctor_count >= 2) makes the invariant single-row, so both cancellations contend on it and one fails its CHECK. A SELECT ... FOR UPDATE on a shared anchor row before the read serialises the two explicitly. Only when the schema genuinely cannot express the rule does SERIALIZABLE become the right tool — and it is a throughput tax plus a retry loop, not a free fix.

Must remember

Write skew needs all four steps. A version column removes step 4's freedom; a FOR UPDATE on a shared anchor removes step 1's freedom; a CHECK-enforced counter row collapses steps 1–3 into one contended write; SERIALIZABLE removes the ability of the set of transactions to run in an order that violates the rule.

03

Isolation levels

The four levels are four bundles of guarantees, not a ladder. They do not nest, because each one is a different trade of what is prevented against what is paid for. The table below is the one to be able to draw from memory, including the footnotes — a candidate who gets the InnoDB row right is demonstrating mechanics rather than slogans.

The anomaly matrix — every anomaly, every level, permitted or not

Must remember

Write skew is possible at every level below SERIALIZABLE, in every engine, without exception. This is not an implementation gap — it follows from the definition: the lower levels constrain what each transaction may see, and write skew is a violation invisible in any individual transaction's view. The two SERIALIZABLE rows are the same guarantee by completely different mechanisms: strict makes bad interleavings impossible, SSI allows them and makes them fail at commit. One costs contention, the other costs retries.

Interview trap — “PostgreSQL's REPEATABLE READ is weaker, so it is the same as MySQL's”

It is the reverse, and this is the single most common cross-engine error. In PostgreSQL REPEATABLE READ is snapshot isolation and there is no separate SNAPSHOT name. In InnoDB it is a hybrid of snapshot reads and gap-locking writes — which is why InnoDB's REPEATABLE READ blocks an UPDATE phantom that PostgreSQL's does not, and why a plain SELECT phantom slips through in both. Code tuned against one engine and deployed against the other gets different blocking behaviour with identical guarantees, which is the worst kind of portability bug.

Choosing a level

The honest framing in a design review is not “which level” but which anomalies does this transaction's correctness argument depend on, and what is the cheapest mechanism that denies them?

From transaction shape to level — and the failure mode of getting it wrong

Trade-off — why isn't the default level SERIALIZABLE?

The condition that flips the answer is whether the workload is contended. Under SERIALIZABLE you buy a guarantee whose cost is paid by whichever transaction loses the race, as either a lock wait (strict) or a full rollback after all the work is done (SSI). On a table with one writer and thousands of readers it costs almost nothing; on fifty writers on the same rows it converts correctness into a throughput collapse, with the retry loop adding load to the exact rows that are already the bottleneck. A database-wide SERIALIZABLE is almost always a sign nobody worked out which transaction needed it.

Scaling reality check

SSI aborts scale with the number of concurrent read-write dependency edges, not with transaction count alone. On a hot row, every transaction is a candidate to abort every other one and the abort rate climbs toward the arrival rate — the retries add load to the contention that caused them, which raises the abort rate, which produces more retries. The design response is to remove the contention structurally (shard the hot rows, or serialise them deliberately), not to keep the retry loop and hope.

Trade-off — migrating a codebase up a level

A codebase with no retry logic cannot be safely moved to REPEATABLE READ or SERIALIZABLE overnight, because raising the level is a global, database-wide setting: the transactions that cannot tolerate the new aborts break for everyone. The migration therefore requires a retry path for 40001 before the level changes, not after. Flipping the setting first converts a latent design gap into a production error rate.

Must remember

SQLSTATE 40001 is a correct error; treating it as a failure is a design mistake that hides real bugs. The operational distinction is between a serialization failure on a transaction that did milliseconds of work — normal, cheap to retry — and one on a transaction that held a connection for forty minutes, which is an architectural problem the retry is hiding. A global retry policy with no attempt cap and no alert on the retry rate converts a correctness bug into connection-pool exhaustion, because every retried transaction holds its connection for the whole backoff.

04

MVCC

Multi-version concurrency control is the one-sentence version — readers never block writers and writers never block readers, because a writer never changes what a reader will see — and it is implemented by never destroying anything. An UPDATE in an MVCC engine is three operations: copy a new row version, mark the old one as superseded, and chain them with a back-pointer.

The most instructive consequence is rollback. Nothing has to be undone. The new version is discarded and the old one — still physically present, still linked, never destroyed — becomes current again. That is why MVCC makes rollback nearly free, and why the engine can afford to be generous with copies.

Must remember

The reader's decision is based on when the reader's snapshot was taken, not on when the row was written. That is the whole mechanism behind REPEATABLE READ stability: the snapshot is fixed, so the comparison against every version is fixed, so the same version is selected every time. “It uses a snapshot” is too vague to reason with; this is the answer that demonstrates you have read the source.

What MVCC costs

The costs are not abstract — they are most of the MVCC-related operational work in a real deployment, and the long-running transaction is behind nearly all of them. Bloat is a read cost, not a space cost, which is why it shows up as “the table got slower” long before anyone checks free disk.

The four costs, and what causes each one
CostWhat it isCauseWhere you see it
Bloat Dead versions accumulate; the physical size grows while the logical size does not. Every sequential scan reads four million physical rows to return one million logical ones Every UPDATE and DELETE leaves at least one version nobody should see again Sudden slow scans, index entries that must follow a chain and discard dead tuples
The vacuum horizon Vacuum cannot remove a version any live snapshot might need, and cannot advance past the oldest live snapshot One transaction open since 03:00 pins everything written since 03:00 as uncollectable Table grows for everyone, not just the long transaction
Transaction-id wraparound Transaction ids are 32-bit; the counter wraps at roughly 2.1  billion, and a wrap while old snapshots exist makes them appear to be in the future Long-running transactions preventing the counter being safely advanced age(datfrozenxid) climbing — a correctness emergency, not just a performance one

Scaling reality check

Bloat scales with update rate × retention time, not with table size. The formula: physical ≈ logical × (1 + updates per row during the maximum transaction lifetime). A table with a one-hour maximum transaction lifetime and rows updated twice per hour sits near 3× its logical size. The same table with a four-day maximum lifetime reaches 200× before vacuum can do anything. The operational number that matters is the longest transaction you permit — which is why statement_timeout and idle_in_transaction_session_timeout are concurrency controls, not performance tuning: they are inputs to this formula.

-- The oldest transaction that has not been vacuumed: this is the horizon.
SELECT pid, state, xact_start, now() - xact_start AS age,
       left(query, 80) AS last_query
  FROM pg_stat_activity
 WHERE xact_start IS NOT NULL
   AND state <> 'idle'
 ORDER BY xact_start LIMIT 10;

-- The metric to alert on directly, before it becomes an outage.
SELECT datname, age(datfrozenxid) AS xid_age
  FROM pg_database
 WHERE age(datfrozenxid) > 100000000;   -- approaching wraparound
Trade-off — MVCC or locking concurrency control?

The condition that flips the answer is the read-to-write ratio and the tolerance for blocking. MVCC wins when reads outnumber writes, when read latency must be predictable, and when blocking is unacceptable — every OLTP system, which is why essentially every major engine converged on it. Locking wins when the working set fits in memory and the engine can afford to serialise, because it produces no garbage, no vacuum and no horizon. That is why strict SERIALIZABLE still exists inside an otherwise-MVCC engine: the right tool for a nightly batch over a table nobody else is touching, the wrong tool as a default. MVCC did not beat locking — it beat blocking, and blocking is what shows up in a latency percentile.

Interview trap — “MVCC means no locks at all”

It means no locks on the read path. The engine still takes ACCESS EXCLUSIVE for DDL, still needs table-level locks for SERIALIZABLE, and InnoDB takes next-key locks on writes even at REPEATABLE READ. “No locks” is also why the cost moves somewhere invisible — from lock waits to bloat, to a vacuum horizon, to a disk that fills with data nobody is allowed to delete.

05

Locks & lock waits

Locks are the tax you pay when you chose serialisation over snapshots, and someone else always sends the bill. The eight relation-level modes and their compatibility matrix are the whole subject — everything else in this section is a consequence of them.

The eight relation-level lock modes

Intention locks are the mechanism that makes table-level refusal cheap: before taking a row lock you declare at table level which finer-grained mode you are about to acquire, so a conflicting table-level requester can be refused immediately instead of scanning. They do not lock rows; they advertise.

Interview trap — “we added a column and the whole database stuck”

Almost every ALTER TABLE takes ACCESS EXCLUSIVE, which is compatible with nothing. It does not wait politely for readers to drain — it requests the one mode nobody can hold, and then every subsequent query queues behind it, including plain SELECTs that were not there when it started. The result is a table that looks frozen: existing statements finish, new statements of any kind queue, and the pile grows until the connection pool is exhausted and the application reports a total outage rather than a slow query.

The senior answer has two halves. First, the cheap escapes: adding a column with a volatile default rewrites the table and holds ACCESS EXCLUSIVE throughout, while a constant default, a nullable column, or a column appended at the end takes it only briefly — CREATE INDEX CONCURRENTLY is the same idea. Second, and this is the staff-level point: the real fix is not a lock timeout, it is not running DDL on the live table during business hours, and a DDL lock's duration is a function of table size — a number that should be discovered in a rehearsal, never during a deploy.

Scaling reality check

ShareUpdateExclusive is how a long write starves VACUUM: it is compatible with nothing except itself, so VACUUM cannot run while anything modifies the table. A long UPDATE on a large table can therefore block autovacuum indefinitely — and by section 4 that is not a slow query, it is uncollected garbage for the whole database. The operational pairing is a statement_timeout on every role that is not a migration role, plus an alert on the oldest running xact_start.

Waits, queues, and who is actually the problem

The lock queue is FIFO, and the holder is never preempted: a new request queues behind everyone already waiting, and cannot jump ahead of them. The consequence is that a lock queue converts one slow transaction into a queue of slow transactions, and the transactions that look slow are mostly innocent.

Interview trap — “the query at the top of pg_stat_activity is the slow one”

Usually not. The victim is the slow query; the blocker is the cause, and the blocker is frequently a transaction that has been open for hours and is doing nothing. Start from xact_start, not from query_start, and remember that an idle-in-transaction session holds every lock it took — including the ACCESS SHARE from its last SELECT — for the whole session.

Lock granularity — a real trade-off, not “finer is better”

Finer is not better, and the staff-level observation is that the case worth reasoning about is not the one you can tune but the one you cannot: DDL and TRUNCATE are table-level in every engine, so no amount of row-level tuning does anything for the incident that actually pages you.

06

Optimistic vs pessimistic

Both detect the same condition — someone else changed the data between your read and your write — by assuming opposite things about the world. Pessimistic takes a lock before reading, so read and write are indivisible with respect to other writers, and the cost is paid by the other transaction as a wait that happens even when no conflict would have. Optimistic reads freely and detects the conflict at write time, and the cost is paid by you, as a discarded transaction plus a retry.

Optimistic: the version column is the whole mechanism

On read you remember the version; on write you put it in the WHERE clause. “0 rows affected” is the entire detection mechanism — there is nothing else to build, and nothing else to configure.

ALTER TABLE products ADD COLUMN version INT NOT NULL DEFAULT 0;

-- READ: note the version alongside the data you are about to decide on.
SELECT id, name, price, version FROM products WHERE id = 7;
--  id | name    | price | version
--  7  | Widget  | 100   | 3

-- WRITE: the version goes in the WHERE clause.
UPDATE products
   SET price = 90, version = version + 1
 WHERE id = 7 AND version = 3;      -- rows affected: 1 -> we won

-- versus, if another transaction committed first:
UPDATE products
   SET price = 90, version = version + 1
 WHERE id = 7 AND version = 3;      -- rows affected: 0 -> we lost, and we know it

Two details make it correct and both are easy to get wrong. The version must be checked in the WHERE clause and the row must be identified by the primary key — a non-unique predicate like WHERE name = 'Widget' AND version = 3 makes the update affect an arbitrary matching row, which is neither a correct check nor a safe write. And version = version + 1 is what makes the next reader's swap fail; without it two transactions could both read version 3 and both write successfully, because the version never changed.

Interview trap — “we added a version column. Is our update safe now?”

Not automatically, and the gap is worth drawing out. A version column only protects the statements that include it in the WHERE clause. An ORM doing dirty checking issues UPDATE products SET price = ? WHERE id = ? — the default generated SQL for most entity states — which does not use the column at all, no matter that the column exists on the entity. The protection is a property of the SQL that reaches the database, not of the schema. The review question that catches every variant: grep the codebase for every UPDATE and DELETE against this table and confirm each one either checks the version or is a documented exception.

Pessimistic: SELECT ... FOR UPDATE

Take the lock before the read. The subtlety that trips people up is that a locking read is not a snapshot read: it does not go through the MVCC visibility path, which is why it can return a value the transaction's own snapshot would not have seen.

Must remember

SKIP LOCKED is not a performance feature; it is a correctness requirement for a multi-consumer queue. Without it, eight workers pulling from one queue are not eight workers — they are eight processes serialised behind whichever one holds the head-of-queue row, which is strictly worse than a single worker because the serialisation point is nondeterministic. With it, FOR UPDATE SKIP LOCKED is the standard shape for SELECT ... LIMIT 1 work distribution.

Interview trap — the snapshot gap under a plain FOR UPDATE

Under snapshot isolation, locking a row does not lock the range around it. PostgreSQL's REPEATABLE READ is a pure snapshot with no range locking at all — inserts are never blocked by readers, and predicate ranges are locked only at SERIALIZABLE. So a transaction that SELECT ... FOR UPDATEs the rows it found can still be surprised by a row that matches its predicate but was not in the result, inserted concurrently afterwards. Locking the rows you found closes write skew on those rows; it does not close phantom reads.

Retry loops

Every retry path in this chapter — optimistic conflict, 40001, deadlock — has the same three requirements, and getting any one wrong turns a resilience mechanism into a load amplifier.

private static final int MAX_ATTEMPTS = 5;   // 1. BOUNDED. Unbounded is a hang
                                           //    with extra steps.

// 2. EXPONENTIAL BACKOFF WITH FULL JITTER. The jitter is load-bearing,
//    not the growth. Without it, every client that failed at the same
//    moment retries at the same moment, forever, in lockstep.
private Duration backoffWithJitter(int attempt) {
    long cap = Math.min(MAX_BACKOFF.toMillis(), BASE_BACKOFF.toMillis() * (1L << attempt));
    return Duration.ofMillis(ThreadLocalRandom.current().nextLong(cap + 1));
}

// 3. RETRY ONLY WHAT IS TRANSIENT.
private boolean isTransient(SQLException e) {
    if (e instanceof SQLTransientException) return true;
    String sqlState = e.getSQLState();
    return "40001".equals(sqlState) || "40P01".equals(sqlState);
}
Scaling reality check

Optimistic concurrency degrades non-linearly and then falls off a cliff. With few contenders the expected attempts per success is near 1. As contenders on one row increase, attempts per success approaches the number of contenders — N writers on one row means on average N/2 attempts per success, and every failed attempt is a full transaction that did real work and was rolled back. Beyond a handful of genuinely concurrent writers on a single row, the wasted work itself becomes the load. The fix is never a better retry loop; it is to remove the contention — partition the counter, or design the workflow so N writers do not all need the same row.

Trade-off — pessimistic or optimistic for this workflow?

The condition that flips the answer is the conflict rate, and it is measurable rather than theoretical. Optimistic is right when conflicts are rare — most user-facing CRUD — because it costs nothing in the common case and needs no lock table, no deadlock handling and no wait. Pessimistic is right when conflicts are frequent and the work per conflict is expensive: a claim-the-next-job queue, an inventory decrement with a multi-step pricing calculation, anywhere a failed attempt would mean discarding seconds of work. The middle case most teams actually have is usually neither — restructure the contended operation into one atomic conditional statement and check the affected-row count, which is strictly better than both.

Interview trap — “a retry that reuses the value it read”

Not a retry. The entire read–decide–write must be inside the loop, not just the write. A loop that retries the UPDATE while reusing the value from the failed attempt's SELECT re-asserts a stale fact — and because the affected-row count will be zero again, it burns every attempt and then reports a failure that was never actually contended.

Must remember

Three retry failure modes to name unprompted: no jitter (a thousand clients fail together, retry together, and the retry loop is the outage — invisible in a test with one client); unbounded attempts (a permanently failing transaction holds its connection, its snapshot, and under REPEATABLE READ the vacuum horizon for as long as it keeps trying — that is the long-running transaction from section 4 wearing a different hat); and retrying at several layers at once, where the effective attempt count is the product and the team believes it is the sum.

07

Deadlocks

A deadlock is a cycle in a wait-for graph, and that is the whole definition. Vertices are transactions and locks; an edge points from a waiter to the holder it is blocked on; a deadlock is a cycle in that graph. Nothing about the cycle is exotic, and no timeout can break it, because in a cycle no transaction is making progress — there is no one whose timeout has merely not fired yet.

Three prevention techniques, in order of preference
TechniqueRuleWhy it is better than the alternativeWhen it is the wrong answer
Global lock order Sort the ids being locked ascending and lock them in that order, everywhere Makes the bug impossible rather than less likely. One line of code, and it is enforceable in review Almost never — reach for it first
Single-row transactions Each unit of work touches one row and commits immediately The wait-for graph becomes a set of isolated nodes instead of a web. This is why SKIP LOCKED claim loops are deadlock-resistant When the items are genuinely not independent, because you lose atomicity across the batch
Reduce the lock surface Every lock is an edge, so removing locks removes cycles: lock only what you will write, and never hold a lock across a remote call Cheap, local, and usually the actual fix in a microservice codebase Never — it is strictly better than the other two as a first pass 
@Transactional
public void applyBatch(Collection<Long> itemIds) {
    List<Long> ordered = itemIds.stream().distinct().sorted().toList();
    for (Long id : ordered) {
        repository.lockById(id);   // SELECT ... FOR UPDATE
        processor.process(id);
    }
    // Every batch job in the system locks in the same order, so no two
    // of them can ever build a cycle. Two such jobs that disagreed on
    // order were the deadlock; this line is the whole fix.
}
Interview trap — “how do you fix deadlocks?”

The trap answer is “retry on failure” or “lower the lock timeout”, and both are wrong in a way that matters. Lowering the lock timeout does not resolve a deadlock at all — a cycle means nobody is progressing, so there is no timeout that can break it; the engine must abort a victim, and it already does. And retrying without fixing the ordering produces a system that deadlocks more often under load, because the retries add load to the exact contention that caused it.

The senior answer: a deadlock is a symptom of inconsistent lock ordering. Enumerate the rows each transaction acquires and the order it acquires them in; find two whose sets overlap and whose orders differ; apply a global total order to every multi-lock path. Then additionally implement a bounded, jittered retry — because even with perfect ordering a three-way cycle you did not enumerate will still occur. The ordering is the fix; the retry is the seatbelt. Confusing the two is the mistake.

Scaling reality check

Detecting a cycle costs a wait, and the default deadlock_timeout of one second is deliberately longer than ordinary lock waits so short cycles never trigger an abort. The consequence is operational: a deadlock is not a fast failure, it is a one-second penalty on top of the aborted work, and a code path that deadlocks on a fraction of requests is a p99 problem long before it is an error-rate problem. If the rate is rising, the ordering is wrong; if the rate is small and flat, the retry is a seatbelt doing its job.

Must remember

Never hold a database lock across a remote call. A SELECT ... FOR UPDATE followed by an HTTP request to a payment gateway holds a row lock for the duration of a network round trip to a third party — the single most common cause of deadlock escalation in a microservices codebase, and the fix is architectural (a saga step with the lock released between steps), not a shorter timeout.

08

Distributed transactions

ACID stops being a property of anything the moment the work crosses a process boundary. Two-phase commit is the protocol that genuinely extends it, and the reason it is nearly absent from modern service architectures is not that it is slow or legacy — it is one specific failure mode.

2PC, XA, saga, or outbox — the condition that picks the answer
PatternUse whenWhat it costsFailure mode
2PC / XA You need true atomicity across resources and cannot change how the far side handles retries and duplicates — a mainframe, a vendor database, a broker with no idempotence A coordinator you must trust more than your architecture lets you trust anything Blocking. Coordinator death leaves participants in-doubt and unavailable
Saga The process is a sequence of steps with a semantic inverse each — refund, release, cancel Designing the compensations, which is real business logic and cannot be generated A compensation fails, so you need a human-replayable state, not a retry
Outbox + idempotent consumer The far side is a service you own and the requirement is “this event must not be lost” A relay, a table, and consumer-side dedup A duplicate, not an outage — detectable and suppressible at the consumer
Interview trap — “just use 2PC across the services”

The reflex is right about the problem and wrong about the cost. The argument against 2PC is not speed and not age — it is that a prepared participant cannot unilaterally abort, so a single coordinator process becomes a availability dependency for every resource it touches. The honest counter-question is: who owns the far side's behaviour? If you own it, the outbox satisfies the same “must not be lost” requirement with a failure mode of a duplicate rather than an outage.

The outbox exists to kill the dual write — writing to your database and publishing a message are two systems with no transaction spanning them, so one of them will eventually be wrong, and the application genuinely cannot tell which. Three outcomes are all reachable and none is detectable from the app: publish throws before the broker got it (event lost forever), throws after (retry duplicates it), or succeeds and the app crashes before recording that (retry duplicates it). Only removing the dual write resolves it.

-- The outbox row and the business row are one atomic unit. There is no
-- window in which the order exists and the event does not.
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (id, topic, payload, created_at)
    VALUES (gen_id(), 'orders', '{...}', now());
COMMIT;

-- The consumer side. The dedup record and the effect are one
-- transaction, so a redelivery cannot apply the effect twice.
CREATE TABLE processed_messages (
  message_key   TEXT PRIMARY KEY,
  consumer_name TEXT NOT NULL,
  processed_at  TIMESTAMPTZ NOT NULL,
  CONSTRAINT dedup_identity UNIQUE (consumer_name, message_key)
);

BEGIN;
  INSERT INTO processed_messages (message_key, consumer_name, processed_at)
    VALUES (:key, :consumer, now());
  -- A duplicate raises a unique violation, rolling the whole
  -- transaction back, so the effect below is never applied twice.
  UPDATE orders SET status = 'CONFIRMED' WHERE id = :order_id;
COMMIT;
Must remember

Claiming “exactly-once” from an outbox is the trap. What you have is at-least-once delivery with exactly-once effect, and the second half comes entirely from the consumer. The argument for accepting at-least-once is not that duplicates are harmless — it is that they are detectable and suppressible at the consumer, whereas a lost event is neither.

Interview trap — the dedup key, and the pruning bug

Two properties are load-bearing and both are commonly wrong. The dedup key must be derived from the message — a consumer-generated UUID is unique on every delivery and deduplicates nothing. And the retention of the dedup table must exceed the broker's maximum redelivery window; a table pruned too aggressively resurrects old duplicates, which presents weeks after the pattern was deployed and working.

Scaling reality check

The outbox is a database table, so it has every operational property of one. Relay lag is the delay between commit and publication and is user-visible for anything time-sensitive — alert on outbox age, not count. Table size grows without bound unless published rows are deleted, and marking then deleting in separate steps leaves the rows to be vacuumed. And the relay is a serialisation point: publishing in key order to preserve per-aggregate ordering caps throughput per key at the relay's publish rate, which is why partitioning the outbox by aggregate id is the design most teams converge on once the numbers matter.
