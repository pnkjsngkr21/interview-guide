Microservices — The Microservices Complete Deep-Dive

Volume 2 — Communication, Data & Consistency

What holds two services together when there is no shared transaction: the guarantees you pick per operation, the keys that make a retry safe, the outbox that makes an event atomic with its write, and the price each one costs.

  • 9 sections
← Vol 1 Vol 3 →

If you only remember five things

  1. There is no exactly-once delivery, and no client can be given one. What exists is at-least-once plus an idempotent consumer. The client must supply the key, because it is the only party that can tell a retry from a new request — and the dedup check must be the insert against a unique constraint, in the same transaction as the business write.
  2. The transactional outbox is the only atomicity you get, and it buys exactly one thing: the business row and the event commit together. It buys no ordering (that is the partition key) and no exactly-once (the relay will publish twice; that is the price, paid by the consumer's dedup record). Purge by published_at, never by age.
  3. A saga is not a distributed transaction with nicer manners. It is a sequence of local transactions and forward business actions that undo earlier ones. Every compensation can itself fail, so it needs its own retry budget, its own idempotency, and a sweep for sagas that are stuck non-terminal past their deadline.
  4. Ordering is per partition, and the partition is derived from a key you choose. Leave the key null and you have round-robin: no ordering at all, for any aggregate, forever. Most teams discover this in production, not in design.
  5. Consistency is a per-operation decision, not a per-system one. Read-your-writes costs a route to the primary or a version token — those are the only two mechanisms, and every third option is an implementation of one of them. Only linearizable lets you write ordinary code, which is why it is a budget decision and not a correctness one.

01

CAP, PACELC, and the consistency spectrum

CAP is a theorem about a network partition, not a menu. The moment the network splits, a system that keeps accepting writes on both sides has two independent histories, and read-repair is a guess dressed as a decision. The choice is not which two of three to pick — it is which one you abandon, and the volume's version of the question is which write did your system accept during the partition. That is the question a partition actually forces, and it is the one most answers skip.

Interview trap

“We chose AP.” Ask which writes were acknowledged on both sides during the partition. If the honest answer is “one of them, the primary's” then the system is a single-writer primary — which is CP, and has been all along. “Available” here means it returns a response rather than an error, and a response containing stale data is a legitimate one. So the real trade is error against wrong, and the systems that are genuinely AP are the ones where wrong is acceptable: a like count, a view counter, a cached product page.

PACELC adds the else branch, and the else branch is where the latency and cost decisions live: if there is a partition else there is latency. Trading consistency for latency is a decision you make on every ordinary day, not just on the day the network breaks. A read that has to reach a quorum pays the slowest replica on every request, forever, to buy a guarantee you only need for the two seconds after a user clicks.

The spectrum

The consistency spectrum — what each rung forbids, and what it costs
Guarantee What it forbids What you pay
Linearizable Nothing. The system reads as if it were one copy Every read goes to the quorum, so read latency tracks the slowest replica
Sequential Only writes that genuinely overlap in real time Writes serialise through one leader
Causal Only a write arriving before a write that it caused Session-scoped: a version carried on the request, or a version vector
Read-your-writes Seeing your own write undone One extra hop to the primary, or a version token in every read
Monotonic reads Your own successive reads going backwards Nothing in latency; a sticky reader, or a token carried forward
Eventual Nothing, given time The application carries the invariant instead of the database

How a user sees it

The question is never “are we eventually consistent” but which read the user is looking at when the replica is behind — because only some of them are bugs.

How eventual consistency reaches the user, and what each read costs to fix
The read If it is stale, the user sees The fix What the fix costs
Order status, right after checkout “My order has vanished” — a 404 on an order that exists Route to the primary Primary capacity on the hottest read you have
Balance A wrong balance, then a support ticket Route to the primary Primary capacity, on an endpoint that gets hammered by polling
Price at checkout Being charged a different price from the one shown Carry the version from the write; escalate to the owner on mismatch A token in a contract you can never remove
Delivery address on the invoice The invoice prints the old address; the parcel goes to the wrong place Read the authoritative store, not the projection — a bigger-latency fix than the other two An extra hop on the critical path
Permission check Access wrongly granted, or wrongly refused Fail closed, and do not cache the decision A slower check, on every call
A value no invariant depends on A slightly out-of-date number Nothing. Leave it eventually consistent None — and this is the row most systems should be in
Must remember

Everything else claiming to be read-your-writes is one of those two or it is not the guarantee: a separate cleverly-ordered read path, a sticky session, a “just retry it after 200ms” — all of them. Note the flip, which is what makes this the right default rather than a compromise: it is far cheaper than linearizable, because only the reads that follow that user's own write pay for it.

SQL isolation levels are a different axis entirely — they govern one database's view of concurrent transactions, not what a client sees across a replica. That material, along with two-phase commit, belongs to Database — Transactions, Isolation & Concurrency. What is yours here is the inter-service consistency above: sagas, the outbox, and idempotency.

02

Idempotency, and the shape of a duplicate

The duplicate is not a bug in the client. It is the correct behaviour of a client that cannot tell a delivered response from a lost one. At-least-once delivery plus an idempotent handler is the only thing that exists, and the entire design question is where the dedup record lives relative to the work it protects.

@Transactional
public PaymentResponse charge(PaymentRequest req, String key) {
    var prior = idempotencyRepo.findByKey(key);
    if (prior.isPresent()) {
        if (prior.get().isInFlight()) {
            throw new RequestStillProcessing(key);
        }
        return prior.get().replayAsResponse();
    }
    try {
        idempotencyRepo.insert(IdempotencyRecord.inFlight(key, req));
    } catch (DuplicateKeyException raced) {
        return idempotencyRepo.findByKey(key).orElseThrow().replayAsResponse();
    }

    Payment payment = gateway.charge(req);
    PaymentResponse response = PaymentResponse.from(payment);
    idempotencyRepo.complete(key, response);
    return response;
}

The result is recorded in the same transaction as the work, so a crash between the two cannot leave a completed charge with no record. The insert is the lock: two concurrent retries race on the unique constraint and one of them loses cleanly.

The seven decisions that decide whether an idempotency key works
Decision The rule When it bites
Who generates it The client, before the first attempt A server-minted key is minted after the response was lost, and dedups nothing
Its scope One logical operation — not one user, not one endpoint A per-user counter key lets a second, genuinely different request through as if it were new
What it stores The response, replayed verbatim: same status, same body Storing “seen” and answering 409 turns a correct retry into a client error, and clients handle 409 by giving up
Where it lives The same transaction as the business write Two transactions means a crash between them is a duplicate with a key that says it succeeded
Concurrency A unique constraint, not a lookup Check-then-act is a race between two consumer threads, and the loser commits anyway
Retention Longer than the longest client retry window, then expiring in batches 200 requests/second with a 7-day TTL holds around 120 million rows — a real table with a real retention job
Effect that matters A guarded state transition, for money and for stock A key can be lost, reused, or expired. A guarded transition cannot be defeated by any of those 
public synchronized boolean reserve(int units) {
    if (status != OrderStatus.PENDING) {
        return false;   // already reserved, shipped or cancelled: a no-op
    }
    this.reservedUnits = units;
    this.status = OrderStatus.RESERVED;
    return true;
}

public synchronized boolean release() {
    if (status != OrderStatus.RESERVED) {
        return false;   // compensating something that was never reserved
    }
    this.reservedUnits = 0;
    this.status = OrderStatus.PENDING;
    return true;
}

The most robust dedup in the set, and the one to reach for on a effect you cannot reverse. The second call to reserve changes nothing and raises nothing: no key, no TTL, no race, and no dependency on the client having behaved. Its cost is that it has to be written into every state-changing method, which is exactly why it is skipped and then regretted.

Must remember

When asked how do you stop duplicates, give the boundary and then say the thing that distinguishes a design from a hope. Key-based suits operations the client knows about — a payment, a POST, an order. Transition-based suits everything a downstream system will replay at you. Then: reconciliation. A periodic job that finds states which should have advanced and did not is a control. A dashboard showing that same job ran is not.

03

REST, gRPC, and the contract between them

Most inter-service failures are not protocol failures. They are a client that made a call it should not have, a provider that returned 200 and an error body, or a field removed by a service that had no way to know who was reading it. The HTTP semantics are the load-bearing part.

Method semantics, and the misuse that produces the incident
Method Correct use The common misuse
GET A read with no side effect — safe to retry, to prefetch, to crawl A GET that debits a card. It is then a POST that browsers, proxies and crawlers will fire twice for you
PUT Full replacement of a known resource; idempotent by definition Treating it as a partial update, so two callers holding stale copies each write a whole object and the second silently reverts the first
PATCH A partial update, applied by the server to the current state Sending a full object to PATCH, so a field the client never read is nulled out
POST Create, or any action that is not naturally idempotent Retrying it on a timeout without a key — the duplicate charge, in a different costume
Interview trap

200 OK with {"error": "..."} in the body. It is the most common inter-service contract bug, because the client checks the status and is satisfied. Two consequences, and the second is the one that costs an outage: callers stop reading error bodies, so your errors are invisible in telemetry; and anything that rewrites the status rewrites the body — an HTML 502 page injected by a proxy or an ingress turns a retryable 503 into a parse error on the client, and the client stops retrying something it should have retried. A 503 with Retry-After is retried; a 502 full of HTML is not.

The error body itself needs a stable, machine-readable code that is part of the contract, distinct from the human-readable message. A client that branches on prose breaks the day someone rewords it, and the failure looks like a customer-facing error rather than a deployment.

Versioning

Versioning is a promise about how long the old shape survives, and the promise is the part that gets left out. The failure mode is always the same: a field removed because no consumer in the repository reads it, by a consumer in a deployment that has not been redeployed in three years.

The compatibility promise you write down, and how it is enforced
Promise The rule When you break it
Additive New fields and new endpoints only. Nothing removed, nothing retyped A producer drops a field because no current consumer reads it — and one does, in a service that has been running since before the field was deprecated
Coexistence v1 and v2 run side by side until v1's traffic is zero Traffic switches in one step, so a v1 client and a v2 server meet for the length of one deploy
Indefinite Old versions are never removed Nothing, except the operational cost of a schema nobody is ever allowed to clean up
The gate Provider: a Buf or OpenAPI diff in CI. Consumer: Pact, run against the provider's build Neither direction is checked, and the break is discovered as a 500 in production by the team that owns neither contract

Additive changes still leak. A new required field is a breaking change wearing a hat: every existing caller omits it, and the provider now has to guess a default. The rule that holds: expand, then contract — add the field as optional, migrate every reader to send it, and only then make it required and stop emitting the old one. The deprecation date gets written into the contract, because an unnamed date is never kept.

gRPC

Trade-off

gRPC buys roughly 3–10× smaller payloads for structured business messages (close to parity for opaque blobs), about 0.3–1ms of framework overhead against 1–3ms for a Spring MVC JSON call, and real streaming. The condition that flips it: do you own both ends? If both sides are yours, on the same release train and the same language, there is no reason to pay the JSON tax. If a browser, a mobile client, or a team you share no language with is the other end, gRPC trades a problem you can solve (a gateway) for one you cannot (a client SDK per platform). HTTP/2 also brings head-of-line blocking at the TCP layer that will not appear in your load tests and will appear in production.

Interview trap

Protobuf's third trap is the one that survives a schema review, because nothing in the .proto file looks wrong: repeated fields have no presence. You cannot tell an empty list from an unset one, which is why proto3 wrappers or optional exist — and why a consumer that cannot distinguish them will clear a field the producer meant to leave alone. Pair it with the enum row in the schema-evolution table below and the shape of the risk is clear: protobuf's defaults turn most contract violations into silence rather than errors, and silence is what a schema test has to be looking for.

Must remember

A timeout budget is a chain, and it only works if it is shorter than every link above it. The client's timeout must exceed the gateway's, which must exceed the downstream's, and each service must pass the remaining budget inward rather than configuring its own number — which is why deadlines propagate as data (a gRPC deadline, a request header), not as a per-service constant. A downstream timeout that is not shorter than its caller's is not a timeout: it fires after the caller has already given up, and the caller's retry arrives while the first attempt is still running. That is the duplicate again, and it is the same duplicate the idempotency key is for.

04

Events, brokers, and what at-least-once really costs

Asynchronous communication moves the failure from the request path to the storage layer, where it is easier to see and much easier to ignore. It buys throughput, decoupling, and availability during a downstream outage. It also means every delivery is speculative, and the consumer is where the contract is actually kept.

Interview trap

“We made it asynchronous to keep the user-facing path fast.” That is avoidance dressed as a decision, and it usually names a synchronous call that was slow because it fetched five things. Events are for work that does not need to be in the user's answer. Once the user is waiting on the result, an event has added a poll, a correlation id, and a timeout, and removed your ability to return an error message.

Scaling reality check

The visibility or ack timeout is a lease, and it is arithmetic. It must exceed the p99 of a normal successful processing, by a generous margin, because expiring early does not drop the work — it hands the same message to a second consumer while the first is still working on it. p99 of 800ms gives a 30s timeout. p99 of 12s gives 60s. p99 of 12s with a 5s timeout is not a tuning choice, it is guaranteed duplicates on every normal batch, and the symptom is an intermittent double-processing that only appears under load, which is the hardest kind of bug to reproduce. The other number worth holding: at 500 events/second, each record gets 600ms of the consumer's budget, so a handler that routinely takes 700ms is manufacturing lag rather than serving it.

Event shape

What the event says, and the failure each shape invites
The event says Reads as Failure mode
“Order 123 was placed” (a fact) Something happened. You may react, and you own what you do about it A consumer that quietly assumes it is the only fact source becomes a second orchestrator, with no record of who was supposed to act
“Place order 123” (a command) One handler owns it, addressed explicitly Broadcast to a topic and read by several handlers: each acts, none of them was supposed to, and the log shows four recipients for one intent
“Order 123 was placed, and the customer is VIP” (a fat fact) Two facts in one payload The second field changes for a reason unrelated to the first, so every consumer is redeployed — and the guarantee the first field was carrying is renegotiated as a side effect
Interview trap

An event that is really an RPC wearing a hat: a noun in the past tense that requires exactly one handler to call exactly one service and then report success. You have kept the coupling, the failure modes and the retries, and given up the ability to see a stuck message as a stuck request. The test is whether you could add a second consumer tomorrow and have it be safe — if not, it was a command and should have been one.

Schema evolution

With a schema registry, the compatibility mode is a declaration, and the direction is the trap. BACKWARD means new readers can read old data — which is the direction you actually want, because consumers are upgraded independently and lag behind producers. FORWARD means old readers can read new data, which matters only if producers are the ones that lag. FULL is both, and is the only one that allows removing a field — at the cost of ordering every deployment so that producers and consumers move together, which across teams means a deployment window you do not have.

The change, and whether the old data survives it
Change Safe under BACKWARD? Note
Add an optional field Yes Old consumers ignore what they do not recognise; that is the whole design
Add a required field No Old consumers omit it, so the provider must invent a default — expand, then contract
Widen a type — int32 to int64 No Silent truncation in an old reader, which is worse than a parse error
Rename a field Yes, if the number is kept Field numbers are the contract; the name is sugar
Remove a field No It is dropped from the wire format, and every consumer that has not been redeployed since will fail or mis-decode
Add a value to an enum Yes An old reader gets an unrecognised integer. Give it an explicit UNKNOWN branch, or you have traded a break for a silent else

Broker selection, consumer group management, and the operational side of running a platform belong to Volume 3 — Operations, Platforms & Evolution; the Spring Cloud Stream bindings to Spring — Distributed Systems. The one fact worth keeping here regardless of library: the partition count is a lifetime cap on consumer parallelism. Three partitions with thirty consumers is twenty-seven idle consumers, and adding partitions later changes the key assignment — so a key's ordering is only stable for as long as the partition count is.

05

Sagas: forward actions, not rollback

A saga replaces a distributed transaction with local ones, and the compensation is forward business logic — refund, release, cancel — not a rollback. That word is doing a lot of work in most designs, because a compensation is itself a distributed call that can time out, be retried, and arrive twice. Two-phase commit is discussed, with its failure modes, in Database — Transactions, Isolation & Concurrency; the short answer is that it is a coordinator every participant must be able to reach, holding locks for the duration of the slowest one.

Choreography against orchestration, and the condition that flips it
  Choreography Orchestration
Who decides the next step Each participant, on receiving an event The orchestrator, which calls each participant
Where the sequence lives Implicit, spread across five handlers One row per saga, queryable
Coupling A participant's new event type can break a consumer it never called None. Participants are called, not observed
Diagnosing a stuck order “Reserved in inventory, nothing further happened” — assembled by hand, from five services One query, and the last error is on the row
The failure mode A seventh participant arrives and nobody can say what the flow does now The orchestrator is unavailable, so the saga stops — and it is a single point you can reason about, rather than a property of the whole system
Trade-off

Choreography buys independence of deployment and no central component to operate. Orchestration buys legibility in exchange for one more thing that can be down, and legibility is what pays during an incident at 3am. The condition that flips it: about four participants, or one participant that is both producer and consumer of two flows. Below that, the handlers are readable and the extra component is pure cost. Above it, the sequence genuinely is not in any one place, and a flow that touches payment at 3am is where you discover that.

void execute(SagaContext ctx) {
    // Persist the intent BEFORE the call, so recovery can tell
    // "not started" from "started, outcome unknown".
    ctx.recordStepStarted(name, maxAttempts);
    try {
        ctx.withDeadline(timeout, () -> participant.call(name, ctx.payload()));
        ctx.recordStepSucceeded(name);
    } catch (StepFailed e) {
        ctx.recordStepFailed(name, e);   // its own budget, not the caller's
        throw new CompensationRequired(ctx.sagaId(), name, e);
    }
}

Line 4 is the load-bearing one. If the process dies between the call and the record, recovery sees a step that was never started and runs it again — which is a duplicate. Persisting the intent first means the only ambiguous state is “started, outcome unknown”, and that one has an answer: ask the participant, or make the step a guarded transition so asking is unnecessary.

How a saga itself fails

Every design discussion goes straight to participant failure and misses the four ways the saga mechanism itself gives up. These are the ones that page you at 3am.

The four ways a saga fails as a saga, not as a participant
Symptom The saga's own failure The control
Stuck forever in a non-terminal state The process died between calling a participant and recording the result A sweep: list in-flight sagas by state and by age. Anything past its deadline is a compensation candidate, and the count is an alert, not a metric
Compensation never converges Forward retries and compensating retries share one budget, and the forward retries have already spent it A separate, smaller budget for compensation, plus its own idempotency — and exhausting it raises an alert rather than a log line
Two copies of the effect The participant's timeout fired, but the effect applied anyway The participant's guarded state transition. The saga cannot dedup its own duplicate
The saga row and the event log disagree The state machine advanced before the event was published, or after it was published and before the row was written One transaction for both — which is the outbox, below
Interview trap

Four different clocks, all shorter than the saga: the coordinator's step timeout, the client's, the gateway's, and the saga's own business deadline. The client gives up at 30s, the saga takes four minutes, each step is allowed 10s. What the client sees is a timeout; what it does is retry; and now two sagas exist for one order — the duplicate from chapter 2, wearing a different costume. The rule is that the saga's deadline must be shorter than every caller's, that the budget propagates inward as data, and that a cancelled or expired saga stays reachable by the caller so the retry finds the existing saga through the idempotency key instead of starting a second one. “The saga finished after the client gave up” is a normal outcome that needs a status endpoint, not a failure.

Must remember

When the question is “how do you make two services consistent”, the strong answer is that no protocol makes two services consistent; you state an application-level invariant and then enforce it — with a saga for the ordered case, and a reconciler for everything else. A saga can guarantee that an eventually-compensated sequence was executed, not that no observer ever saw a half-finished state. Everything else is a better story about the database than about the design.

06

The transactional outbox, the inbox, and CDC

The dual write is the original sin: a database insert and a message publish, from application code, with no transaction spanning them. It is not a rare race. It is four outcomes, three of which are wrong, and which one you get is decided by network timing.

@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    Order order = orders.save(Order.from(cmd));

    // Same transaction, same database. This is the only thing the
    // pattern makes atomic, and the database already knows how.
    outbox.save(OutboxRecord.builder()
            .aggregateId(order.id())            // also the partition key
            .eventType("OrderPlaced")
            .payload(write(OrderPlaced.from(order)))
            .build());                          // published_at stays NULL

    return order;
}

Line 8 is the one that gets forgotten, and it is why the whole design works: the aggregate id is not just an identifier on the event, it is the partition key. An outbox whose key is null has given away the ordering it worked to preserve.

@Scheduled(fixedDelay = 500)
void relay() {
    // FOR UPDATE SKIP LOCKED: two relays never read the same row.
    var batch = outboxRepo.claimBatch(100, Sort.by("createdAt"));

    for (OutboxRecord r : batch) {
        broker.publish(r.topic(), r.aggregateId(), r.payload());
        // A crash here leaves the row unpublished, so the event is
        // published twice. That is the price, paid by the consumer.
        outboxRepo.markPublished(r.id(), Instant.now());
    }
}

The order of lines 7 and 10 is the entire semantics. Swap them and the relay becomes at-most-once: a crash between the two loses the event silently, and a lost event does not page anybody, because the thing that was supposed to notice it is waiting for a message that will never arrive.

CREATE TABLE outbox (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_id TEXT        NOT NULL,
    event_type   TEXT        NOT NULL,
    payload      JSONB       NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);

-- Partial: published rows are excluded entirely, so the index stays
-- small no matter how big the table gets. Without it the relay query
-- is a sequential scan of a hundred million rows, every poll, on the
-- primary, competing with production traffic.
CREATE INDEX idx_outbox_unpublished
    ON outbox (created_at)
    WHERE published_at IS NULL;

-- Purge by published_at, in bounded batches. Never by age: a backlog
-- built during an outage is young, and cutting it by age is a dual
-- write you have reimplemented by accident.
Scaling reality check

The outbox is a write-amplifying table and it is measured in gigabytes. A service writing 500 events/second at roughly 1KB each produces 43GB of outbox rows per day, before indexes, before replication, and before the purge keeps up. So: purge in small batches continuously rather than once at night, right-size the rows (a full-object event is often 1KB where a changed-fields event is a few hundred bytes), and monitor the age of the oldest unpublished row, not the count of unpublished rows — a steady count of ten thousand in a steady state is healthy, and a count of ten in an outage that lasted a minute is a delivery system that has stopped. A backlog that is deep but young is a different incident from a backlog that is small and four hours old, and only the age tells them apart.

The inbox, and CDC

The consumer side needs the same transaction, for the same reason, with the same shape: the dedup record and the business effect commit together. Not a lookup, not a check — the insert is the check, and the unique constraint is what makes two concurrent deliveries of the same message lose cleanly.

CREATE TABLE inbox (
    message_id   VARCHAR(128) NOT NULL,
    consumer     VARCHAR(64)  NOT NULL,
    received_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer, message_id)
);

BEGIN;
  INSERT INTO inbox (consumer, message_id) VALUES ('billing', $1);
  -- DuplicateKeyException here means "already applied". Nothing to do.
  apply_business_effect($1);
COMMIT;

Scope the key by consumer, not just by message: the same message delivered to two different consumers is two deliveries, and collapsing them would break one of them.

Poller against log tailer, and what each one quietly depends on
  Poller Log tailer (CDC)
Latency added The poll interval, plus the batch Near zero — it is already in the write-ahead log
What it can miss Nothing, if the index is right: the rows sit there until read A dropped replication slot replays from the last offset it confirmed
What breaks quietly A missing partial index turns each poll into a sequential scan on the primary It carries the physical row. A DROP COLUMN produces an event the consumer cannot deserialise, and a migration that was safe in the database is not safe on the wire
Schema changes Invisible — the table is yours and you can expand it Ride along into the event, whether you wanted them or not

Both rows are the same principle, and it is the one worth defending if you are asked why not just use CDC everywhere: the relay mechanism changes the latency, and it does not change the delivery guarantee. Whatever moves the bytes, the consumer's transaction has to be the thing that makes a redelivery a no-op.

07

Data ownership and the cross-service query

A database-per-service is an ownership claim, and the moment another service reads those tables the claim is void: it has become a public API with no versioning, no compatibility promise, and a migration that two teams have to coordinate. The diagnostic that settles the argument is a question about people, not about architecture: name the team that runs a migration on this table. If the answer is “all of them, and we have a calendar meeting about it”, the boundary is a diagram.

Must remember

For every cross-domain read, exactly one system owns the truth, and every other copy is a projection with a lag number attached. Not “one system is authoritative, but the others also keep a copy for performance” — because the second clause is where the migration that makes them disagree arrives. Partitioning, shard keys and scatter-gather are a different question, owned by Database — Schema Design, Partitioning & Scaling.

What a per-service database costs, and where the invariant goes instead
What you lose Where the invariant goes The failure mode
A join across two domains A service call, or a projection you rebuild from events The projection is stale for a window nobody sized, and the dashboard that would show it is the one nobody reads
Referential integrity Into the consumer's validation, and the producer's delete path A deleted user leaves live orders behind, because a delete is now a soft-delete plus a rule that nobody is checking
The transaction Into an application-level invariant: a saga, or an event plus a projector Both writes “succeed” and the invariant is violated with no error anywhere — which is why reconciliation is not optional

There are three answers to a cross-service query, and the mistake is not picking the wrong one — it is picking none and doing the join over HTTP in a loop. The tell is requests per inbound request: one page rendering 1,800 calls, none of which error, none of which is individually slow. Parallelising it is the tempting wrong answer — it takes the p50 to 20ms and multiplies the load on every downstream service by 1,800. A page that needs six services' data is a page that wants a projection.

Three answers to a query that crosses a service boundary
Answer How it works Reach for it when Its cost
API composition The caller makes one call per service and joins in memory Roughly four calls, none of them on a hot path A p99 that is the max of four p99s, and one slow service inside the user-facing path
A projection (CQRS) One service subscribes to the others' events and serves a denormalised read store The query is on a hot path, or no single service can answer it in its own shape A second copy of the truth with a lag number attached — and exactly one system that owns it
Denormalised duplication Each service keeps the field it needs, updated by events The field is small, stable, and read on nearly every request Two writable copies, and the second one is a bug waiting for a migration nobody planned
Interview trap

Denormalised duplication with two writers. One service owns the field; a second one also accepts updates to it, because a request had to be served without a call. Now the last-write-wins conflict is not a rare event, it is a race that resolves differently on each replica, and the loser is whichever one the read happened to hit. The rule is not “avoid denormalisation” — it is that a projection has exactly one writer, and if a second service needs to change the value it asks the owner.

08

Caching across a service boundary

Eviction, stampedes, and the mechanics of Redis belong to Database — Redis & Caching. What is specific to a distributed system is that the cache has no owner: the value it holds was written by a service that may not know the cache exists, and a miss is no longer necessarily a call to the owner.

Invalidation strategies, and what each one is really buying
Strategy Rule Cost, or the failure you get instead
TTL A bounded age — and the honest default It buys correctness without an invalidation path, at the price of a hit rate. A short TTL is a guess that trades staleness for throughput, so pick it from the read
Write-through by the owner The owning service pushes the new value on write The owner must know every cache in the system. One it does not know about is a permanent stale read, and nothing ages it out because the TTL is long
Event-driven invalidation The owner emits an event; subscribers drop the key A subscriber is down, or a message is lost, and the key survives. The TTL is still load-bearing — this is an accelerator, not a guarantee
Key versioning The row version is part of the key, so a write orphans the old entry Nothing expires by accident, and no one has to enumerate the caches. The key space grows, so old versions need a sweep
Interview trap

Two cache correctness problems that no amount of tuning fixes, because both are design failures wearing an operational costume. The first is the unowned cache: name who deletes this key when the row changes. If nobody can, the TTL is the only invalidation you have, and the TTL is a guess. The second is a stale read presented as a fresh one — a cached response with no version, so the reader cannot tell that what it is looking at predates its own write, and it propagates further than the database it came from.

Must remember

Negative caching is the one that gets skipped, and it is a correctness decision. Caching a miss is what stops a hot key that does not exist yet from being re-fetched on every request — but a miss cached for the same TTL as a hit will keep serving “no such customer” after the customer is created. Cache negatives briefly, and never on a read the user is about to act on. And across a boundary, the cache key has to carry the tenant: a key without it is not a performance bug, it is a data breach, and it will not show up in any test that only ever authenticates as one tenant.

Every one of these is a figure you cannot derive under pressure, which is the only reason it is on the page. The two that carry the most weight in an interview are the visibility timeout arithmetic and the outbox growth rate, because both turn “it scales” into a specific number — and the two that most often decide whether an answer is believed are 120 million rows and two mechanisms, because they are the two places where a candidate who has actually operated the system does not hesitate.
