5.4 JPMS — Readability, Accessibility & Encapsulation

Section 5.3 says what the module system is for. This section is the mechanism, and it is two ideas that are easy to run together: readability (may I name this type at all?) and accessibility (may I use it from here?). A module can read a type it cannot access, and that gap is where almost every JPMS surprise lives.

  module com.acme.billing {
      requires java.base;                    // readability: I may name java.base's public types
      requires transitive com.acme.api;      // my readers ALSO get to read com.acme.api

      exports com.acme.billing;              // accessibility: everyone who reads me may use this pkg
      exports com.acme.billing.spi to com.acme.web;    // ...but only these modules

      opens com.acme.billing.model;          // reflection too — needed by Jackson, JPA, tests

      uses com.acme.billing.PaymentGateway;  // I will look one up at runtime
      provides com.acme.billing.PaymentGateway
              with com.acme.billing.StripeGateway;      // ...and this is the implementation
  }

  readability   = the `requires` graph      -> do I know the name at compile time?
  accessibility = exports (compile+runtime)  -> may I use it?
                  opens    (reflection only) -> may I reflect over it?
                  private  (this module only) -> nothing else

  a module can READ a type it cannot ACCESS:
  reads com.acme.api but does not export com.acme.billing  ->  compiles, then fails at runtime

The distinction that earns its keep is exports versus opens. exports grants normal compile-time and runtime access to the package's public types. opens grants reflection — setAccessible, getDeclaredMethod, private-field reads. Ordinary code needs exports; frameworks that reflect over your types need opens. That is why a Spring or Jackson application fails at runtime with IllegalAccessException on a private field of an exported package: the package was exported, never opened.

Interview trap

requires transitive does not re-export packages. The JLS is explicit about this in §7.7.1: a package in module m.D is not re-exported by m.C or by m.B. What requires transitive does is make the dependency readable to your own readers — it propagates the edge in the graph, not an exports. If your consumers need m.D’s types directly, m.D itself must exports them. This is the most commonly tested JPMS misconception.

Where module-info.java goes, and what breaks without it

module-info.java must not sit inside a package directory. The usual Maven and Gradle layout puts it beside the package roots:

  my.library/
    src/main/java/
      module-info.java            <- here: sibling of the package directories
      com/acme/billing/           <- a package directory
        Invoice.java

  NOT src/main/java/com/acme/billing/module-info.java

  why: module-info.java is not a member of any package. A source file's
  package must match its directory, and this file's package is the
  unnamed package, which by rule has no directory.

A JAR without module-info.class still works — it becomes an automatic module, named from the JAR filename (commons-lang3-3.14.jar becomes module commons.lang3). Automatic modules read every other module and export every one of their packages, so they are a compatibility bridge, not an encapsulation win. That is why a modular application does not actually gain encapsulation from its third-party dependencies until they ship real module descriptors.

Everything left on the classpath — no --module-path — collapses into a single unnamed module. The unnamed module reads every named module and exports all of its own packages, so it can see inside java.base. Named modules can see the unnamed module but not vice versa in terms of encapsulation. This is the whole reason JDK 9 shipped with dozens of --illegal-access=permit warnings: the JDK’s own internal packages were being opened to code on the classpath. JEP 403 made that default deny in JDK 16 and removed the escape hatch entirely in JDK 17 — on the JDK 25 baseline there is no --illegal-access flag at all.

Must remember

The four --add-* flags differ in what they open, and using the wrong one produces a warning that does not fix the problem:

  • --add-modules — add a module to the root set so it is resolved at all
  • --add-reads — grant readability (the requires graph)
  • --add-exports — grant accessibility for normal use
  • --add-opens — grant deep reflection into a package

--patch-module is the odd one out: it is module augmentation, for adding classes and overriding classes inside an existing named module. It is documented for that purpose and is not a supported remedy for a split package.

Services without a classpath scan

Java 9 gave ServiceLoader a compile-time contract. The consumer declares what it consumes, the provider declares what it supplies, and the module graph connects them at launch time — no reflection, no scanning, and no dependency on an implementation library that the consumer never names.

// consumer module
module com.acme.web { requires com.acme.billing; }

// consumer code — the interface need not be in the module being loaded
PaymentGateway gw = ServiceLoader.load(PaymentGateway.class)
                                    .findFirst().orElseThrow();

// provider module
module com.acme.billing.stripe {
    provides com.acme.billing.PaymentGateway
    with com.acme.billing.StripeGateway;
}

Note what this does not do: it does not help with classpath split packages, which is a module-path resolution error with no flag-based workaround. The same package existing in two modules is a hard failure by design — it is what makes the module graph a reliable model of who can see what.

In production

The practical value of JPMS is verifiable API boundaries. On the classpath, “this class is not public / not exported” is a convention anyone can bypass by declaring the same package name. Under JPMS it is enforced by the module graph, so a library can change its internals without a binary-compatibility risk. The two places it earns its cost back are jlink — you can cut a runtime image containing only the modules you actually resolved, which is the difference between a 250 MB JRE image and a 40 MB one — and the service registry, which turns plug-in discovery from reflection into a launch-time contract.
