Volume 2 — SQL: DDL, DML & Constraints

Every CREATE TABLE is a rule the engine checks on every write, forever, and almost none of it is free. What each type costs in bytes, which ALTER TABLE rewrites the heap, and where a constraint's cost actually lands.

  • 8 sections
← Prev Next →

If you only remember five things

  1. A column type is a constraint you cannot remove cheaply. Widening NUMERIC(12,2) is a heap rewrite under ACCESS EXCLUSIVE, so the type you pick in a design review in March is the one that costs a maintenance window in November.
  2. Rename nothing in a live deploy. RENAME COLUMN is instant in the database and total in the application — the 29-second gap between migration and pods is the outage. Expand, backfill, dual-write, switch reads, contract later.
  3. A foreign key is a lock on another table's row. Its index cost is on the child, its contention cost is on the parent, and the diagnosis of "inserts got slow" therefore points at the table you are not looking at.
  4. NULL is not a value, so it silently defeats half of SQL. WHERE admits only TRUE, so x = 5 and x <> 5 are not complements, and CHECK passes on UNKNOWN.
  5. The performance advice here is scale-dependent; the integrity advice is not. DEFAULT 0 on a column whose absence is meaningful and UNIQUE on a nullable column are wrong on a table of four rows exactly as much as on four hundred million.

No section matches that filter.

01

DDL: locks, rewrites & schema evolution

DDL is the part of SQL that takes locks the application cannot route around, rewrites terabytes, and cannot be rolled back once half done. The only skill worth having is telling declarative DDL (changes the catalogue and the meaning of future statements) from physical DDL (moves bytes) — and asking the engine which one you are about to run rather than guessing.

The ALTER TABLE cost table — the one to memorise

Why the scan and the lock are separate costs: ACCESS EXCLUSIVE freezes the table — no SELECT, no INSERT, only a queue of waiters. A 400-million-row scan held under that lock for nine minutes is a nine-minute application outage, and the symptom is not a database error but the app's own request timeout firing.

Scaling reality check

Above roughly 10 million rows, nothing that scans may hold a lock that blocks reads. The two techniques that exist are NOT VALID plus VALIDATE CONSTRAINT, which splits one exclusive scan into a brief exclusive moment and a concurrent scan, and CREATE INDEX CONCURRENTLY, which accepts a brief window in which the index is invalid. Neither is free. Both are a hundred times better than a nine-minute ACCESS EXCLUSIVE.

Below about 100,000 rows none of this matters and you should stop reading about it. The crossover is not a rule of thumb to quote in an interview — it depends on row width, on scan duration on your hardware, and above all on how long your application can hold a connection before its own timeout fires. Go and measure it.

-- 1. EXPAND. Nullable, no default. Instant, no rewrite.
ALTER TABLE orders ADD COLUMN customer_id bigint;

-- 2. BACKFILL. Batches, outside a single long transaction.
UPDATE orders SET customer_id = user_id
 WHERE id BETWEEN :lo AND :hi AND customer_id IS NULL;

-- 3. DUAL WRITE. Old code writes user_id; new code writes both.
--    This is the phase that takes engineering hours, not SQL minutes.
-- 4. MIGRATE READS. Flip one caller at a time. Both columns exist.
-- 5. CONTRACT. Only once nothing reads or writes user_id.
ALTER TABLE orders DROP COLUMN user_id;
Trade-off — should we ever rename in one step?

Yes, in exactly one situation: a table with no application reading it — about to be dropped, a scratch or staging table, or one small enough that the migration and the deploy share a maintenance window with the application stopped.

No in every other situation, because the deploy and the migration are separate events with an unpredictable gap, and a RENAME is atomic on one side and catastrophic on the other. The sequence costs two columns and two deploys; the rename costs zero columns and, if the gap is thirty seconds, an incident channel.

Flips on: can you prove there is no reader other than the code you are about to change? pg_stat_statements and the slow-query log are how you prove it, not confidence.

Evolving a column a running application touches
SituationRuleWhen it bites
Widen a columnAdd the new column, backfill, switch, drop ALTER COLUMN TYPE rewrites the heap; a 500-GB rewrite is not a migration, it is an outage with extra steps
Add NOT NULLAdd nullable → backfill → SET NOT NULL SET NOT NULL does not rewrite but does scan; the scan is the cost
Add CHECK or FKInstall NOT VALID, remediate, VALIDATE One ADD CONSTRAINT is three operations wearing one costume
Copy a tableCREATE TABLE new (LIKE old INCLUDING ALL) AS SELECT * copies no indexes, constraints, defaults, grants or ownership, and infers types from the expression
Drop somethingDependency query first, not a transaction PG has transactional DDL so BEGIN; DROP; ROLLBACK is a real dry run; MySQL implicitly commits, so it is not
Interview trap — IF NOT EXISTS in migrations

The common answer is "it makes migrations idempotent". It makes them idempotent by suppressing the evidence: it converts a loud, correct failure into a silent no-op, so a migration that believed it changed a table which already existed in a different shape reports green. Idempotency is a property you want; not being able to tell "already correct" from "already wrong" is not.

The real instrument is a migration tool with a version table and a per-migration checksum (Flyway, Liquibase, Alembic, Django), because that can distinguish "step 7 already ran" from "step 7 did nothing" — which the clause structurally cannot. Reserve IF EXISTS for disposable paths: a smoke-test scratch table, an index a concurrent migrator may already have built.

Must remember — you never have to guess

PostgreSQL documents lock levels and rewrite behaviour per ALTER TABLE subform; MySQL exposes it as ALGORITHM=INPLACE | COPY | INSTANT and LOCK=NONE | SHARED | EXCLUSIVE. Write the statement with the algorithm clause against a test clone and read what the engine accepts. Also set a short lock_timeout on the DDL itself, so a migration that cannot get its lock fails fast and retries on the next deploy rather than freezing the table behind a queue that grows for nine minutes.

02

Types, precision & collation

A column type is not a storage optimisation. It is a rule about the data, enforced by the engine on every write, forever, and one of the cheapest protections in the system — which is exactly why it is also one of the hardest things to walk back.

What each type costs, and what it cannot hold
TypeStorage costWhat it cannot hold
integer4 bytes fixed-width Anything above 2,147,483,647. Arithmetic past the boundary is an error on PG, a silent wrap or clamp on MySQL
bigint8 bytes; +4 bytes per value over int Beyond 263. On an 8 kB page of 200-byte rows the extra 4 bytes is roughly a 2% page-count difference
bigint cents (money)8 bytes, fixed Nothing — there is no fraction to round, so the "we lost a penny" bug class is unrepresentable
float / double precision32-bit / 64-bit, sign + exponent + binary significand 0.1. Stored as 0.1000000000000000055…, error about 5.5e-18, and it does not cancel
numeric(p,s) Integer significand + scale, stored inline up to roughly 1,000 bytes of digits, then out-of-line; a variable-length encoding that compares and indexes more expensively than bigint Nothing within its precision — and it rounds rather than erroring. numeric(38,10) is 38 digits, not a free choice
char(n)Exactly n characters, right-padded with spaces A width the domain does not actually fix — and the padding makes UNIQUE/PK behaviour path-dependent
varchar(n) / text in PGIdentical: 4-byte length header + bytes. The n is a catalogue modifier, not enforced on the tuple Nothing extra — the limit is a constraint, and it also feeds the planner's row-width estimate
varchar(n) / text in InnoDB varchar inline behind a 1- or 2-byte length prefix; text goes off-page past a row-size threshold (65,535 bytes for a row) Nothing, but reading a 12-character text value can mean an overflow-page read
timestamptzA UTC instant; rendered in the session zone on read What the local time was where it happened — that needs a separate text column with the IANA zone name
timestampA wall-clock reading with no reference point The information is destroyed on write — you cannot recover which reading was UTC
jsonbParsed and re-serialised on every INSERT and UPDATE Nothing structurally — it has no NOT NULL, no CHECK, no FK, and no statistics for the planner
 
-- What you want
CREATE TABLE ledger_entry (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    amount      numeric(18,4) NOT NULL,   -- 14 integer digits, 4 decimals
    currency    char(3)       NOT NULL,
    posted_at   timestamptz   NOT NULL
);

-- What quietly costs you a penny
CREATE TABLE ledger_entry (amount float NOT NULL);            -- never
CREATE TABLE ledger_entry (amount numeric(38,10) NOT NULL);  -- 38 digits, not free

Why a float cannot represent 0.1: it stores a binary fraction — sign, exponent, and a significand of binary digits — and 0.1 has no terminating binary expansion, exactly as 1/3 has none in decimal. The hardware rounds to the nearest representable value, so the error is representational, it does not cancel across operations, and 0.1 + 0.2 is 0.30000000000000004. Ten thousand additions of $0.10 accumulate a discrepancy of about 1.6e-4 that never goes away.

Interview trap — the int boundary is loud on INSERT and silent on arithmetic

The interesting failures are not on INSERT, which errors immediately and which you will find. They are on arithmetic: PostgreSQL raises integer out of range, MySQL's default sql_mode has historically wrapped or clamped, so UPDATE t SET counter = counter + 1 past the boundary silently produces a negative number. And SUM() over an int column is silently wrong on MySQL where PostgreSQL widens to bigint.

count(*) returns bigint and is safe; SUM(amount) is not. That makes the bug engine-specific, so a schema that is safe on PostgreSQL and unsafe on MySQL is a schema that has been tested on the wrong database. The legitimate ints are a lookup table rebuilt weekly and an engine-managed system column — the test is whether you can state the lifetime bound as a number.

Trade-off — money as NUMERIC or as integer cents?

NUMERIC(18,4) wins when the domain genuinely has fractional units — FX rates, per-kilogram pricing, tax computed fractionally in some jurisdictions — and human review matters. It reads correctly in a SELECT and survives a spreadsheet.

Integer minor units win when the domain is one currency with two decimals: fixed 8 bytes, fastest comparison, smallest index, and no rounding path exists. The cost is convention — every human doing ad-hoc SQL has to divide by 100, and one column named amount_cents beside another named amount is a real 100× error source.

Flips on: how many people query the column outside your application. Finance, support, and a hand-written monthly report → NUMERIC and pay the storage. Only services, all through one repository method → integer minor units. Both are exact; the choice is about who else reads the column.

Choosing a character type
ConceptRuleWhen it bites
textUse it when the honest answer is "I do not know, and it should not be my problem" A varchar(255) on a column that legitimately holds 4,000 characters is a support ticket
varchar(n)Use it when the business has a real maximum; in PG it is a free constraint Converting text to varchar(500) changes the planner's row-width estimate, which can change join strategy for reasons unrelated to your change
char(n)Only when an external standard fixes the width exactly, and on both sides of any join Pads on storage, and pad-space comparison is the ANSI default — so a char(2) joined against a trimmed varchar(2) matches rows nobody expected and reports 3–4% too many
CollationDecides what =, ORDER BY, GROUP BY, UNIQUE and every index on that column mean An index declared COLLATE "en_US_ci" changes comparison semantics for every = on that column database-wide, including queries written long before anyone thought about case
Interview trap — "why did UNIQUE not catch the duplicate email?"

Because a UNIQUE constraint is a statement about the value as stored, and as stored means a byte comparison under the column's collation, which is case-sensitive by default. The team wrote "email is unique" — a claim about identity — and the database implemented "the exact case-sensitive string is unique" — a claim about bytes. Neither is false, and the gap between them is the bug.

The senior fix is to normalise on write, not to loosen the comparison: a stored generated column email_norm as lower(trim(email)) with a UNIQUE index on it, so no writer — service, import, admin tool, psql — can skip the step. A CHECK (email = lower(email)) plus a functional index on lower(email) is the same idea without the column.

Must remember — instants are timestamptz

The failure mode is not subtle: rows written by servers in two regions become mutually incomparable, so a per-hour report double-counts one hour on the spring DST transition and loses an hour on the autumn one — a 100% error on the two days nobody tests, and a support ticket that arrives in March about data written in November.

The trap inside the trap is timestamp DEFAULT now(). now() returns a timestamptz that is silently cast to the naive type on assignment, so the type system offers no warning at all. Instants are timestamptz, durations are interval, and a wall-clock local time that means something to a human is timestamp plus an explicit zone column.

03

Primary, foreign & unique constraints

Volume 1 covered what a constraint claims. This is what each claim costs at write time and implies structurally — which indexes appear on their own, which lock is taken, and which row gets blocked. A PRIMARY KEY and a UNIQUE on the same column differ in four mechanical ways, not one: the PK implies NOT NULL and a UNIQUE does not; in InnoDB the PK is the clustered index and so cannot be invisible or partial while a UNIQUE can; only a PK or UNIQUE can be the target of a foreign key; and many engines let the planner assume a PK has no duplicates at all, which is why SELECT DISTINCT gets dropped on a PK-joined query and never on a UNIQUE-joined one.

What each constraint creates for you
ConstraintIndex it impliesNotes
PRIMARY KEYUnique index on the key columns In InnoDB this is the clustered index; every other index is secondary. A wide PK is a much worse mistake there than in PostgreSQL
UNIQUEUnique index on the column list A real maintained B+ tree on the write path
FOREIGN KEYIndex on the child columns Required by the standard; most engines create it silently or refuse the constraint
FOREIGN KEYIndex on the parent key Usually already there as the parent's PK or UNIQUE
CHECKNone Evaluated row by row; not indexed, not usable by the planner for pruning unless satisfiable
NOT NULLNoneA per-row flag check
DEFAULTNoneA value used when the column is absent from the INSERT list — not a constraint
Interview trap — why does a foreign key need an index on the child?

Not to make the insert fast — to make the referential actions viable. When a parent row is deleted the engine must find every child referencing it in order to RESTRICT, CASCADE or SET NULL them. Without a child index that is a full table scan per deleted parent row — ten thousand parents deleted against a ten-million-row child is a hundred billion row examinations. With it, ten thousand index probes. The standard requires the child columns be indexed, which is why a ForeignKeyConstraintException usually means "add an index", not "fix your data".

The write-side cost is the one forgotten: this index is maintained on every insert and every update of the FK column, forever, and it is pure overhead if the relationship is never used to join — which happens when the FK is a compliance annotation rather than a real relationship.

-- (a) Column-level, anonymous. Works. You will regret the name.
CREATE TABLE orders (
    reference   varchar(32)  UNIQUE,
    customer_id bigint       REFERENCES customers (id)
);

-- (b) Table-level, named. The default for anything you look at twice.
CREATE TABLE orders (
    reference   varchar(32) NOT NULL,
    customer_id bigint      NOT NULL,
    CONSTRAINT orders_reference_key UNIQUE (reference),
    CONSTRAINT orders_customer_fk  FOREIGN KEY (customer_id)
        REFERENCES customers (id) ON DELETE RESTRICT
);
Must remember — name every constraint

Unnamed constraints are generated by a convention that differs by engine — orders_reference_key in PostgreSQL, reference in MySQL, a generated hash in SQL Server. A migration that drops and re-adds a constraint by name works on the developer's laptop and fails in production, halfway through a schema deploy with the new constraint already installed. The rule fits in a lint rule: every constraint has an explicit name following <table>_<purpose>, and the name appears in the migration file.

The ON DELETE / ON UPDATE action matrix
ActionOn parent deleteOn parent key updateUse when
RESTRICTReject immediately, before any other workRejectChildren must be explicitly re-homed first
NO ACTIONReject at end of statement, or at COMMIT if deferrable As RESTRICT You need to move rows within the same statement — the only workable choice for a multi-row re-parenting

Interview trap — why is NO ACTION the default and not CASCADE?

Because the default is a data-safety decision disguised as a syntax default, and getting it wrong is unrecoverable. The error modes are wildly asymmetric: RESTRICT when you wanted CASCADE produces a constraint-violation error — loud, immediate, one statement. CASCADE when you wanted RESTRICT produces four years of order history deleted, silently, with no audit trail, recovered only from a backup. The asymmetry is the whole argument.

Cascade is also a property of the graph, not of one constraint: one DELETE on users can cascade to orders, then to order_line, then to discount_allocations, and the person who wrote the innermost constraint had no idea the outer one existed. Any CASCADE over an unbounded child set is a schema-review flag requiring a written statement of what gets destroyed.

Trade-off — soft delete with SET NULL, or hard delete with CASCADE?

Soft delete is correct when the child rows have independent meaning and someone will need to know they used to belong to something: orders that must survive a GDPR erasure request, audit rows that must outlive the entity they describe, anything with a legal retention requirement. The cost is that the nullable FK and deleted_at must appear in every query, and forgetting once is a data-exposure incident rather than a bug.

Hard delete with CASCADE is correct only when the child is genuinely a component — order_line items have no meaning without the order. The cost, when applied by habit, is a data-destruction policy dressed as a convenience setting.

Flips on a question about the child, not about taste: would a human ever want to see this child row and not know which parent it belonged to? If yes, cascade is wrong. The safe default is RESTRICT, with CASCADE as an explicit, reviewed, per-constraint decision.

UNIQUE on a nullable column — multiple NULLs by engine
EngineMultiple NULLs under UNIQUE
PostgreSQLAllowed — NULLs are distinct (since 9.0)
MySQL / InnoDBAllowed
Oracle, SQLiteAllowed
SQL ServerNot allowed — one NULL per UNIQUE column
Interview trap — UNIQUE does not do what its name says on a nullable column

The standard rejects two rows only if no column in the key is distinctly unequal, and NULL is never distinctly unequal to anything — including another NULL. So every row whose key is NULL is distinct from every other and the constraint is satisfied. The question is never "can it happen", it is "is it what I meant?"

On an optional email, unlimited NULLs is exactly the intent — legacy accounts without an email are normal. On a column called external_ref where the name says "at most one row may have no external reference", it is a bug with a silent signature. The fix is not to loosen the constraint but to make the invariant expressible: a partial unique index on a constant expression filtered to the rows in question, or a NOT NULL column with a sentinel.

Must remember — DEFERRABLE moves the check to COMMIT

A constraint checked immediately cannot express an invariant whose intermediate states are invalid even though the final state is fine — swapping the parents of two adjacent category rows, or building a tree from the leaves up. DEFERRABLE INITIALLY DEFERRED evaluates at COMMIT, where the final state is what matters, and that is its whole reason to exist.

It is not free: a violation now surfaces at COMMIT, so the error points at a line of code that did not cause it — an expensive hour of bisecting. The default of INITIALLY IMMEDIATE is right far more often than people assume, and the right question when a constraint blocks you is whether the invariant genuinely is per-row.

Composite keys follow the leftmost-prefix rule, so column order is a decision about which queries the constraint can accelerate and which fact it enforces. UNIQUE (tenant_id, external_id) says the pair is unique; UNIQUE (external_id, tenant_id) says the external id is unique globally. Both are UNIQUE, they enforce entirely different facts, and the difference is two characters of column order. A multi-tenant integration that assumes partner ids are globally unique will pass local tests and corrupt on the second tenant.

04

CHECK, defaults & domains

A CHECK is a boolean expression over the row being written. It must not evaluate to false; true and unknown both pass. That last clause is the source of the most common CHECK bug in production, and it is a fact about the standard, not an engine quirk.

What a CHECK can and cannot express
RuleExpressible?What to use instead
Two columns of this row must be consistentYes—
A value in a closed setYes, but an ENUM or a DOMAIN is stronger Adding an enum value is a catalogue operation; changing a CHECK means drop, re-add, re-validate every row
This row's total equals the sum of its childrenNo A trigger, or a periodic job — and say which one in a comment
No two bookings overlap in timeNo A PostgreSQL exclusion constraint with a range type, which is correct under concurrency — a trigger checking the neighbouring row cannot see a concurrent inserter
At most one active row per groupNo A partial unique index
A derived value cannot drift from its inputsAssert, not prevent A STORED generated column — then there is no such thing as a row where they disagree
Interview trap — "I validate in the application, so CHECK is redundant"

The error is conflating a check on input with a check on state. Application validation runs before the write, against a snapshot the request did not control. A CHECK runs as the write. The gap is the classic inventory oversell: two concurrent requests each read "1 in stock", each validate "quantity ≤ 1", each subtracts one, and the result is stock of −1 with no exception thrown anywhere.

Three further reasons it is not redundant: the second write path — a backfill, an import, an admin tool, a second service, a psql session from a laptop — never goes through your validation; the rule change creates a window where the code deploys Tuesday and the migration relaxes the constraint Wednesday; and the cost asymmetry is permanent, because validation is ongoing human effort that scales with the number of people who remember, while a constraint scales with the number of writers. The framing that lands: validation protects a request; a constraint protects a dataset.

Must remember — the hierarchy of integrity, strongest first
  1. A type that cannot hold the bad value — bigint for money, an ENUM for a closed set, an interval for a duration. This is the only entry that makes the illegal state unrepresentable rather than checked.
  2. A NOT NULL that means something.
  3. A CHECK for a rule over one row.
  4. A UNIQUE for a rule about identity.
  5. A FOREIGN KEY for a rule about reference.
  6. A trigger — where you go when nothing above can express it, and which costs on every write and is the one mechanism DESCRIBE table cannot show you at all.

Reach for a higher-numbered mechanism only when the lower ones genuinely cannot express the invariant, and when you do, say so in a comment.

-- 1. Install WITHOUT validating. Brief ACCESS EXCLUSIVE.
--    Every NEW write is checked from this instant.
ALTER TABLE subscription
  ADD CONSTRAINT subscription_price_positive
  CHECK (price_cents >= 0) NOT VALID;

-- 2. Scope it. Concurrent-friendly; this count sizes the remediation.
SELECT count(*) FROM subscription WHERE NOT (price_cents >= 0);

-- 3. Remediate in batches. Usually a BUSINESS decision, not a SQL one.

-- 4. Validate under SHARE UPDATE EXCLUSIVE: reads and writes continue.
ALTER TABLE subscription VALIDATE CONSTRAINT subscription_price_positive;
Scaling reality check — ADD CONSTRAINT is three operations wearing one costume

On a 40-million-row table, a single ALTER TABLE … ADD CONSTRAINT … CHECK validates every existing row under ACCESS EXCLUSIVE: a multi-minute table freeze whose symptom is an application timeout, not a database error. The three phases — install NOT VALID, remediate, VALIDATE — should be three separate deploys, so each is independently observable and independently reversible.

Two things a staff engineer volunteers: the remediation is a business decision, because setting 400 negative prices to zero is not obviously right and only someone who understands the domain can choose between zero, absolute value and reversal; and the NOT VALID state is a real, queryable state — a constraint left unvalidated after a deploy is a claim your data does not actually satisfy, and a schema audit should be looking for exactly that.

Trade-off — triggers or CHECK constraints?

CHECK when the rule is computable from the row's own columns. Free to read, visible in DESCRIBE, optimisable, and dropped and re-added like any other object. It cannot see other rows, cannot run a subquery, and cannot fire more than once per row per statement.

A trigger when the rule genuinely needs other rows, needs a side effect, or needs to fire on something other than a row write. It can do almost anything. It also costs on every write to the table whether or not the rule is relevant, it is invisible in a schema dump unless you know to look, it silently stops applying if the column it reads is renamed, and its firing semantics differ by type — statement-level fires once per statement, row-level once per affected row, and bulk paths can bypass it entirely.

Flips on almost always: can this be expressed over one row? If a trigger is in the design, the first move is a redesign — a partial unique index, a generated column, an exclusion constraint.

A CREATE DOMAIN is a named alias with a base type plus a CHECK and optional collation: reusable, visible in the catalogue, enforced on every write, and genuinely valuable for a value that recurs — a currency code, a country code, a non-negative amount. A PostgreSQL ENUM is different in kind: the set of values is itself an object you can extend with ALTER TYPE … ADD VALUE without a table rewrite, which is what makes it the right answer for a closed set the business will extend a value at a time. The condition for either is that the value set really is closed and shared; if only one table has the column, a CHECK there is simpler and equally safe.

Must remember — a DEFAULT is not a constraint

It supplies a value to anyone who forgets, and it supplies it silently. Nothing in the schema distinguishes "the caller asserted zero" from "the caller said nothing and the database decided".

DEFAULT 0 on a column whose absence is meaningful converts "unknown" into "zero", and the conversion is invisible from the schema: the column is NOT NULL, constrained and tidy. Every sum under-reports, every avg is dragged toward the floor, every WHERE weight > 0 silently excludes the unknowns, and nothing errors anywhere.

The defensive form: let the column be NULL when absence is meaningful, and add a CHECK when presence is mandatory. A CHECK (col IS NOT NULL AND col <> '') is the better tool because a default supplies a value to anyone who forgets, while a check refuses the row. And note the scale-free property: this is wrong on a table of four rows exactly as much as on four hundred million — it is the one item on the list that should never be scaled away.

05

DML: INSERT, UPDATE, DELETE, upsert

The common misconception is that the cost of an INSERT is "one row". It is a sequence draw, a lock on somebody else's row, one B-tree insert per index, a tuple write, several WAL records, and a log force at commit. The levers on write throughput are therefore constraint count, not table size.

-- The unique index IS the concurrency control, not the statement logic.
INSERT INTO counters (key, hits) VALUES ('homepage', 1)
ON CONFLICT (key) DO UPDATE
    SET hits = counters.hits + 1;
    --                  ^ the STORED row, not the proposed one.
    -- Writing `excluded.hits` here resets the counter to 1 every time.

-- RETURNING removes the read-after-write round trip and returns
-- generated values the client would otherwise have to guess.
UPDATE account SET balance_cents = balance_cents - 1000
 WHERE id = 42
RETURNING balance_cents;   -- 48200
Interview trap — ON CONFLICT DO UPDATE with no unique index to conflict on

In PostgreSQL you cannot get this: the conflict target must match a unique index, and the statement fails to plan without one — which is the good outcome, because the mistake is caught at deploy time rather than at 3am. In MySQL it is trivially reachable, because ON DUPLICATE KEY UPDATE has no conflict target: it fires on a violation of any unique key, and if there is no unique key there is never a violation, so the statement is silently always a plain insert.

The mechanism is worth being able to state: an upsert is correct only because the unique index provides a serialisation point — the index entry is taken speculatively, so a concurrent inserter of the same key waits for the outcome and then updates the committed row. Remove the index and you have removed the only thing making two concurrent upserts mutually exclusive: two rows, both claiming to be the counter, permanently wrong, with no error. The second-order MySQL trap: with two unique constraints the statement does not tell you which conflicted, and the update clause may itself violate the other.

Must remember — UPDATE with no WHERE is valid SQL

That is a property of the syntax, not the implementation, and it is why UPDATE is the most dangerous ordinary statement in SQL: UPDATE accounts SET balance_cents = 0 is 200 million rows, one implicit transaction, 40 GB of WAL, and every balance gone.

The danger is social, not technical — the engine has no opinion about whether that is what you meant. The defences that actually fire are the ones that make the mistake visible before it is durable: run the predicate as a SELECT first and read the count, use RETURNING so the affected rows are enumerated, and wrap it in an explicit transaction so an obviously wrong row count can be rolled back. That last one is why "did you wrap it in a transaction" is the first follow-up question on any destructive statement — and "it is a single statement, so it is already atomic" is a misunderstanding that costs someone their Friday.

Interview trap — "what's the difference between DELETE and TRUNCATE?"

"Truncate is faster" gets partial credit and teaches nothing. The mechanism is that TRUNCATE creates no MVCC row versions: a DELETE writes a new version per deleted row and leaves that many dead tuples for VACUUM, so a 300-million-row DELETE leaves the table bigger than it found it.

The trap that actually causes incidents is the MVCC one: a TRUNCATE during business hours can be invisible to a long-running reader. A transaction that read 300 million rows before the truncate keeps seeing 300 million rows, builds aggregates on them, and only sees the table empty at its next snapshot — so a report computed from it is wrong with no error reported. TRUNCATE on a live table is a maintenance-window operation, and the window exists because the correctness question is about readers, not writers.

-- Keyset pagination, not OFFSET (OFFSET re-reads and re-locks
-- everything it skipped). Every element here is load-bearing.
WITH batch AS (
    DELETE FROM events
     WHERE id IN (
         SELECT id FROM events
          WHERE id > :last_committed_id
            AND created_at < now() - interval '2 years'
          ORDER BY id
          LIMIT 5000
          FOR UPDATE SKIP LOCKED   -- never block another reaper
     )
    RETURNING 1
)
SELECT count(*) FROM batch;
-- then: record :last_committed_id, COMMIT, sleep, repeat
Scaling reality check — batch size is a function of log volume, not rows

An un-batched delete of 40 million rows is dangerous for four compounding reasons, all of which are about one statement in one transaction: every row stays locked until commit; one snapshot for the whole duration; a multi-gigabyte WAL burst that fills the disk, saturates the log shipper and lands on the replica as one multi-hour transaction blocking everything behind it in the stream; and no progress, no pause, no resume — a failure at 39 million rolls back all 40 million.

The interesting number is WAL per batch, not row count: 5,000 wide rows can be 40 MB of log; 50,000 narrow rows can be 3 MB. So the rule is to choose the batch size so one batch's log volume stays in the low hundreds of megabytes — small enough that the log writer, the shipper and the replica each keep up, large enough that you are not committing 10,000 times. FOR UPDATE SKIP LOCKED is the standard building block for any queue table or work-claiming loop, and the difference between a reaper that degrades gracefully under contention and one that deadlocks against production traffic.

Past about 10 million rows the honest answer is a partition drop — DROP TABLE events_2024 is O(1) rather than O(n), and that is a design decision made long before the day you need the delete.

Trade-off — archive-then-delete, or just delete?

Just delete when the data has no retention obligation, no legal hold and no analytical value. This is rarer than teams assume, because "we might want it for analytics" is a real requirement that never appears on a requirements document. Deleting is the cheapest operation on the list and the only one that leaves you with one fewer thing to operate.

Archive then delete when the data must survive but must not slow the hot table. The cost is that you now have a second store with its own schema, backup policy, restore procedure and compliance story, and migrating it is a project. The benefit is real: the hot table shrinks, its indexes shrink with it, and the queries that matter get faster in a way no amount of index tuning on the original table achieves.

Flips on: has anyone ever queried the old data? If yes and you delete it, the honest answer to the request will be "in a backup taken eleven months ago". If no — and "no" should be an answer you got in writing — archive is a project for a hypothetical.

RETURNING is the clause that changes architecture: it removes the read-after-write round trip, it returns generated values the client would otherwise have to guess, and DELETE … RETURNING is how a GDPR erasure produces a manifest of exactly what was destroyed — the difference between "we processed the request" and "we can prove what we deleted". Always project the few columns you need.

06

NULL & three-valued logic

NULL is not zero, not the empty string, not false, and not a member of any domain. It is a marker that a value is absent or unknown, and the reason it causes so much trouble is arithmetic: SQL's comparison operators were defined over values, and NULL is not one. Every NULL surprise in SQL is a consequence of one sentence.

Must remember — WHERE and HAVING admit only TRUE

UNKNOWN is not "probably true", it is "not false", and it is dropped. So WHERE shipped_at = '2026-01-01' and WHERE shipped_at <> '2026-01-01' are not complements — both exclude the NULL rows, and any query that assumes they partition the table is wrong about exactly the rows whose value is absent.

When a query returns fewer rows than you expect, ask "which predicate was UNKNOWN for the rows I expected?" before you ask anything about indexes. The two operators that fix it: IS NULL, which is a type test rather than a comparison, and IS NOT DISTINCT FROM, which is the correct negation of =. NOT EXISTS is the correct anti-join, because it asks an existence question, which has no third value.

Interview trap — why does x NOT IN (1, 2, NULL) return zero rows?

Because NOT IN is syntactic sugar for x <> 1 AND x <> 2 AND x <> NULL. The third comparison is UNKNOWN for every row, UNKNOWN AND TRUE is still UNKNOWN, and WHERE keeps only TRUE. The row is dropped regardless of what x is — one NULL poisons the predicate globally rather than for matching rows. The result is an empty set, not an error, and the query is syntactically valid, so nothing warns you.

The provenance is what makes it a production incident: nobody typed that NULL. It is a subquery selecting a nullable column, so WHERE id NOT IN (SELECT order_id FROM refunds) dies the day someone makes refunds.order_id nullable — a schema change in a different repository, months earlier. Related: the same reasoning inverts for AND, where FALSE AND UNKNOWN = FALSE, which is why x <> 1 is not x = 1 negated safely.

COUNT(*) counts rows and cannot be confused by a NULL because it never reads a value — and it is not slow, because a row count can come from an index or a visibility-map entry without touching the heap. COUNT(col) counts rows where col is not NULL, which makes count(*) - count(col) a data-quality metric: the number of rows where the field is missing, and on any table where that number is not zero, every aggregate over that column is under-reporting by exactly that much. COUNT(DISTINCT col) skips NULLs and then deduplicates, so it under-reports by the number of absent rows if you were counting the absent value as a category.

Trade-off — COALESCE to zero, or leave it NULL?

Coalesce to zero when absence genuinely means zero — no orders means no revenue, and a financial report that shows a blank for February is wrong. The cost is that you have thrown away the distinction between "zero" and "we could not compute this", and in a pipeline that distinction is load-bearing: a failed upstream query that returns no rows now looks exactly like a month with no sales.

Leave it NULL when absence means unknown — no rows matched because the partition was missing, the source was unavailable, or the range was outside retention. NULL propagates and a downstream NOT NULL insert fails loudly, which is correct: the pipeline stops rather than writing a confident zero.

Flips on a question about the domain, not the code: is there such a thing as a real zero here? For revenue, yes. For a conversion rate whose denominator is zero, no — 0/0 is not zero, and coalescing it reports a catastrophic failure as perfect performance. The general rule: coalesce at the boundary where the domain has agreed what absence means, and nowhere else.

COALESCE and NULLIF are often presented as opposites. They are not: COALESCE substitutes a value and short-circuits, while NULLIF is a guard whose whole purpose is to create a division-by-zero or a constraint violation on demand. Paired, they express "if the divisor is zero, the answer is unknown, and the caller must supply a fallback rather than receive infinity". The trap: COALESCE in a WHERE clause discards the NULL rows rather than matching them and makes the predicate unindexable, so a 200-million-row table gets a sequential scan.

GROUP BY status gives you one row per status plus a row whose label is NULL and whose count is "orders with no status at all" — in a dashboard that row either disappears in the presentation layer or renders as a bar nobody has ever clicked, and it is almost always the most actionable data-quality number in the table. The related trap is ordering: NULLs sort last in ASC on PostgreSQL and first in ASC on MySQL, so the same query returns rows in a different order on two engines. Write NULLS FIRST / NULLS LAST explicitly rather than inheriting a default that differs between the systems you might be migrated onto.

Views, materialized views & generated columns

The mental model that causes the most trouble is "a view is like a table but virtual". The accurate model is narrower: a view is a named query, stored in the catalogue, that the parser expands into the statement using it. No storage, no rows, no statistics of its own, no independent existence — a macro with a schema. Three consequences follow directly: the view does not shield the schema (DROP COLUMN fails with a dependency error in PostgreSQL, or succeeds and leaves you a view that errors at query time in MySQL); it has no statistics of its own; and a view nested twelve deep is twelve queries to read.

View, materialized view, or a real table
ConceptRuleWhen it bites
ViewWhen the query is cheap or the planner can optimise it, and you want one definition rather than twelve Costs what its query costs — never faster, never slower. It is never stale, because it has no contents. Gives up stability of cost, because the plan changes when the statistics do
Materialized viewWhen the query is genuinely expensive and staleness bounded by the refresh window is acceptable A second copy of the data, a refresh job, and a silent failure mode: it has no idea it is out of date, and nothing in the result, plan, log or API response distinguishes a fresh answer from a six-hour-old one

Name the mechanism in review — trigger, dual write, or CDC — because "we'll keep it up to date in the application" is how four write paths become five and the fifth forgets
Scaling reality check — the refresh cost, not the query cost

A full refresh is fine while recomputing is cheaper than maintaining, which in practice means while the source is under about a million rows and the query is a simple aggregate. Past that, three things break in order: the refresh runtime crosses the job's window, the ACCESS EXCLUSIVE swap collides with the peak hour, and the replica cannot apply the recompute inside its lag budget — so a materialized view designed to offload reporting ends up delaying reporting.

The concrete version of that failure: an eight-table-join nightly aggregate, refreshed every five minutes over a 200-million-row source, is 288 recomputes per day, each producing a multi-gigabyte WAL stream the replica must apply inside the same five minutes. The first version of that design fails on replication lag, not on query latency, and the team will diagnose it as a materialized-view problem when it is a source-design problem. The answer is a partitioned source with per-partition refresh, or a real reporting store — and the maximum acceptable staleness has to be written down before the view is built, because that number determines the design.

REFRESH MATERIALIZED VIEW without CONCURRENTLY recomputes into a new structure and swaps only on success, under a brief ACCESS EXCLUSIVE lock — so a failed refresh is a good failure: readers get stale data rather than a partial one. The consequence is that the view is now stale by however long the refresh has been failing, and nothing about the view reports that. CONCURRENTLY lets it run while the table is read and written, at the cost of a UNIQUE index on the view, double the peak disk, and double the compute. The response to either is not "retry harder" — it is to expose the last successful refresh timestamp, alert on refresh age rather than refresh failure, and put a bound on how old the data may get.

Interview trap — WITH CHECK OPTION and the write-through hole

A view over a single table with no aggregation, DISTINCT, set operation or grouping is updatable in most engines: the INSERT, UPDATE or DELETE is routed to the base table. Updatability is about routing, not constraining. The hole is that another writer can set the column the view's predicate tests, so the view and the base table diverge through a path that never goes through the view at all.

The failure that matters is the layered one: stack v_all over v_active over v_verified and an insert through v_verified does not enforce v_active's filter, so v_verified ends up containing rows v_active excludes — the views are supposed to be nested subsets and are not. WITH LOCAL CHECK OPTION checks this view's own predicate; WITH CASCADED CHECK OPTION also checks every view it is built on, which is what a stack wants. The convention that makes the whole question moot: treat views as read-only interfaces and grant writes on the base tables directly.

CREATE TABLE order_line (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint      NOT NULL,
    qty        integer     NOT NULL CHECK (qty > 0),
    unit_cents bigint      NOT NULL,
    line_cents bigint GENERATED ALWAYS AS (qty * unit_cents) STORED
);
-- There is now no such thing as a row where line_cents disagrees.

CREATE TABLE users (
    email      text NOT NULL,
    email_norm text GENERATED ALWAYS AS (lower(trim(email))) STORED
);
CREATE UNIQUE INDEX users_email_norm_key ON users (email_norm);
Interview trap — "why not just use a trigger?"

Because a generated column makes the invariant unrepresentable rather than merely enforced, and a trigger can never do that. line_cents has no value a caller can set — GENERATED ALWAYS means a writer who tries gets an error rather than a silent inconsistency — so there is no code path, in any of the four writers, that can produce a row where the arithmetic disagrees. The trigger version enforces the same rule on every write it happens to intercept, and the trigger itself is invisible in DESCRIBE and in a schema dump.

The honest limit, which is what a staff answer adds: a generated column can reference only other columns of the same row, in a deterministic expression. The moment the derivation needs another row you are back to a trigger — and the right move there is to reshape the invariant first with a partial unique index, an exclusion constraint, or by hoisting the needed data into the row.

Must remember — the view that became load-bearing

A view is a convenience right up until it has six services, two BI dashboards, one compliance export and fourteen hand-written reports reading it, and last reviewed two years ago by someone who has left. It did not become load-bearing through a decision; it accumulated, one individually reasonable consumer at a time, none of which triggered a review — which is exactly why changing it now cannot be a decision either, and has to be a migration with a deprecation window.

The fix is unglamorous and effective: count the consumers with a catalogue query joining the dependency view, because "I feel like a lot of people use this" is not a number; assign an owner in the schema's README; restrict changes to additive ones — CREATE VIEW v2 AS …, migrate consumers one at a time, drop v1 when the count reaches zero; and run the count quarterly. The generalisation is that any interface without an owner and without a versioning policy becomes unchangeable — and the interface in question is usually not the view, it is the table underneath it.
