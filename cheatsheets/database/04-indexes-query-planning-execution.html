Volume 4 — Indexes, Query Planning & Execution

An index is not free speed, it is a permanent tax on every write and a permanent claim on the buffer pool. Learn to price that tax, name the access path a predicate can actually reach, and read a plan leaves-first — and the “why is this query slow” question stops being a guess.

If you only remember five things

  1. A composite index is one sort, and the sort is lexicographic. The index on (a, b) is ordered by a, then by b within each a. So an index can seek on a and then walk b, but it cannot seek on b at all — the b values are scattered across every a run.
  2. An index only pays if it throws away almost the whole table. An index scan costs 3 × 4.0 + k × 4.0 = 12 + 4k; a sequential scan costs N. Break-even is 4k = 0.026N — a 0.64% match rate on spinning media, 2.6% on NVMe. Below it the index is a net loss for every write and every buffer-pool byte it occupies, and the sequential scan is the correct plan. The one exception is the covering index, whose per-row cost drops far enough to move break-even out to 11%.
  3. A B+ tree seek costs three page reads — root, internal, leaf — and then one random heap read per surviving row. Three is the floor, and it is why the break-even arithmetic above exists.
  4. Read EXPLAIN ANALYZE leaves-first, and multiply rows by loops. The bad estimate is the deepest node with a large error ratio; every error above it is inherited. rows=0.5 loops=1000000 is 500,000 rows, not zero.
  5. Every index is paid for twice. Once in write amplification — a 12-index table costs 13 page writes per inserted row — and once in buffer-pool residency, which evicts working set. Adding an index to fix one query degrades every other query that reads the table.

No section matches that filter.

01

Why indexes exist: the break-even arithmetic

A sequential scan reads every page in physical order, so readahead collapses the seek cost and it is far cheaper than the arithmetic suggests — on a spinning disk, roughly 80×. That is why the correct answer to “why is my scan slow” is never “it read too many pages”. The cost is that it reads all of them, and it evaluates the predicate on every tuple, which is CPU proportional to the table size rather than to the answer size.

An index inverts that. It turns the answer into the address. The bill arrives at write time instead, and the entire question of whether an index is worth having reduces to one comparison: the three page reads plus one random heap read per matching row, against reading the table.

What a full scan of the 2 GB orders table costs per device

The same 256,411 pages cost 13 seconds or 34 minutes depending on nothing but the drive. That is why the threshold that decides between scanning and indexing moves by a factor of 40 across hardware generations, and why a hard-coded rule of thumb tuned on somebody's laptop is worse than no rule of thumb.

Scaling reality check

The table size below which the planner correctly prefers a sequential scan moves with the device: roughly 234 rows on NVMe and 9,360 rows on spinning disk — a 40× spread for the same query on the same data. Tune the number, or the planner tunes it for you.

Interview trap

“Add an index to make it selective” is the reflexive answer and it is often wrong. Indexing only pays when the query returns a very small fraction of the table. On a table where your predicate matches 30% of the rows, the index makes the query slower, and the plan you should be arguing for is the sequential scan you already had.

Trade-off

An index buys read speed and pays in write amplification and buffer-pool residency. The condition that flips it: an index on a table with a high write rate and low read hit rate is pure cost. The test is not “is this query slow” but “does this index earn its keep across the whole workload” — which is exactly what the unused-index inventory in section 3 measures.

02

B+ tree internals: fan-out, height, and the leaf chain

A B+ tree stores every record only in the leaves. Internal nodes hold separators — the high key of the run beneath them — and nothing else. That single design choice is why the fan-out is enormous and the height is 3 on a ten-million-row table.

On an 8 kB page there are 8,152 usable bytes after the 24-byte page header. A big-endian int8 separator costs 8 bytes, so 8152 / 16 ≈ 509 entries fit in a leaf and half that fits in an internal node. A classic B-tree must also fit an offset to each record, which drops its fan-out to 39 — a 13× penalty, and the reason its height is log(509)/log(39) larger. B+ trees win because the search key never moves and the leaves carry the payload.

10M rows, 8 kB pages: fan-out decides height, and height decides everything

int8, no INCLUDE50919,6463913

Height is not linear in table size, it is logarithmic in fan-out. 5092 is 259,081 rows; 5093 is 131,950,029; 5094 is 67,162,164,961. Adding a level buys you seven orders of magnitude. This is the answer to “how big do tables get before indexes stop helping” — they do not, because the level count barely moves.

The two properties that make ranges cheap

First, the leaves are linked, doubly, in key order. Once the seek has landed on the right leaf, a range predicate is a walk along the chain, not a second descent. That is the mechanism behind “1 descent + ceil(matching / 509) page reads” — the linear-in-the-answer-size cost that makes an index beat a scan on large ranges and lose to it on small ones.

Second, all of it is sorted. That is what an ORDER BY can be satisfied by, what makes merge joins possible without a sort node, and what makes a leftmost prefix possible at all. The cost of the sorting is the index's width, and width is paid in fan-out, which is paid in height.

Must remember

B-tree stores records in internal nodes; B+ tree stores them only in leaves and puts separators above. Almost every interview question that says “B-tree” when it means the structure your database actually uses is answered by “B+ tree, and here is why the fan-out is 509 instead of 39”.

Interview trap

“The index is small so it fits in memory” is half true in a way that misleads. 157 MB does not fit in a 2 GB buffer pool alongside a working set, and the 180 MB version of the same index moved the pool's hit ratio from 99.1% to 88.3% in the volume's worked example. Index size is measured against the pool, not against RAM.

Page splits and fillfactor

An insert that lands between two keys splits the leaf roughly in half, and every row after it moves. That is why a freshly-built index is half empty: the cost model assumes pages are ~50% occupied after random inserts, which is where the 19,646 leaf pages for 10M rows comes from instead of the ~3,900 a perfectly packed index would need.

The fix is to leave slack on purpose, and it is worth knowing when it applies: a table with a monotonically increasing primary key only ever appends to the rightmost leaf and never splits it, so it does not need a fillfactor. A table with random keys does.

Interview trap

REINDEX and VACUUM are not interchangeable answers to “my index is bloated”. REINDEX rewrites the index and VACUUM reclaims dead space in the heap. A bloated index is fixed by the first; running only VACUUM leaves the index exactly as fat.

03

Index types and what each one costs to maintain

The taxonomy that matters at interview altitude is not “which data structure is this” but which questions can this structure answer at all. A hash index answers equality and nothing else. There is no order in it, so no range, no ORDER BY, no merge join, no skip. A B-tree answers everything. Everything below is a B-tree with a different internal arrangement, chosen because its question set or its write cost is better.

GIN is the one worth dwelling on, because its cost is proportional to the number of keys in the row, not to the number of rows. A 12-tag article writes 12 posting lists. That is why GIN-backed indexes use a pending list: writes land in an unsorted buffer and are merged later, trading read latency for write throughput.

Scaling reality check

BRIN stores one summary entry per 128 blocks. For a 2 GB heap that is 32 KB against 2 GB — 4,900× smaller, at 1/128 of the write cost of a B-tree. It answers min/max ranges, so it works precisely when physical order matches logical order (append-only timestamps). On randomly-ordered data its min and max span the whole block range and it answers nothing.

Covering indexes: paying width for a saved heap read

An INCLUDE column widens the entry from 16 B to 37 B, which drops entries per page from 509 to 220 — and the index from 157 MB to 366 MB. It gains a heap-free read and loses 209 MB of buffer pool. That is the whole trade, and it is worth stating as a trade rather than a free win.

Trade-off

A covering index is worth 209 MB when it removes every heap fetch from a hot query. It is pure loss when the table is updated often, because an index-only scan is only free if every page it references is marked all-visible in the visibility map — and any page with a recently updated tuple is not. The condition that flips it: on a frequently-updated table a covering index still pays Heap Fetches on every row and you have bought 209 MB of cache pressure for nothing.

Interview trap

The volume's scenario table is worth remembering as a shape: a 364 B entry gives 22 entries per page where a 16 B entry gives 509, so the index grows to 23× its naive size and the height climbs from 3 to 5. Wide index entries do not cost linearly. They cost the fan-out, and the fan-out is the height.

Scaling reality check

The target engine caps index key width at 3,000 bytes. Add a 6-byte bigint payload to a 3,000-byte key and a page holds 136 entries instead of 509 — a fan-out of 136, where 1363 = 2.5 million rows is the point at which the tree needs a fourth level. An 8-column, 166 B index gives 49 entries per page and 493 = 117,649 rows. Wide composite indexes stop being efficient well before they stop fitting.

The inventory question

The number to have ready is that in a real production estate a large share of indexes are never used. The volume's worked estate — 340 indexes over 60 tables — has 15-25% of them unused. Over 1,100 tables, 2,400 indexes and 500 GB, the first thing to do is measure usage and drop what nothing reads, because each one costs a write amplification share and buffer-pool pages that a working index needs.

Must remember

A table with 12 indexes costs 13 page writes per inserted row for the index maintenance alone. At 10,000 inserts/second that is 130,000 page writes per second that exist only to keep structures nobody queries. Index count is a write-path metric, not a read-path one.

04

Column order and sargability

An index on (a, b) is one sort, lexicographic. Within a single a value, the rows are ordered by b. Across different a values, the b values restart. That is the whole of the leftmost prefix rule, and every composite-index decision follows from it.

The worked example that makes the rule concrete, on a 10M-row orders:

Order A vs Order B on (region, created_at) — the same five queries, two index definitions

Interview trap

“Put the most selective column first” is the reflexive answer and it is wrong. Cardinality is not the question; which query can still use the index is. Order A serves the 0.08% query in 16 leaf pages and Order B serves it in 1,571. Judge the order against the whole query mix, not against the one query you were asked about.

Trade-off

Widening a composite index to include a third column fixes the filtering for the query that has it, and still leaves the query that only constrains that column with no seek at all. The condition that flips the answer: if status is the predicate 2% of the time and nothing constrains the prefix, a partial index WHERE status = 'pending' is strictly better — the volume's example makes it 52× smaller (394 leaf pages against 19,646) and permanently buffer-resident.

Sargability

A predicate is sargable if the planner can turn it into an index seek or range walk. Most cases where it cannot are one of four things, and all four are fixed at the call site rather than in the index.

Sargable and non-sargable forms, and what each costs

-- 1. Function on the column: expression index, then the query matches it exactly
CREATE INDEX idx_orders_created_day ON orders ((date(created_at)));
-- but the predicate must be written the same way, function included
SELECT * FROM orders WHERE date(created_at) = '2026-01-01';

-- 2. OR across columns: UNION ALL, never UNION
--    UNION deduplicates, which forces a sort or hash over the combined
--    result and can cost more than the OR saved.
SELECT * FROM events WHERE user_ref = 9182
UNION ALL
SELECT * FROM events WHERE ip_address = '10.0.0.7';

-- 3. Implicit cast: the literal's type must match the column's
SELECT * FROM events WHERE user_ref = '9182';   -- varchar column
SELECT * FROM events WHERE customer_id = 9182; -- integer column, no quotes
Interview trap

The implicit-cast trap has a direction, and getting the direction wrong is worse than not knowing it. With a VARCHAR column compared to an integer literal, PostgreSQL converts the literal to text and uses the index cleanly; MySQL's optimiser declines the index instead. The genuine PostgreSQL failure is the reverse: an index on an integer column compared to a text literal, where the column must be cast to text. The general rule survives both: the index is usable only if the conversion falls on the literal side.

Interview trap

An OR with one selective branch and one total branch is a sequential scan, and that is the planner being right. WHERE user_ref = 9182 OR user_ref IS NULL has a branch matching 11,999,960 rows; the planner sees a 100% match, scans, and is correct. The presence of one selective branch does not help if the other is total.

05

Access paths and the cost model

PostgreSQL's planner does not emit milliseconds. It emits relative cost units, calibrated to one sequential 8 kB page read on a cold spinning device. Every decision it makes is a comparison of two numbers in those units, and the constants are configurable — which is the lever, and the liability.

The constants the planner reasons with
Knob Default Meaning
seq_page_cost1.08 kB sequential read
random_page_cost4.08 kB random read — the key ratio
cpu_tuple_cost0.01per tuple: projection + filter
cpu_index_tuple_cost0.005per index tuple
cpu_operator_cost0.0025per operator evaluation
parallel_setup_cost1000fixed cost of launching parallel workers
effective_cache_size4× shared_buffersthe planner's belief about RAM

So the arithmetic is: a sequential scan of 256,411 pages costs 256,411. An index scan costing 3 page reads plus 40 heap fetches costs 3 × 4.0 for the descent, 40 × 4.0 for the random fetches, and a fraction for the CPU — about 12.8, which the planner will pick every time.

Scaling reality check

The 4.0 is a lie on modern hardware, in both directions. On NVMe the true ratio is ~1.0 and random_page_cost = 1.1 is the right setting; on spinning or network-attached storage the true ratio is 8–20 and the default understates it badly. Default cost settings therefore produce bad plans on both kinds of hardware, in opposite directions — too index-scan-happy on flash, too seq-scan-happy on network storage.

The ~25% switch is a heuristic with a real mechanism behind it: once more than about a quarter of the rows is going to be visited in random order, the physical-order advantage of a sequential scan is worth more than the random-read saving, and a bitmap — which collects the matching rows as a bit vector and then reads the heap in physical order — wins both ways. The volume's example has 1,180,233 rows collapsing to a 147 kB bitmap, which is the size argument for why this is even possible.

Interview trap

Buffers: shared hit=256411 is 29 seconds. “All from cache” is not “fast” — hit is RAM at ~100 ns, so the whole scan cost about 26 ms of I/O and the rest was CPU: 8,819,767 rows removed by filter, each an cpu_operator_cost evaluation. The corollary is the one people miss: a high hit ratio alongside large temp read/temp written figures means the I/O is not fine at all — that work went through a temp file because a sort or hash exceeded work_mem.

Must remember

A sequential scan is not a failure and an index scan is not a success. Both appear as the planner being right. The judgement is: does the estimate match reality, and is the shape proportional to the answer or to the table?

06

Joins at runtime

Three algorithms, and the choice between them is almost entirely about the size of the outer relation and whether the inner has an index. Nothing about the query's shape is relevant, which is why “why did it pick a nested loop” has a numeric answer.

Which algorithm wins, from the volume's worked crossover (inner = 1.2M rows)
Outer rows Inner rows Inner index? Chosen Why
401,200,000yesnested loop160 reads vs 1.2M for hash
401,200,000nonested loop (seq inner)40 × 30,769 = 1.2M — a tie
5,0001,200,000yeshash join15,020 vs 1.2M + 5,000
10,000,0001,200,000yeshash join30M vs 1.2M + 10M
10,000,0001,200,000nohash join3.08×1011 vs 1.2M + 10M

A sequential inner makes the nested loop read 10,000,000 × 30,769 = 3.08 × 1011 pages. At 200 IOPS that is 178 days. The ratio against the good nested loop is 1.9×109 — and both plans are nested loops. That is the point: the algorithm is not the variable, the inner access path is.

Interview trap

“Nested loop join” is not by itself a red flag. The volume says it directly: at 40 outer rows against a 1.2M inner with an index, 160 reads is the correct plan and a hash join would be 1.2M reads to build a table you will probe four times. Name the crossover number and the answer stops being a heuristic.

Merge join and the sort it avoids

Merge join wins when both inputs arrive already sorted, when the output must be sorted anyway, or when both relations are large and neither fits in work_mem. The third case is the one people quote and the one that costs: sorting 1.2M rows of 180 bytes is 216 MB against a 4 MB work_mem, so it spills into 54 disk batches and 108 random 8 kB I/Os — 0.54 s of pure sort cost before a single row joins.

Interview trap

A Merge Join with a Sort node under it has already lost. The whole practical argument for indexing is to make the sort disappear: Merge Join without a Sort node, which requires the join predicate to match the index's leading column in the same order. An index on a column you join on is often a sort-elimination index, not a lookup index.

Scaling reality check

work_mem defaults to 4 MB per sort or hash node, per connection. The volume's build-side case is a 254 MB hash table that spilled into 139 batches and 556 random I/Os, costing 2.78 s of pure spill. Raising work_mem is a per-query decision with a memory ceiling multiplier attached; setting it globally on a busy server is an outage generator.

-- The 5 rows-per-outer form the planner cannot infer on its own.
-- For each region, find its top 5 orders by total.
SELECT r.region, o.id, o.total
  FROM regions r
  LEFT JOIN LATERAL (
        SELECT o.id, o.total
          FROM orders o
         WHERE o.region = r.region      -- the inner gets the outer row
         ORDER BY o.total DESC
         LIMIT 5
       ) o ON true
 ORDER BY o.total DESC;
Must remember

LATERAL is how you express an index-nested-loop deliberately. It is also the shape that silently becomes a disaster: remove the LIMIT and it is a correlated subquery the planner must evaluate per outer row, and with no inner index it is the 3.08×1011 regime.

07

Reading EXPLAIN and EXPLAIN ANALYZE

EXPLAIN without ANALYZE is a claim — a cost computed from statistics on a model calibrated for different hardware. EXPLAIN ANALYZE is a measurement, and it runs the query. Conflating them is the first mistake; running EXPLAIN ANALYZE on a long query in a production console is the second.

Neither rows=40 nor rows=1 is the total. 40 × 1,000 = 40,000 and 1 × 40,000 = 40,000. The sub-1 form is the same point made nastier: rows=0.5 loops=1000000 is 500,000 rows, and reading it as “no rows” is how a million-row nested loop gets reported as an empty result.

Where the time went here is the useful part: the inner lookup, performed 40,000 times, is 160 ms of 8,110 ms — 2%. The outer per-loop overhead is 7,750 ms of executor bookkeeping, buffer lookups and visibility checks. And the estimates are good: the outer was estimated at 42 and produced 40 (5% error), the inner at 1 and produced 1. This plan is not a victim of a cardinality error, so the answer is to change its shape, not to reach for ANALYZE or a plan hint.

Interview trap

Finding the bad estimate at the top of the tree. The optimiser's cost for a parent is derived from its children's estimates, so a child that estimated 10,000 and produced 1,000,000 makes the parent wrong, the grandparent wrong, and so on to the root. The top node's error is a symptom; the deepest node's error is the disease.

Must remember

A parent's actual time includes its children's. Always read the tree leaves-up, and subtract to find the node doing local work. In the plan above the Sort shows 8,120 ms because it is the root — its own cost is a 4,212 kB in-memory quicksort, about 180 ms.

Estimates over 1000× wrong: the diagnosis

The mechanism is that a join's output cardinality assumes independence between the join predicates unless extended statistics declare otherwise. If customers.country_id and customers.active are correlated — 99% of active customers in 3 countries — the true result is 590× larger than the product of the two selectivities, and the planner costed a 2,000-row join as cheap and got 1,180,000.

Interview trap

Actual lower than estimated is the direction people forget, and it is a bug too. A node estimated at 1,000,000 that produced 40 means the planner chose a sequential scan over an index scan and the query is doing far more work than it needed. The same deepest-large-ratio-node diagnostic finds it.

Trade-off

EXPLAIN ANALYZE in the review template versus in production. The condition that flips it: EXPLAIN ANALYZE executes the query, so on a write statement or a LIMIT-truncated one it has side effects and timings. Safe form is a transaction you roll back, or EXPLAIN alone for planning review and ANALYZE only in staging.

Statistics and the optimiser

Every estimate in a plan comes from four numbers per column. Knowing which four, and which one nobody looks at, is most of what “why did the planner do that” actually requires.

The four statistics that determine every row estimate
Statistic Answers Watch for
Row counthow many rows the relation hasstale after a bulk load; the planner's most-used number
ndistincthow many distinct values0 means unique — it is a flag, not a count

SELECT attname, n_distinct, correlation, most_common_freqs
  FROM pg_stats
 WHERE tablename = 'orders'
   AND attname IN ('region','status','created_at');

   attname     | n_distinct | correlation | most_common_freqs
  -------------+------------+-------------+----------------------
   region      |        140 |      -0.42  | {0.31,0.28,0.14,...}
   status      |          6 |       0.03  | {0.62,0.11,0.09,...}
   created_at  |          0 |       0.998 | {}
  -- region: 140 values, correlation -0.42. A range predicate on it reads
  --   hundreds of scattered pages. There is no index. Genuine problem.
  -- status: 62% in one bucket. The planner knows, which is why indexing
  --   status does not help a 60%-matching query.
  -- created_at: correlation 0.998 = physically ordered, so a "last 7 days"
  --   predicate reads a contiguous tail. The planner knows. Do not index.

ANALYZE does not read the table — it samples it, and the sample size is the accuracy limit for everything downstream. The default is 300 × default_statistics_target = 30,000 rows, which on a 40M-row table is a 0.075% sample. Raising the target to 1000 gives a 300,000-row sample.

Scaling reality check

A table that has never been ANALYZEd gets the fallback assumption of 200 distinct values for every column, and a uniform distribution. That is the origin of the “planner is stupid” anecdote: it is not wrong, it is answering with the only number it was given. The condition that flips it — if the fallback is fine, the table is small enough that 30,000 rows is most of it.

Interview trap

ANALYZE fixes stale statistics and nothing else. The volume is explicit that the 590× join error survives it, because the data is measured accurately and interpreted incorrectly. Re-running ANALYZE against an independence assumption is treating the symptom; extended statistics are the fix.

Extended statistics: declaring the correlation

-- 99% of active customers are in 3 countries. The planner multiplies
-- the two selectivities and gets an answer 590x too small.
CREATE STATISTICS stat_customer_country_active
    (dependencies, ndistinct, mcv)
    ON country_id, active
    FROM customers;

ANALYZE customers;

dependencies is the 590× fix: it declares a functional dependency (a → b) and switches the estimator from multiplying two independent selectivities to using the MCV list of pairs. ndistinct fixes selectivity for multi-column GROUP BY, where the planner otherwise sums the per-column distinct counts and over-counts when the columns are correlated. mcv supplies a real multi-column most-common-values list, which is what makes the other two accurate on skewed data — without it, dependencies only helps for pairs where one functionally determines the other.

Interview trap

CREATE STATISTICS is per-table. It cannot express that orders.customer_id and customers.id are related, so the estimator still assumes independence across the join — which is the most common source of a catastrophic join cardinality estimate, and the one extended statistics cannot reach. Saying so is the mark of someone who has read the documentation rather than the blog post.

Parameter sniffing: a cached plan is a bet

A prepared statement's plan is chosen from the first few executions and applied to all the rest. Any parameter whose distribution is skewed relative to those first calls is a live grenade, and the failure is one staging can never reproduce.

SELECT * FROM pg_prepared_statements;

PREPARE q AS SELECT * FROM orders WHERE region = $1;
EXECUTE q('EU');      -- 0.41 ms    Index Scan
EXECUTE q('APAC');    -- 29,184 ms Seq Scan, the same plan for both
EXECUTE q('LATAM');   -- 29,184 ms and 292 MB read, for the 10th tenant

-- force custom plans, always
SET plan_cache_mode = force_custom_plan;

-- or make the generic plan safe by declaring the distribution
CREATE STATISTICS (dependencies, ndistinct) ON region, status FROM orders;

The mechanism, with numbers: region is EU 1.1%, US 8.2%, APAC 0.6%, LATAM 0.05%. The first five callers were the US dashboard, so the planner costed a custom plan at 1,918.44 against a generic plan at 2,091.03. The ratio is 1.09, which is under the generic_plan_cost_ratio of 1.10, so the generic plan was adopted. Every subsequent tenant, including one 0.05% of the table, got the scan designed for the common case.

Interview trap

How narrow the margin was: had the first five callers been the EU dashboard instead, the ratio would have been 1,043.19/892.10 = 1.17, the generic plan would not have been adopted, and none of this would have happened. The production bug was decided by a 0.01 difference in a cost ratio and by which user clicked first. That is why “we tested it in staging” is not evidence here: staging has 30,000 rows, one tenant, and the same value every time, so every plan is trivially correct.

Trade-off

Cached plans save planning time; custom plans re-plan every execution. The condition that flips it: when the parameter's distribution is stable, caching is free and worth it; when it is skewed across tenants, regions or tenants-of-tenants, the generic plan is a bet that pays 164× on the median tenant and loses 29 seconds on the tail. The engine-level equivalents are SQL Server's OPTION (RECOMPILE) and Oracle's adaptive cursor sharing — the same decision with different names.

 

Numbers worth memorising

8152 / 16 = 509 Usable bytes per 8 kB page divided by the int8 key width — the fan-out that makes height 3
3 Height of a 10M-row int8 B+ tree: root, 39 level-1 pages, 19,646 leaves
3 page reads The floor for any seek: root, internal node, leaf — before a single heap fetch
0.64% / 2.6% Break-even match rate, spinning media / NVMe. Below it the sequential scan is correct
234 / 9,360 Table size below which the planner prefers a scan: NVMe / spinning — a 40× spread
~25% Match rate at which an index scan gives way to a bitmap heap scan (or an index-only scan, if covering)
4.0 → 1.1 random_page_cost: the default is 4× too high for NVMe and 4× too low for network storage
25,000 Outer rows at which a nested loop over a 1.2M-row inner stops winning
178 days A 10M-row outer over a sequential 1.2M inner: 3.08×1011 reads at 200 IOPS
4 MB Default work_mem, per sort or hash node, per connection
30,000 rows ANALYZE sample: 300 × default_statistics_target of 100
200 Distinct values assumed for a column on a table that has never been ANALYZEd
16 B / 128 blocks BRIN: one summary entry per 128 pages — 32 KB against a 2 GB heap
13 page writes Per inserted row on a table with 12 indexes; 130,000/second at 10k inserts/sec
5 executions, 1.10 Custom plans before a generic plan is adopted, and the cost-ratio threshold that decides it

Two of these deserve their emphasis restated once more. 509 is not a number to memorise for its own sake — it is the input to height, and height is what a seek costs. 25,000 is the join crossover, and quoting it is what separates “nested loops are bad” from an answer.
