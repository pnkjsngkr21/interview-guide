If you only remember five things

  1. One connection is one forked OS process. max_connections (default 100) is a refusal ceiling, not a target. The capacity number is the multiplication — per-connection baseline plus work_mem per plan node per parallel worker per concurrent query — and its failure mode is the OOM killer choosing an innocent backend, not a clean error.
  2. One long-running transaction stops every vacuum in the cluster. A backend publishes backend_xmin; the minimum across the cluster is the horizon, and a dead tuple cannot be reclaimed until the horizon passes it. The holder is almost always idle in transaction, and idle_in_transaction_session_timeout defaults to 0.
  3. REPEATABLE READ in PostgreSQL is snapshot isolation. One snapshot for the transaction's whole life, no gap locks, so read skew survives it. SERIALIZABLE is SSI — optimistic, predicate-lock-tracked, and it aborts a participant at COMMIT with 40001, which you retry by re-running the whole transaction with backoff and jitter.
  4. work_mem is a per-node limit, not a per-query budget. The response to a spill is an index that removes the sort, then SET LOCAL work_mem for the one measured transaction — never a global change, whose worst case scales with connections and query concurrency.
  5. Autovacuum frees space for reuse inside the file; it does not return it. Only VACUUM FULL, CLUSTER or pg_repack shrink the file, and index bloat is a REINDEX problem rather than a VACUUM one.

01

Process model & connections

The mental model almost everyone carries — a listening socket, a thread pool, a shared heap — is wrong in a consequential way. PostgreSQL is a process manager: the postmaster fork()s one backend per connection, that backend handles that connection for its whole life, and it exits when the client disconnects. There is no pool and no work stealing. The price is paid in process creation, per-process memory, and the absence of in-query parallelism unless parallel workers are requested.

Interview trap — how many connections can PostgreSQL handle?

“Hundreds, or a thousand — it's lightweight and fully concurrent” is wrong in the way that matters. max_connections (default 100) is a hard ceiling the postmaster enforces by FATAL: sorry, too many clients already. It is not a performance target, and PostgreSQL does not get more efficient per connection as you add them — past the cache-warm point the marginal connection costs more than it returns. The real number is max_connections × per-connection baseline plus concurrent queries × plan nodes × work_mem × parallel workers.

Trade-off — transaction pooling, and its breakage is quiet

Transaction mode is the right default because it is the only mode that reduces the server-side count, and on any real deployment the count is the binding constraint. What makes it a decision is that every failure mode is silent: a leaked SET is a cross-tenant data leak in a schema-per-tenant design with no error; a leaked session advisory lock is a job that never runs again; a LISTEN that never receives its notification is a missing update. Flips on: the application genuinely needs session state — then transaction mode is wrong and the answer is session mode with a properly sized server-side pool. The review check that catches it is a grep for SET outside a transaction block.

Must remember — the worker pool is one budget

max_worker_processes is the total cluster-wide pool that autovacuum workers, logical replication workers, parallel query workers and extension background workers all draw from; autovacuum_max_workers (default 3) and max_wal_senders (default 10) are sub-caps. The arithmetic that catches teams out: 3 autovacuum + 2 logical replication + 8 parallel workers exceeds a max_worker_processes of 8, and nothing complains. The symptom is a Gather node with fewer children than the GUC suggests — no error — and autovacuum falling further behind schedule. Autovacuum is the consumer whose shortfall is silent and cumulative, so adding an analytics feed can bloat an unrelated table.

Connection churn is not a connection count

A service that opens a database connection per HTTP request never hits max_connections — it drives the postmaster's fork() rate. On Linux with a large shared_buffers segment the page-table copy dominates the fork cost, so a fork storm degrades every connection's latency while each individual query still looks fast. A sawtooth of very short-lived sessions in pg_stat_database.numbackends is churn; a flat line at a high value is a real count problem, and the two have different fixes.

-- lifetime, not count: sample this repeatedly
SELECT count(*) AS backends,
       min(backend_start) AS oldest,
       max(backend_start) AS newest
FROM   pg_stat_activity
WHERE  backend_type = 'client backend';

-- what each connection is actually doing
SELECT application_name, client_addr, state, count(*)
FROM   pg_stat_activity
GROUP  BY 1, 2, 3
ORDER  BY 4 DESC;

The connection question and the memory question are one question. Roughly 2–5 MB of private baseline per backend is resident whether or not the connection is running anything, shared_buffers (default 128 MB) is mapped by all of them and is therefore not per-connection, and the unbounded term is work_mem. Setting statement_timeout (default 0, off) is one of the cheapest reliability improvements available on any PostgreSQL installation, and its absence is why a bad deploy becomes an outage rather than an error message.

02

Storage: pages, heap files & TOAST

A PostgreSQL page is 8 kB and BLCKSZ is compiled in — you cannot configure it. It is slotted: a fixed 24-byte header, tuples growing upward from pd_lower, 4-byte line pointers growing downward from pd_upper, free space in the middle. Three properties of that layout do the explaining work, and all three are things candidates get wrong under pressure.

Must remember — the one fact about PostgreSQL storage

A row's cost is a function of the largest the row ever was, not what it is now. Updates never move a tuple, so a column that once held a multi-megabyte document shaped the page it lived on; shrinking the value leaves a hole that nothing reclaims in place. Diagnose with pgstattuple, and note that a table's relation size and its steady-state page count drift apart for exactly this reason. The fix for the shape is a rewrite — pg_repack, or VACUUM FULL under lock — never VACUUM alone.

Interview trap — ctid and VACUUM

A ctid is a (block, offset) pair: a location, not an identity. It is not a primary key, it is not stable, and it changes whenever an update's new version lands on another page. Using it as a row identifier is a category error; using it as a correlation identifier inside one statement is legitimate. The second half of the trap is that VACUUM does not compact a heap and does not shrink the file — it marks space reusable through the free space map so later inserts can use it.

Interview trap — a table of huge rows that scans fast

A row over roughly 2 kB is compressed, and if still over the threshold moved out of line into a TOAST relation, leaving a pointer in the heap. TOAST is lazy in the direction that matters: SELECT id FROM documents over a table of multi-megagraph documents never dereferences the pointer and does no chunk I/O, while SELECT id, body costs a random chunk read per returned row. The same table is fast for one query and unusable for another with no schema difference — and the team that never selects the column never opens the ticket.

03

MVCC & the vacuum horizon

There is no separate version store. Every row carries its own concurrency metadata in its first 23 bytes, and an UPDATE writes a second copy of the row and redirects the old version's t_ctid at it. Committed-ness is not in the tuple at all: it is recorded once in shared memory and the infomask hint bit is set lazily, the next time any backend touches the page — a cheap design that makes hot pages a contention point. MVCC as theory is 05 — Transactions; what follows is the implementation, and the implementation is where the incidents live.

Interview trap — a long transaction blocks autovacuum for the whole cluster

Not the whole database. Every backend publishes backend_xmin, and the cluster-wide minimum is the horizon autovacuum must respect: a dead tuple cannot be reclaimed until it can prove no running snapshot anywhere can still see it. A REPEATABLE READ transaction sitting in a psql prompt on db3 pins dead tuples in db1 indefinitely, and the symptom is not a lock — nothing is blocked, pg_blocking_pids() returns nothing, latency is normal. Tables simply will not shrink. The three holders of the horizon are long transactions, inactive replication slots, and prepared transactions; the last two are invisible in pg_stat_activity and pin everything forever.

-- the query that finds the incident: the oldest published xmin in the cluster
SELECT pid, datname, application_name, client_addr, state,
       now() - xact_start  AS xact_age,
       backend_xmin,
       left(query, 100)     AS last_query
FROM   pg_stat_activity
WHERE  backend_xmin IS NOT NULL
ORDER  BY xact_start;

-- the two holders nobody thinks of. Both pin the horizon indefinitely.
SELECT slot_name, active, wal_status,
       age(now() - xmin)         AS xmin_age,
       age(now() - catalog_xmin) AS catalog_xmin_age
FROM   pg_replication_slots;
SELECT gid, prepared, now() - prepared AS age FROM pg_prepared_xacts;
Scaling reality check — what 20 million dead tuples cost

Autovacuum's trigger is autovacuum_vacuum_threshold (default 50) plus autovacuum_vacuum_scale_factor (default 0.2) times live tuples. On a 100-million-row table churning 20%, the trigger is 50 + 20,000,000 = 20,000,050 and the table sits 50 rows under the bar. Those 20 million dead versions are roughly 6 GB of heap on a ~40 GB table, and every one of them is a version a scan must walk past — the table is simultaneously using more disk and answering more slowly, which is what makes it hard to believe it is the same problem. On a hot table, override the scale factor per table rather than arguing with the global one.

HOT updates: both conditions must hold, and each has a different fix

-- the number to watch: it tells you WHICH condition is failing
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM   pg_stat_user_tables
WHERE  n_tup_upd > 10000
ORDER  BY hot_pct;

-- buy the room the update needs, then verify after a rewrite
ALTER TABLE events SET (fillfactor = 80);
Must remember — the escalation path from one idle session

The horizon that starves vacuum is the same horizon that gates the freeze, so a long transaction escalates from "the table is bloated" to "the database refuses all writes". The transaction id space is 32-bit — about 4.29 billion ids — and once the distance between the current id and the oldest unfrozen id stops fitting in a signed 32-bit difference, ids can repeat and a committed row's xmin could be reused. PostgreSQL protects the database by failing writes on purpose. The diagnostic is SELECT datname, age(datfrozenxid) FROM pg_database; the prevention is idle_in_transaction_session_timeout, because a pooler that hands a connection back mid-transaction is the same bug wearing a different hat.

04

Types, JSONB & extensions

PostgreSQL's type system is an extensible framework, and the practical consequence is that much of what people call a "PostgreSQL feature" is a plugin. Constraint DDL and the general type-storage question belong to 02 — DDL & Constraints; what belongs here is the handful of type choices that generate real incidents, and jsonb, which behaves like an extension in the ways that cost money.

  • numeric is exact, variable-width, and does its arithmetic in software — correct and slow. float8 is never correct for money; bigint in minor units is correct and fast; money is locale-dependent in both output and input parsing, which makes bulk imports fragile, and should not be used at all.
  • timestamptz stores an absolute instant and renders it in the session's TimeZone; timestamp stores a wall-clock value with no zone, so one stored value means different instants for different readers and nothing errors. Where a business zone matters, store timestamptz plus a separate IANA zone-name column — a single instant rendered locally is not the same as a local wall-clock time, the classic 23:30 case.
  • uuidv7() (PostgreSQL 18) is time-ordered and therefore a far better B-tree key than the random uuidv4(), whose every insert is a random write across the index. There are no unsigned integer types, so there is no MySQL int unsigned overflow behaviour to reason about; bigint is 8 bytes.

Trade-off — when is jsonb the right answer?

jsonb is right when the shape is genuinely not yet known, the attributes are sparse and per-entity, and the read pattern is "fetch the document" plus occasional containment. Flips to real columns the moment attributes are queried by name across many rows, participate in joins, need a foreign key, or need a NOT NULL or CHECK — none of which jsonb provides without a trigger or a hand-written expression index, and joins against jsonb keys are unnests rather than hash joins. The frame that survives a design review: flexibility is only valuable while you are still discovering the shape. A column adopted for flexibility, given a second query with a computed key, given a GIN index to compensate, and then promoted to real columns is a healthy evolution; a blob with a query interface after two years is not.

Interview trap — a GIN index that is silently never used

The opclass is chosen when the index is created and nothing enforces it later. jsonb_path_ops is significantly smaller and faster because it indexes only @> containment; a ?, ?| or ?& key-existence query needs the default jsonb_ops. A jsonb_path_ops index queried with ? produces a sequential scan with no error and no warning — the most common GIN mistake in real schemas. Write down which operators the index is meant to serve, and remember that SELECT payload reads and decomposes every matching row regardless of any index, so its cost scales with the size of the result rather than with selectivity.

SELECT payload @> '{"type":"purchase","currency":"EUR"}';   -- containment
SELECT payload ?  'user_id';                              -- key exists
SELECT jsonb_path_exists(payload, '$.items[*].sku');     -- SQL/JSON path, 12+

-- the containment index: only @> is served, and it is the smaller one
CREATE INDEX events_payload_gin ON events USING gin (payload jsonb_path_ops);

-- the key-existence query needs the default opclass, or it does not use the index
CREATE INDEX events_payload_ops ON events USING gin (payload jsonb_ops);

-- a single-key lookup is usually better served by a small B-tree, not by any GIN
CREATE INDEX ON events (((payload ->> 'user_id')::bigint));

-- if the churn is concentrated, a partial GIN keeps the read benefit and drops the write cost
CREATE INDEX ON events USING gin (payload) WHERE NOT archived;
Must remember — what an extension can and cannot do

An extension can add a data type and its operators, an index access method with its own search structure (PostGIS's GiST and SP-GiST, pgvector's HNSW and IVFFlat), functions, aggregates, casts, procedural languages, and a background worker. It can never change the process model or connection semantics, MVCC, the visibility rule or version chains, WAL or commit behaviour, or how SERIALIZABLE detects conflicts. Those are not features the engine exposes — they are the engine. Since PostgreSQL 13 extensions are also trusted or untrusted, and the trusted list grows between major versions, so a migration that hard-fails on insufficient privilege can succeed after an upgrade with no permission change at all.

The constraint beats the isolation level

Whenever someone proposes SERIALIZABLE, the first question is whether the invariant can be a constraint. EXCLUDE USING gist (room_id WITH =, during WITH &&) states "no two bookings overlap" declaratively, is enforced for every writer including ones nobody audited, needs no retry loop, and cannot be bypassed by a code path that forgets a check — the alternative, checking for an overlap and then inserting, is exactly the read-modify-write pattern SSI exists to abort. It needs btree_gist, because GiST does not support equality on ordinary scalars by itself, and adding one to a large table needs NOT VALID plus a separate validation step.

05

SQL dialect depth

The register throughout this volume is that an answer that does not name the version is not an answer, because several of the things candidates are most confidently wrong about changed in a specific release. Join semantics, window frames, LATERAL and WITH ORDINALITY as query language are 03 — Queries & Joins; what follows is where this dialect is meaningfully richer than the standard.

Interview trap — "PostgreSQL materialises CTEs"

That describes version 11 and earlier. From PostgreSQL 12 a non-recursive CTE with no side effects is inlined: the planner substitutes it into the referencing query exactly as if you had written the subquery, so predicates push down and join order is chosen globally. The exception that must be stated with the claim is that recursive CTEs are always materialised, in every version, because the working table is inherent to the algorithm. Both behaviours remain available on demand with MATERIALIZED and NOT MATERIALIZED, and MATERIALIZED is the right tool when a CTE genuinely must be computed once or calls a volatile function.

-- PostgreSQL 12+: a non-recursive CTE with no side effects is INLINED.
-- Recursive CTEs are ALWAYS materialised, in every version.
WITH recent AS (
    SELECT * FROM orders WHERE placed_at > now() - interval '30 days'
)
SELECT customer_id, count(*) FROM recent GROUP BY customer_id;

WITH cached AS MATERIALIZED     ( SELECT ... )   -- the pre-12 optimisation fence
WITH fresh  AS NOT MATERIALIZED ( SELECT ... )   -- force inlining

-- DISTINCT ON: ORDER BY must LEAD with the DISTINCT ON expressions.
SELECT DISTINCT ON (customer_id) customer_id, id, placed_at, total
FROM   orders
ORDER  BY customer_id, placed_at DESC;   -- not: placed_at DESC, customer_id

-- ON CONFLICT against a PARTIAL index must repeat the index's predicate.
INSERT INTO events (id, kind) VALUES (1, 'a')
ON CONFLICT (id) WHERE archived DO NOTHING;

-- RETURNING works on INSERT, UPDATE, DELETE and MERGE: the identity comes
-- back without a second round trip.
INSERT INTO orders (customer_id, total) VALUES ($1, $2)
RETURNING id, created_at, total;
Interview trap — "cannot affect row a second time"

ON CONFLICT DO UPDATE and MERGE (15+) process source rows one at a time, and a single target row cannot be updated twice within one statement. The real problem is upstream: the source has a fan-out — a join through a one-to-many relationship, or a source that was never deduplicated — so one target row matches three source rows. This is a statement about what the operation means, not a bug. Handle it in the source relation, where it is visible, with a GROUP BY or DISTINCT ON; discovering it as an error inside the merge is the expensive version. The same class also rules out the older COUNT(*) FILTER (WHERE ...)-style idioms' cousins: the MERGE decision is not “is it supported” but “does the source fan out”.

Scaling reality check — a one-line migration is a multi-hour project

ALTER TABLE t ADD COLUMN c jsonb with no DEFAULT is catalog-only: absence of a value is recorded in the null bitmap rather than rewriting 200 million rows. Adding a DEFAULT was the dangerous version on older releases, since a non-volatile default was a full rewrite under lock; since 11 setting one avoids it. The backfill is where the real cost hides: a single UPDATE of 200 million rows is one enormous transaction that holds the vacuum horizon for its entire duration and starves autovacuum for the whole cluster while it runs. Batch it, commit between batches, and accept a window where some rows have the value and some do not. The review question is “what locks does this take and for how long”, not “is the syntax correct”.

06

Indexes & the planner

Choosing between access methods is a bigger lever than choosing columns, because they are genuinely different structures with different failure modes. The B+ tree, leftmost prefix and how to read a plan are owned by 04 — Indexes & Planning; what is here is PostgreSQL's own surface — the six access methods, the three index options that have no direct equivalent elsewhere, and the planner's arithmetic.

Must remember — Heap Fetches is a vacuum signal

An index-only scan is pure only while every heap page in its range is ALL_VISIBLE in the visibility map. VACUUM sets those bits; any update to any row on the page clears them. So a scan that was Heap Fetches: 0 and is now fetching millions of times has not changed its index definition — it has lost the invariant, almost always because a long transaction is stopping vacuum. The node still reads Index Only Scan; if it had become Index Scan instead, the cause would be a query change adding a column the index does not contain, which is a different problem. Adding more columns to the INCLUDE list will not help at all.

Trade-off — covering indexes, and the ratio that decays

INCLUDE earns its place when a query is frequent, reads few rows, and needs columns that are not in the key. It becomes a liability in three specific ways: write amplification, because included columns sit in every leaf entry and are not deduplicated the way key columns are; silent decay, because on an update-heavy table the value falls toward zero as the visibility map goes stale while the write cost stays constant — the worst possible ratio; and design temptation, because including every column a query might want turns the index into a second copy of the table, and the answer to "this query needs six columns" is often to fix the query. Flips on: read-mostly tables and partitioned schemas where the hot table is separated from the cold one. Put filtering and ordering columns in the key, where they can seek; included columns are payload and cannot appear in an index predicate or an ordering.

Interview trap — partial indexes expire silently

A partial index encodes an assumption about selectivity, not just about a predicate — and selectivity is what a growing business changes without telling you. An index built when status = 'open' matched 2% of rows and matching 71% today is still correct and now worse than useless: it feeds its own size into the planner's cost estimate, so the planner may pick an index scan that fetches most of the table in random order over a sequential scan that would read it in order. The metric to alert on is index size against predicate selectivity, not index size. The same trap has an expression-index form: an index on lower(email) is used by WHERE lower(email) = $1 and by nothing else — not by ILIKE, and not by WHERE email = lower($1).

Interview trap — enable_seqscan = off is a diagnostic, not a fix

It does not make the cost estimate correct; it removes the planner's ability to choose correctly, by making sequential scans look so expensive that it will index scan where scanning would be far faster. The query gets a plan that looks right and performs worse, and the underlying mis-estimate is still there, so the next data distribution change moves the cost back. It is session-scoped, so in a pooled-connection application it leaks onto unrelated queries. The legitimate sequence is narrow: set it, confirm the plan changed and the query got faster, and conclude that the row estimate for that node is wrong — then go and fix the estimate with ANALYZE, default_statistics_target, CREATE STATISTICS and calibrated random_page_cost / effective_cache_size.

Those four repairs are exhaustive, and which one applies is decided by finding the lowest node in the plan where rows= and actual rows= differ by more than an order of magnitude — every node above it is a consequence rather than a cause. Stale statistics, insufficient statistics, a correlation the planner's independence assumption cannot represent, or a hardware assumption that does not match the machine. Extended statistics are the most under-used feature in the whole subject: CREATE STATISTICS s (dependencies, ndistinct) ON status, customer_id FROM orders; fixes the case where two predicates on columns that move together multiply to an estimate that is off by orders of magnitude, and no amount of re-ANALYZE helps because the problem is the model, not the sample.

The two lines people skip, and the spill arithmetic

temp read=40218 written=40218 is roughly 314 MB of temporary file written and read back, and it dominates the 812 ms runtime — a node exceeded its work_mem allocation. work_mem defaults to 4 MB and is a limit per node, so that plan authorised it four times over, with the hash node scaled again by hash_mem_multiplier (default 2.0, PostgreSQL 16+); four parallel workers each ran their own copy, and every concurrent query on the connection multiplied it again. The fix in order: eliminate the operation — a composite index on (status, placed_at DESC) satisfies both the filter and the ordering, so the planner reads 50 index entries in order and stops, with no sort and no memory exposure at all; then SET LOCAL work_mem for the one measured transaction; then a per-role override with the multiplication done for the expected concurrency; and never a global change. Sort Method: quicksort Memory: 25kB is the same problem one input row away — a cliff, not a slope.

07

Isolation, SSI & locking

The anomalies, the four levels as theory, and what write skew is are owned by 05 — Transactions. What follows is what PostgreSQL actually does, and two of its properties surprise almost every candidate: REPEATABLE READ is not lock-based, and SERIALIZABLE can abort a transaction after every statement in it has succeeded.

The four levels as PostgreSQL implements them
LevelImplementationPrevents
READ UNCOMMITTEDTreated as READ COMMITTED — the name is a fictionNothing. A dirty read is not something you can do here at all
READ COMMITTED (default)A new snapshot per statementDirty reads. A read-modify-write inside it can interleave
REPEATABLE READA single snapshot for the transaction's whole life; no gap or predicate locksDirty reads and non-repeatable reads. Not phantoms, and not read skew
SERIALIZABLESnapshot isolation plus SSI — optimistic, predicate-lock trackedAll four, by aborting one participant at commit
Interview trap — 40001 at COMMIT is the mechanism working

It is not a bug and not data loss: SERIALIZABLE is SSI, not a locking protocol, and refusing to let an unserialisable outcome stand is the entire point of the level. The application must retry the entire transaction from the first statement, with bounded attempts and exponential backoff plus jitter, because it is the reads that determined the outcome and re-running only the last statement is meaningless. 40P01 (deadlock) belongs in the same handler. Before building the loop, ask whether the invariant can be a CHECK, a unique index, or an EXCLUDE USING gist — a constraint needs no retry, covers write paths nobody audited, and is not exposed to a transaction containing a non-idempotent side effect. A retry loop is a liability when the transaction also calls an external API.

Interview trap — REPEATABLE READ does not stop read skew

It gives one consistent snapshot for the transaction's whole life, which is a strong guarantee, but the snapshot itself can be inconsistent with respect to transactions that committed while it ran. Take the two-way bank check: T1 reads A and B and passes “A ≥ 50”; T2 reads B and A and passes “B ≥ 50”; both debit and both commit with an overdraft, because each snapshot excludes the other's commit. The reason is structural: preventing read skew classically requires gap locks or predicate locks held for the duration, and PostgreSQL takes neither — it relies on MVCC. So a REPEATABLE READ transaction is the wrong tool for a multi-table consistency check, which is the intuition most people carry from engines with lock-based REPEATABLE READ. The same snapshot explains an intermittent reporting discrepancy: a deterministic one is a grain mismatch; one that varies between runs is read skew, and the long transaction causing it is probably the same one starving vacuum.

Locking clauses: FOR NO KEY UPDATE is the under-used default
ClauseLocksUse for
FOR UPDATEExclusive, conflicts with everythingRead-modify-write on the row's value, when the decision cannot be one statement
FOR NO KEY UPDATEExclusive but weaker — does not conflict with FOR KEY SHAREThe right default for application updates. It leaves concurrent foreign-key checks alone
FOR SHAREShared“Read now, ensure it does not change.” Many concurrent holders become a multixact, which vacuum must resolve before the row can go
FOR KEY SHAREWeaker shared; never blocks a non-key updateWhat foreign-key checks take — a single id fits in xmax, so no multixact
NOWAIT—Fail immediately rather than block; converts unbounded request latency into a handleable error
SKIP LOCKED—Work queues: take only what nobody else holds

Interview trap — zero rows is not a terminal answer

Under READ COMMITTED, when FOR UPDATE finds a row updated by a transaction that has since committed, it follows the update and re-evaluates the WHERE clause against the new version, silently skipping the row if it no longer matches. The guarantee is “I have locked a row that currently matches”, not “the row I saw”. Under REPEATABLE READ the same query raises could not serialize access due to concurrent update instead of returning nothing. Any code that treats “no rows” as terminal is wrong under the default isolation level, and the fix is a loop plus a WHERE clause that carries the state the caller needs. Related: a row lock is a t_xmax, so waiting for a row is waiting for a transaction — which is why pg_locks shows you transactionid and virtualxid rather than anything named after your table, and why pg_blocking_pids() is the query to have ready.

-- T1                                    T2
BEGIN;                                   BEGIN;
SELECT count(*) FROM seats              SELECT count(*) FROM seats
WHERE show_id = 1 AND sold = false;  -- 200    -- 200   same snapshot view
UPDATE seats SET sold = true            UPDATE seats SET sold = true
WHERE show_id = 1 AND seat_no <= 100; WHERE show_id = 1 AND seat_no BETWEEN 101 AND 300;
-- 100 rows                               -- 200 rows
COMMIT;                                   COMMIT;
-- SUCCEEDS                               -- ABORTED: 40001. Retry the WHOLE transaction.

-- Work queue: 12 workers, no coordination.
BEGIN;
SELECT id, payload FROM jobs
WHERE   status = 'pending'
ORDER   BY priority DESC, created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- do the work HERE, inside this transaction
UPDATE jobs SET status = 'done' WHERE id = $1;
COMMIT;
Trade-off — the work queue, and its two hidden costs

The work belongs inside the claiming transaction, so the lock that guarantees exclusivity is held throughout; a dead worker then rolls the claim back and the job returns to the queue. That is at-least-once delivery, which means the system genuinely cannot know whether the side effect landed before the crash — so every job must be idempotent, with the key recorded in the same transaction as the effect. The cost of doing it right is that the transaction is open for the length of the job, and that is this page's own failure mode: a 40-minute video transcode holding a transaction open pins the cluster's vacuum horizon for 40 minutes. Flips on genuinely long work, which needs a claimed_at timestamp with a visibility timeout plus a sweep that requeues stale running rows. Teams routinely ship the first of these three elements and not the other two.

Advisory locks are the fourth primitive and the easiest to misuse. Prefer the transaction-scoped variants always: pg_advisory_xact_lock(hashtext('monthly-close')) is released automatically at commit or rollback and cannot leak, whereas pg_advisory_lock is session-scoped and in a pooled connection is released only by an explicit unlock — skipped on every error path, every crash, and every connection the pool retires. The next request to borrow that connection holds a lock nobody can see and the job never runs again. Always namespace the key, because a bare 42 lives in a global space shared with every other subsystem and nothing in the code says what it protects. For exactly-once work that must survive a crashed worker, the third option is neither: a lease row with (owner, expires_at) claimed by a conditional UPDATE ... WHERE expires_at < now() — survives a crash because it expires, works across a failover, and is visible in ordinary table queries.

PostgreSQL detects deadlocks and breaks them by aborting one participant with 40P01 after deadlock_timeout (default 1 second) of waiting — which is why the symptom is usually reported as “the database hung”. A deadlock is always an inconsistent lock order: acquiring in whatever order the application happens to touch rows, different entry points beginning at different tables, or FOR UPDATE over a row set with no ORDER BY, so the order the executor returns is not guaranteed stable. Sort the ids and lock them in that order, every time. Three settings turn an opaque incident into a diagnosable one: log_lock_waits = on, deadlock_timeout lowered to a few hundred milliseconds, and lock_timeout set per role — which is nearly always better than a request hanging for as long as the blocking transaction lives.

08

Autovacuum, bloat & the operational surface

Almost every autovacuum incident reduces to one misunderstanding: autovacuum reclaims space for reuse inside the file, but it does not return it to the operating system. That single fact explains VACUUM FULL, pg_repack, and most of “the table is 400 GB and only 2 GB of it is data”. The launcher wakes every autovacuum_naptime (default 60s), works out which tables exceed their thresholds, and hands each to one of autovacuum_max_workers (default 3) workers — shared across the whole cluster, so three tables vacuum concurrently and everything else waits.

The trigger, and the three things that stop it

That trigger is per-table, and a churn-heavy table will always outrun the cluster-wide default: autovacuum_vacuum_scale_factor = 0.02 on that one table is the single highest-value knob in this section.

Vacuum and bloat symptoms, in the order the volume reports them
SymptomCauseFix
Table will not shrink; df shows the file at its high-water mark Mass DELETE/UPDATE. VACUUM makes dead space reusable inside the file and never truncates it Delete in batches so each pass keeps up, drop the scale factor on that table, then pg_repack in a window
No autovacuum runs at all; last_autovacuum is days old A long transaction — usually idle in transaction — publishing an old backend_xmin Rank pg_stat_activity by xact_start, kill it, and set idle_in_transaction_session_timeout off its default of 0
Vacuum runs and finishes; the table still will not shrink An inactive replication slot or a prepared transaction holding the horizon — neither visible in pg_stat_activity Check pg_replication_slots and pg_prepared_xacts; drop the slot, then COMMIT PREPARED or ROLLBACK PREPARED
An index-only scan loses Heap Fetches: 0 and gets slower, with nothing changed Autovacuum has not set the visibility-map bits, and any update to any row on a page clears them Fix the starvation, not the plan — the plan was always correct — then REINDEX if the index itself has bloated
Writes fail with ENOSPC Usually the first row, discovered late. Occasionally the anti-wraparound pass is urgent and cannot finish while the horizon is pinned Free disk to get the database writable first; then fix the horizon. Verify with df and pgstattuple, not with a guess
Reads fine, every write refused The transaction-ID wraparound write stop, and it was coming for a long time Emergency sequence: stop the app, terminate old backends, drop abandoned slots, resolve prepared xacts, VACUUM FREEZE, resume
Must remember — two of the three horizon holders are invisible

Ask “what is holding the xmin horizon?” and the reflex answer is pg_stat_activity, which finds one of the three. A replication slot abandoned when a subscriber was decommissioned, without pg_drop_replication_slot, and a PREPARE TRANSACTION that was never committed are both absent from pg_stat_activity and both pin everything indefinitely. A prepared transaction is visible only in pg_prepared_xacts; the slot in pg_replication_slots, with its xmin_age and catalog_xmin_age. Put all three on the same dashboard; the two silent ones are the ones that survive a restart.

Getting the space back

Diagnose before repairing, and in this order — pgstattuple for authoritative free-space numbers, pg_stat_user_tables for live versus dead, df to confirm the file is actually the size you think — then repair.

The bloat repair ladder, cheapest first
OperationWhat it actually doesWhat it costs on a live system
VACUUM Marks dead space reusable inside the file Cheap and non-blocking, and the file never shrinks. Index free space is reclaimed at one cycle per pass and never below the high-water mark
REINDEX INDEX CONCURRENTLY Rebuilds an index into a new relation and swaps it in (PostgreSQL 12+) No ACCESS EXCLUSIVE lock. Longer, cannot run inside a transaction block, and needs a clean REINDEX if it fails. On a partitioned parent it rebuilds each partition (PostgreSQL 14+)
REINDEX on a GIN index The only thing that reclaims a pending list grown past gin_pending_list_limit (4 MB) Takes the lock. Check the pending-list size with pgstatginindex() first
pg_repack Rewrites the heap into a new relation, swaps, and drops the original The production default. Needs a PRIMARY KEY, roughly twice the table’s size free in disk, and a brief ACCESS EXCLUSIVE at the swap
VACUUM FULL / CLUSTER Rewrites the table and truncates the file ACCESS EXCLUSIVE for the whole duration — every read and write on that table blocks — plus about 2× the disk and 2× the time
Trade-off — VACUUM FULL against pg_repack

pg_repack is roughly 2× the disk and a maintenance window; VACUUM FULL is roughly 2× the disk, 2× the time, and every concurrent read and write on that one table blocked for the duration — a query pile-up that lands on a table nobody is repairing. Flips towards VACUUM FULL when the table is small enough that the lock is shorter than the repack, when pg_repack is not installed and cannot be, and when no usable PRIMARY KEY exists, because pg_repack cannot proceed without one. It also flips back: an ACCESS EXCLUSIVE that no one can wait behind during a trading window is worse than a stale high-water mark, and a file that is large but not yet hurting anyone should be left alone until it is.

Wraparound, and why the guard is not a guarantee

The 32-bit transaction-ID space is about 4.29 billion ids, consumed by every INSERT and UPDATE. After roughly two billion live transactions the distance between the current id and the oldest unfrozen id stops being representable as a signed 32-bit difference, and PostgreSQL protects the database by failing writes on purpose rather than allowing id reuse — reuse would make a committed row appear to have been written by something that never happened. A loud, total, obvious write outage is the recoverable failure; silent corruption is not. That is the design decision to be able to defend.

autovacuum_freeze_max_age (default 200,000,000) makes the anti-wraparound freeze pass urgent, and the write stop arrives near two billion — a factor of ten of headroom, deliberately, so operators have transaction throughput to notice. The failure of that design is not the threshold. It is that the guard only works if autovacuum is making progress, and autovacuum makes progress only if the horizon is moving, and the horizon is exactly what a long transaction, an abandoned slot, or a prepared transaction holds still.

Interview trap — the freeze guard does not make wraparound impossible

It makes the freeze pass urgent at 200 million, and urgent is not the same as achieved. The guard fires on a condition it cannot enforce: it cannot freeze a tuple a running snapshot might still read, so a database 250 million behind with one stuck transaction stays 250 million behind, logging that the anti-wraparound pass is urgent on every cycle, until it reaches the write stop and refuses all writes. age(datfrozenxid) that is not falling is the diagnostic — not its absolute value, which only tells you how late you already are. The emergency order is always the same: stop the application so nothing allocates new ids, terminate the old backends, drop abandoned slots, resolve prepared transactions, confirm age(datfrozenxid) is falling, then VACUUM FREEZE, and only then resume writes and fix what allowed the horizon to drift.

The operational surface

None of these is on by default, and all three should be on before they are needed.

# log every temp file, with its size
log_temp_files = 0

# log every autovacuum, so "why did it not run" is answerable
log_autovacuum_min_duration = 0

# make lock waits visible before they become an incident
log_lock_waits = on
log_checkpoints = on
log_min_duration_statement = 500

log_temp_files = 0 is the highest-value line in that list, and it is not close. A work_mem spill does not appear in pg_stat_statements as slow — the spill time is often amortised over a plan that looks cheap — and it raises no error. It appears as Buffers: temp read=... written=... in EXPLAIN (ANALYZE, BUFFERS) and nowhere else, unless you asked for it in advance. log_autovacuum_min_duration = 0 is what turns “vacuum stopped” from an archaeology exercise into a log line.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- total time, not mean time: the query that matters is not the
-- slowest one, it is the one eating the cluster's throughput
SELECT calls,
       round(total_exec_time::numeric, 0)  AS total_ms,
       round(mean_exec_time::numeric, 2)   AS mean_ms,
       shared_blks_hit + shared_blks_read  AS blks,
       round(100.0 * shared_blks_hit
             / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS hit_pct,
       left(query, 90) AS query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;

-- the temp-file spammers, ranked by bytes spilled
SELECT query, calls, temp_blks_written,
       pg_size_pretty(temp_blks_written * 8192::numeric) AS temp_written
FROM   pg_stat_statements
WHERE  temp_blks_written > 0
ORDER  BY temp_blks_written DESC
LIMIT  20;
Interview trap — resetting the statistics you are debugging with

pg_stat_statements_reset() exists, it is a single statement, and it is exactly what teams reach for when the numbers look wrong during an incident. It destroys the baseline that identified the incident — you have just deleted the ranked list of what was slow while the slowness is still happening. Snapshot the view into a scratch schema and diff two snapshots instead. Two neighbours matter for the same reason: auto_explain with log_nested_statements is how you capture the plan for a query that only misbehaves sometimes, and track_io_timing = on gives real per-checkpoint I/O timings at a measurable overhead, which is why it is off by default.

Two rules close the section. Alert on n_dead_tup / n_live_tup > 0.4 and on age(datfrozenxid) > 150,000,000, with pg_replication_slots and pg_prepared_xacts on the same dashboard. And set idle_in_transaction_session_timeout in a pooler or a role, not globally, to something like five minutes — it is the single best guard against every failure mode on this page, and its default is off.
