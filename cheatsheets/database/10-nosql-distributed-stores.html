If you only remember five things

  1. CAP is a per-operation claim made during a partition. A database is not "CP" or "AP" — the guarantee lives at the consistency level of a single statement. Partition tolerance is not a choice, so the only choice is C or A, made per operation and only while the partition lasts.
  2. The partition key is the design, and it is a commitment. It is simultaneously the unit of storage, of replication, of write throughput and the ceiling on query shape. Changing it is a data migration with a dual-write window, not a configuration change.
  3. Adding nodes does not fix a hot partition. Throughput scales per partition. A single key keeps its per-key ceiling however many nodes join, and adaptive capacity redistributes capacity across partitions without ever splitting one.
  4. In an LSM store a delete is a write. A tombstone is a row that must be read, compared and merged until gc_grace_seconds (10 days) passes — which is a resurrection-bug guard, not a tuning knob.
  5. "Schemaless" is a misnomer in both DynamoDB and MongoDB. You designed a key schema; you wrote it in the client instead of in DDL. What you gained is a new non-key attribute without a migration, and what you lost is the database telling you a client broke the contract.

01

Why relational stores stopped being the default

"We moved to NoSQL because relational databases don't scale" is four claims wearing one coat. The senior move is to take them apart, because three of the four have a cheaper answer that takes a sprint rather than a migration, and only one is a genuine architectural limit.

Which scale — and which engine actually fixes it
The scaleWhat it really isThe right answer
Write throughputA relational primary is a single writer by construction — one leader process, one WAL, one lock manager Distributed store. This is the one NoSQL genuinely fixed
Data volume per machineA 10 TB table on a 64 GB box — a working set that does not fit Partitioning. See 06 — Schema & Scaling
Read throughput, p99 latencyReads scale with replicas A read replica and a routing layer. Usually cheaper than a store change
Developer velocity"I want to store a JSON blob" — a schema problem in a platform costume A jsonb column, a GIN index, or a partial index

So the genuinely unsolvable-by-PostgreSQL case is narrow: write throughput exceeding what one process can push, on an append-mostly workload that is never joined. If a 30 GB database is "too slow", the working set fits in RAM and PostgreSQL will serve it faster than any distributed store serves it over the network; the honest question is what the write rate is and what one write costs, because a write whose SELECT sequential-scans is a bug, not a ceiling.

The four cost claims, and what each really costs you
ClaimTrue?The cost
Schema rigidityNarrower than it sounds ALTER TABLE ADD COLUMN nullable with no default is metadata-only in PostgreSQL and InnoDB. Changing the shape of an entity is a project — shadow table, batched backfill, dual-write window, cutover — in any store
Single-writer throughputYes, structurally Fixed by distribution, which buys you a partition key and a cross-shard query problem in exchange
Operational costUnderrated, and the real bill Replaced, not removed: compaction debt, repair windows, partition-key audits, capacity modelling — against the removed single-writer ceiling and the manual VACUUM

Trade-off — shard PostgreSQL, or move to Cassandra?

Both end up with a partition key and a cross-shard query problem; the difference is who owns the shard router and what the cross-shard query costs. Flips on: how many distinct query patterns exist and how many are cross-shard. Two or three, and you shard Postgres — Citis, or an application-level routing layer — and keep joins. Fifteen patterns including "everything for this user, every entity type, sorted by date", and a wide-column store where each pattern gets its own table is cheaper, because the alternative is eight hand-written fan-out queries you maintain forever.

02

CAP, precisely, and the consistency ladder

The theorem is an impossibility result and it is conditional: during a network partition, no system can guarantee both linearizable consistency and total availability. Two consequences are routinely dropped, and both are what an interviewer is listening for. First, outside a partition a distributed system can offer both, so CAP describes a rare dramatic moment and not your production. Second, partition tolerance is not a choice — partitions are the normal failure mode of a network — so the real decision is C or A, and it is only forced while the partition lasts. That is the same content as the else branch of PACELC, and it is the else branch that governs your configuration: your read consistency level, your cache TTL, your replica routing, your SLAs.

What an operation does when the network splits
OperationWhat a partition doesEngine behaviour
Write to a single-writer relational primaryPrimary is on the minority side Write fails and returns an error — C
Read from a replica during that partitionReachable but behind Read succeeds with old data — A
QUORUM write, RF=3, one node isolated2 of 3 still reachable Succeeds; the isolated node is repaired later by hinted handoff
QUORUM write, RF=3, two nodes isolatedOnly 1 of 3 reachable Fails. This is the C half, and it is real
ONE read, RF=3Whichever replica answers Succeeds, may be stale — A
ALL write, RF=3Any node down Fails under any partition. Maximally C, minimally A
DynamoDB read, ConsistentRead=trueQuorum unreachable Blocks, then fails — an error, never a stale value

The "C" outcomes are failures, and that is the point. An engineer who said "we chose consistency" and did not realise it means "we chose to return 503 to some users" has not finished the design. The most common real resolution is a system that is read-available and write-unavailable under partition: serving stale reads is small and explicable, accepting writes on both sides is split-brain whose reconciliation is your problem forever.

Interview trap — "is your database CP or AP?"

The question is malformed, because it asks for a property the thing does not have. Name the operation and the condition instead: "our order-status read is served from any replica and may be seconds stale; our payment write requires a quorum of three, so it fails on the minority side rather than forking." Three things worth adding. A single-writer primary with asynchronous replicas is CP, not AP — partition the primary and writes fail. CAP says nothing about the 99.99% of the time there is no partition, which is why PACELC's else branch is the one that governs your configuration.

The consistency ladder — memorise the cost column, not the definitions
ModelWhat it forbidsWho pays
LinearizableNothing. All operations take effect at one point between invocation and response Nobody. Code is ordinary. Costs a quorum per operation
SequentialReordering operations from the same client Low — sticky session or client-side sequencing
CausalObserving an effect without its cause None of these engines offers a switch. You build it
Read-your-writesShowing a client state older than a write it was told succeeded Low, but it is a contract that needs a test
Monotonic readsShowing a value older than one the client already saw Low — read a catch-up replica, or pin the session
EventualNothing in steady state. Guarantees only convergence The application. Every screen, computed field, and "why is this number wrong" ticket
Must remember — the models are not settings

There is no "eventual consistency: on" anywhere. A consistency model is a consequence of a consistency level, a read preference, a routing decision, a write concern or a read concern. A candidate who cannot name the setting behind a guarantee does not yet understand the system they are defending. And the most valuable guarantee in practice — read-your-writes — is always constructed, never configured, because no engine offers a causal-consistency switch. There are exactly two mechanisms: route the read to where the write landed, or carry a version token and escalate when the replica is behind. Everything else is an implementation of one of the two.

Must remember — "eventually consistent" is not a specification

It names no bound, no mechanism, no failure case and no owner. A usable claim needs four things: the bound (Cassandra's ONE read is unbounded even in normal operation — it is whatever the slowest reachable replica says, and a node that is down rather than lagging does not answer at all); the mechanism (anti-entropy, hinted handoff, read repair, a projection worker — each with different failure behaviour); the failure case (a node holding the newest value down for a week); and who is watching (nodetool tp, a replication-lag alarm). A convergence guarantee nobody monitors is a hope.

03

Partitioning & the hot partition

Everything else in this volume is engine detail. The partition key is the design: it determines how much data lives on one machine, how much write throughput one machine absorbs, whether a query is a point read or a fan-out, and whether a rebalance moves a petabyte or a megabyte. The general argument about denormalising, sharding and shard-key choice belongs to 06 — Schema & Scaling; what belongs here is what each of these three engines does with the key it is given.

One query, three key schemas — the difference is a p99
Key designWorkLatency
pk = customer_id,
sk = order_ts DESC		 One partition, one range, 25 rows ~1 RTT, independent of table size
pk = order_id No idea which partition holds that customer's orders — read every partition, filter, sort 1 RTT + N partitions. Pages forever; times out at 1M rows and again at 10M
pk = customer_id,
no sort key		 One node, but the whole partition, sorted in the application Fine at 200 orders, 40 ms at 20,000, a 1.2 GB payload at 200,000

A partition is a unit of storage as well as a unit of throughput, which is what makes the third row a trap: Cassandra enforces a practical partition-size budget of roughly 5–10 GB, and DynamoDB publishes a hard 10 MB per physical partition. A key that grows without bound is a table that was never partitioned — everything works until it does not, and by then it is in production.

Must remember — a partition key is four things at once

It is the unit of storage, the unit of replication, the unit of write throughput, and the ceiling on query shape. Change any one and you have changed all four, which is why "let's just shard by a different key" is a data-migration project with a downtime plan, not a configuration change. The design-review question is therefore never "is this key good for one query" but "walk me through the whole access-pattern list and show me every query this key serves and every query it turns into a scan." The artefact that makes it survivable is one page: every query as a WHERE clause, its expected rate, and — for each — whether it is a point read.

Trade-off — hash or range partitioning

Hash wins in almost every case: even distribution with no coordination, and no hot range at the end of the key space. Its cost is that range queries touch every partition, so the compensation is a sort key designed so the hot access pattern is a prefix scan of one partition. Range partitioning is right when the dominant pattern is a range scan and the key space is naturally bounded — a country code, a tenant list you control. Flips on: a partition key that is a monotonically increasing value — a timestamp, an autoincrement, a ULID. Then hash it. That one sentence prevents the most common hot-partition incident there is.

Scaling reality check — the per-partition ceiling

The number to carry: about 1,000 WCU/s and 1,000 RCU/s on a single partition, with up to 3,000 RCU/s for strongly consistent reads on one partition. A customer, an account, a device or a tenant is a natural single partition key, and any of them can legitimately be a 1,000-writes-per-second key. The moment your per-tenant write rate approaches a few hundred per second, you are designing a "one big tenant" problem — and the fix is in the key, not in the capacity.

Interview trap — "adaptive capacity will fix the hot key"

Adaptive capacity is real, documented and useful: it continuously tracks item sizes and request distribution across a table's partitions and delivers burst capacity to the ones that need it, so a skewed workload is not provisioned for its worst partition across the whole table. It redistributes capacity across partitions. It never splits one. The per-partition ceilings are structural, because a partition is the unit of distribution. The same is true of Cassandra's ring: adding nodes changes token ownership, not the size of a partition. And the most common actual root cause is not a hot cluster — it is a defaulted dimension. A null, a "tenant-default" from an unconfigured integration, or a placeholder device id collapses a whole class of writers onto one key, and a logical bug in the client becomes a physical ceiling in the database. The standing rule that follows: any dimension a client can default must never be a partition key.

04

Cassandra: the LSM write path

Cassandra never modifies a file in place. Writes go to memory, memory is flushed to immutable files, and files are merged in the background — the log-structured merge tree. That single inversion is the whole engine, and every operational question about Cassandra is one of two questions: is this a write problem or a read problem?

The coordinator hashes the partition key with Murmur3, maps the token to a range, and reads the replica set from gossiped ring metadata — every node knows the topology, so there is no registry service. Each replica appends to its commit log first, then updates its memtable; the order is what makes the write durable when the process dies. If a replica is down, the coordinator stores a hinted handoff entry and, given the quorum was met, returns success. The read path is harder than a lookup: a bloom filter per SSTable, built at write time, lets the reader skip a file without touching the disk, and a partition index — a sampled key-to-offset summary — lets it seek into a multi-gigabyte file. Once the key is found the scanner keeps reading forward, because rows of one partition are adjacent on disk — which is why a wide SELECT * on one partition is a fast sequential scan.

Size-tiered vs leveled compaction
Size-tiered (STCS)Leveled (LCS)

Write amplificationHigh — up to ~10× the base data in the worst case; a row updated many times is rewritten many timesLower, amortised across levels
Read amplificationLow — few, large filesHigher at L0, decreasing deeper
Latency profileBursty: fast, then a long compaction pauseSmooth: constant background I/O

Time-window compaction (TWCS) is size-tiered with buckets arranged by a time column, and it is the right answer for a table with a TTL: old data is dropped in whole buckets rather than tombstoned one row at a time — the one case where the expensive-deletion concern largely disappears.

Interview trap — "compaction is background, so it doesn't affect performance"

It is background work, which means it competes for the same disk bandwidth, and on a write-throughput-bound cluster the compaction queue is the first thing to fall behind. The chain: writes arrive faster than compaction merges, so the SSTable count grows, so reads must consult more files, so read p99 climbs — and if it gets bad enough, memtables cannot flush, the commit log becomes the only copy of new data, and a node failure in that window is real data loss. So a compaction backlog is a durability incident in slow motion. The metric that tells you which regime you are in is compaction queue depth and pending bytes on the affected nodes. The staff-level version: compaction is a capacity problem wearing a latency costume, and the fix is a write-rate reduction, a better partition key, or TWCS for a TTL table — not a bigger compaction throughput setting.

Must remember — tombstones, and what gc_grace_seconds protects

An LSM store cannot remove anything, because the row it would remove is in an immutable SSTable that someone else is reading at this instant. So a delete is written as a tombstone: a row with a deletion timestamp that sorts after the data and wins the read comparison. That tombstone is a row, and it must be read, compared and merged on every read of that partition until it is dropped. gc_grace_seconds (default 10 days) is the minimum retention, and the reason is a resurrection bug: if a replica was down when the delete happened and returns inside that window, hinted handoff replays the old row to it, and if the tombstone had already been dropped, the resurrected row would win and the data would come back from the dead, silently and permanently. It is a correctness guarantee about a reordering that is going to happen, not a tuning knob. The failure signature to know: a partition where a large fraction of rows are tombstones. Compaction then spends its I/O merging deletion markers instead of live data, every read of that partition pays more comparisons per row returned, and there is no error message anywhere. The root cause is almost always deleting most of a partition — a DELETE that removes 90% of rows leaves a partition that is 90% tombstone and slower for the next ten days even though it is nearly empty. Detect with nodetool sstablesummary; mitigate with a TTL plus TWCS, or a partition key with enough cardinality that the delete ratio per partition stays low.

05

Cassandra: modelling from the WHERE clause

A relational engineer arrives with a well-earned instinct to normalise, and in Cassandra that instinct is actively harmful. The reason is the query model: there is no join, and a query can only locate data through the partition key, so anything you intend to filter on has to be in the primary key. The consequence is structural: a predicate on a non-key column is not a query change, it is a schema migration — a new table, a backfill, and a dual-write. The read path is fixed at table-creation time, so the model is derived from the reads: write every query as a WHERE clause with its rate, ask whether Cassandra can answer it with a partition key plus a clustering range, and make each one a table. In Cassandra, a duplicate is cheaper than a join — the question is never "is this duplication acceptable" but "which queries justify it, and how stale may it be".

CREATE TABLE products_by_category (
  category     text,                    -- partition key: the query's WHERE
  created_at   timestamp,               -- clustering 1: gives the range AND
  sku          text,                    -- clustering 2: makes it unique
  bucket       int,                     -- page-split a category that grows
  name         text,
  price_cents  int,
  PRIMARY KEY ((category, bucket), created_at, sku)
) WITH CLUSTERING ORDER BY (created_at DESC, sku ASC);

-- served: one partition, one range, LIMIT 20. No sort step, no fan-out.
SELECT * FROM products_by_category
  WHERE category = 'tools' AND bucket = 0
    AND created_at > ?  LIMIT 20;

Clustering columns do two jobs: they identify rows within a partition, and they order them, so ORDER BY on a clustering column is free — the query is a range scan over adjacent rows. Two consequences candidates miss: ORDER BY on a non-clustering column is not supported, and the clustering order is a page-design decision. Time-ordered data plus a LIMIT is the single most common Cassandra table shape, and the most common reason a "slow query" is actually a missing clustering order.

Interview trap — "we added an index on status, why is it still slow?"

A Cassandra secondary index is a local index on each node, not a global one. Answering the query means fanning out to the replicas of every partition that could hold a match — a point read becomes a ring-wide scatter-gather whose latency is the slowest participant. And Cassandra will not return a partial answer: all replicas of the base table's data must be up, because a down replica is an unknown gap in the index. Since 3.0 a 2i query still requires a partition key restriction, so you have already denormalised and the index is buying a small convenience. The fix is not a better index, it is a table: status is low-cardinality, which makes it an excellent partition key in a dedicated table where the query is one partition, one range, one node. A secondary index on a column 40% of your reads filter on is a fan-out on 40% of your reads.

And ALLOW FILTERING is the other trap: it applies the non-key predicate after reading rows from the partition, so it reads every row and throws most of them away. The cost is proportional to partition size, not result size, and modern Cassandra emits a warning for every such query — but the honest framing is that it is a development affordance, and in production it is a full partition scan with a filter bolted on. The detail that makes it a review emergency: the query is correct, it returns the right row, it just took 1.8 seconds, so nothing reports an error and latency is the only signal.

Consistency levels at RF = 3, and what each one costs
LevelReplicas must ackReads contactUse it for
ONE11Default; fast, may be stale
QUORUM2 — floor(RF/2)+12The default write level
ALL33Almost never for writes
LOCAL_QUORUM2 within one DC2Multi-DC; avoids the inter-DC round trip

The formula is floor(RF/2) + 1, so RF=2 gives 2 — which is why RF=2 is not survivable, since a quorum of 2 of 2 is unavailable the moment one node is down. RF=3 is the smallest useful value; RF=5 buys a lower probability of an unavailable quorum under correlated failure (a rack, an AZ, a bad disk batch) at 5/3 the write cost and the same read cost as RF=3.

Must remember — a QUORUM read is also a write

Three latency facts separate a staff answer from a mid-level one. First, ONE and QUORUM within one DC are both about one RTT — replicas are contacted in parallel and the coordinator waits for the required count, so QUORUM costs more nodes, not another round trip. A QUORUM read that is 10× slower than ONE is telling you it is multi-DC (pay the inter-DC RTT, use LOCAL_QUORUM) or the cluster is divergent — not that the quorum is expensive. Second, a QUORUM read performs read repair: it compares versions and writes back to any replica that has fallen behind, so the read is also a write and its tail latency is a function of how divergent your cluster is. A cluster that has never been repaired has a permanently expensive read path. Third, ALL on writes is nearly always wrong — it maximises C at the cost of availability and adds nothing meaningful over QUORUM, whose quorum intersection already gives you read-your-writes.

So QUORUM is not linearizability: majority intersection guarantees the reader sees the write, and linearizability in Cassandra is a SERIAL statement running a Paxos round, meaningful only within a single partition. The three mechanisms that finish the consistency story are all repair: read repair (a QUORUM read, and probabilistically a ONE read at read_repair_chance, default 10%, reconciles a lagging replica), hinted handoff (the coordinator stores the mutation for a down replica and replays it on return), and nodetool repair (the manual anti-entropy backstop). The honest sentence names all three: there is no timer, no bound and no guarantee in the protocol — convergence is a property of operations that are running. A node down longer than gc_grace_seconds has had its hints dropped and is permanently divergent until someone runs repair.

Denormalised writes are two writes, and there is no cross-partition transaction — so the levels and the acceptable staleness window are part of the design: primary at QUORUM, read-optimised copies at ONE, and a staleness alert on the copies. The most common Cassandra production bug is not a performance problem but a consistency problem nobody named: a read that joins a QUORUM table and an ONE table client-side returns a state that never existed — a price from the current row and a stock count from four seconds ago. The database is correct at every level you asked for; the design is the bug.

06

DynamoDB: keys, consistency, capacity

A DynamoDB table has a declared key schema — a partition key and an optional sort key, each a single attribute of type S, N or B. The partition key's value is hashed to select a physical partition, replicated across a three-AZ quorum; the sort key orders the items inside it. A Query with a partition key equality and an optional sort key range is the one efficient query shape. Everything outside the key is an untyped, undeclared attribute. The hash exists to keep distribution even without coordination, which is precisely why ordering has to be re-introduced explicitly. A composite sort key such as SK = "ORDER#" + zero-padded-sequence gives a type-prefixed stream, so one table can serve "all orders then all refunds" with the ordering encoded in the key — that is the single-table design's central trick.

Work the numbers once, because a candidate who says "1 KB is 1 WCU" and cannot compute a bill has memorised half a rule. A 2 KB item written 10,000 times/s is 20,000 WCU/s. Read 20,000 times/s, a 2 KB item is one 4 KB block, so 0.5 RCU each eventually consistent. If 5% of reads are strongly consistent: 19,000 EC reads at 0.5 = 9,500 RCU/s, plus 1,000 SC reads at 1 = 1,000 RCU/s, so 10,500 RCU/s total — 5% of the read traffic is 9.5% of the read cost. On a global table the write number doubles to 40,000 WCU/s. And one fact couples schema to cost directly: a 3.9 KB item costs 1 RCU and a 4.1 KB item costs 2 RCU, so shaving 200 bytes off an item can halve a read. Strip the fields you do not read on that path.

// pk = USER#u42, sk = "ORDER#000000017"  -> orders, newest first
QueryRequest.builder()
    .tableName("store")
    .keyConditionExpression("pk = :p AND sk BETWEEN :lo AND :hi")
    .expressionAttributeValues(Map.of(":p", "USER#u42",
        ":lo", "ORDER#000000000", ":hi", "ORDER#999999999"))
    .scanIndexForward(false)
    .build();
// begins_with(sk, "ORDER#") is the other type: one partition, one prefix,
// still no GSI, so still no GSI eventual consistency and no GSI write cost.
Must remember — GSIs are always eventually consistent

There is no ConsistentRead parameter on a global secondary index and there never has been — a GSI is a separately-provisioned, separately-maintained structure updated asynchronously from the base table. A local secondary index has the same options as the table itself. So the rule is structural, not a preference: if a read must be strongly consistent, it must be served by the base table, which means the access pattern has to be in the base table's key schema. If it is only reachable through a GSI, the strong-consistency requirement is unmeetable and the design changes rather than the flag. This bites hardest when the requirement emerges late — "we now need to look up orders by promo code" — where a strongly consistent version of that read simply does not exist, and your options are to re-key the base table, to design the read path around eventual consistency (retry until the value appears, or re-read by primary key), or to maintain a strongly consistent projection under its own key with a transaction.

Interview trap — PutItem as a partial update

PutItem replaces the whole item. A PutItem with three attributes on an item that has ten silently deletes the other seven — no error, the data is simply gone. It is the single most common DynamoDB data-loss bug. The second is the lost update: GetItem, add 1, PutItem is two operations where the intent was one, so two workers both read 41 and both write 42. UpdateItem with SET counter = counter + :one or ADD quantity :n is evaluated atomically by the service, so a counter is safe in one round trip with no read. But any business logic that depends on the current value — "increment only if below the limit" — needs a condition expression, which is DynamoDB's only atomic guard, and the thing behind optimistic locking, idempotency keys and uniqueness enforcement. Note the scope honestly: a condition expression is a transaction on one item, not across items.

// Nothing is written unless the state is still what we read.
UpdateItemRequest.builder()
    .tableName("inventory")
    .key(k -> k.partitionValue("sku#8812"))
    .updateExpression("SET available = :new")
    .conditionExpression("available >= :requested")
    .expressionAttributeValues(Map.of(":new", 0, ":requested", 3))
    .build();
// Fails with ConditionalCheckFailedException -> nothing written, caller
// retries against fresh state. Do not retry blind: read the reasons.
Trade-off — on-demand or provisioned, and the question that comes first

On-demand costs roughly 2× the per-unit price of provisioned and buys predictability with no autoscale lag and no ProvisionedThroughputExceededException under a burst you did not predict; provisioned is billed whether you use it or not, needs headroom above your expected peak rather than your average, and lags a spike by minutes while autoscaling chases it. Flips on: predictability — spiky or low-volume traffic, and a launch whose peak is unknowable, favour on-demand; steady well-understood production traffic favours provisioned. The meta-point is the one an interviewer is listening for: neither fixes a bad access pattern. A Scan over a 40 GB table costs the same provisioned or on-demand — you have moved the cost from capacity units to request latency — and on-demand makes the accidental scan spectacularly expensive in dollars rather than merely slow. Before choosing a capacity mode, ask whether each pattern is a Query against a key or a Scan, because a Scan is a capacity incident either way. The same is true of FilterExpression: it is applied after the read, so it changes nothing about what DynamoDB fetches, and a filter on a non-key attribute is a full partition read whose p50 looks unchanged while the p99 sits at four seconds.

One table or many is decided by the access-pattern list, not by the argument. One table wins when entities are accessed together and no single entity is unbounded — many point reads, no GSI write cost, no GSI eventual consistency, and begins_with(sk, "ORDER#") doing the filtering. Many tables with GSIs win when entities have genuinely different volumes, lifetimes or traffic shapes, or when one entity is large enough that 10 MB is a wall — a single table has one capacity profile, and a lookup at 50 rps sharing a table with a timeline at 20,000 rps shares a throttle domain, which is a bug waiting for a launch. The transaction is the third answer and usually a design smell: 2× capacity, 2× latency, 100 items, one region, and the honest staff position is that the invariants needing a cross-item transaction usually belong inside one item.

07

MongoDB: documents, embedding, pipelines

A MongoDB document is a BSON value — key-value pairs where a value can be a scalar, an array or a nested document, nested to 100 levels. The flexibility is real in exactly three places, and a candidate who cannot name the three is describing the marketing version. Optional and sparse attributes cost nothing, with no ALTER TABLE. A small, co-located, bounded sub-structure arrives with its parent in one read, with no join. And the shape can evolve without a migration. The same three properties become liabilities under conditions that are easy to miss: a field optional to one client is optional to every client, and two services writing total and total_cents both succeed while the reader silently gets undefined; co-location is only free while the sub-structure is small; and evolving the shape without a migration means the readers must evolve too, and nothing tells you when they have.

Embed or reference — a boundedness rule, not a preference
Embed whenReference when
Read patternData is read with its parentData is queried on its own
GrowthGrows slowly — the bound is knownGrows without bound, or "it depends on the customer"
CardinalityBelongs to the parent 1:1 or 1:fewShared between parents — a product in a million orders is one document referenced a million times
IndexesNever queried independentlyNeeds its own indexes
You getOne read, always internally consistent, no joinOne read per item, or a $lookup — two-phase and possibly inconsistent
Interview trap — "MongoDB is schemaless, so it is more flexible than Postgres"

The correction is that it is not schemaless, it is un-validated. The schema still exists; you moved it out of the database into every client, where it is a convention rather than a constraint. The cost is exactly that the database will not tell you when a client breaks it: a service that writes total where the reader expects total_cents succeeds, returns no error, and produces a NaN in a dashboard. The honest position is not "MongoDB has no schema" but "MongoDB's schema is optional, lives in the document, and you should turn on validation or you have replaced a constraint with a hope." Two limits on what validation buys: it gives you types, required fields, ranges, enums and pattern matching — a large fraction of a typed column plus a CHECK — but not a cross-document invariant, a foreign key, or a uniqueness constraint across documents. And it cannot check a cross-field invariant: a schema can require total_cents to be an integer ≥ 0 and still cannot assert it equals the sum of the line items, because JSON Schema cannot express that. Cross-document integrity in MongoDB is application code, exactly as in Cassandra and DynamoDB.

There is a real asymmetry against the wide-column stores here, and it is worth saying out loud where a team is nervous about going NoSQL: MongoDB's embedding is a decision you make per field and can revisit per field, whereas a Cassandra or DynamoDB partition key is a commitment for a whole query pattern. MongoDB's mistakes are recoverable — moving a field from an array to a referenced collection is a program you write — so it is a legitimate reason to feel more relaxed about MongoDB. Its embedding rule is a boundedness rule, and the practical answer to a growing per-entity structure is a bounded, bucketed sub-collection rather than an array.

The aggregation pipeline — performance is decided by stage order
StageWhat it doesThe trap
$matchFilters documents Pushed to an index only if it is first and the shape is indexable. Putting it last is the single most common pipeline mistake
$project / $addFieldsReshapes, computes Nothing is indexed on a computed field — filtering on one is a scan
$unwindExplodes an array into documents Multiplies document count; every later stage pays for it
$groupAccumulates — always blocking Holds a hash table of every group in memory or on disk. There is no streaming
$sortSorts — also blocking Sort after a $group; before an expensive match it is a full sort
$limitCaps output Put it before an expensive $group when you only need the top N
$lookupA join, from a field in this collection to another The simple form is a loop — one query on the foreign collection per input document, so 1,000 inputs is 1,000 queries. Only the pipeline form uses an index

The rule that makes the pipeline usable: match early, unwind late, group as few times as possible, and $lookup as late as you can while still narrowing what it sees. A pipeline that starts with a $lookup before a $match is a full collection scan multiplied by a per-document loop, and with an array localField it fans out once per array element on top of that. The practice that pays for itself: every non-trivial pipeline gets an explain("executionStats") against a production-sized fixture, plus a comment naming the index it relies on — a pipeline that depends on an index whose comment does not say which is one index deletion away from a 40-second query.

// $match first and indexable -> pushed down, uses the index
// $lookup LAST, and in its pipeline form so the join can use an index
db.orders.aggregate([
  { $match: { status: "SHIPPED", created_at: { $gte: cutoff } } },
  { $group: { _id: "$customer", spend: { $sum: "$total_cents" } } },
  { $sort:  { spend: -1 } },
  { $limit: 20 },
  { $lookup: {
      from: "customers",
      localField: "_id", foreignField: "_id",
      pipeline: [ { $match: { tier: { $in: ["gold", "platinum"] } } } ]
  } }
])
db.runCommand({
  collMod: "orders",
  validator: { $jsonSchema: {
      required: ["_id", "customer", "items", "total_cents", "status"],
      properties: {
        customer:   { bsonType: "string", pattern: "^u#[0-9]+$" },
        total_cents: { bsonType: "int", minimum: 0 },
        status:      { enum: ["PENDING","PAID","SHIPPED","CANCELLED"] }
      } } },
  validationLevel: "strict",   # apply to all inserts and updates
  validationAction: "error"    # reject the write, do not warn
})
Must remember — write concern and read concern for money

Write concern is durability: w: 0 is fire-and-forget and a "successful" write may not exist anywhere; w: 1, the default on a standalone and a replica-set primary, is acknowledged by one node and is lost if that node dies before replication; w: "majority" is acknowledged by a majority and survives the loss of a minority. Read concern is what a read may return: local (the default) returns the node's own state, which on a secondary may lag; available may read a stale node; majority returns data a majority has acknowledged; linearizable reads from the primary, waits for majority agreement, and is the only true linearizable read — about twice the load of majority, and it fails during a primary election. The combination to say in a design review is { w: "majority" } with readConcern: "majority", and the reasoning is the failover case, not the happy path: the entry is on a majority before the write returns, so the new primary is guaranteed to have it, which gives read-your-writes and monotonicity across the failover — the guarantee a ledger actually needs. linearizable is not needed once the write concern is right, and it cannot check a cross-field invariant either. Add a wtimeout so a replica-lag spike fails fast rather than queueing, and alert on oplog lag, because a majority write that is slow is a write that is going to time out.

Scaling reality check — where the 16 MB wall actually bites

It is not the limit that costs you, it is how late the limit arrives: the figure above walks the eighteen months, and the design was fine on the day it was written. The part that is easy to miss is the shape of the B2B case. An order that can legitimately have 5,000 lines is past the wall before the design is finished, and those are exactly the customers whose failures cost the most. Ask four questions of any embedded array, in order: is there a bound, is it read with the parent every time, is it shared, and what is the growth rate per document? "It depends on the customer" is an answer that means reference it — or bucket it.

08

Choosing between them

The question a senior interviewer asks is not "which database is fastest". It is how do I know the access patterns, and what happens to this system when I am wrong about them — and the honest answer is that the choice is a function of three inputs: whether the access patterns are known and fixed, how much of the query is a filter on a non-key column, and how much operational appetite the team has. The third is frequently the deciding factor and it is not a technical one.

The decision, by workload shape — and what you get when you pick wrong
StoreFits this workloadAccess pattern it demandsWhen you pick it for the wrong one
Cassandra Known, fixed, high-volume point and range reads on one key; write rate is the binding constraint and the data is never joined Every query expressed as a WHERE clause before the schema; one table per query pattern; denormalised copies written together and named with their staleness The new query becomes ALLOW FILTERING or a 2i fan-out. It is fast at 10,000 rows and a denial of service at 10 million, and it gets worse every day
DynamoDB The same known patterns, where the team does not want to run a cluster and the bill is acceptable; serverless shape A one-page access-pattern list — each pattern as a concrete Query with key expression, rate and item size, checked for point-read-ness The Scan or FilterExpression that is a capacity bill either way, and the hot key that adaptive capacity cannot split. Cheapest to operate, most expensive to un-choose
MongoDB Document-shaped entities with a bounded co-located structure, and a meaningful fraction of queries filtering on a non-key attribute or moderately variable reporting logic Embedding decisions made per field with a stated bound, and collMod validation switched on An unbounded array that passes every test for a year and then one customer crosses 16 MB. Recoverable, because embedding is revisited per field — unlike a partition key
Postgres / MySQL Relational data, ad-hoc SQL, real joins, variable requirements — which is most data, and a 40-query application is a Postgres application Nothing. It is the default, and the cost of leaving is a migration The cost lands the other way: a single-writer ceiling on an append-only never-joined workload, and every cross-entity query becomes a hand-maintained fan-out
Must remember — what makes the choice expensive to undo

Think in reversibility, not features. The partition key is near permanent: it determines the physical layout, the per-key throughput ceiling and the only efficient query shape, and changing it is a data migration with a dual-write window plus a rewrite of every query that relied on the old shape. The denormalised duplicate is close behind, because the application has started depending on it and its staleness has become load-bearing in a user interface the database team does not own — removing one is a product change, not a migration. One-table-versus-many is moderate: it changes the capacity model and the throttling domains. By contrast the consistency level per statement is a parameter and is cheap to change, which is exactly why it is the decision that gets made by accident. And the meta-answer is the window: all of these are cheap before the first production row lands and expensive afterwards. A NoSQL decision made before there is data is a two-week decision; the same decision after two years of data is a two-quarter migration, and naming that window is often the most valuable thing a staff engineer contributes to the review.

Two warnings decide more cases than any feature comparison. First, the ordering in a design review is model first, cache second, never the reverse — adding a cache is reversible, local and additive, because a miss falls through and a wrong cache is flushed; a cache in front of a cache-shaped data model is much harder to remove than it was to add. And the deeper reason: a cache in front of a full scan is a latency band-aid on a capacity bill that grows linearly with data, which makes it the only mechanism here that gets worse as the data gets bigger. Second, the three artefacts that make any of this survivable cost an afternoon and are missing almost every time: the access-pattern list, the partition review that walks it against the proposed keys and names the queries that become scans, and the exit cost — one paragraph on what it would take to move this data to a different store in two years. A team that has written the exit cost makes better day-one decisions, because the key schema is suddenly visible as the thing that would be expensive to change. Redis is in this picture too, and it is not a system of record: it is the only store here whose failover can lose an acknowledged write (see 09 — Redis & Caching).
