Volume 9 — Redis & Caching Strategies

What a cache is actually buying you, which of the six strategies owns the read path, and how to tell a stampede from a penetration from an avalanche when the graph spikes.

  • 9 sections
  • From the source volume
← Prev Next →

If you only remember five things

  1. A cache is a latency and load decision, not a speed one. A hit costs 0.2 ms; a miss costs 0.2 ms + the query + the write, about 2.4 ms — twelve times a hit. At a 1% miss rate the average is 0.224 ms; at 10% it is 0.44 ms. Past roughly 10% the cache is not earning its invalidation complexity, so fix the query instead.
  2. Cache-aside is the default because the cache has no code path to the database. If Redis is down, the application still works — it is just slower. Every strategy that embeds cache knowledge in the write path trades that property for a cheaper miss.
  3. Stampede, penetration and avalanche are three different bugs with three different fixes. Stampede is one hot key expiring under N concurrent readers. Penetration is requests for keys that never existed. Avalanche is a whole keyspace expiring at once. Confusing them is the mistake this page exists to prevent.
  4. An eviction policy is not a safety net. maxmemory is a write on the command path: with volatile-lru and keys that carry no TTL, every write is rejected with OOM while evicted_keys stays at zero. The policy has no candidate set to choose from.
  5. Persisting a cache is a claim that its contents are worth restoring. And the AOF records an eviction as a DEL — so enabling persistence protects you from a crash, not from a full instance.

Nothing matches that filter.

01

What Redis actually is

Redis is four layers, and most surprises come from confusing which one you are looking at: a RESP protocol that is a stream of human-readable, binary-safe bytes over a socket; a command and data-structure layer that is just an in-memory store with smarter access patterns than SELECT; a single-threaded execution layer that runs commands one at a time; and a memory and durability layer that decides what happens when the memory runs out.

The single-threaded loop is a deliberate bet. It buys atomicity of single commands for free — no lock convoy, no lost update between a read and a write inside one command — it makes fork() cheap because there is nothing to coordinate with, and it removes a whole class of data race from the engine. What it does not buy is preemptibility: O(n) work inside a command blocks every other client for the duration. That is the whole of Redis's concurrency story, and the reason KEYS is a production incident.

Interview trap

io-threads 4 does not make command execution parallel, and io-threads-do-reads defaults to no — so with only read traffic you have added threads without turning on the read path. The setting that matters for a read-heavy cache is the second one, and it is off by default.

Scaling reality check

The headline is 100,000+ operations per second. The number a client actually gets is 50,000–80,000, and 1,000 sequential commands across regions cost 20–40 seconds — pipelined they cost 20–40 milliseconds. Round trips, not throughput, are the first wall.

That is why the first question about Redis is never "how fast is it" but how many round trips does one request cost. MGET collapses N gets into one; pipelining collapses N round trips into one without changing the reply count; a Lua script collapses both, because the script runs to completion inside the single thread and nothing interleaves with it.

Trade-off

Single-threaded execution is the right bet while commands are O(log n) or better and the working set fits in memory. It stops being the right bet the moment you need to scan, sort or aggregate a large collection inside one command — the flip condition is whether any single command is unbounded in the size of the keyspace. If yes, the fix is to change the command, not to add threads.

02

Data structures & when each one fits

The choice is not "which structure is fastest" — it is which one makes the operation atomic on the server. Every structure below exists so a read-modify-write collapses into one command the loop runs to completion.

Interview trap

A hash and a JSON string hold the same data, but only the hash gives you per-field atomicity. Chose the hash the moment a second writer can touch the object — the cost is an extra network round trip to read it all back, and the benefit is that HSET cannot lose a field it never read.

Memory is decided here, not later. A hash below 128 fields and 64 bytes is stored as a listpack, one contiguous allocation; past either threshold it converts to a hashtable plus per-field overhead of 40–50 bytes. A small-object workload that quietly crosses that line pays 2 GB of pure overhead across 10 million five-field hashes. Both thresholds are configurable, and a listpack-encoded hash can be forced back by hand with HSTRLEN if you know it will shrink.

Must remember

Bitmaps only work on dense integer domains. User ids that are sparse or start at zero per tenant will allocate a bitmap as wide as the largest id, and a 64-bit id is 8 exabytes. Check the density before you choose one.

03

Caching strategies

Six named strategies, but only two independent decisions: where the write happens, and who owns the read path on a miss. Ask those two questions and you can derive any strategy you meet in an interview.

The six patterns, by the two decisions they actually make
StrategyRead path on a missWrite pathWho knows about the cache?
Cache-asideApplication queries the database, then populatesApplication writes the database, then deletes or sets the keyOnly the application. Redis has no code path to the database.
Read-throughCache loads on the application's behalfUnchanged — the write path is the same as cache-asideThe cache library. The miss is one call, not two.
Write-throughUnchangedCache writes through to the database before returning successBoth. The write path is now a distributed write with no atomicity.
Write-behindUnchangedCache accepts the write and flushes asynchronouslyThe cache. Fast writes, and data loss on the flush window.
Refresh-aheadUnchanged — a hit is still served immediatelyA worker refreshes before the TTL expires, at ~90% of itThe cache. Hits stay hits; the miss path is rarer.
Read-repairStale value returned, and a repair is queued behind itUnchangedThe cache. No user ever waits on the source of truth.

Cache-aside is the default, and the reason is structural rather than performance: the cache is not on the write path and has no code path to the database. If Redis is unreachable, the application is slower and correct. Its cost is the double round trip on a miss — GET, then the query, then SETEX — which is the number below.

What a miss rate does to the average request
Miss rateAverage latencyVerdict
0% (pure hit)0.2 msThe floor, set by the round trip alone
1%0.224 msWhere most working caches live — clearly worth it
10%0.44 msPast this, the invalidation machinery is costing more than it saves
100% (cache down)2.4 msCorrect, just slow. This is the failure mode you accepted when you chose cache-aside.
Scaling reality check

The 2.4 ms miss decomposes as 0.2 ms of GET, 2 ms of SELECT and 0.2 ms of SETEX — and two of those 2.4 ms are the query you already had. The flip condition: when the query costs 200 ms, a miss is a thousand times a hit and no achievable hit rate rescues the average. At that point the answer is the covering index from Volume 4, not another caching layer.

Trade-off

Write-through buys a cache that is never stale and never needs invalidation, and pays for it with a distributed write that has no atomicity across the two systems — a failure between the cache write and the database write leaves them permanently disagreeing, and nothing rolls it back. Choose it when the read:write ratio is high and stale reads are unacceptable; the flip condition is tolerating bounded staleness, at which point cache-aside wins.

Read-repair and stale-while-revalidate share one property: they never make a user wait on the source of truth. Both need a throttle, because "queue a repair on every stale hit" turns one slow source into a herd — and both turn staleness into a value you configure rather than a bound you hope for.

04

Eviction & memory

maxmemory is not a limit checked at the end of the operation. It is a write on the command path: before admitting a new allocation, Redis runs the eviction policy, which may itself be O(samples) work the client is paying for. That is why maxmemory interacts with latency even when nothing is evicted.

The policies differ first in where they look for a victim.

Eviction policies by candidate set, not by eviction quality
PolicyCandidate setGood forFails when
allkeys-lru / -lfu / -randomEvery keyAny cache, and the default safe choiceNothing — there is always a candidate
volatile-lru / -lfu / -randomOnly keys with a TTL setMixed durable and ephemeral data in one instanceA single key with no TTL, and every write is rejected with OOM while evicted_keys stays at 0
noevictionNone — writes are rejected at maxmemoryAn instance that is a primary datastore, not a cacheYou expected a cache and got an outage
Interview trap

volatile-lru on an instance whose keys have no TTL does not fall back to allkeys. It has an empty candidate set, so it evicts nothing and every write fails with an OOM error at 100% maxmemory while INFO stats reports evicted_keys:0. The metric that looks healthy is the metric that is lying to you.

LRU versus LFU is a bet on the workload's past. LRU trusts recency: one scan over your keyspace destroys it. LFU trusts frequency, with an 8-bit saturating counter incremented logarithmically (lfu-log-factor 10) and decayed on read (lfu-decay-time 1), so a key that was hot yesterday and idle today fades rather than pinning memory forever. A workload that introduced 500,000 cold keys in 30 seconds is the case LFU exists for — LRU evicts all of them and keeps the hot set only by luck.

Both are approximate: Redis samples maxmemory-samples random keys (default 5, commonly raised to 10) and takes the best of those, aborting after about four times the sample size. Five samples on a keyspace dominated by one hot region will happily evict a hot key. The approximation is the price of not maintaining a global recency list, which would cost a write to every key on every read.

Reading memory pressure: which number moved
SignalReadingWhat it means
mem_fragmentation_ratio1.0–1.5Healthy
mem_fragmentation_ratio> 1.5Allocator cannot return memory; consider activedefrag
mem_fragmentation_ratio> 2.0Investigate now — usually a large value deleted after a fork
mem_fragmentation_ratio< 1.0Swap, or the kernel is over-committing on your behalf
used_memory vs cgroup limit400 MB used, maxmemory 1900mb, process OOM-killedThe kernel killed you, not Redis. maxmemory was never the ceiling that fired.

The last row is the reason to check evicted_keys before you check anything else. And the container row is the one people get wrong in interviews: in a cgroup, the OOM killer reads the container's RSS, so maxmemory set to 90% of the limit is a promise the kernel does not honour. Set it to roughly 70–80% and leave the headroom.

// Racy: another client can read the key in the gap and rebuild it without a TTL.

redis.expire(key, Duration.ofSeconds(300));

// Atomic: the TTL is part of the same command, so no window exists.

Scaling reality check

A one-byte key costs 50–100 bytes of overhead before its value — roughly 24 bytes of dictionary entry plus 8–16 bytes of jemalloc per allocation. Ten million counters therefore cost 500 MB to 1 GB. If you are counting things, decide between one counter key and a bitmap before you size the instance.

05

The three classic cache bugs

Three different bugs, three causes, three fixes. In production all three arrive as "the cache broke", which is how teams spend a week adding TTL jitter to a penetration attack. Tell them apart first.

Stampede, penetration, avalanche — kept deliberately distinct
BugCauseSignatureFix
Stampede One hot key expires or is evicted while N concurrent requests want it One key, a burst of identical database queries, DB CPU spikes for a few seconds, then it self-heals Single-flight mutex, probabilistic early expiry, or stale-while-revalidate
Penetration Requests for keys that do not exist, so nothing is ever cached and the miss repeats forever Many distinct keys, all misses, sustained — not a burst, a plateau Negative caching with a short sentinel TTL, a bloom filter, or input validation
Avalanche A large share of the keyspace expires together — a cold start, a uniform TTL, or a deploy that changed every TTL at once Every key misses at once, over minutes or hours, right after a restart or deploy TTL jitter, and the sizing rule below

The stampede, in numbers

One hot key, 4,000 QPS against it, 200 ms rebuild, pool of 50. Capacity is 50 / 0.2 = 250 queries per second. Arrival is 4,000. That is a 16-fold overshoot, a backlog growing at roughly 3,750 per second, and about 16 seconds before the queue drains — assuming nothing else in the system degrades in the meantime. The system re-heals only while the rebuild time stays under pool_size / QPS, which here is 12.5 ms. A rebuild slower than that is a stampede that does not self-heal.

The four fixes, and what each one actually costs

Probabilistic early expiryNoneWidens to the next refresh windowOne extra metadata read per hitNo — an evicted key has no fetchedAt, so the guard never fires
Stale-while-revalidateA refresh fan-out, which needs a throttleA hard TTL you chooseUsers can be served data you know is oldNo

private final ConcurrentHashMap<String, CompletableFuture<String>> inFlight = new ConcurrentHashMap<>();

String load(String key) {
  String hit = redis.opsForValue().get(key);
  if (hit != null) {
    return hit;
  }
  // computeIfAbsent runs the mapping exactly once per key; the losers wait on it.
  return inFlight.computeIfAbsent(key, k -> CompletableFuture.supplyAsync(() -> {
    String fresh = loadFromDatabase(k);
    redis.opsForValue().set(k, fresh, ttl);
    return fresh;
  }, executor)).join();
}
Must remember

The single-flight map is per process. Twenty pods means twenty independent locks, so the naive fix reduces a 16× overshoot to 20× one — much better, not solved. If you need a fleet-wide guarantee, the distributed version is a short-lived lock key with a TTL, and the TTL is what saves you when a pod dies holding it.

record Entry(String value, long fetchedAt) {}

Entry get(String key) {
  Entry e = store.get(key);
  if (e == null) {
    return loadAndStore(key);
  }
  long age = System.currentTimeMillis() - e.fetchedAt();
  long ttl = ttlMillis;
  // Rebuild early with probability rising to 1 as the entry nears expiry.
  // One unlucky caller gets the fresh value; everyone else is still a hit.
  if (age > ttl - ttl * Math.sqrt(random.nextDouble())) {
    return loadAndStore(key);
  }
  return e;
}
Interview trap

The probabilistic guard stores a fetchedAt alongside the value, so it needs a different data structure than the plain string you were caching — migrating the key type is the actual work. And it is useless against eviction: an evicted key has no timestamp, so the guard that was supposed to spread the load never fires on the miss that eviction just caused.

Penetration and avalanche

Penetration is 50 connections each taking 1 ms, which is a 50,000 QPS capacity against a database that will not survive it — against an attack issuing 10,000 to 50,000 requests per second for keys that never existed. The id-increment variant is quieter and just as effective. A bloom filter is the cheap structural fix: 1.2 MB at 1% false-positive rate for 1 M elements, no false negatives, and it turns 50,000 misses per second into roughly 500.

Avalanche is arithmetic, not malice. 2,000,000 keys warming at a rebuild capacity of 250 per second is 8,000 seconds, about 2.2 hours, during which the hit rate is near zero. Jitter is the fix and it is arithmetic too: spreading a 3,600 s TTL by ±300 s turns 2,000,000 expiries into 3,333 keys per second across a 600 second window. The sizing rule that falls out: jitter window × expiry rate ≤ miss budget. Pick the window from the budget; do not pick the jitter first.

Scaling reality check

Your database's ceiling is not your connection pool, it is the database's own concurrency limit — a few hundred active queries regardless of how many pods you run. Twenty pods × 50 connections is 1,000 against a global limit of 100–200, so each pod is individually "healthy" and collectively destructive. That is the same argument as Volume 6's shard-key sizing, applied to a connection pool.

06

Invalidation & consistency

Cache invalidation is the hard part, and the underlying reason is that Redis and your database are two independent systems with no atomic write across both — the same fact that makes isolation levels Volume 5's subject, seen from the other side. There is no transaction spanning them, so every strategy here is about choosing which inconsistency window you can live in, not about eliminating it.

Invalidation approaches and the window each one leaves
ApproachAtomic with the write?Staleness boundFailure mode
Delete the key after commitNo, but idempotent and it fails safeOne round tripThe delete-then-stale-repopulate race, below
@CachePut inside the transactionNo — it fires even on rollbackNone while the transaction commitsCache holds a value the database rejected
Short TTL onlyNothing to be atomic withMean staleness is ttl/2Bounded and dull, which is why teams underestimate the alternatives
Transactional outbox + idempotent consumerYes — the message and the row commit togetherOutbox poll interval plus consumer lagDuplicate deliveries, so the consumer must be idempotent
Versioned keys in the key nameYes, by constructionZero — the old key is never read againEvery version stays resident until its TTL; key count multiplies
Must remember

Compare-and-set on a version field, or put the version in the key name. The second is more effective because it needs no read at all — the reader's write lands under user:42:v17 while the writer already moved everyone to v18, and the stale key is simply never read again.

Interview trap

A sliding TTL is not a safety feature. GETEX key EX 300 on every read makes hot keys never expire, which converts a bounded staleness window into an unbounded one and quietly removes your only backstop against a missed invalidation.

Trade-off

Versioned keys remove the race entirely at the cost of unbounded key growth until each version's TTL lands, so you are trading a correctness bug for a memory budget. The flip condition is write volume: at high write rates the old versions are a large fraction of the keyspace and allkeys-* starts evicting live data, at which point a short TTL plus CAS is the better answer.

One case has no cache-based answer. A key built from more than one namespace — a list of a user's posts plus a global feed page — cannot be deleted correctly, because you do not know every key that contains it. The options are to key on a single entity and re-derive the list, or to encode the dependency in the key and accept the fan-out. Multi-region is the harder version of the same problem, and the answer there is that you do not have one: a cache invalidation protocol across regions is a distributed system, and pretending otherwise is how people end up debugging a stale user record from a region that was never told.

07

Persistence & durability

Two mechanisms. The question is not which is better but how much data you will lose and how long a restore may take. RDB is a point-in-time fork-and-write; AOF appends every write operation. You can have both, either, or — on a cache — neither.

Choosing a durability mechanism
MechanismWhat it storesLoss windowUse it when
RDB (save 3600 1, 300 100, 60 10000)A full snapshotSince the last successful save — up to an hour under the defaultRestarts are rare and a fast, small dataset is enough

Scaling reality check

The AOF rate is set by the storage, not by Redis. A cloud EBS-style volume flushing 5–20 ms per fsync caps you at 50–200 writes per second with appendfsync no — worse than everysec, because the flush is in the path either way. And on cloud volumes the flush may be accompanied by an explicit cache-line flush (FUA), which is a different cost model again. Measure the volume, not the instance.

The fork() is where persistence surprises people. It is copy-on-write, so the child shares pages until something is written — which means the cost of a background save is proportional to your write rate during the save, not to the dataset. 20,000 writes/s across a 100 ms fork is about 2,000 extra pages. The genuinely dangerous case is a keyspace-wide scan during the fork: every page it touches must be copied, and on a 32 GB dataset that is the OOM kill you will be paged for. Set vm.overcommit_memory 1 so the fork is permitted at all, use rpl-diskless-sync yes so a replica's parent ships the snapshot over the socket rather than to disk, and check rdb_last_bgsave_status rather than assuming the last save worked.

Interview trap

Persistence does not protect you from eviction, and this trips people up constantly: the AOF records an evicted key as a DEL. A restart faithfully restores the post-eviction keyspace, which is exactly the keyspace that was already wrong. If your incident was memory pressure, restoring from AOF restores the symptom.

Must remember

Turning on persistence for a cache is a claim — that the contents are worth minutes of recovery time and a slower restart. Make it deliberately, and be able to say what you would lose if you did not.

08

Replication, Cluster & sharding

Replication in Redis is asynchronous, and that single word is the entire failure model. A write acknowledged by the primary may not exist on any replica yet, so a failover loses it. The knobs do not prevent that; they decide whether you are allowed to acknowledge a write while replication is behind, and they are the right answer for a datastore and the wrong one for a cache.

Choosing between Sentinel, Cluster and a managed service
OptionHandlesBlast radiusChoose it when
SentinelAutomatic failover of one primary-replica pair or trio10–30 s of unavailability, plus whatever writes master_repllag allowed you to acknowledgeOne node’s worth of data — availability, not capacity
ClusterFailover and horizontal partitioning across 16,384 slotsA resharding move, and the coordination that comes with itOne machine genuinely cannot hold the working set
Managed serviceThe failover, usually30–60 s, with no lever you controlNobody on the team wants to be on call for a failover

When you do accept the loss, bound it: min-replicas-to-write 1 with min-replicas-max-lag 2 makes the primary refuse writes rather than acknowledge data no replica has, and WAIT 1 1000 makes one client wait for a replica to catch up before it reports the write landed. The repl-backlog-size of 1 MB and repl-backlog-ttl of 3,600 s are the window in which a replica re-synchronises without a full resync — size it for your longest expected outage, not the average one.

The fixed slot count is not arbitrary: 16,384 is a bitmap that fits in 2 KB, which every node can hold and gossip in full. Nodes do not ask a directory service; they exchange a 2 KB map and know everything. The consequence is that you cannot rebalance by moving data at runtime into arbitrary sizes — you move slots, in batches, while the cluster keeps serving.

Interview trap

MOVED and ASK are not the same, and answering otherwise is the standard Cluster mistake. MOVED means the slot has permanently moved — update your topology and retry. ASK means it is mid-migration and this one key is temporarily elsewhere: serve it from the ASKING target and retry without updating your map.

Must remember

Redis Cluster is a partitioning mechanism, not a shared-nothing shard you can place yourself. Slot ownership is computed from the key, so the distribution follows your key naming — and an access pattern that hits one hash tag gets one node no matter how many you added. Choosing a distribution-friendly key layout is Volume 6’s shard-key argument; the slots are only how Redis implements it.
