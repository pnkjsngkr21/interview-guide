Volume 1 — Fundamentals & the Relational Model

The layer between the SQL you type and the bytes that move: what a page is, why row width beats row count, and where every abstraction stops paying for itself.

  • 8 sections
  • From the source volume
Next →

If you only remember five things

  1. A database is three layers wearing one interface — a query engine, a storage engine, and a concurrency protocol. SQL is declarative, so it names the answer and never the route, and an incident is almost always one of the three layers disagreeing with your intent.
  2. The page is the unit of I/O and it is read whole. Row width therefore drives performance more than row count: a single-row SELECT on a 16 kB page reads 16 kB, and SELECT * on 50M rows of 200 bytes touches roughly 625,000 pages against about 40,000 for four narrow columns.
  3. The heap is an unordered pile of slotted pages. Deleting frees nothing until VACUUM, an update appends rather than moves, and steady-state tuple size is a function of the largest the row ever got.
  4. Schema or application is decided by how many things can write the table. A foreign key costs a lock on the parent row for the duration of the statement; an application check costs nothing and covers only the writers you control.
  5. Normalisation removes anomalies, not write cost. It makes a fact safe to store in one place; denormalising is a separate, physical decision that is only justified when the slow path is measured and the sync mechanism is named.

01

What a database is actually doing

"A database stores data so you can retrieve it" describes the storage engine's job and skips the part that generates incidents. The useful decomposition is three layers, and the layering is load-bearing: SQL describes what you want, and the engine decides how to get it. When a query is slow the answer is almost never "the query is wrong" — it is the optimiser mispredicting a row count, the storage engine reading 40,000 pages instead of 40, or the concurrency layer making you wait behind a long transaction, which then shows up as query time.

Interview trap — "where does the database store my data?"

"On disk" is true in a way that is useless, because working sets live in RAM and there are three layers of caching between your SELECT and the platter. A cache hit in the buffer pool and a cache hit on disk are completely different latencies, which is why EXPLAIN (ANALYZE, BUFFERS) reports shared hits and reads separately: that ratio is your real measure of how well the pool is sized for this workload. An I/O counter showing zero does not mean the query was cheap — it means the OS was willing to serve it.

Must remember — what the write-ahead log is actually for

If the data file were authoritative, every commit would have to force the modified pages to disk in a random-access pattern while holding locks, so throughput would be bounded by device random-write latency. The WAL inverts that: changes are appended sequentially and forced once per commit, and the data file is updated lazily. Two things follow. Durability is a property of the log, not the data file — which is why fsync on the log is the only thing standing between "committed" and "committed for real". And a dirty page can be evicted from the buffer pool as a memcpy, because the log already has the change and will replay it.

Naming these five things for an unfamiliar engine is what lets you read its documentation and triage "the database is slow" without an hour of guessing.

Scaling reality check — when the planner stops searching

The join-order search space is n! for n tables, so no engine enumerates it. PostgreSQL and MySQL both use dynamic programming over interesting orderings: for six tables an exhaustive permutation search is 720 plans, which is tractable, so they consider all of them. Past roughly 8–10 tables the space outgrows exhaustive search and the optimiser falls back to heuristics. A join across more than about eight tables is usually a schema problem wearing a query costume, and the fix is a denormalised bridge table, not a planner hint.

02

Pages, heaps & the physical layer

Every performance question in this volume eventually reduces to one question: how many pages did this touch? A page is the unit of I/O, the unit of buffer-pool occupancy, the unit of coarse locking, and — in most engines — the unit that must be written entirely to make one small change durable in the data file. It is fixed at initialisation, not per table, which is why managed services rarely let you touch it: you choose it at the point where you know the workload, and that point is usually gone by the time you want to change it.

MySQL InnoDB16 kBFixed at init, innodb_page_size
SQL Server8 kB—
Oracle8 kB—
Interview trap — why is SELECT * slow?

The reflexive answer is "it transfers more over the network." That is the last stage and often the smallest. The real cost is upstream, in five stages, and only the fifth is the network: (1) every column is read, so no index-only scan is possible, because that needs every referenced column present in the index; (2) if the row exceeds the page size, TOAST chunks are fetched — an extra random read per oversized row, on top of the scan; (3) more bytes per row means fewer rows per page, so the same logical row count touches proportionally more pages; (4) serialisation moves from "parse four columns" to "parse forty"; (5) then the network. Quantified: on a 50M-row table with 200-byte rows and a 16 kB page, SELECT * touches roughly 625,000 pages against about 40,000 for four narrow columns — and the second number is the one that changes your latency.

Scaling reality check — steady-state tuple size

Measure with pg_column_size(row), diagnose with pgstattuple. A table carrying 20 bytes of tuple in an 8 kB page where you expected 8 kB's worth of rows has usually survived thousands of in-place updates. Steady-state tuple size is a function of the largest the row ever got, not its current width, because a slotted page never compacts. A table that once held a 4 kB JSON blob permanently pays the 4 kB per-row cost long after the blob is gone, until a VACUUM FULL — a rewrite under an ACCESS EXCLUSIVE lock, so a scheduled operation, never a live one — or a logical rewrite clears it.

Interview trap — "is the data in the order I inserted it?"

Only until something is updated. An updated row is usually written to new free space rather than moved back — a PostgreSQL HOT update appends a new tuple version at the end of the page and leaves a dead one behind. So physical order degrades toward "order of last update," not "order of insertion." The useful reply to a colleague who says the heap is insertion-ordered is: "until the first update — and the first update is always the first update." It is also the mechanism behind index-only-scan regressions: the visibility map stops covering the pages and reads that were free start re-fetching the heap.

The consequence engineers miss most often is that a range predicate on the primary key is a full scan. WHERE id BETWEEN 1 AND 100 is not a range scan on a heap: the optimiser has no basis for assuming those rows live anywhere in particular, and without an index the information does not exist anywhere in the file. Related: SELECT without ORDER BY has no defined order at all, even though it appears to return insertion order — so any test that depends on row order without ORDER BY is a test that passes on Tuesday and fails on Friday.

Does the index contain the row, or a pointer to it?
EngineWhat the leaf holdsWhat that costs
PostgreSQLA (block, offset) pointer into the heap A second, random page read per lookup. A range fetch over a large index degrades because index adjacency is not heap adjacency
MySQL InnoDBThe whole row — the clustered index is the table; secondaries hold (key, primary_key) Bigger, more uniform read cost per lookup; a much bigger write cost, because a row update is a delete-plus-insert at the leaf and every secondary index update moves the primary key
ElasticsearchThe document sits adjacent to the postings in _source Write amplification on every index update; the right trade when reads dominate

Which is why "MySQL feels slower than PostgreSQL for the same indexed query on a wide table" is not necessarily a MySQL problem. The crossover depends on read-to-write ratio and row width, and you find it by measuring both, not by asking which engine is faster.

One more write-path fact that earns its place: every indexed column is written on every insert. An insert into a table with six indexes is six B+ tree insertions plus one heap write, each with its own WAL record, so the common "why is insert slow" answer is not the table — it is the index count. The free-space map explains the rest: a table that was once huge and is now small is still slow to insert into if there are no free pages, because every insert may extend the relation.

03

The relational model

Codd's model is a logical theory: it says what a relation is, what a functional dependency is, what normalisation means, and it says nothing whatsoever about how bytes are laid out on a device. The separation is deliberate and it is load-bearing, because the whole performance discussion in section 2 lives in the gap between the two layers.

What the model says, and what SQL actually gives you
ConceptThe modelSQL
RelationA set of tuples — no duplicates possibleA bag of rows; duplicates survive unless you remove them
TupleAn ordered list of attribute-value pairsA row, but names resolve by position or name, and NULL is a marker, not a value
DomainA named set of permissible valuesA type — which most engines extend with arrays, JSON, ranges, hstore
Foreign keyDoes not exist. A relation can only contain valuesFK constraints with ON DELETE actions, layered on by every engine
NULLDoes not exist. "No value" is not a valueEverywhere, and three-valued logic as the consequence
OrderingNoneORDER BY, indexes, and a planner that cares about both
Interview trap — why is UNION slower than UNION ALL?

Because the model says a relation is a set, and a set has no duplicates, so UNION is defined as set union and must eliminate duplicates — which means a hash aggregate or a sort of the whole result, usually a spill to disk on anything large. The correct code-review question is not "is UNION bad" but "do these two branches actually overlap?" If they are provably disjoint by construction — different date ranges, disjoint status values, an id range above the other's — then UNION ALL is not an optimisation, it is the same query written correctly. The mirror-image mistake is worse: reaching for UNION ALL on branches that can overlap converts a slow query into a wrong one, and the duplicate surfaces as a double-counted total in a financial report.

Adding NULL is the model's permanent price, and knowing the shape of the bill is worth a sentence in an interview: WHERE admits a row only when the predicate is definitely true, so NOT IN against a list containing a NULL is never true, COUNT(col) skips nulls, SUM over no non-null values is NULL rather than zero, and a comparison to NULL must be written IS NULL rather than = NULL. The depth belongs to Volume 2; the shape is enough here.

Key vocabulary — and what it tells you about the schema
TermDefinitionIn users(id, email, created_at)
SuperkeyAny attribute set that uniquely identifies a tuple{id}, {id, email}, {id, email, created_at} — all three
Candidate keyA minimal superkey: remove any attribute and uniqueness breaks{id} and {email} — two of them
Primary keyThe chosen candidate key, made NOT NULL and UNIQUEid
Alternate keyThe remaining candidate keysemail — and it should carry a UNIQUE constraint whether or not you query on it

The highest-value schema check in a design review is naming the alternate candidate keys: if email is a candidate key then email identifies a user, and that is a domain fact belonging in a constraint. The vocabulary also makes two other answers cheap — why PRIMARY KEY implies NOT NULL and UNIQUE (a key that permits NULL identifies nothing, because NULL = NULL is unknown), and why an FK targeting customers.email would be valid and considerably worse: an email change becomes an update to every referencing row.

-- {id} and {email} are BOTH minimal superkeys.
-- {id} is chosen as the primary key; email is an alternate key
-- and still identifies a user, so it gets a UNIQUE.
CREATE TABLE users (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT users_email_key UNIQUE (email)  -- the row people forget
);

-- a CHECK cannot see other rows, so "at most one NULL" is not a CHECK
CREATE UNIQUE INDEX users_email_one_null ON users (email) WHERE email IS NULL;
Interview trap — "UNIQUE allows one NULL, right?"

This is a genuine integrity hole produced by an accident of the standard's duplicate rule: two rows are duplicates only if no column is distinctly unequal, and NULL is never distinctly unequal to anything. So email VARCHAR(255) UNIQUE will happily accept 4,000 rows with email IS NULL on PostgreSQL. The result is engine-dependent, which is itself worth saying out loud:

EngineMultiple NULLs under UNIQUE
PostgreSQLAllowed (9.0+ treats NULLs as distinct)
MySQL / InnoDBAllowed
SQL ServerNot allowed — one NULL per UNIQUE column
OracleAllowed

If the column is genuinely optional and unique-if-present, several NULLs are the intended behaviour. If every row should have an email, the constraint did not stop the bug and those rows are ones your application cannot look up. The fix is a partial unique index (WHERE col IS NULL) or a filtered index — not a CHECK, because CHECK cannot see other rows.

04

Keys, constraints & referential integrity

Must remember — four facts that answer most constraint questions

PRIMARY KEY is unique plus not-null, enforced on every write. FOREIGN KEY is a lock on the parent row for the duration of the statement. CHECK is a per-row boolean and is useless across rows. DEFERRABLE moves the check to COMMIT rather than per statement. Everything else in this section is a consequence of those four.

-- a range a type could nearly express
ALTER TABLE subscriptions
  ADD CONSTRAINT subscriptions_dates_valid CHECK (starts_at < ends_at);

-- a cross-column invariant on one row: the valuable CHECK
ALTER TABLE employees
  ADD CONSTRAINT salary_within_band CHECK (salary BETWEEN 0 AND salary_cap),
  ADD CONSTRAINT manager_not_self  CHECK (manager_id IS NULL OR manager_id <> id);

-- a reference across rows: only a FOREIGN KEY can enforce this
ALTER TABLE orders
  ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id) ON DELETE RESTRICT;

The framing that earns the staff answer is that these answer different questions. Service-layer validation answers "did this request arrive well-formed?" A constraint answers "is this row, right now, in a state the rest of the system can assume is impossible?" Validation protects a request; a constraint protects a dataset. They come apart in four ordinary ways:

Interview trap — "I validate in the service, why do I need a constraint?"

1. The second write path. A backfill script, a data import, an admin tool, a migration. All of them can write; none go through your service. 2. The race. Two requests both pass validation against "quantity > available". Both succeed, the invariant is violated, and no throw ever fired, because each request was individually valid. 3. Partial failure. The service validates, writes to two tables, the second write fails, the transaction rolls back — good — but the same path invoked from a queue consumer with a slightly different ordering does not. 4. The rule changes. The code deploys on Tuesday; the constraint is dropped on Wednesday by a migration that relaxes it. For a day the old rule is gone and the new one is not yet in the code, which is exactly when bad data gets written.

Trade-off — should the database enforce the foreign key?

Enforce it when the data outlives the code that writes it, when more than one service or job writes the table, or when the reference is load-bearing. A foreign key is a distributed assertion that a certain kind of bad state is now impossible, and it holds for every future writer including the one you have not written. Do not enforce it when the referenced rows live in another service, when the table is sharded or the reference is intentionally soft, or when the write path cannot tolerate the lock — a hot parent row, a customer with 40,000 orders, serialises inserts and shows up as lock waits rather than as slow queries. Flips on: who else can write this table. One writer deployed with the schema, an application check is fine and cheaper. Three writers, one a data import that runs outside your deploy, the constraint is what stops a bad import corrupting the table and the lock cost is the price of that.

ON DELETE is a data-destruction policy, not a convenience setting
ActionWhat happens to childrenUse when
RESTRICTRejects the parent delete immediatelyThe default worth defaulting to. Children must be explicitly re-homed first
NO ACTIONRejects at statement or constraint-check time — deferrable, so at commitYou want to move rows, then delete
CASCADEDeletes the childrenThe child is a genuine component of the parent — order_line rows have no independent meaning — and there are few of them

The production shape of the CASCADE mistake is worth knowing because it has happened. An engineer runs a one-off DELETE FROM users WHERE email = ...; it takes 4.7 seconds and locks two tables, and nobody is down. Six weeks later a support ticket arrives because a customer's entire order history has vanished from the admin UI. The cascade had been applied by habit for an unrelated child table and took 41,000 orders rows with it. The delete was not inside an explicit transaction because the client wraps a single statement in an implicit one — which is correct behaviour, and is exactly why nothing could be rolled back. Prevention: default to RESTRICT, treat CASCADE on a table that grows without bound as a review flag, and wrap any large DELETE in an explicit transaction after a SELECT count(*).

ALTER TABLE category
  ADD CONSTRAINT category_parent_fk
  FOREIGN KEY (parent_id) REFERENCES category(id)
  DEFERRABLE INITIALLY DEFERRED;   -- checked at COMMIT, not per row

BEGIN;
  -- swap two parents. Each step transiently violates the constraint.
  UPDATE category SET parent_id = 12 WHERE id = 11;
  UPDATE category SET parent_id = 11 WHERE id = 12;
COMMIT;   -- the only place the constraint is evaluated, and it passes

The lesson in a small feature is large: a constraint is a statement about transaction boundaries, not about rows. It exists for invariants spanning multiple rows whose correct write order is not the obvious one — building a tree from the leaves up, swapping two adjacent parents, a multi-row re-parenting. And the first question when you find yourself working around a constraint is whether the invariant genuinely is per-row.

Adding a constraint to a table that already has 400 million rows

Adding a constraint to a large table is a migration with a data-quality prerequisite, not a schema change. Related: constraints are validated on UPDATE as well as INSERT, so an update touching a CHECKed column is validated the same way.

05

Normalisation & denormalisation

Normalisation is not tidiness and not a purity ladder. It is a set of rules for removing redundancy caused by functional-dependency violations, and the reason to remove it is mechanical: it is only safe to store a fact in one place if updating the fact requires updating that one place. A functional dependency A → B means any two rows agreeing on A must also agree on B.

Interview trap — "normalisation makes writes slower, so it's outdated"

The claim fails on its own terms, because it compares an insert into one denormalised table against an insert into one normalised table with no joins — which is not the comparison normalisation asks for, since the denormalised form is not admissible: it stores the same fact three times, so the cost model differs in kind, not in degree. You cannot move Alice without touching three rows. The honest trade-off is that normalisation removes anomalies — classes of incorrect data no application code can prevent, because the code is not the only writer — while denormalisation buys read latency and join avoidance at the cost of a second consistency mechanism you now have to build, run, and monitor. The common failure is the reverse sequence: denormalise everywhere "to be fast," then discover you have three code paths that must update five tables in the right order or they disagree. That is not performance engineering; it is a distributed system with no transactions, and it is far more expensive than a join.

The normal forms, and the anomaly each one removes
FormRuleFixes
1NFAtomic values — no arrays, no repeating groups, no col1, col2, col3 columnsMulti-valued attributes and ragged rows
2NF1NF + no partial dependency on a composite key; every non-key column depends on the whole keyUpdate and insertion anomalies in tables with composite keys
3NF2NF + no transitive dependency: no non-key column depends on another non-key columnThe update anomaly — the one that actually bites
BCNF3NF + every determinant is a candidate keyNon-trivial FD violations a 3NF schema still permits
4NF3NF + no non-trivial multi-valued dependencyInsertion anomalies where the redundancy is an MVD, not an FD
5NF4NF + no join dependencyMVD cases 4NF cannot decompose further. Rarely reached
Interview trap — what is the difference between 3NF and BCNF?

Both forbid a non-key attribute from depending on a non-key attribute; the gap is who the determinant is. 3NF relaxes this when the determinant is a candidate key — it only requires that no non-key attribute depends on a non-key attribute, so A → B where A is another candidate key is fine. BCNF does not relax it: every determinant must be a candidate key, so A → B is illegal unless A itself is one. The gap appears with overlapping candidate keys — say (student, subject) and (student, exam) are both candidate keys and there is a dependency student → tutor. That is legal in 3NF and illegal in BCNF. The pragmatic answer: 3NF is almost always good enough, BCNF is the theoretical refinement, and the difference matters far less than whether anyone has actually checked what the candidate keys are.

Three anomalies follow from the unnormalised orders table that carries customer_name and customer_city alongside the order, and each one is an incident someone has already had. Update: Alice moves to Manchester — update one row and every report about her city is wrong, or update three and you have a loop that misses rows added while it runs. Insertion: a new customer with no orders cannot be recorded at all, because there is no row in which to put them without inventing an order. Deletion: you delete order 3, the only order that happened to record her city that month, and you have now destroyed information about a customer who still exists — deleting an order destroyed data about a customer, which is the tell that the table is holding two entities' facts at one grain.

Must remember — state the grain, in one sentence, in the table comment

"One row per order_line" costs nothing and prevents an entire class of incident. Grain determines the primary key, what a UNIQUE constraint can even mean, which aggregations are possible without double-counting, and whether a join to another table multiplies rows. Almost every schema design disagreement is a grain disagreement in disguise: two engineers each build a correct orders table and the bug appears when the code assumes one row per order and gets three. Every double-counting bug in production is a grain bug that nobody wrote down.

-- WRONG: joins order-level to line-level, then sums a line measure
SELECT o.id, o.status, SUM(l.amount) AS revenue
FROM orders o JOIN order_lines l ON l.order_id = o.id
GROUP BY o.id, o.status;   -- revenue is multiplied by average lines per order

-- RIGHT: aggregate to the grain you need BEFORE joining
WITH lines AS (
    SELECT order_id, SUM(amount) AS line_total
    FROM order_lines
    GROUP BY order_id
)
SELECT o.id, o.status, l.line_total AS revenue
FROM orders o
JOIN lines l ON l.order_id = o.id;

Two shapes of this bug are worth naming. The simple one is a join that also selects an order-level column and looks fine, because the order columns are simply repeated on each output row and only the aggregate is wrong. The dangerous one is the three-way join — adding products to get a product name, where a line's product joins to five variants, produces fifteen rows and a SUM that is five times too large. In a financial report that passes review, because the headers are right and the numbers are plausible. The detective step before the fix is SUM(DISTINCT ...), which confirms the diagnosis; the real fix is the CTE above; the prevention is the table comment.

Three ways to denormalise — and they fail differently
MechanismFreshnessWrite costFailure mode
Trigger or GENERATED columnImmediate+1 write per row on the parentSlows the write path. The usual choice when the value is read constantly
Materialised viewUntil REFRESHZero on the base tablesSilently stale with no error at all. Needs a refresh schedule and a staleness SLA

Trade-off — should I denormalise?

The condition that says yes needs all three: the join is on a measured hot path, you have the numbers to prove it, and you can name how the redundancy stays consistent. If any one is missing — it is a slow suspicion, you cannot say how the copy is kept in step, or the "denormalised" column is one three services write to — the answer is no. The reason to be conservative is that denormalisation converts a consistency problem the database already solves in one transaction into a distributed consistency problem you must solve yourself across a trigger, a refresh, or a service boundary. The database's version is synchronous and already tested; trading it for a millisecond of join latency is usually a bad deal, and it is always a bad deal if you are guessing rather than measuring. Flips on: reversibility — denormalising is cheap to add and expensive to remove, because by the time you want the redundancy gone there are four code paths and a job that read the column and cached it. So normalise first, then denormalise one measured path deliberately and own the sync.

06

Relational algebra & the execution model

Relational algebra is a small closed set of operators; SQL is a syntax for a subset of it. The reason to know it is not academic — the fixed clause order follows directly from the operators, and every one of the SQL questions candidates get wrong is explained by that order.

The operators every plan is a composition of
OperatorSQL formWhat it does
Selection σWHEREFilters rows by a predicate
Projection πSELECT col_listChooses columns — and is what gives them names
Join ⋈JOIN ... ONCombines relations on a condition
Union ∪UNIONCombines relations, removing duplicates
Rename ρASRenames attributes
Aggregation γGROUP BY, COUNT, SUMGroups and reduces
Semi-joinEXISTS, INKeeps left rows that have a match in right
Anti-joinNOT EXISTSKeeps left rows that have no match in right
Interview trap — why can I not use a SELECT alias in WHERE?

Because WHERE filters rows, and the alias does not exist until SELECT has run, and SELECT runs after WHERE. It is not a parser quirk — it follows from the algebra. WHERE operates on a relation of tuples of the base schema; projection is what produces the relation with your chosen names. ORDER BY is different because it is specified to run after SELECT, which is why ORDER BY total works while WHERE total > 100 does not. The useful half of the answer is the workaround and its cost: repeating the expression is free, because the optimiser evaluates it once. The wrong workaround — wrapping the query in a subquery or CTE and filtering on the alias in the outer query — works and frequently blocks predicate pushdown to the scan, putting the filter above a materialisation boundary. If the expression is expensive enough that you want to name it, the right fix is a generated column or a functional index.

Must remember — predicate pushdown, and the three cases it cannot do

Pushing filters toward the leaves is the optimiser's most valuable transformation: a filter applied early removes rows that would otherwise be joined, aggregated, sorted, or shipped. Joining 41M orders to 8M customers and then filtering to 40K is a different cost model from scanning 41M, filtering to 40K, scanning 8M, and joining 40K to 40K. It fails in three cases worth naming. 1. A predicate on the nullable side of an outer join cannot be pushed past the join without changing the result: LEFT JOIN customers ... WHERE c.tier = 'GOLD' would drop the unmatched orders the outer join was meant to preserve. 2. A volatile expression cannot be pushed, because evaluating it earlier may produce a different answer. 3. A correlated subquery predicate is pushable only when the subquery is uncorrelated. Add the sting: filtering after an outer join also discards the unmatched rows, silently converting the LEFT JOIN into an inner join — so the optimiser is right not to push it, but the query is still wrong.

Interview trap — does join order matter?

The reflexive answer is "no, the optimiser handles it"; the sharper answer is "yes, and here are the three cases where it does." For most queries the planner permutes orderings and picks by estimated cost, so your ordering is noise. It becomes yours when the planner stops searching exhaustively, when it is misinformed — since order is chosen from estimated row counts, a stale statistic gives a bad order exactly as readily as a bad access path, and the fix is ANALYZE, not reordering — and, the case that actually bites, when the join types make the order semantically load-bearing. LEFT JOIN is not associative: a LEFT JOIN b JOIN c and a LEFT JOIN (b JOIN c) are different queries with different results, and the parser is entitled to regroup them. That is a correctness hazard rather than a performance one, and raising it unprompted is the difference between a senior answer and a staff one.

There is exactly one logical plan for your query and a very large number of physical plans, and choosing between them is a cost-estimation problem driven by statistics that may be wrong. Which is why "add an index and see what happens" is not a debugging method — you are perturbing the cost model and hoping the guess changes. The method is to make the statistics true (ANALYZE), then read what the optimiser does with the truth. A monthly report that used to take 4 seconds and now takes 3 minutes with unchanged SQL is a changed plan, and a changed plan needs a changed cause: stale statistics, a lock, or index bloat after a year of churn. Diagnose by comparing estimated to actual rows at the first node where they diverge by more than roughly an order of magnitude — everything below it is a consequence.

Scaling lenses on relational data

"Relational databases don't scale" is half true in a way that makes it worse than useless: the true half names a specific structural limit, and the false half lets people skip the fix. The accurate statement is that a relational database's ceiling is a write-concurrency ceiling, not a data ceiling — and a missing composite index or a stale statistic looks exactly like hitting it. Teams that conclude "NoSQL" from a slow table usually needed ANALYZE and one index, and end up with a document store that is slower, has no transactions, and cannot answer the join they needed six weeks later.

What actually bounds a relational write path

Interview trap — "which database for a high-write system?"

The reflexive answer is DynamoDB or Cassandra, and it is usually driven by a benchmark that measured single-row puts against a database that was misconfigured. The senior answer starts by asking what the write actually is. If it is append-only telemetry, the Postgres write path is a sequential WAL append and a heap insert — partition by time, and most NoSQL stores handle that no better. If it is a hot key, every write touching the same row or partition, then no store helps: a single partition is a single-node bottleneck in every system, and the fix is to spread the key, not to change databases. The genuinely hard case is high write volume plus rich ad-hoc queries, and the answer there is usually "shard by tenant on a relational engine" — keeping the joins you cannot give up and giving up only the write throughput you were not using. The point worth making out loud: the bottleneck is concurrency, and every store has a concurrency ceiling, at a different shape.

A design review that jumps to rung 7 without having measured rungs 1 and 3 is not making a technical decision, it is making a social one. The related staffing trap: sharding early to "prepare for scale" while the schema is small is the worst possible timing, because the resharding procedure is the one part that cannot be rehearsed at small scale — the moment you have 4 million rows, the shard key is chosen, cross-shard uniqueness is lost, and the only options are a live resharding migration or accepting the mistake. Spend the same quarter making the shard key discoverable: identify the candidate keys, find the one every query already carries, check its cardinality and distribution, and note the one or two queries that would fan out.

Sharding does not remove distributed-systems problems; it converts each relational guarantee into a harder one you now have to build, test, and monitor. And the two you lose first — a UNIQUE constraint and a foreign key — are the two cheapest integrity guarantees in SQL. That is not a performance regression you can buy back with more hardware; it is a correctness property you have to re-implement, and the application-level replacement is strictly weaker.

Trade-off — when is sharding the right answer?

The condition is that you have a tenant or region key that every query can carry, and the data for one key genuinely belongs together. Not "we expect high traffic" — at high traffic, rungs 1–5 get you a long way. The specific shape is a multi-tenant system where one query almost always touches one tenant, the tenant boundary is also a compliance or ownership boundary, and growth within a tenant is genuinely unbounded. Under those conditions sharding is close to free: the shard key is the partition key, joins stay within a shard, and the foreign key problem largely disappears because related rows travel together. Under any other condition you are buying cross-shard transactions, cross-shard uniqueness, cross-shard joins, and a resharding procedure, in exchange for write throughput a bigger instance and one more index would probably have bought. The question that decides it, and that you should ask in the review, is: "what is our shard key, and show me the three most common queries — which shard does each touch?" If any of them touches all of them, you have not chosen a shard key, you have chosen a fan-out.

Which closes with the framing that makes "which database" a sequence rather than a preference, and the order is the point. 1. What is the access pattern — one fixed key lookup, a few known queries, or arbitrary ad-hoc predicates? This alone eliminates most candidates. 2. What is the write volume, and is it append-only or a hot key? 3. What is the consistency requirement, stated as a bound? "Immediately" or "within one second" are specifications; "eventually" is not. 4. What is the query flexibility requirement? Ad-hoc predicates across entity types is the one thing relational engines are uniquely good at. 5. What does the team already operate? A new store is an on-call rotation, a backup story, a restore test, and a runbook before it is a data model. 6. What does it cost to undo? This is the one that gets skipped — the answer for "add a cache" is small; the answer for "move to a document store" is a rewrite of every query and every test. If the answers to 1 and 2 are a fixed key lookup and high volume with no ad-hoc queries, DynamoDB is right and the conversation was short.
