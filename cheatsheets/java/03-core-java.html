The five places where Java's abstraction leaks: what every object silently inherits, why == on a boxed value lies, how failure is declared and propagated, what package-private actually scopes, and what erasure deletes.

If you only remember five things

  1. Equal objects must share a hashCode; the reverse is not required. Override both together. A hash-based lookup hashes first and compares only inside that bucket, so a mismatched hash means two equal keys are never even compared.
  2. Autoboxing calls valueOf(), which caches -128..127. Inside that range two boxed values are the same object, so == agrees with equals() by accident. Outside it, == compares references and is false for equal numbers.
  3. Unboxing null throws NPE at the unboxing site, not where the null originated — a missed Map.get() is the common source, and the stack trace points at arithmetic.
  4. finally always runs, and a return inside it silently discards the one from try. The only things that skip it are System.exit() and a JVM crash.
  5. Generics are erased, so List<String> and List<Integer> are one class at runtime. No instanceof List<String>, no new T[10], and no overloading on a type parameter alone. PECS is what wildcards are for.

01

The Object class

Every class implicitly extends java.lang.Object and inherits equals(), hashCode(), toString(), getClass(), clone(), finalize() (deprecated), and the wait/notify family. The defaults are identity: equals() is reference comparison, hashCode() an implementation-specific integer, practically the memory address. A class representing a value overrides both.

The five rules, and the one that is not required
RuleStatementBreaks when
Reflexivea.equals(a) is true Over-complicated logic that misses the this == o fast path

TransitiveTwo true comparisons imply a third Surfaces only for specific data combinations, and silently corrupts sorted and hashed structures
ConsistentSame answer while the compared state is unchanged A field used by the comparison is mutated mid-life
hashCode consistency a.equals(b) true implies a.hashCode() == b.hashCode() Overriding equals() and leaving hashCode() alone
Not requiredUnequal objects may share a hashCode() Nothing — a collision is legal and expected at scale. The reverse is what is forbidden
 
@Override

    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Point p = (Point) o;
    return x == p.x && y == p.y;
}

@Override
public int hashCode() {
    return Objects.hash(x, y);   // changes whenever equals() does
}

@Override
public String toString() {
    return "Point{x=" + x + ", y=" + y + "}";
}

Interview traps

equals(MyClass other) is an overload, not an override. The parameter type does not match equals(Object), so Object's method stays live and collections call the wrong one.

A hashCode() that returns a constant compiles and satisfies the contract — every instance lands in one bucket, degrading lookups to O(n). This is the one contract-compliant implementation that is still a serious performance bug.

toString() is a contract, not a convenience. The default is ClassName@hexHashCode with no field content, and its output routinely ends up in logs, parsed by audit tooling, and diffed across versions.

clone() is the design Java moved away from

Object.clone() is protected and shallow. Implementing Cloneable — a marker interface with no methods — is not enough: the class must override clone() as public or it throws CloneNotSupportedException. Nothing in the compiler stops you from publishing a shallow copy whose mutable fields are shared with the original. A copy constructor saves nothing meaningful and removes every one of those failure modes.

Must remember — identity equality is sometimes correct

A Thread, a connection, a lock — anything that denotes a genuinely unique instance rather than a value is better with Object's default. Overriding equals() on those classes is the error, and the fields-based version costs real time on every call once a class sits in a hot Set.

02

Wrapper classes & autoboxing

Wrappers exist because generics and collections take reference types only: List<int> does not compile, List<Integer> does. Autoboxing is the compiler calling valueOf(); unboxing is the reverse, and it is the direction that throws.

What is cached, and what == therefore does
WrapperCached range== on two equal values
Integer, Short, Long -128 to 127, guaranteed by the JLS; Integer's upper bound widens with -XX:AutoBoxCacheMax True below the bound, false above
ByteIts entire rangeTrue — but only because every byte is cached
Character0 to 127True for ASCII, false above it
BooleanTRUE and FALSE, always True — it is a singleton, so it works by luck rather than by design
Float, DoubleNever cached Never reliable, at any value
 
Integer a = 100, b = 100;
a == b;                            // true  — same cached instance

Integer x = 200, y = 200;
x == y;                            // false — two distinct objects

Map<String, Integer> counts = new HashMap<>();
int total = counts.get("missing") + 1;   // NPE — unboxing null

Long sum = 0L;                     // unbox, add, rebox — every iteration
for (long i = 0; i < 1_000_000; i++) sum += i;
long sum2 = 0L;                    // allocates nothing
Interview trap — the NPE that points at the wrong line

Unboxing null throws at the point of unboxing, which is often far from where the null came from. A Map.get() miss, or an unset Boolean entity field on a nullable column, produces an NPE whose stack trace points at arithmetic rather than at the lookup. The fix is Objects.equals() or an explicit null check, not defensive arithmetic.

The mirror case: comparing a wrapper to a primitive unboxes the wrapper. It does not autobox the primitive, so wrapper == 5 is a numeric comparison and wrapper == otherWrapper is a reference comparison.

Trade-off — primitive or wrapper

The default is the primitive. Flips on: the value must be able to represent a genuine "not provided" state, or it must be a generic type argument. Outside those two cases a wrapper is a null-safety hazard and, in a loop, an allocation per iteration. That last cost is a genuine hot-path concern and largely irrelevant in ordinary business logic, where I/O dominates — the debuggability win is not. The mirror trap is Map<String, Object> used to avoid writing a DTO: it throws away every compile-time check the DTO would have given you.

new Integer(100) bypasses the cache entirely and has been deprecated since Java 9 — valueOf() is the cache-aware factory. Wrapper identity does not affect Set<Integer> membership, since a set compares with equals(); the trap is confined to explicit ==.

03

Exception fundamentals

static int test() {
    try { return 1; }
    finally { return 2; }        // returns 2 — finally wins
}

try (FileInputStream in = new FileInputStream("data.txt");
     FileOutputStream out = new FileOutputStream("copy.txt")) {
    in.transferTo(out);
}   // both closed, out first; a close() failure is SUPPRESSED

try {
    parseConfig();
} catch (IOException e) {
    throw new ServiceStartupException("Failed to start", e);
}
The finally trick question, and its worse twin

finally runs even when the try block returns — the return value is computed first, then finally executes, and a return inside it silently discards the original. The only things that skip it are System.exit() and a JVM crash during the try.

The worse twin: if finally throws, that exception replaces the one from the try entirely — the original is gone, not suppressed. That is precisely what try-with-resources exists to stop.

The unchecked exceptions worth knowing cold

NullPointerExceptionA method call or field access on null Also the unboxing trap, above

ArithmeticExceptionInteger division by zero 5.0 / 0 is Infinity; 0.0 / 0.0 is NaN. IEEE 754, not an exception
IllegalArgumentExceptionAn argument violating the documented contract NumberFormatException extends it
IllegalStateExceptionCalled at the wrong point in the object's lifecycle —
Three compile-time rules that catch people writing catches
RuleWhat happens if you break it
A catch for a subclass must precede one for its superclass The subclass catch is unreachable, and that is a compile error
A catch for a checked type nothing in the try can throw Compile error — but the same catch on an unchecked type is always legal
Multi-catch catch (A | B e) A and B must not be subtypes of each other, and e gets their common supertype
Must remember — where a broad catch is correct

catch (Exception e) in a service body swallows unrelated bugs alongside the failure you meant, which is why it is a smell. It is not a smell at a top-level web boundary, where any unexpected failure must become a safe response — that is the one place the broad catch is the deliberate design, and the one place that separates "our bug" (500, page someone) from "bad input" (400, log it).

04

Exception design

Checked or unchecked, and whether you need a new class at all
The failure is…ExtendWhat that costs the caller
An external, recoverable condition the caller can act on — insufficient funds, file not found ExceptionEvery caller must catch or declare it, and think about it
A programming error or contract violation — bad state, illegal argument RuntimeException Nothing is forced, and the "recovery" is fixing the bug. Forcing a catch would be boilerplate without safety
Already covered by a JDK type — IllegalArgumentException, IllegalStateException That type Nothing. A custom class here adds API surface and a name someone has to learn
A third-party library type escaping into your API A wrapping unchecked type Keeps the dependency's exception types out of every caller's signature

A custom type earns its complexity where callers must catch that specific failure distinctly — retryable versus permanent, so handling branches on the type alone. A team convention of "always unchecked" is not a reason: the decision is per exception, and a checked exception every caller merely catches and rethrows is not doing its job.

Interview trap — suppressed is not the same as lost

If the try body and close() both throw, the try body wins as the propagated exception and the close() failure is attached as a suppressed exception, readable via getSuppressed(). Nothing is lost. The manual pre-Java-7 pattern was strictly worse: a close() failure in finally overwrote the original outright. That difference is the whole argument for try-with-resources.

Resource acquisition is a separate case: if the constructor throws, there is nothing to close, and only the constructor's exception propagates.

try-with-resources, precisely
QuestionAnswer
Which types qualifyAnything implementing AutoCloseable
Order of close()Reverse of declaration — the last declared closes first
Both body and close throwBody propagates; close's is suppressed
What it removesThe manual finally block, and with it the leak-on-one-path bug class
Must remember — always chain the cause

throw new ServiceException("Failed", e) preserves the original getCause() and prints the full chain. throw new ServiceException("Failed") destroys the trail, and the stack trace you get in production names the wrong layer. This is a one-argument omission with a large diagnostic cost, which is why a linter rule flagging any catch that constructs a new exception without passing the cause is a reasonable team default.

Scaling reality check — exceptions are not free

Constructing a throwable captures a stack trace, so an exception thrown on every request for an expected outcome is a control-flow statement paying exception cost. Signal absence with Optional.empty() or null instead. The line: occasional throw on a genuine error is correct; routine throw is a design smell, and it is both slower and harder to read. The related trap is printStackTrace(), which writes to stderr where production log collection usually is not watching.

Production scenario — the exception with no context

Problem: a batch job reports a bare NullPointerException that cannot be traced to anything. Investigation: the layer that caught it logged "query failed" and rethrew a fresh exception with no cause attached. Root cause: the original stack trace was discarded at the wrap. Solution: chain the cause at every boundary. Prevention: static analysis on catch blocks that construct a new throwable without a cause argument.

05

Packages & access control

A package is a namespace that maps to a directory and scopes default (package-private) access; the full modifier table is Volume 2's. The package declaration must be the first non-comment line in the file, and java.lang is implicitly imported.

Interview traps

A wildcard import never reaches subpackages. import java.util.*; does not bring in java.util.concurrent — each level needs its own import, which is why IDE autocomplete goes quiet there.

Package-private is scoped to the package name, not the directory or the JAR. Two classes both declaring package com.example.billing; see each other's package-private members even from different JARs on the classpath, because the JVM checks the name string and nothing else.

That is also why it is not a security boundary. Anyone can declare a class under your package name and gain access to it. Only the module system's exports and opens provide enforced encapsulation.

Classpath versus module path, Java 9 onward
ClasspathModule path (JPMS)
What is visibleEvery public class on the classpath Only packages the module explicitly exports
Split packagesAllowed, and the source of real conflicts Disallowed — module resolution fails
Declared byImplicitly, by directory and JAR structure An explicit module-info.java
What public meansVisible everywhere on the classpath Visible within the module only, until the package is exported
Must remember — the boundary is your API surface

Package-private members and non-exported packages are implementation detail: you may refactor them freely. Anything public and exported is API surface, subject to semantic-versioning discipline. That is also the precise compatibility rule: renaming an internal helper from public to package-private is safe, while adding a checked exception to a widely-called method is a breaking change for every existing caller.

Two structural choices come up in review, neither universally right. Packaging by feature keeps one capability's code together and scales better for large, independent feature sets; packaging by layer — controllers, services, repositories — can be clearer in a smaller codebase. A zero-public-class package behind a single facade encapsulates well, at the cost of forbidding several independently useful entry points. The measure is cohesion, not size.

06

Generics fundamentals

Before Java 5, collections held raw Object references: a type mismatch compiled cleanly and surfaced as a ClassCastException at retrieval. Generics move that check to compile time — which is what makes JpaRepository<Order, Long> reusable across every entity without per-entity boilerplate.

// extends covers BOTH inheritance and implementation in a bound
static <T extends Comparable<T>> T max(List<T> list) { ... }

// class bound first, then any number of interface bounds
class Sorter<T extends Number & Comparable<T> & Serializable> { ... }

// List<int> does not compile; List<Integer> does
// new T[10] does not compile either
Interview traps

There is no implements in a type bound. <T extends Comparable<T>> is correct even though Comparable is an interface, and a class bound must be listed before any interface bounds. A bound means "this type or any subtype" — Number itself is admitted by <T extends Number>.

A raw List and List<Object> are not equivalent. The raw type disables checking entirely, reintroducing the exact ClassCastException generics were added to remove; List<Object> is fully checked, just permissively.

Primitives are not type arguments. This is also why new T[10] fails: array creation needs a concrete runtime component type, which erasure cannot supply. The production workaround is an Object[] plus a narrowly scoped @SuppressWarnings("unchecked") — which is exactly why ArrayList<T> is usually the better answer.

Trade-off — a bound, or nothing

A bound turns an unchecked cast inside your method body into a compile error, which is the entire point: <T extends Comparable<T>> lets you call compareTo() safely. Flips on: an unchecked cast inside a generic class is the signal that the parameter should have been bounded. A bound that is too broad forces the same casts back in; one that is too narrow refuses types no caller needed excluded.

The mirror error is over-genericising. A method whose only caller ever passes String gains nothing from a type parameter — the flexibility is unused complexity, and a concrete signature is clearer.

07

PECS & type erasure

Generics are invariant: List<String> is not a subtype of List<Object>. That is deliberate — otherwise you could insert an Integer into what is really a List<String>, and unlike arrays, generics carry no runtime type information to catch it.

What each wildcard lets you do
WildcardMeansRead asWrite
? extends TA list of T or some unknown subtype T, always safeNothing but null
? super TA list of T or some unknown supertype Object onlyT, always safe
?A list of some unknown typeObject only Nothing but null
Must remember — PECS

Producer Extends, Consumer Super, from Effective Java. If a parameter only produces values for you, use ? extends; if it only consumes values from you, use ? super. If it does both, use neither — take an exact type parameter, because a wildcard can never give full read and write flexibility at once. You can never get both from a wildcard.

// the shape Collections.copy() itself uses
static void copy(List<? extends Number> src, List<? super Number> dst) {
    for (Number n : src) dst.add(n);
}
List<Integer> ints = List.of(1, 2, 3);
copy(ints, new ArrayList<Object>());

// what erasure leaves behind
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
a.getClass() == b.getClass();      // true — one runtime class
a instanceof List<String>;       // DOES NOT COMPILE
Everything erasure rules out
You cannot…Because
obj instanceof List<String>The type parameter does not exist at runtime to check against. Only instanceof List<?> compiles
Create new T[10]Array creation needs a concrete runtime component type
Overload on a type parameter aloneBoth methods erase to the same raw signature — a duplicate-method compile error
Declare a static field of type TT is meaningful per-instantiation; static members belong to the class
Write catch (T e)The JVM cannot verify which type was actually thrown

Erasure is also why Jackson needs a TypeReference<List<MyDto>> rather than a bare List.class: with no runtime element type it captures the parameterized signature through an anonymous subclass and recovers it by reflection — the general workaround whenever a library must cross the erasure boundary.
