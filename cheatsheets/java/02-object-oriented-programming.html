The eight concepts every design conversation turns on, and the three places Java quietly refuses to behave the way the textbook version says it does.

If you only remember five things

  1. Writing any constructor deletes the compiler's no-arg one. Hibernate, Jackson and JUnit all instantiate reflectively, so a single new @Entity constructor turns into a runtime failure in a test that passed an hour ago.
  2. Only instance methods dispatch on the runtime type. Fields and static methods resolve by the reference type, so Animal a = new Dog() gives you Dog.speak() and Animal.legs in the same statement.
  3. final on a reference locks the reference, not the object. final List<String> names = new ArrayList<>() is still a perfectly mutable list; the fix is a defensive copy or an unmodifiable view at the boundary.
  4. Encapsulation is protecting invariants, not generating accessors. A public getter and setter for every field is the field re-exposed through indirection; return this.items hands out a live reference and no protection at all.
  5. Favor composition over inheritance is a default, not a law. It flips back when the relationship is a genuine, stable IS-A whose subclasses stay substitutable — a PaymentException extends RuntimeException is not a mistake.

01

Objects, constructors & this

A class is compile-time metadata — one Class object in Metaspace. An object is a runtime heap allocation, and there may be zero or millions of them for one class. An @Entity class is a blueprint; each database row becomes a separate object wearing it.

Interview trap — the constructor that deletes another

The compiler generates a default no-arg constructor only if you declare none at all. Add one parameterised constructor and the no-arg one is gone. Jackson, Hibernate and JUnit instantiate reflectively and need it back, which is why an @Entity that used to work fails the moment a constructor is added. Declare the no-arg one explicitly — protected for an entity, so the framework can use it while application code is nudged through the real constructor.

class Employee {
    private String name;
    private double salary;

    Employee() {
        this("Unknown", 0.0);      // MUST be the first statement
    }

    Employee(String name, double salary) {
        this.name = name;          // the parameter shadows the field
        this.salary = salary;
    }
}

this has four uses: disambiguate a shadowed field, chain to another constructor, pass the current object to something else, and return this for a fluent builder. It is a reserved keyword, not a variable — it cannot be reassigned, and it does not exist inside a static method, which has no current instance to point at.

The constructor mistake that is not a compile error

Write name = name; in a constructor where the parameter shadows the field and the field silently keeps its default. Nothing fails, no test fails, and the object exists in a state the class was supposed to make impossible — the same class of bug as a public setter, arrived at by accident.

02

static

static moves ownership from per object to per class: resolved at compile time, and never part of dynamic dispatch — static methods resolve by the compile-time type of the reference (section 05).

What can carry the modifier
MemberCan be static?Note
FieldYesOne copy shared by every instance
MethodYesNo this, so no instance fields by name
Nested classYesNo implicit reference to an outer instance, unlike an inner class
BlockYesstatic { } runs once, during class initialisation
ConstructorNoThere is no instance in a static context to construct
Top-level classNoAlready effectively static; only nested classes can say it
Static state is lazy, once per class, and it does not reset

Static fields and static { } blocks initialise on the class's first active use — not at JVM startup — and exactly once per class loader. Two consequences candidates rarely produce: two unrelated tests that pass alone and fail together are almost always sharing static state in one JVM, and a static initialiser that throws poisons the class for good — ExceptionInInitializerError on the first attempt, NoClassDefFoundError on every one after.

@Service                     // one instance for the whole app:
public class ReportService {   // effectively a static, managed by the container
    private String lastReport; // shared by every concurrent request thread

    public Report build(String user) {
        this.lastReport = user + ": report";
        return new Report(lastReport);
    }
}
Production scenario — the cross-user data leak

Problem: a @Service returns one user's data to another. Investigation: the field is a plain instance field, not static, and the method is not synchronized. Root cause: Spring beans are singletons, so an instance field on a @Service is shared mutable state — the developer's per-request expectation never existed. Solution: move the per-request value into a method local, or a request-scoped bean. Prevention: never put per-request state on a singleton bean, and treat lint rules banning mutable static fields as load-bearing rather than pedantic.

What static is for: constants, pure stateless utility methods, and the initialization-on-demand holder singleton — a private static nested class whose construction the JVM guarantees happens once, correctly, with no lock. Not for anything that has to vary per user, per request, or per test.

03

Encapsulation & access modifiers

There is no JVM mechanism here. Encapsulation is a compiler check plus a discipline you either keep or quietly abandon — reflection walks straight past it with setAccessible(true), legitimate in a framework and a smell in business logic. The point is not hiding; it is that no public path leaves the object in a state its own invariants forbid.

Access, and what each level costs you
ModifierSame classSame packageSubclass, other packageUnrelated package
privateYesNoNoNo
defaultYesYesNoNo
protectedYesYesYes — through a reference of its own typeNo
publicYesYesYesYes
Interview trap — protected is not "package plus subclasses"

protected does grant the whole package, so any class in the same package reaches it with no inheritance relationship at all. The sharp edge is the cross-package case: a subclass in another package may only touch that member through a reference of its own type or a subtype. Through a plain Account-typed reference it will not compile. Same rule applies to a protected constructor, which is why package-private constructors are not subclassable from another package at all.

The two leaks that survive a review

Getter/setter for everything. Re-exposes the field through indirection with none of the validation that was the point. Generating a private field and a pair of unconstrained accessors is encapsulation in name only — the test is whether any sequence of valid-looking public calls can produce an invalid state.

Returning live internal state. return this.items; hands the caller a reference to your List; they can add, remove and clear it with no validation and no notification. Note the fix is not symmetric: Collections.unmodifiableList is a live view — if any other reference mutates the backing list, the change shows through it. Only a defensive copy gives the independent guarantee.

public class BankAccount {
    private double balance;                   // never exposed as a field
    private final List<Txn> history = new ArrayList<>();

    public void withdraw(double amount) {     // the only way the balance goes down
        if (amount > balance) throw new IllegalStateException("Insufficient");
        balance -= amount;
        history.add(Txn.of(amount));
    }

    public List<Txn> getHistory() {
        return List.copyOf(history);           // not `return history;`
    }
}

Read access is not the enemy. A getter returning an immutable value, or a getBalance() that computes a derived figure cheaply and without side effects, is encapsulation working. What breaks invariants is uncontrolled mutation — which is why validation in a setter is worth nothing if the constructor takes the same field and skips the check.

04

Inheritance & the IS-A relationship

A subclass object physically contains the memory layout of every class in its chain, so a Car holds Vehicle's fields plus its own. It does not inherit access to a parent's private field by name — that field is in the object, reachable only through whatever public or protected members the parent exposes. Constructors are never inherited at all.

Why single inheritance, stated properly

Java allows exactly one extends because two parents supplying conflicting implementations of the same signature leave the compiler with no defensible choice. It is the diamond problem — an ambiguity problem, not a "code duplication" one. Interfaces sidestep it because they carry constants rather than competing state, and since Java 8 they can carry default bodies too, which is why a conflict between two of them is still an error you must resolve yourself.

class Rectangle {
    double width, height;
    void setWidth(double w)   { width  = w; }
    void setHeight(double h) { height = h; }   // independent - that is the contract
}

class Square extends Rectangle {
    @Override void setWidth(double w)   { super.setWidth(w);  super.setHeight(w); }
    @Override void setHeight(double h) { super.setHeight(h); super.setWidth(h); }
}
When the answer is still inheritance

The test is whether a PaymentException genuinely is-a RuntimeException and stays substitutable in a catch block — it does, so extend it. The same goes for a family of Shape subtypes sharing a color field. What is not a reason is convenience: a premium customer that differs only by a tier value is a field, not a subclass. A hierarchy four or five levels deep is where reviewers start asking whether behaviour is still traceable, and at six or more constructor parameters they start asking for a builder.

05

Polymorphism: overloading & overriding

Overloading is resolved at compile time from the declared argument types. Overriding is resolved at runtime: the JVM looks the method up in the object's actual class and walks up the hierarchy only if that class has not overridden it.

class A {
    int x = 1;                              // field
    static String who() { return "A"; }     // static method
    void speak() { System.out.println("A"); }
}

class B extends A {
    int x = 2;                              // hides A.x — no override
    static String who() { return "B"; }     // hides A.who()
    @Override void speak() { System.out.println("B"); }
}

A ref = new B();
ref.speak();               // B  — runtime type
System.out.println(ref.x); // 1  — reference type
A.who();                   // "A" — compile time
The two kinds, and what each one is blind to
AspectOverloadingOverriding
SignatureMust differMust be identical
ResolvedCompile time, from declared argument typesRuntime, from the object's actual class
Subtype constraintNoneSame or narrower return; access can widen but not narrow
Checked exceptionsNoneSame, narrower, or none — never broader
@OverrideNot applicableCatches a typo'd signature at compile time

Covariant returns have been legal since Java 5, and unchecked exceptions are the escape hatch on the exception rule — an override may throw one the parent never declared. final and private methods cannot be overridden at all, and a static one can only be hidden. Every dependency-injected interface call in Spring is this mechanism: the caller sees the interface, the JVM routes the call to whichever bean was wired in.

06

Abstraction, abstract classes & interfaces

Abstraction is the design goal — expose what a type can do, hide how. Abstract classes and interfaces are Java's two tools for it, and the difference that still matters after Java 8 and 9 is instance state and constructors. Nothing else fundamental moved.

AspectAbstract classInterface
Per parent typeOne extendsAny number of implements
ConstructorsYes — and they do real work for the subclassNone
FieldsAny, instance or static, mutable or notImplicitly public static final — constants only
Method bodiesAny mix of abstract and concretedefault and static since 8, private helpers since 9
Reached forClosely related types sharing state and partial implementationA capability unrelated types can adopt
 
interface Flyable   { default void move() { System.out.println("Flying"); } }
interface Swimmable { default void move() { System.out.println("Swimming"); } }

class Duck implements Flyable, Swimmable {
    @Override
    public void move() {
        Flyable.super.move();   // COMPILE ERROR until one is chosen
    }
}
Interview trap — two outdated rules in one answer

"Interfaces can't have implementation" stopped being true in Java 8, and "interfaces can't have private methods" stopped being true in Java 9. Probing for a current answer usually means checking exactly this. The second trap is quieter: when two interfaces supply the same default signature, Java does not pick a winner — it refuses to compile until the class overrides it, optionally delegating with InterfaceName.super.method(). That rule is precisely how multiple interface inheritance stays free of the diamond problem while still carrying behaviour.

Trade-off — interface or abstract class

Reach for the abstract class when the types are a family sharing state — all the Shape subtypes need a color and a shared printInfo(), which is state a plain interface cannot hold. Reach for the interface when you are naming a capability: Comparable, Serializable, a payment plugin contract that third parties will implement without wanting your constructor. Flips on: how many implementations you expect and who writes them.

The failure mode in both directions is the same. An abstract class with one subclass that exists only "for future flexibility" is indirection with no payoff; an interface with twelve methods of which each implementer needs three is a burden being paid in no-op UnsupportedOperationException stubs. Both should be split.

07

Composition, association & aggregation

These three are not three separate concepts — aggregation and composition are both kinds of association, and the whole set is a spectrum of ownership strength measured by one question: can the part exist without the whole, and can it be shared between wholes?

class Car {
    private final Engine engine;    // Car HAS-A Engine — it is not IS-A Engine

    Car(Engine engine) {            // accepts an interface: any impl, any test double
        this.engine = engine;
    }

    void start() { engine.ignite(); }
}
Must remember — composition over inheritance

Inheritance couples a subclass to the implementation of its parent, which is where the fragile base class problem comes from: changing a superclass's internals breaks subclasses that never depended on the changed part, and your own code review does not see it. Composition couples only to a public interface, and because the dependency arrives through a constructor it can be substituted in a test. That is the whole reason Spring DI is built this way.

It is a default, not a ban. A hierarchy that is small, stable and wholly inside one team may be simpler as inheritance, and a genuine IS-A with substitutable behaviour — custom exceptions extending RuntimeException — is not the mistake everyone assumes it is.

Trade-off — what the two approaches cost you

Composition is more flexible, more testable and immune to the fragile base class, and it costs you a few explicit delegation methods that inheritance would have given you free. Inheritance is less code and a stronger guarantee that a type can be treated as its parent — and it is fixed at compile time, single-parent, and shared across every subclass at once. Flips on: whether the "what varies" is a kind of thing or a behaviour you plug in. A pluggable Strategy is composition, and it can be swapped mid-lifecycle, which overriding cannot do; a Shape is inheritance, and a Strategy object that never changes is the same indirection for nothing.

08

final

final means "assigned or defined once" at whatever level you apply it — a compiler-enforced restriction a reviewer can trust, stopping exactly one thing. Which is why the interesting question is what it does not stop.

One modifier, four targets, four different guarantees
Applied toEffectEarns its place on
Local or fieldAssigned once, everConstants; constructor-injected dependencies; captures in a lambda
MethodNo subclass may override itCorrectness or security logic a subclass must not be able to alter
ClassNo subclass at allImmutable types, security-sensitive types, utility classes
ParameterCannot be reassigned in the bodyDefensive signal; converts an accidental reassignment into a compile error
Interview trap — final is not immutable

final List<String> names = new ArrayList<>() locks the reference. The list is still mutable, names.add(...) still works, and a getter returning it still leaks it. The same gap applies to a final class: it blocks subclassing, nothing more, and the class can still hold a mutable field. Real immutability needs private final fields, no setters, and defensive copying on construction and on the way out — so the systematic audit is to walk every field and ask both questions.

A final field does not have to be assigned inline — it needs to be definitely assigned exactly once by the end of every constructor path, which is what makes constructor-injected private final fields safe and what lets @RequiredArgsConstructor generate the constructor for you. And final does not stop a class implementing interfaces, overloading its own final methods, or being abstract — that last combination is a contradiction and a compile error.

The runtime trap: final breaks proxying

Spring's default AOP works by generating a subclass that overrides the advised methods. A final method cannot be intercepted that way, and a final class cannot be subclassed at all — the advice is silently not applied rather than loudly rejected. The mirror image: a final class is still perfectly testable through an interface it implements, so "final hurts testability" is only true of the concrete type.

Why String is final: no subclass can override equals() or hashCode() and break the string pool's sharing assumptions, in a type the JDK trusts for class names, file paths and reflection. Immutability and final-ness reinforce each other there, but they are two separate properties.
