If you only remember five things

  1. volatile gives visibility, never atomicity. volatile int c; c++ still loses updates — the increment is read-modify-write.
  2. The Executors factories are unbounded. Both fixed and cached grow without limit in one dimension or the other. Construct ThreadPoolExecutor with a bounded queue yourself.
  3. Lock.unlock() needs a finally. synchronized releases structurally and cannot leak a lock; an explicit one can, and then blocks everyone forever.
  4. Deadlock needs all four Coffman conditions at once. Prevention is one globally agreed lock order, which makes circular wait structurally impossible.
  5. BlockingQueue replaced hand-rolled producer-consumer. If you must show the manual version, the condition check is while, never if.

Threads: fundamentals & lifecycle

The shared heap is why concurrency is hard: parallelism nearly free, in exchange every shared mutable object is a potential race.

Interview trap

There is no RUNNING state. RUNNABLE covers both executing and waiting for the scheduler. The mirror image: a dump full of RUNNABLE threads at low CPU is an I/O signal, not a compute one.

Interview trap

run() instead of start() compiles, runs, and gives you zero concurrency — it is an ordinary synchronous call on the current thread. Second start() throws IllegalThreadStateException; a thread cannot be restarted. setPriority() is a platform-dependent hint, never a scheduling guarantee.

Production scenario — OOM from a fixed pool

Problem: a service on newFixedThreadPool(10) grows in memory under load, then OOMs. Investigation: heap dump shows millions of queued Runnables. Root cause: the unbounded internal LinkedBlockingQueue — arrival beats service rate, so tasks accumulate instead of the producer being throttled. Solution: explicit ThreadPoolExecutor, bounded queue, CallerRunsPolicy. Prevention: default to explicit construction.

Interview trap

future.get() immediately after submit(), with nothing in between, throws away the entire benefit of submitting asynchronously. The related trap: a Callable that throws has the exception stored in the Future, surfaced only at get() — code that never calls get() never learns the task failed.

Trade-off — fixed rate vs fixed delay

scheduleAtFixedRate measures from the previous run's start, so a slow task piles executions back-to-back. scheduleWithFixedDelay waits after the previous run finishes, so it cannot back up. Flips on: fixed rate for polling where cadence matters more than cost; fixed delay for variable durations.

Shutdown

shutdown() stops accepting new tasks and does not interrupt running ones — they drain. shutdownNow() interrupts and returns the never-started tasks. Executor threads are non-daemon, so a forgotten shutdown() keeps the JVM alive: shut down, then awaitTermination(timeout), then shutdownNow().

class Counter {
    public synchronized void a() { count++; }   // locks this, whole method

    public void b() { synchronized (this) { count++; } }

    private final Object lock = new Object();
    public void c() { synchronized (lock) { count++; } }  // BEST
}
Two traps, same root cause

Locking on this: this is public, so any outside code can synchronize on it and cause contention or a deadlock unrelated to your class. Use a private lock object.

Instance vs static synchronized: the instance method locks this, the static one locks the Class object. Different locks, zero mutual exclusion. Refactoring a method between static and instance silently removes all coordination between callers.

Must remember — when volatile is exactly right

A single flag or reference, written by one thread, read by others, no check-then-act. The moment you need read-decide-write as one unit — double-checked locking, lazy init, compareAndSet — a bare volatile is insufficient, because JIT reordering can expose a partially-constructed object.

04

Atomics & explicit locks

AtomicInteger c = new AtomicInteger(0);
c.incrementAndGet();          // atomic, no lock
c.getAndIncrement();          // returns old, then increments
c.compareAndSet(5, 10);       // "if still 5, set 10"
c.updateAndGet(x -> x * 2); // read-compute-write, atomic

LongAdder adder = new LongAdder();   // high-contention counting
Trade-off — CAS is not free

Atomics are optimistic: every thread proceeds, and a conflict causes a retry rather than a block. Under low-to-moderate contention this beats a lock, because no thread sleeps. Under high contention the retries spin and can underperform a lock that simply queues — which is why LongAdder exists, striping counters across cells to cut CAS traffic. The cost: sum() is dearer than AtomicLong.get(), so it is not a drop-in replacement when you need an exact cheap read.

Two boundaries that catch people

Atomics protect one variable. An invariant spanning several fields — "decrement balance and increment available, together" — still needs a real lock.

computeIfAbsent runs under internal locks. A slow or blocking computation inside that lambda degrades concurrent throughput on the whole map, and can deadlock against other operations on it. Keep those lambdas pure; look the value up outside the call.

Lock lock = new ReentrantLock();
lock.lock();
try {
    // critical section
} finally {
    lock.unlock();      // MUST be here
}

Interview trap — the lock that is never released

An exception mid-critical-section without a finally leaves the lock held forever, and every thread waiting on it blocks forever. This is structurally impossible with synchronized — the strongest argument for the implicit form in simple cases.

Trade-off — ReadWriteLock, and is a Lock just better?

ReadWriteLock suits caches and config read constantly and written rarely, where a plain lock would serialise readers that do not conflict. Flips on: write-heavy workloads, where its bookkeeping exceeds the read-concurrency benefit.

More broadly, ReentrantLock is not simply better. For a short critical section, synchronized is simpler, cannot leak a lock, and is JIT-optimised to near-equivalent performance. The explicit lock earns its cost only when you use a capability from the table above.

05

Coordination utilities

NeedUseKey property
Cap concurrent access to NSemaphore A lock generalised from 1 holder to N. Always release() in a finally — a missed release is a permanent permit leak
Wait for N tasks to finish, onceCountDownLatch One-shot. Workers call countDown(), other threads await(). Never resets
Make N peers meet repeatedlyCyclicBarrier Reusable. The same threads both work and await(). Exact party count required up front
Interview trap — latch vs barrier

The distinction is structural, not behavioural. CountDownLatch separates roles — workers count down, others await, and the count never returns. CyclicBarrier makes participants mutual peers — the same N threads all await() each other, and the barrier resets.

Classic answers: latch to hold startup until five initialisation tasks finish; barrier for a parallel simulation where phase one must complete before any thread starts phase two.

A CountDownLatch past zero is inert — further countDown()s are no-ops and await() returns immediately. A latch constructed per-class rather than per-test lets every later test pass trivially.

Semaphore permits = new Semaphore(3);
permits.acquire();
try {
    // at most 3 threads EVER in this block at once
} finally {
    permits.release();     // not releasing is a permanent leak
}

The production use is capping concurrent calls to a rate-limited downstream — a third-party API, or a connection pool whose ceiling is independent of your executor size.

06

Failure modes

Must remember — deadlock prevention

Deadlock requires all four Coffman conditions simultaneously: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one and it cannot happen.

The standard practical technique is a single global lock-acquisition order agreed across the whole codebase — always take the lower-ordered lock first. Circular wait then becomes structurally impossible rather than merely unlikely. This is the answer interviewers are almost always fishing for.

Four ways a class becomes thread-safe
StrategyHowExample
ImmutabilityNo mutable state to race onString, wrappers, records
SynchronizationLocks enforce exclusive accesssynchronized, Lock
Lock-freeCAS with optimistic retryAtomicInteger, ConcurrentHashMap
ConfinementState never actually sharedThreadLocal, request-scoped objects

Thread-safe means correct under concurrent access with no external synchronization required by the caller. Confinement is the one candidates forget to name, and it is frequently the right answer — a per-thread session needs no lock at all.

BlockingQueue<Task> queue = new LinkedBlockingQueue<>(100);  // bounded

// Producer
void produce(Task t) throws InterruptedException {
    queue.put(t);        // blocks when full
}

// Consumer
void consume() throws InterruptedException {
    Task t = queue.take();  // blocks when empty
}
Interview trap — if you must hand-roll it

Pre-java.util.concurrent this was wait/notify inside synchronized, and the condition check is while, never if — a spurious wakeup can occur with no notify at all, and a single check lets the thread proceed on a stale condition. Interviewers may ask you to demonstrate the manual version to show you know the primitives. The production answer is always BlockingQueue.

Production scenario — the hung batch job

Problem: a hand-rolled producer-consumer occasionally hangs under load. Investigation: dump shows consumers in WAITING with a non-empty buffer. Root cause: if (buffer.isEmpty()) wait(); — a spurious wakeup let a consumer proceed against a stale check. Solution: BlockingQueue. Prevention: never hand-roll wait/notify in new code.

07

Running it in production

Take a thread dump first

The universal first step for "service appears hung", because one dump separates the failure modes that look identical from outside:

  • Circular BLOCKED chain — deadlock. A merely slow service is not this.
  • All workers WAITING on a pool queue — pool starved; threads are blocked on I/O, not computing.
  • Many RUNNABLE at low CPU — I/O or scheduling, not a hot loop.
  • One thread genuinely working — no concurrency bug, just slow work.
Trade-off — sizing the pool

Derive it: Little's Law, concurrency = arrival rate × service time. Recording the assumption lets a future engineer re-derive the number when a dependency's latency changes, rather than re-guess it.

Sizing to core count suits CPU-bound work. Against blocking I/O, threads are idle most of the time, so size by the concurrency the downstream can absorb, not by availableProcessors(). A core-sized pool on I/O-bound work is the classic cause of starvation under load.

Trade-off — daemon threads

Non-daemon threads keep the JVM alive after main() returns, and executor threads are non-daemon by default — so a forgotten shutdown() is what actually hangs a process. The cost: a daemon thread can be killed mid-execution when the JVM exits, so cleanup that must complete belongs on a non-daemon thread or a shutdown hook.

An uncaught exception kills only its own thread, not the JVM — but it vanishes if nothing is watching. Periodic scheduled tasks that throw stop repeating, which is a frequent cause of a "the job just stopped" incident.
