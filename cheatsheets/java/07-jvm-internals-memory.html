If you only remember five things

  1. Only the reference lives on the stack; the object always lives on the heap. For StringBuilder sb = new StringBuilder(), sb is a slot in the method's frame — the StringBuilder it points to is on the heap, whether the reference was a local, an instance field, or a static field.
  2. Metaspace replaced PermGen in Java 8 and, unlike PermGen, is unbounded by default. It grows into native memory outside -Xmx, so a classloader leak consumes host memory that heap-only monitoring never sees. Capping it with -XX:MaxMetaspaceSize converts a silent host-level kill into a debuggable OutOfMemoryError.
  3. Class identity is the pair (class loader, fully-qualified name). Two loaders loading the same class name produce two incompatible types — which is exactly what ClassCastException: X cannot be cast to X means, and it is not a compiler bug.
  4. HotSpot's GC is tracing from GC roots, not reference counting. An unreachable cycle is collected; the cost is that reachable garbage is not, and no amount of heap size fixes an application that still holds a reference.
  5. OutOfMemoryError: Unable to create new native thread is not a heap problem. The OS refused another native thread, so -Xmx does nothing for it — look at the thread pool bounds and the OS thread limit instead.

01

Runtime data areas

Areas are shared across the process or per-thread, one per thread. Almost every memory question reduces to which list an item is on.

Interview trap

"The StringBuilder is on the stack" is wrong. The variable is a slot in the frame; the object is on the heap. Stack frames are popped in O(1) with no GC involvement at all — which is exactly why stack memory is fast, and why it can never hold the object.

Must remember — PermGen vs Metaspace

Metaspace replaced PermGen in Java 8. PermGen had a fixed maximum, so OutOfMemoryError: PermGen space was a normal sight in Java 7 app servers that reloaded classes. Metaspace grows into native memory and is unbounded unless you cap it with -XX:MaxMetaspaceSize — a change that moved the failure from a visible exception to a host-level OOM kill.

Scaling reality check — the container limit is not -Xmx

Metaspace, thread stacks, the code cache, and direct ByteBuffers are all outside -Xmx. A container whose limit equals -Xmx gets OOM-killed by the kernel while the JVM's own heap metrics still look healthy. Leave a deliberate gap, and budget heap, Metaspace, thread count, and a native buffer as four separate lines.

Thread count is a memory line, not just a concurrency one: every thread reserves its own stack, megabyte-scale by default, so a pool sized by core count alone is under-provisioned in a memory-constrained container.

02

Class loaders

A class is not identified by its name.

LoaderLoads fromWritten inParent
Bootstrapjava.base and core JDK modulesNative — not a Java object in older JVMsNone
PlatformOther JDK platform modules (was Extension pre-9)JavaBootstrap
ApplicationYour classpath or module pathJavaPlatform

Delegation is parent-first: check the cache, then the parent recursively, and load it yourself only if no ancestor can. A request for java.lang.String is answered by Bootstrap, not by the loader that received it.

Interview trap — what delegation prevents

Parent delegation is a security and consistency mechanism, not a convenience. Define your own java.lang.String and try to load it: Bootstrap answers first and your class is unreachable. Modern module encapsulation blocks the attempt outright on top of that. The legitimate exceptions are child-first delegation in app servers and plugin systems, and overriding loadClass() to skip the parent — both deliberate, both unusual.

class PluginClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytecode = readFromPluginJar(name);
        return defineClass(name, bytecode, 0, bytecode.length);
    }
}
Must remember — the loader is the leak, not the classes

A classloader becomes collectable only when it is unreachable and every class it loaded is unreachable — one lingering static field or one thread still running plugin code pins the whole graph. That is why hot redeploys in a long-running app server climb in Metaspace monotonically.

Two consequences worth stating out loud: Metaspace is reclaimed by class unloading, not by the young/old generational cycle, and two loaders of the same class mean two Metaspace entries for it.

03

Object creation & memory layout

new Foo() runs a fixed sequence:

  1. Load the class if not already loaded.
  2. Allocate a zeroed heap block: header plus all fields.
  3. Write the header — klass pointer into Metaspace, and a mark word for identity hash, GC age, and lock state.
  4. Run super(), then field initializers, then the constructor body.
  5. Return the reference.
Every object on the heap, HotSpot 64-bit
PartSizeContains
Mark word8 bytesIdentity hash (lazily computed, then cached), GC age, lock state
Klass pointer4 bytes compressed, else 8Pointer to the class metadata in Metaspace
Instance dataVariableThe field values, in a JVM-chosen order
Padding0–7 bytesRounds the object up to a multiple of 8
Interview trap — an empty object still costs 16 bytes

Twelve bytes of header with compressed pointers, rounded up to 16. It is small, but it is not free, and it is what makes a collection of millions of tiny wrappers — or every boxed primitive in a hot loop — a real line item on the heap.

Two related ones: the JVM is free to reorder fields for alignment, so declaration order is not layout, and the identity hash lives in the mark word precisely so it survives the GC moving the object during compaction.

Allocation is usually lock-free: each thread pre-reserves a TLAB — a small private chunk of Eden — so the common case is a pointer bump inside its own buffer. The cost is slow-path allocation and TLAB refill under heavy contention, so cutting per-request allocation pays off.

Two cases bypass the TLAB: objects too large for a sensible buffer, and — on some collectors — very large objects allocated straight into the old generation or a dedicated large-object area. An object can reach old age without ever surviving a Minor GC.

04

GC fundamentals

An object is garbage when it is unreachable from any GC root — stack variables, static fields, JNI references. The collector traces from those roots, marking everything transitively reachable as live.

Interview trap — it is not reference counting

There is no per-object count, so an unreachable cycle is collected rather than leaked. The flip side is the part candidates miss: a reachability GC cannot know that a reachable object is *logically* dead, which is the whole definition of a leak in Java.

The generational hypothesis — most objects die young — is the one empirical claim the heap layout rests on.

TermScopeWhat it tells you
Minor GCYoung generation onlyFast, frequent, and healthy on its own. Frequency tracks allocation rate
Major GCOld generation, collector-dependentTerminology varies by collector and by JDK doc; do not lean on the distinction
Full GCEntire heap, plus MetaspaceThe expensive one. Frequent Full GCs mean the old generation is filling faster than it should
Trade-off — diagnosing a pause

Rising Minor GC frequency with flat pause duration points at allocation rate. Rising Minor GC duration at stable frequency points at a growing live set. A full pause points at promotion or leak. Flips on: which of the two numbers moved — collapsing them into one "GC is getting worse" signal loses the diagnosis.

05

Collectors & tuning

Choosing a collector
CollectorApproachPick it when / when it bites
SerialSingle-threaded, stop-the-worldSmall heaps, single core, CLI tools. Pauses scale with heap
ParallelMulti-threaded stop-the-worldThroughput-first batch work where pause time does not matter. Was the default before Java 9
CMSMostly concurrent, no compactionFragments, and is removed in modern JDKs. Do not carry its flags onto G1
G1Fixed-size regions, most-garbage first, mostly concurrentThe default since Java 9. Still not generational in the contiguous-Eden sense, and still has STW root scanning
ZGC / ShenandoahFully concurrent, compaction includedVery large heaps with a hard latency budget. Trades some raw throughput for it
Two traps in one sentence

Parallel GC is not the default — G1 has been since Java 9, and CMS has been removed outright, so migrating off it means re-deriving your flags rather than carrying them over. Concurrent does not mean pause-free: G1 and ZGC both still stop the world for root scanning, and ZGC's sub-millisecond pauses are a design property, not a guarantee you inherit by choosing it.

Tuning optimises for at most two of throughput, latency, and footprint, which is why "the modern default" is a starting point, not an answer. -XX:MaxGCPauseMillis is a goal G1 adapts its collection scope toward, not a promise: set it implausibly aggressive and G1 collects more often and smaller without hitting the target, costing throughput for nothing.

java -Xms4g -Xmx4g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:MaxMetaspaceSize=256m \
     -XX:+HeapDumpOnOutOfMemoryError \
     -jar orders-service.jar
Must remember — -Xms equal to -Xmx

Deliberate and common in production. It removes heap-resize pauses, at the cost of committing the full heap up front. It is not a universal win — for a genuinely short-lived tool, JVM ergonomics may be the better answer, and a resource-constrained container may prefer a smaller committed heap over predictable sizing. Also worth knowing: -Xmx is a hard cap, and a max below the min fails at startup.

Scaling reality check — the first fix is not a flag

Before tuning anything, cut the allocation rate. Fewer, smaller, shorter-lived objects mean less GC work under any collector, and they often remove the need for the tuning entirely. -Xmn is worth reaching for when there is a large volume of short-lived garbage, but a bigger young generation is not free: each Minor GC scans a larger Eden, and less heap is left for the old generation.

Negatively framed, because teams get this wrong: well-intentioned tuning can make a service worse. Tune against measured GC logs from a production-like load, not a benchmark of somebody else's workload.

06

Memory errors

A leak in a garbage-collected language is not a missing free() — it is an object that stays reachable long after the application stopped needing it. The collector is behaving correctly; the references are the bug.

PatternWhy it holds the reference
Unbounded static collectionStatic fields live for the class's whole lifetime; nothing ever evicts
Listener registered, never removedThe registering object holds the listener, which holds everything it captured
ThreadLocal in a pooled threadPool threads are reused forever, so the value persists across unrelated requests
Non-static inner classSilently retains the enclosing instance and its whole graph
Classloader leakOne live reference pins the loader, its class metadata, and its statics
 
private static final ThreadLocal<RequestContext> CTX = new ThreadLocal<>();

void handle(Request req) {
    CTX.set(new RequestContext(req));
    try {
        service(req);
    } finally {
        CTX.remove();   // the pooled thread outlives this request
    }
}
Must remember — the OOM variants are different incidents

Java heap space is the heap full and GC cannot free enough. Metaspace means the cap was hit, usually a classloader leak. GC overhead limit exceeded is the JVM giving up rather than let it grind — over 98% of time in GC while reclaiming under 2%. Unable to create new native thread is the OS refusing a thread, and -Xmx is irrelevant to it. StackOverflowError is an Error, not an OOM at all.

For the thread variant, the fix is on the concurrency side — see Volume 6 on why the cached-pool factory grows without limit. This page will not restate it.

StackOverflowError is one thread exceeding its fixed stack. Unbounded recursion is the usual cause, but so is legitimately deep input: deeply nested JSON overflows where a flat payload of the same size does not, which is why it survives testing. Raising -Xss buys depth; an explicit heap-allocated stack changes the bound, because the heap is far larger than the per-thread stack.

// depth bounded by -Xss
static void flatten(Node n, List<Node> out) {
    if (n == null) return;
    flatten(n.left, out);
    out.add(n);
    flatten(n.right, out);
}

// depth bounded by heap
static void flattenIterative(Node root, List<Node> out) {
    Deque<Node> stack = new ArrayDeque<>();
    stack.push(root);
    while (!stack.isEmpty()) {
        Node n = stack.pop();
        if (n == null) continue;
        out.add(n);
        stack.push(n.right);
        stack.push(n.left);
    }
}
Interview trap — don't reach for the heap first

Raising -Xmx on a real leak only delays the same crash and makes the eventual one larger and harder to read. Catching OOM and clearing a cache to "recover" is worse: by then other threads may have failed mid-operation, and the JVM is in a degraded state. Diagnose which variant occurred, then fix the cause.

The diagnostic path is a heap dump, taken before the restart, since restarting destroys the evidence. Look for unexpectedly high retained size rather than shallow: a small object holding a large collection is the classic culprit, and it is invisible to a shallow-size view. Trace the GC root path back to the reference keeping it alive. One dump is a snapshot; two taken apart show what is growing — the actual signature of a leak.

Trade-off — evidence against uptime

A heap dump costs disk and write time at the worst possible moment, and a full disk silently produces no dump at all. Take it anyway: an OOM with no dump is an incident nobody can learn from. The same logic favours trend alerts on instance counts and on sawtooth (rise, drop, rise) rather than staircase (rise, partial drop, rise higher) memory shape — the staircase is a leak, and it is visible long before the crash.

The full incident workflow — dashboards, runbooks, postmortems, capacity review — is Volume 9's. What belongs here is the mechanism: which area failed, what kept the object reachable, and which flag bounds it.
