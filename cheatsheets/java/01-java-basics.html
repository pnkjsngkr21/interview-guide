If you only remember five things

  1. Java is compiled and interpreted. javac compiles source to bytecode; the JVM then interprets that bytecode and JIT-compiles hot methods to native code at runtime. Answering either half alone signals a shallow reading.
  2. "Write once, run anywhere" is a property of the bytecode, not the JVM. The JVM is native software compiled per OS and architecture — which is exactly what makes the bytecode above it portable.
  3. Java is unconditionally pass-by-value. For an object argument the value copied is the reference, so mutation is visible to the caller and reassignment of the parameter is not. "Pass-by-reference for objects" is the single most common wrong answer in the language.
  4. You cannot shadow java.lang.String with your own class, and the reason is structural, not stylistic: class loading is parent-first, so the Bootstrap loader's copy is always found first.
  5. Never use double for money, and never assume an int key is big enough. Binary floating point cannot represent decimal fractions exactly; int stops at about 2.1 billion, a ceiling real systems have hit and paid a painful migration for.

01

Java and the execution model

Interview trap — "is Java compiled or interpreted?"

Both, and the answer has two halves. Source to bytecode is compilation, done by javac. Bytecode to machine code at runtime is interpretation plus JIT. Reject the adjacent claim too: the bytecode is portable, not the JVM — the per-platform JVM is what makes that portability possible.

Interpreter and JIT are not alternatives — they run in the same process
InterpreterJIT compiler
Startup costNone — starts executing immediatelyNeeds profiling data first
Steady stateSlower, re-decodes bytecode every callNear-native
Applies toCold code, first invocationsHot methods after warm-up
Implemented by—C1 (fast compile) and C2 (aggressive: inlining, escape analysis, devirtualisation)
Scaling reality check — the warm-up cliff

Every freshly started pod serves its first requests through the interpreter. The first requests after a deploy run 2-10x the steady-state p99, then flatten as C2 compiles the hot paths — which is why a canary's first-minute latency can look like a regression when nothing regressed.

  • Also degrades later. C2 optimises on optimistic assumptions; when one breaks the JVM falls back, reprofiles, and recompiles — a latency spike in a long-running process.
  • Worse in containers. Compiler threads compete for CPU with application threads, so a small CPU limit steepens the curve, and interpreted code allocates more, adding GC pressure early on.
  • Flips on: processes living longer than about five minutes should stay on HotSpot; short-lived or scale-to-zero workloads want GraalVM native-image, whose ahead-of-time compilation removes warm-up entirely at the cost of peak throughput and explicit reachability metadata for reflection.

-XX:TieredStopAtLevel=1 stops at C1 and suits short-lived processes; -Xint disables the JIT, which is a debugging tool and never a performance one. Timing a single call in main() measures the interpreter, not the JVM — use JMH.

02

JDK, JRE & class loading

Nested, not interchangeable — each one is the one before it plus more
ComponentAddsWho needs it
JVMClass loader, runtime data areas, execution engineAnyone running bytecode
JREJVM + core class librariesRunning a compiled app
JDKJRE + javac, javadoc, jar, jshell, jlinkWriting or compiling Java
Interview trap — "I downloaded the JRE"

Since Java 11 Oracle has not shipped a standalone JRE download — you install a JDK even to run. The nesting is conceptually correct; the distribution is not. The related trap is saying the JVM compiles Java to bytecode: javac does that.

The three phases are independent of the delegation chain: loading and linking can complete while initialization is still pending. Initialization happens on active use — instantiation, a static method call, or a static field read that is not a compile-time constant — and Class.forName() triggers it by default, unlike some other loading APIs. Preparation is where static fields get their defaults (0, null, false) before any static initializer overwrites them.

Must remember — when the class loader becomes your problem

It is abstracted away only until it is not. Plugin systems and app servers load each plugin in its own loader precisely to isolate conflicting dependency versions. Two failure modes to recognise on sight: ClassCastException: Foo cannot be cast to Foo means the same class was loaded twice by two loaders and they are genuinely different types; OutOfMemoryError: Metaspace in a hot-redeploying server means old classloaders are being retained. Metaspace replaced PermGen after Java 8 and grows into native memory unless capped with -XX:MaxMetaspaceSize.

Everything that is not a primitive is a reference type holding a pointer-like value to a heap object, default null. String is a class, not a primitive, however much the compiler special-cases it.

Interview trap — narrowing truncates, it never rounds

A narrowing floating-point to integral conversion drops the fractional part toward zero, so (int) 3.99 is 3, not 4; and a narrowing integral conversion wraps the bit pattern, so (byte) 130 is −126 — not an exception, not a clamp.

Widening can lose precision too. Promoting a large long to float needs no cast and still discards digits, because widening is a statement about range, not precision. And byte/short arithmetic silently promotes to int, so byte c = b + b; does not compile.

int i = 130;
byte b = (byte) i;          // -126 — wraps, does not clamp
double d = 3.99;
int truncated = (int) d;    // 3    — truncates toward zero
long big = 9_000_000_000L;
float lossy = big;          // compiles with no cast, still loses digits
byte sum = (byte) (b + b);  // the cast is required: b + b is an int
Must remember — the two field-type decisions that reach production

Never double for money. Binary floating point cannot represent values like 0.1 exactly, and the error compounds. Use BigDecimal, stating the scale and rounding mode explicitly on every operation — an ArithmeticException from an unspecified divide() and a silent equals() mismatch between 1.0 and 1.00 are both reconciliation bugs. Build it from new BigDecimal("0.1"), never new BigDecimal(0.1), which bakes in the double's error before you start.

Never size an identifier as int on hope. The ceiling is about 2.1 billion, and auto-increment primary keys have genuinely reached it in production, forcing a migration to BIGINT. The same argument rules out byte for counters, which overflow almost immediately at request volume.

Wrapping, the Integer cache range, and boxed-value collections belong to Volume 3 and Volume 4.

04

Variables

Three kinds of variable, three different lifetimes
KindLives inDefault?Fails when
LocalThe thread's stack frameNo — the compiler requires definite assignment Reading one before assignment is a compile error, not a zero
InstanceHeap, inside each objectYes — 0 / null / false Nothing at declaration; the field survives as long as the object is reachable
StaticMetaspace, one copy per classYes Nothing, and it is never re-initialised per instance — one shared value for the class's whole life

Two distinctions that get collapsed. Scope is where the name is legal to write; lifetime is when the memory exists — for a local they track together, but a lambda can capture a value that outlives the frame it was declared in. And final is not immutability: it stops the variable being reassigned while the object it points at stays mutable, so a final List can still have elements added.

Interview trap — why lambda captures must be effectively final

The lambda may run on another thread, or after the enclosing method has returned, so the JVM copies the value in rather than sharing the stack slot. Reassignment would make the copy and the original disagree with no way to reconcile them, so any reassignment anywhere in the method is a compile error.

The mirror-image bug is a constructor parameter shadowing a field: assign without this. and you have written param = param — the field silently keeps its default value.

Production scenario — the singleton field that leaks users

Problem: one user's request-scoped data appears on another user's screen, intermittently. Investigation: the data is held in a field of a Spring @Service, which is a singleton — so concurrent requests share it. Root cause: a fundamentals misunderstanding about where instance state lives and who else can see it. Solution: a local variable, a method parameter, or request-scoped storage. Prevention: make the field final where possible and lint non-final static state outright — mutable shared state is a disproportionate source of concurrency bugs relative to its convenience. The same shape appears as an unsynchronised static counter silently losing increments under load.

Operators

Six operators whose exact behaviour is worth having ready

Interview trap — & and | are legal on booleans

On boolean operands they are logical operators that do not short-circuit, so both sides always evaluate. A null guard written with & is an NPE waiting to happen, and an OR of permission flags becomes a set of expensive checks — a possible database round trip — that always run.

The narrow legitimate exception: deliberate & to guarantee a side effect runs regardless of the boolean's value.

if (user != null && user.isActive()) { ... }   // safe
if (isValid(a) & isValid(b))        { ... }   // both calls run, always

int x = 5;
// x++ yields 5 and sets x = 6; ++x then sets x = 7 and yields 7
x = x++ + ++x;   // 12

Compound assignment (+=, |=) carries an implicit narrowing cast, and pre- versus post-increment differ in the value the expression yields, not the variable's final state — which is why chained increments compile, read terribly, and produce off-by-one bugs that survive review.

06

Control flow

// Classic statement — falls through to the next case with no warning
switch (day) {
    case MONDAY:
    case TUESDAY:
        send("Early week");
        break;              // omit this and TUESDAY's body runs too
    case FRIDAY:
        send("Almost weekend");
        break;
    default:
        send("Other");
}

// Java 14+ expression — no fall-through, and it yields a value
String result = switch (day) {
    case MONDAY, TUESDAY -> "Early week";
    case FRIDAY           -> "Almost weekend";
    default               -> "Other";
};
Interview trap — a missing break is a silent bug

Fall-through is the default, so an order-status handler missing one break silently executes the next case's logic — the status transitions through states nobody wrote. Java 14's arrow syntax exists specifically to remove this footgun: each case is self-contained, and the whole thing becomes an expression that can be assigned or returned. Migrating a legacy switch is worth doing for exactly this reason.

The companion question is when default can be omitted: the compiler can prove an enum or sealed switch exhaustive, but not one over int.

Loop selection, and the one that is guaranteed to surprise
LoopCondition checkedRuns at least once?Use for
forBefore each iterationNoKnown count, index access
whileBefore each iterationNoCondition-driven, count unknown
do-whileAfter each iterationYes, always"Run once, then check" — a batch job that processes an empty queue still executes its body
for-eachVia IteratorNoTraversing without an index

Two structural features worth naming on sight: a labelled break outer; exits the tagged loop from any nesting depth, where a plain break leaves only the innermost one; and mutating a collection inside a for-each loop throws ConcurrentModificationException, because the iterator tracks a modification count that structural changes invalidate. That exception is not perfectly reliable — removing the second-to-last element can slip past the check — so it is a reason to use removeIf() or the iterator's own remove(), not a guarantee. Iterator mechanics live in Volume 4.

Methods

static void mutate(StringBuilder sb) {
    sb.append(" world");     // same object the caller holds — visible
}

static void reassign(StringBuilder sb) {
    sb = new StringBuilder("other");  // only the local copy moves
}
Overload resolution, in the order the compiler applies it
RuleConsequenceFailure mode
Exact match winsResolution uses the static types of the arguments, at compile time Calling the wrong overload looks fine and dispatches wrongly at runtime if the argument's type is wider than expected
Widening beats boxingWith only print(long) and print(Integer), print(5) picks long Overloads that differ only by boxing are a genuine ambiguity hazard in review
Return type is not a signatureYou cannot overload by changing only the return type — a compile errorReaching for a name like getOrCompute() to force the issue
Varargs is lastMust be the final parameter, only one per method; calling with zero arguments yields an empty array, not an error An empty-varargs call reaching a sum() returns 0 and looks like a silent data-loss bug

A static method belongs to the class, cannot be overridden — a same-signature method in a subclass only hides it, resolved at compile time from the reference type — and cannot reference this. Recursion needs a reachable base case; without one the result is StackOverflowError, an Error and not an Exception, so catch (Exception e) will not catch it. Recursion is a reasonable choice when the input's maximum depth is genuinely bounded and known; it is the wrong default for user-supplied nesting.

08

Arrays

Interview trap — array equals and asList

arr.length is a public final field, not a method — the opposite of String.length() and List.size(). And arrays do not override equals, so a == b and a.equals(b) are both reference comparisons and both return false for two equal-content arrays. Use Arrays.equals(), Arrays.deepEquals() for nested arrays, and Arrays.toString() — a bare array printed gives you [I@1a2b3c.

Arrays.asList(arr) returns a fixed-size view backed by the array: set() works and writes through to the array; add() and remove() throw UnsupportedOperationException.

Two decisions the type system does not make for you
ArrayCollection
SizeFixed at creation; resizing is copy-and-replaceResizable
PrimitivesHeld directly, no boxing, cache-friendlyRequires wrappers
Type safetyCovariant — a runtime riskInvariant and checked at compile time
CostLower overhead, minimal APIMore overhead, rich API

Java has no true multidimensional array: int[][] is an array of arrays, so each row can have a different length and each row is a separate heap object. The performance case for primitive arrays is narrow — a genuinely hot numeric path where the boxing and pointer-chasing of a List<Double> dominates. The same logic applies to flags: a boolean[] typically costs a byte per element, so a BitSet is far more compact for millions of flags.

09

Strings

Must remember — why String is immutable

Every "modifying" method returns a new object and leaves the original untouched, so s.toUpperCase(); with the result discarded does nothing. Immutability is what makes four things work at once: the string pool can share objects safely, an immutable value is inherently thread-safe with no synchronization, class names, paths and credentials cannot be validated and then mutated behind the validator's back, and hashCode() is computed once and cached — which is why String is a fast HashMap key.

String a = "hello";
String b = "hello";
a == b;                     // true  — literals share one pooled object
String c = new String("hello");
a == c;                     // false — new always bypasses the pool
a.equals(c);                // true  — same content
c.intern() == a;            // true  — intern returns the canonical instance

== on strings compares references, always. It appears to work for two literals only because of pool sharing, and stops working the moment one side came from new, a parameter, or runtime-built data — so the same comparison can be true in one line and false in the next. a.equals(b) throws NPE if a is null, so prefer Objects.equals(a, b), or put the literal on the left. And final String is a different concept: it prevents reassigning the variable, not mutating an object.

// O(n^2) — a new String on every iteration
String result = "";
for (int i = 0; i < 1000; i++) {
    result += i;
}

// O(n) — mutates one internal buffer
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.append(i);
}
String, StringBuilder, StringBuffer
StringStringBuilderStringBuffer
Thread safeYes, by immutabilityNoYes, synchronized methods
Repeated appendQuadraticLinearLinear, plus lock overhead
Use forFixed or rarely-changing textLocal string building, loopsGenuinely shared buffers, rarely
Interview trap — where the compiler helps, and where it does not

The compiler optimises simple single-expression + concatenation into a StringBuilder itself, so hand-rolling one for "a" + b + c is ceremony. It cannot do that inside a loop, which is why concatenation in a hot loop is a repeatedly-flagged code-review finding — it degrades to quadratic time and drags GC churn behind it. The same eager-evaluation problem applies to a concatenated argument inside a log-level guard: the string is built even when the level would discard it, so use the logging framework's parameterized form.

Two older traps with a version attached: pre-Java 7, substring() shared the original char[], so a tiny substring could retain a huge string in memory — Java 7+ copies, fixing the leak at a small cost. And trim() only strips characters at or below U+0020; strip() (Java 11+) is Unicode-aware and is what a Unicode-whitespace bug report is asking for.

String.valueOf(null) produces the literal "null" rather than throwing — which is how a cache key built from a boxed nullable ID silently collapses every null case onto the same entry.
